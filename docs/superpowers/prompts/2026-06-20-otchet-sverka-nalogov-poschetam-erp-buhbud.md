## Источники сверки (РЕШЕНИЕ: оба регл. Хозрасчетный 64x/65x)

### ЕРП-сторона (регл. бухучёт, ЛОКАЛЬНЫЙ запрос — НЕ COM!)
`РегистрБухгалтерии.Хозрасчетный.ОстаткиИОбороты(&НачалоПериода, &КонецПериода, , , Счет В ИЕРАРХИИ(&Счета), , )`, где `&Счета = массив ссылок ПланыСчетов.Хозрасчетный.НайтиПоКоду("641")/("642")/("651")` (иерархия покроет 6411/6412/6413/6414/6415/6417/642/651 и субсчета), фильтр `Ост.Организация.КодПоЕДРПОУ В (&МассивЕДРПОУ)`, разрез **Счёт.Код**, сальдо `СуммаКонечныйОстатокКт − СуммаКонечныйОстатокДт` (Кт−Дт, пассив-плюс), начальный аналогично, обороты `СуммаОборотКт`(Начислено)/`СуммаОборотДт`(Уплачено). **БЕЗ COM** — это та же база. **БЕЗ НДФЛ-схлопывания.**

> ВАЖНО: pre-тестом ЗАФИКСИРОВАТЬ, какие организации реально присутствуют в ЕРП Хозрасчетном по налоговым счетам. Если регл.учёт ЕРП ведётся только по своей орг (40645273), а BuhBud-сторона агрегируется по 3 орг — это даст расхождение (by-design сигнал, не баг). Отразить это в Help.

### BuhBud-сторона (регл. бухучёт, через COM) — 1:1 как в эталоне
`РегистрБухгалтерии.Хозрасчетный.ОстаткиИОбороты(&НП, &КП, , , Счет.Код В (&Счета), , )` где `&Счета` — массив строк-кодов `"6411","6412","6413","6414","6415","6417","642","651"` (V83-массив; на стороне BuhBud надёжнее фильтр по `Счет.Код В (...)`), фильтр `Ост.Организация.КодПоЕДРПОУ В (&МассивЕДРПОУ)`, разрез **Организация.КодПоЕДРПОУ + Счёт.Код**, сальдо Кт−Дт, обороты ОборотКт/ОборотДт. ТЗ — **только примитивы** (Счёт.Код строка + числа) → `ЗначениеВСтрокуВнутр`. После выгрузки в ЕРП — агрегация по **Счёт.Код** (орг схлопывается).

**Карта Счёт.Код → ВидНалога** (только для описательной колонки-метки; 1:1 с обработкой переноса `_ТипНалогаПоСчету`): 6411→НДФЛ, 6412→НДС, 6413→НалогНаПрибыль, 6414→ЕдиныйНалог, 642→ВоенныйСбор, 651→НачисленныйЕСВ, **6415/6417/прочее→ДругиеНалоги**. Для субсчетов мапить по префиксу (СтрНачинаетсяС). ВидНалога — `Строка` (метка), НЕ EnumRef (счёт первичен).

### Орг-фильтр
`А_ВБалансе` есть **только в ЕРП**. ERP-side: `ВЫБРАТЬ Орг.КодПоЕДРПОУ ИЗ Справочник.Организации ГДЕ Орг.А_ВБалансе И Орг.КодПоЕДРПОУ<>""` → массив 3 орг (40645273, 41597184, 44590697) → передать в обе стороны (ЕРП-фильтр и BuhBud-фильтр). **Организация в строки НЕ выводится** — только фильтр.

## Архитектура обмена счетов (ЕРП ↔ BuhBud) — почему сверка по Счёт.Код корректна

Правила обмена `_Rarzrabotki/ExChange/ПравилаОбменаДаннымиЕРПБух/ExchangeRules.xml` (правило конвертации с кодом **`Хозрасчетный`**, `Источник/Приемник = ПланСчетовСсылка.Хозрасчетный`) синхронизируют план счетов **1:1**:
- `СинхронизироватьПоИдентификатору=true` — один и тот же счёт имеет **одинаковый GUID** в обеих базах;
- **поле поиска `Поиск="true"` на реквизите `Код`** — при обмене счёт идентифицируется **по Коду** (после GUID);
- блок `<Значения>` — таблица предопределённых счетов **идентична** (Источник = Приемник, напр. `Амортизация→Амортизация`); **никаких кастомных обработчиков / перекодировки** на счетах нет;
- передаются реквизиты `Код`, `Наименование`, `ЗапретитьИспользоватьВПроводках`, `ПометкаУдаления`;
- направление набора: Источник-имена = Бух (`Подразделения`, `Направления`), Приемник = ЕРП (`СтруктураПредприятия`, `НаправленияДеятельности`) ⇒ **загрузка Бух→ЕРП** (регл. Хозрасчетный ЕРП мирорится из BuhBud).

**Следствие для отчёта:** счёт `6411` в ЕРП и `6411` в BuhBud — гарантированно **один и тот же счёт** (обмен сам сопоставляет по Коду+GUID). Значит сверка по `Счёт.Код` идёт по **штатному ключу обмена**, а не по эвристике. `Разница≠0` или счёт-только-в-одной-базе = **пробел загрузки/обмена** (а не «разные планы счетов») — это и есть рабочий сигнал отчёта; отразить в Help. Источник-knowledge: `_Rarzrabotki/notebook/knowledge/exchange_erp_buhbud.md` (`ПланСчетовСсылка.Хозрасчетный→ПланСчетовСсылка.Хозрасчетный`).

## Сборка результата (merge в BSL по Счёт.Код)

- Ключ строки: `СокрЛП(Счёт.Код)`.
- Соответствие ключ→строка результирующей ТЗ; **FULL-merge**: счёт, присутствующий только в одной базе (или с Разница≠0), = **не-перенесённый / расхождение обмена** (обмен синхронизирует счета 1:1 по Коду — см. «Архитектура обмена счетов» — поэтому такой счёт это пробел загрузки, а НЕ «разные планы счетов»).
- Колонки результирующей ТЗ: измерение **Счёт**(Строка, код) + **ВидНалога**(Строка, метка по карте) + 4 показателя (НачальныйОстаток / Начислено / Уплачено / КонечныйОстаток), на каждый тройка **ЕРП / BuhBud / Разница (=ЕРП−Бух)** = 12 числовых.
- `ВнешниеНаборыДанных = Новый Структура("Налоги_Сравнение_Счета", ТаблицаСравнение)`.
- Знак: единая конвенция **Кт−Дт (пассив=плюс)** к ОБЕИМ сторонам. `.ОстаткиИОбороты` — `КонечныйОстатокКт − КонечныйОстатокДт`.
- Счёт — **строка Счёт.Код** (НЕ `ПланСчетовСсылка`). Обмен синхронизирует план счетов **1:1 по `Код`** (поле поиска `Поиск=true`) **+ GUID** (`СинхронизироватьПоИдентификатору`), identity, без перекодировки → `Счёт.Код` это **штатный ключ сопоставления обмена**, сверка по нему архитектурно корректна. Строку берём, чтобы не таскать кросс-базную ссылку `ПланСчетовСсылка` (объекты base-local даже при совпадающем GUID).

## СКД (Template.xml) — упростить относительно эталона
- dataSet `DataSetObject` `Local`, name/objectName=`Налоги_Сравнение_Счета`; поля: Счет(xs:string), ВидНалога(xs:string) + 4 тройки `xs:decimal Digits=15 FractionDigits=2 AllowedSign=Any`; `totalField` Сумма(...) на каждую числовую.
- Параметры: Период / НачалоПериода / КонецПериода (как у эталона).
- `settingsVariant`: группировка **плоско по Счет** (упорядочить по коду); БЕЗ группировки по организации; папки колонок по 4 показателям (Нач.остаток / Начислено / Уплачено / Кон.остаток), каждая с тройкой ЕРП/Бух/Разница. ВидНалога — выбранное поле в строке (рядом со Счётом).

## Дата / нюансы
- Дефолт периода — Custom `2025-12-01 .. 2025-12-31` (КонецПериода = КонецДня(31.12.2025)).
