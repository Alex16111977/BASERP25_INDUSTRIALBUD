# Prompt для нового сеанса ИИ: Доработка `Отчет.А_ОтчетPL` — параметр СКД `ВключатьДочерние`

> **Роль:** инженер BAS ERP 2.5 (CFO-level финансовой аналитики).
> **Языки в коде:** 1С:BSL (ru-ua), SQL запроса 1С, XML (Dxl/XDTO).
> **Окружение:** Windows, Git Bash, PowerShell 5.1, 1C:Enterprise 8.3.20+, MCP `1c-workerp`, Python 3.13 + pywin32.

## 0. TL;DR (what & why)

Добавить в `Отчет.А_ОтчетPL` параметр СКД **`ВключатьДочерние`** (тип `xs:boolean`). Параметр фильтрует только PL-часть запроса (`втPL` → условие `ТЧ.Ссылка.ВключатьДочерние = &ВключатьДочерние`). ЕРП- и Казна-части (регистры `ПрочиеРасходы`/`ФинансовыеРезультаты`/`ПрочиеДоходы`/`А_ДвиженияДенегИзКазны`) **не трогать** — они остаются фильтроваться через отбор СКД `Подразделение + НаправлениеДеятельности` (пользователь настроил сам, **менять эти настройки запрещено**).

Это решает задвоение в расшифровке документа 097 (ЦО, `ВключатьДочерние=Ложь`) из-за параллельного документа 096 (СВОД, `ВключатьДочерние=Истина`), у которых **одинаковые** `Подразделение` и `НаправлениеДеятельности`.

## 3. Проблема (конкретные данные из MCP)

За **февраль 2026** в базе есть два документа `А_ОтчетPL` с одинаковым `Подразделение` и `НаправлениеДеятельности`, но **разным `ВключатьДочерние`**:

| Номер | UUID | Подразделение | ПодразделениеСтрока | ВключатьДочерние | Направление |
|---|---|---|---|---|---|
| **096** | `0f95464e-3b5a-11f1-a2e8-ae822d4b0de9` | Производство | PL_Производство_СВОД | **`true`** | Производство |
| **097** | `0f95464f-3b5a-11f1-a2e8-ae822d4b0de9` | Производство | PL_ЦО_Производство | **`false`** | Производство |

Когда фин. открывает расшифровку документа **097** (ЦО), отчёт СКД применяет отбор через `ПользовательскиеНастройки`:
- `Подразделение = Производство` ✓
- `НаправлениеДеятельности = Производство` ✓

→ Оба документа 096 и 097 **проходят отбор** и склеиваются. Фин. видит сводные суммы вместо ЦО-разреза.

**Нужно:** отчёт должен показывать только **один** из двух, в зависимости от флага `ВключатьДочерние`.

## 4. Принятое архитектурное решение

**Параметр СКД `ВключатьДочерние`** (Булево). Фильтрует **только** `втPL` (PL-документ). На ЕРП/Казну **не влияет** (они остаются фильтроваться через отбор СКД по Подразделение/Направление).

### 4.1 Почему не другие варианты (контекст обсуждения с пользователем, не переделывать)

- ❌ **Вариант A — отбор `Документ` через `ПользовательскиеНастройки`.** ЕРП-регистры (ПрочиеРасходы, ФинансовыеРезультаты, ПрочиеДоходы) **не имеют** поля `Документ = А_ОтчетPL.Ссылка`. При таком отборе вся ЕРП-часть отфильтровывается → отчёт теряет факт.
- ❌ **Вариант B — параметр `&ТекущийДокумент` по ссылке.** При смене периода в форме отчёта параметр остаётся указывающим на документ старого периода → PL-часть пуста. Потребует авто-откат параметра = заплатка.
- ❌ **Вариант C — отбор `ПодразделениеСтрока` в СКД.** Меняет настройки отбора пользователя (запрещено).
- ❌ **Вариант D (поле в ТЗ вместо параметра).** ЕРП/Казна без связи с PL получили бы `NULL` в `ВключатьДочерние` → при отборе `= Ложь`/`= Истина` пропадают из отчёта.
- ✅ **Параметр СКД** — структурная семантика (не ссылка), не задевает ЕРП/Казну, работает при смене периода.

### 4.2 Почему параметр НЕ влияет на ЕРП/Казну — обоснование

Флаг `ВключатьДочерние` — **атрибут PL-документа** (как лист Excel). ЕРП-факт в регистре `ПрочиеРасходы` не имеет этого флага. Для фин. логично, что в расшифровке:
- PL-часть показывает только данные конкретного листа Excel (097 = ЦО без сводов).
- ЕРП-часть показывает **всё** по подразделению «Производство» за период — это фактическая «правда» для сверки.

Это соответствует кассовый vs начисление сверке, которую делает фин.

## 10. Что НЕ делать (антипаттерны по опыту проекта)

1. ❌ **НЕ выдумывать имена полей регистров.** Всегда `get_metadata_structure` сначала. Пример ошибки прошлого: `БДДС.Организация` не существует — поле только в Регистраторе.
2. ❌ **НЕ использовать `В ИЕРАРХИИ` внутри `СУММА(ВЫБОР КОГДА ...)`.** Запрещено в 1С. Альтернатива — `UNION ALL` с `В ИЕРАРХИИ` в `WHERE` каждого подзапроса. Источник: `MEMORY.md` раздел "В ИЕРАРХИИ inside aggregate functions".
3. ❌ **НЕ использовать подзапрос внутри агрегатной функции.** Та же ошибка.
4. ❌ **НЕ передавать имя ТЧ как `Движения`** — зарезервировано платформой (`Документ.Движения` — это коллекция движений по регистрам). В данной задаче не применимо, но запомни — в любых новых ТЧ.
5. ❌ **НЕ использовать русские COM-методы напрямую в Python** без `getattr(obj, "Имя")`.
6. ❌ **НЕ грузить `Form.xml` или `Module.bsl` формы напрямую через `db-load-xml -Partial`.** Будет ошибка "Неизвестный объект метаданных Document.X.Form.Y.Ext". Грузить через `Forms/ФормаДокумента.xml`. В этой задаче не применимо, но если дойдёт до правки формы — помни.
7. ❌ **НЕ править `Reports/А_ОтчетPL/` напрямую без предварительной прогонки через build-пайплайн.**
8. ❌ **НЕ менять настройки вариантов СКД** (внутри `<settingsVariant>` в Template.xml). Даже если кажется «там тоже нужно что-то поправить» — спроси пользователя.
9. ❌ **НЕ создавать новых .md, .bat, .py файлов** без явного запроса. Если нужно — Write только в явно указанные пути.
