# Дизайн: добавить счёт 665 в отчёт сверки А_ВзСС(Форма1) ↔ Бухгалтерия

> Дата: 2026-06-04. Тип: малое расширение внешнего СКД-отчёта (.erf). Период проверки: декабрь 2025.
> Рабочая папка: `C:\Configuration_downloads\BASERP25` (ветка `claude/bas-doc-skills`; Designer/erf-build работают отсюда).
> Отчёт: `_Rarzrabotki/Отчеты/А_СравнитьОстаткиВзаиморасчетыСотрудникиЕРПсBASБухгалтерия` (.erf + папка-исходник).
> Навыки: Rule #-1 (Python COM ПЕРЕД изменением запроса), `erf-build`, `verification-before-completion`.

## 1. Задача

В отчёт сверки ЕРП `А_ВзаиморасчетыССотрудниками` (Форма1) ↔ Бухгалтерия (BuhBud) добавить бухгалтерский
счёт **665** к текущим **661/663**. На 665 в BuhBud есть движения и остатки (ЦПХ-расчёты), которые сейчас
не попадают в сверку.

## 2. Архитектура отчёта (по коду)

Внешний СКД-отчёт. `Ext/ObjectModule.bsl` в `ПриКомпоновкеРезультата`:
1. `ПолучитьОстаткиЕРП` — ЕРП `А_ВзаиморасчетыССотрудниками.ОстаткиИОбороты` (Форма1) по (ФЛ × ОргБух).
2. `ПолучитьОстаткиBuhBud` — COM в BuhBud, `Хозрасчетный.ОстаткиИОбороты`, фильтр `Счет.Код В ("661","663")`,
   Субконто1=ФизическиеЛица, агрегация по (ФЛ через `А_ИдКод` × Орг через `ЕДРПОУ`), знак Кт−Дт (пассив).
3. `КонвертироватьТЗ_BuhBud` — А_ИдКод→ФЛ, ЕДРПОУ→Орг.
4. `ОбъединитьТаблицы` — join по (А_ИдКод, ЕДРПОУ), 4 разницы.
5. Вывод через СКД.

ЕРП-сторона (`А_ВзСС`) уже включает всех сотрудников — **менять не нужно**. 665 — чисто бухгалтерский счёт,
правка только в BuhBud-стороне.

## 3. Grounded факты (Python COM, Rule #-1)

- Счёт 665 = «Розрахунки за договорами ЦПХ», **пассивный**, Субконто1 = **Справочник.ФизическиеЛица**
  (идентично 661/663 — метка ВидаСубконто «Працівники організацій», тип = ФизическиеЛица).
- Текущий фильтр `Субконто1 ССЫЛКА Справочник.ФизическиеЛица` и извлечение `А_ИдКод` работают для 665 без изменений.
- Декабрь 2025: 665 = 10 строк (ФЛ×Орг). **Алов (ІНДЕПТ СТІЛ): нач.долг 21 433,49 Кт / выплата 21 433,49 Дт / кон.сальдо 0.**
- Все юр.лица баланса (`Организации.А_ВБалансе = ИСТИНА`: ІНДАСТРІАЛБУД 40645273, ДЖИ ТРИ 41597184,
  ІНДЕПТ СТІЛ 44590697) покрыты фильтром отчёта. Строки на орг вне баланса (напр. І.П.С. ТРЕЙД 45143198)
  корректно отсекаются.

## 4. Подход

**Слить 665 в существующую бухгалтерскую сторону** (661+663+665 суммируются в те же бакеты ФЛ×Орг).
Отчёт уже суммирует 661+663 без разбивки по счёту → добавление 665 в IN-список согласовано с текущим дизайном.

Отвергнуто:
- Отдельная колонка по счёту → потребовала бы измерение «Счёт» в СКД (несогласованно: 661 и 663 тоже не разбиты).
- Отдельный отчёт → дублирование.

## 5. Объём изменений

**Файл `_Rarzrabotki/Отчеты/А_СравнитьОстаткиВзаиморасчетыСотрудникиЕРПсBASБухгалтерия/Ext/ObjectModule.bsl`:**
1. **Функционально (1 строка, ~173):** `Ост.Счет.Код В ("661", "663")` → `Ост.Счет.Код В ("661", "663", "665")`.
2. Метки для консистентности: комментарии (~17, ~122) и сообщение об ошибке (~186) «661/663» → «661/663/665».

**Метки заголовков/справки (косметика, для пользователя):**

4. `А_СравнитьОстаткиВзаиморасчетыСотрудникиЕРПсBASБухгалтерия.xml` — синоним отчёта (ru/uk): «661/663» → «661/663/665».

## 6. Эффект

Бух-сторона = 661+663+665. ЦПХ-расчёты (Алов и др.) становятся видны в сверке. Существующие 661/663-числа
не искажаются (665 только добавляется суммированием в бакеты ФЛ×Орг). Где у ФЛ нет 665 — без изменений.

## 7. Проверка (Rule #-1 + verification-before-completion)

**RED/GREEN через Python COM (зеркало запроса отчёта):**
- RED (до): запрос BuhBud с `В ("661","663")` — 665-движения не входят.
- GREEN (после): запрос с `В ("661","663","665")` за декабрь возвращает 665-строки (Алов ІНДЕПТ СТІЛ нач.остаток
  21 433,49 / выплата 21 433,49 / кон 0); суммы 661/663 по контрольным ФЛ не изменились (регрессия).
- Сборка `.erf` без ошибок (`erf-build` / `erf-validate`).

## 8. Грабли

- `XMLСтрока(ТипЗначения)` / `NewObject("Дата", y,m,d,...)` через COM падают — даты задавать литералом `ДАТАВРЕМЯ`
  в тексте запроса; тип субконто читать через `ВидСубконто.ТипЗначения.Типы()` + `Метаданные.НайтиПоТипу`.
- `erf-build` собирать против реальной BaseERP (стаб-2.17 падает — память `sravnit_vzss_sotrudniki_report`).

  но делает 665-сторону видимой — это и есть задача. Полное закрытие Алова — отдельный вопрос данных.
