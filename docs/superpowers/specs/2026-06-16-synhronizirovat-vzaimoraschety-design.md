## 1. Цель

Перепрофилировать внешнюю обработку
`_Rarzrabotki/Обработки/СинхронизироватьВзаиморасчеты` (сейчас — дословный клон
товарной `СинхронизироватьТоварыТолькоТовары`) под **контроль расхождений
взаиморасчётов по контрагентам** между ERP (`BaseERP`) и BAS Бухгалтерія
(`BuhBud`). Полный паритет с товарным сиблингом: **все 3 фазы**
(сверка остатков → анализ документов → действия синхронизации).

Запросы сверки берём 1:1 из отчёта-донора
`_Rarzrabotki/Отчеты/А_СравнитьОстаткиВзаиморасчетыКонтрагентыЕРПсBASБухгалтерия`.

## 2. Подтверждённые факты (проверено на живой базе / в коде)

1. **Оперативный регистр `РасчетыСКлиентами` пишется реальными
   документами-источниками**, НЕ служебным `РегистраторРасчетов`. Подтверждено
   запросом `ПРЕДСТАВЛЕНИЕ(ТИПЗНАЧЕНИЯ(Регистратор))`: в январе 2026 это
   Реализация товаров и услуг, Акт выполненных работ, ПКО, РКО, Поступление
   безнал. ДС, Списание безнал. ДС, Взаимозачет задолженности, Заказ клиента,
   Ввод остатков. ⇒ Фаза 2 (анализ через `СоответствияОбъектовИнформационныхБаз`
   по `Регистратор`) переносится с товаров **1:1**.
2. Все эти документы присутствуют в правилах обмена ERP↔BuhBud (`exchange_erp_buhbud.md`),
   UUID сохраняется 1:1 (Реализация→Реализация, ПКО→ПКО, Поступление безнал→
   ПоступлениеНаРасчетныйСчет, Списание безнал→СписаниеСРасчетногоСчета,
   Взаимозачет→КорректировкаДолга и т.д.).
3. Счета BuhBud для сверки взаиморасчётов:
   361, 362, 631, 632, 6851, 6852, 6855 (два субсчёта), 3771, 3772, 601, 602,
   684, 655. Позиция субконто (Контрагенты / Договоры) определяется динамически
   через `ПланСчетов.Хозрасчетный.ВидыСубконто` (как в отчёте).
4. Ключ сопоставления ERP↔BuhBud — реквизит `А_ИдКод` у `Контрагенты` и
   `ДоговорыКонтрагентов` (+ `Код` валюты). Тот же приём, что у товаров
   (Номенклатура.А_ИдКод + Склад.А_ИдКод).
5. Перепроведение документов взаиморасчётов через COM теряет
   `РегистраторРасчётов` → РСППС=0 (память `feedback_com_repost_skips_registrator_raschetov`).
   Поэтому Фаза 3 перепроводит **в UI-сессии** обработки
   (`РеквизитФормыВЗначение` → серверный вызов), а не через `V83.COMConnector`.
   Массовую историю перепроводит пользователь сам в UI.

## 3. Решения по объёму (утверждено пользователем)

- Объём: **все 3 фазы** (как у товарного сиблинга).
- Детализация позиций: **Контрагент × Договор × Валюта**.
- Охват: **все контрагенты без исключений** (аналог исключения «обмінних
  складів» НЕ применяем; служебных вроде НеизвестныйПартнёр не фильтруем).

## 4. Архитектура — 3 фазы (зеркало товаров)

Двухуровневая форма-«трилистник»:
**мастер `ТаблицаКонтрагентов`** → **позиции `ТаблицаРасхождений`
(Контрагент×Договор×Валюта)** → **`ТаблицаДокументов`** (фильтруется активным
контрагентом мастера + флагом «Только расхождения»).

### Фаза 1 — `СравнитьОстатки()`
1. ERP-остатки: UNION ALL `РегистрНакопления.РасчетыСКлиентами.ОстаткиИОбороты`
   + `РасчетыСПоставщиками.ОстаткиИОбороты`, `ЛЕВОЕ СОЕДИНЕНИЕ
   РегистрСведений.АналитикаУчетаПоПартнерам` по `КлючАналитики` →
   Контрагент, Договор, Договор.ВалютаВзаиморасчетов. Группировка
   Контрагент×Договор×Валюта (как в отчёте, ветка «не ПоДням»).
2. BuhBud-остатки (COM): `РегистрБухгалтерии.Хозрасчетный.ОстаткиИОбороты`
   по списку счетов (п. 2.3), `Счет В ИЕРАРХИИ (&Счет)`, динамическая позиция
   субконто Контрагенты/Договоры через `ВидыСубконто`; фильтр организаций по
   `КодПоЕДРПОУ` (Организации с `А_ВБалансе`). Сериализация ТЗ через
   `V83.ЗначениеВСтрокуВнутр` → `ЗначениеИзСтрокиВнутр`; конвертация
   ИдКод→ссылки ERP через временную таблицу (как в отчёте `КонвертироватьТЗ_BuhBud`).
3. Сведение: индекс по ключу `КонтрагентКлюч|ДоговорКлюч|ВалютаКод`,
   FULL-OUTER в памяти. В `ТаблицаРасхождений` пишем только строки, где хотя бы
   одна из 4 величин (Нач/Приход/Расход/Кон) расходится `Окр(Δ,2) <> 0`.
4. Сводка `ЗаполнитьСводПоКонтрагентам()`: ключ КонтрагентКлюч; считаем
   Договоров (число позиций), Σ|Разница|. Денежные суммы по контрагенту НЕ
   складываем между валютами (несовместимы) — Σ|Разница| как индикатор.

### Фаза 2 — `АнализироватьДокументы(ИндексКонтрагента = -1)`
Для каждого отмеченного контрагента, по всем его позициям (Договор×Валюта):
- **Прямой анализ (ERP):** UNION `РасчетыСКлиентами.Обороты` +
  `РасчетыСПоставщиками.Обороты`, фильтр по `АналитикаУчетаПоПартнерам`
  (Контрагент.А_ИдКод + Договор.А_ИдКод), `ЛЕВОЕ СОЕДИНЕНИЕ
  СоответствияОбъектовИнформационныхБаз` по `Регистратор` ↔
  `УникальныйИдентификаторИсточника`, узел
  `ПланОбмена.ОбменУправлениеПредприятиемБухгалтерия20`. Мера —
  `СуммаПриход − СуммаРасход`. По каждому документу определяем
  действие/статус (см. таблицу действий ниже).
- **Обратный анализ (BuhBud, COM):** `Хозрасчетный.ОстаткиИОбороты`
  периодичность `Регистратор`, фильтр по расчётным счетам + субконто
  Контрагент+Договор (по А_ИдКод) + организации `А_ВБалансе`; находим
  документы BuhBud без пары в ERP. UUID документа BuhBud берём через
  `V83.XMLСтрока(Рег.УникальныйИдентификатор())`; обратное сопоставление в ERP —
  через `СоответствияОбъектовИнформационныхБаз`.
- Дедупликация: карты по UUID Бух и по представлению (как в товарах);
  сумма Бух проставляется в уже найденную строку, если документ совпал.
- Финальная нормализация: если СуммаЕРП == СуммаБух (Окр,2) и ≠0 →
  Действие сбрасывается, Статус = «Збігається», Синхронизировать = Ложь.

### Фаза 3 — `ВыполнитьСинхронизацию()`
Диспетчер `ВыполнитьДействиеСтроки` без изменений логики:

| Действие | Что делает |
|---|---|
| Розпровести в ЕРП | `Записать(РежимЗаписиДокумента.ОтменаПроведения)` |
| Провести в ЕРП | `Записать(…Проведение)` (резолв типа по `СоответствияОбъектовИнформационныхБаз`) |
| Перепровести в ЕРП | ОтменаПроведения + перечитать объект + Проведение (UI-сессия) |
| На обмін в BuhBud | `V83.ПланыОбмена.ЗарегистрироватьИзменения(Узел, СсылкаBuhBud)` |

Ленивое COM-подключение и поиск узла обмена — как в товарах.

## 5. Модель данных (схема XML обработки)

Объектные реквизиты: `НачалоПериода`, `ОкончаниеПериода` (Дата),
`Контрагент` (СправочникСсылка.Контрагенты — фильтр), `Договор`
(СправочникСсылка.ДоговорыКонтрагентов — фильтр), `ПоказыватьТолькоРасхождения`
(Булево).

**ТЧ `ТаблицаРасхождений`** (позиции): Раздел (Строка),
Контрагент (Контрагенты), Договор (ДоговорыКонтрагентов), Валюта (Валюты),
НачОстатокЕРП, НачОстатокБух, ПриходЕРП, ПриходБух, РасходЕРП, РасходБух,
ОстатокЕРП, ОстатокБух, Разница (все Число 15,2), Синхронизировать (Булево),
КонтрагентКлюч (Строка 50), ДоговорКлюч (Строка 50), ВалютаКод (Строка 10).

**ТЧ `ТаблицаДокументов`**: Раздел, Контрагент, Договор, ТипДокумента (Строка),
ДокументЕРП (ДокументСсылка/Строка), ДокументБух (Строка), СуммаЕРП, СуммаБух
(Число 15,2), Действие (Строка), Статус (Строка), UIDДокумента (Строка),
UIDДокументаБух (Строка), ЕстьСоответствие (Булево), Синхронизировать (Булево),
ЕстьРасхождение (Булево).

**ТЧ `ТаблицаКонтрагентов`** (мастер): Контрагент, КонтрагентКлюч (Строка 50),
Договоров (Число), СуммаРазницы (Число 15,2), Документов, Действий,
ТребуютРешения (Число), Синхронизировать (Булево).

`Раздел` = «Клієнти» / «Постачальники» — различает источниковый регистр.

## 6. Валютная логика

Сравнение ведём в **валюте взаиморасчётов** договора (как в отчёте):
- ERP: `РасчетыСКлиентами/Поставщиками` уже в валюте взаиморасчётов (измерение
  Валюта регистра) — берём суммы напрямую.
- BuhBud: если `Договор.ВалютаВзаиморасчетов = ВалютаРегламентированногоУчета`
  (грн) → `СуммаХХХ`; иначе → `ВалютнаяСуммаХХХ`.
- Колонка `Валюта` в позициях; ключ включает `ВалютаКод`.

мастер-деталь сохраняются. Цвет надписи — кодом (`ЦветаСтиля`), не в XML
(память `epf_load_xdto_textcolor`).

## 8. Тестирование (Rule #-1 / #5 — ОБЯЗАТЕЛЬНО)

Каждый запрос ПЕРЕД переносом в BSL прогнать Python COM-тестом на реальной базе
(`_Rarzrabotki/Python/test/`):
1. ERP UNION остатков (Фаза 1) — структура полей, ненулевой результат.
2. BuhBud COM остатки (Фаза 1) — динамическое субконто, валютные суммы.
3. Сведение и совпадение Σ по контрольному контрагенту против отчёта-донора.
4. Фаза 2 прямой запрос (Обороты + СоответствияОбъектовИнформационныхБаз) —
   что Регистратор = реальный документ и пара резолвится.
5. Фаза 2 обратный COM-запрос.
6. После BSL — `epf-build`, COM-smoke открытия обработки
   (память `win32com_epf_smoke_gotchas`), затем перенос в основную конфигурацию.
