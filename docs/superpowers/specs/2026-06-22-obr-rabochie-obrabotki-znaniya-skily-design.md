# Дизайн: База знаний + скилы `obr-*` — инженерия рабочих обработок 1С

> Дата: 2026-06-22 · Проект: BAS ERP 2.5 INDUSTRIALBUD · Ветка: `claude/*`
> Тип: spec (brainstorming → этот документ → writing-plans → реализация)
> Аналог структуры: `_Rarzrabotki/notebook/knowledge_БСП/` (знание-над-скилами)

---

## 1. Цель

Дать ИИ **знания + скилы**, превращающие его в компетентного **инженера рабочих обработок 1С**, способного **создавать и дорабатывать внешние обработки** класса:

> **запрос в базу → анализ → заполнение/создание документов**, с UX формы: **отборы/фильтры, вывод итогов, действия по строкам, массовые операции**.

Эталоны-цели (то, что ИИ должен уметь дорабатывать «как родное»):
- `_Rarzrabotki/Обработки/Создания комплектаций для бух учета` (запрос остатков сч.2051 → норма из спецификации → распределение → заполнение 4 документов `КомплектацияНоменклатуры`; форма с отборами Склад/Еталон + итоги).
- `_Rarzrabotki/Обработки/СинхронизироватьТоварыТолькоТовары` (сверка ЕРП↔BuhBud по товарам; форма с колонками/отбором/итогами + действия по строкам + перепроведение).

**Не цель:** тяжёлые tier-5 рабочие места (ПомощникПродаж, ОбеспечениеПотребностей) — только «продвинутый референс» в одном разделе, не предмет базы.

## 2. Домен (семейство обработок проекта)

В `_Rarzrabotki/Обработки/` ~75 обработок. Группы:
1. **Запрос → заполнение/создание документов** (ядро): СозданиеКомплектацийБух, «Заполнить документы ПокупкаПродажаВалюты», «Создать реализации…», СоздатьПриобретениеПоРеализации, ЗаполнениеНачисленийЗП, «Заполнить Счета учета», ЗаполнитьСчетУчетаВДоговоре.
2. **Сверка/синхронизация двух баз**: СинхронизироватьТовары(ТолькоТовары), СинхронизироватьВзаиморасчеты, СинхронизироватьДеньги(Касса).
3. **Перенос остатков**: Перенос остатков денег/номенклатуры/ОС/налогов/сотрудников/РасчетыСПартнерами.
4. **Перепроведение / Анализ дисбаланса / Служебные**: Перепровести*, А_ОбработкаДисбаланса*, ОчисткаБитыхСсылок, ПоискИУдалениеДублей.

**Общий каркас (инвариант домена):** тонкая форма (`РеквизитФормыВЗначение("Объект")` ↔ движок) → движок в `Ext/ObjectModule.bsl` (запросы 1С → ТЧ результата) → заполнение/создание документов (обязательные поля, `А_`-флаги, Курс/Кратность, идемпотентность) → форма с **отборами, итогами, действиями по строкам**. Сборка `.epf` (epf-build), smoke через win32com.

## 3. Принцип грунта (как в БСП)

Знания и скилы **грунтуются вербатим на реальных обработках проекта** (`_Rarzrabotki/Обработки/`), НЕ из памяти. Каждый паттерн/сниппет — со ссылкой на файл-источник. Запросы 1С — проверяются через Python COM/MCP перед попаданием в reference (Rule #-1).

## 5. Критерии успеха (приёмка)

1. **Свежий агент** (без этого контекста), прочитав папку знаний + скилы как контекст, по промту «добавь в `СозданиеКомплектацийБух` фильтр по номенклатуре и итоги, считающиеся по наложенному поиску» — выдаёт корректную правку формы+движка **без галлюцинаций** (правильный мост, отборы, пересчёт итогов).
2. Тот же агент по промту «создай обработку: запрос остатков X → создать документы Y» — строит каркас (тонкая форма + движок + фабрика документов с обязательными полями) в стиле проекта.
3. Все сниппеты в знаниях — со ссылкой на файл-источник в `_Rarzrabotki/Обработки/`; запросы прогнаны через Python COM/MCP.
4. Скилы проходят гейт `bas-verify` (epf-build + smoke на эталоне).

## 6. Подход к реализации (для writing-plans)

Порядок: (1) грунт — глубоко прочитать 4-6 реальных обработок-эталонов разных семейств (СозданиеКомплектацийБух уже прочитан; добавить СинхронизироватьТоварыТолькоТовары, одну «Создать…», одну «Заполнить…»); (2) написать `obr_arhitektura_obrabotki.md` + 3 тематических знания (вербатим-сниппеты); (3) написать 4 скила `obr-*` (frontmatter + тело, REQUIRED BACKGROUND связка); (4) overview + prompts + feedback_loop; (5) 2 кейса; (6) KNOWLEDGE_MAP; (7) приёмка свежим агентом на задаче «итоги по поиску» → фикс пробелов; (8) память + индекс.
