# Дизайн: РКО «Выплата работнику» — фильтр движений по одному ФизЛицу

**Дата:** 2026-06-07
**Тип:** bugfix к [2026-05-28-rko-dsnalichnye-vkassu-per-strpredpr-design](2026-05-28-rko-dsnalichnye-vkassu-per-strpredpr-design.md) и §3.9–3.13 knowledge_А_ВзаиморасчетыССотрудниками
**Длительность:** ~1 рабочая сессия (BSL правка в 4 файла + Python COM тесты)
**Подход:** A (точечный фильтр в каждом ВКассу-запросе)

## 🎯 Бизнес-мета (CFO)

РКО с операцией **«Выплата по ведомости работнику»** (`ХозяйственныеОперации.ВыплатаЗарплатыРаботнику`) выдаёт деньги **одному** сотруднику по ведомости. На форме поле «Работник» хранится в реквизите `ПодотчетноеЛицо` (тип `СправочникСсылка.ФизическиеЛица`).

Вся «ВКассу-логика» (§3.9–3.13) для зарплатных РКО берёт расшифровку из ТЧ
`Документ.ВедомостьНаВыплатуЗарплатыВКассу.А_РасшифровкаВыплатыЗарплатаПоФизлицам`
через джойн `Рш.Ссылка = РКО.Ведомость` и фильтрует только по 3 зарплатным ХозОп — **но не по конкретному работнику**. Поэтому единичная выплата проводится на **всю ведомость**.

### Пример бага — РКО ІБ00-000006 от 30.01.2026

| Реквизит | Значение |
|---|---|
| Операция | Выплата по ведомости работнику (`ВыплатаЗарплатыРаботнику`) |
| Работник (`ПодотчетноеЛицо`) | Марчук Юрій Олександрович |
| Ведомость | ВКассу ІБ00-000019 (в А_Расшифровке 5 сотрудников) |
| СуммаДокумента | **21 612,50** (только Марчук) |

Движения регистра `А_ВзаиморасчетыССотрудниками` (и зеркально ПАП) — **5 строк** вместо 1:

```
Расход | Форма2 | Строительство | Марчук Юрій Олександрович   | 21 612,50   ← должна остаться ТОЛЬКО эта
Расход | Форма2 | Строительство | Зубов Олександр В'ячеславович| 16 670,50   ← лишняя
Расход | Форма2 | Строительство | Шумко Андрій Анатолійович   | 17 710,00   ← лишняя
Расход | Форма2 | Строительство | Гончаренко Валерій Петрович | 16 670,50   ← лишняя
Расход | Форма2 | Строительство | Пешко Сергій Іванович       | 21 659,50   ← лишняя
                                                  ИТОГО движений: 94 323,00 ≠ 21 612,50
```

**Последствия:** физическая касса (`РегНак.ДенежныеСредстваНаличные`) показывает выбытие 94 323,00 при фактических 21 612,50 (завышение ~5×); долг по ЗП в А_ВзСС гасится на лишние суммы; при наличии отдельных РКО на остальных работников те же суммы задваиваются. Если по той же ведомости есть 5 РКО (по одному на работника), итог — 5×5 = 25 движений и пятикратное переполнение баланса.

## 📋 Цель

| Поле | ДО | ПОСЛЕ |
|---|---|---|
| Движений по ІБ00-000006 (каждый из 5 регистров) | 5 (вся ведомость) | **1** (только Марчук) |
| Σ движений | 94 323,00 | **21 612,50** = СуммаДокумента |
| `ВыплатаЗарплатыЧерезКассу` / `Раздатчиком` | вся ведомость | **вся ведомость** (без изменений) |

**Инварианты после фикса:**
- Σ signed А_ВзСС + Σ signed ПАП(ОплатаТруда) ≈ 0 per Регистратор (TOL 1 ₽).
- `ДенежныеСредстваНаличные`: Σ per Касса = СуммаДокумента (баланс физкассы цел).
- ПАП per СтрПредпр: Приход(ОплатаТруда) = Расход(ДенСрНал) (плуги не возникают).
- Drill-down по СтрПредпр сохраняется: если у работника несколько единиц техники — все его строки остаются, Σ = его сумма.

## 🏗 Архитектура решения (Approach A)

### Принцип

В каждый запрос, джойнящий `Документ.ВедомостьНаВыплатуЗарплатыВКассу.А_РасшифровкаВыплатыЗарплатаПоФизлицам КАК Рш ПО Рш.Ссылка = <РКО>.Ведомость`, добавить в `ГДЕ` условие:

```1c
И (НЕ <РКО>.ХозяйственнаяОперация = ЗНАЧЕНИЕ(Перечисление.ХозяйственныеОперации.ВыплатаЗарплатыРаботнику)
   ИЛИ Рш.ФизическоеЛицо = <РКО>.ПодотчетноеЛицо)
```

Семантика:
- ХозОп ≠ Работнику (ЧерезКассу/Раздатчиком) → первый операнд истина → берутся все строки ведомости (поведение не меняется).
- ХозОп = Работнику → остаются только строки, где `Рш.ФизическоеЛицо = ПодотчетноеЛицо`.

Оба поля — `СправочникСсылка.ФизическиеЛица` (типы совпадают, сравнение корректно). Точная финальная редакция условия (скобки/`<>` vs `НЕ =`) проверяется Python COM тестом **до** внесения в BSL (Rule #-1).

### 5 точек правки (4 файла)

| # | Файл / процедура | Алиас РКО | Куда |
|---|---|---|---|
| 1 | `AccumulationRegisters/А_ВзаиморасчетыССотрудниками/Ext/ManagerModule.bsl` — `ЗаполнитьИзРКО`, ветка ВКассу (319-338) | `Д` | в `ГДЕ` перед `СГРУППИРОВАТЬ` |
| 2a | `DataProcessors/ДвиженияАктивовПассивов/Ext/ManagerModule.bsl` — `ПАП_РКО_ВКассу_Замена`, половина «Приход ОплатаТруда» (3835-3861) | `РКО` | новый `ГДЕ` перед `СГРУППИРОВАТЬ` |
| 2b | та же процедура, половина «Расход ДенСрНал» (3865-3891) | `РКО` | новый `ГДЕ` перед `СГРУППИРОВАТЬ` |
| 3 | `Documents/РасходныйКассовыйОрдер/Ext/ManagerModule.bsl` — `ТекстЗапросаТаблицаДенежныеСредстваНаличные`, Локализация-1 (2326-2361) | `ДанныеДокумента` | в `ГДЕ` (2348-2354) |
| 4 | `CommonModules/РасходныйКассовыйОрдерЛокализация/Ext/Module.bsl` — `ТекстЗапросаТаблицаДвиженияДенежныеСредстваДоходыРасходы` (функция с 2980), Локализация-1 — джойн А_Расшифровки ~3034 | `ДанныеДокумента` | в `ГДЕ` |

> Жёсткий гард из 3 ХозОп (ЧерезКассу/Раздатчиком/Работнику) + ТипВедомости=ВКассу остаётся без изменений во всех 4 местах. Новое условие добавляется **внутри** уже отобранных ВКассу-строк.

### Что НЕ трогаем (out-of-scope, осознанно)

- **Старая (не-ВКассу) ветка `ЗаполнитьИзРКО`** (340-360): читает ТЧ `ВыплатаЗаработнойПлаты`, которую платформа для единичной выплаты не заполняет; наши документы идут через ВКассу.
- **Типовые ветки Локализация-2** в файлах 3 и 4: их взаимоисключающий гард `НЕ (ВКассу И зарплатные)` уже корректно отдаёт зарплатные ВКассу-РКО в Локализацию-1.
- **Структура регистров** — никаких мета-правок (memory `feedback_no_typical_register_changes`).
- **Массовая перепроводка исторических РКО** — отдельным шагом по решению пользователя (в этой итерации — только ІБ00-000006).

## ✅ План верификации (Rule #-1 + bas-verify)

1. **Pre-test (Python COM, ДО BSL).** Прогнать новое условие фильтра на ІБ00-000006:
   - результат = ровно 1 ФЛ (Марчук), Σ `КВыплате` = 21 612,50;
   - контрольно: на РКО с `ВыплатаЗарплатыЧерезКассу` тот же запрос возвращает полную ведомость (фильтр не задел).
2. **BSL.** Внести условие в 4 файла (5 запросов). Скопировать изменённые файлы в основную конфигурацию `C:\Configuration_downloads\BASERP25\` (Rule #4).
3. **Загрузка.** `/db-load-xml -Mode Partial` + `/db-update -Dynamic+` (memory `feedback_use_db_skills_for_config_load`).
4. **Перепроводка ІБ00-000006 — через UI 1С** (делает пользователь): COM-перепроводка ненадёжна для движений.
5. **Verify (Python COM):**
   - все 5 регистров → 1 движение Марчук = 21 612,50;
   - Σ-инвариант А_ВзСС + ПАП(ОплатаТруда) ≈ 0;
   - `ДенежныеСредстваНаличные` Σ per Касса = СуммаДокумента;
   - ПАП per СтрПредпр: Приход ОТ = Расход ДенСр;
   - идемпотентность (повторный прогон Δ=0).
6. **Sanity-регрессия:** РКО `ВыплатаЗарплатыЧерезКассу` на всю ведомость по-прежнему раскладывается полностью (эталон §3.12 — N0000052986, 12 СтрПредпр / 348 800).

Тесты складывать в `_Rarzrabotki/Python/test/` (каталог-каталог скриптов — memory `balans_klient_scripts_catalog`), именование `test_rko_vyplata_rabotniku_*`.

## ⚠️ Риски и грабли

| Риск | Митигизация |
|---|---|
| Приоритет операторов `НЕ … = … ИЛИ …` в языке запросов 1С | Финальную редакцию (скобки/`<>`) валидируем Python COM тестом до BSL |
| `ПодотчетноеЛицо` пусто при ХозОп=Работнику (битый документ) | Фильтр даст 0 строк — приемлемо; работник для такой операции обязателен |
| Designer кэширует BSL | После `cp` — `/db-load-xml` + `/db-update` или правка configVersion (memory `feedback_designer_cache_invalidation`) |
| Рассинхрон 5 регистров, если правку внести не во все | Все 5 в одном дизайне; verify проверяет каждый |
