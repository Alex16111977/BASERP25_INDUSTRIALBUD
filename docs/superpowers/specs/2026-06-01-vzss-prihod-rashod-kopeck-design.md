# Дизайн: Форма1 — начисления и налоги совпадают до копейки между ОтражениеЗарплатыВФинансовомУчете и ПередачаНачислений

> **Тип:** design / spec (superpowers brainstorming). Создан 2026-06-01, уточнён 2026-06-01 (scope сужен пользователем).
> **Источник задачи:** `_Rarzrabotki/notebook/knowledge_А_ОтражениеЗПпоКазне/PROMPT_Расхождение_ВзСС_Приход_Расход.md`
> **Эталон:** ФизЛицо «Шишкіна Людмила Григорівна», декабрь 2025; документы `ОтражениеЗарплатыВФинансовомУчете 000Ц-000003` (дочерний) и `А_ПередачаНачисленийМеждуПодразделениями 000000001`, оба от 31.12.2025.

## 0. Решение по объёму (бухгалтерская практика, подтверждено пользователем 2026-06-01)

- **Разрыв «начислено ↔ выплачено» за месяц — НОРМА, не ошибка.** Банк может доплатить в следующем месяце, касса — выплатить меньше. Остаток регистра против фактических выплат (СБДС/РКО) НЕ сводится к нулю за месяц; разница переходит сальдо. → **−110.26 (Ф1) и +128.58 (Ф2) — вне scope, оставляем как есть.**
- **В scope — только одно:** все суммы по **Форме1** — и начисления (NET «Зарплата управл»), и их налоги (НДФЛ/ВС/ЕСВ) — должны совпадать **до копейки** между `ОтражениеЗарплатыВФинансовомУчете 000Ц-000003` (Приход) и `ПередачаНачислений 000000001` (перенос). Это устраняет фантомный остаток −0.01 на исходном подразделении.

Принцип: Бухгалтерия — контрольный итог; Казна — коэффициент распределения; единый ключ округления; после распределения по подразделениям Σ по (ФЛ, организация) сверяется с бух-итогом до копейки.

---

## 1. Проблема (узкая, в scope)

`ПередачаНачислений` реклассифицирует уже начисленное Ф1-обязательство (зарплата + её налоги) между подразделениями. Реклассификация обязана быть равна исходному начислению копейка-в-копейку. Сейчас по Шишкіной на исходном подразделении (Спецтехника) повисает **−0.01**: Приход(ОЗФУ) = 6685.70, перенос = 6685.71.

(Остаток против выплат — −110.25 Ф1 Производство, +64.29 Ф2 — НЕ трогаем, это норма «начислено↔выплачено».)

## 2. Discovery (подтверждено MCP execute_query, Rule #-1)

Родительские/дочерние Ф1-строки `НачисленнаяЗарплатаИВзносыПоФизлицам` (дочерний — копия 1‑в‑1, ObjectModule стр. 3104/3151):

| Подр | Способ | Сумма |
|---|---|---:|
| Производство | Зарплата управленческого персонала (NET) | 6685.71 |
| Спецтехника | Зарплата управленческого персонала (NET) | 6685.71 |
| Производство | Удержание с админ зарплату (gross-up НДФЛ) | 1997.03 |
| Спецтехника | Удержание с админ зарплату (gross-up НДФЛ) | 1997.03 |
| (обе) | Начисления на админ зарплату (ЕСВ, ВзносыВсего) | 0 (взносы 1910.2x) |

`НачисленныйНДФЛ` (отдельная ТЧ): Производство **1997.02** / Спецтехника **1997.04** (Σ = 3994.06 = `НалогиБухгалтерия`: НДФЛ 3125.79 + ВоенСбор 868.27).

`ПередачаНачислений.Начисления` по Шишкіной: одна строка 6685.71 (Спецтехника → Производство).

## 3. Корневая причина (−0.01)

Официальный Ф1-НДФЛ присутствует в ОЗФУ **дважды**, разбит по подразделениям по **разным ключам**:
- (a) gross-up строка «Удержание с админ зарплату» в `НачисленнаяЗарплатаИВзносыПоФизлицам` — **равномерно** (1997.03 / 1997.03); создаётся `_ОтрЗП_СоздатьСтрокиNETФЛ_Новый` (≈1820);
- (b) ТЧ `НачисленныйНДФЛ` — **по весу Казны** (1997.02 / 1997.04); создаётся `_ОтрЗП_ЗаполнитьНДФЛИзНалогов` (≈2217).

Регистр Приход = `Σ НачисленнаяЗарплата(Налог=пусто) − НачисленныйНДФЛ` = («Зарплата управл» 6685.71 + «Удержание» 1997.03) − НДФЛ(1997.02/1997.04) = **6685.72 / 6685.70**.
`ПередачаНачислений` = «Зарплата управл» = **6685.71 / 6685.71**.
Разница `(Удержание 1997.03 − НДФЛ 1997.0x) = ±0.01` и есть расхождение. Это один налог, поделённый двумя способами.

## 4. Где центрируется решение

Все документы «ОЗФУ-стороны» формируются в потоке формы `ЗаполнитьВсеНаСервере()`:
`ЗаполнитьНачисленияУпризЗуп2` → `ЗагрузитьНалогиИУдержанияИзЗарплатыБух` → `ЗаполнитьОтражениеЗарплатыВФинансовомУчетеИзБазЗП` → `ЗаполнитьДляОтражения_ДокументОтражениеЗарплатыВФинансовомУчете` → `Записать(Проведение)` → `СоздатьДокументНачисления` → `СоздатьДокументОтражениеЗарплатыВФинансовомУчете` (Приход) → `СоздатьПередачуНачисленийМеждуПодразделениями` (перенос).
**Правки — внутри этих алгоритмов `Documents/А_ОтражениеЗПпоКазне/Ext/ObjectModule.bsl`.**

## 5. Дизайн (единственная фаза)

**Цель:** по каждому (ФЛ, подразделение) Ф1 — начисления (NET) и налоги (НДФЛ/ВС/ЕСВ) — идентичны до 0.01 между дочерним ОЗФУ (Приход) и `ПередачаНачислений`. Перенос с исходного подразделения = ровно начисленному там (net-zero на исходном до 0.01).

**Изменения:**

1. **Единое распределение официального Ф1-НДФЛ по подразделениям (по коэффициенту Казны).**
   gross-up «Удержание с админ зарплату» (`_ОтрЗП_СоздатьСтрокиNETФЛ_Новый` ≈1820) и `НачисленныйНДФЛ` (`_ОтрЗП_ЗаполнитьНДФЛИзНалогов` ≈2217) должны разбиваться **по одному ключу (вес Казны) и с одним якорем «остаток на последнем»** — это один и тот же налог. Тогда `(«Удержание» − НачисленныйНДФЛ) = 0` по подразделению, и `Начислено − НДФЛ = «Зарплата управл»` ровно → регистр Приход = «Зарплата управл» = `ПередачаНачислений`.

2. **NET «Зарплата управл» по подразделению согласован с GROSS и НДФЛ.** `Зарплата управл`_подр = GROSS_подр − НДФЛ_подр, всё по одному коэффициенту Казны (а не GROSS/НДФЛ по разным базам).

3. **Якорная сверка округления до копейки (новая переиспользуемая утилита).**
   После распределения по подразделениям проверять `Σ доль = контрольный бух-итог по (ФЛ, организация)`; копеечный остаток досаживать на якорное подразделение (наибольшая доля). Применить в `_ОтрЗП_РаспределитьNETПоПодр` (≈2161), `_ОтрЗП_ЗаполнитьНДФЛИзНалогов` (≈2217), `_ОтрЗП_РаспределитьПоВесам` (≈1778).

4. **`ПередачаНачислений` зеркалит начисление и налоги.** `_ПНМП_ЗаполнитьНачисления` (≈3716) / `_ПНМП_ЗаполнитьНалоги` (≈3730) дают по подразделению ровно те же суммы, что в дочернем ОЗФУ (после п.1–п.2 они уже сходятся).

## 6. Вне scope

- **Разрыв «начислено ↔ выплачено»** (−110.26 Ф1, +128.58 Ф2): нормальная бухгалтерская практика (timing: доплата по банку в след. месяце, недоплата по кассе). Регистр против фактических выплат за месяц в ноль не сводим.
- Изменение фактически выплаченного (Казна) — это факт.
- ❌ Перепроведение ОЗФУ/А_ОтражениеЗПпоКазне через COM (только UI). ❌ Костыль ±0.01 строкой. ❌ BSL без Python/MCP-теста (Rule #-1). ❌ Переменная `Ссылка` (зарезервировано).

## 7. Критерии приёмки

1. ✅ Discovery построчно показывает причину −0.01 (§2–§3).
2. ✅ По Шишкіной по каждому (подразделение) Форма1: NET «Зарплата управл», НДФЛ, ВС, ЕСВ **идентичны до 0.01** между `ОтражениеЗарплатыВФинансовомУчете 000Ц-000003` и `ПередачаНачислений 000000001`.
3. ✅ Регистр: по каждому (ФЛ, подразделение) Ф1 `Приход(ОЗФУ) = перенос(ПередачаНачислений)` до 0.01; остаток −0.01 на исходном подразделении устранён.
4. ✅ Инвариант: Σ Ф1+Ф2 = `НачисленияУпр.Сумма`; Σ по (ФЛ, организация) = бух-итог до копейки; `ОрганизацияБухгалтерия` всех Ф1-строк заполнена.
5. ✅ Глобально: по всем ФЛ с `НачисленияУпр≠0` Ф1-начисления+налоги (ОЗФУ ↔ ПередачаНачислений) не разъезжаются ни по одной строке.
6. ✅ Остаток против выплат (−110.26/+128.58) сохраняется как есть (проверка, что мы его НЕ изменили).
7. ✅ Файлы скопированы в основную конфигурацию (Rule #4); загрузка `/db-load-xml -Mode Partial` + `/db-update -Dynamic+`.
