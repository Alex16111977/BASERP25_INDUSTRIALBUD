# Дизайн: устранение расхождения Приход ≠ Расход в РегистрНакопления.А_ВзаиморасчетыССотрудниками (до копейки)

> **Тип:** design / spec (superpowers brainstorming). Создан 2026-06-01.
> **Источник задачи:** `_Rarzrabotki/notebook/knowledge_А_ОтражениеЗПпоКазне/PROMPT_Расхождение_ВзСС_Приход_Расход.md`
> **Эталон:** ФизЛицо «Шишкіна Людмила Григорівна», декабрь 2025, документ `А_ОтражениеЗПпоКазне` №000000001 от 31.12.2025.
> **Принцип (от пользователя):** Бухгалтерия — контрольный итог; Казна — только коэффициент распределения; единое округление; после распределения по подразделениям Σ по организации сверяется с бух-итогом до копейки; перенос возвращает начисление в исходную организацию до 0.01.

---

## 1. Проблема

В отчёте «Взаиморасчёты с сотрудниками для баланса» (источник — `РегистрНакопления.А_ВзаиморасчетыССотрудниками`) по физлицам остаётся ненулевой остаток: и копейки (±0.01), и десятки/сотни гривен. По Шишкіной за декабрь 2025 итог остатка **+18.32** при ожидаемом 0.

## 2. Discovery (подтверждено данными через MCP execute_query, Rule #-1)

Движения регистра по Шишкіной за 2025-12 и их источники:

| Форма / Подр | Приход (источники) | Расход (источники) | Остаток |
|---|---:|---:|---:|
| Ф1 Производство | 6685.72 (дочерний ОЗФУ) + 6685.71 (ПередачаНач, Приход) | 13481.68 (4× СБДС банк) | **−110.25** |
| Ф1 Спецтехника | 6685.70 (дочерний ОЗФУ) | 6685.71 (ПередачаНач, Расход) | **−0.01** |
| Ф2 Производство | 21314.29 (дочерний ОЗФУ) | 21250.00 (2× РКО касса) | **+64.29** |
| Ф2 Спецтехника | 30314.29 (дочерний ОЗФУ) | 30250.00 (2× РКО касса) | **+64.29** |

Ключевые факты:
- **Доминирующий Расход — реальные выплаты** (СБДС банк для Ф1, РКО касса для Ф2), а НЕ `ПередачаНачислений`.
- `ПередачаНачислений` по Шишкіной — одна строка: 6685.71, Спецтехника → Производство (внутренний Ф1-перенос).
- Дочерний ОЗФУ НДФЛ Ф1 = 1997.02 + 1997.04 = **3994.06 = `НалогиБухгалтерия` (НДФЛ 3125.79 + ВоенСбор 868.27)** → начисление уже считается по Бухгалтерии.
- Казна take-home (`РаспределениеКазна.СуммаНачисления`): Ф1 = 13481.68 (= факт банка), Ф2 = 51500.00 (= факт кассы).

Родительские Ф1-строки `НачисленнаяЗарплатаИВзносыПоФизлицам` (дочерний — копия 1‑в‑1):

| Подр | Способ | Сумма |
|---|---|---:|
| Производство | Зарплата управленческого персонала | 6685.71 |
| Спецтехника | Зарплата управленческого персонала | 6685.71 |
| Производство | Удержание с админ зарплату | 1997.03 |
| Спецтехника | Удержание с админ зарплату | 1997.03 |

`НачисленныйНДФЛ` (отдельная ТЧ): Производство 1997.02 / Спецтехника 1997.04.

## 3. Корневые причины (три независимые)

1. **−0.01 (округление НДФЛ по подразделениям) — БАГ кода.**
   Регистр Приход = `Σ НачисленнаяЗарплата(Налог=пусто) − НачисленныйНДФЛ` =
   («Зарплата управл» 6685.71 + «Удержание с админ» 1997.03) − НачисленныйНДФЛ.
   «Удержание с админ» разбит **равномерно** (1997.03 / 1997.03), а `НачисленныйНДФЛ` — **по весу Казны** (1997.02 / 1997.04). Это **один и тот же официальный НДФЛ, разбитый по подразделениям по разным ключам**. Разница `(Удержание − НДФЛ)` даёт +0.01 / −0.01 по подразделению, из‑за чего Приход = 6685.72 / 6685.70, тогда как `ПередачаНачислений` = «Зарплата управл» = 6685.71 / 6685.71. → расхождение ±0.01.

2. **−110.26 (Ф1): начисление (Бухгалтерия) ↔ выплата (Казна).**
   Начисление NET Ф1 = GROSS 17365.48 − Бух.НДФЛ 3994.06 = 13371.42. Банк (СБДС) выплатил Казна take-home 13481.68. Δ = 110.26. Выплата — факт, пересчитать нельзя.

3. **+128.58 (Ф2): начисление (РаспределениеФ2) ↔ выплата (Казна-касса).**
   Начисление Ф2 = 51628.58. Касса (РКО) выплатила Казна Ф2 = 51500.00. Δ = 128.58.

Итог: −0.01 − 110.26 + 128.58 = **+18.31 ≈ +18.32** ✅.

**Замечание к постановке промта:** промт предполагал, что Расход = `ПередачаНачислений`. Фактически `ПередачаНачислений` — внутренний Ф1-перенос (даёт только −0.01), а 110.26/128.58 — это «начисление Бухгалтерия ↔ фактическая выплата Казна».

## 4. Принцип решения

Код `А_ОтражениеЗПпоКазне` **уже** реализует «Бухгалтерия — итог, Казна — коэффициент» (NET из `НачисленияУпр`, НДФЛ из `НалогиБухгалтерия`, GROSS из `НачисленияБух`; распределение по весам `РаспределениеКазна` методом «остаток на последнем»). Не хватает: **единого ключа округления между ветками и сверки итога по (ФЛ, организация) до копейки**.

Все документы, проводящие регистр через «ОЗФУ-сторону», формируются в потоке формы `ЗаполнитьВсеНаСервере()`:
`ЗаполнитьНачисленияУпризЗуп2` → `ЗагрузитьНалогиИУдержанияИзЗарплатыБух` → `ЗаполнитьОтражениеЗарплатыВФинансовомУчетеИзБазЗП` → `ЗаполнитьДляОтражения_ДокументОтражениеЗарплатыВФинансовомУчете` → `Записать(Проведение)` → `СоздатьДокументНачисления` → `СоздатьДокументОтражениеЗарплатыВФинансовомУчете` (Приход) → `СоздатьПередачуНачисленийМеждуПодразделениями` (Расход).
**Решение центрируется в этих алгоритмах.**

## 5. Дизайн — Phase 1 (ядро: Приход = Расход по подразделению до 0.01)

**Цель:** суммы начисления (дочерний ОЗФУ, читается Приходом) и `ПередачаНачислений` (Расход) совпадают по каждому (ФЛ, подразделение, форма) до копейки; Σ по (ФЛ, организация) = бух-итог.

**Изменения:**

1. **Единый источник разбивки официального НДФЛ по подразделениям.**
   `НачисленныйНДФЛ` (`_ОтрЗП_ЗаполнитьНДФЛИзНалогов`, ≈2217) и Ф1-строки «Удержание с админ зарплату»/«Зарплата управл» (`_ОтрЗП_СоздатьСтрокиNETФЛ_Новый`, ≈1820) должны разбиваться по подразделениям **по одному ключу и с одним якорем «остаток на последнем»**. Тогда `(Удержание − НачисленныйНДФЛ) = 0` в каждом подразделении, и регистр Приход = «Зарплата управл» = `ПередачаНачислений` по подразделению.

2. **Якорная сверка округления до копейки (новый алгоритм-утилита).**
   После любого распределения суммы по подразделениям (`_ОтрЗП_РаспределитьNETПоПодр` ≈2161, `_ОтрЗП_ЗаполнитьНДФЛИзНалогов` ≈2217, `_ОтрЗП_РаспределитьПоВесам` ≈1778, `_ПНМП_ЗаполнитьНачисления` ≈3716) выполнять проверку: `Σ доль по подразделениям = контрольный бух-итог по (ФЛ, организация)`; копеечный остаток досаживать на якорное подразделение (наибольшая доля). Вынести в одну переиспользуемую процедуру.

3. **`ПередачаНачислений` зеркалит начисление.**
   `_ПНМП_ЗаполнитьНачисления` (≈3716) берёт ту же per-подразделение NET, что попадает в Приход регистра (после п.1 «Зарплата управл» по подразделению уже равно Приходу). Гарантировать net-zero по исходной организации до 0.01 (Спецтехника: Приход − перенос_из = 0).

**Результат Phase 1:** −0.01 устранён; по каждому (ФЛ, подразделение) Приход(ОЗФУ) и Расход(ПередачаНач) совпадают; Σ Ф1+Ф2 = `НачисленияУпр.Сумма` (инвариант сохранён).

## 6. Дизайн — Phase 2 (опционально, требует подтверждения: устранение 110.26 / 128.58)

110.26/128.58 — это «начисление Бухгалтерия ↔ фактическая выплата Казна». Чтобы регистр сошёлся в ноль по Бухгалтерии (как просит критерий промта), **сумма выплаты (Расход) в балансе должна стать бухгалтерской, а Казна — коэффициентом распределения**.

Рекомендуемый вариант (**P1**): `А_ОтражениеЗПпоКазне` — единственный писатель «выплаты-закрытия» в баланс-регистр: пишет Расход в бух-суммах, распределённый по коэффициенту фактической выплаты (`РаспределениеКазна` Ф1/Ф2); `СБДС`/`РКО` больше НЕ пишут `А_ВзаиморасчетыССотрудниками`. Регистр всегда ноль. Минус: регистр становится чистым бух-балансом (не кэшем); фактический кэш Казны — в денежных регистрах.

> ⚠️ Затрагивает `ЗаполнитьИзСписанияБезнал`/`ЗаполнитьИзРКО` (перестают писать регистр) и их Σ-инвариант vs ПАП. Требует отдельного подтверждения объёма перед реализацией. На исторических месяцах (дек.2025–апр.2026) фактический кэш Казны ≠ бух-начисление — после P1 эта разница уходит в денежные регистры, а не в баланс сотрудников.

## 7. Критерии приёмки

1. ✅ Discovery построчно показывает, на каком шаге Приход ≠ Расход (выполнено в §2–§3).
2. ✅ После Phase 1 по Шишкіной: по каждому (Форма, Подразделение) `Приход(ОЗФУ) = Расход(ПередачаНачислений)` до 0.01; остаток «−0.01» устранён.
3. ✅ Инвариант не нарушен: Σ Ф1+Ф2 = `НачисленияУпр.Сумма`; `ОрганизацияБухгалтерия` всех Ф1-строк заполнена; Σ по (ФЛ, организация) = бух-итог до копейки.
4. ✅ Глобально (все ФЛ с `НачисленияУпр.Сумма ≠ 0`): часть «Приход(ОЗФУ) vs ПередачаНачислений» не разъезжается ни по одной строке.
5. ⏳ (если выбран Phase 2/P1) После перепроведения через UI 1С остаток регистра по Шишкіной = 0 по каждому (Форма, Подразделение), 110.26/128.58 устранены.
6. ✅ Файлы скопированы в основную конфигурацию (Rule #4); загрузка через `/db-load-xml -Mode Partial` + `/db-update -Dynamic+`.

## 8. Тестирование (Rule #-1, обязательно перед BSL)

- Python COM: после правок прогнать `_ОтрЗП_*` логику на эталоне (Шишкіна, дек.2025) и сверить per-(ФЛ,подр,форма): `Приход(дочерний ОЗФУ) == «Зарплата управл» == ПередачаНачислений` до 0.01.
- Перепроведение `А_ОтражениеЗПпоКазне` №1 — **только через UI 1С Enterprise** (НЕ COM: COM теряет движения/сессионные параметры).
- Глобальная проверка: запрос по всем ФЛ с `НачисленияУпр≠0`, сравнение Приход(ОЗФУ) ↔ ПередачаНачислений по строкам.
