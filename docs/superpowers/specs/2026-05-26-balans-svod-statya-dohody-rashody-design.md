# Расшифровка статей «Расходы/Доходы текущего периода» через `СтатьяДоходыРасходы` — Design

**Дата:** 2026-05-26
**Документ:** `Документ.А_ФинРез_Баланс` → `РегистрСведений.А_ОтчетБаланс_Свод`
**Функция:** `Свод_ПрочиеРасходыДоходы` в `Documents/А_ФинРез_Баланс/Ext/ObjectModule.bsl` (lines 888-1052)
**Контекст:** Канон v2 modular redesign (см. [balanse_pattern_and_roadmap.md](../../_Rarzrabotki/notebook/knowledge_Balanse/balanse_pattern_and_roadmap.md))

## 1. Проблема

Пользователь убрал статьи «Расходы текущего периода» и «Доходы текущего периода» из `ИсключенныеСтатьи()` — теперь они идут в `А_ОтчетБаланс_Свод` через `Свод_ПрочиеРасходыДоходы` (т.к. Источник ∈ `{Прочие расходы, Прочие доходы, Партии прочих расходов}`).

**Однако** `ПАП.Аналитика` для этих статей всегда = «Без аналитики» (Перечисление.СтатьиБезАналитики) — расшифровки нет. Тестируемый документ `Финансовый результат Баланс (для OLAP) 00000000004` от 30.04.2026 12:00:00: в Глобино-2 остаток `2 400,00` без указания какой реальной статьи расходов он соответствует.

## 2. Решение

Использовать `РегистрНакопления.ДвиженияДоходыРасходыПрочиеАктивыПассивы` (ДвДохРасх, тип Turnovers) для расшифровки. Тот же документ-Регистратор пишет в оба регистра одновременно:
- ПАП: статья = «Расходы текущего периода» (балансовая), аналитика = «Без аналитики»
- ДвДохРасх: статья = реальная (ПВХ.СтатьиРасходов / ПВХ.СтатьиДоходов)

Канон-образец — `Свод_СебестоимостьТоваров` (детали + плуги).

## 3. Что уже готово

- В РС `А_ОтчетБаланс_Свод` **уже добавлено измерение `СтатьяДоходыРасходы`** (тип `ChartOfCharacteristicTypesRef.СтатьиРасходов` + `СтатьиДоходов`, составной) — пользователем заранее.
- `Свод_ПрочиеРасходыДоходы` уже активна, балансирует, тянет суммы через ПАП Источник∈{ПрочиеДоходы/ПрочиеРасходы/ПартииПрочихРасходов}.
- Поле `Аналитика1` существует, типизировано как Строка.

## 4. Структура нового запроса в `Свод_ПрочиеРасходыДоходы`

### Принятая стратегия — канон §2 «детали из ДвДохРасх + плуги к ПАП»

**Источник signed Σ детали — `ДвДохРасх.Сумма`** (не `ПАП.Сумма`). Это критично:
- Σ ДвДохРасх per (Регистратор, Период, Подр, СтатьяДоходыРасходы) — точно одна строка per (документ, статья)
- Плуг (Расхождение=Истина, СтатьяДоходыРасходы пустая) компенсирует любую разницу `Σ ДвДохРасх − ПАП` по ключу (Орг, Подр, Статья, Source)
- Гарантия инварианта Σ==ПАП за счёт плугов (как Свод_СебестоимостьТоваров)

**Зона действия JOIN — только статьи `Расходы текущего периода` и `Доходы текущего периода`.** Для остальных статей источника {ПрочиеДоходы, ПрочиеРасходы, ПартииПрочихРасходов} (например «Прочие пассивы», «Прибыли и убытки» с Источник=ПрочиеРасходы) сохраняем СУЩЕСТВУЮЩУЮ логику через `ВЫРАЗИТЬ(ПАП.Аналитика)` — без JOIN. Это разделяется через UNION ALL в `втПРД` (две ветви).

### 4.1 `втПРД` — две ветви UNION ALL

**Ветвь A** — для статей «Расходы текущего периода» / «Доходы текущего периода»:
```sql
ВЫБРАТЬ
    ДДР.Организация КАК Организация,
    ЕСТЬNULL(ДДР.Подразделение, ЗНАЧЕНИЕ(Справочник.СтруктураПредприятия.ПустаяСсылка)) КАК Подразделение,
    ПАП.Статья КАК Статья,
    ПАП.Источник КАК Source,
    ЗНАЧЕНИЕ(Справочник.ОбъектыЭксплуатации.ПустаяСсылка) КАК ОбъектыЭксплуатации,
    ЗНАЧЕНИЕ(Справочник.НематериальныеАктивы.ПустаяСсылка) КАК НематериальныйАктив,
    ЗНАЧЕНИЕ(Перечисление.ТипыНалогов.ПустаяСсылка) КАК ТипНалога,
    ДДР.Статья КАК СтатьяДоходыРасходы,
    СУММА(ВЫБОР КОГДА ДДР.Период < &НачМес ТОГДА ДДР.Сумма ИНАЧЕ 0 КОНЕЦ) КАК СуммаНачальныйОстаток,
    СУММА(ДДР.Сумма) КАК СуммаКонечныйОстаток
ИЗ РегистрНакопления.ДвиженияДоходыРасходыПрочиеАктивыПассивы КАК ДДР
    ВНУТРЕННЕЕ СОЕДИНЕНИЕ РегистрНакопления.ПрочиеАктивыПассивы КАК ПАП
        ПО ДДР.Регистратор = ПАП.Регистратор
        И ДДР.Период = ПАП.Период
        И ЕСТЬNULL(ДДР.Подразделение, ЗНАЧЕНИЕ(Справочник.СтруктураПредприятия.ПустаяСсылка)) = ЕСТЬNULL(ПАП.Подразделение, ЗНАЧЕНИЕ(Справочник.СтруктураПредприятия.ПустаяСсылка))
ГДЕ
    ДДР.Организация = &Орг
    И ДДР.Период <= &КонМес
    И (ПАП.Статья = &РасхТекПер ИЛИ ПАП.Статья = &ДохТекПер)
    И ПАП.Источник В (&Ист)
    И (ТИПЗНАЧЕНИЯ(ДДР.Статья) = ТИП(ПланВидовХарактеристик.СтатьиРасходов)
        ИЛИ ТИПЗНАЧЕНИЯ(ДДР.Статья) = ТИП(ПланВидовХарактеристик.СтатьиДоходов))
СГРУППИРОВАТЬ ПО ДДР.Организация, ЕСТЬNULL(ДДР.Подразделение,...), ПАП.Статья, ПАП.Источник, ДДР.Статья
```

**Ветвь B** — для ВСЕХ остальных статей источника {ПрочиеДоходы, ПрочиеРасходы, ПартииПрочихРасходов} (как было — субконто через ВЫРАЗИТЬ ПАП.Аналитика, СтатьяДоходыРасходы=NULL):
```sql
ОБЪЕДИНИТЬ ВСЕ
ВЫБРАТЬ
    ПАП.Организация,
    ЕСТЬNULL(ПАП.Подразделение, ...) КАК Подразделение,
    ПАП.Статья КАК Статья,
    ПАП.Источник КАК Source,
    ЕСТЬNULL(ВЫРАЗИТЬ(ПАП.Аналитика КАК Справочник.ОбъектыЭксплуатации), ...) КАК ОбъектыЭксплуатации,
    ЕСТЬNULL(ВЫРАЗИТЬ(ПАП.Аналитика КАК Справочник.НематериальныеАктивы), ...) КАК НематериальныйАктив,
    ЕСТЬNULL(ВЫРАЗИТЬ(ПАП.Аналитика КАК Перечисление.ТипыНалогов), ...) КАК ТипНалога,
    NULL КАК СтатьяДоходыРасходы,
    СУММА(signed_Period<НачМес),
    СУММА(signed_все)
ИЗ РегистрНакопления.ПрочиеАктивыПассивы КАК ПАП
ГДЕ
    ПАП.Организация = &Орг
    И ПАП.Период <= &КонМес
    И ПАП.Источник В (&Ист)
    И ПАП.Статья <> &РасхТекПер И ПАП.Статья <> &ДохТекПер
    И НЕ ПАП.Статья В ИЕРАРХИИ(&Искл)
СГРУППИРОВАТЬ ПО ...
```

### 4.2 Дальше — как в каноне §2

- `втПРДСт` — Σ `втПРД` per (Орг, Подр, Статья, Source)
- `втПАП` — ПАП основная (как сейчас, signed, Источник∈&Ист, НЕ Статья В ИЕРАРХИИ(&Искл))
- `втКлючи` — РАЗЛИЧНЫЕ из ОБЪЕДИНИТЬ ВСЕ втПАП ∪ втПРДСт
- Финал:
  - **Детали** из `втПРД`: Расхождение=Ложь, `Аналитика1` = СокрЛП(ПРЕДСТАВЛЕНИЕ(СтатьяДоходыРасходы)) если заполнена, иначе fallback на ТипНалога/ОбъектыЭксплуатации/НМА
  - **Плуги** где `|втПАП.КО − втПРДСт.КО| > 0.01`: СтатьяДоходыРасходы=NULL, Аналитика1="", Расхождение=Истина, НО=Δ_НО, КО=Δ_КО

### 4.3 Sanity (pretest)

Должен подтвердить: **Σ ДвДохРасх per (Регистратор, Период, Подр)** статьи СтатьиРасходов **== Σ ПАП per тот же ключ** для статей «Расх.тек.пер.» и Источник=ПрочиеРасходы. Если расхождения — плуги компенсируют (баланс Σ==ПАП сохраняется), но детали менее точные.

## 10. Риски

1. **Σ ДвДохРасх per (Регистратор, Подр) ≠ Σ ПАП**:
   - Пример: документ Расчёт себестоимости пишет в ПАП per разные Регистратор-ИД но в ДвДохРасх сворачивается per Регистратор. **Mitigation:** плуг компенсирует.
2. **JOIN per Период точный?** ДвДохРасх.Период == ПАП.Период всегда. Если нет — JOIN с ослабленным фильтром только по Регистратору+Подразделению.
3. **Документы без ДвДохРасх записи** (например Корректировка регистра): останутся в плуге с пустой СтатьяДоходыРасходы. Это нормально (как канон §2).
4. **Регрессия Σ для статьи «Прочие расходы»**: предыдущая логика хорошо балансировала через `ВЫРАЗИТЬ(ПАП.Аналитика)` для НЕ-«Расх.тек.пер.» статей. Mitigation: для НЕ-«Расх.тек.пер.» статей в Свод_ПрочиеРасходыДоходы — JOIN на ДвДохРасх не делать (СтатьяДоходыРасходы NULL), оставить логику расчёта Аналитики1 как сейчас.

## 11. Альтернатива не принятая

- **fill-when-unique per Регистратор**: проще, но теряем разнесение многострочных документов. Отклонено.
- **Не трогать существующий запрос, только добавить JOIN в текущую структуру**: риск удвоения сумм. Отклонено.
