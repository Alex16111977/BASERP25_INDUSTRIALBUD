# Дизайн: перенос ссылок на базы SQLSERVER → localhost, переименование баз, унификация идентификатора регистра

Дата: 2026-07-15
Статус: утверждён пользователем (v2)
Базы: BaseERP (ЕРП) + внешние zup/zup2/bas_industrialbud/kazna на localhost

## 1. Задача

Пользователь переносит рабочие базы на сервер `localhost` и переименовывает 4 внешние
информационные базы. Требуется:

1. Заменить строки COM-подключения `Srvr="SQLSERVER";Ref="<старое>"` на
   `Srvr="localhost";Ref="<новое>"` по всему репозиторию (документация, Python-тесты,
   конфигурационные файлы инструментов).
2. Обновить регистр сведений `А_НастройкиПодключенияБаз`, через который конфигурация ЕРП
   получает соединения, чтобы 1С реально соединялась с переименованными базами.
3. **Унифицировать идентификатор регистра с именем базы** (`ИдентификаторБазы` = `ИмяБазы`),
   что тянет за собой правку всех ~61 вызова регистра по идентификатору.
4. Явно затронуть файлы `C:\Configuration_downloads\BASERP25\.v8-project.json` и `…\CLAUDE.md`.

### Маппинг (5 пар)

| Было (Ref / идентификатор) | Стало | Примечание |
|---|---|---|
| `BuhBud` | `bas_industrialbud` | BAS Бухгалтерія |
| `BuhKazn` | `kazna` | Казна |
| `zup_1` | `zup` | ЗУП регламентная |
| `zup_2` | `zup2` | ЗУП управленческая |
| `BaseERP` | `BaseERP` (имя не меняется) | только сервер `SQLSERVER`→`localhost` |
| `BaseERPRazr` | `BaseERPRazr` (имя не меняется) | только сервер; найдена при sweep, не в исходном списке (см. ниже) |

Во всех строках сервер `SQLSERVER` → `localhost` (включая BaseERP). Опечатка исходного
запроса (`Srvr="localhost` без закрывающей кавычки) исправлена на валидное `Srvr="localhost"`.

**BaseERPRazr (6-я база, решение принято при реализации).** Sweep обнаружил 7 файлов
(Python-тесты ВРМ + анализ Balanse), обращающихся к `Srvr="SQLSERVER";Ref="BaseERPRazr"`
(dev-копия ЕРП, `Администратор/24043`). Проверка: база существует и на localhost, и на
SQLSERVER. Не в исходном списке пользователя, но по прямой аналогии с одобренным решением
«BaseERP тоже на localhost» и универсальной темой SQLSERVER→localhost — сервер переведён на
localhost, имя не меняется. В регистр `А_НастройкиПодключенияБаз` не входит (как и BaseERP).

**BASERP25 (мёртвая ссылка, НЕ трогаем).** `_Rarzrabotki/Python/test/test_os_sravnenie.py:20`
использует `Srvr="SQLSERVER";Ref="BASERP25";Usr="cfo";Pwd="2442"`. Проверка: базы `BASERP25`
нет ни на localhost, ни на SQLSERVER — предсуществующий баг/опечатка (вероятно, имелось в виду
`BaseERP`). Вне рамок этой задачи — оставлено как есть, отмечено для пользователя.

## 2. Контекст: регистр `А_НастройкиПодключенияБаз` уже внедрён

Недавний рефакторинг (коммиты 9f9047e6, 4f590bd1, e105a4a2) вынес строки подключения из
BSL-кода в регистр сведений + модуль `А_ПодключенияБазСервер`. Конфигурация больше НЕ хранит
литерал `Srvr="SQLSERVER";Ref=…` — вместо этого вызывает по идентификатору:

```bsl
V83 = А_ПодключенияБазСервер.УстановитьСоединение("BuhBud");        // возвращает COM-соединение
Стр = А_ПодключенияБазСервер.СтрокаПодключения("zup_2");            // возвращает строку
```

Реальное имя базы (`ИмяБазы`) и сервер хранятся как ДАННЫЕ регистра. До этой задачи
идентификатор-ключ и `ИмяБазы` совпадали со СТАРЫМ именем (`BuhBud`, `zup_1`…).

### Инкапсуляция регистра

Регистр читается/пишется ТОЛЬКО в `CommonModules/А_ПодключенияБазСервер/Ext/Module.bsl`
(функция `НастройкиБазы()` — чтение по `ИдентификаторБазы`; процедура
`ЗаполнитьНастройкиПоУмолчанию()` — запись). Никакой другой код не обращается к полю
`ИдентификаторБазы` этого регистра напрямую. Вызывающие передают идентификатор строковым
аргументом в `УстановитьСоединение`/`СтрокаПодключения`.

### Метаданные регистра НЕ меняются

`InformationRegisters/А_НастройкиПодключенияБаз.xml`: измерение `ИдентификаторБазы` (Строка 50,
MainFilter), ресурсы `Сервер`/`ИмяБазы`/`Пользователь`/`Пароль` (Строка 100), реквизит
`Комментарий` (Строка 200). Имена полей остаются — меняются только ЗНАЧЕНИЯ записей.
Унификация «идентификатор = имя базы» — это изменение данных, а не структуры.

## 3. Слой 1 — литеральные строки `Srvr="SQLSERVER";Ref="X"`

Полный охват репозитория. Формат единообразный:
`v8.Connect('Srvr="SQLSERVER";Ref="zup_1";Usr="cfo";Pwd="2442"')`.

**Метод:** Python-скрипт с 5 явными парными заменами (НЕ blanket-regex по `SQLSERVER`).
Анкор на пару `Srvr="SQLSERVER";Ref="X"` гарантирует, что не заденем чужие базы и не тронем
строковые аргументы-идентификаторы в вызовах регистра (там нет `Srvr=`/`Ref=`).

| # | Ищем | Заменяем |
|---|---|---|
| 1 | `Srvr="SQLSERVER";Ref="BuhBud"` | `Srvr="localhost";Ref="bas_industrialbud"` |
| 2 | `Srvr="SQLSERVER";Ref="BuhKazn"` | `Srvr="localhost";Ref="kazna"` |
| 3 | `Srvr="SQLSERVER";Ref="zup_1"` | `Srvr="localhost";Ref="zup"` |
| 4 | `Srvr="SQLSERVER";Ref="zup_2"` | `Srvr="localhost";Ref="zup2"` |
| 5 | `Srvr="SQLSERVER";Ref="BaseERP"` | `Srvr="localhost";Ref="BaseERP"` |

**Охват файлов:** ~200 Python-тестов (`_Rarzrabotki/Python/test`,
`_Rarzrabotki/notebook/**/test`), docs (`docs/superpowers/{specs,plans,prompts}`,
`_Rarzrabotki/notebook/knowledge*`), `CLAUDE.md`. Кодировка UTF-8, замена только в
совпавших строках, отчёт по числу правок на файл.

**`.v8-project.json`** — структурные поля (не строка подключения): правится отдельно.
Записи `erp` (server→localhost, ref=BaseERP без изменений) и `buhbud`
(server→localhost, ref→bas_industrialbud). Других баз в файле нет.

**Контроль:** после sweep `grep 'Srvr="SQLSERVER"'` по репозиторию = 0.

## 5. Что НЕ трогаем

- **Метаданные регистра** (`InformationRegisters/А_НастройкиПодключенияБаз.xml`).
- **Чужой `ИдентификаторБазы`** в модулях Rarus USO2 / `СМ_WS_Обмен`,
  `ИнтеграцияС1СДокументооборот*`, `БлокировкаРаботыСВнешнимиРесурсами`,
  `РегламентныеЗаданияСлужебный` (Kazna/BASEBuh) — это поле обмена другой подсистемы.
- **Имена переменных BSL**, процедуры, логика.
- **`OlapBASERP`** — это ADO/SQL-строка (`sa`/пароль), не 1С-COM `Srvr=;Ref=`.
- **Структура типовых объектов/регистров** (feedback_no_typical_register_changes).
- **Python-скрипты, не относящиеся к подключениям** — только строки подключения.

## 6. Порядок реализации

1. Проверка Python COM: переименованные базы существуют и подключаются на localhost
   (`Srvr="localhost";Ref="bas_industrialbud";Usr="cfo";Pwd="2442"` и т.д.). Гейт для 4a/приёмки.
2. Слой 1 (sweep) + `.v8-project.json` + Слой 2c (вызовы) — Python-скрипты в worktree.
3. Слой 2b (сид), 2d (тест), 2e (комментарий) — точечные правки.
4. Контроль grep: `SQLSERVER`=0; старые идентификаторы в
   `УстановитьСоединение/СтрокаПодключения`=0; `Ref="BaseERP"` жив, имя не переименовано.
5. Rule #4: копировать изменённые файлы в основной каталог `C:\Configuration_downloads\BASERP25\`.
6. Адверсариальная верификация полноты/корректности diff (мульти-агентный workflow, read-only).
7. Загрузка конфигурации в БД (`db-load-xml`/`db-update`; учесть кэш Designer —
   feedback_designer_cache_invalidation).
8. Слой 2a: rekey живого регистра через Python COM (удалить 4 старые + создать 4 новые).
9. Пересборка 12 `.epf/.erf` (epf-build/erf-build) + win32com-smoke.
10. Приёмка Python COM: `УстановитьСоединение` для 4 новых идентификаторов даёт живое
    соединение; негативный тест на несуществующий идентификатор (пароль не течёт в ошибку);
    smoke одного документа и одного отчёта.
11. Git: коммит(ы) в ветке `claude/*`, сообщения на русском; финал автономно
    (feedback_autonomous_finish_merge_push_pr) с учётом git_push_large_files_cherry_pick.

## 7. Риски и допущения

- **Гейт:** если переименованные базы ещё не существуют на localhost — файловые/кодовые правки
  корректны, но rekey живого регистра (4a), загрузка конфигурации и приёмка не пройдут;
  в этом случае остановиться на файловых правках и сообщить пользователю.
- **Цена унификации идентификатора:** +~61 правка вызовов и пересборка 12 `.epf/.erf` сверх
  простого переименования баз; runtime-результат тот же. Принято осознанно по требованию.
- **Пересборка .epf/.erf:** Designer держит блокировки — сборка последовательная, не
  параллельная (epf_build_stub_isolation_gotcha).
- **Грабли платформы:** после `cp` .bsl в основной каталог инвалидировать кэш ConfigDumpInfo;
  частичная загрузка флагов общего модуля — сверять по факту.
- **Идемпотентность сида:** `ЗаполнитьНастройкиПоУмолчанию()` не перетирает существующие
  записи → перед повторным сидом старые ключи должны быть удалены (шаг 8).
