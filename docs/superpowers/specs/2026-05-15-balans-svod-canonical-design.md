**⚠️ КЛЮЧОВЕ ВИПРАВЛЕННЯ v1.2 (факт-чек штатного звіту + БД, лютий/ТОВ ІНДАСТРІАЛБУД):** теза v4/v1.1 «виключити `Собственные средства`/`Доходы`/`Расходы текущего периода` бо `Прибыли и убытки` компенсує» — **ХИБНА**. Факт із БД: `Расходы текущего периода` = стаття типу **АКТИВ** (+33.6М, незакриті витрати періоду — балансовий актив), `Доходы текущего периода` = **ПАСИВ** (−0.6М), `Налоги` = двостороння **АктивПассив**, `Прибыли и убытки` = **ПАСИВ** (−152.2М). **Повний набір 16 статей нетто = 0.00 → Актив=Пасив виконується БЕЗ будь-якого фільтра.** Виключення цих статей ламало баланс на −32.9М (= сума хибно виключеного). Висновок v1.2 (згодом уточнено): фільтра не робити; склад = ВСІ статті.

**⚠️ УТОЧНЕННЯ v1.3 (рішення фінансиста + перевірка реалізацією на січні):** v1.2 над-виправив. **Запит** штатного звіту фільтра по `Статья` не має — АЛЕ робочий **варіант** звіту (веде фінансист) застосовує «Не в группе из списка», що виключає `Собственные средства`/`Доходы`/`Расходы текущего периода`. Свёд повторює робочий **варіант** (презентацію), тож **фільтр виключення ПОВЕРНУТО**. Не ламає баланс бо: емпірично (`diag_filter_jan.py`) у **закритому** січні всі 3 групи мають **КонОст=0.00** (поточний P&L згорнуто) → Σ з фільтром=0.00, Актив=Пасив. «−32.9М» було лише для **відкритого** лютого. Свёд — для закритих періодів. `Статья.АктивПассив` лишається downstream (OD-9); фільтр — у BSL (OD-3 v1.3).

**Історична причина головного ризику:** у попередній сесії баг розбіжності ~40М відтворено експериментально — він виник від неконтрольованої двоступеневої агрегації + LEFT JOIN, що розмножував рядки (sN −110→−133, sK −152→−112). Захист від цього — ядро цього дизайну (OD-2).

**Єдиний недоведений ризик (key risk):** з розвідки `Обработки.ДвиженияАктивовПассивы` у попередній сесії — `ИдентификаторФинЗаписи` є зарезервованим полем, але **НЕ заповнюється при формуванні ПАП**; зв'язок ПАП↔джерело в штатній обробці реалізований через `АналитикаУчетаПоПартнерам` / `СтатьиРасходов`, а **не** через цей ключ. Отже JOIN за `ИдентификаторФинЗаписи` (Етапи 2-4) **може взагалі не працювати**. Канон закриває цей ризик двома жорсткими вимогами: блокуючий GATE перед Етапом 2 (OD-2) і самодостатність Етапу 1 без жодного JOIN (OD-8).

## 3. Архітектурний принцип

1. **СУМИ ЗАВЖДИ з `ПрочиеАктивыПассивы.ОстаткиИОбороты`** — єдине джерело сум, **без UNION-подвоєння**. Штатний `Отчёт.УправленческийБаланс` бере ТІЛЬКИ ПАП (`Reports/УправленческийБаланс/.../Template.xml:712`).
2. **Субконто — гібрид:**
   - `ПАП.Аналитика` конкретна (ОЗ, НМА) → субконто прямо з ПАП через `ВЫРАЗИТЬ`.
   - `ПАП.Аналитика = СтатьиБезАналитики` → субконто LEFT JOIN з балансового регістра-джерела за `ИдентификаторФинЗаписи` (спільний ключ). **JOIN тільки збагачує субконто, суми лишаються з ПАП.**
3. **Регістр-джерело НЕ дає сум** — лише розшифровку. Жодного UNION з регістрів-джерел.
4. `ВЫРАЗИТЬ` — **тільки в SELECT**. `СГРУППИРОВАТЬ ПО Б.Аналитика` (composite як-є). Винесення `ВЫРАЗИТЬ` у GROUP BY → злиття груп через NULL → втрата Σ (перевірено в минулій сесії — не повторювати).
5. **Етап 1 — чистий ПАП, нуль JOIN, нуль залежності від `ИдентификаторФинЗаписи`.** Це робить Етап 1 самодостатнім deliverable (OD-8): робочий баланс по статтях існує незалежно від того, чи спрацює ключ для Етапів 2-4.

### Підхід реалізації запиту: **B — ступінчасті ВТ з предагрегованим джерелом** (затверджено)

- Базова ВТ: `ПАП.ОстаткиИОбороты(&НачП, &КонП=КонецДня(КонМес), Авто, , (орг+ВключатьДочерние) И НЕ Статья В ИЕРАРХИИ(&ИсключенныеСтатьи))` — **фільтр виключення 3 груп** (v1.3 OD-3), розклад `ВЫРАЗИТЬ` у SELECT, `СГРУППИРОВАТЬ ПО Б.Организация, Б.Подразделение, Б.Статья, Б.Аналитика`, `ИМЕЮЩИЕ` відсікає рядки де всі 4 суми = 0.
- Етапи 2-4: LEFT JOIN до **предагрегованого підзапиту** регістра-джерела (`ВЫБРАТЬ ... СГРУППИРОВАТЬ ПО ИдентификаторФинЗаписи` → гарантовано ≤1 рядок на ключ), що збагачує субконто-виміри статей етапу. Суми не чіпаються.
- Відхилено: **A** (монолітний LEFT JOIN — повертає баг розмноження рядків ~40М); **C** (домерж у BSL — надлишковий).

## 5. Зафіксовані проєктні рішення (OD-1 … OD-7)

### OD-1 — `Source` = **гібрид** (рішення фінансиста)

- **Етап 1:** `Source = ЗНАЧЕНИЕ(Перечисление.А_ИсточникБаланса.ПрочиеАктивыПассивы)` (усе реально з ПАП → точна звірка зі штатним звітом).
- **Етапи 2-4:** `Source = регістр-збагачувач` (РасчетыСКлиентами / РасчетыСПоставщиками / СебестоимостьТоваров / ДенежныеСредстваБезналичные / ДенежныеСредстваНаличные / ПрочиеРасходы). Сума все одно з ПАП — `Source` означає «з якого регістру взято РОЗШИФРОВКУ рядка», даючи drill-down у Power BI.
- **Передумова:** `Перечисление.А_ИсточникБаланса` має лише 3 значення. Для Етапів 3-4 фінансисту треба **додати значення enum** (мінімум: СебестоимостьТоваров, ДенежныеСредстваБезналичные, ДенежныеСредстваНаличные, ПрочиеРасходы). Фінансист керує метаданими вручну — це **передумова-ворота кожного етапу 2-4 (підтвердження + за потреби додавання enum)**, не блокер.
- **Документований fallback:** якщо drill-down по джерелу розшифровки фінансисту НЕ потрібен → спрощення «`Source = ПрочиеАктивыПассивы` завжди» (тоді enum не розширюється). Це **єдине справді бізнес-рішення** — фіксується підтвердженням фінансиста перед Етапом 2.

### OD-2 — Захист від розмноження рядків (ядро дизайну, обов'язково всі 3)

1. **Вимога 1 — БЛОКУЮЧИЙ GATE перед Етапом 2 (Rule #-1, до будь-якого BSL).** Найперший крок Етапу 2 — Python COM тест придатності ключа:
   ```
   ВЫБРАТЬ КОЛИЧЕСТВО(*) КАК К ИЗ РегистрНакопления.ПрочиеАктивыПассивы.Остатки(&Д) ГДЕ ИдентификаторФинЗаписи <> ""
   ```
   плюс перевірка 1:1 з регістром-джерелом для статей етапу.
   **Якщо `К = 0` / поле порожнє / зв'язок не 1:1 → Етапи 2-4 БЛОКУЮТЬСЯ.** План **не сміє мовчки** припускати, що ключ працює і **не робить автоматичний silent-fallback**. Замість цього — **ескалація фінансисту** з документованими альтернативами ключа: `Регистратор + Контрагент`, або `АналитикаУчетаПоПартнерам` / `СтатьиРасходов` (як у штатній `Обработки.ДвиженияАктивовПассивы` — підтверджено розвідкою: ПАП НЕ заповнює `ИдентификаторФинЗаписи`, зв'язок там через ці аналітики). Вибір альтернативного ключа — рішення фінансиста, після чого пре-тест повторюється для нового ключа.
2. **Джерело в LEFT JOIN — тільки предагрегований підзапит** (`СГРУППИРОВАТЬ ПО <ключ>`) → ≤1 рядок на ключ.
3. **Пост-інваріант:** Σ по `Статья` після етапу == Σ по `Статья` Етапу 1 (до копійки). Зміна Σ = регрес → відкат.

### OD-3 — Фільтр виключення 3 груп ПОВЕРНУТО (v1.3, рішення фінансиста, closed-period-safe)

- **BSL застосовує** `НЕ Статья В ИЕРАРХИИ(&ИсключенныеСтатьи)`, де `ИсключенныеСтатьи` = `Собственные средства`, `Доходы текущего периода`, `Расходы текущего периода` (пошук по Наименование). Це повторює робочий **варіант** штатного `Отчёт.УправленческийБаланс` «Не в группе из списка», який веде фінансист (презентація для стейкхолдерів).
- **Чому не ламає Актив=Пасив:** свёд — для **закритих** періодів. Емпірично (`diag_filter_jan.py`, січень/ТОВ): усі 3 групи мають `СуммаКонечныйОстаток = 0.00` (поточний P&L згорнуто, Собств. кошти порожні) → Σ КонОст з фільтром = **0.00**, Актив=Пасив зберігається. Перевірено Test 1/2/3 (січень): rows=46, 711 рядків, 14 статей регістр↔ПАП до копійки, Σ=0.00.
- **Застереження (відкритий період):** для НЕзакритого місяця (напр. лютий) `Расходы текущего периода` ще накопичується (КонОст≠0) → фільтр там зламав би баланс на ту суму. Свёд проводити лише за **закриті** періоди. (Документовано; контроль — Σ КонОст ≈ 0 у Test 3, який впаде якщо період відкритий.)

- `Прибыли и убытки` — НЕ виключається (окрема коренева стаття, у балансі).
- Той самий фільтр застосовується у BSL ТА у звірці Test 3 з обох боків (OD-5).

### OD-5 — Test 3 (критерій успіху)
