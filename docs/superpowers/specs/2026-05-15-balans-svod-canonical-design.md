## 3. Архітектурний принцип

1. **СУМИ ЗАВЖДИ з `ПрочиеАктивыПассивы.ОстаткиИОбороты`** — єдине джерело сум, **без UNION-подвоєння**. Штатний `Отчёт.УправленческийБаланс` бере ТІЛЬКИ ПАП (`Reports/УправленческийБаланс/.../Template.xml:712`).
2. **Субконто — гібрид:**
   - `ПАП.Аналитика` конкретна (ОЗ, НМА) → субконто прямо з ПАП через `ВЫРАЗИТЬ`.
   - `ПАП.Аналитика = СтатьиБезАналитики` → субконто LEFT JOIN з балансового регістра-джерела за `ИдентификаторФинЗаписи` (спільний ключ). **JOIN тільки збагачує субконто, суми лишаються з ПАП.**
3. **Регістр-джерело НЕ дає сум** — лише розшифровку. Жодного UNION з регістрів-джерел.
4. `ВЫРАЗИТЬ` — **тільки в SELECT**. `СГРУППИРОВАТЬ ПО Б.Аналитика` (composite як-є). Винесення `ВЫРАЗИТЬ` у GROUP BY → злиття груп через NULL → втрата Σ (перевірено в минулій сесії — не повторювати).
5. **Етап 1 — чистий ПАП, нуль JOIN, нуль залежності від `ИдентификаторФинЗаписи`.** Це робить Етап 1 самодостатнім deliverable (OD-8): робочий баланс по статтях існує незалежно від того, чи спрацює ключ для Етапів 2-4.

### Підхід реалізації запиту: **B — ступінчасті ВТ з предагрегованим джерелом** (затверджено)

- Базова ВТ: `ПАП.ОстаткиИОбороты(&НачП, &КонП=КонецДня(КонМес), Авто, , <фільтр орг + В ИЕРАРХИИ>)` з фільтром виключення (OD-3), розклад `ВЫРАЗИТЬ` у SELECT, `СГРУППИРОВАТЬ ПО Б.Организация, Б.Подразделение, Б.Статья, Б.Аналитика`, `ИМЕЮЩИЕ` відсікає рядки де всі 4 суми = 0.
- Етапи 2-4: LEFT JOIN до **предагрегованого підзапиту** регістра-джерела (`ВЫБРАТЬ ... СГРУППИРОВАТЬ ПО ИдентификаторФинЗаписи` → гарантовано ≤1 рядок на ключ), що збагачує субконто-виміри статей етапу. Суми не чіпаються.
- Відхилено: **A** (монолітний LEFT JOIN — повертає баг розмноження рядків ~40М); **C** (домерж у BSL — надлишковий).

## 5. Зафіксовані проєктні рішення (OD-1 … OD-7)

### OD-1 — `Source` = **гібрид** (рішення фінансиста)

- **Етап 1:** `Source = ЗНАЧЕНИЕ(Перечисление.А_ИсточникБаланса.ПрочиеАктивыПассивы)` (усе реально з ПАП → точна звірка зі штатним звітом).
- **Етапи 2-4:** `Source = регістр-збагачувач` (РасчетыСКлиентами / РасчетыСПоставщиками / СебестоимостьТоваров / ДенежныеСредстваБезналичные / ДенежныеСредстваНаличные / ПрочиеРасходы). Сума все одно з ПАП — `Source` означає «з якого регістру взято РОЗШИФРОВКУ рядка», даючи drill-down у Power BI.
- **Передумова:** `Перечисление.А_ИсточникБаланса` має лише 3 значення. Для Етапів 3-4 фінансисту треба **додати значення enum** (мінімум: СебестоимостьТоваров, ДенежныеСредстваБезналичные, ДенежныеСредстваНаличные, ПрочиеРасходы). Фінансист керує метаданими вручну — це **передумова-ворота кожного етапу 2-4 (підтвердження + за потреби додавання enum)**, не блокер.
- **Документований fallback:** якщо drill-down по джерелу розшифровки фінансисту НЕ потрібен → спрощення «`Source = ПрочиеАктивыПассивы` завжди» (тоді enum не розширюється). Це **єдине справді бізнес-рішення** — фіксується підтвердженням фінансиста перед Етапом 2.

### OD-2 — Захист від розмноження рядків (ядро дизайну, обов'язково всі 3)

1. **Вимога 1 — БЛОКУЮЧИЙ GATE перед Етапом 2 (Rule #-1, до будь-якого BSL).** Найперший крок Етапу 2 — Python COM тест придатності ключа:
   ```
   ВЫБРАТЬ КОЛИЧЕСТВО(*) КАК К ИЗ РегистрНакопления.ПрочиеАктивыПассивы.Остатки(&Д) ГДЕ ИдентификаторФинЗаписи <> ""
   ```
   плюс перевірка 1:1 з регістром-джерелом для статей етапу.
   **Якщо `К = 0` / поле порожнє / зв'язок не 1:1 → Етапи 2-4 БЛОКУЮТЬСЯ.** План **не сміє мовчки** припускати, що ключ працює і **не робить автоматичний silent-fallback**. Замість цього — **ескалація фінансисту** з документованими альтернативами ключа: `Регистратор + Контрагент`, або `АналитикаУчетаПоПартнерам` / `СтатьиРасходов` (як у штатній `Обработки.ДвиженияАктивовПассивы` — підтверджено розвідкою: ПАП НЕ заповнює `ИдентификаторФинЗаписи`, зв'язок там через ці аналітики). Вибір альтернативного ключа — рішення фінансиста, після чого пре-тест повторюється для нового ключа.
2. **Джерело в LEFT JOIN — тільки предагрегований підзапит** (`СГРУППИРОВАТЬ ПО <ключ>`) → ≤1 рядок на ключ.
3. **Пост-інваріант:** Σ по `Статья` після етапу == Σ по `Статья` Етапу 1 (до копійки). Зміна Σ = регрес → відкат.

- Виключити з регістра 3 групи/статті. `СтатьиАктивовПассивов` **ієрархічний**: `Собственные средства` = **ГРУПА** (родитель «Источники финансирования»); `Доходы текущего периода` / `Расходы текущего периода` = **кореневі статті**. - Етап 1 — окремий завершений цикл реалізації з власним PASS-критерієм (OD-5). Закриття Етапу 1 (commit) **не залежить** від результату GATE OD-2.
- Це знімає key-risk з критичного шляху: робочий результат гарантовано є незалежно від долі Етапів 2-4.

## 6. Алгоритм `ОбработкаПроведения` (інваріант для всіх етапів)

```bsl
Процедура ОбработкаПроведения(Отказ, РежимПроведения)
    НачМесяца = НачалоМесяца(Месяц);
    КонМесяца = КонецМесяца(Месяц);
    // 1. Дублікат-захист: SELECT ПЕРВЫЕ 1 з Документ.А_ФинРез_Баланс
    //    за Организация + Месяц(МЕЖДУ Нач/Кон) + ВключатьДочерние, Ссылка<>ТекущийДок,
    //    НЕ ПометкаУдаления, Проведен → якщо є: Отказ=Истина, повідомлення, Возврат.
    // 2. Движения.А_ОтчетБаланс_Свод.Записывать = Истина;
    // 3. Запрос.Текст = СформироватьЗапросСверткиБаланса();
    //    параметри: &НачалоПериода=НачМесяца, &КонецПериода=КонецДня(КонМесяца),
    //               &Организация, &ВключатьДочерние
    // 4. Движения.А_ОтчетБаланс_Свод.Загрузить(Запрос.Выполнить().Выгрузить());
КонецПроцедуры
```

`ОбработкаЗаполнения`: `Организация = А_Привилегированный.А_ПолучитьОрганизациюУпр()`, `Месяц = НачалоМесяца(ТекущаяДатаСеанса())` якщо не заповнені.

`СформироватьЗапросСверткиБаланса()` — будується ПІД фактичні 17 вимірів БД: типізовані `ВЫРАЗИТЬ` для тих типів TypeSet, що мають окремий вимір (`ОбъектыЭксплуатации`, `НематериальныйАктив`, `Номенклатура`, `Контрагент`, `Партнер`, `Склад`, `ФизическоеЛицо`, `ДенежныеСредства`); решта → `Аналитика3 = ПРЕДСТАВЛЕНИЕ(Б.Аналитика)`; `ОбъектРасчетов = ПустаяСсылка` для Етапу 1; `Source` per OD-1; `Аналитика1/2 = ""` для Етапу 1. **Жодних колонок під неіснуючі виміри** (стара чернетка SELECT-ила `ТипНалога/СтатьяДвиженияДС/...` — їх у БД немає, `Загрузить()` впаде).

## 7. План верифікації (Rule #-1) — інваріантний цикл на КОЖЕН етап

1. **Python COM пре-тест запиту** (`_Rarzrabotki/Python/test/`): запит етапу 1:1 як піде в BSL; для етапів 2-4 — додатково тест 1:1 `ИдентификаторФинЗаписи`. Asserts: rows>0; балансова рівність `КонОст≈НачОст+Приход−Расход` (tol 0.01); субконто статей етапу непорожні; виключені статті відсутні; (для 2-4) Σ по статтях не змінилась.
2. Переписати/доповнити `СформироватьЗапросСверткиБаланса` під фактичну структуру.
3. `cp` BSL/XML у main config (Rule #4) → `/cf-validate` → `/db-load-xml -Mode Partial` → `/db-update -Dynamic+`. БД заблокована Конфигуратором → попросити користувача закрити, **не обходити**.
4. **Test 2:** проведення (Дата опівдні TZ-safe, режим `РежимЗаписиДокумента.Проведение`). Asserts: Проведен; рядки за Регистратор>0; 4 ресурси балансуються; перепроведення idempotent.
5. **Test 3:** звірка з ПАП до копійки (OD-5) + субконто етапу заповнені + (2-4) Σ по статтях == Етап 1.
6. PASS усіх → `cp` у main config → git commit.

> Python COM: ітерувати ValueTable через `tz.Количество()`/`tz.Получить(i)`; дати опівдні (`datetime(2026,2,1,12,0,0)`) проти timezone-зсуву.

## 8. Розбивка етапів (реалізація — окремими циклами writing-plans)

| Етап | Статті | Механізм | Передумова | Критерій |
|---|---|---|---|---|
| **1 (MVP)** | 1-6 | `ВЫРАЗИТЬ(ПАП.Аналитика)` + фільтр 3 груп; Source=ПАП; **0 JOIN** | — (самодостатній, OD-8) | Test 3: Актив=Пасив (після фільтра), збіг з ПАП до копійки (лютий/ТОВ — своя цифра) |
| **2** | 7-10 | LEFT JOIN `РасчетыСКлиентами`/`РасчетыСПоставщиками` (предагрег.) → `ОбъектРасчетов`; Source=регістр | **GATE OD-2 PASS** (блокуючий) + підтвердження OD-1 фінансистом | ОбъектРасчетов заповнено; Σ по статтях не змінилась |
| **3** | 11-15 | LEFT JOIN `СебестоимостьТоваров`/`ДенежныеСредства*` (предагрег.) → Номенклатура/Склад/ДенежныеСредства/ФизЛицо; Source=регістр | GATE OD-2 PASS; Enum +значення (фінансист) | Субконто заповнено; Σ не змінилась |
| **4** | 16 | LEFT JOIN зарплатні/`ПрочиеРасходы` (предагрег.) → ФизЛицо + Аналитика2=ПРЕДСТ.(ВидОперацииЗП); Source=регістр | GATE OD-2 PASS; Enum +значення | Субконто заповнено; Σ не змінилась |

Черговість 2→3→4 не критична (рішення фінансиста). **Етап 1 — перший, окремий і завершений deliverable (OD-8); Етапи 2-4 стартують ТІЛЬКИ після PASS блокуючого GATE OD-2.** Провал GATE → Етапи 2-4 не виконуються, Етап 1 лишається робочим результатом.
