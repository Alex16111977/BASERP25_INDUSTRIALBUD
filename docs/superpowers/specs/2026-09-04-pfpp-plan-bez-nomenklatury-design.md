## 1. Задача

Разделить источники плана и факта, каждый берёт данные из своего места.

1. **План** строится ТОЛЬКО из реквизитов `Справочник.А_СтруктураСебестоимости.Комплектующие`:
   загальна назва — `К.ОбщееНазвание`, аналітика — `СокрЛП(К.НоменклатураСС)`, одиниця —
   `К.ЕдиницаОбщееНазвание`. Реквизит `Номенклатура` в плане не используется нигде.
2. **Факт** берётся из карточки номенклатуры: загальна назва — `Номенклатура.А_ОбщееНазваниеНоменклатуры`
   (как сейчас), аналітика — `СокрЛП(Номенклатура.Наименование)` текстом, как в бухгалтерском близнеце.
   Ссылка на карточку уходит в отдельное измерение `Номенклатура`.

Причина (кейс пользователя, СС «МД ООН Админ»): пять строк спецификации с назвою «Мінеральна вата 100»
привязаны к карточке «EKOBOARD 50*610*1250», у которой карточная назва «Мінеральна вата 50». Отчёт брал
назву плана из карточки, и план 250 пач на дім уезжал под «вату 50».

| Строки СС | Назва строки | Назва карточки | Кол на дім |
|---|---|---|---|
| 34, 36, 37, 190, 192 | Мінеральна вата 100 | Мінеральна вата 50 | 250 |
| 35, 191 | Мінеральна вата 50 | карточки нет | 45 |

После правки (× `КоличествоДомов` = 4): план «Мінеральна вата 100» = 1000 пач / 392 993,96,
план «Мінеральна вата 50» = 180 пач / 75 810,32.

## 2. Приоритет (решение пользователя 04.09.2026)

Отчёт ведётся ради четырёх структур себестоимости: **МД ООН 2026, МД ООН Админ,
МД IRС 2026 15 м, МД IRС 2026 30 м**. Эталоны, приёмка и разбор расхождений — по ним.
ВООЗ, ОРІЛЬ, ПРООН проверяются только на отсутствие ошибок.

## 4. Дизайн

### 4.1. Плановая ветка грейна (ветка 2, материалы)

| Поле грейна | Было | Стало |
|---|---|---|
| `ОбщееНазвание` | `ВЫБОР КОГДА К.Номенклатура = ПустаяСсылка ТОГДА К.ОбщееНазвание ИНАЧЕ К.Номенклатура.А_ОбщееНазваниеНоменклатуры КОНЕЦ` | `К.ОбщееНазвание` |
| `Единица` | `К.Номенклатура.ЕдиницаИзмерения` | `К.ЕдиницаОбщееНазвание` |
| `Аналитика` | `К.НоменклатураСС` | `СокрЛП(К.НоменклатураСС)` |
| `Номенклатура` (новое поле) | — | `ЗНАЧЕНИЕ(Справочник.Номенклатура.ПустаяСсылка)` |
| остальные поля ветки | — | без изменений |

После правки в плановой ветке нет ни одного обращения к `К.Номенклатура`.

### 4.2. Фактовая ветка грейна (ветка 5, закупки)

| Поле грейна | Было | Стало |
|---|---|---|
| `ОбщееНазвание` | `СТ.АналитикаУчетаНоменклатуры.Номенклатура.А_ОбщееНазваниеНоменклатуры` | без изменений |
| `Аналитика` | `СТ.АналитикаУчетаНоменклатуры.Номенклатура` (ссылка) | `СокрЛП(СТ.…Номенклатура.Наименование)` (текст) |
| `Номенклатура` (новое поле) | — | `СТ.АналитикаУчетаНоменклатуры.Номенклатура` (ссылка) |
| `НоменклатураНаименование` | наименование карточки | без изменений (остаётся; дублирует аналітику, трогать не будем) |
| ресурсы, фильтры, `Стоимость` с НДС | — | без изменений (инвариант) |

Никакой переклейки факта на назву спецификации нет: факт живёт по данным карточки.

### 4.3. Карта «назва → етап» (`МаппингОбщееНазваниеЭтап`)

Ключ строится по `К.ОбщееНазвание.Наименование`, отбор по заполненной назве строки. Обращение к карточке
убирается. Разнос факта по етапу продолжает работать: имён загальних назв, которые встречаются только
у карточек, ноль, поэтому карточная назва факта всегда находит ключ в карте.

### 4.4. Постобработки

- `ЗаполнитьЭтапФактМатериалов`: строка факта определяется по заполненному новому измерению `Номенклатура`
  (раньше по `ТипЗнч(Аналитика) = Номенклатура`); загальна назва берётся из поля `ОбщееНазвание` строки,
  ключ — `СокрЛП(имя)`. Обращение `Аналитика.А_ОбщееНазваниеНоменклатуры` уходит, так как аналітика стала текстом.
- `КлючГруппыПланНаФакт`: ветка «по ссылке номенклатуры» читает новое поле `Номенклатура`, а не `Аналитика`;
  ветка «по тексту» работает как раньше. Правила ETC 1, 2, 4 не меняются.
- `ЗаполнитьПланНаФакт`: синтетическая строка получает `Номенклатура` = пустая ссылка; при заполненной
  загальній назві `Аналитика` = `""`, иначе текст образца.

### 4.5. Таблица значений и схема компоновки

- `СоздатьПустуюТаблицу`: `Аналитика` остаётся составной (труд и EV кладут туда ссылки на работу и физлицо),
  добавляется колонка `Номенклатура` типа `СправочникСсылка.Номенклатура`. Грейн становится 19 колонок,
  порядок колонок во ВСЕХ шести ветках UNION синхронизируется.
- `Template.xml`: добавляется поле-измерение `Номенклатура` с титулом «Номенклатура» (ru и uk),
  в структуру группировок по умолчанию не входит. Правка только Python-скриптом с проверкой числа замен
  и контролем разбора XML (LESSONS §7: файл на табах).

### 4.6. Две копии

Правки идут в обе копии. Корневой `Templates/ОсновнаяСхемаКомпоновкиДанных.xml` конфигурационного отчёта
НЕ копируется из внешнего (там свой uuid макета). Внешний `.erf` собирается против свободной базы с БСП
(`bas_industrialbud`, `cfo`/`2442`), конфигурационная копия грузится частичной загрузкой XML с обновлением
конфигурации базы.

По четырём приоритетным структурам прогноз либо не меняется, либо становится точнее.
Рост целиком приходится на ПРООН, ВООЗ и ОРІЛЬ: там 62 из 69 строк с назвой-синонимом в спецификации,
их план встанет под назву строки, а факт останется под назвой карточки и не будет его гасить.
Это следствие правила «план читается как спецификация» и лечится чисткой данных, не кодом.
База знаний фиксирует, что 16.07.2026 обратная правка была откачена именно из-за такого роста
(FINDINGS §18: ВООЗ +242 677,19, ОРІЛЬ +28 632,31). Сейчас решение принято осознанно, приоритет отдан
корректности плана по четырём рабочим структурам.

Единица: появится у 555 строк плана, где сейчас пусто, и сменится у 134 строк (снимок из СС вместо
текущей единицы карточки).

## 7. Инварианты, которые НЕ трогаем

Факт материалов — закупки с НДС (`СебестоимостьТоваров.Стоимость`, `Приход`, регистратор
`ПриобретениеТоваровУслуг`, подразделение из `СС.ПодразделениеЗакупки` по иерархии); факт не двоится
(соединение с `ВТ_Подр1` по истине); план = норма × `СС.КоличествоДомов`; блок «1. Праця» — только часы,
план работ только с единицей «чол/год»; украинские титулы; служебные имена полей схемы не переводятся;
одинаковый набор и порядок колонок во всех ветках UNION.
