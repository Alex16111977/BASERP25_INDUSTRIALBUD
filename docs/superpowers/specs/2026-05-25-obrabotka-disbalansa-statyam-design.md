## 1. Контекст и проблема

### 1.1 Проблема

`РегистрСведений.А_ОтчетБаланс_Свод` (записывается документом `Документ.А_ФинРез_Баланс`) содержит **плуги-балансировки** с пометкой `Расхождение=Истина` когда Σ деталей `РасчетыСКлиентамиПоСрокам` / `РасчетыСПоставщикамиПоСрокам` (РСКПС/РСППС) не равна Σ `ПрочиеАктивыПассивы` (ПАП) по ключу `(Орг, Подр, Статья, Source)`.

Эти плуги — индикатор что **первичные документы** периода записали движения в РСКПС/РСППС и в ПАП **рассогласованно**. Типовые причины (по результатам декабря 2025 + анализа апреля 2026):
- **C1** документ написал в РСКПС/РСППС но не написал парную проводку в ПАП по статье долга → возникает «time-of-flight asymmetry»: ПАП пишет на статью ВыданныеАвансы вместо ЗадолженностиПередПоставщиками, потому что в момент проведения остатки по ОР еще не показывали долг
- **C2** частичная асимметрия — ПАП и РСППС оба пишут, но на разные суммы / разные статьи

**Текущий процесс устранения** — вручную:
1. Аналитик ищет плуги через SQL/Python COM
2. По каждой группе делает FULL OUTER JOIN ПАП vs РСКПС/РСППС через `ДокументРегистратор` → находит конкретные документы
3. Передаёт список пользователю на ручное перепроведение через UI

Это занимает часы, и каждый раз приходится переписывать одни и те же запросы.

### 1.2 Решение — автоматизировать через внешний отчёт

Доработать существующий пустой каркас `_Rarzrabotki/Обработки/А_ОбработкаДисбалансаПоСтатьямБаланса.xml`:
- Кнопка «Анализ расхождений» → находит первичные документы-виновники, заполняет ТЧ
- Кнопка «Перепровести» → перепроводит документы в транзакциях per-документ
- Результат немедленно виден в ТЧ: какие документы исправились, по каким осталось расхождение, какие упали с ошибкой

### 1.3 Не входит в scope

- Не трогаем типовые регистры (memory `feedback_no_typical_register_changes`)
- Не правим `DvAktPas` или `Свод_РасчетыСПартнерами` (есть отдельный FIX-2026-05-23 для случая ПереносАванса; наш случай — другой класс time-of-flight)
- Не обрабатываем Source ∈ {СебестоимостьТоваров, ДенежныеСредства, ПрочиеРасходыДоходы, ПрочиеАктивыПассивы_Прямой, ОплатаТруда} — для них логика поиска виновников другая (отдельный движок на каждый Source)
- Не работаем с Партнёр=НашеПредприятие (внутрифирменные взаиморасчёты — отдельная история)

## 2. Архитектура

**Тип объекта:** внешний отчёт (ExternalReport) — каркас уже создан с реквизитами `НачалоПериода` / `ОкончаниеПериода`. Меняем только: добавляем 2 реквизита + 1 ТЧ + ObjectModule.bsl с логикой + Form/Module.bsl с обработчиками + Form.xml с двумя кнопками и колонками ТЧ.

**Поток данных:**
```
Пользователь задаёт период
        ↓
[Анализ расхождений] → запрос А_ОтчетБаланс_Свод (плуги РСКПС/РСППС)
        ↓
для каждого месяца с плугами:
   запрос FULL OUTER ПАП vs РСКПС/РСППС через ДокументРегистратор
        ↓
ТЧ ДокументыРасхождения заполняется виновниками (Δ ≠ 0)
        ↓
Пользователь жмёт [Перепровести]
        ↓
per-документ транзакция: НачатьТранзакцию → Записать(Проведение) → ЗафиксироватьТранзакцию
        ↓
пересчёт Δ для перепроведённого документа → обновление НовоеСостояние в ТЧ
```

**Архитектурный шаблон:** копия паттерна `_Rarzrabotki/Обработки/А_ОбработкаДисбалансаПоПодразделениям` — те же 4 файла, та же обёртка `НаКлиенте → НаСервере → метод объекта`. Меняется только содержательная логика поиска виновников.

| `ОшибкаТекст` | Строка(500) | ОписаниеОшибки() если перепроведение упало |

## 4. Алгоритм `АнализРасхождений()`

### 4.1 Подготовка

1. Очистить ТЧ `ДокументыРасхождения`
2. Валидация: `НачалоПериода`/`ОкончаниеПериода` заполнены (иначе ошибка)
3. Получить организацию из контекста (через справочник или константу — ТОВ ІНДАСТРІАЛБУД, ЕДРПОУ 40645273)

### 4.2 Сбор плугов

Один запрос к `А_ОтчетБаланс_Свод`:

```sql
ВЫБРАТЬ РАЗЛИЧНЫЕ
    Т.Регистратор.Месяц КАК Месяц,
    Т.Подразделение.Код КАК ПодрКод,
    Т.Подразделение КАК Подр,
    Т.Статья КАК Статья,
    Т.Source КАК Source
ИЗ РегистрСведений.А_ОтчетБаланс_Свод КАК Т
ГДЕ Т.Расхождение = ИСТИНА
    И Т.Регистратор.Месяц МЕЖДУ &НачалоПериода И &ОкончаниеПериода
    И Т.Source В (
        ЗНАЧЕНИЕ(Перечисление.ИсточникиУправленческогоБаланса.РасчетыСКлиентамиПоСрокам),
        ЗНАЧЕНИЕ(Перечисление.ИсточникиУправленческогоБаланса.РасчетыСПоставщикамиПоСрокам))
    И Т.Организация = &Орг
```

Если задан `Подразделение` — добавить фильтр `И Т.Подразделение В ИЕРАРХИИ (&ВыбПодр)`.

### 4.3 FULL OUTER JOIN ПАП vs РСКПС/РСППС per месяц

Группируем плуги по `Месяц`. Из результата §4.2 для каждого месяца формируем 2 массива параметров:
- `МасивКодов` — уникальные `Подр.Код` для этого месяца
- `МасивСтатей` — уникальные `Статья` для этого месяца

Затем для каждого месяца — один большой запрос (по всем найденным `(Подр, Статья, Source)` сразу):

```sql
// втПАП — все движения ПАП этого месяца по нужным (Подр.Код, Статья, Source)
ВЫБРАТЬ
    Т.Регистратор КАК Док,
    Т.Подразделение.Код КАК ПодрКод,
    Т.Статья КАК Статья,
    Т.Источник КАК Source,
    СУММА(ВЫБОР КОГДА Т.ВидДвижения = ЗНАЧЕНИЕ(ВидДвиженияНакопления.Приход)
                ТОГДА Т.Сумма ИНАЧЕ -Т.Сумма КОНЕЦ) КАК ПАП_Sign
ПОМЕСТИТЬ втПАП
ИЗ РегистрНакопления.ПрочиеАктивыПассивы КАК Т
ГДЕ Т.Период МЕЖДУ &НачМес И &КонМес
    И Т.Организация = &Орг
    И Т.Подразделение.Код В (&МасивКодов)
    И Т.Источник В (&РСКПС, &РСППС)
    И Т.Статья В (&МасивСтатей)
СГРУППИРОВАТЬ ПО ...
;
// втРС — РСКПС + РСППС (через РегистраторРасчётов), inverted ДолгУпр для поставщиков
ВЫБРАТЬ
    Р.ДокументРегистратор КАК Док,
    ВЫБОР КОГДА Р.ОбъектРасчетов.Подразделение = ПустаяСсылка
        ТОГДА Р.ОбъектРасчетов.Договор.Подразделение.Код
        ИНАЧЕ Р.ОбъектРасчетов.Подразделение.Код
    КОНЕЦ КАК ПодрКод,
    -- Для поставщиков (Source=РСППС) DolgSign инвертируется, для клиентов нет
    -- Это знаем из canon Свод_РасчетыСПартнерами: для статьи ЗПП пишется -ДолгУпр
    -- Поэтому Δ = ПАП_Sign + РСППС_DolgSign (без инверсии в формуле, инверсия учтена в стороне РСППС)
    СУММА(ВЫБОР КОГДА Р.ВидДвижения = ЗНАЧЕНИЕ(ВидДвиженияНакопления.Приход)
                ТОГДА -Р.ДолгУпр  -- инвертируем здесь чтобы Δ = ПАП - (-РСППС) = ПАП + сюда подставленная инверсия
                ИНАЧЕ Р.ДолгУпр КОНЕЦ) КАК РСППС_Sign
ПОМЕСТИТЬ втРСППС
ИЗ РегистрНакопления.РасчетыСПоставщикамиПоСрокам КАК Р
    ЛЕВОЕ СОЕДИНЕНИЕ РегистрСведений.АналитикаУчетаПоПартнерам КАК АП
        ПО Р.АналитикаУчетаПоПартнерам = АП.КлючАналитики
ГДЕ Р.Период МЕЖДУ &НачМес И &КонМес
    И АП.Организация = &Орг
    И АП.Партнер <> &НашеПредприятие
    И (выражение Подр.Код через ОР с fallback) В (&МасивКодов)
СГРУППИРОВАТЬ ПО ...
;
-- Аналогично втРСКПС (для клиентов: без инверсии в РСКПС_Sign — для статьи Долг клиента знак прямой)
ОБЪЕДИНИТЬ ВСЕ
...
;
// Финал: FULL OUTER + фильтр |Δ| > 0.01
ВЫБРАТЬ
    ЕСТЬNULL(ПАП.Док, РС.Док) КАК Док,
    ЕСТЬNULL(ПАП.ПодрКод, РС.ПодрКод) КАК ПодрКод,
    ЕСТЬNULL(ПАП.Статья, РС.Статья) КАК Статья,
    ЕСТЬNULL(ПАП.Source, РС.Source) КАК Source,
    ЕСТЬNULL(ПАП.ПАП_Sign, 0) КАК ПАП_Sign,
    ЕСТЬNULL(РС.РС_Sign, 0) КАК РСППС_Sign,
    ЕСТЬNULL(ПАП.ПАП_Sign, 0) - ЕСТЬNULL(РС.РС_Sign, 0) КАК Дельта
ИЗ втПАП КАК ПАП
    ПОЛНОЕ СОЕДИНЕНИЕ втРС КАК РС
    ПО ПАП.Док = РС.Док И ПАП.ПодрКод = РС.ПодрКод И ПАП.Статья = РС.Статья И ПАП.Source = РС.Source
ГДЕ ЕСТЬNULL(ПАП.ПАП_Sign, 0) - ЕСТЬNULL(РС.РС_Sign, 0) > 0.01
   ИЛИ ЕСТЬNULL(ПАП.ПАП_Sign, 0) - ЕСТЬNULL(РС.РС_Sign, 0) < -0.01
```

**Знак формулы зафиксирован практикой (см. drill-down апреля 2026):**
- Для **РСППС** (поставщики, статья ЗПП): инверсия `-ДолгУпр` уже в стороне РС, поэтому `Δ = ПАП - (-РСППС_Dolg) = ПАП + РСППС_Dolg` (где `РСППС_Sign` уже содержит инверсию)
- Для **РСКПС** (клиенты, статья ЗадКл): без инверсии, `Δ = ПАП - РСППС_Sign` напрямую

Это разделено по UNION ALL в `втРС`: ветка РСППС с инвертированным `ДолгУпр`, ветка РСКПС без инверсии.

### 4.4 Запись результата в ТЧ

Каждая строка результата → новая строка ТЧ с заполненными `Документ`, `Подразделение`, `Статья`, `Source`, `ПАП_Sign`, `РСППС_Sign`, `Дельта`. `Обработан=Ложь`, `НовоеСостояние=""`, `ОшибкаТекст=""`.

### 4.5 Сообщение пользователю

`Сообщить("Найдено N документов с расхождением на сумму |Σ Δ| = X")`. Если `Подразделение` задано — отдельная строка про фильтр.

## 5. Алгоритм `ПерепровестиДокументы()`

### 5.1 Основной цикл

```bsl
КолОК = 0;
КолСталоОК = 0;
КолОшибок = 0;
КолОсталасьΔ = 0;

Для Каждого Стр Из ДокументыРасхождения Цикл
    Если Стр.Обработан Тогда
        Продолжить;
    КонецЕсли;
    Если НЕ ЗначениеЗаполнено(Стр.Документ) Тогда
        Продолжить;
    КонецЕсли;
    
    НачатьТранзакцию();
    Попытка
        ДокОбъект = Стр.Документ.ПолучитьОбъект();
        Если ДокОбъект = Неопределено Тогда
            ВызватьИсключение "Битая ссылка / документ удалён";
        КонецЕсли;
        // Записать(Проведение) автоматически распроводит и проводит заново
        // включая создание РегистраторРасчётов через подписки событий
        ДокОбъект.Записать(РежимЗаписиДокумента.Проведение);
        ЗафиксироватьТранзакцию();
        
        // Пересчёт Δ после перепроведения
        НоваяΔ = ПересчитатьДельтуОдногоДокумента(
            Стр.Документ, Стр.Подразделение, Стр.Статья, Стр.Source);
        
        Стр.ПАП_Sign = НоваяΔ.ПАП;
        Стр.РСППС_Sign = НоваяΔ.РСППС;
        Стр.Дельта = НоваяΔ.Δ;
        
        Если Окр(?(НоваяΔ.Δ < 0, -НоваяΔ.Δ, НоваяΔ.Δ), 2) < 0.01 Тогда
            Стр.Обработан = Истина;
            Стр.НовоеСостояние = "ОК";
            КолСталоОК = КолСталоОК + 1;
        Иначе
            Стр.НовоеСостояние = "Δ=" + Формат(НоваяΔ.Δ, "ЧДЦ=2");
            КолОсталасьΔ = КолОсталасьΔ + 1;
        КонецЕсли;
    Исключение
        ОтменитьТранзакцию();
        Стр.НовоеСостояние = "ОШИБКА";
        Стр.ОшибкаТекст = ОписаниеОшибки();
        КолОшибок = КолОшибок + 1;
    КонецПопытки;
КонецЦикла;

Сообщить("Перепроведение завершено:");
Сообщить("  Стало OK: " + КолСталоОК);
Сообщить("  Осталась Δ: " + КолОсталасьΔ);
Сообщить("  Ошибок: " + КолОшибок);
```

### 5.2 Функция `ПересчитатьДельтуОдногоДокумента(Док, Подр, Статья, Source)`

Тот же FULL OUTER но за один Регистратор и один ключ:

```sql
ВЫБРАТЬ
    ЕСТЬNULL(ПАП.S, 0) КАК ПАП,
    ЕСТЬNULL(РС.S, 0) КАК РСППС,
    ЕСТЬNULL(ПАП.S, 0) - ЕСТЬNULL(РС.S, 0) КАК Дельта
ИЗ (ВЫБРАТЬ СУММА(ВЫБОР КОГДА ВидДвижения=Приход ТОГДА Сумма ИНАЧЕ -Сумма КОНЕЦ) КАК S
    ИЗ РегистрНакопления.ПрочиеАктивыПассивы 
    ГДЕ Регистратор = &Док И Подразделение = &Подр И Статья = &Статья И Источник = &Source) ПАП,
   (ВЫБРАТЬ СУММА(ВЫБОР КОГДА ВидДвижения=Приход ТОГДА -ДолгУпр ИНАЧЕ ДолгУпр КОНЕЦ) КАК S
    ИЗ РегистрНакопления.РасчетыСПоставщикамиПоСрокам
    ГДЕ ДокументРегистратор = &Док И (Подр-выражение)=&Подр)
        КАК РС
```

(Аналогично для РСКПС, выбор между ветками по `Source` параметру.)

### 5.3 Ключевые решения

- ✅ Транзакция per-документ (НЕ глобальная) — упал один, остальные не страдают
- ✅ `Записать(РежимЗаписиДокумента.Проведение)` — атомарно делает «отменить+провести»
- ✅ После перепроведения — мгновенный пересчёт Δ через мини-запрос
- ✅ Битые ссылки (документ удалён) — поймать как ошибку и показать в ТЧ
- ✅ Никакой `Удалить()` — только перепроведение (memory `feedback_no_doc_delete_in_tests`)

5. ✅ Σ-инвариант штатного `Отчёт.УправленческийБаланс`: |Актив|=|Пассив| per организация **не ухудшился** (НЕ должен стать хуже чем был до)

1. ❌ После перепроведения через COM-обработку РегистраторРасчётов исчез → STOP, передать на UI

3. ❌ Штатный `Отчёт.УправленческийБаланс` показал ухудшение Σ
4. ❌ Тесты упали на Python COM ошибках (несоответствие типов, парсинг и т.п.)

## 9. Riski і memory

### 9.1 Memory которые применимы

- ✅ `feedback_com_repost_skips_registrator_raschetov` — проверяется в Тесте 2; если COM-обработка ломает РегистраторРасчётов, STOP
- ✅ `feedback_no_doc_delete_in_tests` — никаких `Удалить()`, только перепроведение
- ✅ `feedback_designer_cache_invalidation` — после сборки ERF через `/erf-build` обработка читается каждый раз заново из файла (это ERF, не часть конфигурации в Designer кэше)
- ✅ `feedback_query_pre_check` + Rule #-1 — все SQL запросы pre-test через Python COM или MCP execute_query ПЕРЕД вставкой в BSL
- ✅ `feedback_balans_etalon_period_serverside` — даты передавать серверно через `ДАТАВРЕМЯ(...)` в тексте запроса, не через `SetParameter(datetime)` (где это применимо в самом ObjectModule)
- ✅ `feedback_no_typical_register_changes` — типовые регистры не трогаем (читаем только)
- ✅ `feedback_balans_klient_perenosa_avansa_only` — НЕ применяется: наш случай не ПереносАванса (это апрель 2026, time-of-flight для Оплата поставщику)
- ✅ `feedback_balans_live_code_source_of_truth` — источник истины canon `Свод_РасчетыСПартнерами` в `Documents/А_ФинРез_Баланс/Ext/ObjectModule.bsl` (использовали для понимания знака формулы)

### 9.2 Основной risk + mitigation

| Risk | Vероятность | Impact | Mitigation |
|---|---|---|---|
| COM-перепроведение через обработку ломает РегистраторРасчётов | Средняя | Высокий | Тест 2 на 2-х маленьких документах перед массовым прогоном |
| Запрос FULL OUTER падает на типах MCP (`Несоответствие типов`) | Низкая | Низкий | Pre-test через Python COM (не MCP), при необходимости упрощение типов |
| После перепроведения остаётся Δ ≠ 0 (например, в момент перепроведения остатки в РСППС ещё не показывают долг) | Средняя | Средний | Колонка `НовоеСостояние = "Δ=<новое>"` — видно сразу, можно перепровести по очереди начиная с источника долга (ПриобретениеТоваровУслуг) |
| Битые ссылки / удалённые документы | Низкая | Низкий | Обработка ошибок в `Попытка`, ОшибкаТекст в ТЧ |
| Регрессия по другим подразделениям (плуги выросли в Глобино-2 и т.п.) | Низкая | Средний | После Теста 3 — запрос Σ |Δ| годовой по всем подразделениям через тот же скрипт что в декабрьском verify |
