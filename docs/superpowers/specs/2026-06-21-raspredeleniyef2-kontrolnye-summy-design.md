# РаспределениеФ2 — контрольные суммы по сотруднику + флаг расхождения

> Дата: 2026-06-21. Брейншторм-дизайн (одобрен пользователем).
> Цель: заполнять в ТЧ `Сотрудники` две контрольные колонки и поднимать флаг шапки
> `А_Расхождение`, когда «перечислено» ≠ «по распределению» ≠ «по ДДС».

---

## 1. Контекст и назначение

Документ `РаспределениеФ2` (ЕРП, зеркало Казны по UUID 1:1) — наличная выплата ЗП.
Имеет три табличные части:

| ТЧ | Роль | Ключевые колонки |
|----|------|------------------|
| `Сотрудники` (цель) | агрегат на сотрудника | `Сотрудник`, `СуммаНачисления` (=«Перечисления»), `СуммаПоДДС`, `СуммаПоРаспределение` |
| `Распределение` (источник 1) | детализация Сотр×Подр | `Сотрудник`, `СуммаНачисления`, `СуммаЗатрат`, `ОтработаноЧасов` |
| `А_ДвижениеДДС` (источник 2) | зеркало БДДС Казны (заполняется из `А_ОтражениеЗПпоКазне.СоздатьДвиженияДДСПоОтражениюЗП()`) | `Сотрудник`, `СтатьяДвиженияДенежныхСредств`, `Сумма` |

Колонки `СуммаПоРаспределение`/`СуммаПоДДС` + флаг `А_Расхождение` образуют **контрольную
сверку**: «перечислено» (`СуммаНачисления`) против «по распределению» против «по ДДС».

## 2. Что делаем

- `Сотрудники.СуммаПоРаспределение` = Σ `Распределение.СуммаНачисления` по этому сотруднику.
- `Сотрудники.СуммаПоДДС`           = Σ `А_ДвижениеДДС.Сумма` по этому сотруднику.
- `А_Расхождение` (шапка, Булево) = Истина, если есть хотя бы одна расходящаяся строка.

Источник для `СуммаПоРаспределение` — именно `Распределение.СуммаНачисления` (колонка
`СуммаЗатрат` пуста во всех проверенных данных; `СуммаНачисления` сходится 1:1 с
`Сотрудники.СуммаНачисления`).

## 3. Точка входа

Расширяем существующую `Процедура ПередЗаписью(...)` в
`Documents/РаспределениеФ2/Ext/ObjectModule.bsl` — там уже считается `СуммаДокумента`.
Добавляем вызов приватной `_ЗаполнитьКонтрольныеСуммы()`. Срабатывает на **любой**
записи/проведении, включая перепроведение из
`А_ОтражениеЗПпоКазне.СоздатьДвиженияДДСПоОтражениюЗП()` (именно тогда наполняется `А_ДвижениеДДС`).

## 4. Алгоритм (агрегация в памяти, без запроса)

Запрос в `ПередЗаписью` читал бы **старое** сохранённое состояние — поэтому считаем по ТЧ
объекта в памяти. Вызов гейтится `Если НЕ ОбменДанными.Загрузка` (см. §7).

1. Три карты `Соответствие` `Сотрудник → Σ`, **пустой Сотрудник пропускаем**:
   `КартаРаспределение` (Σ `Распределение.СуммаНачисления`), `КартаДДС` (Σ `А_ДвижениеДДС.Сумма`),
   `КартаНачислено` (Σ `Сотрудники.СуммаНачисления`).
2. Колонки: обход ТЧ `Сотрудники`; «итог по сотруднику» кладём в **первую строку** сотрудника
   (`СуммаПоРаспределение = КартаРаспределение[Сотрудник]`, `СуммаПоДДС = КартаДДС[Сотрудник]`),
   в дублях того же сотрудника и в пустых строках — **0**. Так итог колонки (подвал формы)
   равен итогу источника, а не задваивается. Присваивание, не накопление → идемпотентно.
3. Флаг (§6) — агрегат по сотруднику.

`Соответствие`, ключованное ссылкой, корректно работает и с «битыми» ссылками: битая ссылка
в `Сотрудники` и `Распределение` — одна и та же (один UUID), поэтому `СуммаПоРаспределение`
сходится даже у «дрейфующих» строк; в `КартаДДС` их (другой, живой) ссылки нет → `СуммаПоДДС = 0`.

## 5. Ключ сопоставления — ТОЛЬКО ссылка `Сотрудник`

Проверка по всей базе (на 2026-06-21):

- ТЧ `Сотрудники`: 1420 строк, **0** с заполненным `ИНН`, **0** с `КодСотрудникаКазна`, **0** с `ФИО`.
- 32 строки с «битой» ссылкой `Сотрудник` (указывает на удалённый элемент справочника); у всех 32 —
  пустые `ИНН`/`Код`/`ФИО`.
- ТЧ `А_ДвижениеДДС`: 2117 строк, битых ссылок 0, пустой `Сотрудник` у 15.

Вывод: **fallback по `ИНН`/`КодСотрудникаКазна` технически невозможен** — этих данных в
документах нет. Единственный рабочий ключ — ссылка `Сотрудник`. Это сознательное решение
(а не упрощение): у 32 «дрейфующих» строк нет общего бизнес-ключа с ДДС, поэтому они получают
`СуммаПоДДС = 0` и честно подсвечиваются флагом `А_Расхождение` для ручной починки.

## 6. Флаг `А_Расхождение`

Пересчитывается с нуля каждый раз (Истина/Ложь). Считается **на уровне сотрудника (агрегат)**, а
не строки — иначе дубли строк по одному сотруднику давали бы ложное расхождение, а сотрудник из
источника без строки в `Сотрудники` (orphan) — терялся бы молча.

Берём **объединение ключей** трёх карт (`КартаНачислено ∪ КартаРаспределение ∪ КартаДДС`, пустой
Сотрудник исключён). Сотрудник считается расходящимся, если:

- `Окр(ИтогНачислено − ИтогРаспределение, 2) <> 0`, **или**
- (часть по ДДС) `Окр(ИтогНачислено − ИтогДДС, 2) <> 0`.

`А_Расхождение = Истина`, если есть хотя бы один расходящийся сотрудник. Это покрывает:
дрейф/битые ссылки (ДДС у сотрудника = 0), orphan-источник (Начислено = 0, источник > 0), дубли
строк (сходятся в итоге → НЕ расхождение).

**Гейт по ДДС:** ДДС-сравнение учитывается только если `А_ДвижениеДДС.Количество() > 0`. Пока
ДДС не построен (первый импорт из Казны) — это «ещё не сверено», а не расхождение; флаг по ДДС
не зажигаем.

## 7. Краевые случаи

- **Пустой `Сотрудник`** во всех трёх ТЧ исключается из карт и из флага. Сверка идёт «по сотруднику»,
  а пустые строки (в т.ч. by-design строки ДДС без статьи/сотрудника, 15 строк / Σ 976 300 по базе;
  и 22 строки `Сотрудники` с пустым сотрудником / Σ 367 000) ни к какому сотруднику не относятся и
  не должны давать ложных расхождений. Колонки у таких строк = 0.
- **Дубли строк по одному сотруднику** (в `Сотрудники` есть, 5 документов): итог кладём в первую
  строку, в остальных 0 → подвал формы не задваивается; флаг (агрегат) их корректно сводит.
- **Толеранс** — копейки через `Окр(..., 2)`.
- **`ОбменДанными.Загрузка`** — вызов `_ЗаполнитьКонтрольныеСуммы()` **гейтится** `Если НЕ
  ОбменДанными.Загрузка` (симметрично гарду в `ПриЗаписи`). Это защищает от пересчёта/затирания
  контрольных значений при импорте через обмен ERP↔Казна и при «флаговых» записях из подписки РКО
  (`РасходныйКассовыйОрдер_ПриЗаписи` пишет Ф2 с `Загрузка=Истина` ради смены флагов). При штатном
  перепроведении из `СоздатьДвиженияДДСПоОтражениюЗП()` `Загрузка=Ложь` (там `Записать(Проведение)`
  без `Загрузка`), поэтому суммы заполняются. Расчёт `Организация`/`СуммаДокумента` оставлен как был
  (вне scope).

## 8. Вне scope (не делаем)

- Не заполняем `ИНН`/`ФИО`/`КодСотрудникаКазна`.
- Не чиним «битые» ссылки `Сотрудник`.
- Не добавляем строки в `Сотрудники` (напр. сотрудников, что есть только в ДДС).
- Не трогаем движения / `ОбработкаПроведения` / `ПриЗаписи` / создание ВКассу.

## 11. Состязательное ревью (multi-agent) — закрытые находки

Финальный код прошёл адверсариальное ревью (5 линз × verify). Все подтверждённые дефекты исправлены
до финальной регрессии 75/75:

| # | Находка | Severity | Исправление |
|---|---------|----------|-------------|
| 1 | Дубль строк по сотруднику → ложный `А_Расхождение` | major | Флаг считается агрегатом по сотруднику (§6) |
| 2 | Orphan (сотрудник в источнике без строки в `Сотрудники`) → флаг молчит, деньги «теряются» | major | Объединение ключей трёх ТЧ в флаге; verify на №043/018 |
| 3 | Дубль → задвоение колонок в подвале формы | major | Итог по сотруднику кладём в первую строку, дубли → 0 (§4) |
| 4 | Нет гейта `ОбменДанными.Загрузка` в `ПередЗаписью` (асимметрия с `ПриЗаписи`) | major→minor | Вызов гейтится `Если НЕ ОбменДанными.Загрузка` (§7) |

Дополнительно по результатам ревью: пустой Сотрудник (в т.ч. by-design строки ДДС без статьи)
исключён из карт и флага (§7), иначе давал бы ложные расхождения.
