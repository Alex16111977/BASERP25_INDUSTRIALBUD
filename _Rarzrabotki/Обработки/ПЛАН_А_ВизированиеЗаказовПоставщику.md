## 1. Как ЗаказПоставщику реально живёт в этой базе (факт, не теория)

### 1.1 Жизненный цикл статуса

```
       создание в ЕРП                            обмен из BuhBud
  (Заполнить → ОбработкаЗаполнения)         (СоздатьДокумент, без Заполнить)
              │                                        │
   ИнициализироватьДокумент:1614                       │  ObjectModule:529
        Статус = Согласован                            │  Статус = Подтвержден (при пустом)
              │                                        │
              └──────────────┬─────────────────────────┘
                             ▼
              подписка А_СобытияОбъектов:791
              ЕСЛИ ЭтоНовый → Статус = Согласован   ← БЕЗУСЛОВНО, перетирает всё
                             │
                             ▼
                    в БД: Статус = Согласован
```
⇒ **Любой новый заказ, независимо от происхождения, записывается как `Согласован`.**
⇒ `Подтвержден` в базе (6931 шт.) появляется **позже**, отдельным действием: командами «Установить статус»
   из форм списка, либо АРМами (`ОбеспечениеПотребностей`, `ФормированиеЗаказовПоставщикам`).

### 1.2 Движения по статусам — замер (BaseERPRazr, ФО включена, один заказ, Кол = 10)

| Статус | РН.ЗаказыПоставщикам | РН.ДвижениеТоваров | РН.ТоварыКПоступлению | Смысл |
|---|---|---|---|---|
| НеСогласован | Заказано **10**, КОформлению 0 | — | — | заказ виден в «Заказано» |
| **Согласован** | Заказано **10**, КОформлению 0 | ПланСНеподтв 10 | — | **оформлен, но не подтверждён** |

## 2. КОНСТРУКЦИЯ (пересобранная)

### 2.1 Семантика статусов под визирование

| Статус | Смысл в контуре визирования |
|---|---|
| `Согласован` | **«оформлен, ждёт визы»** — дефолт любого нового заказа. Имя обманчиво, но это типовое поведение; **не ломаем** |
| **`Подтвержден`** | **«завизирован — можно принимать товар»** ← **виза открывает этот переход** |
| `Закрыт` | закрытие заказа — **виза не участвует**, не блокируем |
| `НеСогласован` | **не используем** (в базе 0 таких; подписка `:791` их не даёт появиться) |

### 2.2 Точка контроля: **гейт на повышение до `Подтвержден`**

```
Согласован ──[ВИЗА ПРОЙДЕНА]──▶ Подтвержден ──▶ КОформлению + ТоварыКПоступлению
     ▲                                                (можно оформить поступление)
     └──[ОТКЛОНЕНО]────────────── возврат
```

**Почему это работает, а прежняя схема — нет:**
переход `Согласован → Подтвержден` происходит на **уже существующем** документе.
Подписка `А_СобытияОбъектов:791` срабатывает **только для `ЭтоНовый()`** ⇒ **она этот переход не затирает.**
⇒ Гейт в `ObjectModule.ПередЗаписью` **работает**. Подписку **трогать не нужно.**

**Что отсюда следует (важно — три проблемы снимаются сами):**
- ❌ **не нужно** менять дефолт `ИнициализироватьДокумент` на `НеСогласован` (не будет «паралича ввода»)
- ❌ **не нужно** править подписку `А_СобытияОбъектов`
- ❌ **не нужно** трогать `ОбновитьЗаказПоставщикуПослеОбмена` и обмен
- ❌ **не нужна** миграция истории

### 2.3 Гейт — точный код и точное место

Место: `Documents\ЗаказПоставщику\Ext\ObjectModule.bsl`, `ПередЗаписью`,
**строго ПОСЛЕ** строки `Если ОбменДанными.Загрузка Тогда Возврат; КонецЕсли;` (:545).
*(До неё стоит `ОбновитьЗаказПоставщикуПослеОбмена` — её не трогаем; а обновление ИБ пишет с
`ОбменДанными.Загрузка = Истина` и тоже проходит мимо.)*

```bsl
//++ А_Визирование
А_ВизированиеСервер.ПроверитьЗапретОбходаВизирования(ЭтотОбъект, Отказ);
//-- А_Визирование
```

```bsl
Процедура ПроверитьЗапретОбходаВизирования(ДокОбъект, Отказ) Экспорт

    // 1. статус ставит сам движок визы
    Если ДокОбъект.ДополнительныеСвойства.Свойство("А_ВизаДвижок") Тогда
        Возврат;
    КонецЕсли;

    // 2. ДИСКРИМИНАТОР КОНТУРА: пустая виза = документ вне контура
    //    (обменный заказ или один из 10 060 исторических). Миграция не нужна.
    Если НЕ ЗначениеЗаполнено(ДокОбъект.А_Виза_Состояние) Тогда
        Возврат;
    КонецЕсли;

    // 3. блокируем ТОЛЬКО повышение до Подтвержден — рубежа, где появляются
    //    КОформлению и ТоварыКПоступлению. «Закрыт» и понижения не трогаем.
    Если ДокОбъект.Статус <> Перечисления.СтатусыЗаказовПоставщикам.Подтвержден Тогда
        Возврат;
    КонецЕсли;

    // 4. статус этой записью не меняется (перепроведение уже подтверждённого) — пропускаем
    Если ЗначениеЗаполнено(ДокОбъект.Ссылка) Тогда
        СтарыйСтатус = ОбщегоНазначения.ЗначениеРеквизитаОбъекта(ДокОбъект.Ссылка, "Статус");
        Если СтарыйСтатус = ДокОбъект.Статус Тогда
            Возврат;
        КонецЕсли;
    КонецЕсли;

    // 5. виза пройдена
    Если ДокОбъект.А_Виза_Состояние = Перечисления.А_Визы_Состояния.Утвержден Тогда
        Возврат;
    КонецЕсли;

    // 6. администратор визирования
    Если РольДоступна("ПолныеПрава") ИЛИ РольДоступна("А_ВизированиеАдминистратор") Тогда
        Возврат;
    КонецЕсли;

    ОбщегоНазначенияКлиентСервер.СообщитьПользователю(
        "Заказ не завизирован — статус «Подтвержден» недоступен.
        |Отправьте заказ на визирование через рабочее место «Визирование заказов поставщикам».",
        ДокОбъект.Ссылка, "Статус", , Отказ);

КонецПроцедуры
```

### 2.4 Где заказ входит в контур

Врезка ставится в **`ИнициализироватьДокумент` (ObjectModule:1584)**, а **не** в тело `ОбработкаЗаполнения`.

**Почему именно там:** `ИнициализироватьДокумент` вызывается из **обоих** интерактивных путей —
из `ОбработкаЗаполнения` (:638-640) и из `ПриКопировании` (:992). Если положить только в
`ОбработкаЗаполнения`, **копия заказа** приедет с пустой визой и **ложно выпадет из контура**.

```bsl
//++ А_Визирование
Если НЕ ЗначениеЗаполнено(А_Виза_Состояние) Тогда
    А_Виза_Состояние = Перечисления.А_Визы_Состояния.Черновик;
КонецЕсли;
//-- А_Визирование
```

| Путь появления заказа | `Заполнить()` | `А_Виза_Состояние` | Контур |
|---|---|---|---|
| интерактивно / на основании / из АРМов | да (проверено, 4 места) | `Черновик` | **внутри** |
| копирование | да (`ПриКопировании:992`) | `Черновик` | **внутри** |
| обмен из BuhBud (КД 2.0) | **нет** (доказано) | **пусто** | снаружи |
| 10 060 существующих | — | **пусто** | снаружи |

### 2.6 Выбор схемы визирования — исправленная формула специфичности

`ПолныйКод()` **не годится** (A3): падает на пустой ссылке, немонотонен.

```bsl
Функция ГлубинаИзмерения(Ссылка)
    Если НЕ ЗначениеЗаполнено(Ссылка) Тогда
        Возврат 0;                       // пустое измерение = «любой» = минимальная специфичность
    КонецЕсли;
    Возврат 100 + 10 * Ссылка.Уровень(); // строго монотонно по уровню (проверено на 847 элементах)
КонецФункции

Глубина = 1000 + ГлубинаИзмерения(СтатьяДДС) + ГлубинаИзмерения(Подразделение);
```
`НаправленияДеятельности` — **плоский** (9 элементов, вложенных нет) ⇒ в «Глубину» **не входит**
(дал бы константу и создал ложное впечатление вклада).

Сортировка выбора схемы: `Приоритет, ПриоритетСхемы, Глубина Убыв, Подразделение Убыв, СтатьяДДС Убыв, Организация Убыв, ФормаОплаты Убыв`.

### 2.7 Движок визы — контракт записи (по типовому ЕРП)

**Движок визы документ НЕ ПИШЕТ** — только меняет объект в памяти и возвращает результат.
Пишет **вызывающий**. Это в точности контракт `УстановитьСтатус` / `УстановитьСтатусДокументов`
(`ОбщегоНазначенияУТВызовСервера:110` меняет, `:116` пишет).

Финальная виза (маршрут пройден):
```bsl
ДокОбъект.ДополнительныеСвойства.Вставить("А_ВизаДвижок", Истина);
Если НЕ ДокОбъект.УстановитьСтатус("Подтвержден", Неопределено) Тогда   // ← Подтвержден, НЕ Согласован
    Возврат Ошибка("Заказ не заполнен, статус «Подтвержден» не установлен");
КонецЕсли;
```
Отклонение / возврат в черновик:
```bsl
ДокОбъект.ДополнительныеСвойства.Вставить("А_ВизаДвижок", Истина);
ДокОбъект.УстановитьСтатус("Согласован", Неопределено);   // движения КОформлению/ТКП уходят
```

### 2.8 Журнал `.epf` — что меняется против прежнего промта

- Запрос динсписка: **без `СГРУППИРОВАТЬ ПО`** (A2 — запрещено в динсписке).
  Очередь — через `Т.Ссылка В (ВЫБРАТЬ Т2.Ссылка ИЗ Документ.ЗаказПоставщику.А_ТекущиеВизирующие КАК Т2 ГДЕ Т2.Пользователь = &ТекущийПользователь)`.
- Первое условие — дискриминатор контура: `А_Виза_Состояние <> ПустаяСсылка` (иначе вывалятся 10 060 обменных).
- Массовые команды — на типовом механизме (клиент: `ПроверитьПолучитьВыделенныеВСпискеСсылки` →
  `ПоказатьВопрос` → сервер → `ОповеститьПользователяОбУстановкеСтатуса`; сервер — калька
  `УстановитьСтатусДокументов` с блокировкой объекта и построчными ошибками).
- Условное оформление — `Список.КомпоновщикНастроек.Настройки.УсловноеОформление`, цвета `ЦветаСтиля.*`.
- Отборы — `ОтборыСписковКлиентСервер` + `ПриЗагрузкеДанныхИзНастроекНаСервере` (сохранение между сеансами).

## 3. 🔴 РАЗВИЛКА, КОТОРУЮ РЕШАЕТ ЗАКАЗЧИК: АРМы создают заказ сразу `Подтвержден`

Найдено три места, где заказ создаётся/переводится в `Подтвержден` **программно**:

| Место | Что делает |
|---|---|
| `DataProcessors\ОбеспечениеПотребностей\ManagerModule:2552` | АРМ обеспечения создаёт заказ и сразу ставит `Подтвержден` |
| `DataProcessors\ФормированиеЗаказовПоставщикам\ManagerModule:521` | массовое автосоздание подтверждённых заказов |
| `DataProcessors\ФормированиеЗаказовПоставщикуПоПлану\Forms\Форма:2597` | **прямое присваивание** `Статус = Подтвержден` (мимо `УстановитьСтатус`) |

Эти заказы создаются через `Заполнить()` ⇒ попадают **в контур** ⇒ **упрутся в гейт**.

| Вариант | Последствие |

## 5.2 🔧 Что вскрылось только на живой базе (уже учтено в коде)

**(1) `ВнешнееСоединение = Истина` ОБЯЗАТЕЛЕН** у `А_ВизированиеСервер` и `А_ВизированиеВызовСервера`.
Модуль документа теперь вызывает общий модуль, и без этого флага **любая запись `ЗаказПоставщику`
через COM-соединение падает на компиляции** («Переменная не определена»), а COM в проекте используется
постоянно (обмен, обработки). Так же настроен соседний `А_ПодключенияБазСервер`.
`Привилегированный` при этом не ставить — флаги несовместимы.

**(2) `РН.ТоварыКПоступлению` заказами в BaseERP НЕ пишется вообще** — 0 записей на 10 061 заказ
(при 31 494 записях от других типов документов). Поэтому рубеж «заказ в силе» в этой базе определяется
**только ресурсом `КОформлению`** в `РН.ЗаказыПоставщикам`. (Замер на BaseERPRazr показывал ТКП — там
другие настройки склада; не путать базы.)

**(3) Врезка входа в контур — только в `ИнициализироватьДокумент`,** плюс сброс визы в `ПриКопировании`
до её вызова. Подтверждено: копия заказа корректно получает `Черновик`.

**(4) COM-грабли (в тестах, не дефекты кода):** `erp.String()` от перечисления отдаёт **синоним**, а не имя;
`ДокОбъект.УстановитьСтатус("X", None)` из Python ломает типовой код (Python `None` ≠ `Неопределено`), из BSL
тот же вызов работает; `Комментарий` — неограниченная строка, в `ГДЕ` только через `ВЫРАЗИТЬ`.
