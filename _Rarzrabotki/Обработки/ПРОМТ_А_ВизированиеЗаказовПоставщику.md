## 0. TL;DR — что строим

В BaseERP появляется контур **визирования заказов поставщикам** — калька механизма из базы **Казна**
(`Документ.СчетНаОплатуПоставщика` + `ФормаСписка_Визирование`), перенесённая на `Документ.ЗаказПоставщику`:

1. **Инфраструктура визирования** (новые объекты конфигурации, префикс `А_`): роли визирования, схемы
   визирования (цепочки ролей), регистр адресации «кто визирует под какой ролью» (с замещением на отпуск),
   регистр выбора схемы по реквизитам заказа, общий модуль-движок.
2. **Доработка `Документ.ЗаказПоставщику`**: визовые реквизиты + 3 табличные части + 4 тонкие врезки в
   типовые обработчики. **Типовое проведение НЕ трогаем.**
3. **Рабочее место** — внешняя обработка `А_ВизированиеЗаказовПоставщику.epf`: журнал с режимами очереди
   («Все» / «Мне на визирование» / «Могу подписать заранее»), отборы, массовое утверждение/отклонение по
   выделенным строкам, итоги, история виз по активной строке.

**Ключ интеграции (главное архитектурное решение):** виза управляет **типовым `Статус`** заказа.
Все роли подписали → `Статус = Согласован` → движения в `РН.ЗаказыПоставщикам` / `ТоварыКПоступлению` /
`РасчетыСПоставщиками` появляются **сами** (типовые запросы движений уже гейтятся на
`Статус <> НеСогласован`). Не подписано → `НеСогласован` → движений нет. Плюс запрет ручного обхода.

**Область действия визирования (решено, см. §3.5):** контур визирования распространяется **только на новые
заказы, создаваемые в ЕРП**. Заказы, приезжающие обменом из бухгалтерии (а это все 10 060 существующих),
остаются **вне контура** и работают как сейчас — авто-подтверждение. Обмен **не трогаем**.

**Дискриминатор контура (ключевой приём — благодаря ему НЕ нужна миграция):**
`ОбработкаЗаполнения` при загрузке через обмен **не вызывается**. Значит:

| Как появился заказ | `А_Виза_Состояние` | Контур визирования |
|---|---|---|
| создан в ЕРП (интерактивно / `Заполнить()` / на основании) | `Черновик` (ставит `ОбработкаЗаполнения`) | **внутри** — визируется |
| приехал обменом из бухгалтерии | **пустое** | **снаружи** — авто-`Подтвержден`, гейт молчит |
| существующие 10 060 заказов | **пустое** | **снаружи** — не трогаются вообще |

Всё, что проверяет гейт и показывает журнал, отсекается по `ЗначениеЗаполнено(А_Виза_Состояние)`.
**Миграция исторических данных не требуется.**

## 1. 🚧 Жёсткие ограничения

- **Rule #-1 (абсолютный):** каждый запрос 1С — сначала **Python COM тест против BaseERP**, только потом в BSL.
  Ни одного исключения. Шаблон теста — §9.
- **Типовые регистры и типовое `ОбработкаПроведения` заказа НЕ менять.** Точка воздействия — только `Статус`
  через типовой API `УстановитьСтатус(...)`.
- **🔒 ОБМЕН С БУХГАЛТЕРИЕЙ НЕ ТРОГАТЬ** (§3.5). Ни правила обмена, ни `ОбновитьЗаказПоставщикуПослеОбмена`.
  Заказы, приезжающие из BuhBud (а это все 10 060 существующих), остаются **вне контура визирования** и
  авто-подтверждаются как сейчас. Визирование обменного потока — **будущая отдельная задача, в объём не входит**.
- **Миграция исторических данных НЕ ДЕЛАЕТСЯ** — дискриминатор (§0, §6.3 п.1) выводит все существующие
  заказы из-под гейта автоматически.
- Врезки в типовые модули `ЗаказПоставщику` — **минимальные и в хвост** типовых обработчиков, обрамлённые
  комментариями `//++ А_Визирование` / `//-- А_Визирование`, вся логика — в общем модуле `А_ВизированиеСервер`.
- Рабочее место — **внешняя обработка `.epf`** (не форма списка документа, не обработка конфигурации).
  Цвет/оформление в ней — **только кодом** (`Новый Цвет` / `ЦветаСтиля`); `<TextColor>style:...` в XML
  валит `epf-build` («Исключение XDTO»).
- **Уведомления (e-mail, регламентные задания) в v1 НЕ делаем.** Визирующий видит свою очередь в журнале.
  Не тащить эту фазу в объём.
- Rule #4: работа в worktree → после каждой правки `cp` изменённых файлов в основной каталог

### 3.2 🔑 Как `Статус` гейтит движения — и от чего это зависит (ЧИТАТЬ ВНИМАТЕЛЬНО)

В `Documents\ЗаказПоставщику\Ext\ManagerModule.bsl` условия по статусу встречаются в двух видах:

**(а) Жёсткие — работают всегда** (напр. строка **2552**, запрос по ТЧ `ЭтапыГрафикаОплаты`):
```

```

**(б) Под функциональной опцией** (строки ~1069, 1087, 1099, 1130, 1146, 1154, 1164):
```

```
Параметр `&НеИспользоватьСтатусыЗаказовПоставщикам` = **отрицание** функциональной опции
`ИспользоватьСтатусыЗаказовПоставщикам`.

### 🚨 ИНВАРИАНТ ПРОЕКТА: `ИспользоватьСтатусыЗаказовПоставщикам` = **ВКЛЮЧЕНА**

Проверено через COM **14.07.2026**: `ПолучитьФункциональнуюОпцию("ИспользоватьСтатусыЗаказовПоставщикам")`
→ **Истина**. Опция включена владельцем базы специально под этот проект
(НСИ и администрирование → Закупки → Статусы документов → «Статусы заказов поставщикам»).

**При включённой опции** `&НеИспользоватьСтатусы = Ложь`, все условия вида `(Статус = X ИЛИ &Не...)`
схлопываются в `Статус = X` ⇒ **`Статус = НеСогласован` ⇒ движений нет.** Это и есть точка интеграции визы
(ровно как в Казне `Если Виза_Состояние <> Утвержден Тогда Возврат` в `ОбработкаПроведения`).

**⚠️ Если опцию выключить — визирование теряет силу:** движения пойдут независимо от статуса,
незавизированный заказ будет резервировать и создавать потребность. **Это единственная внешняя настройка,
от которой зависит весь контур.** Обязательно:
- проверять её в acceptance (§10, п.0);
- на старте `А_ВизированиеСервер` — если опция выключена, писать предупреждение в журнал регистрации;
- в документации сдачи — отдельным пунктом «не выключать».

> движения», опираясь на `grep` без чтения контекста. На деле строки 1179–1242 — это **вычисляемые поля**

## 5. ФАЗА 2 — движок `А_ВизированиеСервер`

Портировать **вербатим по смыслу** из Казны (источники — §2), с заменами из §3.4.

### 5.1 `ПолучитьМассивПользователей(пПараметры) Экспорт` → Массив пользователей
Порт `ИдентификацияВизирующихПоРолям.ПолучитьМассивПользователей`.
- Вход (Структура): `Роль`, `Подразделение`, `Организация`, `НаправлениеДеятельности`, `Дата`.
- Собрать массив подразделений — **вверх по иерархии** (`Пока ЗначениеЗаполнено(П) Цикл ... П = П.Родитель`),
  плюс `Неопределено` и пустая ссылка (= «любое»). Аналогично организации/направления.
- Запрос к `РС.А_ИдентификацияВизирующихПоРолям` с ветвлением по `Роль.ВидАдресации`
  (`Объект В (&Подразделения)` / `В (&Организации)` / `В (&Направления)`).
- Учесть **переадресацию**: если `Переадресация = ИСТИНА` и `Дата` попадает в
  `[ПереадресацияС; ПереадресацияДо]` (пустая граница = без ограничения, сравнивать с `ДАТАВРЕМЯ(1,1,1)`) —
  добавить `Переадресант` в результат.
- Вернуть уникальный массив `Справочники.Пользователи`.

### 5.2 `ПолучитьСхемуВизирования(пПараметры) Экспорт` → `А_СхемыВизирования`
Порт `ОпределениеСхемыВизированияПоСчетам.ПолучитьСхемуВизирования`.
- Вход: `Подразделение`, `Организация`, `СтатьяДвиженияДенежныхСредств`, `ФормаОплаты`, `Сумма`,
  `НаправлениеДеятельности`, `Должность`.
- Подразделение и СтатьяДДС — **разворачивать вверх по иерархии** в массивы (+ пустая ссылка).
- Запрос: `Т.Подразделение В(&Подразделения) И Т.Организация В(&Организации) И Т.Должность В(&Должности)
  И Т.НаправлениеДеятельности В(&Направления) И Т.ФормаОплаты В(&ФормыОплаты)
  И Т.СтатьяДвиженияДенежныхСредств В(&СтатьиДДС) И Т.Сумма <= &Сумма`.
- Разрешение конфликта (когда подошло несколько правил) — **точно как в Казне**:
  1. вычисляемый в запросе `Приоритет` специфичности:
     `Должность=точная И СтатьяДДС=точная → 1`; `Должность=пустая И СтатьяДДС=точная → 2`;
     `Должность=точная И СтатьяДДС=пустая → 3`; иначе `9`;
  2. затем ресурс `ПриоритетСхемы`;
  3. затем `Глубина` = `1000 + СтрДлина(СтатьяДДС.ПолныйКод()) + СтрДлина(Подразделение.ПолныйКод())`
     (пустая ссылка → вклад 0) — **чем длиннее полный код, тем специфичнее правило**;
  4. сортировка `"Приоритет, ПриоритетСхемы, Глубина Убыв, Подразделение Убыв, СтатьяДДС Убыв,
     Организация Убыв, ФормаОплаты Убыв"` → берём первую строку.
- Нет совпадений → пустая ссылка (движок обязан на это среагировать — §5.4).

### 5.3 `ПолучитьМассивРолейПоСхеме(Схема) Экспорт` → Массив ролей
`ВЫБРАТЬ Роль ИЗ Справочник.А_СхемыВизирования.Роли ГДЕ Ссылка = &Ссылка УПОРЯДОЧИТЬ ПО НомерСтроки`.

### 5.4 `УстановитьСостояние(ДокОбъект, пСостояние, пДопы) Экспорт` — **машина состояний**

`пДопы` (Структура, всё опционально): `ТекущийПользователь` (по умолчанию
`Пользователи.ТекущийПользователь()`), `ЭтоАвтоВиза` (Ложь), `ЭтоИзФормы` (Ложь), `ДатаВизы`
(`ТекущаяДата()`), `Виза_Причина` (Строка), `СхемаВизирования` (принудительная схема).

**Ветвление по `пСостояние`:**

| `пСостояние` | Действие |
|---|---|
| `Черновик` | `А_Визы.Очистить()`; `А_Виза_Состояние = Черновик`; `А_Виза_ТекущаяРоль = Инициатор`; `НужныПольз = Истина` |
| `Утвержден` / `Отклонено` | `НужныВизы = (А_Виза_Состояние <> НаВизировании)` — т.е. **маршрут строится один раз**, при первом утверждении инициатором; `НужныПольз = Истина` |
| **`ПустаяСсылка()`** | **предварительная («отложенная») виза** — см. ниже, и **выход** |
| иначе (`Анулировано`) | `НужныПольз = Истина` |

**Предварительная виза** (`пСостояние = Перечисления.А_Визы_Состояния.ПустаяСсылка()`):
- найти/создать строку в `А_ПредварительныеВизы` по `ТекущийПользователь`;
- `Утверждено = ?(ЭтоИзФормы, НЕ Утверждено, Истина)` — тумблер; `ДатаУтверждения = ТекущаяДата()`;
  `Комментарий = пДопы.Виза_Причина`;
- **если пользователь уже в `А_ТекущиеВизирующие`** (его очередь наступила) — сразу рекурсивно
  `УстановитьСостояние(ДокОбъект, Утвержден, {ТекущийПользователь, ЭтоАвтоВиза=Истина, ДатаВизы})`;
- **Возврат** `{Успех=Истина}`. **Документ НЕ пишем** — пишет вызывающий (см. «Контракт записи» ниже).

**Если `НужныВизы`** (строим маршрут):
1. Параметры схемы = `{Подразделение, Организация, ФормаОплаты, СтатьяДвиженияДенежныхСредств
   (= `А_СтатьяДвиженияДенежныхСредств`), Сумма (= `СуммаДокумента`), НаправлениеДеятельности,
   Должность (= `ДолжностьПользователя(Автор)`, см. §8.7)}`.
2. Схема = `пДопы.СхемаВизирования` → иначе `ПолучитьСхемуВизирования(Параметры)`;
   **`ДокОбъект.А_ПриоритетнаяСхемаВизирования`, если заполнена, перебивает всё.**
3. **Схема пустая → вернуть ошибку «Не определена схема визирования», НИЧЕГО не писать, Возврат.**
4. `А_Визы.Очистить()`; для каждой роли схемы (по порядку) → `А_Визы.Добавить().Роль = Роль`.
5. `А_ТекущиеВизирующие.Очистить()`.
6. `А_ПредварительныеВизы.Очистить()`; для каждой роли получить пользователей (§5.1), **свернуть по
   Пользователю** (один пользователь = одна строка), в реквизит `Роли` склеить через `", "` названия его
   ролей. Это даёт «кто вообще будет подписывать» — чтобы человек мог подписать заранее.

**Общая часть (штампуем текущую визу):**
- `ТекРоль = А_Виза_ТекущаяРоль`; если пусто И (`Менеджер = ТекПольз` ИЛИ `Автор = ТекПольз`) → `Инициатор`.
- Найти строку `А_Визы` по `А_Виза_ТекущаяРоль`. Если роль = `Инициатор`, строки нет, а `А_Визы` не пусты →
  `А_Визы.Вставить(0)` (**инициатор становится первой строкой истории**). Иначе — найденная строка либо
  `А_Визы.Добавить()`.
- Заполнить строку: `Роль`, `Пользователь = ТекПольз`, `Дата = ДатаВизы`, `Виза_Состояние = пСостояние`,
  `Авто = ЭтоАвтоВиза`, `Комментарий = пДопы.Виза_Причина`.
- `А_Виза_Дата = ТекущаяДата()`; `А_Виза_Причина = пДопы.Виза_Причина` — **явным присваиванием**, см. §8.12.

**Если `НужныВизы ИЛИ НужныПольз`:**

*Ветка `пСостояние = Утвержден`:*
1. `А_Виза_ТекущаяРоль = Неопределено`.
2. Идти по `А_Визы` сверху вниз; **первая строка с незаполненным `Виза_Состояние`** → это следующая роль:
   `А_Виза_ТекущаяРоль = Строка.Роль`; `А_ТекущиеВизирующие` = `ПолучитьМассивПользователей(...)` для неё;
   `Прервать`.
3. `А_Виза_Состояние = ?(А_Виза_ТекущаяРоль пустая, Утвержден, НаВизировании)`.
4. **🔑 ИНТЕГРАЦИЯ СО СТАТУСОМ:**
   - `А_Виза_Состояние = Утвержден` (маршрут пройден целиком):
     ```bsl
     ДокОбъект.ДополнительныеСвойства.Вставить("А_ВизаДвижок", Истина);   // снимает гейт §6.3
     Если НЕ ДокОбъект.УстановитьСтатус("Согласован", Неопределено) Тогда
         // заказ не прошёл ПроверитьЗаполнение() — визу НЕ применяем
         Возврат Ошибка("Заказ не заполнен, статус «Согласован» не установлен");
     КонецЕсли;
     ```
   - `А_Виза_Состояние = НаВизировании` → `Статус` остаётся `НеСогласован`, ничего не делаем.
5. **Авто-утверждение по предварительным визам:** если среди `А_ПредварительныеВизы` есть строка
   с `Утверждено = Истина`, чей `Пользователь` попал в свежие `А_ТекущиеВизирующие` — рекурсивно
   `УстановитьСостояние(ДокОбъект, Утвержден, {ТекущийПользователь = тот, ЭтоАвтоВиза = Истина,
   ДатаВизы = ДатаУтверждения, Виза_Причина = Комментарий})`; `Прервать`.

*Ветка `пСостояние ∈ {Черновик, Отклонено, Анулировано}`:*
1. `А_ТекущиеВизирующие` = уникальный набор `[Менеджер, Автор]` (возврат мяча инициатору).
2. `А_Виза_Состояние = пСостояние`; `А_Виза_ТекущаяРоль = Инициатор`.
3. **🔑 ИНТЕГРАЦИЯ:**
   ```bsl
   ДокОбъект.ДополнительныеСвойства.Вставить("А_ВизаДвижок", Истина);
   ДокОбъект.УстановитьСтатус("НеСогласован", Неопределено);   // движения уходят
   ```

### 🔑 КОНТРАКТ ЗАПИСИ: движок визы документ НЕ ПИШЕТ

**Это отличие от Казны и это принципиально.** В Казне `Виза_УстановитьСостояние` в конце сам делал
`ДокОбъект.Записать(Проведение)` — потому что его звали прямо из формы. У нас движок встроен в типовую
схему ЕРП, а там контракт другой (см. `ОбщегоНазначенияУТВызовСервера.УстановитьСтатусДокументов:107–122`):

```
Объект = Ссылка.ПолучитьОбъект();
Если Не Объект.УстановитьСтатус(НовыйСтатус, ДопПараметры) Тогда Продолжить; КонецЕсли;  // ← НЕ пишет
Объект.Записать(?(Выборка.ЗаписьПроведением, Проведение, Запись));                        // ← пишет ВЫЗЫВАЮЩИЙ
```

⇒ **`А_ВизированиеСервер.УстановитьСостояние(ДокОбъект, …)` только меняет объект в памяти** (реквизиты
`А_Виза_*`, ТЧ `А_Визы` / `А_ТекущиеВизирующие` / `А_ПредварительныеВизы`, и через типовой
`ДокОбъект.УстановитьСтатус("Согласован"/"НеСогласован", …)` — реквизит `Статус`) и **возвращает результат.
Запись делает вызывающий:**

| Вызывающий | Кто пишет |
|---|---|
| пакетный движок `А_ВизированиеВызовСервера.УстановитьВизуДокументов` (§7.3) | **он**, в `Попытка`, `Записать(РежимЗаписиДокумента.Проведение)` |
| форма документа / прочий код | **он же**, после вызова |

Так снимается двойная запись и мы получаем ту же устойчивость, что у типового: блокировка → изменение →
одна запись → счётчик.

**Флаг `ЭтоАвтоВиза`** теряет роль «не писать» (движок и так не пишет) и остаётся только пометкой
«виза поставлена автоматически» → пишется в `А_Визы.Авто`. Рекурсивный вызов для авто-визы по
предварительным визам меняет тот же объект в памяти — запись всё равно одна, в конце, у вызывающего.

**Возвращаемое значение — ВСЕ ветки без исключения возвращают структуру** `{Успех: Булево, ТекстОшибки: Строка}`.
Ни одного «голого» `Возврат;`. Исключений не бросать — массовое утверждение обязано собирать ошибки
построчно и продолжать (§8.5).

### 5.5 `ДоступныеСостояния(ДокСсылка, пДопы = Неопределено) Экспорт` — гейт прав
Порт `Виза_ДокументДоступен_НовыеСостояния`. Возвращает
`Структура {ФормаДоступна: Булево, Состояния: СписокЗначений, СкипатьЭлФормы: Строка}`.

| Текущее `А_Виза_Состояние` | Кому что доступно |
|---|---|
| ссылка не заполнена (новый) | все состояния |
| `Черновик` / `Анулировано` / `Отклонено` | автор/менеджер или `ПолныеПрава`/`А_ВизированиеАдминистратор` → `{Утвержден, УтвержденСКомментариями, УтвержденПоСхеме, Черновик, Отклонено, Анулировано}` |
| `НаВизировании` | тек. пользователь ∈ `А_ТекущиеВизирующие` **или** админ → `{Утвержден, УтвержденСКомментариями, Отклонено}`;<br>автор/админ → дополнительно `{Черновик, Анулировано}`;<br>тек. пользователь ∈ `А_ПредварительныеВизы` → дополнительно `ПустаяСсылка()` («ОТЛОЖЕНО (виза)») |
| `Утвержден` | только админ → `{Отклонено}` |

Представления состояний в `СписокЗначений` — как в Казне: «Утвердить», «Отклонить», «Анулировать»,
«Черновик», «ОТЛОЖЕНО (виза)» и т.д.

### 5.6 `ДолжностьПользователя(Пользователь) Экспорт` → `СправочникСсылка.Должности`

### 6.3 Врезки в `ObjectModule` (4 штуки, все в хвост типовых обработчиков)

**(1) `ОбработкаЗаполнения`** — в конец:
```bsl
//++ А_Визирование
Если НЕ ЗначениеЗаполнено(А_Виза_Состояние) Тогда
    А_Виза_Состояние = Перечисления.А_Визы_Состояния.Черновик;
КонецЕсли;
//-- А_Визирование
```

**(2) `ПриКопировании`** — в конец: сбросить `А_Виза_*` реквизиты и очистить `А_Визы`,
`А_ТекущиеВизирующие`, `А_ПредварительныеВизы`.

**(3) `ПередЗаписью`** — в конец, **строго в этом порядке**:
```bsl
//++ А_Визирование
А_Виза_ТекущиеВизирующие = А_ВизированиеСервер.ПредставлениеТекущихВизирующих(ЭтотОбъект);

Если ОбменДанными.Загрузка Тогда
    Возврат;   // ← КРИТИЧНО: иначе обмен с BuhBud встанет (§8.4)
КонецЕсли;

Если ПометкаУдаления И НЕ Ссылка.ПометкаУдаления Тогда
    А_Виза_Состояние = Перечисления.А_Визы_Состояния.Анулировано;
КонецЕсли;

// ГЕЙТ ОБХОДА: без визы статус «Согласован»/«Подтвержден» не выставить
А_ВизированиеСервер.ПроверитьЗапретОбходаВизирования(ЭтотОбъект, Отказ);
//-- А_Визирование
```
Сам гейт (в общем модуле). **Порядок проверок критичен — читать вместе с §0 и §3.5:**
```bsl
Процедура ПроверитьЗапретОбходаВизирования(ДокОбъект, Отказ) Экспорт

    // 1. ДИСКРИМИНАТОР КОНТУРА — сердце решения.
    //    Пустое визовое состояние = документ ВНЕ контура визирования: это либо заказ, приехавший
    //    обменом из бухгалтерии (при обмене ОбработкаЗаполнения не вызывается, значит Черновик
    //    никто не поставил), либо один из 10 060 исторических. Их не трогаем — гейт молчит.
    //    Благодаря этой проверке миграция исторических данных НЕ НУЖНА.
    Если НЕ ЗначениеЗаполнено(ДокОбъект.А_Виза_Состояние) Тогда
        Возврат;
    КонецЕсли;

    // 2. статус ставит сам движок визирования — пропускаем
    Если ДокОбъект.ДополнительныеСвойства.Свойство("А_ВизаДвижок") Тогда
        Возврат;
    КонецЕсли;

    // 3. блокируем ТОЛЬКО статусы, порождающие движения.
    //    «Закрыт» НЕ блокируем — иначе незавизированный заказ невозможно закрыть (тупик).
    Если НЕ (ДокОбъект.Статус = Перечисления.СтатусыЗаказовПоставщикам.Согласован
          ИЛИ ДокОбъект.Статус = Перечисления.СтатусыЗаказовПоставщикам.Подтвержден) Тогда
        Возврат;
    КонецЕсли;

    // 4. статус НЕ меняется этой записью (перепроведение/правка шапки уже согласованного) — пропускаем
    Если ЗначениеЗаполнено(ДокОбъект.Ссылка) Тогда
        СтарыйСтатус = ОбщегоНазначения.ЗначениеРеквизитаОбъекта(ДокОбъект.Ссылка, "Статус");
        Если СтарыйСтатус = ДокОбъект.Статус Тогда
            Возврат;
        КонецЕсли;
    КонецЕсли;

    // 5. виза пройдена — разрешаем
    Если ДокОбъект.А_Виза_Состояние = Перечисления.А_Визы_Состояния.Утвержден Тогда
        Возврат;
    КонецЕсли;

    // 6. админ может обойти
    Если РольДоступна("ПолныеПрава") ИЛИ РольДоступна("А_ВизированиеАдминистратор") Тогда
        Возврат;
    КонецЕсли;

    ОбщегоНазначенияКлиентСервер.СообщитьПользователю(
        "Заказ не завизирован — статус «" + ДокОбъект.Статус + "» недоступен.
        |Отправьте заказ на визирование через рабочее место «Визирование заказов поставщикам».",
        ДокОбъект.Ссылка, "Статус", , Отказ);

КонецПроцедуры
```
**Пункт 1 — сердце решения:** он выводит из-под гейта весь обменный поток и всю историю, поэтому миграция
данных не нужна.
**Пункт 4 — обязателен:** без него перепроведение или правка уже согласованного заказа **внутри контура**
упрётся в «Отказ».

⚠️ Ранний выход по `ОбменДанными.Загрузка` (врезка 3, ДО вызова гейта) — **второй, независимый
предохранитель**. Оставить оба: дискриминатор закрывает «обменный заказ не должен видеть визу», а
`ОбменДанными.Загрузка` — любые будущие сценарии загрузки.

**(4) новый экспортный метод** (тонкий, делегирует):
```bsl
// Устанавливает состояние визы. Обёртка над движком.
Функция А_Виза_УстановитьСостояние(пСостояние, пДопы = Неопределено) Экспорт
    Возврат А_ВизированиеСервер.УстановитьСостояние(ЭтотОбъект, пСостояние,
        ?(пДопы = Неопределено, Новый Структура, пДопы));
КонецФункции
```

### 6.5 Чего НЕ делаем
- `ОбработкаПроведения` — **не трогаем вообще**.
- `Согласован` / `ДатаСогласования` — **не пишем руками**, их ведёт типовой механизм.
- **`ОбновитьЗаказПоставщикуПослеОбмена` (ObjectModule:503) — НЕ трогаем.** Обменные заказы продолжают
  авто-подтверждаться (§3.5). Визирование обменного потока — будущая отдельная задача.
- **Правила обмена — НЕ трогаем.** Визовые реквизиты/ТЧ в правила конвертации не добавлять.
- **Миграция исторических данных — НЕ ДЕЛАЕМ.** Дискриминатор §6.3 п.1 выводит все 10 060 существующих
  заказов из-под гейта автоматически (у них пустое `А_Виза_Состояние`).
- Типовые формы `ФормаДокумента` / `ФормаСписка` — **в v1 не трогаем** (визовые реквизиты видны через
  рабочее место). Показ визы в форме документа — отдельная фаза, если попросят.

### 6.6 Как заказ попадает в контур визирования (и как НЕ попадает)

| Путь появления заказа | Вызывается `ОбработкаЗаполнения`? | `А_Виза_Состояние` | Контур |
|---|---|---|---|
| Интерактивно в ЕРП (кнопка «Создать») | да | `Черновик` | **внутри** |
| `Заполнить(Основание)` — «Создать на основании» | да | `Черновик` | **внутри** |
| Программно: `СоздатьДокумент()` + `Заполнить(...)` | да | `Черновик` | **внутри** |
| Программно: `СоздатьДокумент()` **без** `Заполнить(...)` | **нет** | пустое | снаружи ⚠️ |
| Загрузка обменом из бухгалтерии (КД 2.0) | **нет** | пустое | снаружи (by design) |
| 10 060 существующих заказов | — | пустое | снаружи |

**Единственная дыра — предпоследняя строка:** программное создание заказа минуя `ОбработкаЗаполнения`.
Такой заказ выпадет из контура. Это и есть предмет инвентаризации §6.7.

### 6.7 🚨 Инвентаризация программных мест ПЕРЕД включением гейта

### 7.1 Реквизиты формы

### 7.2 Запрос динамического списка
Порт запроса Казны, шапка `ЗаказПоставщику` + вычисляемые колонки.

🚨 **Первое условие — отсечь всё, что вне контура.** Без него в журнал вывалятся все 10 060 обменных
заказов (§3.5). Это условие **не отключается ни одним режимом/отбором**:
```
ГДЕ
    Т.А_Виза_Состояние <> ЗНАЧЕНИЕ(Перечисление.А_Визы_Состояния.ПустаяСсылка)   -- ← только контур
    И (&РежимОчереди = 0
            И (&ПоказыватьПомеченные ИЛИ НЕ Т.ПометкаУдаления)
        ИЛИ &РежимОчереди = 1
            И Т.А_ТекущиеВизирующие.Пользователь = &ТекущийПользователь
            И Т.А_Виза_Состояние = &Состояние_НаВизировании
            И НЕ Т.ПометкаУдаления
        ИЛИ &РежимОчереди = 2
            И Т.А_ПредварительныеВизы.Пользователь = &ТекущийПользователь
            И Т.А_ПредварительныеВизы.Утверждено = ЛОЖЬ
            И Т.А_Виза_Состояние = &Состояние_НаВизировании
            И НЕ Т.ПометкаУдаления)
```
⚠️ Осторожно: `ПустаяСсылка` перечисления — **это не то же самое**, что состояние «предварительная виза»
(там `ПустаяСсылка()` используется как маркер команды, а не как значение реквизита). В реквизите
`А_Виза_Состояние` пустая ссылка означает ровно одно: **документ вне контура визирования**.
⚠️ **Обращение к ТЧ через точку от основной таблицы размножает строки** — см. §8.2. Обязательно проверить
через Python COM оба варианта (`СГРУППИРОВАТЬ ПО` как в Казне vs `Ссылка В (ВЫБРАТЬ ... ИЗ ...ТЧ)`) и взять
тот, что даёт корректное количество и приемлемый план.

Колонки списка: `Номер`, `Дата`, `Организация`, `Подразделение`, `Партнер`, `Контрагент`, `СуммаДокумента`,
`Статус` (заказа), `А_Виза_Состояние`, `А_Виза_ТекущаяРоль`, `А_Виза_ТекущиеВизирующие`, `А_Виза_Дата`,
`Автор`, `Менеджер`, `НаправлениеДеятельности`, `Комментарий`, признак наличия присоединённых файлов.

Параметры списка (устанавливать в `ПриСозданииНаСервере` и при смене режима):
`&ТекущийПользователь`, `&РежимОчереди`, `&Состояние_НаВизировании`, `&ПоказыватьПомеченные`.

**🥇 Отборы — через ТИПОВОЙ механизм** (`ФормаСпискаЗаявокКСогласованию:24–46, 65–96`), а не только через
`УстановитьЭлементОтбораДинамическогоСписка`:
```bsl
// ПриСозданииНаСервере — с поддержкой внешнего параметра СтруктураБыстрогоОтбора
ОтборыСписковКлиентСервер.ОтборПоЗначениюСпискаПриСозданииНаСервере(
    Список, "Организация", Организация, СтруктураБыстрогоОтбора);
...
// ПриЗагрузкеДанныхИзНастроекНаСервере — ОТБОРЫ СОХРАНЯЮТСЯ МЕЖДУ СЕАНСАМИ
ОтборыСписковКлиентСервер.ОтборПоЗначениюСпискаПриЗагрузкеИзНастроек(
    Список, "Организация", Организация, СтруктураБыстрогоОтбора, Настройки);
```
- `Подразделение` — `ВидСравненияКомпоновкиДанных.ВИерархии`; период — `МеньшеИлиРавно` (как `ДатаОплаты`).
- **Параметр формы `СтруктураБыстрогоОтбора`** — чтобы журнал можно было открыть извне сразу с нужным
  отбором (например, из формы заказа: «показать все мои на визировании»).
- **Дефолт при открытии — режим «Мне на визирование»** (в типовом дефолт `Статус = НеСогласована`, т.е.
  форма сразу показывает то, что ждёт решения; наш аналог — очередь текущего пользователя).

### 7.3 Команды (массовые, по `Элементы.Список.ВыделенныеСтроки`)
| Команда | Что делает |
|---|---|
| **Утвердить** | вопрос «Утвердить N заказов?» → по каждому: `ДоступныеСостояния` содержит `Утвержден`? → `А_Виза_УстановитьСостояние(Утвержден)`. Для инициатора из `Черновик` это же действие **строит маршрут и отправляет на визирование**. |

Для «Отклонить» — между вопросом и сервером добавляется `ПоказатьВводСтроки` («Укажите причину отказа»),
причина уходит в `ДопПараметры.Виза_Причина` (как в Казне `ФормаСписка_Визирование:149–202`).

**Сервер — новый общий модуль `А_ВизированиеВызовСервера` (Вызов сервера), функция
`УстановитьВизуДокументов(МассивДокументов, ИмяСостояния, ДопПараметры = Неопределено)` → Число.**
Это **точная калька** `ОбщегоНазначенияУТВызовСервера.УстановитьСтатусДокументов` (`:23–130`) — копировать
структуру построчно, заменив только «статус» на «визу»:

| Шаг типового движка | Наш аналог |
|---|---|
| шаблоны ошибок `НСтр` (помечен на удаление / не проведён / статус совпадает / не заблокировать / не записать) | те же, про визу |
| `СформироватьЗапросПроверкиПриСменеСтатуса` | `А_ВизированиеСервер.СформироватьЗапросПроверкиПриСменеВизы(МассивДокументов, ИмяСостояния)` — те же поля выборки: `Ссылка, Представление, СостояниеСовпадает, Проведен, ПометкаУдаления, ЗаписьПроведением (= ИСТИНА)` + **`ВЗоне` (= `А_Виза_Состояние` заполнено)** |
| универсальные проверки построчно | помечен на удаление · **не проведён** · состояние уже совпадает · **вне контура визирования** (§8.15) |
| `ПроверкаПередСменойСтатуса` | `А_ВизированиеСервер.ДоступныеСостояния(...)` — можно ли текущему пользователю поставить это состояние (§5.5) |
| `ЗаблокироватьДанныеДляРедактирования(Ссылка)` в `Попытка` | **так же** — не выбрасывать |
| `Объект.УстановитьСтатус(...)` | `Объект.А_Виза_УстановитьСостояние(Состояние, ДопПараметры)` |
| `Объект.Записать(Проведение)` в `Попытка` | **так же — пишет ИМЕННО ЭТОТ движок, ровно один раз.** Движок визы документ не пишет (§5.4, «Контракт записи») |
| `Возврат КоличествоОбработанных` | **так же** |

**Почему именно так, а не самописный цикл:** типовой движок уже даёт блокировку объекта, корректные
сообщения с привязкой к документу (`СообщитьПользователю(текст, Ссылка)` → кликабельно), устойчивость к
ошибке одного документа и совместимый со всей ЕРП контракт. Плюс типовая клиентская обвязка
(`ПроверитьПолучитьВыделенныеВСпискеСсылки`, `ОповеститьПользователяОбУстановкеСтатуса`) переиспользуется
без единой строки своего кода.

⚠️ **Не заворачивать пакет в одну транзакцию** — ошибка одного заказа не должна откатывать уже поставленные
визы остальных (типовой движок тоже не заворачивает). Транзакционный оркестратор
`ПомощникПродаж:5879/6304/6306` — это про создание пакета связанных документов, у нас другой случай.

⚠️ **Требование «документ проведён»** — типовой движок отклоняет непроведённые. Оставляем: на визирование
уходит только проведённый заказ (проведение при `Статус = НеСогласован` разрешено, движений не даёт).

## 8. 🔥 Грабли (все обязательны к учёту)

### 8.1 Rule #-1 — тест запросов Python COM **перед** BSL
Ни один запрос не попадает в BSL без успешного прогона против BaseERP. Шаблон — §9.

### 8.2 Обращение к ТЧ через точку от основной таблицы **размножает строки**
`Т.А_ТекущиеВизирующие.Пользователь = &Пользователь` в `ГДЕ` порождает неявное соединение → дубли строк.
Казна лечит `СГРУППИРОВАТЬ ПО` со всеми колонками + `МАКСИМУМ(...)` по агрегатам. Альтернатива без дублей:
```
И Т.Ссылка В (ВЫБРАТЬ Т2.Ссылка ИЗ Документ.ЗаказПоставщику.А_ТекущиеВизирующие КАК Т2
              ГДЕ Т2.Пользователь = &ТекущийПользователь)
```
**Проверить оба через COM**, выбрать корректный + быстрый.

### 8.3 Неограниченные строки не группируются
`А_Виза_ТекущиеВизирующие` — Строка(250) по метаданным. `Комментарий` заказа — неограниченный, в запрос
брать только через `ВЫРАЗИТЬ(Т.Комментарий КАК СТРОКА(1024))`.

### 8.4 `ОбменДанными.Загрузка` — гейт ОБЯЗАН пропускать
У `ЗаказПоставщику` есть `А_Обработан` / `А_НомерДокументаИзБух` ⇒ документ участвует в обмене с BuhBud.
Если гейт §6.3 сработает при загрузке из обмена — **обмен встанет**. Первая же проверка в `ПередЗаписью`
после пересчёта строки визирующих: `Если ОбменДанными.Загрузка Тогда Возврат; КонецЕсли;`

### 8.5 `УстановитьСтатус` возвращает `ПроверитьЗаполнение()`
Незаполненный заказ **не станет** «Согласован». Массовое утверждение обязано собирать ошибки построчно и
продолжать, а не бросать исключение на первом документе.

### 8.6 `Ссылка` — запретное имя локальной переменной в BSL
Конфликтует с системным свойством и даёт молчаливые сбои внутри `Попытка/Исключение`. Использовать
`ДокСсылка` / `РезСсылка`.

### 8.7 У `Справочник.Пользователи` в ЕРП **нет реквизита `Должность`** (в Казне был)
Схема визирования в Казне использует `Ответственный.Должность` как измерение специфичности.
Решение для v1: функция `А_ВизированиеСервер.ДолжностьПользователя(Пользователь)` —
`Пользователи → Физлицо → Сотрудники/кадровая история → Должность`. **Реализовать честно; если не
резолвится — вернуть пустую ссылку** (тогда отрабатывают строки схемы с пустой `Должность`, что корректно).
Измерение `Должность` в РС **оставить** — оно нужно для полноты порта.

### 8.8 Внешняя обработка: цвет только кодом
`<TextColor>style:...</TextColor>` в `Form.xml` внешней обработки валит `epf-build` («Исключение XDTO»).
Всё оформление — программно.

### 8.9 Управляемую форму нельзя проверить headless через COM
`win32com` smoke проверяет только создание объекта обработки и вызов серверных методов. **Форму открывать
в клиенте самому** и убедиться, что она рисуется, отборы работают, кнопки живые.

### 8.10 Designer кеширует BSL
После `cp` `.bsl` в основной каталог — обновление конфигурации (`db-load-xml` + `db-update`, скилы
`db-*`), не биться с `1cv8.exe` вручную.

### 8.11 `ПолныйКод()` в расчёте «Глубины»
Работает: `СтруктураПредприятия`, `СтатьиДвиженияДенежныхСредств`, `НаправленияДеятельности` —
все иерархические, `CodeLength = 9`. Но **проверить через COM** на реальных элементах.

### 8.12 `ЗаполнитьЗначенияСвойств(ДокОбъект, пДопы)` **не сработает** — мешает префикс `А_`
В Казне реквизиты называются `Виза_Причина`, `Виза_Состояние`, и ключи структуры `пДопы` совпадают с ними
по имени — поэтому `ЗаполнитьЗначенияСвойств` их переносит. У нас реквизиты называются `А_Виза_Причина`,
`А_Виза_Состояние` — **имена не совпадут, перенос молча не произойдёт**.
⇒ Все визовые поля документа писать **явными присваиваниями**. `ЗаполнитьЗначенияСвойств(ДокОбъект, пДопы)`
из порта **убрать** (либо звать с явным списком свойств).

### 8.13 `ОбработкаЗаполнения` при обмене НЕ вызывается — на этом стоит весь дискриминатор
КД 2.0 создаёт объект и присваивает свойства напрямую, `ОбработкаЗаполнения` не срабатывает. Именно поэтому
у обменного заказа `А_Виза_Состояние` остаётся пустым, и он естественным образом оказывается вне контура
(§6.6). **Проверить это эмпирически** (Python COM: создать заказ через `СоздатьДокумент()` без `Заполнить()`
и убедиться, что визовое состояние пустое) — на этом факте держится и гейт, и журнал, и отсутствие миграции.

### 8.14 Второй кастомный хук в пути записи — подписка
`CommonModules\А_СобытияОбъектов\Ext\Module.bsl:721` → `ЗаказПоставщику_ПередЗаписью`. Отрабатывает **после**
`ПередЗаписью` модуля объекта. Прочитать целиком перед врезкой гейта: если он меняет `Статус`, порядок
проверок гейта надо пересмотреть.

### 8.15 Обменный заказ можно завизировать «случайно»
Если пользователь откроет обменный заказ и нажмёт что-то, что проставит `А_Виза_Состояние`, документ
провалится в контур и заблокируется гейтом. Поэтому: команды журнала и кнопки визирования **не должны быть
доступны** для документов с пустым визовым состоянием, а сам журнал их не показывает (§7.2). Дополнительно —
в `А_ВизированиеСервер.УстановитьСостояние` проверять: если `А_Виза_Состояние` пустое **и** `Статус` уже
`Подтвержден`/`Согласован` → вернуть `{Успех=Ложь, ТекстОшибки="Заказ вне контура визирования (создан
обменом)"}` и ничего не писать.

## 12. Порядок работ

1. **Разведка механизма** — прочитать источники §2.3 (Казна: ObjectModule 164–420, ManagerModule 1–183,
   оба РС, форму `ФормаСписка_Визирование`).
2. **Разведка инженерии (§2.1 + §2.2)** — прочитать базу знаний по рабочим местам и **открыть эталоны**
   по карте §2.2: `ПомощникПродаж:2967/2976/2986/6603` (команды над выделением),
   `ОбеспечениеПотребностей:796/803/2188` (master-detail) и `:24/4763` (оформление кодом),
   `РегистрацияИзмененийДляОбменаДанными:2048–2066` (динсписок). **Это отдельный шаг, не «по ходу дела».**
3. **Инвентаризация §6.7** — кто создаёт заказ программно и кто ставит ему статус. Прочитать подписку
   `А_СобытияОбъектов:721`. **До написания кода.**
4. **Фаза 1** — объекты конфигурации (§4), `meta-validate`.
5. **Фаза 2** — движок `А_ВизированиеСервер` (§5). Каждый запрос — сначала Python COM.
6. **Фаза 3а** — реквизиты + ТЧ + врезки 1/2/4 в `ЗаказПоставщику` (§6.1–6.3), **но гейт пока НЕ включать**.
   Обновить конфигурацию. Проверить: обмен по-прежнему приносит заказы, существующие заказы перепроводятся.
7. **Проверить дискриминатор эмпирически (§8.13)** — обменный/программно созданный без `Заполнить()` заказ
   имеет пустое `А_Виза_Состояние`; созданный интерактивно — `Черновик`. **Гейт включать только если это так.**
8. **Фаза 3б — включить гейт §6.3.** Немедленно прогнать регрессию обмена и истории (acceptance пп. 11–14).
9. **Заполнить тестовые данные** — 2 роли, схема, адресация.
10. **Фаза 4** — `.epf` рабочего места (§7), по карте эталонов §2.2; `epf-build`; **открыть в клиенте самому**.
11. **Acceptance** — сквозной smoke §10 целиком.
12. **`bas-verify`** — гейт §11 (включая заземление на эталоны и tier ≥ 3). Только после него — «готово».

> что обменный поток остаётся вне контура. Гейт — единственное место, где эта разработка может сломать
> боевые закупки (10 060 документов, поток идёт ежедневно).
