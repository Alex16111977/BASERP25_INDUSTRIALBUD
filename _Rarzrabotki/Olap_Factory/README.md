# Olap_Factory — витрина «План-факт производства» и модель Power BI

Отдельный контур, **независимый от `_Rarzrabotki/Olap/Ai_Olap`**: своя база `OlapFactory`,
свой ETL-проект, свой WHITELIST маппинга. Ai_Olap и его пайплайны (PnL / Cashflow / Balance)
не затрагиваются — перегенерация маппинга здесь не может сдвинуть их `_FldNNN`.

```
Olap_Factory/
├─ Py_Olap/                        ETL-проект (клон движка ai_olap + своя конфигурация)
│  ├─ .venv/                       окружение (23 пакета, requirements.txt)
│  ├─ ai_olap/                     движок: extractors / transformers / loaders / orchestrator
│  ├─ mapping/refresh_mapping.py   WHITELIST из 12 объектов 1С -> baserp_storage.json
│  ├─ pipelines/dim_factory.json               7 справочников-измерений (full_reload)
│  ├─ pipelines/fact_planfact_proizvodstvo.json факт из РС А_ПланФактПроизводство_Свод
│  ├─ scripts/ddl_olap_factory.sql + apply_ddl.py
│  ├─ scripts/introspect_planfakt_fields.py    физические _InfoRg / _Fld
│  ├─ scripts/build_pbip.py                    генератор модели Power BI
│  └─ tests/verify_olap_factory.py             приёмка витрины (сверка с 1С)
├─ ПланФактВиробництва.pbip                    проект Power BI
├─ ПланФактВиробництва.SemanticModel/          модель: 9 таблиц, 22 меры, 9 связей (TMDL)
└─ ПланФактВиробництва.Report/                 отчёт (одна пустая страница — визуалы за вами)
```

## Цепочка

`Документ.А_Отчет_ПланФактныйПроизводство` (проведение) → `РегистрСведений.А_ПланФактПроизводство_Свод`
→ ETL → `OlapFactory.Fact_PlanFactProizvodstvo` → `vw_Fact_PlanFact` → Power BI.

Вся бизнес-логика живёт в 1С. ETL — чистый копировщик: ни одной формулы, ни одного фильтра
по смыслу данных.

## Запуск

```bash
cd C:\Configuration_downloads\BASERP25\_Rarzrabotki\Olap_Factory\Py_Olap
.venv\Scripts\python.exe main.py                      # весь конвейер: справочники + факт
.venv\Scripts\python.exe main.py --run-once fact_planfact_proizvodstvo
.venv\Scripts\python.exe main.py --run-once fact_planfact_proizvodstvo --period 2026-07
.venv\Scripts\python.exe main.py --validate           # схема пайплайнов
.venv\Scripts\python.exe tests\verify_olap_factory.py # приёмка: SQL == 1С
```

Порядок при доработке 1С: перепровести документы → `main.py` → Refresh в Power BI.

**Если менялся состав измерений/ресурсов регистра** — сначала
`.venv\Scripts\python.exe mapping\refresh_mapping.py`, затем
`scripts\introspect_planfakt_fields.py` и правка `_FldNNN` в raw_sql пайплайна.
Платформенные номера полей зависят от порядка реквизитов и сдвигаются.

## Модель Power BI

Открыть `ПланФактВиробництва.pbip` в Power BI Desktop (2.153+). Модель подтянется из TMDL,
данные — из `OlapFactory` в режиме Import. Чтобы получить `.pbix` — «Файл → Сохранить как».

**Правило периода зашито в меры.** `План, год`, `План, грн`, `План, к-сть` и
`Плановий розрахунок матеріалів, грн` обёрнуты в `REMOVEFILTERS('Calendar')` — они показывают
полную картину при любом положении слайсера дат. `Факт`, `Виконання` и всё производное от них
следуют за выбранным периодом. Это ровно поведение отчёта `А_ПланФактныйПроизводствоПолный`:
план — состояние кошториса «как сейчас», факт — за окно.

Все таблицы читаются **native query с явным списком колонок**. Так сделано намеренно: коннектор
`Sql.Database` кеширует схему, и при обычном `[Schema=,Item=]` новая колонка после `ALTER TABLE`
не появляется даже после Full Refresh. При добавлении колонки в SQL — дописать её в список
в `scripts/build_pbip.py` и пересобрать модель.

**Calendar — зеркало эталона.** С 02.08.2026 таблица не сеется своим кодом, а копируется
один в один из живой `OlapBASERP.dbo.Calendar` — той самой, которую показывает
`_Rarzrabotki/PowerBi/Industrial/PL.pbix`: 43 колонки, те же имена и типы, 2024-01-01 … 2027-12-31.
Делает это `scripts/apply_ddl.py` (`синхронизировать_календарь`): структуру читает из
`INFORMATION_SCHEMA` соседней базы, строки — межбазовым `INSERT … SELECT`. В `OlapBASERP`
только читаем, никогда не пишем. Правки календаря делаются в эталоне, локальные правки
в витрине затрутся следующим прогоном.

## Представления

* `vw_Fact_PlanFact` — факт с разрешённой составной аналитикой: `Analytics_Name` собирает
  номенклатуру, физлицо или свободный текст в одну читаемую колонку. Благодаря этому в модели
  нет неоднозначных связей и нет DAX-лукапов.
* `Dim_Departments_Tree` — рекурсивный CTE с `Level1..Level5` и путём: готовый drill
  «Производство → МД IRS 2026 → 15 м → №1».

## Расшифровка до первичного документа

`Dim_Documents` даёт то же, что расшифровка в 1С: за каждой цифрой видно документ-источник.
Собирается одним `UNION ALL` по четырём физическим таблицам BaseERP и хранит готовое
представление вида «Табель учета рабочего времени (казна) 000003207 от 01.07.2026».

| Тип строки | Ведёт на | Документов |
|---|---|---:|
| `Факт` (часы) | Табель учета рабочего времени (казна) | 20 |
| `Факт` (материалы) | Приобретение товаров и услуг | 356 |
| `Виконання` | Выполнение работ модулей | 27 |
| `План` | Структура себестоимости (карточка кошториса) | 5 |
| `ПланНаФакт` | — | 0 |

🔴 У строк ETC документа нет **by design**: это расчётный остаток плана, а не проводка.
В отчёте они лягут в строку «пусто» — так и должно быть.

В Power BI таблица называется **Документи**, связана с фактом по `Document_ID`
(many-to-one, single). Чтобы получить расшифровку — положить `Документи[Документ]`
в таблицу рядом с любой мерой. FK-сирот 0: каждая цифра находит свой документ.
