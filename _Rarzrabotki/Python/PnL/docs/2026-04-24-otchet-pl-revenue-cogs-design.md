# Доработка `Отчет.А_ОтчетPL` — Выручка через `ВыручкаИСебестоимостьПродаж` + CoGS через флаг на ДДС

**Дата:** 2026-04-24  
**Статус:** согласовано финансистом, готово к реализации

---

## Context

### Проблема #1 — «мусорный» регистратор в расшифровке Выручки
`Reports/А_ОтчетPL/Ext/ObjectModule.bsl` (строки 151–198) получает Выручку от продаж из `РегистрНакопления.ФинансовыеРезультаты.Обороты(..., Регистратор, ...)`. Этот регистр — **сводный**: документ `РасчетСебестоимостиТоваров` при закрытии месяца пишет в него итоговую выручку, и тогда в drill-down отчёта вместо исходной Реализации финансист видит служебный «Расчёт себестоимости товаров 0Ц-xxx».

Проверено MCP-запросом на февраль 2026:
- `ФинансовыеРезультаты.Обороты` даёт 61.5 млн грн по СтатьяДоходов=«Выручка от продаж», регистратор = РасчетСебестоимости.
- `ПрочиеДоходы` содержит только «Прочие доходи» и «Курсовые разницы» — Выручки от продаж в нём нет.

### Проблема #2 — Себестоимость продаж (CoGS) вообще не попадает в А_ОтчетPL
В текущем запросе нет источника CoGS. Сумма `5 215 829,27 ₴` за февраль 2026 по Глобино-2 (видно в «Доходы и расходы предприятия») должна стоять в А_ОтчетPL строке «Строительные материалы», но её там нет.

`АнализДоходовРасходов` CoGS тоже **не показывает** — он работает только с `ПрочиеДоходы`/`ПрочиеРасходы`/`ПартииПрочихРасходов`. Шаблона «как правильно делать» из стандартной конфигурации нет — нужно сделать самостоятельно.

### Источник-решение
`РегистрНакопления.ВыручкаИСебестоимостьПродаж` — специализированный регистр, хранит и Выручку (ресурс `СуммаВыручкиБезНДС`), и Себестоимость (ресурс `СтоимостьУпрБезНДС`), с полем `ДокументДвижения` (исходный документ-источник — Реализация/АктВыполненныхРабот/ВозвратТоваровОтКлиента). Тестом MCP подтверждено: за февраль 2026 — Выручка 51.5 млн, CoGS 16.2 млн.

## Архитектура потока данных

```
[ВыручкаИСебестоимостьПродаж]
    ├── СуммаВыручкиБезНДС > 0 → втЕРП_Доходы_Детали (новый источник Выручки)
    │      │ СтатьяДоходов = В.АналитикаУчетаНоменклатуры.СтатьяДоходов
    │      │ Документ      = В.ДокументДвижения   (Реализация, не РасчетСебестоимости)
    │      └→ JOIN Справочник.А_Статьи_PL ПО СтатьяДоходов → PL-статья
    │
    └── СтоимостьУпрБезНДС > 0 → втЕРП_CoGS_Детали (новый CTE)
           │ ДДС      = &ДДСCoGS   (из нового флага на ДДС)
           │ Документ = В.ДокументДвижения
           └→ JOIN втPL_ДДС (ТЧ Справочник.А_Статьи_PL.Статьи) ПО ДДС → PL-статья

[ПрочиеДоходы]  (без изменений)
    └→ Курсовые + Прочие доходи + Доходы от Фин.деятельности

[ПрочиеРасходы]  (без изменений)
    └→ Все расходы включая ЗП (единственный регистр, где есть ЗП)

[А_ДвиженияДенегИзКазны]  (без изменений)
    └→ Казна-блок отчёта
```

## Секция 1 — Доработка конфигурации

### 1.1. Новый реквизит справочника `СтатьиДвиженияДенежныхСредств`
| Свойство | Значение |
|---|---|
| Имя | `А_ПриёмникСебестоимостиПродажPL` |
| Тип | Булево |
| Синоним | «Приёмник себестоимости продаж (PL)» |
| Подсказка | «Истина — на эту статью ДДС в отчёте А_ОтчетPL вешается сумма Себестоимости продаж из регистра ВыручкаИСебестоимостьПродаж. Только одна ДДС в системе должна иметь этот флаг.» |
| Default | Ложь |
| Индексирование | DontIndex |

Позиция в XML — после `А_НеИспользоватьКазна` (логическое соседство с другими А_-булевыми).

### 1.2. Форма элемента ДДС
Чекбокс «Приёмник себестоимости продаж (PL)» после существующего `А_НеИспользоватьКазна`.

### 1.3. Валидация в `ПередЗаписью` (МодульОбъекта ДДС)
```bsl
Если А_ПриёмникСебестоимостиПродажPL И НЕ ПометкаУдаления И НЕ ОбменДанными.Загрузка Тогда
    Запрос = Новый Запрос;
    Запрос.Текст = "ВЫБРАТЬ ПЕРВЫЕ 1 Ссылка
                  |ИЗ Справочник.СтатьиДвиженияДенежныхСредств
                  |ГДЕ А_ПриёмникСебестоимостиПродажPL
                  |   И Ссылка <> &Текущая
                  |   И НЕ ПометкаУдаления";
    Запрос.УстановитьПараметр("Текущая", Ссылка);

        ВызватьИсключение "Только одна ДДС в системе может быть Приёмником себестоимости продаж PL. "
            + "Снимите флаг с другой статьи ДДС перед установкой здесь.";
    КонецЕсли;
КонецЕсли;
```

## Секция 2 — Доработка `Reports/А_ОтчетPL/Ext/ObjectModule.bsl`

### 2.1. Новая функция чтения параметра
```bsl
Функция ПолучитьДДСПриёмникCoGS()
    Запрос = Новый Запрос;
    Запрос.Текст = "ВЫБРАТЬ ПЕРВЫЕ 1 Ссылка
                  |ИЗ Справочник.СтатьиДвиженияДенежныхСредств
                  |ГДЕ А_ПриёмникСебестоимостиПродажPL И НЕ ПометкаУдаления";
    Рез = Запрос.Выполнить().Выгрузить();
    Если Рез.Количество() = 0 Тогда
        Возврат Справочники.СтатьиДвиженияДенежныхСредств.ПустаяСсылка();
    КонецЕсли;
    Возврат Рез[0].Ссылка;
КонецФункции
```

Вызывается в `ПолучитьОбъединенныеДанные` перед построением запроса. Параметр `&ДДСCoGS` передаётся в запрос.

### 2.2. Замена источника Выручки (строки ~149–199)
Удаляется подзапрос с `ФинансовыеРезультаты`. Новый блок в `втЕРП_Доходы_Детали`:

```sql
ВЫБРАТЬ
    В.Подразделение КАК Подразделение,
    В.АналитикаУчетаНоменклатуры.СтатьяДоходов КАК СтатьяДоходов,
    В.ДокументДвижения КАК Документ,
    ВЫБОР
        КОГДА В.ДокументДвижения ССЫЛКА Документ.РеализацияТоваровУслуг
            ТОГДА ВЫРАЗИТЬ(В.ДокументДвижения КАК Документ.РеализацияТоваровУслуг).Контрагент
        КОГДА В.ДокументДвижения ССЫЛКА Документ.АктВыполненныхРабот
            ТОГДА ВЫРАЗИТЬ(В.ДокументДвижения КАК Документ.АктВыполненныхРабот).Контрагент
        КОГДА В.ДокументДвижения ССЫЛКА Документ.ВозвратТоваровОтКлиента
            ТОГДА ВЫРАЗИТЬ(В.ДокументДвижения КАК Документ.ВозвратТоваровОтКлиента).Контрагент
        ИНАЧЕ ЗНАЧЕНИЕ(Справочник.Контрагенты.ПустаяСсылка)
    КОНЕЦ КАК Контрагент,
    СУММА(В.СуммаВыручкиБезНДС) КАК СуммаЕРП
ИЗ РегистрНакопления.ВыручкаИСебестоимостьПродаж.Обороты(
        &НачалоПериода, &КонецПериода, Регистратор,
        СуммаВыручкиБезНДС <> 0
    ) КАК В
ГДЕ В.АналитикаУчетаНоменклатуры.СтатьяДоходов <> ЗНАЧЕНИЕ(ПланВидовХарактеристик.СтатьиДоходов.ПустаяСсылка)
    И В.ДокументДвижения <> ЗНАЧЕНИЕ(Документ.РеализацияТоваровУслуг.ПустаяСсылка)
СГРУППИРОВАТЬ ПО В.Подразделение, В.АналитикаУчетаНоменклатуры.СтатьяДоходов, В.ДокументДвижения, <CASE...>

ОБЪЕДИНИТЬ ВСЕ

-- ПрочиеДоходы.Обороты — оставить как сейчас, без изменений
ВЫБРАТЬ П.Подразделение, П.СтатьяДоходов, П.Регистратор, <CASE для Контрагент>, СУММА(П.СуммаПриход)
ИЗ РегистрНакопления.ПрочиеДоходы.Обороты(&НачалоПериода, &КонецПериода, Регистратор, )
...
```

> Конкретные фильтры (`РасчетСебестоимости`, `НалоговоеНазначение`, `ТипЗапасов`, `ХозяйственнаяОперация`) подбираются в Python-тестах (Секция 3) до совпадения суммы с эталоном. Финальный набор фиксируется в плане реализации.

### 2.3. Новый CTE `втЕРП_CoGS_Детали`
Вставляется между `втЕРП_Доходы_Детали` и `втКазна_ПоПодрДДС`:

```sql
ВЫБРАТЬ
    В.Подразделение КАК Подразделение,
    &ДДСCoGS КАК ДДС,
    В.ДокументДвижения КАК Документ,
    <CASE для Контрагент, те же типы что в 2.2> КАК Контрагент,
    СУММА(В.СтоимостьУпрБезНДС) КАК СуммаЕРП
ПОМЕСТИТЬ втЕРП_CoGS_Детали
ИЗ РегистрНакопления.ВыручкаИСебестоимостьПродаж.Обороты(
        &НачалоПериода, &КонецПериода, Регистратор,
        СтоимостьУпрБезНДС <> 0
    ) КАК В
ГДЕ &ДДСCoGS <> ЗНАЧЕНИЕ(Справочник.СтатьиДвиженияДенежныхСредств.ПустаяСсылка)
    И В.ДокументДвижения <> ЗНАЧЕНИЕ(Документ.РеализацияТоваровУслуг.ПустаяСсылка)
СГРУППИРОВАТЬ ПО В.Подразделение, В.ДокументДвижения, <CASE для Контрагент>
```

Если флаг не проставлен в системе (`&ДДСCoGS = ПустаяСсылка`) — WHERE даёт 0 строк, CoGS не появляется в отчёте.

### 2.4. Интеграция CoGS в итоговый поток
В существующем блоке `втЕРП_ПоPL_Расх` (строки ~262–284) объединяется с новым:

```sql
ВЫБРАТЬ <поля> ИЗ втЕРП_Расх_Детали КАК ЕРПР
    ВНУТРЕННЕЕ СОЕДИНЕНИЕ втPL_ДДС КАК PLДДС ПО PLДДС.ДДС = ЕРПР.ДДС

ОБЪЕДИНИТЬ ВСЕ

ВЫБРАТЬ <те же поля> ИЗ втЕРП_CoGS_Детали КАК ЕРПР
    ВНУТРЕННЕЕ СОЕДИНЕНИЕ втPL_ДДС КАК PLДДС ПО PLДДС.ДДС = ЕРПР.ДДС
```

Так CoGS идёт через тот же механизм ДДС→ТЧ Статьи→PL-статья, что и прочие расходы. Никакой специальной логики на уровне СКД не требуется.

### 2.5. Параметры запроса
- `&НачалоПериода`, `&КонецПериода`, `&ВключатьДочерние` — уже есть.
- `&ДДСCoGS` — **новый**, заполняется через `ПолучитьДДСПриёмникCoGS()`.

### 3.2. Протокол разработки
1. Пишется Python-тест → прогон через `mcp__python-runner__run_command`.
2. Подбираются фильтры в запросе до совпадения с эталоном.
3. **Только после** успешного теста финальный запрос переносится в `ObjectModule.bsl`.
4. Запускается `test_otchet_pl_parity.py` на проде — должен подтвердить паритет.

### 3.3. Настройка финансистом после деплоя
1. В 1С открывает нужную ДДС (создаёт новую или берёт существующую), ставит галку `А_ПриёмникСебестоимостиПродажPL`, записывает.
2. В справочнике `А_Статьи_PL` открывает PL-статью (напр. «Строительные материалы»), добавляет эту ДДС в ТЧ `Статьи`, записывает.
3. Формирует А_ОтчетPL за февраль 2026 — CoGS должен появиться на PL «Строительные материалы» для Глобино-2 как 5 215 829,27 ₴.

Если ошибся в выборе ДДС — меняет в справочнике, переформирует отчёт. Код не трогается.

## Out of scope

### Корректировка 1: СтатьяДоходов hardcode
Спека припускала `АналитикаУчетаНоменклатуры.СтатьяДоходов` — це **не працює** (у `Справочник.КлючиАналитикиУчетаНоменклатуры` нема такого поля). Рішення: **hardcode** значення `СтатьяДоходов = "Выручка от продаж"` (UUID `77981290-6ea2-11f0-a2de-bccbaebe2890`) для всіх записів з `ВыручкаИСебестоимостьПродаж`. У `Справочник.А_Статьи_PL` тільки 1 PL-стаття з цією СтатьюДоходов — тому розкладу по статтях не потрібно.

### Корректировка 2: Поля .Обороты з суфіксом «Оборот»
Ресурси на віртуальній таблиці `.Обороты` мають суфікс `Оборот`: `СуммаВыручкиБезНДСОборот`, `СтоимостьУпрБезНДСОборот`.
