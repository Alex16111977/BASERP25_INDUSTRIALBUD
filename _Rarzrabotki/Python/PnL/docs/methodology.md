# Методология сверки PnL: Excel ↔ А_ОтчетPL ↔ АнализДоходовРасходов

**Владелец**: финансовая служба (ЛОВП ФД)
**Версия**: 1.0 от 2026-04-17
**Область применения**: компания ТОВ "ІНДАСТРІАЛБУД", конфигурация BAS ERP 2.5

---

## 1. Три источника истины

```
        Excel PnL                А_ОтчетPL (док)              АДР (1С отчёт)
       (финансист)         ←→     (transit в 1C)        ←→    (источник факта 1С)
            │                         │                            │
            │                     из Excel                     из регистров
            │                         │                            │
       PL статьи    ──соответствие──  А_Статьи_PL  ──ДДС── СтатьиДвиженияДенежныхСредств
       Листы        ──соответствие──  СтруктураПредприятия  (подразделения)
```

Каждый из них имеет свою «правду»:

| Источник | Что правда | Риски |
|---|---|---|
| **Excel PnL** | Оценка финансиста (где деньги должны быть — классификация для PnL) | Ручной ввод: опечатки, забытые суммы |
| **А_ОтчетPL** (Документ) | Транзит Excel в 1С через Python-пайплайн | Маппинг может неверно сопоставить статью |
| **АнализДоходовРасходов** | Факт оборотов по регистрам `ПрочиеРасходы` / `ПрочиеДоходы` | Не видит документы, пишущие только в `Хозрасчетный` |

---

## 2. Схема связей справочников (на уровне метаданных)

```
Catalog.А_Статьи_PL                  ← главный справочник PnL финансиста
   ├─ Реквизит.СтатьяДвиженияДенежныхСредств  ←  Catalog.СтатьиДвиженияДенежныхСредств
   ├─ Реквизит.СтатьяДоходов                  ←  ПВХ.СтатьиДоходов
   ├─ Реквизит.Группа                         ←  Catalog.А_ГруппаСтатей_PL
   ├─ Реквизит.ТипСтатьи                      ←  Enum (Доход/Расход/ОперационныйИтог/Информационный)
   └─ ТЧ.Статьи (дополнительные ДДС)

ПВХ.СтатьиРасходов                   ← платформенный справочник
   └─ Реквизит.А_СтатьяДвиженияДенежныхСредств ← Catalog.СтатьиДвиженияДенежныхСредств

ПВХ.СтатьиДоходов                    ← платформенный справочник
   └─ Реквизит.А_СтатьяДвиженияДенежныхСредств ← Catalog.СтатьиДвиженияДенежныхСредств
```

**Ключевой факт (подтверждён из данных)**: реквизит `А_Статьи_PL.СтатьяДвиженияДенежныхСредств` — **не уникальный ключ**. Одна ДДС может указывать на несколько PL-статей (напр. ДДС «ЗП» → 4 статьи PL: ЗП РМ, ЗП упр, ЗП подсобников, ЗП произв.).

Следовательно — **нельзя построить однозначный автоматический маппинг ПВХ → PL только через ДДС**.

## 3. Архитектурный gap: документ ЗП в `ПрочиеРасходы`, не в `Хозрасчетный`

Документ `ОтражениеЗарплатыВФинансовомУчете` пишет **156 записей в РегистрНакопления.ПрочиеРасходы** и **0 записей** в других регистрах (проверено на № 000Ц-000003, декабрь 2025).

### Последствия

| Отчёт | Видит ЗП? | Почему |
|---|:---:|---|
| АнализДоходовРасходов | ✅ | Читает `ПрочиеРасходы.ОстаткиИОбороты` |
| А_ОтчетPL | ❌ | Читает `ДвиженияНоменклатураДоходыРасходы`, `ДвиженияКонтрагентДоходыРасходы`, `ДвиженияДенежныеСредстваДоходыРасходы` — эти регистры пусты для ЗП-документа |

Данные ЗП в документе `А_ОтчетPL` всё же есть — но **из Excel через ТЧ `ДанныеОтчета`** (ручной импорт финансиста). Расхождение < 1% с АДР (сравнено на Астарте декабрь 2025: АДР 12.8 млн ₴ ↔ PL 12.8 млн ₴, см. `astarta_december.md`).

### Рекомендация (отдельная задача)

Расширить `Reports/А_ОтчетPL/Ext/ObjectModule.bsl` — добавить источник `ПрочиеРасходы` и `ПрочиеДоходы`, как это делает стандартный отчёт АнализДоходовРасходов. После этого запросы будут сверять суммы автоматически.

## 4. Правильный способ чтения регистра ПрочиеРасходы

Регистр **оборотный транзитный** — на каждую статью платформа пишет симметрично Приход + Расход с равными суммами (сальдо всегда = 0).

### ❌ Неправильно (приводит к ошибочным выводам):

```sql
-- НЕ делать: эквивалентно 2× реальной суммы
СУММА(Сумма) ИЗ РегистрНакопления.ПрочиеРасходы
```

### ✅ Правильно:

```sql
-- Для PnL за период — берём СуммаРеглПриход из виртуальной таблицы .Обороты
СУММА(Об.СуммаРеглПриход) AS PnL_Сумма
ИЗ РегистрНакопления.ПрочиеРасходы.Обороты(
    ДАТАВРЕМЯ(2025,12,1), 
    ДАТАВРЕМЯ(2025,12,31,23,59,59), , ) КАК Об
ГДЕ Об.Подразделение.Наименование = &Подр
```

Поля:
- `СуммаПриход` / `СуммаРеглПриход` — расходы признаны за период (это и есть PnL)
- `СуммаРасход` / `СуммаРеглРасход` — те же суммы ушли в распределение (ими пренебрегаем для PnL)
- `Сумма*НачальныйОстаток` / `Сумма*КонечныйОстаток` — остатки не по деньгам, а по распределению

## 5. Чек-лист: диагностика разрыва по подразделению

Когда финансист находит расхождение «Excel показывает X, а АДР показывает Y»:

### Шаг 1 — зафиксировать факт в числах

```sql
-- АДР (правда) за период по подразделению
ВЫБРАТЬ 
    ЕСТЬNULL(Об.СтатьяРасходов.Наименование, "(пусто)") КАК СтатьяРасходов,
    СУММА(Об.СуммаРеглПриход) КАК СуммаРегл
ИЗ РегистрНакопления.ПрочиеРасходы.Обороты(ДАТАВРЕМЯ(ГГГГ,ММ,1), ДАТАВРЕМЯ(ГГГГ,ММ,31,23,59,59), , ) КАК Об
ГДЕ Об.Подразделение.Наименование = "ИмяПодразделения"
СГРУППИРОВАТЬ ПО Об.СтатьяРасходов.Наименование
УПОРЯДОЧИТЬ ПО СуммаРегл УБЫВ
```

### Шаг 2 — получить PnL из документа А_ОтчетPL за тот же период и подразделение

```sql
-- Документ А_ОтчетPL — ДанныеОтчета (что из Excel)
ВЫБРАТЬ 
    ТЧ.Статья.Наименование КАК СтатьяPL,
    ТЧ.Статья.Группа.Наименование КАК ГруппаPL,
    ТЧ.Сумма
ИЗ Документ.А_ОтчетPL КАК Док
ЛЕВОЕ СОЕДИНЕНИЕ Документ.А_ОтчетPL.ДанныеОтчета КАК ТЧ ПО ТЧ.Ссылка = Док.Ссылка
ГДЕ Док.Дата МЕЖДУ ДАТАВРЕМЯ(ГГГГ,ММ,1) И ДАТАВРЕМЯ(ГГГГ,ММ,31,23,59,59)
  И Док.Подразделение.Наименование = "ИмяПодразделения"
  И НЕ Док.ПометкаУдаления
УПОРЯДОЧИТЬ ПО ТЧ.НомерСтроки
```

### Шаг 3 — сравнить статья-в-статью

Построить таблицу:

| Статья АДР | СуммаРегл АДР | Соответствующая PL-статья (по ДДС) | Сумма PL | Δ ₴ | Δ % |

### Шаг 4 — классифицировать разрыв

| Δ % | Классификация | Действие |
|---|---|---|
| < 1 % | Копеечная погрешность | Игнорировать |
| 1-10 % | Разная группировка статей | Финансист решает: объединить/разделить |
| > 10 % | Структурный разрыв | Разбираться: пропущен документ? Не тот маппинг? |
| АДР есть, PL нет | Статья пропущена в Excel | Финансист добавляет в Excel; или создать PL-статью для не-включаемых |
| PL есть, АДР нет | Статья есть только в Excel | Бухгалтерия должна создать документ в 1С |

### Шаг 5 — обратить внимание на ЗП (known gap)

Если расхождение связано со статьями ЗП (Зарплата/Удержание/Начисления) — помнить что **А_ОтчетPL** не может автоматически сверить их с 1С. Факт = АДР, PL = из Excel, если расхождение < 1% — всё в порядке.

## 6. Правила работы с данными 1С (для ИИ)

Эти правила зафиксированы после ошибки интерпретации «упр+регл = 2 записи» (2026-04-17):

1. **Гипотеза ≠ факт**. Перед выводом из данных — явно проверять альтернативные интерпретации запросом (разбивка по другим столбцам, `СГРУППИРОВАТЬ ПО ВидДвижения` и т. п.).
2. **Виртуальные таблицы .Обороты / .Остатки** — приоритетно для PnL-значений. Платформа сама корректно свернёт Приход/Расход.
3. **NotebookLM** как источник архитектурных знаний о конкретной конфигурации. Для стандартных объектов 1С — NotebookLM может молчать; тогда помечаю вывод как «из фактов данных».
4. **Различать факт и интерпретацию** в выводах. Если пишу «это значит X» — за этим должна стоять явная логика, а не догадка по симптому.

## 7. Чек-лист перед добавлением нового листа Excel

Когда финансист хочет добавить новый PnL-лист (напр. новый проект):

- [ ] Подразделение в 1С (`СтруктураПредприятия`) существует? Если нет — создать через ERP-интерфейс.
- [ ] UUID подразделения добавить в `07_mapping_sheet_to_struct.json` либо через автоматический matching (имя листа = имя подразделения с fuzzy ≥ 85 %), либо через ручной override в `config.py → MANUAL_SHEET_TO_STRUCT_OVERRIDES`.
- [ ] Статьи Excel — есть в `А_Статьи_PL`? Если нет — создать в 1С.
- [ ] `СтатьяДвиженияДенежныхСредств` в новой PL-статье — заполнена и уникальна? Проверить что нет другой PL-статьи с такой же ДДС (иначе автоматический матч будет неоднозначным).
- [ ] Запустить пайплайн `01 → 02 → 03 → 04 → 04b → 05 → 06 → 07 → 08 → 12`.
- [ ] Проверить верификационные скрипты: `_verify_excel_vs_pl.py` и `_verify_pl_vs_adr.py`.
