## 1. Архитектурный gap (1.1 + 1.2)

### Документ ЗП 000Ц-000003 (`ОтражениеЗарплатыВФинансовомУчете`) от 31.12.2025

UUID `c2dff300-35f9-11f1-a2e8-ae822d4b0de9`, проведён.

Распределение записей по регистрам:

| Регистр | Записей | Сумма использования |
|---|---:|---|
| **РегистрНакопления.ПрочиеРасходы** | **156** | ← видит АДР ✅ |
| РегистрНакопления.ДвиженияНоменклатураДоходыРасходы | 0 | читает А_ОтчетPL — пусто |
| РегистрНакопления.ДвиженияКонтрагентДоходыРасходы | 0 | читает А_ОтчетPL — пусто |
| РегистрНакопления.ДвиженияДенежныеСредстваДоходыРасходы | 0 | читает А_ОтчетPL — пусто |
| РегистрНакопления.ПрочиеДоходы | 0 | не применимо |
| РегистрБухгалтерии.Хозрасчетный | **0** | бух проводок **нет** |

**Вывод**: документ ЗП пишет **только в `ПрочиеРасходы`**. Этот регистр **не входит в источники отчёта А_ОтчетPL** — поэтому через запросный уровень отчёт "не видит" зарплату.

Тем не менее, данные ЗП всё равно попадают в документ А_ОтчетPL — **из Excel** через ТЧ `ДанныеОтчета` (финансист сам вносит). Суммы сходятся с АДР (см. `astarta_december.md`, расхождение < 1 %). Проблема не в цифрах, а в **отсутствии автоматической сверки**.

### Природа регистра ПрочиеРасходы (подтверждено виртуальной таблицей .Обороты)

- Оборотный транзитный регистр
- На каждую статью: `СуммаПриход = СуммаРасход` (приходит в портфель расходов и сразу распределяется дальше)
- Сальдо = 0
- **Для PnL берём `СуммаРеглПриход`** (или `СуммаПриход` для управленческого учёта)

## 2. Карта соответствия трёх справочников (1.3)

Файл: `_Rarzrabotki/Python/PnL/data/json/mapping_master.csv` (68 строк ПВХ).

### Ключевая архитектурная проблема

Реквизит `А_Статьи_PL.СтатьяДвиженияДенежныхСредств` — **классификатор, НЕ уникальный ключ**. Одна ДДС указывает на несколько PL-статей:

| ДДС | Сколько PL-статей ссылается | PL-статьи |
|---|---:|---|
| «ЗП» | **4** | ЗП РМ, ЗП упр, ЗП подсобников, ЗП производственного |
| «Персонал» | **7** | Затраты на командировки, Премии (упр+произв), Транспортные затраты (упр+произв), Удержание с зп упр, Командировочные произв. |
| «Прочие услуги банка» | **2** | Услуги, Услуги банков |
| «Начисления на зарплату PM» | **2** | Начисления на зарплату PM, Начисления на управленч. зарплату |

Следовательно **нельзя построить однозначный автоматический маппинг ПВХ→PL только через ДДС**.

### Типы проблем (все 68 строк в CSV)

| Тип | Кол-во | Пример |
|---|---:|---|
| ✅ Связь работает (ДДС однозначна) | 27 | Будівельні матеріали → Строительные материалы |
| ⚠️ Нет_связи (ДДС заполнена в ПВХ, но нет соответствующей PL или PL указывает на другую ДДС) | 28 | Зарплата управленческого персонала (ПВХ) ↔ ЗП управленческого (PL с ДДС='ЗП') |

| 🔴 ДДС_МНОЖЕСТВ (одна ДДС → 2 PL) | 2 | «Прочие услуги банка» |
| ⚠️ СтатьяДоходов отсутствует в ПВХ (для доходных) | 3 | Прочие доходы Фин деятельности |

## 3. Рекомендации по фиксу маппинга

### Что надо сделать в А_Статьи_PL

1. **Переустановить ДДС в 4 ЗП-статьях** на детальные (вместо "ЗП"):
   - ЗП производственного персонала → ДДС "Зарплата производственного персонала"
   - ЗП ИТР → уже правильно "Зарплата ИТР"
   - ЗП РМ → ДДС "Зарплата PM"
   - ЗП упр → ДДС "Зарплата управленческого персонала"
   - ЗП подсобников → ДДС "Зарплата подсобников"

2. **Переустановить ДДС в Персонал-статьях** (7 шт) на детальные ДДС (Суточные, Удержания и т.д.).

3. **Исправить неверные ДДС**:
   - PL «ИТ расходы» → ДДС вместо "Транспортные расходы" = "Обслуживание офисной техники"
   - PL «Реклама» → проверить, точно ли ДДС = «Реклама» (сейчас ПВХ с «Реклама» кидает в неё всё подряд)

4. **Заполнить ДДС у 5 PL-статей** (сейчас пусто):
   - Телекомуникационные услуги → ДДС «Интернет»
   - Юридические услуги → ДДС «Прочие юр услуги»
   - Логистические затраты → ДДС «Транспортные расходы»
   - Финансовые расходы → ДДС «Расходы по кредитам» или создать новую
   - Расход от ивест. Деятельности (ОС) → ДДС (отдельная)

5. **Создать новые PL-статьи** (под что-то, чего нет):
   - Зарплата механизаторов + Удержание + Начисления (3 шт)
   - Зарплата кладовщика
   - Амортизация (крупные суммы без PL)

6. **Разрешить дубли "ЗП РМ" vs "ЗП управленческого"** — объединить в одну, или распределить по типам.

### Что надо сделать в Python-маппинге

После правки А_Статьи_PL:
- Перезапустить `04_match_articles.py` — fuzzy по именам даст корректные результаты
- Обновить `05_mapping_pl_to_dds.json` на реальных ДДС из АДР
- Расширить `10_mapping_statya_dohodov.json` на все доходные статьи

## 4. Что делать в рамках текущей итерации (скорректированный план)

Оригинальный план плана предполагал **полную автоматизацию маппинга**. Теперь ясно, что это невозможно без ручных правок в А_Статьи_PL — и это ответственность финансиста (который решает, как классифицировать «Зарплата механизаторов»: отдельная статья или вливается в «ЗП производственного»).

Что остаётся в программном скоупе этой итерации:

1. **Создать `mapping_master.csv`** (✅ готово) — финансист видит все разрывы и может решить.
2. **Фикс 07_mapping_sheet_to_struct.json**: Техника → Логистика, ПРОООН → МД ПРООН.
3. **Расширить 10_mapping_statya_dohodov.json**: добавить все доходы.
4. **Обновить methodology.md**: описать архитектуру, правильный путь сверки, известные gap-ы.
5. **Создать скрипт верификации** А_ОтчетPL vs АДР (учесть проблему дублирующихся ДДС — в верификации пропускать такие статьи с меткой «требует ручной проверки»).

**НЕ делаем автоматически** (требует решения финансиста):
- Правки А_Статьи_PL (перезалив реквизитов ДДС)
- Создание новых PL-статей (Зарплата механизаторов, Амортизация и т.д.)
- Объединение дублирующихся PL-статей

Эти правки — отдельная задача после проверки пользователем `mapping_master.csv`.
