# MASTER-ПРОМТ
## «Изучи типовую конфигурацию BAS ERP 2.5 и создай набор скилов по созданию объектов в типовом стиле»

> Как пользоваться: открой **новую** сессию ИИ в каталоге `C:\Configuration_downloads\BASERP25` и вставь весь текст ниже (от разделителя до конца) как одно задание.

---

Ты — senior‑разработчик 1С (BSL, платформа 8.3) и автор Agent Skills. Рабочий каталог — `C:\Configuration_downloads\BASERP25` (конфигурация **BAS ERP 2.5, ТОВ ІНДАСТРІАЛБУД**).

## ЦЕЛЬ

Изучить **типовые** (без префикса `А_`) объекты конфигурации, извлечь их конвенции и создать в `.claude/skills/` **набор скилов**, по которым любой будущий ИИ сможет создавать новые объекты (документы, справочники, регистры), отвечающие требованиям конфигурации — **«как другие, типовые объекты»**: тот же стиль формы (окна), те же общие процедуры, те же паттерны движений и проведения.

Результат — не пересказ одного объекта, а **переиспользуемые правила**, выжатые из нескольких типовых эталонов.

## ЖЁСТКИЕ ПРАВИЛА (соблюдай на всех фазах)

1. **Rule #‑1 (критично):** прежде чем поместить ЛЮБОЙ запрос 1С в код скила/reference — сначала проверь его через Python COM (`V83.COMConnector`, база `BaseERP`). Нет Python‑теста = нет запроса в скиле.
2. **Изучай ТОЛЬКО типовое.** Объекты с префиксом `А_` — это кастомные доработки/артефакты обмена, **они НЕ эталон стиля**. Не копируй их структуру и не ссылайся на них как на образец.
3. **Не выдумывай** имена полей, реквизитов, регистров. Бери их из реальной структуры: MCP `get_metadata_structure` / `list_metadata_objects`, выгрузка XML, `execute_query`.
4. **Копируй конвенции, не изобретай.** Если у всех типовых документов форма построена по одному шаблону — повтори этот шаблон, а не «как принято вообще в 1С».
5. **Не строй с нуля то, что уже есть.** Используй готовые кирпичи‑скилы из `.claude/skills/` (`meta-compile`, `meta-edit`, `meta-info`, `meta-validate`, `form-compile`, `form-edit`, `form-patterns`, `form-validate`, `1c-bsl-standards`, `1c-bsl-review`). Твои скилы — **тонкие оркестраторы поверх них + знание стиля**, а не дубликаты.

## ФАЗА 0 — ИЗУЧЕНИЕ (обязательна ДО любой генерации)

Изучи эталоны (только типовые):

| Тип | Эталоны |
|-----|---------|
| Документы | `ПриобретениеТоваровУслуг`, `РеализацияТоваровУслуг`, `ПоступлениеТоваровУслуг`, `ПеремещениеТоваров` |
| Справочники | `Номенклатура`, `Контрагенты`, `ДоговорыКонтрагентов`, `Склады` |
| Регистры | `ТоварыНаСкладах` (накопления), `ЦеныНоменклатуры` (сведений) + регистры, по которым двигаются изучаемые документы |

Для **каждого документа** разбери и выпиши:
- состав реквизитов шапки и **стандартные реквизиты** (Номер, Дата, Организация, Ответственный, Комментарий, Проведён…);
- табличные части и их реквизиты;
- **управляемые формы**: какие есть (ФормаДокумента, ФормаСписка…), состав и **именование групп** (`ГруппаШапка`, `ГруппаШапкаЛевая`, `ГруппаПодвал`…), командная панель, типовые команды, обработчики событий;
- **модуль объекта**: структура `ОбработкаПроведения`, работа с движениями, блокировки, отложенное отражение;
- **модуль менеджера**: какие процедуры/функции типовые;
- **движения по регистрам**: какие регистры, измерения/ресурсы, как формируются;
- какие **общие модули** вызываются (БСП и прикладные) и зачем.

Для **справочников** и **регистров** — аналогично (реквизиты/измерения/ресурсы, формы, владельцы, иерархия, периодичность, типы).

Как изучать (порядок):
1. `list_metadata_objects` → найди объект;
2. `get_metadata_structure` / скил `meta-info` → точная структура;
3. при необходимости — читай XML‑выгрузку объекта в каталоге конфигурации;
4. факты о данных проверяй `execute_query` (после Python COM по Rule #‑1).

Дополнительные источники:
- база знаний проекта: `_Rarzrabotki/notebook/knowledge/` (особенно `document_posting_chain.md`, `settlements_architecture.md`, `document_hidden_fields.md`, `register_report_map.md`);
- правила проекта: `CLAUDE.md` (включая Rule #‑1 и правило префикса `А_`) и `…/memory/MEMORY.md`.

**Главная задача фазы:** выдели, что присутствует во ВСЕХ типовых эталонах (→ обязательная конвенция), а что варьируется (→ параметр выбора). Фиксируй именно повторяющееся.

## ФАЗА 1 — ЗАФИКСИРУЙ КОНВЕНЦИИ

Сложи извлечённое в reference‑чек‑листы (это станет содержимым скила `bas-house-style` и его `reference/`):
- **Именование** объектов, реквизитов, форм, групп, обработчиков; правило **синонима**.
- **Стандартные реквизиты** документа/справочника и когда они нужны.
- **Состав и компоновка управляемой формы** «как у типовых» (порядок групп, расположение ТЧ, командная панель).
- **Общие модули**, которые типовой объект обязан/может вызывать.
- **Движения и проведение**: шаблон `ОбработкаПроведения`, наборы движений, блокировки, отложенное отражение в учёте.
- **Программное заполнение**: обязательные поля типовых документов, чтобы запись/проведение прошли корректно (например для расчётных документов — `Курс=1`, `Кратность=1`, суммы взаиморасчётов; см. `settlements_architecture.md`).

## ФАЗА 2 — СГЕНЕРИРУЙ СКИЛЫ

Создай в `.claude/skills/` (каждый — своя папка с `SKILL.md`):

| Скил | Что внутри |
|------|-----------|
| `bas-house-style` | reference‑«конституция» стиля типовых объектов (итоги Фазы 1). На него ссылаются остальные скилы |
| `bas-doc-new` | пошагово: новый Документ в типовом стиле — метаданные (`meta-compile`) + ТЧ + форма (`form-compile`/`form-patterns`) + модули; ссылается на `bas-house-style` |
| `bas-catalog-new` | новый Справочник в типовом стиле |
| `bas-register-new` | новый регистр (накопления/сведений) + привязка движений документа |
| `bas-doc-fill` | программное создание записей типовых документов (обязательные поля, `Курс/Кратность`, взаиморасчёты, корректное проведение) |
| `bas-verify` | гейт проверки результата (Python COM по Rule #‑1 + `meta-validate`/`form-validate` + `1c-bsl-review`) |

> Если по итогам изучения логичнее объединить/разделить скилы — можно, но обоснуй и не теряй покрытие (новый объект → форма → проведение → программное заполнение → проверка).

## КОНТРАКТ ФОРМАТА СКИЛОВ (соблюдай строго)

- `SKILL.md` начинается с YAML‑frontmatter: **`name`** (kebab‑case, латиница/цифры/дефис, ≤64) и **`description`**.
- **`description`** — самое важное поле (по нему скил находят):
  - третье лицо, начинай с **«Используй когда…»**;
  - перечисли **конкретные триггеры/симптомы** (например: «нужно создать новый документ», «добавить проведение», «движения по регистру»);
  - **НЕ пересказывай workflow** скила в описании (иначе ИИ выполнит описание вместо чтения тела);
  - сделай описание достаточно «настойчивым», чтобы скил срабатывал, даже если пользователь не назвал его явно.
- Тело `SKILL.md` — **< 500 строк**, сканируемое (заголовки, таблицы, короткие списки).
- **Progressive disclosure:** тяжёлые детали выноси в `reference/*.md` (ссылки из `SKILL.md`, **только один уровень** вложенности); детерминированную механику — в `scripts/`.
- **Один отличный пример** лучше пяти посредственных; пример — из реального типового объекта, с указанием пути.
- **Язык — русский** (как у существующих кастомных скилов проекта).
- Каждое правило **привязывай к реальному эталону** (имя объекта/путь), а не к абстрактному «в 1С принято».

## ФАЗА 3 — ВЕРИФИКАЦИЯ (обязательна)

1. **Rule #‑1:** все запросы из скилов прогони через Python COM — должны выполняться без ошибок.
2. **Структурная проверка:** `meta-validate` / `form-validate` на сгенерированных примерах.
3. **BSL‑ревью:** `1c-bsl-review` на любом BSL внутри скилов.
4. **Тест свежим агентом (главный критерий):** дай отдельному агенту без контекста только что созданный `bas-doc-new` и задачу «создай новый документ <X> в типовом стиле». Если он справляется без дополнительных подсказок — скил готов. Если буксует — зафиксируй, чего не хватило, дополни скил, повтори.
5. Итерируй, пока тест свежим агентом не проходит.

## ANTI‑PATTERNS / RED FLAGS (стоп и переделай)

- Берёшь `А_*` объект как образец стиля. (Изучай только типовое.)
- Выдумал имя поля/реквизита/регистра без `get_metadata_structure`.
- Запрос попал в скил без Python COM теста.
- `description` пересказывает процесс вместо триггеров → скил «срабатывает мимо».
- `SKILL.md` распух >500 строк → выноси в `reference/`.
- Скил дублирует то, что уже умеет `meta-compile`/`form-compile`.
- При программном заполнении забыл обязательные поля (`Курс/Кратность`, суммы взаиморасчётов) → суммы/движения = 0.
- Правила записаны как «история одного случая», а не как переиспользуемый паттерн.
