# 04. Документ.ПринятиеКУчетуОС

## Метаданные

- **Имя:** `Документ.ПринятиеКУчетуОС`
- **Версия:** 2.1 (в Designer «Принятие к учёту ОС (2.1)»)
- **XML:** `Documents/ПринятиеКУчетуОС.xml`
- **ObjectModule:** `Documents/ПринятиеКУчетуОС/Ext/ObjectModule.bsl`
- **Версия 2.4:** есть `Документ.ПринятиеКУчетуОС2_4` (не покрывается этим файлом)

## Назначение

Регистрирует приём объекта основных средств в эксплуатацию: переводит накопленные капитальные вложения (РН.ВложенияВНеоборотныеАктивы) в стоимость ОС (РН.СтоимостьОС). С этого момента по объекту начинается начисление амортизации.

## ★ Ключевое отличие от АмортизацияОС

**`Документ.ПринятиеКУчетуОС.ObjectModule.bsl` НЕ упоминает `ПрочиеАктивыПассивы`** (grep подтвердил).

То есть документ **сам в РН.ПрочиеАктивыПассывы НЕ пишет**. Это значит:
- Сразу при проведении баланс не меняется на уровне ПАП
- Перенос движений ПрочиеАктивыПассивы делает **штатная Обработка.ДвиженияАктивовПассивов** при закрытии месяца
- Обе стороны (Дт «Основные средства» и Кт «Вложения в необоротные активы») создаются ОДНОВРЕМЕННО штатной обработкой → симметрично, расхождений быть не должно

## Подтверждение симметрии (Март 2026)

`Python/test/03_scan_march2026.py` показал:

```
=== ПринятиеКУчетуОС ===
  Всего документов: 8, асимметричных: 0, Σ|Δ|: 0,00
  Σ ΣДт = 0,00, Σ ΣКт = 0,00, нетто Δ = 0,00
```

**Σ ΣДт = 0 и Σ ΣКт = 0** означает что **ни один из 8 документов** ПринятиеКУчетуОС за Март 2026 **не имеет** прямых движений в РН.ПрочиеАктивыПассивы по регистратору-документу.

Все движения в ПАП по этим объектам ОС появляются с регистратором **А_ФинРез_Баланс** при свертке штатной Обработкой.ДвиженияАктивовПассивов, и они симметричны по построению.

## Какие регистры документ двигает на самом деле

(Подтвердить через `get_metadata_structure` или `list_all_movements`:)

| Регистр | Что записывает |
|---|---|
| РН.ВложенияВНеоборотныеАктивы | Расход: уменьшает накопленные кап.вложения по объекту |
| РН.СтоимостьОС | Приход: увеличивает первоначальную стоимость ОС |
| РН.ПервоначальныеСведенияОСМеждународныйУчет | (если включён международный учёт) |
| РН.ПервоначальныеСведенияНалогОС / БухгалтерскийУчет | Первоначальные сведения для расчёта налоговой амортизации |
| РБ.Хозрасчетный | Бухгалтерская проводка Дт 10 Кт 15 |

## Когда искать здесь причину Δ в Контроле баланса

- **Никогда** для штатной механики приёма ОС в учёт (если 03_scan_march показал Σ|Δ| = 0)
- **Только** если кто-то добавит кастомный код в ObjectModule вроде А_СформироватьДвиженияАктивовПассивов (по аналогии с АмортизацияОС) — тогда возможна та же асимметрия

## Метод проверки

```python
# Адаптация 02_compare_prochie_rashody_vs_pap.py для этого документа
DOC_UUID = "<uuid конкретного ПринятиеКУчетуОС>"
# Меняем erp.Документы.АмортизацияОС → erp.Документы.ПринятиеКУчетуОС
```

Если результат симметричный (Δ=0 по подразделению) — баг отсутствует. Если асимметричный — искать кастомный код в ObjectModule.

## ✅ 2026-05-25 — правка формы (разрешён метод 100% для счетов 10 класса)

**Коммит:** `cd059c503`
**Файл:** `Documents/ПринятиеКУчетуОС/Forms/ФормаДокумента/Ext/Form/Module.bsl`

### Что было

В функциях `ПолучитьСписокСпособовАмортизацииБУ()` и `ПолучитьСписокСпособовАмортизацииНУ()` метод `_100` (100%) добавлялся в выпадающий список **только** для счетов МНМА/БиблФонды (счета 11X). Для счетов 10X (ОС, в т.ч. 103, 104, 105, 106) были доступны: Линейный, Уменьш.остатка, Ускор.уменьш., Кумулятивный.

### Что стало (правка +4 строки)

В обеих функциях в ветке «Иначе» (для счетов 10X) добавлено:
```bsl
// {А_Доработка 2026-05-25} Разрешить метод 100% для счетов класса 10 (ОС)
СписокПеречисления.Добавить(Перечисления.СпособыНачисленияАмортизацииОС._100);
```

### Почему это безопасно

- Типовая логика амортизации (`УчетОСВызовСервера.bsl:6445-6507`) поддерживает метод `_100` **универсально** для любого счёта
- Дополнительных проверок «счёт vs метод» в типовом коде нет
- Метод `_100` для счёта 10X означает начисление амортизации в **месяце принятия к учёту** (вместо следующего месяца как для Линейного)

### Эффект на бух/нал учёт

🚨 **Внимание:** метод 100% для счетов 10 класса — это **нестандартное** применение по украинскому ПСБО 7. Стандарт предполагает 100% только для МНМА (счета 11X). Если применить 100% для обычного ОС:
- Бух.отчётность отразит ускоренное списание стоимости
- Налоговая декларация по налогу на прибыль может потребовать обоснования
- Это **сознательное решение пользователя** (по учётной политике организации)
