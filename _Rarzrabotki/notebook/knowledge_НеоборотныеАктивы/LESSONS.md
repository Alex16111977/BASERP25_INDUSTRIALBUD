## L1. Контроль баланса показывает «Δ по документу» — НЕ значит баг Свода

Контроль баланса (`Отчёт.УправленческийБалансКонтроль`) проверяет **Σ Дт ≡ Σ Кт** по регистратору в РН.А_ОтчетБаланс_Свод. Эта проверка ловит **3 разных типа ошибок:**

1. **Баг Свода** — функция `Свод_*` некорректно сопоставила источники → нужно править функцию в `Документ.А_ФинРез_Баланс.ObjectModule.bsl` (так было для денег: [[knowledge_Balanse_money]])
2. **Баг исходного документа** — документ записал асимметричные данные в РН.ПрочиеАктивыПассивы → нужно править документ (наш случай для АмортизацияОС)
3. **Задвоение от параллельных учётов** — типовая логика разделяет одно событие на 2 строки разных учётов, штатная обработка суммирует → дублирование

Алгоритм отличия: запустить `02_compare_*` для конкретного документа — если ΣДт ≠ ΣКт в самом РН.ПАП, баг (2) или (3). Если в ПАП всё симметрично, но плуг в Своде, — баг (1).

## L2. ★ Антипаттерн: «БОБА + УПР» строки в РН.ПрочиеРасходы

**Симптом:** для одного ОС в РН.ПрочиеРасходы создаются 2 строки Приход амортизация в одном периоде:
- **БОБА** строка: Сумма = СуммаУпр = СуммаРегл (одинаковые) — это бух/нал учёт
- **УПР** строка: Сумма > 0, СуммаУпр > 0, **СуммаРегл = 0** — это управ учёт

**Происхождение (для редакции 2.1 BAS ERP с украинской локализацией):**
- БОБА: типовая логика типа `УчетОСВызовСервера.НачисленнаяАмортизация`, пишет сумму **без НДС**
- УПР: локализационная логика добавляет НДС (стоимость × 1,20) для управ.учёта

**Симптом в РН.ПАП:**
- Штатная Обработка.ДвиженияАктивовПассивов берёт Σ Сумма обеих строк → Дт «Расходы текущего периода» = БОБА + УПР (задвоение)
- Кастомная А_-процедура берёт Σ СуммаРегл → Кт «Основные средства» = только БОБА (асимметрия)

**Диагностика:** `Python/test/04_drill_prochie_rashody_2_rows.py`.

**Маркер УПР строки:** `СуммаРегл = 0 И СуммаУпр > 0`.

**Решение:** заменить логику в РН.ПАП так, чтобы для управ.баланса бралась **только УПР строка** (с НДС). См. [[FINDINGS]] §6 вариант B.

## L3. РН.ПрочиеРасходы имеет 3 разные суммы — критически важно знать какую брать

```
РН.ПрочиеРасходы:
  Сумма       — основная (часто = СуммаУпр = бух с НДС)
  СуммаУпр    — управленческий учёт (для управ.баланса)
  СуммаРегл   — регламентированный учёт (для бух/нал)
  СуммаБезНДС / СуммаУпрБезНДС / СуммаРеглБезНДС — без НДС
  НДСРегл     — отдельно сумма НДС
```

**Для управ.баланса должна использоваться `СуммаУпр` ТОЛЬКО из УПР строк** (где СуммаРегл = 0). Не суммировать все строки!

## L6. Проблема НДС в управ.учёте — две стороны

В управ.учёте НДС обычно **невозмещаем** — стоимость ОС учитывается с НДС. В бух/нал.учёте — обычно возмещаем (отдельной строкой Дт НДС).

**Принцип отражения** (из запроса пользователя): «для управ.баланса сумма берётся **С НДС**».

### Сторона A — видимая (Контроль баланса)

Типовой механизм 2.1 для **некоторых** ОС создаёт «УПР строку» в РН.ПрочиеРасходы (Сумма_с_НДС, СуммаРегл=0). Штатная Обработка.ДвиженияАктивовПассывы суммирует БОБА (бух) + УПР (управ) → задвоение Дт.

**Для каких ОС создаётся УПР строка** — определяется типовой логикой (вероятно, по НалоговомуНазначению карточки ОС). В нашем случае 4 ОС из 12 имеют УПР строку, 8 не имеют.

### Сторона B — невидимая (скрытый остаток в управ.балансе)

Для **ВСЕХ** ОС, оприходованных С НДС в РН.ПАП:
- Поступление = X (с НДС)
- Амортизация Кт = X / 1.20 (без НДС, по бух)
- Остаток после полной амортизации = X − X/1.20 = X × (НДС/100) = 20% от Кт

Этот остаток **висит на балансе вечно**, потому что амортизация никогда не списывает НДС-часть.

В нашем случае Σ скрытый остаток = 27 865,47 по 12 ОС в одном месяце. С каждым новым ОС остаток растёт.

### Правильное решение

Брать **сумму из остатка в РН.ПАП на начало месяца** (а не из РН.ПрочиеРасходы, где БОБА/УПР с разной семантикой). Делить на СПИ_оставшийся → симметричная пара Дт «Расходы» / Кт «ОС» = эта сумма.

Источник истины: **РН.ПрочиеАктивыПассывы.Остатки(НачалоМесяца, Статья=ОсновныеСредства, Аналитика=ОС, Источник=ПустаяСсылка)** — там уже сидит стоимость с НДС.

## L7. Кастомные процедуры `А_*` в типовых документах — высокий риск асимметрии

Когда в `ObjectModule.bsl` типового документа добавляют свою процедуру, которая пишет в один из «двухсторонних» регистров (РН.ПрочиеАктивыПассывы, РН.ВложенияВНеоборотныеАктивы) ТОЛЬКО одну сторону проводки — это **архитектурный риск**.

**Симптом:**
- Документ при проведении пишет половину проводки
- Вторую половину создаёт штатная Обработка.ДвиженияАктивовПассывы при закрытии месяца
- Если штатная и кастомная процедуры берут **разную базу суммы** (Сумма / СуммаУпр / СуммаРегл / Сумма с НДС / Сумма без НДС) — асимметрия гарантирована

**Митигация:**
- Перед написанием А_-процедуры, читающей суммы — посмотреть **что использует штатная** (`Обработка.ДвиженияАктивовПассивов`, ObjectModule её же)
- Использовать тот же `Сумма`/`СуммаУпр`/`СуммаРегл`, что и штатная
- Прогнать smoke-тест: после правки 1 документа сразу `02_compare_*` — Σ Дт должна совпасть с Σ Кт по регистратору

## L8. Подразделения с Δ=0 — критически важная диагностическая инфо

Когда Контроль баланса показывает Δ, **сначала разрезать по подразделениям**: если Δ ≠ 0 локализована в 1-2 подразделениях, а в остальных = 0 — это **сильная улика** что проблема связана с **спецификой ОС в этих подразделениях**.

В нашем случае:
- Глобино-2 (Δ 76 367,55), ЦО (Δ 25 693,00) — асимметричны (Гайковерт, Вышки, Фильтр — закуплены с НДС)
- АВРОРА, МХП, Чорноморськ — симметричны (ОС закуплены без НДС или НДС не отделён)

→ Проблема НЕ в подразделении и НЕ в документе — она в **карточке конкретного ОС** (был ли при приёмке НДС).

## L9. Закрытие месяца ≠ диагностика — порядок имеет значение

Если месяц **не закрыт** (А_ФинРез_Баланс за этот месяц не проведён), то РН.А_ОтчетБаланс_Свод не содержит данных за этот период → Контроль баланса покажет 0 (по технической причине, а не потому что баланс сошёлся).

**Правило:** при диагностике сначала убедиться, что:
1. А_ФинРез_Баланс за исследуемый месяц проведён
2. Штатная Обработка.ДвиженияАктивовПассивов запущена (через закрытие месяца)
3. Только потом запускать Контроль баланса

## L13. ★ Граница: «управ.учёт vs бух/нал» — можно править колонки/регистры по-разному

При работе с расхождениями управ.баланса есть строгая граница **на уровне колонок** (а не только регистров):

### Регистры

| Регистр | Учёт | Можно править в А_-доработках? |
|---|---|:-:|
| **РН.ПрочиеАктивыПассывы** | Управленческий баланс | **ДА** (целиком — Очистить+перезапись) |
| **РН.А_ОтчетБаланс_Свод** | Сводный (производный) | ДА (но через свой документ А_ФинРез_Баланс) |
| **РН.ПрочиеРасходы** | Первичный (источник для бух+нал+упр+PnL) | **ЧАСТИЧНО** — см. ниже про колонки |
| РБ.Хозрасчетный | Бухгалтерский | **НЕТ** (типовая отчётность, налоги) |
| РС.ПараметрыАмортизацииОСБУ | Бух/нал параметры | **НЕТ** (читать можно) |
| РС.ПервоначальныеСведенияОС | Бух/нал параметры | **НЕТ** |
| РН.СтоимостьОС / РН.АмортизацияОС | Универсальный (2_4) | НЕТ (но в этой базе они пусты) |

### Колонки РН.ПрочиеРасходы

В РН.ПрочиеРасходы можно править **только управ-колонки**, не трогая регл/нал:

| Колонка | Учёт | Кто читает | Можно править? |
|---|---|---|:-:|
| **Сумма** | Управ (= бух обычно) | А_ФинРез_PL, штатная Обработка.ДвиженияАктивовПассывы (→ Дт РН.ПАП) | **ДА** |
| **СуммаУпр** | Управ | OLAP, А_ОтчетPL | **ДА** |
| **СуммаУпрБезНДС** | Управ без НДС | (производное) | ДА |
| СуммаРегл | Регл/нал | Налоговые отчёты, декларация по налогу на прибыль | **НЕТ** |
| СуммаРеглБезНДС | Регл без НДС | Налоговые отчёты | **НЕТ** |
| НДСРегл | НДС регл | Декларация по НДС | **НЕТ** |
| СуммаБезНДС | Бух без НДС | (производное) | **НЕТ** |

**Правило:** при правке управ.амортизации меняем **только Сумма / СуммаУпр / СуммаУпрБезНДС**. Колонки **СуммаРегл, СуммаРеглБезНДС, НДСРегл** остаются как штатно посчитала типовая обработка → бух/нал.учёт сохраняется, налоговая декларация по налогу на прибыль не меняется.

**Применимо для Варианта B v2:**
- РН.ПрочиеАктивыПассывы — Очистить()+полная перезапись (только управ.регистр)
- РН.ПрочиеРасходы — точечная правка через `НаборЗаписей.Прочитать()→изменить колонки→Записать()`, **только Сумма и СуммаУпр в БОБА строках**
- РБ.Хозрасчетный — не трогаем (формируется штатно ДО наших А_-доработок через `РеглУчетПроведениеСервер.ОтразитьДокумент(...)`)

## L12. Метаданные регистров — обязательно через get_metadata_structure

Поля типа «МетодНачисленияАмортизации» в РС.ПараметрыАмортизацииОСБУ можно угадать неверно — там этого поля нет (только в УУ). Правило: перед запросом к незнакомому регистру → `get_metadata_structure` или `list_metadata_objects`.

## L14. ★ Опыт применения Варианта B v2 (2026-05-25)

### Что сработало хорошо

1. **3 отдельных процедуры** (расчёт / правка ПрочиеРасходы / Очистить+перезапись ПАП) — чистая декомпозиция, легко отлаживать поэтапно.
2. **Передача `КартаУправАморт` через параметр** между процедурами — Соответствие[ОС → Структура] позволяет посчитать ОДИН раз и переиспользовать без перерасчёта.
3. **«Доступная стоимость» = Σ Приход до КонМес − Σ Расход до НачМес (исключая свой регистратор)** — универсально работает для:
   - ОС оприходованных в прошлом месяце (Гайковерт через ПринятиеКУчетуОС 07.02.2026 → остаток на 01.03 = 27 367,55)
   - ОС оприходованных в текущем месяце (Платформа через СписаниеТоваров 12.03.2026 → Σ Приход за месяц = 5 458,00)
4. **Исключение `Регистратор <> &Р`** в запросе → можно перепроводить документ повторно без петли (старые движения этого регистратора не учитываются, ведь они сейчас перезаписываются).
5. **Старая `А_СформироватьДвиженияАктивовПассывов` оставлена в коде** для отката — занимает место, но даёт safety net.
6. **Snapshot AFTER_FIX_2026_05_25/** сразу после успешного фикса → база для будущих регрессий через `diff`.
