# А_ОтчетPL ↔ АнализДоходовРасходов — 100% паритет и целостность справочника А_Статьи_PL

Дата генерации: 2026-04-17
Тип: ЗМІННИЙ (обновлять при изменении Reports/А_ОтчетPL/Ext/ObjectModule.bsl или Catalogs/А_Статьи_PL/Ext/ObjectModule.bsl)
Источник: сеанс разработки 2026-04-17 (итерация 2)

## Краткое содержание

Кастомный отчёт `Отчет.А_ОтчетPL` был переписан для достижения 100% паритета «План (Excel) vs Факт (АДР, 1С-регистры)» по каждому подразделению × каждой статье. В справочник `Справочник.А_Статьи_PL` добавлены контроли целостности (модуль объекта `ПередЗаписью`) + реквизит-маркер `А_СозданоАвтоматически` для статей, которые созданы скриптом (без Excel-исходника). Написан автотест паритета `_verify_pl_parity_adr.py`, который классифицирует расхождения на OK / DATA_GAP (ошибка Excel) / MAPPING_BUG (непривязанная ДДС, ЦЕЛЬ: 0). Файл отвечает на вопросы: откуда брать ЕРП-сумму для PnL, какие архитектурные правила у справочника А_Статьи_PL (уникальность ДДС с учётом shared-статей), как устранить 398 тыс ₴ «без расшифровки на PL-статью», как создавать новые PL-статьи из ДДС АДР автоматически.

## Контекст задачи

Финансист-пользователь открывал вариант `Отчет.А_ОтчетPL.РасшифровкаДокументаОтчетPL` и видел:
- По подразделению «Астарта. Тищенки» декабрь 2025 есть **две пустые строки** с `Сумма ЕРП = 398 409.56 ₴` и `Разница = -398 409.56 ₴` — это обороты из АДР **без расшифровки на PL-статью** (пустые «Группа статей PL» и «Статья PL»).
- Все ЗП-статьи («Зарплата ИТР», «ЗП производственного персонала» и т. д.) показывали `Сумма ЕРП = 0`, хотя в АДР по ним суммы есть.

Оба симптома указывали на архитектурный разрыв:

1. **А_ОтчетPL читал не те регистры.** Исходная логика — три производных регистра `РегистрНакопления.ДвиженияНоменклатураДоходыРасходы`, `ДвиженияКонтрагентДоходыРасходы`, `ДвиженияДенежныеСредстваДоходыРасходы`. Эти регистры содержат **только распределённые** на себестоимость расходы. `Документ.ОтражениеЗарплатыВФинансовомУчете` в них не пишет (пишет только в `РегистрНакопления.ПрочиеРасходы`, 156 записей на документ, подтверждено через MCP `execute_query` по полю `Регистратор`).
2. **Справочник А_Статьи_PL не был консистентным.** Часть ДДС из АДР не была привязана ни к одной PL-статье (17 штук на 25.17 млн ₴ за 3 месяца), часть ДДС дублировалась между 2-7 PL (ДДС «Персонал», «Начисления на зарплату PM»). Отсутствовал контроль целостности при записи.

Цель: **приводим нашу часть (отчёт + справочник) к 100 %**. Если финансист ошибся в Excel — это `DATA_GAP`, явно помечается, но не маскируется.

## Решение

### 1. Новая архитектура запроса отчёта А_ОтчетPL

Файл: `Reports/А_ОтчетPL/Ext/ObjectModule.bsl`, функция `ПолучитьОбъединенныеДанные(НачалоПериода, КонецПериода) Экспорт` (~60-220 строки после переписывания).

**Источники данных** (как в стандартном `Отчет.АнализДоходовРасходов`):
- Доходы: `РегистрНакопления.ФинансовыеРезультаты.Обороты` (выручка от продаж через `СтатьяДоходов`) + `РегистрНакопления.ПрочиеДоходы.Обороты` (прочие доходы через `СтатьяДоходов`), объединение UNION ALL внутри подзапроса.
- Расходы: **РегистрНакопления.ПрочиеРасходы.Обороты** (единственный первичный регистр). Поле для PnL — `СуммаРеглПриход` (регламентированный приход). Связь на PL — через `Об.СтатьяРасходов.А_СтатьяДвиженияДенежныхСредств`.

**Структура временных таблиц** (7 CTE):

| № | Таблица | Содержимое |
|---|---|---|
| 1 | `втPL` | 1 строка на `(Подразделение, СтатьяPL)`, из `Документ.А_ОтчетPL.ДанныеОтчета`, агрегаты по `СуммаФома1`, `СуммаФорма2`, `Сумма`. Группировка без ДДС — избегаем задвоения при JOIN с ТЧ. |
| 2 | `втPL_ДДС` | РАЗЛИЧНЫЕ `(СтатьяPL, ДДС)` из `Справочник.А_Статьи_PL.Статьи`. Связь PL → все её ДДС. |
| 3 | `втЕРП_Доходы_Сырые` | UNION ALL: `ФинансовыеРезультаты.Обороты` (ДоходыРеглБезНДСОборот) + `ПрочиеДоходы.Обороты` (СуммаРеглПриход). |
| 4 | `втЕРП_Доходы` | Агрегат по `(Подразделение, СтатьяДоходов)`. |
| 5 | `втЕРП_Расх_Сырые` | `ПрочиеРасходы.Обороты`, поле `СтатьяРасходов.А_СтатьяДвиженияДенежныхСредств` как ДДС, `СуммаРеглПриход`. |
| 6 | `втЕРП_Расх` | Агрегат по `(Подразделение, ДДС)`. |
| 7 | **`втЕРП_Расх_Агр`** | Агрегат ЕРП на уровне `(Подразделение, СтатьяPL)` через LEFT JOIN `втPL × втPL_ДДС × втЕРП_Расх`. Одна PL может иметь N ДДС — суммируется всё. Задвоения нет, потому что одна ДДС ∈ одна PL (гарантия модуля объекта, см. ниже). |

**Финальное соединение** (`втPL_сЕРП`):
```
ВЫБРАТЬ
    PL.Подразделение, PL.ПодразделениеСтрока, PL.Группа, PL.СтатьяPL,
    NULL КАК ДДС,   -- в итоговой строке одна PL-статья, ДДС неактуальна
    PL.СуммаФ1, PL.СуммаФ2, PL.СуммаPL,
    ЕСТЬNULL(ЕРПД.СуммаЕРП_Доход, 0) + ЕСТЬNULL(АГР.СуммаЕРП_Расх_Агр, 0) КАК СуммаЕРП,
    PL.СуммаPL - (ЕСТЬNULL(ЕРПД.СуммаЕРП_Доход, 0) + ЕСТЬNULL(АГР.СуммаЕРП_Расх_Агр, 0)) КАК Разница
ИЗ втPL КАК PL
    ЛЕВОЕ СОЕДИНЕНИЕ втЕРП_Доходы КАК ЕРПД
        ПО PL.Подразделение = ЕРПД.Подразделение И PL.СтатьяДоходов = ЕРПД.СтатьяДоходов
    ЛЕВОЕ СОЕДИНЕНИЕ втЕРП_Расх_Агр КАК АГР
        ПО АГР.Подразделение = PL.Подразделение И АГР.СтатьяPL = PL.СтатьяPL
```

**Итоговый UNION ALL** — три набора:
1. `втPL_сЕРП` — основные строки (PL + ЕРП)
2. `втЕРП_БезPL_Доходы` — выручка/прочие доходы из АДР, СтатьяДоходов которых не связана ни с одной `А_Статьи_PL.СтатьяДоходов`. Эти строки — сигнал MAPPING_BUG (NULL вместо PL-статьи).
3. `втЕРП_БезPL_Расходы` — ДДС из АДР, не привязанные ни к одной `А_Статьи_PL.Статьи`. Тоже MAPPING_BUG.

Проверка: `ГДЕ НЕ ЕРПР.ДДС В (ВЫБРАТЬ PLД.ДДС ИЗ втPL_ДДС КАК PLД)`. После наведения порядка в справочнике (см. раздел 2) эти блоки должны возвращать **ноль строк** — все ДДС АДР привязаны к PL.

**Функция `Экспорт`**: модификатор `Экспорт` добавлен на сигнатуру `ПолучитьОбъединенныеДанные`, иначе Python COM не может вызвать её напрямую (проблема: `AttributeError: <unknown>.ПолучитьОбъединенныеДанные`).

### 2. Справочник А_Статьи_PL — контроли целостности

#### 2.1 Новый реквизит `А_СозданоАвтоматически` (Булево)

Файл: `Catalogs/А_Статьи_PL.xml` (добавлен через skill `meta-edit`).

Свойства:
- Имя: `А_СозданоАвтоматически`
- Тип: `xs:boolean`
- Synonym (ru): «Создано автоматически (нет в Excel)»
- ToolTip (ru, LocalStringType с v8:item): «Истина — статья создана автоматически из ДДС АДР (нет в Excel). Требует проверки финансиста.»

Критический нюанс меtа-edit: параметр `ToolTip` при первой правке пытается записаться как простая строка `<ToolTip>текст</ToolTip>` — это вызывает ошибку XDTO `LocalStringType` при `db-load-xml`. Фикс — вручную править XML на структуру `<ToolTip><v8:item><v8:lang>ru</v8:lang><v8:content>текст</v8:content></v8:item></ToolTip>`.

**Назначение флага** — отделить 2 категории PL-статей:
- `Истина` — статья создана Python-скриптом `_apply_dds_assignments.py` для покрытия ДДС из АДР, которые не было в Excel-форме финансиста. Отображается в отчёте со `Сумма ЕРП > 0` и `Сумма PL = 0` (или с минусом в `Разница`).
- `Ложь` — статья, присутствующая в Excel финансиста (стандартная).

Python-пайплайн при следующей заливке автоматически снимает флаг (`А_СозданоАвтоматически = Ложь`), если имя авто-созданной статьи обнаружилось в `02_unique_articles.json` (финансист добавил её в Excel).

#### 2.2 Модуль объекта: 4 правила при записи

Файл: `Catalogs/А_Статьи_PL/Ext/ObjectModule.bsl`. Папка `Ext` создаётся впервые — раньше модуля не было.

Процедура `ПередЗаписью(Отказ)`:

```bsl
#Если Сервер Или ТолстыйКлиентОбычноеПриложение Или ВнешнееСоединение Тогда

Процедура ПередЗаписью(Отказ)

    Если ОбменДанными.Загрузка ИЛИ ЭтоГруппа ИЛИ ПометкаУдаления Тогда
        Возврат;
    КонецЕсли;

    ТипРасхода = ТипСтатьи = Перечисления.А_ТипСтатьиPL.Расход;

    // Правило 1 — шапочная ДДС для расходов (с исключениями по коду)
    Если ТипРасхода И НЕ ЗначениеЗаполнено(СтатьяДвиженияДенежныхСредств) Тогда
        Если Не ЭтоРасходИсключениеБезДДС() Тогда
            ВызватьИсключение "Для расходной статьи PL «" + Наименование +
                "» обязательно заполнить поле ""Статья движения денежных средств"" в шапке.";
        КонецЕсли;
    КонецЕсли;

    // Правило 2 + 3 — ТЧ Статьи согласована с шапкой
    Если ЗначениеЗаполнено(СтатьяДвиженияДенежныхСредств) Тогда
        Если Статьи.Количество() = 0 Тогда
            ВызватьИсключение "Табличная часть ""Статьи"" у PL «" + Наименование +
                "» не может быть пустой: должна содержать минимум 1 строку с шапочной ДДС.";
        КонецЕсли;
        ШапочнаяВТЧ = Ложь;
        Для Каждого Стр Из Статьи Цикл
            Если НЕ ЗначениеЗаполнено(Стр.СтатьяДвиженияДенежныхСредств) Тогда
                ВызватьИсключение "Пустая строка в ТЧ ""Статьи"" у PL «" + Наименование + "» недопустима.";
            КонецЕсли;
            Если Стр.СтатьяДвиженияДенежныхСредств = СтатьяДвиженияДенежныхСредств Тогда
                ШапочнаяВТЧ = Истина;
            КонецЕсли;
        КонецЦикла;
        Если НЕ ШапочнаяВТЧ Тогда
            ВызватьИсключение "Шапочная ДДС «" + СтатьяДвиженияДенежныхСредств +
                "» должна присутствовать в ТЧ ""Статьи"" у PL «" + Наименование + "».";
        КонецЕсли;
    КонецЕсли;

    // Правило 4 — адаптивная уникальность ДДС через обороты АДР
    ДДСМассив = Новый Массив;
    Для Каждого Стр Из Статьи Цикл
        Если ЗначениеЗаполнено(Стр.СтатьяДвиженияДенежныхСредств) Тогда
            ДДСМассив.Добавить(Стр.СтатьяДвиженияДенежныхСредств);
        КонецЕсли;
    КонецЦикла;

    Если ДДСМассив.Количество() > 0 Тогда
        // Найти другие PL-статьи, использующие те же ДДС
        Запрос = Новый Запрос;
        Запрос.Текст =
        "ВЫБРАТЬ
        |   ТЧ.СтатьяДвиженияДенежныхСредств КАК ДДС,
        |   ТЧ.Ссылка КАК PLСсылка
        |ИЗ Справочник.А_Статьи_PL.Статьи КАК ТЧ
        |ГДЕ ТЧ.СтатьяДвиженияДенежныхСредств В (&ДДСМассив)
        |   И ТЧ.Ссылка <> &Ссылка
        |   И НЕ ТЧ.Ссылка.ПометкаУдаления";
        Запрос.УстановитьПараметр("ДДСМассив", ДДСМассив);
        Запрос.УстановитьПараметр("Ссылка", Ссылка);
        ТЗКонфликтов = Запрос.Выполнить().Выгрузить();

        Если ТЗКонфликтов.Количество() > 0 Тогда
            // АДАПТИВНАЯ ПРОВЕРКА: у конфликтной ДДС есть обороты в АДР за 12 месяцев?
            // Если сумма = 0 → shared-ДДС (zontik), разрешаем.
            // Если > 0 → падаем.
            НачалоПериода = ДобавитьМесяц(НачалоМесяца(ТекущаяДатаСеанса()), -12);
            КонецПериода = КонецМесяца(ТекущаяДатаСеанса());

            ДДСКонфликтов = Новый Массив;
            Для Каждого СтрК Из ТЗКонфликтов Цикл
                Если ДДСКонфликтов.Найти(СтрК.ДДС) = Неопределено Тогда
                    ДДСКонфликтов.Добавить(СтрК.ДДС);
                КонецЕсли;
            КонецЦикла;

            ЗапрОборот = Новый Запрос;
            ЗапрОборот.Текст =
            "ВЫБРАТЬ
            |   Об.СтатьяРасходов.А_СтатьяДвиженияДенежныхСредств КАК ДДС,
            |   СУММА(Об.СуммаРеглПриход) КАК Сумма
            |ИЗ РегистрНакопления.ПрочиеРасходы.Обороты(&НП, &КП, , ) КАК Об
            |ГДЕ Об.СтатьяРасходов.А_СтатьяДвиженияДенежныхСредств В (&ДДСМассив)
            |СГРУППИРОВАТЬ ПО Об.СтатьяРасходов.А_СтатьяДвиженияДенежныхСредств
            |ИМЕЮЩИЕ СУММА(Об.СуммаРеглПриход) > 0";
            ЗапрОборот.УстановитьПараметр("НП", НачалоПериода);
            ЗапрОборот.УстановитьПараметр("КП", КонецПериода);
            ЗапрОборот.УстановитьПараметр("ДДСМассив", ДДСКонфликтов);
            ТЗОбороты = ЗапрОборот.Выполнить().Выгрузить();

            Если ТЗОбороты.Количество() > 0 Тогда
                // Есть реальные обороты — падаем с подробным сообщением
                ТекстОшибки = "ДДС не может использоваться одновременно в нескольких PL-статьях, если по ней есть обороты в АДР." + Символы.ПС;
                ТекстОшибки = ТекстОшибки + "Проблемные ДДС:" + Символы.ПС;
                Для Каждого СтрО Из ТЗОбороты Цикл
                    КонкурПЛ = "";
                    Для Каждого СтрК Из ТЗКонфликтов Цикл
                        Если СтрК.ДДС = СтрО.ДДС Тогда
                            КонкурПЛ = КонкурПЛ + " '" + СтрК.PLСсылка + "'";
                        КонецЕсли;
                    КонецЦикла;
                    ТекстОшибки = ТекстОшибки + "  - " + СтрО.ДДС + " (сумма " + Формат(СтрО.Сумма, "ЧГ=") + " ₴): уже в " + КонкурПЛ + Символы.ПС;
                КонецЦикла;
                ТекстОшибки = ТекстОшибки + "Решение: уберите эту ДДС из ТЧ ""Статьи"" одной из PL-статей.";
                ВызватьИсключение ТекстОшибки;
            КонецЕсли;
            // Если сумма = 0 (shared-ДДС без оборотов) → проходим дальше, запись разрешена.
        КонецЕсли;
    КонецЕсли;

КонецПроцедуры

// Исключения из правила шапочной ДДС (инвестиционная деятельность, финансовая)
Функция ЭтоРасходИсключениеБезДДС()
    ИсключенияКодов = Новый Массив;
    ИсключенияКодов.Добавить("000000028"); // Расход от ивест. Деятельности (ОС)
    ИсключенияКодов.Добавить("000000056"); // Финансовые расходы
    Возврат ИсключенияКодов.Найти(Код) <> Неопределено;
КонецФункции

#КонецЕсли
```

**Ключевая инженерная находка** — правило 4 использует **адаптивную уникальность через обороты АДР**, а не жёсткий whitelist UUID в коде:
- Одна ДДС может быть в нескольких PL, если у неё **нет реальных оборотов** в `ПрочиеРасходы` за последние 12 месяцев (примеры: ДДС «Персонал» УТ-001044 — zontik без оборотов, присутствует в 6 PL-статьях «Премия производственного персонала», «Командировочные производственного», «Транспортные затраты производственного», «Премия управленческого», «Транспортные затраты управленческого», «Затраты на коммандировки управленческого»).
- Если обороты есть → платформа падает с сообщением, в котором перечислены конфликтные ДДС + имена конкурирующих PL-статей.

Преимущества перед whitelist'ом:
1. Адаптивность — если завтра появится документ с оборотом по ДДС «Персонал», платформа автоматически начнёт ловить дубль без правки кода.
2. Нет захардкоженных UUID в модуле.

### 3. Инвентаризация ДДС и автосоздание PL-статей

#### 3.1 Скрипт `_collect_adr_dds.py` — сбор всех ДДС из АДР за 3 месяца

Файл: `_Rarzrabotki/Python/PnL/scripts/_collect_adr_dds.py`.

Запрашивает 3 месяца (декабрь 2025, январь 2026, лютий 2026) по 3 источникам:

## Ловушки и подводные камни

### 6.1 `РегистрНакопления.ПрочиеРасходы` — оборотный транзитный регистр

**НЕПРАВИЛЬНО**: суммирование через основную таблицу `СУММА(Р.Сумма)` — даёт двойное значение, т.к. на каждую статью платформа пишет симметрично Приход + Расход с равными суммами (сальдо = 0).

**ПРАВИЛЬНО**: виртуальная таблица `.Обороты`, поле **`СуммаРеглПриход`** (или `СуммаПриход` для управленческого учёта). Пример:
```sql
ВЫБРАТЬ СУММА(Об.СуммаРеглПриход) КАК PnL_Сумма
ИЗ РегистрНакопления.ПрочиеРасходы.Обороты(&НП, &КП, , ) КАК Об
ГДЕ Об.Подразделение.Наименование = &Подр
```

Подтверждено через прямой запрос: для Астарты декабрь 2025 `СуммаПриход = СуммаРасход` для каждой статьи, сальдо = 0.

### 6.2 Документ `ОтражениеЗарплатыВФинансовомУчете` пишет ТОЛЬКО в `ПрочиеРасходы`

Проверено через MCP запрос по 7 регистрам для документа с UUID `c2dff300-35f9-11f1-a2e8-ae822d4b0de9` (000Ц-000003 от 31.12.2025):

| Регистр | Записей |
|---|---:|
| `РегистрНакопления.ПрочиеРасходы` | **156** |
| `ДвиженияНоменклатураДоходыРасходы` | 0 |
| `ДвиженияКонтрагентДоходыРасходы` | 0 |
| `ДвиженияДенежныеСредстваДоходыРасходы` | 0 |

Т.е. документ ЗП не создаёт бух.проводок и не пишет в производные регистры. Только `ПрочиеРасходы`. Это принципиально — любой PnL-отчёт, который хочет видеть ЗП, должен читать `ПрочиеРасходы`.

### 6.3 Python COM кэш модулей отчёта

После `db-load-xml -UpdateDB` модуль в конфигурации БД обновлён, но **активная Python COM-сессия** может продолжать работать со старой скомпилированной версией функции отчёта. Симптом: прямой `execute_query` через MCP возвращает новые данные, а `conn.Отчеты.А_ОтчетPL.Создать().ПолучитьОбъединенныеДанные(...)` возвращает устаревшие.

**Решение для тестов** — писать автотест через прямой `execute_query` с воспроизведением логики отчёта (7 CTE-таблиц), а не через вызов метода отчёта. Это даёт независимую проверку и обходит кэш.

### 6.4 `str(CatalogRef)` в Python COM возвращает `<COMObject <unknown>>`

При работе с таблицей значений из отчёта нельзя использовать `str(r.Подразделение)` для фильтрации — Python получит строку `"<COMObject <unknown>>"`, не имя подразделения. Варианты:
- Использовать **строковые колонки напрямую** (`r.ПодразделениеСтрока` — это `Строка(150)` в документе, не ссылка).
- Обращаться к `.Наименование` у ссылки: `str(r.Подразделение.Наименование)`.
- Или через `conn.XMLСтрока(r.Подразделение)` для получения UUID.

### 6.5 MCP execute_query параметры типа ссылка

Инструмент `mcp__1c-workerp__execute_query` **не принимает** `DocumentRef.*` или `CatalogRef.*` как значение параметра (ошибка «Нельзя сравнивать поля неограниченной длины и поля несовместимых типов»). Обход:
- Подзапрос по номеру/наименованию: `ГДЕ Регистратор В (ВЫБРАТЬ Ссылка ИЗ Документ.ОтражениеЗарплатыВФинансовомУчете ГДЕ Номер = "000Ц-000003")`.
- Или фильтрация по строковому имени: `ГДЕ Об.Подразделение.Наименование = "Астарта. Тищенки"` прямо в запросе.

### 6.6 meta-edit и ToolTip реквизита

Skill `meta-edit` при операции `modify-attribute` с параметром `tooltip=<текст>` сохраняет его как простой элемент `<ToolTip>текст</ToolTip>`. При `db-load-xml` платформа ругается: `Ошибка XDTO в файле - <Catalog>.xml, при чтении свойства: ToolTip` (ожидается структура `LocalStringType`).

Ручной фикс — преобразовать в:
```xml
<ToolTip>
    <v8:item>
        <v8:lang>ru</v8:lang>
        <v8:content>текст</v8:content>
    </v8:item>
</ToolTip>
```

### 6.7 Уникальность ДДС — shared vs жёсткая

Ошибочное решение «одна ДДС = одна PL» ломается для обобщающих ДДС без оборотов (например «Персонал»), которые исторически используются в нескольких PL-статьях как placeholder. Правильно — **адаптивная проверка через обороты АДР**:
- Обороты за 12 месяцев = 0 → ДДС разрешено использовать в N PL.
- Обороты > 0 → строгая уникальность, dupli кладутся с текстом ошибки.

Реализация — в правиле 4 модуля `Catalogs/А_Статьи_PL/Ext/ObjectModule.bsl`, строки ~60-150.

### 6.8 Разные пути к Python venv

- `C:\Python313\python.exe` — глобальный Python, не видит `%USERPROFILE%\AppData\Roaming\Python\Python313\site-packages` (user-site отключён в скрытой конфигурации).
- `C:\Configuration_downloads\BASERP25\_Rarzrabotki\Python\venv\Scripts\python.exe` — venv проекта, сюда устанавливать пакеты через `-m pip install openpyxl rapidfuzz pywin32`.
- В MCP `python-runner` при использовании `python` (без полного пути) используется другой Python (3.11.9), который может не иметь нужных пакетов. Всегда указывать полный путь к venv.

## НДС в ЕРП-фактах — почему `СуммаПриход`, а не `СуммаРеглПриход`

**Проблема:** в отчёте пользователь видел ЕРП-сумму в 1.2 раза меньше суммы в PL-документе. Пример: ПТУ Астарта.Тищенки январь 2026 по статье «Курьерские» сумма PL = 1013.70 ₴ (с НДС), а ЕРП показывал 844.75 ₴. Умножение на 1.2 (ставка НДС в Украине 20%) давало 1013.70 — то есть ЕРП тянул **без НДС**.

**Корень:** в исходной версии отчёта использовался ресурс `СуммаРеглПриход` виртуальной таблицы `РегистрНакопления.ПрочиеРасходы.Обороты`. В БАС ERP 2.5 ресурсы этого регистра:
- `Сумма` — полная сумма движения (управленческая, с НДС)
- `СуммаБезНДС` — без НДС (управленческая)
- `СуммаРегл` — сумма регламентная **без НДС**
- `СуммаРеглБезНДС` — то же что СуммаРегл (в некоторых случаях отличается)
- `НДСРегл` — чистый НДС (регламентный)

**Пример фактических значений для одного движения ПТУ** (проверено через COM-запрос):
```
Сумма=176.70   СуммаРегл=147.25   НДСРегл=29.45
147.25 + 29.45 = 176.70 ✓
```

**Вывод:** `Сумма` = с НДС, `СуммаРегл` = без НДС. Консультация с NotebookLM подтвердила: типовой `АнализДоходовРасходов` использует именно `СуммаПриход` (ресурс `Сумма`) для данных отчёта «в валюте упр. учёта с НДС» (параметр СКД `ДанныеОтчета=1`).

**Правка:**
```bsl
// БЫЛО:
СУММА(Р.СуммаРеглПриход) КАК СуммаЕРП
// СТАЛО:
СУММА(Р.СуммаПриход) КАК СуммаЕРП
```
Аналогично для `ПрочиеДоходы` (`СуммаПриход` вместо `СуммаРеглПриход`) и `ФинансовыеРезультаты` (`ДоходыОборот` вместо `ДоходыРеглБезНДСОборот`).

**Верификация:** Python COM-тест `test_otchetpl_sum_with_vat.py`: для ПТУ Астарта.Тищенки январь 2026 по курьерским сумма `СуммаПриход` = 176.70+530.10+306.90 = 1013.70 ₴ = PL-сумма. ✓

## СКД-параметр `ВключатьДочерние` (added 2026-04-20)

В Template.xml добавлен пользовательский параметр `<parameter><name>ВключатьДочерние</name>` (xs:boolean, default=`false`, useRestriction=false). Параметр находится между блоками `Период` и `НачалоПериода` в `<dataParameters>`.

**Что фильтрует:** только блок `втPL` запроса через условие `И ТЧ.Ссылка.ВключатьДочерние = &ВключатьДочерние` в WHERE. Реализовано в `Reports/А_ОтчетPL/Ext/ObjectModule.bsl`:

2. Передаётся в `ПолучитьОбъединенныеДанные(НачалоПериода, КонецПериода, ВключатьДочерние = Ложь)`.
3. Устанавливается через `Запрос.УстановитьПараметр("ВключатьДочерние", ВключатьДочерние)`.

**Что НЕ фильтрует:** блоки `втЕРП_Расх_Детали`, `втЕРП_Доходы_Детали`, `втКазна_ПоПодрДДС` — намеренно. Регистры `ПрочиеРасходы`, `ФинансовыеРезультаты`, `ПрочиеДоходы`, `А_ДвиженияДенегИзКазны` не имеют семантически связанного с PL флага — они показывают весь факт по подразделению. Фильтрация по подразделению/направлению делается на уровне СКД-настроек варианта (через `ПользовательскиеНастройки`), не через этот параметр.

- 000000097 (PL_ЦО_Производство, ВД=Ложь, 1 226 801.76 ₴)

## Формат фильтров в XML (критически важно!)

Для того чтобы фильтр в варианте был **редактируемым** и чтобы `viewMode` не отбрасывался платформой, XML должен быть в формате:

```xml
<dcsset:item xsi:type="dcsset:FilterItemComparison">
    <dcsset:use>false</dcsset:use>
    <dcsset:left xsi:type="dcscor:Field">Подразделение</dcsset:left>
    <dcsset:comparisonType>InListByHierarchy</dcsset:comparisonType>
    <dcsset:right xsi:type="v8:ValueListType">
        <v8:valueType/>
        <v8:lastId xsi:type="xs:decimal">-1</v8:lastId>
    </dcsset:right>
    <dcsset:viewMode>Normal</dcsset:viewMode>
    <dcsset:userSettingID>GUID</dcsset:userSettingID>
</dcsset:item>
```

**Ключевые требования (проверено через `/db-dump-xml` после `/db-load-xml`):**
- `comparisonType = InListByHierarchy` (для иерархических справочников) или `InList` — **НЕ** `Equal`.
- `<right> = v8:ValueListType` — **НЕ** `dcscor:DesignTimeValue`.
- `<viewMode> = Normal` — **НЕ** `QuickAccess` (платформа отбрасывает `QuickAccess` когда `right=DesignTimeValue`).

**Если использовать `Equal + DesignTimeValue`** — платформа при `/db-load-xml` загружает XML, но `viewMode` **молча отбрасывает**. При `/db-dump-xml` это поле пропадает. Как следствие — фильтр становится `Inaccessible` («Недоступный»).

## Передача отборов из формы документа → отчёт

**Симптом:** пользователь кликает «Открыть сверку с 1С» на форме документа А_ОтчетPL — отчёт открывается, но фильтр `Подразделение` в шапке стоит на режиме «Недоступный», нельзя перетащить в шапку или редактировать.

**Корень (БСП, задокументированное поведение):** модуль `CommonModules/ОтчетыСервер/Ext/Module.bsl`, процедура `УстановитьФиксированныеОтборы` (строки 2145-2184):
```bsl
Недоступный = РежимОтображенияЭлементаНастройкиКомпоновкиДанных.Недоступный;
Для Каждого КлючИЗначение Из СтруктураОтборов Цикл
    ...
    ОбщегоНазначенияКлиентСервер.УстановитьЭлементОтбора(
        ОтборыКД, Имя, Значение, ВидСравненияКД, , Истина, Недоступный, "");
КонецЦикла;
```

Когда форма документа передаёт `ПараметрыФормы.Вставить("Отбор", ...)`, БСП применяет каждый элемент с `РежимОтображения = Недоступный` — это дизайн БСП для **фиксированных** (read-only) отборов.

**Правильное решение — передавать отбор через `ПользовательскиеНастройки`:**

```bsl
// НЕ ТАК:
ПараметрыФормы.Вставить("Отбор", Отбор);

// А ТАК — через ПользовательскиеНастройки, где РежимОтображения наследуется из XML (Normal):
ПараметрыФормы.Вставить("ПользовательскиеНастройки", СформироватьПользовательскиеНастройкиОтчета(
    Дата, ВариантКлюч, ПодразделениеОтбора, НаправлениеОтбора));
```

В функции `СформироватьПользовательскиеНастройкиОтчета`:
1. Загрузить Компоновщик с настройками варианта.
2. **Проход 1** по `Компоновщик.Настройки.Отбор.Элементы` (тут `ЛевоеЗначение` доступно) — прочитать `ИдентификаторПользовательскойНастройки` (GUID) для фильтров «Подразделение» и «НаправлениеДеятельности».
3. **Проход 2** по `Компоновщик.ПользовательскиеНастройки.Элементы` (тут `ЛевоеЗначение` **недоступно**) — найти по GUID и установить `Элемент.ПравоеЗначение = СписокЗначений; Элемент.Использование = Истина`.

**Критично:** в `ПользовательскиеНастройки.Элементы` свойство `ЛевоеЗначение` выдаёт ошибку «Свойство 'ЛевоеЗначение' не поддерживается элементом коллекции пользовательских настроек». Нужно использовать GUID для идентификации, полученный из variant-level `Настройки.Отбор.Элементы`.

Полный код функции — см. `Documents/А_ОтчетPL/Forms/ФормаДокумента/Ext/Form/Module.bsl` (живой пример).

**Детали этого паттерна в отдельном документе:** `report_open_from_form.md` (NotebookLM source `14581045-be96-43d4-8c8b-8cba20e7afed`).

## Агрегация СуммаЕРП на уровне СтатьяPL

После новой архитектуры СуммаЕРП рассчитывается иначе:
- PL-строка имеет `СуммаЕРП = 0` (ЕРП-часть вынесена в детали).
- ЕРП-детали имеют `СуммаЕРП = <своя сумма>`, суммируются при группировке СтатьяPL.

**Итог группировки СтатьяPL:**
- `Ф1/Ф2/PL` = `Σ(из PL-строки)` = сумма из Excel.
- `СуммаЕРП` = `Σ(из ЕРП-деталей по всем ДДС этой PL)` = сумма из 1С с НДС.
- `Разница` = `Σ(PL) - Σ(ЕРП)` через totalField СКД.

**Визуальный эффект:** под каждой СтатьёйPL в разворачивании появляются блоки по ДДС:
- Блок «(Пусто)» с одной строкой PL-документа (Ф1/Ф2/PL заполнены, ЕРП=0).
- Блоки с конкретными ДДС и списком документов-регистраторов ЕРП (Ф1/Ф2/PL=0, ЕРП=частичные).

Это приемлемо — «Пусто»-блок информативен, содержит PL-сумму которую не разбили по ДДС.
