## TL;DR

Отчёт `Отчет.А_ОтчетPL` — кастомный финансовый отчёт PnL «План vs Факт» для финансиста INDUSTRIALBUD. Сравнивает плановые суммы из `Документ.А_ОтчетPL` (заполненные по Excel-листам подразделений) с фактическими оборотами из стандартных регистров ЕРП. Дополнительно показывает кассовый поток из `Регистр.А_ДвиженияДенегИзКазны` для сверки кассового метода учёта.

Ключевые особенности:
- **5 источников данных**, объединённых в **8 временных таблиц (CTE)** и 7 финальных UNION ALL блоков.
- **Виручка берётся из `РегистрНакопления.ВыручкаИСебестоимостьПродаж`** (ресурс `СуммаВыручки`, с НДС) — не из `ФинансовыеРезультаты` (там Виручку пишет `Документ.РасчетСебестоимостиТоваров` агрегированно, что ломало drill-down).
- **CoGS** (себестоимость продаж) тоже из `ВыручкаИСебестоимостьПродаж` (ресурс `Стоимость`, с НДС), привязка к PL-статье через **флаг-маркер** на одной ДДС.
- 2 СКД-параметра: `Период` (StandardPeriod) и `ВключатьДочерние` (Boolean, default=Ложь).
- 3 варианта СКД для разных сценариев открытия.
- Фильтрация по подразделениям/направлениям делается на уровне СКД-настроек варианта (через `ПользовательскиеНастройки`), не в запросе.

Боль, которую отчёт решает: финансист хочет видеть в одной строке за конкретное подразделение и статью план (Excel) и факт (1С-регистры) — стандартный `Отчет.АнализДоходовРасходов` показывает только факт, а Excel-планы лежат отдельно. Дополнительно — стандартный отчёт CoGS не показывает (АДР работает только с ПрочиеДоходы/ПрочиеРасходы), а финансисту критично видеть Себестоимость продаж по Реализациям.

## Архитектура запроса

Файл: `Reports/А_ОтчетPL/Ext/ObjectModule.bsl`, функция `ПолучитьОбъединенныеДанные(НачалоПериода, КонецПериода, ВключатьДочерние = Ложь) Экспорт`.

Дополнительная функция модуля: `ПолучитьДДСПриёмникCoGS()` — возвращает ссылку на ДДС с флагом `А_ПриёмникСебестоимостиПродажPL = Истина` или ПустаяСсылка.

### Источники данных (5 регистров)

| Источник | Назначение | Поле для PnL |
|---|---|---|
| `Документ.А_ОтчетPL.ДанныеОтчета` | План (Excel) | `СуммаФома1`, `СуммаФорма2`, `Сумма` |
| `РегистрНакопления.ПрочиеРасходы.Обороты` | Факт-расходы (включая ЗП через ОтражениеЗарплатыВФинансовомУчете, амортизацию, аренду, материалы) | `СуммаПриход` |
| `РегистрНакопления.ВыручкаИСебестоимостьПродаж` (прямая таблица, не .Обороты) | **Факт-Виручка от продаж** (СтатьяДоходов hardcode) и **факт-CoGS** | `СуммаВыручки` (с НДС) для Виручки, `Стоимость` (с НДС) для CoGS, `ДокументДвижения` для drill-down |
| `РегистрНакопления.ПрочиеДоходы.Обороты` | Прочие доходы (курсовые, штрафы, фин. деятельность) | `СуммаПриход` |
| `РегистрНакопления.А_ДвиженияДенегИзКазны.Обороты` | Кассовый поток (справочно) | `СуммаОборот` (расход = отрицательный, приход = положительный) |

> **Почему Виручка берётся из прямой таблицы `ВыручкаИСебестоимостьПродаж`, не из `.Обороты`:** на виртуальной таблице `.Обороты` поле `ДокументДвижения` НЕДОСТУПНО (это реквизит, не измерение). А именно `ДокументДвижения` даёт чистую ссылку на исходный документ Реализации (`Документ.РеализацияТоваровУслуг`, `АктВыполненныхРабот`, `ВозвратТоваровОтКлиента`, `КорректировкаРеализации`) — НЕ на службовий `РасчетСебестоимостиТоваров`. Поэтому drill-down показывает реальную Реализацию.

### Связь PL ↔ ЕРП

| Тип | Через что связывается |
|---|---|
| Расходы PL ↔ ЕРП (ПрочиеРасходы) | `Справочник.А_Статьи_PL.Статьи.СтатьяДвиженияДенежныхСредств` ↔ `СтатьяРасходов.А_СтатьяДвиженияДенежныхСредств` |
| **CoGS PL ↔ ЕРП (ВыручкаИСебестоимостьПродаж.Стоимость)** | `Справочник.А_Статьи_PL.Статьи.СтатьяДвиженияДенежныхСредств` ↔ `&ДДСCoGS` (одна ДДС с флагом `А_ПриёмникСебестоимостиПродажPL`) |
| Доходы PL ↔ ЕРП (Виручка) | hardcode `ВыручкаОтПродаж` ↔ `Справочник.А_Статьи_PL.СтатьяДоходов = "Выручка от продаж"` |
| Доходы PL ↔ ЕРП (Прочие) | `Справочник.А_Статьи_PL.СтатьяДоходов` ↔ `СтатьяДоходов` (плана видов характеристик) |
| Касса ↔ PL | `Касна.СтатьяДвиженияДенежныхСредств` ↔ та же ДДС что у расходов PL |

### Структура временных таблиц (8 CTE)

| № | Таблица | Что внутри |
|---|---|---|
| 1 | `втPL` | План из `Документ.А_ОтчетPL.ДанныеОтчета`. **Здесь действует фильтр СКД-параметра `ВключатьДочерние`.** |
| 2 | `втPL_ДДС` | РАЗЛИЧНЫЕ `(СтатьяPL, ДДС)` — справка для JOIN |
| 3 | `втЕРП_Расх_Детали` | Факт-расходы из ПрочиеРасходы с детализацией до Регистратора и Контрагента (через ВЫРАЗИТЬ для 9 типов документов). **НЕ зависит от ВД.** |
| 4 | `втЕРП_Доходы_Детали` | Факт-доходы UNION ALL: **(а) ВыручкаИСебестоимостьПродаж** (Виручка с НДС, СтатьяДоходов hardcode = ВыручкаОтПродаж, Документ = ДокументДвижения) + **(б) ПрочиеДоходы** (курсовые, фин.деятельность). **НЕ зависит от ВД.** |
| 5 | **`втЕРП_CoGS_Детали` (НОВЫЙ)** | CoGS из `ВыручкаИСебестоимостьПродаж.Стоимость` (с НДС). Подразделение, ДДС=&ДДСCoGS, Документ=ДокументДвижения, Контрагент через CASE WHEN ССЫЛКА (4 типа). WHERE: `&ДДСCoGS <> ПустаяСсылка` (если флаг не выставлен — 0 строк). |
| 6 | `втКазна_ПоПодрДДС` | Кассовый оборот по `(Подразделение, ДДС, ДокументДвиженияКазны, Контрагент)`. **НЕ зависит от ВД.** |
| 7-8 | `втPL_Строки`, `втЕРП_ПоPL_Расх` (включает CoGS через UNION ALL!), `втЕРП_ПоPL_Доходы`, `втЕРП_БезPL_Расх`, `втЕРП_БезPL_Доход`, `втКазна_ПоPL`, `втКазна_БезPL` | Финальные блоки для UNION ALL — каждый со своими нулями в неактуальных колонках |

### Финальное объединение

`втЕРП_ПоPL_Расх` теперь содержит **2 источника** через UNION ALL:
1. `втЕРП_Расх_Детали JOIN втPL_ДДС` — стандартные расходы из ПрочиеРасходы
2. **`втЕРП_CoGS_Детали JOIN втPL_ДДС`** — CoGS из ВыручкаИСебестоимостьПродаж (через флаг ДДС)

7 финальных блоков UNION ALL → выгружается через `Запрос.Выполнить().Выгрузить()` → передаётся в СКД как Внешний набор данных «Данные» через `Структура("Данные", ТаблицаДанных)`.

### Параметры запроса

| Параметр | Источник | Назначение |
|---|---|---|
| `&НачалоПериода` | СКД (derived из `&Период.ДатаНачала`) | Начало периода |
| `&КонецПериода` | СКД (derived) | Конец периода (КОНЕЦПЕРИОДА .ДЕНЬ) |
| `&ВключатьДочерние` | СКД-параметр | Фильтр PL-документов (см. ниже) |

## Параметры СКД

В `Templates/ОсновнаяСхемаКомпоновкиДанных/Ext/Template.xml` определены 3 параметра, из них 2 пользовательских и 1 derived:

| Имя | Тип | Default | useRestriction | Назначение |
|---|---|---|---|---|
| `Период` | `v8:StandardPeriod` | `ThisMonth` | false | Стандартный период отчёта |
| `ВключатьДочерние` | `xs:boolean` | `false` | false | **Фильтрует только PL (втPL)** — выбирает между ЦО-документами и СВОД-документами |
| `НачалоПериода` | `xs:dateTime` | derived | true | `&Период.ДатаНачала` (служебный, для запроса) |
| `КонецПериода` | `xs:dateTime` | derived | true | `КОНЕЦПЕРИОДА(&Период.ДатаОкончания, "ДЕНЬ")` (служебный) |

### Что фильтрует `ВключатьДочерние` и что НЕ фильтрует

**Фильтрует:** только блок `втPL` через условие в WHERE:
```
ГДЕ ТЧ.Ссылка.Дата МЕЖДУ &НачалоПериода И &КонецПериода
    И НЕ ТЧ.Ссылка.ПометкаУдаления
    И ТЧ.Ссылка.ВключатьДочерние = &ВключатьДочерние
```

**НЕ фильтрует:** блоки `втЕРП_Расх_Детали`, `втЕРП_Доходы_Детали`, `втЕРП_CoGS_Детали`, `втКазна_ПоПодрДДС`. Эти регистры не имеют семантически связанного с PL флага «включать дочерние» — они показывают весь факт по подразделению за период.

### Обоснование такой фильтрации

Атрибут `Документ.А_ОтчетPL.ВключатьДочерние` — это «семантика плана»: одна Excel-форма за подразделение либо «ЦО» (только это подразделение), либо «СВОД» (само + все дочерние через `А_НаправлениеДеятельности`). Это атрибут сводности плановой стороны.

ЕРП-факт в регистре `ПрочиеРасходы`/`ВыручкаИСебестоимостьПродаж` не имеет такого флага — там просто строки с подразделением и статьёй. Поэтому при расшифровке:
- PL-часть = «правильный лист Excel» (097 ЦО или 096 СВОД, не оба)
- ЕРП-часть = «вся правда по подразделению за период»

Это соответствует кассовый-vs-начисление сверке, которую делает финансист.

## Настройка CoGS-маркера финансистом (1 раз перед использованием)

1. Справочник «Статьи движения денежных средств» → найти/создать ДДС, призначену для CoGS (например «Себестоимость реализации»).
2. Поставить галочку «**Приёмник себестоимости продаж (PL)**» (реквизит `А_ПриёмникСебестоимостиПродажPL` Boolean), записать.
   - Платформа сама проверит уникальность через ПередЗаписью модуля объекта `СтатьиДвиженияДенежныхСредств` — только одна ДДС в системе может иметь этот флаг (исключение бросается при попытке поставить второй раз).
3. Справочник «А_Статьи_PL» → нужная PL-статья (напр. «Будівельні матеріали») → ТЧ «Статьи» → добавить эту ДДС, записать.
4. Сформировать `Отчет.А_ОтчетPL` → CoGS появится в выбранной PL-статье по подразделениям и Реализациям.

> **Можливе подвоєння:** если в ТЧ Статьи PL уже есть «обычная» ДДС (для ПрочиеРасходы) и добавили ДДС-маркер CoGS — суммы сложатся. Решение финансиста: оставить обе суммы (если они означают разную природу витрат) или удалить одну из ДДС из ТЧ.

## 3 варианта СКД

| Вариант | Назначение | Рекомендуемый default ВД |
|---|---|---|
| `Основной` | Открытие отчёта из меню «Отчёты». Полная сверка PL ↔ ЕРП ↔ Касса. | На усмотрение пользователя (можно показать в шапке через `ПользовательскиеНастройки`) |
| `А_ОтчетPL_РасшифровкаДокументаОтчетPL` | Открытие из формы конкретного PL-документа кнопкой «Расшифровка документа PL». Фильтр по `Подразделение` + `НаправлениеДеятельности` через `ПользовательскиеНастройки`. | **Ложь** (ЦО-режим — не показывать СВОД-дубликаты) |
| `А_ОтчетPL_РасшифровкаПоНаправлению` | Открытие с фильтром по направлению деятельности. | **Истина** (по направлению логично видеть СВОД) |

**Дефолты ВД для каждого варианта настраиваются вручную в Конфигураторе** в `<settingsVariant><dataParameters>...`. **ИИ менять эти настройки не должен** — это red-line проекта.

## Документная иерархия: ЦО vs СВОД

Кейс «Производство, февраль 2026»:

| Номер | Подразделение | ПодразделениеСтрока | ВключатьДочерние | Логика |
|---|---|---|---|---|
| 000000096 | Производство | PL_Производство_СВОД | **true** | Сводный лист — план для всего направления, включая дочерние ЦО |
| 000000097 | Производство | PL_ЦО_Производство | **false** | План только для центрального ЦО Производства |

При открытии расшифровки из 097 финансист хочет видеть:
- PL = только данные 097 (1 226 801.76 ₴)
- ЕРП = весь факт по «Производство» за период (включая то, что распределено на дочерние)
- Касса = весь кассовый поток

**Без СКД-параметра ВключатьДочерние** оба документа (096 и 097) проходят отбор `Подразделение=Производство, Направление=Производство` и склеиваются → суммы PL удваиваются (1.2 млн + 20.3 млн = 21.5 млн), что неверно.

**С СКД-параметром ВД=Ложь** в WHERE втPL остаётся только 097.

## Build / Deploy

### Build sandbox

Не править `Reports/А_ОтчетPL/` напрямую. Workflow:

1. Скопировать в build:
```
cp Reports/А_ОтчетPL/Ext/ObjectModule.bsl _Rarzrabotki/build/А_ОтчетPL/Ext/
cp Reports/А_ОтчетPL/Templates/ОсновнаяСхемаКомпоновкиДанных/Ext/Template.xml _Rarzrabotki/build/А_ОтчетPL/Templates/ОсновнаяСхемаКомпоновкиДанных/Ext/
```
2. Применить правки в `_Rarzrabotki/build/А_ОтчетPL/`.
3. Pre-check через `mcp__1c-workerp__execute_query` (правило #4 проекта — сначала тест запроса).
4. Скопировать build → Reports/.
5. Загрузить через `db-load-xml -Mode Partial -UpdateDB`.

### db-load-xml команда

```
powershell -File .claude/skills/db-load-xml/scripts/db-load-xml.ps1 \
  -InfoBaseServer "SQLSERVER" -InfoBaseRef "BaseERP" \
  -UserName "Администратор" -Password "24043" \
  -ConfigDir "." -Mode Partial \
  -Files "Reports/А_ОтчетPL/Ext/ObjectModule.bsl,Reports/А_ОтчетPL/Templates/ОсновнаяСхемаКомпоновкиДанных/Ext/Template.xml" \
  -UpdateDB
```

### Блокировки deploy

- Если Конфигуратор открыт пользователем — partial-load упадёт. Попросить закрыть.
- Если в Template.xml кривое XSD — db-load-xml выдаст ошибку валидации.

## Anti-patterns (что НЕ делать с этим отчётом)

1. **НЕ менять настройки `<settingsVariant>` из ИИ.** Дефолты параметров и фильтры вариантов СКД настраивает пользователь сам в Конфигураторе. Это red-line проекта.
2. **НЕ использовать отбор `Документ` через `ПользовательскиеНастройки`.** ЕРП-регистры не имеют поля `Документ = А_ОтчетPL.Ссылка` — отбор выкосит всю ЕРП-часть. Для разделения ЦО/СВОД использовать СКД-параметр `ВключатьДочерние`.
3. **НЕ делать `ВключатьДочерние` полем ТЗ а не параметром.** Блоки `втЕРП_БезPL_*` и `втКазна_БезPL` получили бы NULL в этом поле — при отборе `=Ложь`/`=Истина` они выпадут из отчёта.
4. **НЕ применять фильтр ВД к ЕРП/Казне в запросе.** Атрибут существует только у `Документ.А_ОтчетPL`. Регистры не имеют этого флага.
5. **НЕ передавать `Параметры.Отбор` в команде «Расшифровка документа PL».** Это сделает фильтр Недоступным (см. `report_open_from_form.md`). Использовать `ПользовательскиеНастройки` через `НайтиСредиПользовательских` + `userSettingID` (см. `bsp_report_filters_from_document.md` в memory).
6. **НЕ использовать `В ИЕРАРХИИ` внутри агрегатных функций.** В этом запросе не применимо, но общее правило проекта.
7. **НЕ менять имя ТЧ `Движения`.** Зарезервировано платформой. В этой ТЧ называется `ДанныеОтчета` — корректно.
8. **НЕ использовать поля БезНДС (`СуммаВыручкиБезНДС`, `СтоимостьУпрБезНДС`)** — стандартный отчёт «Доходы и расходы предприятия» работает с НДС, и финансист сравнивает с ним. Использовать `СуммаВыручки` и `Стоимость` (оба с НДС).
9. **НЕ использовать СтатьюДоходов через `АналитикаУчетаНоменклатуры.СтатьяДоходов`** — у `Справочник.КлючиАналитикиУчетаНоменклатуры` НЕТ поля `СтатьяДоходов` (проверено). Хардкодить `ЗНАЧЕНИЕ(ПланВидовХарактеристик.СтатьиДоходов.ВыручкаОтПродаж)`.
10. **НЕ использовать `--` SQL-комментарии внутри `ИЗ (...)`-подзапросов** — 1С парсер падает с «Ожидается ВЫБРАТЬ».
11. **НЕ использовать двойные кавычки `"`** в SQL-комментариях внутри BSL-строки — парсер считает их закрытием BSL-строки.
