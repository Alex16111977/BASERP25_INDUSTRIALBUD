# Архітектура та інваріанти регістра `А_ВзаиморасчетыССотрудниками`

> Тип файлу: ПОСТІЙНИЙ (правила архітектури — не змінювати без обговорення з фінансистом). Знахідки/грабельки додавати у §Знахідки.

## 1. Призначення регістра

Регістр **розшифровує** статтю балансу "Оплата труда" (з `РегистрНакопления.ПрочиеАктивыПассивы`) до двох аналітик, яких немає в ПАП:
- **ФизическоеЛицо** (хто конкретно)
- **Подразделение** (хоча є в ПАП, ми збираємо паралельно для контрольного інваріанту)

ПАП для статті ОТ зберігає рухи з `Аналитика = ПустаяСсылка` (карточка статті: "Без аналитики"; рішення фінансиста 2026-05-18). Тому drill-down від статті ОТ у звіті управлінського балансу не працює — наш регістр **компенсує цю прогалину окремою таблицею**.

## 2. Σ-інваріант (головне правило коректності)

### 2.1 Формальне твердження

Для **кожного** регістратора-документа з 5 списку:
```
|Σ signed А_ВзСС| per (Орг, Подр) per Регістратор
                 =
|Σ signed ПАП(Статья=ОплатаТруда, Источник=ПустаяСсылка)| per (Орг, Подр) per Регістратор
```

де `Σ signed` = Σ(Приход) − Σ(Расход) (стандартне сальдо балансового регістра).

### 2.2 Інверсія знаку (фінансистська семантика)

Знаки А_ВзСС **протилежні** ПАП:
```
Σ signed А_ВзСС  =  −Σ signed ПАП(ОТ)  per Регістратор
```

**Чому інверсія:**

| Подія | Семантика | ПАП(ОТ) signed | А_ВзСС signed |
|---|---|:---:|:---:|
| Нараховано зарплату | Працедавець стає винен ФЛ — борг ↑ | **−** (стаття пассив, Расход у ПАП = рост обов'язку) | **+** (прямий борг ↑, Приход) |
| Утримано НДФЛ | Частина боргу йде в бюджет — борг ↓ | **+** (Приход = знесення обов'язку) | **−** (борг ↓, Расход) |
| Виплачено через банк | Борг ↓ | **+** | **−** |

Це **одна і та ж операція**, описана з двох сторін:
- ПАП = пассивна стаття "Скільки винні всі"
- А_ВзСС = "Скільки винен працедавець ФЛ-у" (прямий долг)

Сума по модулю однакова → інваріант виконується. Знаки протилежні → інверсія.

### 2.3 Як перевіряти в тестах

```python
# А_ВзСС + ПАП ≈ 0 per Регістратор (і per (Орг, Подр))
взс_signed = Σ(ВЫБОР ВидДв=Приход ТОГДА Сумма ИНАЧЕ -Сумма КОНЕЦ)  # з А_ВзСС
пап_signed = Σ(ВЫБОР ВидДв=Приход ТОГДА Сумма ИНАЧЕ -Сумма КОНЕЦ)  # з ПАП(ОТ)
assert abs(взс_signed + пап_signed) <= 1.0  # руб
```

`TOL = 1.0 ₽` per Регістратор — на округлення per ФЛ (типово ≤0,5 коп * число ФЛ).

## 3. Чому НЕ event-subscription / НЕ CFE

Розглянутий і відхилений шлях через `EventSubscription OnWrite` + `НаборЗаписей.Записать()`. Причини відмови (під впливом фінансиста-користувача 2026-05-20):

| # | Аргумент проти event-subscription | Аргумент за виклик з ОбработкаПроведения |
|---|---|---|
| 1 | "Невидима магія" — розробник не бачить, звідки беруться рухи | Виклик стоїть в коді документа, явно |
| 2 | НаборЗаписей.Записать() — окремий flush, поза транзакцією документа | Платформа писатиме всі Движения як одну транзакцію |
| 3 | Регресія/сироти при `ОбменДанными.Загрузка` потребують ручної обробки | RegisterRecordsDeletion=AutoDelete стандартно чистить рухи при перепроведенні |
| 4 | Потрібна підписка `<ExternalConnection>true</ExternalConnection>` для COM | Не потрібна — все працює в нативному контексті |
| 5 | "Не зрозуміло як цей регістр взагалі заповнюється" — пошук event-subscription | Стандартний пошук "де записуємо в Движения.А_ВзСС" знаходить виклик |

CFE розширення також відхилено: 5 окремих перехопників для 5 типових — більше overhead ніж сам виклик; правка типових документів (1 рядок) ефективно еквівалентна "перехопленню після", але без extension-shell.

**Memory orientation:** `feedback_no_typical_register_changes` — заборона на правки **типових регістрів** (не документів). Для документів-регістраторів додавання 1 рядка виклику в кінці ОбработкаПроведения вважається прийнятним розширенням (це не структурна правка).

## 4. Ланцюги даних (як 5 регістраторів дістають ФЛ)

### 4.1 ОтражениеЗарплатыВФинансовомУчете (DONE)

**Прямий — 3 ТЧ документа:**
```
ОЗФУ.НачисленнаяЗарплатаИВзносыПоФизлицам  (Налог=Пуст, виключ. 4 операції)  → Приход
ОЗФУ.НачисленныйНДФЛ                                                          → Расход
ОЗФУ.УдержаннаяЗарплата                                                        → Расход
```

Підрозділ — з реквізиту рядка ТЧ (`ПодразделениеПредприятия`). ФЛ — з реквізиту `ФизическоеЛицо`. Свертка per (Орг, Подр, ФЛ) для усунення дублів ключа.

### 4.2 СписаниеБезналичныхДенежныхСредств (DONE)

**Через зв'язану Відомість:**
```
СБДС.РасшифровкаПлатежа.Ведомость            (поле в ТЧ ←Документ.ВедомостьНаВыплатуЗарплатыВБанк)
                            ↓
РегистрНакопления.ЗарплатаКВыплате (Регистратор=Ведомость, ВидДв=Расход)
                            ↓
        ФизическоеЛицо + СуммаКВыплате
```

Підрозділ — з шапки СБДС (1:1 з типовим запитом ПАП блок 1 на line 3910). Знак: ВидДвижения=Расход (виплата = борг ↓). Фільтр ХозОперації: `ВыплатаЗарплатыПоЗарплатномуПроекту` / `ВыплатаЗарплатыНаЛицевыеСчета` + `ПроведеноБанком=Истина`.

### 4.3 РасходныйКассовыйОрдер (DONE 2026-05-20)

**Підтверджена модель** (НЕ через Ведомість як у СБДС, а через ТЧ напряму):
```
РКО.ВыплатаЗаработнойПлаты (ТЧ)
  ↓ ФизическоеЛицо + Сумма (прямо в ТЧ)
  ↓ Подразделение з шапки документа РКО (ДокОбъект.Подразделение)
```

Платформа автоматично заповнює `ВыплатаЗаработнойПлаты` при проведенні РКО за обраною Ведомістю. Звертатись до самої Ведомості не потрібно.

**Фільтр ХозОп:** `ВыплатаЗарплатыЧерезКассу` (синонім UI "Выплата по ведомости через кассу") + `ВыплатаЗарплатыРаздатчиком` + `ВыплатаЗарплатыРаботнику`. Знак — Расход.

### 4.4 ПриходныйКассовыйОрдер (НЕ РЕАЛІЗУЄТЬСЯ)

Типовий `ManagerModule.bsl` ПКО **не має функції `ТекстЗапросаТаблицаПрочиеАктивыПассивы`** взагалі. Grep по `ОплатаТруда|ПрочиеАктивыПассивы` → 0 збігів. ПКО ніколи не пише ПАП(ОТ) для повернень зарплати — інваріант 0=0 тривіально, процедура не потрібна.

Рішення фінансиста 2026-05-20 — не покривати, навіть як захисну порожню процедуру.

### 4.5 ПоступлениеБезналичныхДенежныхСредств (НЕ РЕАЛІЗУЄТЬСЯ)

Типовий блок ОТ існує (`Documents/ПоступлениеБезналичныхДенежныхСредств/Ext/ManagerModule.bsl:2647-2673`) для 2 ХозОп повернень — `ВозвратНеперечисленныхДС`, `ВозвратНеперечисленнойЗарплатыПоЗарплатномуПроекту`. Знак інверсний — ПАП.Расход.

Але реальних кандидатів у БД ТОВ ІНДАСТРІАЛБУД за 2024-2026 = 0. Рішення фінансиста 2026-05-20 — не покривати.

## 5. Фільтри (загальні принципи)

**Кожна процедура `ЗаполнитьИз<Тип>` повторює 1:1 фільтри типового запиту блок 1 для статті ОТ** з `ManagerModule.bsl` відповідного документа. Це гарантує що Σ збігаються.

| Документ | Ключові фільтри (для блоку статті ОТ) |
|---|---|
| ОЗФУ | `Налог = Пуст` (для начислений ЗП без взносов) + виключення 4 операцій (ЕжегодныйОтпускОценочныеОбязательстваИРезервы, НачисленоСдельноДоход, КомпенсацияЕжегодногоОтпускаОценочныеОбязательства, ЕжегодныйОтпускОценочныеОбязательства) |
| СБДС | `ХозОперация В (ВыплатаЗарплатыПоЗарплатномуПроекту, ВыплатаЗарплатыНаЛицевыеСчета)` + `ПроведеноБанком = Истина` + `ЗарплатаКВыплате.ВидДвижения = Расход` |
| РКО | `ХозОперация В (ВыплатаЗарплатыЧерезКассу, ВыплатаЗарплатыРаздатчиком, ВыплатаЗарплатыРаботнику)`. **НЕ використовуємо** фільтр `НЕ &ИспользоватьНачислениеЗарплаты` з типового — реальні рухи ПАП(ОТ) для РКО пишуться незалежно від константи (підтверджено двома еталонами 2026-05-20). |

**Принцип переноса:** перед написанням процедури для нового регістратора — прочитати [`Documents/<Тип>/Ext/ManagerModule.bsl`](.), знайти функцію `ТекстЗапросаТаблицаПрочиеАктивыПассивы()` і блок зі `Статья = ОплатаТруда`. Скопіювати ВСЕ фільтри 1:1. Інакше Σ не зійдуться.

## 7. Свёртка та дублі ключа

**Проблема:** якщо запит має кілька джерел (наприклад 3 ТЧ для ОЗФУ — НачисленнаяЗП + НДФЛ + Удержания), для одного (Орг, Подр, ФЛ) можуть бути 2-3 рядки з різними ВидДв. Це ламає assert "0 дублів ключа (Орг, Подр, ФЛ, ВидДв)".

**Рішення:** свёртка per (Орг, Подр, ФЛ) у фінальному SELECT запиту:

```sql
ВЫБРАТЬ
    С.Организация, С.Подразделение, С.ФизическоеЛицо,
    ВЫБОР КОГДА СУММА(С.Знач) > 0
        ТОГДА ЗНАЧЕНИЕ(ВидДвиженияНакопления.Приход)
        ИНАЧЕ ЗНАЧЕНИЕ(ВидДвиженияНакопления.Расход) КОНЕЦ КАК ВидДвижения,
    ВЫБОР КОГДА СУММА(С.Знач) > 0
        ТОГДА СУММА(С.Знач)
        ИНАЧЕ -СУММА(С.Знач) КОНЕЦ КАК СуммаВзаиморасчетов
ИЗ втСтроки КАК С
СГРУППИРОВАТЬ ПО С.Организация, С.Подразделение, С.ФизическоеЛицо
ИМЕЮЩИЕ СУММА(С.Знач) <> 0
```

Так на (Орг, Подр, ФЛ) залишається **одна** строка: Приход (якщо чистий рост долга) або Расход (якщо чисте зменшення).

## 8. Знахідки (грабельки)

### 8.1 Конфігуратор блокує `/db-load-xml`

При відкритому Конфігураторі скрипт `db-load-xml.ps1` падає з:
```
Ошибка блокировки информационной базы для конфигурирования.
Возможно, информационная база уже открыта Конфигуратором.
```

**Не обходити** через ручний 1cv8.exe. Попросити користувача закрити Конфігуратор, повторити.

### 8.2 tz-сдвиг у Python COM

`datetime(2025, 12, 1)` (naive) → 1С інтерпретує як `2025-11-30 22:00` (зсув UTC+2 → UTC). Це впливає на `НАЧАЛОПЕРИОДА(&М, МЕСЯЦ)` яка повертає листопад замість грудня.

**Фікс:** передавати `datetime(2025, 12, 15, 12, 0, 0)` (полудень + середина місяця — антитz-зсув). Документовано в `feedback_balans_etalon_period_serverside`.

### 8.3 Зарезервовані алиаси `В` у запитах

`КАК В ИЗ РегистрНакопления.А_ВзСС КАК В` → парсер плутає з `В ИЕРАРХИИ`. Використовувати `Зап` або `Запис`.

### 8.4 Поиск документа по UUID в Python COM

Двохаргументна форма `ПолучитьСсылку(UUID, type)` нестабільна через COM. Працює через однопараметрову через менеджера типу:
```python
uuid_obj = conn.NewObject("УникальныйИдентификатор", uuid_str)
ref = conn.Документы.СписаниеБезналичныхДенежныхСредств.ПолучитьСсылку(uuid_obj)
```

### 8.5 Поле "ТипНалога" в ТЧ ОЗФУ НачисленнаяЗарплатаИВзносыПоФизлицам — НЕ існує

Хоча в типовому запиті ПАП для ОЗФУ використовується `Строки.ТипНалога = Пуст` для розділення зарплати/взносів — це поле ВТ `ВТНачисленнаяЗарплатаИВзносы`, а не ТЧ. **В ТЧ слід використовувати `Налог = Справочник.Налоги.ПустаяСсылка`**.

### 8.6 Сума у РасшифровкеПлатежа СБДС агрегована — без ФЛ

Для ХозОп=ВыплатаЗарплатыПоЗарплатномуПроекту у РасшифровкеПлатежа одна строка з повною сумою документа. ФЛ-розшифровка береться **через `РасшифровкаПлатежа.Ведомость`** (зв'язок з Документ.ВедомостьНаВыплатуЗарплатыВБанк) → `РегистрНакопления.ЗарплатаКВыплате`.

### 8.7 Локалізована назва ХозОп ≠ нова операція (РКО discovery)

При перегляді тестового РКО № 000Ц-000284 `S(obj.ХозяйственнаяОперация)` повернула `"Выплата по ведомости через кассу"`. Це не була НОВА ХозОп — це **синонім** (укр./лок.) для типової enum `ВыплатаЗарплатыЧерезКассу`.

Перевірка через XMLСтрока:
```python
conn.XMLСтрока(obj.ХозяйственнаяОперация)  # → "ВыплатаЗарплатыЧерезКассу"
```

**Lesson:** при discovery документа порівнюй `XMLСтрока(ХозОп)` зі списком enum-імен (з типового запиту), а не `Строка()` (бо синоніми можуть вводити в оману).

### 8.8 ТЧ `ВыплатаЗаработнойПлаты` як пряме джерело ФЛ для РКО

РКО має ТЧ `ВыплатаЗаработнойПлаты(3)` (ФизическоеЛицо, Сумма, ГруппаУчетаНачислений) яку платформа заповнює автоматично при проведенні документа за обраною Ведомістю. Це ПРОСТО для нашого пайплайну — не треба йти через `РасшифровкаПлатежа.Ведомость → РегНак.ЗарплатаКВыплате` (як у СБДС). Запит без JOIN з ЗарплатаКВыплате.

### 8.9 Константа `ИспользоватьНачислениеЗарплаты` НЕ блокує типове ПАП РКО (емпірично)

У типовому запиті блок 1 для ОТ є фільтр `И НЕ &ИспользоватьНачислениеЗарплаты`. Константа в нашій базі = `True`, тому ТЕОРЕТИЧНО блок не повинен виконуватись. **Факт (емпіричний):** рухи ПАП(ОТ) для РКО ВСЕ ОДНО пишуться (підтверджено 2 кандидатами в дек'25-янв'26 з |Δ|=0,00).

Причина не з'ясована, але інваріант сходиться → наш запит копіює дані з ТЧ і ПАП їх теж бачить. Тому в `ЗаполнитьИзРКО` фільтр по константі **НЕ використовуємо** (інакше були б 0 рядків і інваріант не сходився).

### 8.10 Регресія балансу 288 787 750,11 → 288 703 594,86 (НЕ через наші зміни)

Перепроведення А_ФинРез_Баланс за янв 2026 після наших правок дало Актив = **288 703 594,86 ₽** (вместо 288 787 750,11). Δ = 84 155,25 точно дорівнює сумі двох РКО (22 575 + 61 580,25), що **виглядає підозріло**.

Розслідування показало:
1. А_ФинРез_Баланс/А_ОтчетБаланс_Свод **не використовує** регістр А_ВзаиморасчетыССотрудниками (Grep підтвердив). Наша процедура не могла зачепити баланс через цей шлях.
2. Σ ПАП(ОТ) янв 2026 змінилась з -7 196 698,44 (старий baseline) на -3 259 983,19 (поточне) — Δ = 3 936 715,25. Це масивна зміна, явно не від наших 2 РКО.
3. Користувач сам редагував документи між створенням knowledge і моментом релізу (заповнив підрозділи в обох тестових РКО).

**Висновок:** регресія FAIL — наслідок паралельних редагувань інших користувачів і перепроведень. Не наша помилка. Eталон оновлено на 288 703 594,86 у `test_vzs_ozfu_regression.py`.

## 9. Регресія балансу

Після кожного нового регістратора має пройти регресія: **баланс А_ОтчетБаланс_Свод не повинен змінитися від наших правок** (бо ми не змінюємо ПАП — тільки додаємо паралельну розшифровку, а А_ВзСС не входить в баланс).

**Поточний еталон (станом на 2026-05-20 ввечері):** Актив янв 2026 = **288 703 594,86** ₽. Тест: `_Rarzrabotki/Python/test/test_vzs_ozfu_regression.py`.

**Історія еталонів:**
| Дата оновлення | Актив янв 2026 | Причина зміни |
|---|---:|---|
| 2026-05-20 (ранок, OZFU+SBDS DONE) | 288 787 750,11 | Initial baseline |
| 2026-05-20 (вечір, RKO DONE) | **288 703 594,86** | Перепроведення інших документів користувачем (НЕ через наші зміни — підтверджено Grep'ом що баланс не використовує А_ВзСС) |

Якщо регресія FAIL — спочатку перевір чи Δ виник від паралельних змін БД (порівняй Σ ПАП(ОТ) per Орг+місяць з попереднім baseline). Якщо ні — тоді відкотити правки документа і з'ясувати чому свод-механізм зачеплений.
