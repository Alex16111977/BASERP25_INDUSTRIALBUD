## 1. ОтражениеЗарплатыВФинансовомУчете (DONE 2026-05-20)

### 1.1 Призначення

Документ ОЗФУ (типовий, без префікса А_, але з кастомними доробками в нашій конфігурації) відображає **нарахування зарплати** у фінансовому/управлінському обліку. Дані формуються з системи Казна та з регістра `ВзаиморасчетыССотрудниками` (типового).

У ПАП пише **рух з Расход** (для пассивної статті ОТ це означає **рост обов'язку працедавця**). У наш А_ВзСС пишемо **Приход** (борг працедавця перед ФЛ ↑) — інверсія знаку, фінансистська семантика.

        ФизическоеЛицо + СуммаКВыплате

## 3. РасходныйКассовыйОрдер (DONE 2026-05-20)

### 3.1 Призначення

Документ РКО типовий — фіксує **видачу готівки з каси**. Якщо ХозОп = "Выплата зарплати по ведомости через кассу/раздатчиком/работнику" (синонім UI: "Выплата по ведомости через кассу") — це фактична виплата зарплати готівкою, борг працедавця перед ФЛ зменшується.

У ПАП пише **рух з Приход** (для пассивної статті ОТ це означає **зменшення зобов'язання**). У наш А_ВзСС пишемо **Расход** — інверсія, як для СБДС.

### 3.2 Джерело даних — пряма ТЧ ВыплатаЗаработнойПлаты

На відміну від СБДС (де потрібна зв'язка через Ведомість), РКО має ВЛАСНУ ТЧ `ВыплатаЗаработнойПлаты` з прямими полями:

```
РКО.ВыплатаЗаработнойПлаты:
  - ФизическоеЛицо  (СправочникСсылка.ФизическиеЛица)
  - Сумма           (Число)
  - ГруппаУчетаНачислений (СправочникСсылка.ГруппыУчетаНачисленийИУдержаний)
```

Платформа автоматично заповнює цю ТЧ при проведенні РКО за обраною Ведомістю.

**Підрозділ** — з шапки РКО (`ДокОбъект.Подразделение`). У типовому запиті ПАП блок 1 (line 3042) `Подразделение = НЕОПРЕДЕЛЕНО`, але ми беремо з шапки для drill-down. Інваріант сходиться: ми порівнюємо |Σ| per Регістратор (per Орг сумарно), а не per Подр.

### 3.3 Фільтри (1:1 з типовим запитом ПАП блок 1, line 3051-3055)

- `Д.ХозяйственнаяОперация В (ВыплатаЗарплатыЧерезКассу, ВыплатаЗарплатыРаздатчиком, ВыплатаЗарплатыРаботнику)`

### 3.8 Knowledge: чому НЕ використано фільтр `НЕ &ИспользоватьНачислениеЗарплаты`?

У типовому запиті блок 1 для ОТ є умова `И НЕ &ИспользоватьНачислениеЗарплаты`. Константа в нашій базі = `True`, тому ТЕОРЕТИЧНО блок не повинен виконуватись. Але **факт:** рухи ПАП(ОТ) для РКО ВСЕ ОДНО пишуться (підтверджено на 2 кандидатах).

Причина не з'ясована (можливо через інший кодовий шлях у конфігурації BAS ERP 2.5), але **інваріант все одно сходиться** — наш регістр пише точно те ж саме що ПАП(ОТ). Тому фільтр по константі ми НЕ використовуємо.

### 3.9 Розширення 2026-05-27: розрізна логіка для нашої ВКассу

**Зміна:** Процедура `ЗаполнитьИзРКО` отримала розвилку по `ТипЗнч(ДокОбъект.Ведомость)`:

- **Якщо `Ведомость = Документ.ВедомостьНаВыплатуЗарплатыВКассу`** (наша кастомна ВКассу з ТЧ `А_РасшифровкаВыплатыЗарплатаПоФизлицам`) → **НОВА** гілка:
  - Джерело: ТЧ `Ведомость.А_РасшифровкаВыплатыЗарплатаПоФизлицам` (13 полів після уніфікації з ТЧ.Зарплата)
  - Підрозділ у регістрі: `Рш.Подразделение.А_Подразделение` (КАСТОМНИЙ реквізит справочника `ПодразделенияОрганизаций` — конвертація ПодрОрг → СтрПредпр)
  - Σ = `СУММА(Рш.КВыплате)`
  - Групування per (Орг, СтрПредпр, ФЛ) → **N рухів регістра** замість 1 шапочного рядка
- **Інакше** (Ведомість пуста або інший тип) → стара логіка (ТЧ.ВыплатаЗаработнойПлаты + 3 хозоперації) — без змін, зворотна сумісність.

**Ключова особливість:** до зміни всі рухи РКО йшли на ОДИН Підрозділ з шапки. Після зміни — рухи розрізняться по N СтрПредпр з рядків А_Расшифровки. Це дозволяє звітам управлінського балансу деталізувати "Оплата труда" по фондах/техніці.

**Точкова навігація `Рш.Подразделение.А_Подразделение`** — *кастомний* реквізит справочника `ПодразделенияОрганизаций` (не типове `Подразделение` — воно тут відсутнє). Це специфіка цього проекту (префікс `А_`).
