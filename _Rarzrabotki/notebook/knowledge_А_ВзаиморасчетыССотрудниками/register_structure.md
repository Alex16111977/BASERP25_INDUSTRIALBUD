## 2. Виміри (5)

> ⚠️ **Оновлено 2026-05-31 / 2026-06-01:** фінансист додав 2 виміри — `ФормаPL` (розділення офіційна/управлінська ЗП) і `ОрганизацияБухгалтерия` (юр.особа-платник офіційної частини). Було 3.

| # | Вимір | Тип | Заповнення |
|---|---|---|---|
| 1 | `Организация` | Справочник.Организации | завжди (RLS, індекс) |
| 2 | `ФормаPL` | Перечисление.А_ФормыPL (Форма1/Форма2) | завжди (з ТЧ-джерела руху) |
| 3 | `Подразделение` | Справочник.СтруктураПредприятия | завжди |
| 4 | `ФизическоеЛицо` | Справочник.ФизическиеЛица | завжди (головна аналітика drill-down) |
| 5 | `ОрганизацияБухгалтерия` | Справочник.Организации | **тільки для Форма1** (Форма2/ЕСВ — порожньо) |

**Чому такий набір?**
- `Организация` обов'язковий (доступ по організаціях через RLS); індексований.
- `ФизическоеЛицо` — головна аналітика drill-down (для чого і створювався регістр).
- `Подразделение` — фінансовий розріз балансу.
- `ФормаPL` — Форма1 (бух/офіційна, банк) / Форма2 (управ/ЦПХ, каса). Див. [knowledge_А_ОтражениеЗПпоКазне/17_formapl_split.md](../knowledge_А_ОтражениеЗПпоКазне/17_formapl_split.md).
- **`ОрганизацияБухгалтерия`** — яка юр.особа несе офіційне (Форма1) зобов'язання. Заповнюється: у дочірньому ОЗФУ — `СоздатьДокументОтражениеЗарплатыВФинансовомУчете` (з «Зарплата управл», мульти-орг → домінантний); у СБДС — `Д.А_ОрганизацияБухгалтерия`; у ПередачаНачислений — `Н.ОрганизацияБухгалтерия`. РКО (Форма2) — порожньо. Див. [knowledge_А_ОтражениеЗПпоКазне/18_vzss_uderzhanie_ndfl_align.md](../knowledge_А_ОтражениеЗПпоКазне/18_vzss_uderzhanie_ndfl_align.md).

**Дозволи RLS** (з `Ext/ManagerModule.bsl`):
```bsl
Процедура ПриЗаполненииОграниченияДоступа(Ограничение) Экспорт
    Ограничение.Текст =
    "РазрешитьЧтениеИзменение
    |ГДЕ
    |    ЗначениеРазрешено(Организация)
    |    И ЗначениеРазрешено(ФизическоеЛицо)";
КонецПроцедуры
```

Доступ розрізає БД по орг + фіз.особі (стандартний механізм БСП УправлениеДоступом).

## 3. Ресурси (1)

| Ресурс | Тип | Значення |
|---|---|---|
| `СуммаВзаиморасчетов` | Число(15, 2, ±) | сума в валюті взаєморозрахунків |

**Чому одна сума, не дві (приход/расход)?** Balance-регістр сам розрізняє Приход/Расход через `ВидДвижения` стандартного реквізиту запису. Σ signed = Σ(Приход.Сумма) − Σ(Расход.Сумма).

**Знак суми у запису** — завжди **позитивний** (≥0). Напрямок (приход чи расход) — у `ВидДвижения`.

## 6. RecordSetModule — `ПередЗаписью`

Файл: `AccumulationRegisters/А_ВзаиморасчетыССотрудниками/Ext/RecordSetModule.bsl`

```bsl
Процедура ПередЗаписью(Отказ, Замещение)

    Если ЗарплатаКадры.ОтключитьБизнесЛогикуПриЗаписи(ЭтотОбъект) Тогда
        Возврат;
    КонецЕсли;

    // нулевые движения не пишем
    НулевыеСтроки = Новый Массив;
    Для Каждого Запись Из ЭтотОбъект Цикл
        Если Запись.СуммаВзаиморасчетов = 0 Тогда
            НулевыеСтроки.Добавить(Запись);
        КонецЕсли
    КонецЦикла;
    Для Каждого НулеваяСтрока Из НулевыеСтроки Цикл
        ЭтотОбъект.Удалить(НулеваяСтрока);
    КонецЦикла;

    // Приводим периоды к началу месяца.
    Для Каждого Запись Из ЭтотОбъект Цикл
        Запись.Период = НачалоМесяца(Запись.Период);
    КонецЦикла;

КонецПроцедуры
```

**Поведінка:**
1. Інтеграція з механізмом БСП ЗарплатаКадры (skip-flag для відключення бізнес-логіки)
2. Відкидає рядки з `СуммаВзаиморасчетов = 0` (наприклад якщо `ЗаполнитьИзОтраженияЗП` згенерував порожній рядок)
3. Нормалізує `Період → НачалоМесяца` (для агрегації балансу по місяцях, а не по днях)

**Наслідок для коду наповнення:** у `ManagerModule` процедурах `ЗаполнитьИз<Тип>` достатньо передати `Запись.Период = ДокОбъект.Дата` — RecordSetModule сам приведе до НачалоМесяца. **Виняток:** `ЗаполнитьИзНачальнойЗадолженности` передає `ДокОбъект.Месяц` (а не `Дата`), бо в документа вводу остатків `Дата` (тех.дата вводу) і `Месяц` (період остатку) розходяться — типове проведення пише `ВзаиморасчетыССотрудниками` з періодом=`Месяц`, наш регістр мусить збігатися. Див. [registratory_done.md §4](registratory_done.md).

## 7. ManagerModule — структура

Файл: `AccumulationRegisters/А_ВзаиморасчетыССотрудниками/Ext/ManagerModule.bsl`

```
#Если Сервер Или ТолстыйКлиентОбычноеПриложение Или ВнешнееСоединение Тогда

  // Стандартные подсистемы.УправлениеДоступом
  Процедура ПриЗаполненииОграниченияДоступа(Ограничение) Экспорт ... КонецПроцедуры
  // Конец СтандартныеПодсистемы.УправлениеДоступом

  #Область СлужебныеПроцедурыИФункции
    #Область ПервоначальноеЗаполнениеИОбновлениеИнформационнойБазы
      Процедура ЗаполнитьОрганизацию() Экспорт ... КонецПроцедуры  // bootstrap скрипт (одноразовий)
    #КонецОбласти
    #Область ЗаполнениеДвижений
      Процедура ЗаполнитьИзОтраженияЗП(ДокОбъект) Экспорт ...            // 5 з 7 регістраторів —
      Процедура ЗаполнитьИзСписанияБезнал(ДокОбъект) Экспорт ...         // по одній процедурі
      Процедура ЗаполнитьИзРКО(ДокОбъект) Экспорт ...                    // на кожний тип
      Процедура ЗаполнитьИзПередачиНачислений(ДокОбъект) Экспорт ...     // (DONE 2026-05-29)
      Процедура ЗаполнитьИзНачальнойЗадолженности(ДокОбъект) Экспорт ... // (DONE 2026-06-01; період=Месяц)
      // ПКО та ПостБезнал — НЕ РЕАЛІЗУЮТЬСЯ (рішення фінансиста 2026-05-20)
    #КонецОбласти
  #КонецОбласти

#КонецЕсли
```

**Конвенція імен:**
- Прибрав префікси типу `Документа.` — імена короткі і виразні (`ЗаполнитьИзОтраженияЗП`, `ЗаполнитьИзСписанияБезнал`, `ЗаполнитьИзРКО`, etc.)
- Параметр `ДокОбъект` — типу `ДокументОбъект.<Тип>` (передається з `ЭтотОбъект` у виклику)
- Кожна процедура має заголовок-коментар з Σ-інваріантом, ланцюгом даних, фільтрами, тестом

**Спільний контракт усіх `ЗаполнитьИз<Тип>`:**
1. `ДокОбъект.Движения.А_ВзаиморасчетыССотрудниками.Записывать = Истина;`
2. `ДокОбъект.Движения.А_ВзаиморасчетыССотрудниками.Очистить();`
3. Якщо `НЕ ДокОбъект.Проведен` → `Возврат` (порожній набір записаний → очищення)
4. Запит з фільтрами специфічними для цього документа
5. Цикл `Для Каждого СтрТЗ Из Результат Цикл` → `Движения.А_ВзСС.Добавить()`
6. `Запись.Период = ДокОбъект.Дата` (буде нормалізовано RecordSetModule) — **виняток** `НачальнаяЗадолженностьПоЗарплате`: `ДокОбъект.Месяц` (період остатку ≠ тех.дата вводу)
7. Знаки — фінансистські (Приход=борг ↑, Расход=борг ↓), не "ПАП-семантика"

Платформа сама запише `Движения.А_ВзСС` у складі стандартного циклу проведення документа.

## 8. Точка інтеграції в кожному документі-регістраторі

В ОбработкаПроведения кожного документа-регістратора (7 підписаних; 5 реалізовано) в самому кінці додається ОДНА строка:

```bsl
Процедура ОбработкаПроведения(Отказ, РежимПроведения)

    // ...типова логіка документа (типове проведення)...

    // Кастомне наповнення А_ВзаиморасчетыССотрудниками (розшифровка ОТ по ФЛ+Подр).
    // Σ-інваріант per (Орг,Подр) = ПАП(Статья=ОТ, Источник=Пуст) per Регистратор.
    РегистрыНакопления.А_ВзаиморасчетыССотрудниками.ЗаполнитьИз<Тип>(ЭтотОбъект);

КонецПроцедуры
```

**Чому такий патерн (а не event-subscription / CFE розширення):**
- ✅ Прозоро: розробник бачить виклик у звичному місці ОбработкаПроведения
- ✅ Єдина транзакція: рухи нашого регістра записуються разом з типовими ПАП, ВзСС, тощо
- ✅ Стандартна ідемпотентність: при перепроведенні документа платформа сама видаляє старі рухи усіх регістраторних регістрів (включно з нашим) і записує нові
- ❌ Альтернатива через event-subscription `OnWrite` — менш прозоро, потребує НаборЗаписей.Записать() поза транзакцією, регресія складніша
