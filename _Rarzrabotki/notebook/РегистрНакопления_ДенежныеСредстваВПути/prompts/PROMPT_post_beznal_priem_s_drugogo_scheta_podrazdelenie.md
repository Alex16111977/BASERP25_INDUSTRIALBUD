# Промт — ПостБезнал «Поступление с другого счёта»: Подразделение отправителя в РНДС.ВПути

> Зеркало сегодняшней (2026-06-14) доработки **ПКО «Поступление денежных средств из другой кассы»**
> (`Python/test/edit_pko_priem_podrazdelenie.py`). Теперь то же самое — для **безналичного** перевода
> между счетами «Поступление с другого счёта», чтобы баланс «деньги в пути» сворачивался в ноль
> **по реквизиту Подразделение**.

## 🟢 СТАТУС 2026-06-14 — РЕАЛИЗОВАНО ЗАЩИТНО (фикс = no-op на текущей базе)

**ЭМПИРИЧЕСКАЯ ПРОВЕРКА (все 2100 проведённых «Поступление с другого счёта»):** у **2100/2100** документов
`Подразделение` шапки **УЖЕ РАВНО** Подразделению отправителя (парного Списания) — пара найдена у всех,
расхождений 0. То есть движения ВПути.Расход и ПАП «в пути» **уже** падают на отправителя, и транзит
безнала **уже сворачивается по подразделению**. Премиса ниже («шапка получателя ≠ отправитель») для этой
базы **не подтвердилась** (в отличие от ПКО, где шапка = получатель).

**Решение (по выбору пользователя): внедрено ЗАЩИТНО** — 3 правки кода применены и загружены (smoke PASS,
no-regression: ПКО-плечо цело, процедура заполнения работает), НО:
- фикс сейчас **no-op** (`А_ПодразделениеОтправитель` всегда = шапке);
- **бэкфилл 2099 и массовый перепровод НЕ требуются и НЕ выполнялись** (нулевой эффект на баланс);
- правки оставлены как защита: если появится документ с шапкой ≠ отправитель — он самозаполнится (хук обмена)
  и свернётся корректно.

Диагностика: `Python/test/diag_postbeznal_header_vs_sender.py` (2100/2100 header==sender).

## TL;DR

`РегистрНакопления.ДенежныеСредстваВПути` — это транзитный (клиринговый) счёт между двумя плечами
внутреннего перевода денег. Чтобы остаток «в пути» сворачивался в **ноль по каждому Подразделению**,
оба плеча обязаны нести **одно** подразделение — **отправителя**.

- **Списание** «Перечисление на другой счёт» пишет РНДС.ВПути **Приход** с `Подразделение = шапка Списания` (= отправитель). Это уже сделано (пилот №3).
- **Поступление** «Поступление с другого счёта» пишет РНДС.ВПути **Расход**, но берёт `ДанныеДокумента.Подразделение` (стандартная шапка Поступления). У получателя шапка часто = его **собственное** подразделение (или «Главный офис»), а не отправителя → расход уезжает не туда → пара **не сворачивается** по Подразделению.

**Решение (как в ПКО):** на стороне Поступления брать `А_ПодразделениеОтправитель` (с fallback на шапку),
и заполнять этот реквизит по **парному проведённому Списанию**.

**ТРИ правки кода + бэкфилл истории** (как у ПКО — задача = 3 правки, не 2!):
1. `ManagerModule.bsl` — блок 2 (`ПоступлениеДенежныхСредствСДругогоСчета`): `Подразделение = ВЫБОР(А_ПодразделениеОтправитель, иначе шапка)`.
2. `ObjectModule.bsl` — процедура `А_ЗаполнитьПодразделениеОтправителяПоСписаниюБезнал()` + вызов из обмена-казны.
3. **`DataProcessors/ДвиженияАктивовПассивов/Ext/ManagerModule.bsl` — ПАП-проекция упр.баланса** (ОБЯЗАТЕЛЬНО, иначе баланс НЕ свернётся!): в каскаде `МАКСИМУМ(ВЫБОР…)` процедуры `ДобавитьТекстЗапросаДенежныеСредстваВПути` добавить приоритетную ветку `ДокПоступление.А_ПодразделениеОтправитель` перед `ДокПоступление.Подразделение`. См. **Часть 4**.
4. Бэкфилл 2099 исторических документов (Python COM) + смоук, массовый перепровод — пользователю.

> ⚠️ **Почему 3 правки, а не 2** (урок ПКО 2026-06-14): строка `ПрочиеАктивыПассивы` со статьёй «Денежные средства в пути» формируется НЕ из движения регистра ВПути, а проекцией управленческого баланса, которая берёт Подразделение из ШАПКИ документа-регистратора. Правка только движения ВПути (п.1) исправит регистр ВПути, но ПАП «в пути» останется на получателе → баланс не свернётся, а smoke даст ЛОЖНЫЙ PASS. Часть 4 обязательна.

**Тестовый документ:** `Поступление безналичных ДС 00DL-006964 от 01.12.2025 16:48:03`, **9 641 228,35 UAH**,
ХозОп «Поступление ДС с другого счета», парное `Списание 000Ц-000090`, отправитель — **Строительство**.
У него `А_ПодразделениеОтправитель` уже заполнен вручную (Строительство) → удобный эталон для проверки кода
ManagerModule (бэкфилл на нём не нужен, нужен на остальных 2099).

## Бухгалтерская суть (зачем)

Перевод денег с депозитного счёта на расчётный внутри одной организации:

| Плечо | Документ | Движение РНДС.ВПути | Подразделение (как надо) |
|---|---|---|---|
| Отправитель | `Списание 000Ц-000090` «Перечисление на другой счёт» | **Приход** +9 641 228,35 | Строительство |
| Получатель | `Поступление 00DL-006964` «Поступление с другого счёта» | **Расход** −9 641 228,35 | Строительство |

Свёртка по Подразделению: `Строительство: +9 641 228,35 − 9 641 228,35 = 0` ✅.

Если Поступление возьмёт подразделение **получателя** (напр. «Главный офис»):
`Строительство: +9 641 228,35` (висит вечно), `Главный офис: −9 641 228,35` (висит вечно) ❌ —
ровно это даёт ~56 групп `Расхождение=Истина` по статье «Денежные средства в пути» в `А_ОтчётБаланс_Свод`.

**Вывод (подтверждён пользователем):** источник Подразделения для плеча Поступления —
**`А_ПодразделениеОтправитель`** (подразделение отправителя), а не шапка получателя.

## Часть 2 — правка ObjectModule (заполнение отправителя)

Аналог `А_ЗаполнитьПодразделениеОтправителяПоРКО()` из ПКО. Добавить процедуру и вызвать её
из обмена-казны (где уже формируются казначейские реквизиты), перед `А_ОбработанКазна = Истина;`.

### Матчинг Поступление → Списание (по паре счетов, не по документу!)

Одно Списание может породить несколько Поступлений (и наоборот) — матчить **построчно по паре счетов**:

| Поступление | = | Списание «Перечисление на другой счёт» |
|---|---|---|
| `Организация` | = | `Организация` |
| `БанковскийСчет` (получатель) | = | `БанковскийСчетПолучатель` |
| `БанковскийСчетОтправитель` (источник) | = | `БанковскийСчет` (свой счёт Списания) |
| `СуммаДокумента` | = | `СуммаДокумента` |
| `Валюта` | = | `Валюта` |
| `Дата` | ≥ | `Дата` |

Копировать: `Списание.Подразделение → А_ПодразделениеОтправитель`,
`Списание.Ссылка → А_СписаниеБезналичныхДенежныхСредств`.

## Часть 3 — бэкфилл 2099 исторических

`А_ПодразделениеОтправитель` пуст у 2099 проведённых документов; exchange-хук на них не сработает ретроспективно.
Нужен **Python COM-скрипт** `Python/test/backfill_post_beznal_otpravitel.py`, который для каждого пустого
документа применяет тот же матчинг и записывает `А_ПодразделениеОтправитель` + `А_СписаниеБезналичныхДенежныхСредств`.

**Порядок:**
1. **Смоук**: применить к 00DL-006964 (уже заполнен — должен быть идемпотентным/STOP) + к 1-2 пустым из той же выборки → verify РНДС.ВПути после перепровода = подразделение отправителя, Σ не изменилась.
2. **Запись поля** ≠ перепровод движений: после установки `А_ПодразделениеОтправитель` нужно перепровести документ, чтобы блок 2 MM подхватил новое значение в РНДС.ВПути.
3. **Массовый перепровод 2099** — отдать **пользователю** (UI 1С Enterprise или ревьюнутый COM-скрипт, который запускает пользователь). Память `feedback_user_reposts_history_self`. COM здесь безопасен (нет РСКПС/РСППС), но всё равно встроить safety-check как в `pilot_post_03_repost.py`.

> Запись реквизита через COM: `ОбменДанными.Загрузка = Истина`, `Записать()` без проведения для установки
> поля; затем отдельный проход `Записать(РежимЗаписиДокумента.Проведение)`. См. память

## Часть 4 — ПАП-проекция управленческого баланса (ОБЯЗАТЕЛЬНО)

Строка `РегистрНакопления.ПрочиеАктивыПассивы` со статьёй «Денежные средства в пути» формируется проекцией
упр.баланса, которая **игнорирует измерение регистра ВПути** и берёт Подразделение из ШАПКИ
документа-регистратора через каскад `МАКСИМУМ(ВЫБОР…)`.
