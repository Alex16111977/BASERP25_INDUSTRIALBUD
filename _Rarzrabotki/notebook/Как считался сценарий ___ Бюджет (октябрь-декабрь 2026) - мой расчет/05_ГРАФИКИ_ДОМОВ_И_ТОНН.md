## 0. Итог в одном абзаце

План («План робіт на квартал») даёт **8 / 8 / 3 = 19 домов** (окт / ноя / дек). Реалистичный график — **5 / 8 / 4 = 17

отгрузки каждого дома выводится из ВРМ: «часы до готовности» (порог − освоено на 30.09) раздаются домам по порядку
номеров (FIFO) из месячной мощности цеха, равной EV-часам сентября по проекту (IRC 1 139,094 ч, ООН Админ 1 554,666 ч).
У ООН 2026 график задан в коде вручную (2/3/3/2), у санвузла — ноябрь. Тонны МК в обоих графиках одинаковые и равны
плану (Каменец 48,463 т окт + 18,14 т дек, Кривий Ріг 6,654 т окт). В 1С загружен **реалистичный** график.
Операционный чистый поток квартала: реалистичный **−10 590 062,11**, план **−7 494 993,07** (план лучше на
3 095 069,04). Разница почти целиком в поступлениях, которые при реалистичном графике переезжают за горизонт (январь 2027+).

**Какой темп взят.** Код берёт **сентябрь по проекту** (`raschet.py:165–166`), а не максимум по месяцам. Для цеха в

Причина выбора записана в истории сессии (решение 1): мощность меряется EV-часами, а не домами, потому что дома разных
проектов разной трудоёмкости (IRC 30 м — 640 ч, ООН Админ — 2 150 ч). Отброшенные варианты:
- общий «потолок домов в месяц» — 6 домов IRC 15 м в августе это маленькие дома, такой потолок завышает;
- рост +15–20 %/мес ко всему цеху — фактом не подтверждён.

**Docstring устарел — не «чинить» код по нему.** Docstring функции `драйверы()` (`raschet.py:98`) говорит: «темп цеха
по EV-часам ВРМ, лучший месяц + обоснованный рост». Код (`raschet.py:165–166`) берёт сентябрь по проекту, без роста и
без выбора лучшего месяца. Верное правило — то, что в коде: сентябрь по проекту без роста. Так записано в решении 1
истории сессии, где рост +15–20 % прямо отброшен.

## 4. Пороги отгрузки и готовность домов на 30.09 (`vypolnenie_rabot.json["houses"]`)

`plan_h` — сумма `ПланЧасыМодуля` по ТЧ `Работы` последнего проведённого `Документ.А_ВыполнениеРаботМодулей` по дому.
`done_h` — сумма `ПланЧасыМодуля × Процент / 100`. Для IRC 30 м и ООН Админ дата снимка 2026-09-30.

- **IRC 30 м: порог 100 %** (`raschet.py:168`, аргумент `1.0`). Основание: №1 и №2 уехали при `done_h = plan_h = 639,99`.
- **ООН Админ: порог 66,67 %** (`raschet.py:170–171`): `thr_adm = 1 433,3332 / 2 149,9998 = 0,666666…` (ровно 2/3).
  Основание: №1 отгружен 17.09 при 1 433,3332 из 2 149,9998 ч. Остаток часов, `plan_h − max(thr, done_h) =
  716,6666 ч` на дом, считается доделками на объекте и уходит в ЗП **следующего месяца после отгрузки**
  (`raschet.py:387`, 401–404; у отгруженного №1 — в октябрь, `raschet.py:389–393`).

Справочно, IRC 15 м (000000008, все 6 отгружены в августе): последний снимок ВРМ 19.08 — 416,96 из 673,96 ч (61,9 %).
В график IV кв. эти дома не входят.

## 5. Алгоритм FIFO реалистичного графика (`raschet.py:130–144`)

```
остаток_мес = темп; мес_i = 0                      # мес_i = 0 → октябрь 2026
для дома h по возрастанию номера (стр. 121):
    если h отгружен: ship_real = "2026-09"; дальше
    need = max(0, thr − done_h)                     # часы до порога
    пока need > 1e-6:
        взять = min(need, остаток_мес); need −= взять; остаток_мес −= взять
        если need > 1e-6: мес_i += 1; остаток_мес = темп    # месяц исчерпан → следующий
    ship_real = сдвиг("2026-10", мес_i)            # месяц, в котором израсходован последний час
    need_h = max(0, thr − done_h)
```

Свойства, которые важно знать, прежде чем менять метод:
1. **Последовательно, а не параллельно.** Вся мощность месяца идёт на самый ранний по номеру дом, пока он не дойдёт
   до порога. На деле №4–7 строятся одновременно (у всех по 7,07 %). Модель даёт самые ранние даты первым домам и
   самые поздние — последним.
2. **Дом уезжает в месяце, когда израсходован его последний час.** Дом, чьи часы растянулись на октябрь и ноябрь, едет
   в ноябре.
3. **Неиспользованная мощность не переносится и не передаётся другому проекту.** Мощности IRC и ООН Админ независимы.
4. **Мощность ООН 2026 не вычитается из цеха.** ООН 2026 в ВРМ нет, его дома идут поверх 2 693,76 EV-ч/мес.
   Это риск двойного счёта мощности. В записке 07 он явно не учтён. Близкий по смыслу риск 2 записки 07 — другой:
   реально ли ООН 2026 строится (в ВРМ нет, ЗП по проекту в Казне 0).

## 13. Как пересчитать или изменить метод графиков

**Пересчёт на новых данных.** Снимки обновляются скриптами `03` (отгрузки), `04` (план), `05` (ВРМ), затем расчётчик.
Перед этим проверить:
- **`n_ship` считает все отгрузки с 01.09** (`raschet.py:123`). Если в снимке будут октябрьские отгрузки, они тоже
  попадут в «отгружено», получат `ship_real = "2026-09"` (`raschet.py:133`), а поступления — «100 % в октябре» с
  индексом даты по номеру (`raschet.py:453`). Для нового периода границу `"2026-09-01"`, `ПЕРВЫЙ` и `"2026-09"`
  надо сдвинуть.
- **Темп берётся по жёстко заданному месяцу `"2026-09"`** (`raschet.py:165–166`). При новом снимке его надо менять
  явно.
- **Отгруженными считаются первые по номерам дома.** Если уедет не следующий по номеру дом, нужна другая привязка
  (по ВРМ `done_h ≥ thr` или по названию заказа).
- **Другие зашитые месяцы и даты, связанные с графиком** (тоже менять при переносе на новый период):
  - `raschet.py:175` — месяцы `реал_оон` (2026-10 … 2027-01);
  - `raschet.py:190` — месяц санвузла `"2026-11"`;
  - `raschet.py:203–204` — факт тонн МК за `"2026-09"`;
  - `raschet.py:227` — транспорт Админа, факт за `"2026-09"`;
  - `raschet.py:247–248` — ЗП Каменца 08–09, рейсы Каменца за 09;
  - `raschet.py:255–258` — тонны и ЗП Кривого Рога 07–08, рейсы за 07;
  - `raschet.py:273` — `"2026-09-01"`: профиль IRC строится по отгрузкам до сентября;
  - `raschet.py:452` — `h["ship_real"] == "2026-09"` (100 % в октябре для отгруженных IRC);
  - `raschet.py:465–466` — 50 % отгруженного Админа = `сдвиг("2026-09", 2)`, в тексте зашиты «17.09 / 29.09»;
  - `raschet.py:520–521` — август (тонны) и сентябрь (оплаты) у Кривого Рога.

  Полный перечень зашитых дат расчётчика и скриптов — `09_КАК_ПЕРЕСЧИТАТЬ_И_ИЗМЕНИТЬ.md`, §8.5.
