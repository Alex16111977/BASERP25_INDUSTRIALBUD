### 2.1. Снимок данных — условие сравнения с числами прототипа

Числа ниже посчитаны на снимке **03.10.2026 10:52**: 4 800 движений 20/22/26/28, 503 строки поступлений
(`data/demo_svyaz_ss_30m.json` → `snapshot`). Перед приёмкой проверяются контрольные суммы снимка (нетто, BuhBud,
`caveats[14]`):

| Контроль | Значение 03.10 |
|---|---|
| Списано №1 / №2 / №3 | 679 256,57 / 608 574,70 / 100 669,28 |

| Склад проекта «ІБ _МД IRC 2026» | 3 044 261,07 |

- Суммы совпали → ожидаемые значения = таблица §2.2 до копейки.
- Не совпали (идут новые списания на №3, склад проекта меняется каждый день) → эталон пересчитывается прототипом
  (`final3.py`) на замороженной фикстуре этапа 0, и движок сравнивается с ним. Кейсы по №1 и №2 (отгружены 22.09 и
  01.10) должны совпасть с 03.10 при любом снимке, если не было исправлений задним числом. Исключение — ЦСП 9 и ОСБ 50
  на складе №2 (99 649,86 с ПДВ, `caveats[16]`): их досписание или перемещение изменит итоги К9–К10, но не К1–К8.

**База денег.** Прототип считает факт как нетто × (1 + ПДВ партии), как бюджет v3. РК и Шахматка — по ставке карточки
(×1,2) (`caveats[8]`). Поэтому:
- количества сравниваются точно везде;
- деньги точно сравниваются в Python-движке на базе прототипа;
- в отчёте BuhBud деньги сравниваются с эталоном, пересчитанным прототипом на базе ставки карточки. Например, «понад
  норму» РК №9 / №11 / №12 = 62 083,73 / 89 463,43 / 9 148,46, а у прототипа 60 586,35 / 87 081,30 / 9 872,03.

### 2.3. Инварианты (проверяются автоматически в каждом прогоне приёмки)

| # | Инвариант | Как проверить | Эталон |
|---|---|---|---|
| И1 | **Регрессия: без связей = текущему** | Пустая ТЧ (или все связи неподтверждены, параметр выключен) → вариант «за зв'язками» построчно равен `ШахматкаКонтроль`; РК в обоих режимах даёт одинаковые ТЧ | Прототип «как сейчас»: Докупити 1 293 881,78 = кэш f41 до копейки; F + Лежить по 127 ОН на №1–№2 = РК №9 / №11 (`caveats[7]`, `caveats[15]`). Отчёт: «Понад» при N > 0 = 68 436,65 (17 236,37 / 42 182,47 / 9 017,81, `totals.now.ponad_yak_u_zviti_N_bilshe_0*`). Сверять И1 с самим отчётом, а не с видом прототипа: на сборках они расходятся (септик №1: отчёт 7 шт, прототип 1), [06](06_proekt_mehanizma.md) §4.1 |
| И2 | **Сохранение суммы факта** | По каждому классу (списано на дом, лежит на доме, склад проекта), в количестве и деньгах: Σ по строкам + поза СС + МШП + пулы ОН + складові + надлишок = Σ по карточкам | Прототип: равенство до копейки (`caveats[15]`) |
| И3 | **Ни одна карточка дважды** | Для каждой карточки Σ взятых долей = 1; полуфабрикат 00-00023184 не даёт прямого вклада; сборки на доме посчитаны один раз | Прототип: «одна картка двічі не рахується» (`caveats[15]`), N:1 только у труби 110/3000 |
| И4 | **Норма не меняется** | Σ норм строк = Σ `Комплектующие.Сумма` | 1 009 864,74 на дом, 7 069 053,18 на 7 домов (`card`) |
| И5 | **Тождество строки** (незавершённые дома) | N × домов = Σ min(F + S, N) + Перемістити + Докупити | по каждой строке, расхождение 0 |
| И6 | **Перезагрузка не рвёт связи** | Перезагрузка СС из Excel в памяти (с откатом транзакции) → 0 осиротевших связей, Σ `Сумма` неизменна | — |
| И7 | **Обмен не задет** | После записи СС `А_СтруктураСебестоимости` в ERP получает те же `Комплектующие`; ТЧ связей в ERP не появляется; журнал обмена без ошибок | — |
