    - Вариант (в), ERP считает сам: вторая копия логики и зеркало связей в ERP.

## 2. Атрибуция факта узлам (обратное разузлование)

### 2.1. Постановка

**[В]** «Норма дома = разузлованная спецификация» ([M1] §6.4): каждая карточка-лист получает норму и ключ «строка СС / путь узла». Факт приходит как плоский список карточек из КН дома. Нужно обратное отображение «карточка → строка / узел». Оно однозначно, если карточка связана с одной строкой спецификации. Если строк несколько, нужно правило.

**[Ф]** Почему считать на уровне дома, а не по документу:
1. **Норма задана на дом**, а РК делит её на «Виробничий» и «Відвантажено» по складам.
2. **Карточка дробится по документам.** На 30 м №1 так раздроблены 16 из 151 карточки вне служебных сборок. Например, саморіз 4,8х35: 1 250 шт в 148 и 500 шт в 158; 6 карточек — норма + понад в «Виробничий» (`kn_rows.json`).
3. **Деление «в нормі / понад» в РК — по ОН**, а не по строкам спецификации (`RKO` `ЗаполнитьАнализ` 1766–1866, [R2] §1.4). При атрибуции по спецификации оно меняется (§2.4, §2.5).
4. **Дублей карточки внутри одной КН нет** (0 из 337 строк), поэтому пара (КН / СборкаТоваров, карточка) — однозначный ключ для обратного распределения денег.

### 2.7. Рекомендуемый алгоритм (вывод)

```
Вход: дом Д; спецификация дома (вариант, иначе эталон) — разузлованная плоская таблица листьев
      Л = {КлючСтрокиСС, ПутьУзла, Номенклатура, Норма (ед. карточки), Приоритет связи, Этап};
      связи карточка → лист (роль, коэффициент, приоритет) — те же, что у РК;
      факт Ф = строки КН РК дома (кроме строки-полуфабриката) + детали служебных КН дома (только старые дома),
      ключ (КН, Номенклатура), количество в ед. карточки.
1. Свести Ф по Номенклатуре на дом (Σ по всем КН), запомнить доли каждой КН.
2. Для каждой карточки К с кандидатами-листьями L(К):
     нет кандидатов         → псевдоузел «Поза специфікацією» (или «МШП» для документов МШП);
     один кандидат          → весь факт туда; превышение над нормой — категория «понад нормою»;
     несколько кандидатов   → в пределах Σ норм: сначала листья с явным приоритетом связи (по возрастанию),
                              при равных приоритетах — пропорционально норме листьев;
                              превышение сверх Σ норм — пропорционально норме, категория «понад нормою».
   Группы взаимозаменяемых карточек на группу листьев («Гвинтові кріплення») — как одна «карточка»:
     Σ количества группы раскладывается на листья по доле нормы; состав карточек в каждом листе = состав группы.
3. Обратно на документы: количество (лист, К) делится между КН по их долям из шага 1 → (КН, К, лист, категория, кол-во).
4. Деньги (в ERP): стоимость пары (СборкаТоваров = КН по UUID, К) из СебестоимостьТоваров, Расход,
   × кол-во строки / Σ кол-во пары. Если месяц не закрыт — стоимость 0 и признак «оценка не закрыта».
```

**[В]** Почему так:
- П1 по умолчанию — повторяемость и отсутствие произвола. Явный приоритет — когда технолог знает, куда идёт аналог. Отдельная категория превышения — чтобы оно не пряталось в узлах.
- Деньги ERP — сходимость с PL. Количество BuhBud — потому что там связи и норма.

Порядок сортировки в шаге 2 зафиксирован полностью: приоритет → `КлючСтрокиСС` → `Номенклатура.Код`. Тогда при повторной загрузке даже П2 детерминирован.

## 3. Варианты доставки в ERP и регистратор движений

### 3.1. (а) Новое ПКО обмена «РК → новый документ ERP А_…»

**[Ф]** Что потребуется:
- `РасчетКомплектаций` в `XR` и в `RegistrationRules.xml` (сейчас 0 вхождений, [R3] §0 п. 11);
- новая ТЧ атрибуции в РК (BuhBud), ПКО и ПВД в `XR`, регистрация РК в плане обмена BuhBud;
- живые правила загружены в базы, а не только в файл ([06](../../06_proekt_mehanizma.md) стр. 51, память `kazna_erp_pravila_obmena_zhivut_v_baze.md`), поэтому правка нужна в обеих базах;
- на стороне ERP — образец `СборкаТоваров`: ПКО ставит `А_Обработан = Ложь`, ERP в `ПередЗаписью` вызывает «…ПослеОбмена» (`STO` 225–251). Правило уважает `А_Необновлять` (`XR` 14851).

**[В]** Минусы:
- **У РК нет проведения**, он пишется при каждом «Розрахувати» и смене статуса. Каждая запись регистрирует РК к выгрузке, и ERP перепроводит документ дома от промежуточных состояний.
- Деньги в такой ТЧ — BuhBud: расходятся с ERP на уровне карточки (§2.2). Оценку всё равно придётся делать в ERP.
- Обмен асинхронный и пакетный. Нет точки «РК готов → ERP загрузил», если не вводить статусный фильтр в ПВД.
- Самая высокая связность: метаданные в двух базах + правила в двух базах.

Плюс один — полностью автоматический поток без отдельного запуска.

**[В]** Схема для фактов узлов:
1. ERP-обработка или регламент подключается к BuhBud.
2. Вызывает в BuhBud экспортную функцию движка атрибуции, например `РасчетКомплектацийСервер.АтрибуцияФактаПоУзлам(Дом)`. Нужен общий модуль с флагом «Внешнее соединение». Можно читать и уже сохранённую ТЧ атрибуции РК. Функция возвращает строки (UUID КН, UUID карточки, ключ листа / путь узла, категория, количество).
3. ERP находит `СборкаТоваров` по UUID КН (1:1, §1.3), get-or-create документ дома, оценивает по `СебестоимостьТоваров` и проводит.

Тот же путь [M3] §4.3 выбрал для норм (РС `А_НормыМатериаловДомов`), поэтому подключение и движок разузлования общие.

### 3.3. (в) ERP считает сам по `СборкаТоваров` / `СписаниеНедостачТоваров` + перенесённой спецификации

**[Ф]** Вход в ERP есть: строки сборок 1:1 с КН (§1.4), себестоимость по паре (документ, карточка), выбытие изделия (§1.6), склад → дом.
Нет:
- спецификации — её перенос в ERP пока вариант ([M1] §6.5, [M3] §4.2: 5–8 дней, правила в двух базах);
- **связей карточка → строка** с ролью, коэффициентом и приоритетом;
- признака служебной сборки.

**[В]** Вариант требует зеркала спецификации и связей в ERP и **второй реализации** алгоритма §2.7, кроме BuhBud (РК). Две реализации разойдутся при первом изменении правила. Плюс один: деньги ERP «из коробки» и нет зависимости от доступности BuhBud при формировании.

### 3.4. Сравнение

| Критерий | (а) ПКО обмена | (б) COM-загрузчик | (в) ERP считает сам |
|---|---|---|---|
| Где логика атрибуции | BuhBud (одна) | BuhBud (одна) | **ERP + BuhBud (две)** |
| Надёжность | средняя: асинхронно; РК без проведения пишется часто; ошибки ПКО видны только в протоколе обмена | высокая: явный запуск, превью, протокол; проверка «КН проведена ↔ сборка в ERP есть и проведена» до записи | высокая во время работы; риск — расхождение двух реализаций |
| Повторная загрузка | UUID РК → документ ERP, замещение обменом; `А_Необновлять` блокирует обновление | get-or-create по дому, отмена проведения → очистка → проведение, без удаления; контроль по `ВерсияДанных` источников | перепроведение по событию; get-or-create тот же |
| Согласованность сумм с себестоимостью ERP | только если ERP переоценивает при проведении | да: оценка по `СебестоимостьТоваров` при проведении + перепроведение после закрытия месяца | да |
| Связь с решением [M3] (нормы) | разные механизмы | **один механизм** (подключение, движок) | разные |
| Трудоёмкость (оценка) | высокая: метаданные в двух базах, ПКО/ПВД/регистрация, приёмка через обмен | средняя: 1 документ + 2 регистра в ERP, загрузчик ~200–300 строк, экспорт движка в BuhBud | высокая: зеркало спецификации и связей + движок в ERP |

**[В]** Порядок величин в днях (по аналогии с оценками [M3] §6.3):
- (б) — ≈ 4–6 дней поверх готового движка разузлования и связей в BuhBud;
- (а) — ≈ 7–10 дней;
- (в) — ≈ 8–12 дней.

Это оценка, не замер.

## 4. Рекомендация

### 4.1. Документ-регистратор

**[В]** `Документ.А_ФактУзловДома` (рабочее имя, «Факт вузлів будинку») — **один на дом**.

| Часть | Состав | Источник |
|---|---|---|
| Шапка | `Организация`, `Подразделение` (дом, ключ get-or-create), `СтруктураСебестоимости` (А_СС типа дома), `Спецификация` (строка или ссылка на зеркало, когда оно будет), `РасчетКомплектацийUID` (Строка 36), `ДатаЗагрузки`, `ОценкаЗакрыта` (Булево), `Комментарий` | BuhBud РК / ERP |
| ТЧ `Состав` (из чего собирались) | `ДокументСборки` (`СборкаТоваров`), `Номенклатура`, `КлючСтрокиСС`, `ПутьУзла`, `Категория` (в нормі / понад нормою / поза специфікацією / МШП), `Количество` (ед. карточки), `КоличествоВЕдиницеСтроки`, `Стоимость`, `СтоимостьБезНДС` | количество — BuhBud (§2.7 шаги 1–3); деньги — ERP (шаг 4) |
| ТЧ `Выбытие` (как списывались) | `ДокументВыбытия` (`РеализацияТоваровУслуг` / `СписаниеНедостачТоваров`), `Дата`, `ДоляИзделия` (выбыло / собрано), `Стоимость` | ERP: `СебестоимостьТоваров`, Расход изделия дома со складов дома (§1.6) |
| ТЧ `Источники` (контроль свежести) | `ДокументСборки`, `ВерсияДанных` сборки на момент загрузки, `ВерсияДанныхКН` (из BuhBud), `ПериодЗакрыт` | ERP + BuhBud |

**[В] Регистры** — только набросок движений, состав согласовать с синтезом и [M3] §4.5 по ключам `КлючСтрокиСС` / `ПутьУзла`:
- **РН «Состав узлов» (обороты)** — «из чего собирались». По строке ТЧ `Состав` — запись с `Период` = дата `ДокументСборки`. Измерения: дом, `КлючСтрокиСС`, `ПутьУзла`, `Номенклатура`, `Категория`, `ДокументСборки`. Ресурсы: количество, стоимость.
- **РН «Узлы домов» (остатки)** — «как собирались и списывались».
  - Приход «узел собран»: по каждому (`ПутьУзла`, `ДокументСборки`) доля узла = атрибутированная норма в этом документе / норма узла в доме, с `Период` = дата сборки.
  - Расход «узел выбыл»: по строке ТЧ `Выбытие`, доля изделия × собранное, с `Период` = дата выбытия. Остаток регистра — узлы «на складе / в незавершённом» дома.

Документ проводит оба регистра. Типовые регистры и движения типовых документов не меняются (память `feedback_no_typical_register_changes.md`).

### 4.2. Когда создаётся

**[В]**
1. **Количества — после КН.** Условие загрузки дома:
   - РК в статусе «Документи створено» или «Цикл закрито»;
   - все КН из `ДокументиКомплектації` проведены в BuhBud;
   - все они есть в ERP как проведённые `СборкаТоваров` с тем же UUID.

   Иначе дом получает статус «очікує обміну», документ не пишется. Запуск — кнопкой в ERP-обработке (по проекту / дому) и регламентом после сеанса обмена.
2. **Деньги — после закрытия месяца.** Шаг регламента закрытия, после `РасчетСебестоимостиТоваров`: найти документы `А_ФактУзловДома`, где у `Источники` период ≤ закрытого и `ОценкаЗакрыта = Ложь`, и перепровести их. Стоимость пересчитывается из `СебестоимостьТоваров`.

   Альтернатива: не хранить стоимость в регистре, а оценивать в отчёте соединением с `СебестоимостьТоваров` по (`ДокументСборки`, `Номенклатура`). Перепроведение не нужно, но запрос отчёта тяжелее, и снимок «как было» теряется.
3. **Выбытие — по событию ERP.** `Реализация` и `СписаниеНедостачТоваров` изделия дома. ТЧ `Выбытие` заполняет сам ERP при каждом перепроведении документа дома, BuhBud для этого не нужен. 30 м №1 сейчас: выбыла 1 единица (реализация 22.09), вторая ждёт `ТребованиеНакладная` («Досписання монтажу» просрочено с 30.09).

### 4.3. Что делать при перерасчёте РК

**[Ф]** «Розрахувати» / «Заповнити документи» переписывают **те же** КН: очистка ТЧ и запись (`RKO` 2069, 2131). Если документу не осталось строк, проведённый документ распроводится (2111). Обмен передаёт обновлённую КН в ту же `СборкаТоваров` по UUID (`XR` 14856).

**[В]** Порядок:
1. Загрузчик сравнивает `ВерсияДанных` КН (BuhBud) и сборок (ERP) с сохранёнными в ТЧ `Источники`. Есть отличие — дом в статусе «змінено після завантаження».
2. Пока КН и сборка не равны (обмен ещё не прошёл), документ дома **не перезаписывается**. Иначе количества BuhBud не сойдутся с количествами ERP.
3. После обмена: `ОтменаПроведения` → очистка ТЧ → заполнение → `Проведение`. Без удаления документа (память `feedback_no_doc_delete_in_tests.md`, правило get-or-create).
4. Если перерасчёт РК задел **закрытый** месяц ERP, деньги станут верными только после повторного `РасчетСебестоимостиТоваров` этого месяца. Документ дома остаётся с `ОценкаЗакрыта = Ложь` до перезакрытия.
5. Если РК удалён или дом больше не считается, документ дома распроводится с комментарием. Он не удаляется.

## 5. Открытые вопросы

1. Правило по умолчанию для нескольких кандидатов: П1 (доля нормы) или П2 (приоритет)? И нужен ли групповой псевдоузел («Гвинтові кріплення») в самой спецификации? Это решает технолог / пользователь (§2.3).
2. Привязаны ли узлы спецификации к этапам «Виробничий / Відвантажено»? Если да, склад КН становится сильной подсказкой (§2.3).
3. Где хранить результат атрибуции в BuhBud: ТЧ РК (видно бухгалтеру, переживает перерасчёт как `ПричиниЦеху`) или только функция движка по запросу? От этого зависит, что читает загрузчик.
4. Старые дома с полуфабрикатом (30 м №1 и 15 м с септиком в 2 КН) переносить по особой ветке §2.5 или начинать регистры с домов без полуфабрикатов?
5. Расхождение BuhBud / ERP по карточкам (саморіз 4,2*19: 263,52 против 644,00) — особенность партий ERP или ошибка оценки? Это не исследовалось. На отчёт по узлам не влияет, если деньги берутся из ERP.

## Что это значит для проекта

1. **Отказ от комплектаций полуфабрикатов ничего не ломает на пути факта.** Факт дома и так приходит в ERP плоским списком карточек: 4 КН РК → 4 `СборкаТоваров`, 1:1 по строкам и UUID. Дом 30 м №2 уже собран так. Узел становится учётной сущностью спецификации, и «из чего собран узел» получается обратным разузлованием, а не документом.
2. **Движений для регистров узлов в ERP нет ни в одном существующем документе.** Нужен новый регистратор, один документ на дом. Его состав берётся из BuhBud: только там связи «карточка → строка спецификации» и движок, которым пересчитывается РК. Оценка и выбытие берутся из ERP.
3. **Доставка — COM-загрузчик ERP**: тот же механизм, что [M3] предлагает для норм (`А_НормыМатериаловДомов`). Одно подключение, один движок разузлования в BuhBud, правила обмена не трогаются. Образцы кода в конфигурации уже есть (`ZRK`, `А_СинхронизироватьТоварыТолькоТовары`, обработка начальной задолженности Ф2).
4. **Атрибуция — на уровне дома, по детерминированному правилу.** Явный приоритет связи → доля нормы → превышение отдельной категорией. Иначе повторная загрузка после «Розрахувати» даст другие цифры (пример §2.3: 527,54 против 2 390,33 грн на одной строке при тех же количествах).
5. **Деньги — из себестоимости ERP по паре «сборка × карточка»**, количество — из BuhBud. Только так отчёт по узлам сходится с `СебестоимостьТоваров` и `А_ОтчетPL_ПолныйЕРП_Остатки`. Цена: деньги текущего месяца появляются после `РасчетСебестоимостиТоваров`, значит, в регламент закрытия месяца нужен шаг «перепровести факт узлов».
6. **Для спецификации ([M1] §6) из N2 следуют требования:**
   - у каждого листа — стабильный `КлючСтрокиСС` и путь узла;
   - у связи карточка → лист — приоритет;
   - желательно `Этап` у узлов;
   - узел «Поза специфікацією» и категория «МШП» на уровне дома, чтобы Σ по узлам = расходу дома в ERP.
7. **Старые дома с полуфабрикатом** (служебные сборки 174/175) требуют отдельной ветки загрузчика. Их строки «Комлпект септика» в сборке дома заменяются деталями служебных сборок. Признак `Служебная` в ERP не доходит, поэтому служебную сборку надо распознавать по «изделие ≠ изделие дома на складе дома».
