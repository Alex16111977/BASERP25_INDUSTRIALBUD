# 01 Формулы — ПАП vs РСКПС

> Точные формулы для двух регистров-источников и почему они должны
> сходиться (но иногда не сходятся).

---

## Регистр 1 — `ПрочиеАктивыПассивы` (ПАП)

Балансовый регистр для управленческого учёта. Хранит **движения**
(не остатки) с указанием `ВидДвижения` (Приход / Расход).

### Ключевые поля движения

| Поле | Тип | Назначение |
|---|---|---|
| `Регистратор` | Документ.* | документ-источник движения |
| `Период` | Дата | дата движения (обычно = дата документа) |
| `ВидДвижения` | Приход/Расход | направление |
| `Сумма` | Число | сумма (всегда положительная, направление — в ВидДвижения) |
| `Организация` | Спр.Организации | юр.лицо |
| `Подразделение` | Спр.СтруктураПредприятия | управленческое подразделение |
| `Статья` | ПВХ.СтатьиАктивовПассивов | строка баланса |
| `Источник` | Перечисление.ИсточникиУправленческогоБаланса | "категория" движения |
| `Аналитика` | composite | произвольный субконто-объект |

### Формула остатка (signed)

```
signed = ВЫБОР КОГДА ВидДвижения = Приход ТОГДА Сумма ИНАЧЕ -Сумма КОНЕЦ

НМ_<месяц> = Σ signed по [Период < НачМес]    -- начальный остаток
КМ_<месяц> = Σ signed по [Период <= КонМес]   -- конечный остаток
оборот за месяц = КМ - НМ = Σ signed по [Период МЕЖДУ НачМес И КонМес]
```

### Фильтр статьи "Задолженность клиентов"

```sql
ГДЕ Организация = &ТОВ_ИНДАСТРИАЛБУД
    И Подразделение В ИЕРАРХИИ (&ПодрГлобино2)
    И Источник = ЗНАЧЕНИЕ(Перечисление.ИсточникиУправленческогоБаланса.РасчетыСКлиентамиПоСрокам)
    И Статья = &СтатьяЗадолженностьКлиентов
    -- OD-3 фильтр: исключить служебные статьи (как в Свод_*)
    И НЕ Статья В ИЕРАРХИИ (
            ЗНАЧЕНИЕ(ПВХ.СтатьиАктивовПассивов.СобственныеСредства),
            ЗНАЧЕНИЕ(ПВХ.СтатьиАктивовПассивов.ДоходыТекущегоПериода),
            ЗНАЧЕНИЕ(ПВХ.СтатьиАктивовПассивов.РасходыТекущегоПериода)
        )
```

> Статья "Задолженность клиентов" сама по себе не входит в исключаемые,
> но фильтр стоит ставить **точно** как в Свод_РасчетыСПартнерами,
> чтобы суммы сходились побитово.

### Знак «Задолженность клиентов»

По коду Свод_РасчетыСПартнерами строка для клиентов (Партнер ≠ НашеПредприятие):
- `ДолгУпр > 0` → ПАП пишет `ВидДвижения = Приход`, `Сумма = ДолгУпр` (увеличение долга)
- `ДолгУпр < 0` (предоплата) → ПАП пишет `ВидДвижения = Расход` ИЛИ статья меняется на "ПолученныеАвансы"

Значит: для статьи `Задолженность клиентов` **только положительные нетто-долги клиентов**;
авансы выделены в отдельную статью `ПолученныеАвансы` (через `ПредоплатаУпр`).

## Регистр 2 — `РасчетыСКлиентамиПоСрокам` (РСКПС)

Регистр-расшифровка для отчёта `ВедомостьРасчетовСКлиентами`. Хранит
движения по партнёрам, объектам расчётов и срокам.

### Ключевые поля

| Поле | Тип | Назначение |
|---|---|---|
| `Регистратор` | Документ.* | документ-источник |
| `Период` | Дата | |
| `ВидДвижения` | Приход/Расход | |
| `АналитикаУчетаПоПартнерам` | Спр.КлючиАналитикиУчетаПоПартнерам | косвенный JOIN для Организация/Партнёр/Контрагент/Договор |
| `Партнер` | Спр.Партнеры | партнёр (включая `НашеПредприятие` для собств.орг.) |
| `ОбъектРасчетов` | Спр.ОбъектыРасчетов | сам объект расчётов (заказ клиента, договор и т.п.) |
| **`ДолгУпр`** | Число (ресурс) | сумма долга в валюте упр.учёта |
| `ПредоплатаУпр` | Число (ресурс) | сумма предоплаты в валюте упр.учёта |
| `СрокОплаты` | Дата | |

### Формула остатка (через виртуальную таблицу)

```sql
ВЫБРАТЬ
    Р.ДолгУпрНачальныйОстаток КАК НачОст_ДолгУпр,
    Р.ДолгУпрКонечныйОстаток  КАК КонОст_ДолгУпр
ИЗ
    РегистрНакопления.РасчетыСКлиентамиПоСрокам.ОстаткиИОбороты(
        &НачМес, &КонМес, , ,
        Партнер <> ЗНАЧЕНИЕ(Справочник.Партнеры.НашеПредприятие)
    ) КАК Р
    ЛЕВОЕ СОЕДИНЕНИЕ РегистрСведений.АналитикаУчетаПоПартнерам КАК Аналит
        ПО Р.АналитикаУчетаПоПартнерам = Аналит.КлючАналитики
ГДЕ Аналит.Организация = &ТОВ_ИНДАСТРИАЛБУД
    И ВЫБОР КОГДА Р.ОбъектРасчетов.Подразделение = ЗНАЧЕНИЕ(Справочник.СтруктураПредприятия.ПустаяСсылка)
            ТОГДА Р.ОбъектРасчетов.Договор.Подразделение
            ИНАЧЕ Р.ОбъектРасчетов.Подразделение
      КОНЕЦ В ИЕРАРХИИ (&ПодрГлобино2)
```

> Важно: фильтр `Партнер <> НашеПредприятие` ставится **внутри** параметров
> виртуальной таблицы, чтобы 1С отбросил эти строки **до** агрегации
> остатков (тогда они не попадут в `ДолгУпр[Нач|Кон]Остаток`).

### Формула движения за период

```sql
ВЫБРАТЬ
    Р.Регистратор,
    СУММА(ВЫБОР КОГДА Р.ВидДвижения = ЗНАЧЕНИЕ(ВидДвиженияНакопления.Приход)
                ТОГДА Р.ДолгУпр ИНАЧЕ -Р.ДолгУпр КОНЕЦ) КАК Сигнед_РСК
ИЗ РегистрНакопления.РасчетыСКлиентамиПоСрокам КАК Р
ГДЕ Р.Период МЕЖДУ &НачМес И &КонМес
СГРУППИРОВАТЬ ПО Р.Регистратор
```

## Почему ПАП и РСКПС теоретически должны сходиться

`Свод_РасчетыСПартнерами` (см. `Documents/А_ФинРез_Баланс/Ext/ObjectModule.bsl`)
проектирует РСКПС в ПАП **1:1 по ресурсу**:
- `ДолгУпр > 0` → статья `ЗадолженностьКлиентов` (для клиентов)
- `Партнер = НашеПредприятие` → отдельная ветка `ЗадолженностьСобственныхОрганизаций`
- Подразделение проектируется через `ОбъектРасчетов.Подразделение` (fallback `Договор.Подразделение`)
- Организация — через `АналитикаУчетаПоПартнерам`

**Если каждый документ декабря пишет движения в ОБА регистра консистентно,
то Σ ПАП(статья="ЗадолженностьКлиентов", Глобино-2) == Σ РСКПС(Глобино-2)**.

### Гипотезы — почему могут НЕ сойтись

1. **Документ декабря пишет ПАП напрямую (минуя РСКПС)** — например, ручная
   корректировка через `КорректировкаЗаписейРегистров` / `ОперацияБух` /
   `А_ВводНачальныхОстатков` → ПАП движется, РСКПС нет.
2. **Реклассификация подразделения** — документ записывает в ПАП с одним
   подразделением, а `ОбъектРасчетов.Подразделение` уже изменён на другое
   (после движения). Тогда документ виден в одном из срезов и не виден в другом.
3. **Изменение `Договор.Подразделение`** — fallback указывает на новое
   подразделение, а ПАП записал по старому.
4. **Изменение типа статьи у документа** — документ пишет в РСКПС с
   `ДолгУпр < 0` (предоплата), а в ПАП это уже не "Задолженность клиентов"
   а "ПолученныеАвансы". Тогда в нашем срезе по статье "Задолженность клиентов"
   будет рассогласование.
5. **Распроведённый/удалённый документ** — есть движения в одном регистре,
   нет в другом (если регистр не очищен механизмом проведения).
