# 🧩 Универсальный промт: разработка/доработка любой обработки 1С на лучших практиках

> **Что это:** мета-шаблон. Приложи этот файл к запросу + опиши свою задачу в блоке «ЗАДАЧА» (3–6 строк) —
> ИИ соберёт **правильный, полный промт** на разработку/доработку обработки (или сразу выполнит),
> используя скилы `obr-*` и базу знаний `knowledge_БАЗА_ЗНАНИЙ_Рабочие_места`.
>
> Покрывает 4 семейства обработок: **заполнение/создание документов · сверка двух баз · анализ/диагностика · перенос остатков / перепроведение.**

---

## 1. Как пользоваться (2 шага)

1. **Заполни блок «ЗАДАЧА»** ниже (только то, что знаешь — остальное ИИ уточнит/решит сам по базе знаний).
2. Отправь ИИ: *«Используя базу знаний `knowledge_БАЗА_ЗНАНИЙ_Рабочие_места` и скилы `obr-*`, собери правильный промт на разработку обработки по блоку ЗАДАЧА (или сразу выполни)»* + этот файл + блок ЗАДАЧА.

ИИ обязан: подключить скилы `obr-*`, заземлиться на **ЭТАЛОН** (не на память), прогнать запросы через Python COM (Rule #-1), и выдать промт по **скелету (§4)** с **чек-листом (§5)**.

## 5. Чек-лист «правильного промта» (ИИ проверяет себя)

- [ ] Подключены скилы `obr-*` (хаб + по семейству) и гейт `bas-verify`.
- [ ] Заземление на **ЭТАЛОН** (вербатим со ссылкой на файл-источник), обработки-примеры не названы эталоном.
- [ ] **Rule #-1**: запросы прогнать через Python COM против нужной базы ПЕРЕД BSL.
- [ ] Заполнение документов: транзакция + журнал; идемпотентность; структура-результат (не пустой `Исключение`).
- [ ] Расчётные документы → обязательные поля (`Курс/Кратность/А_`-флаги, `bas-doc-fill`); нерасчётные → не нужно (явно указать какой случай).
- [ ] Значения в запросе — `&Параметр`, типы — `ЗНАЧЕНИЕ(...)`; без хардкод-литералов кодов.
- [ ] UX (если есть): отборы + итоги-по-поиску (поле-поиск, штатный «Найти» события не даёт); оформление **кодом** (не XML).
- [ ] Ограничения базы соблюдены (если «всё в .epf» — нет объектов конфигурации).
- [ ] Сборка `.epf`/`.erf` из изолированного каталога против нужной базы; форму проверять в клиенте.
- [ ] Acceptance с **контрольными цифрами** (smoke) + чек-лист пользователю в Enterprise.

## 6. Канон-напоминания (частые грабли из базы знаний)

- **Эталон ≠ пример.** РМ из `Рабочие места/` — эталон; обработки из `Обработки/` — примеры для подъёма.
- **Цвет внешней обработки — только кодом** (`Новый Цвет`/`ЦветаСтиля`); `<TextColor>style:`-XML валит `epf-build` («Исключение XDTO»).
- **Управляемую форму нельзя проверить headless через COM** — открывать в клиенте.
- **Литерал в тексте запроса:** `""Код""` (удвоенные кавычки) в BSL ↔ `"Код"` (одинарные) в Python COM.
- **Поля виртуальных таблиц `.Обороты()`** имеют префиксы `Приход/Расход/Оборот` — без Python-теста не угадать (Rule #-1).
- **Видимая ТЗ формы ≠ полный набор** — документы заполнять из полного `Объект.ТЧ`, фильтр на «анализ» на заполнение не влияет.
- **COM-перепроведение в новой архитектуре взаиморасчётов теряет РегистраторРасчётов** → перепроводить расчётные документы только из UI.
- **Кросс-базный UUID 1:1** (сверка): `V83.string` (lowercase) для Казны; маппинг через `А_ИдКод`/`СоответствияОбъектовИнформационныхБаз`.
- **`ObjectModule` обработки** держать тонким: экспортные оркестраторы в `#ПрограммныйИнтерфейс`, тяжёлое — в `#СлужебныеПроцедурыИФункции` (если «всё в .epf» — без общего модуля конфигурации).
- **Сборка при locked Designer** — против `BuhBud`/изолированно (бинарник конфиг-независим), либо stub-cfg 2.17→2.13.
