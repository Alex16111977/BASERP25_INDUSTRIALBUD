## 0. ЭТАЛОН vs ПРИМЕР — на чём заземляется промт (читать первым)

🚨 **Грунт у скилов двойной, с РАЗНЫМИ ролями. Промт всегда тянет ОБА — но не путать, что есть что.**

| Роль | Где лежит | Что это в промте |
|------|-----------|------------------|
| **ЭТАЛОН** ⭐ | `_Rarzrabotki/Рабочие места/` — `ПомощникПродаж`, `ОбеспечениеПотребностей` (класс A, tier 5) + [`БАЗА_ЗНАНИЙ_Рабочие_места_1С.md`](../../Рабочие%20места/БАЗА_ЗНАНИЙ_Рабочие_места_1С.md) | «Как профессионально». Отсюда вербатим-кирпичики (транзакционный оркестратор, фон, master-detail, условное оформление кодом). Промт должен **просить уровень класса A**. |
| **ПРИМЕР** (НЕ эталон!) | `_Rarzrabotki/Обработки/` — `Создания комплектаций для бух учета`, `СинхронизироватьТоварыТолькоТовары` и др. | Это то, что промт **поднимает** до эталона («до → применить эталонный паттерн → после»). Никогда не называть эталоном в промте. |

**Доменный ЭТАЛОН для всех наших обработок «запрос → заполнение/создание документов» — класс A РМ** (операционный формирователь-«корзина»): менеджер набрал условия/корзину → ОДНИМ действием создал и провёл ПАКЕТ документов в транзакции. Это ровно сценарий наших обработок. Поэтому правильный промт звучит как «**в стиле рабочего места класса A**», а не «просто обработка».

⚠️ **Rule #-1 в любом промте по умолчанию.** Любой запрос 1С — сперва Python COM прогон на боевой базе, потом в BSL. Цепочки через точку (`Договор.А_ДоговорПоставщика.*`), префиксы полей виртуальных таблиц (`СуммаПриход`/`СуммаРасход` у `.Обороты()`, НЕ `Дебет`/`Кредит`) и наличие реквизитов (`А_РеализацияТоваровУслуг`, `А_ИдКод`) проверяются на метаданных ДО переноса в код.

## 1. Как скилы включаются

**Механизм — авто по полю `description`.** ИИ читает `description` каждого скила (там триггер-фразы) и сам подгружает подходящий, когда промт совпадает по смыслу. **Слеш-команда не обязательна** — достаточно описать задачу обычным языком, употребив триггер-слова.

**Хаб подтягивается первым.** Все три тематических скила — `obr-zapros-zapolnenie`, `obr-forma-otbory-itogi`, `obr-sverka-sinhronizaciya` — в своём `REQUIRED BACKGROUND` обязывают сначала прочитать **`obr-obrabotka`** (каркас рабочей обработки: тонкая форма + движок `ObjectModule`/`А_<Объект>Сервер` + мост `РеквизитФормыВЗначение`/`ЗначениеВРеквизитФормы`; когда нужен `.epf`, а когда объект конфигурации). Один промт «создай обработку…» = вся связка.

**Базовые `epf-*`/`form-*` переиспользуются, не дублируются.** `obr-obrabotka` внутри вызывает существующие `epf-init`/`epf-build`/`epf-add-form`, `form-compile`/`form-edit`/`form-patterns`; запросы СКД (если есть) — `skd-compile`; заполнение документов — `bas-doc-fill`. Гейт качества — существующий **`bas-verify`** (новый скил-гейт НЕ создаётся).

**Если хочешь наверняка** — назови скил явно: «используй скил `obr-forma-otbory-itogi`».

## 3. Советы для надёжного срабатывания

- **Назови слово «обработка»** (внешняя обработка / движок обработки / рабочее место) — главный триггер хаба `obr-obrabotka`.
- **Проси уровень класса A** — «в стиле рабочего места», «как ПомощникПродаж/ОбеспечениеПотребностей», «транзакцией», «в фоне». Без этого скил даст каркас, но не дотянет до планки tier 5.
- Для UX-доработок формы — слова **«фильтр»**, **«отбор»**, **«итоги»**, **«итоги по поиску»**, **«подытоги по отбору»**, **«действие по строке»**, **«массовая кнопка»**, **«подвал ТЧ»**, **«условное оформление кодом»**, **«фоновый расчёт»**, **«длительная операция»** → `obr-forma-otbory-itogi`.
- Для логики данных — **«запрос остатков»**, **«запрос оборотов»**, **«заполнить документ кодом»**, **«создать документ из обработки»**, **«транзакцией»**, **«идемпотентно»**, **«get-or-create»** → `obr-zapros-zapolnenie`.
- Для двух баз — **«сверка двух баз»**, **«ЕРП↔Казна»**, **«ЕРП↔BuhBud»**, **«синхронизация»**, **«перепровести помеченные»**, **«нетование сторон»**, **«найти документ по UUID»**, **«фазная обработка»** → `obr-sverka-sinhronizaciya`.
- Для расчётных документов добавь **«с взаиморасчётами»** — подтянется `bas-doc-fill` (без `Курс=1`/`Кратность=1` суммы взаиморасчётов = 0; см. `obr_zaprosy_zapolnenie.md` и `CLAUDE.md` §«Programmatic Document Creation»).
- Используй **префикс `А_`** в имени нового объекта (проектное правило: `А_` = кастом INDUSTRIALBUD).
- **Назови базу-источник** (BuhBud `cfo/2442` / Казна `КазначействоBASERP` / ЕРП `BaseERP`) — определяет COM-строку и сторону запроса; для бух-баз сразу включится логика субконто через `ПланСчетов.Хозрасчетный.ВидыСубконто`.
- Скил не подхватился? Допиши явно: **«используй `obr-obrabotka`»** — вызовется принудительно.

## 4. Три «класса» обработок — какой промт под какой грунт

Класс определяет, что включится поверх хаба. **Грунт класса — реальный код**, но роль грунта разная: ЭТАЛОН (РМ) задаёт планку, ПРИМЕР-обработка — то, что поднимаем.

| Класс | ЭТАЛОН (планка) | ПРИМЕР-обработка (поднимаем) | Слова-триггеры в промте | Скил поверх `obr-obrabotka` |
|-------|-----------------|------------------------------|--------------------------|------------------------------|
| **Заполнение/создание документов** | `ПомощникПродаж` (пакет до 12 типов в транзакции), `ОбеспечениеПотребностей` (мастер 5 шагов) | `Создания комплектаций для бух учета`, `СоздатьПриобретениеПоРеализации`, `Заполнить документы ПокупкаПродажаВалюты` | «запрос остатков», «заполнить ТЧ кодом», «создать документ», «транзакцией», «get-or-create», «идемпотентно» | `obr-zapros-zapolnenie` + `bas-doc-fill` |
| **UX рабочего места** | `ОбеспечениеПотребностей` (master-detail, фон, отборы на СКД), `ПомощникПродаж` (УсловноеОформление ~380 стр) | `Создания комплектаций для бух учета` (закладка «Аналіз залишків»), `СинхронизироватьТоварыТолькоТовары` (грид складов/документов) | «фильтр», «итоги по поиску», «условное оформление кодом», «master-detail», «подвал ТЧ», «фон» | `obr-forma-otbory-itogi` |
| **Сверка/синхронизация двух баз** | паттерны cross-base из РМ класса B/D (дерево, динсписки) + правила UUID 1:1 проекта | `СинхронизироватьТоварыТолькоТовары`, `СинхронизироватьВзаиморасчеты`, `СинхронизироватьДеньгиКасса`, `А_ОбработкаДисбалансаПоПодразделениям` | «сверка двух баз», «COM ЕРП↔BuhBud/Казна», «нетование», «фазность», «перепровести помеченные» | `obr-sverka-sinhronizaciya` |

## 5. Готовые промты для трёх флагманских задач

Три развёрнутых промта-«заготовки». Каждый явно помечает роли источников (ЭТАЛОН РМ vs ПРИМЕР-обработка), чтобы скил заземлился правильно. Копируй, подставляй свои объекты.

### 5.1 Подними `СозданиеКомплектацийБух` до профессионального рабочего места

ПРИМЕР-обработка `Создания комплектаций для бух учета` — то, что **поднимаем**. Эталон UX-кирпичиков — класс A РМ.

```text
ЗАДАЧА: Подними ПРИМЕР-обработку СозданиеКомплектацийБух (база BuhBud, cfo/2442) до
рабочего места класса A. НЕ называть её эталоном — это код, который дорабатываем.

ОБЯЗАТЕЛЬНО ПРОЧИТАЙ ПЕРВЫМ:
- Хаб-скил obr-obrabotka (каркас + мост форма↔движок), затем obr-forma-otbory-itogi.
- Кейс: _Rarzrabotki/notebook/knowledge_БАЗА_ЗНАНИЙ_Рабочие_места/case_sozdanie_komplektacij.md
- ЭТАЛОН (планка «как профессионально»): _Rarzrabotki/Рабочие места/ОбеспечениеПотребностей
  и ПомощникПродаж (УсловноеОформление кодом, master-detail, итоги) + БАЗА_ЗНАНИЙ_Рабочие_места_1С.md.
- Грунт ПРИМЕРА (что правим): _Rarzrabotki/Обработки/Создания комплектаций для бух учета/
  (Ext/ObjectModule.bsl + Forms/Форма/Ext/Form/Module.bsl + Form.xml).

СДЕЛАТЬ (поднять, применяя эталонные паттерны):
1. ФОН/ОТБОРЫ/ИТОГИ-ПО-ПОИСКУ. Закладка «Аналіз залишків»: группа «Відбір»
   (ОтборСклад/ОтборЭталон/ТолькоПонадНорму/Пошук — каждое поле с Event OnChange →
   одна процедура ПрименитьОтборИИтоги) + read-only ТаблицаАнализа (Footer=true) +
   панель «Підсумки» (3 итога ИтогоЗалишок/ИтогоВНорме/ИтогоПонад).
   ⚠ Штатный «Найти» (SearchStringAddition/Ctrl+F) НЕ даёт события → фильтр-с-итогами
   НЕвозможен; нужен реквизит-строка Пошук + OnChange. Видимая ТЗ ≠ полный набор:
   полный живёт в Объект.ТабличнаяЧастьОстатков, итоги считаются в ТОМ ЖЕ проходе фильтра.
2. ЦВЕТ КОДОМ. Подсветка итогов/строк «понад норму» — через УсловноеОформление и
   ЦветаСтиля в ПриСозданииНаСервере (как ПомощникПродаж). НЕ <TextColor>style:…</TextColor>
   в Form.xml — это валит epf-build «Исключение XDTO» (память epf_load_xdto_textcolor).
3. ВЫНОС ЛОГИКИ. Тяжёлый расчёт РассчитатьАнализ()/ЗаполнитьДокументыПоАнализу() оставить
   на сервере; форма — только мост РеквизитФормыВЗначение("Объект") → метод → ЗначениеВРеквизитФормы.
   Если расчёт долгий — в фон (триада ДлительныеОперации, образец ОбеспечениеПотребностей).

НЕ ТРОГАТЬ типовые регистры (только чтение). Логика — в кастомные объекты.
ПРОВЕРКА (bas-verify, успех не заявлять без неё): Python COM тест запроса сч.2051 (Rule #-1) +
form-validate + epf-build + COM-smoke (спец 000000003/ПРООН/07.04.2026 = 126 строк, баланс 0).
```

Что включится: `obr-obrabotka` (хаб) → `obr-forma-otbory-itogi` (отбор/итоги/цвет кодом/фон) + `form-edit` → `bas-verify`.

**Грунт «до» (ПРИМЕР-обработка — кандидат на подъём, НЕ эталон):** на каждую команду форма гоняет round-trip всего объекта, итоги считает вручную циклом, цвет хардкодит `Новый Цвет(...)` —
```bsl
// ПРИМЕР (поднять): Forms/Форма/Ext/Form/Module.bsl
Элементы.ИтогоВНорме.ЦветФона = Новый Цвет(214, 240, 214);          // хардкод RGB
ОбъектОбработки = РеквизитФормыВЗначение("Объект");
ОбъектОбработки.РассчитатьАнализ();
ЗначениеВРеквизитФормы(ОбъектОбработки, "Объект");
Сообщить("Розраховано позицій: " + Объект.ТабличнаяЧастьОстатков.Количество());
```
*(источник-ПРИМЕР: `_Rarzrabotki/Обработки/Создания комплектаций для бух учета/Forms/Форма/Ext/Form/Module.bsl`)*

**Эталонный приём «после» (ЭТАЛОН РМ — куда поднять цвет):** условное оформление строить кодом, цвет — через `ЦветаСтиля`, а не RGB-литерал —
```bsl
// ЭТАЛОН РМ: программное УсловноеОформление
Элемент = УсловноеОформление.Элементы.Добавить();
ОтборЭлемента = Элемент.Отбор.Элементы.Добавить(Тип("ЭлементОтбораКомпоновкиДанных"));
ОтборЭлемента.ЛевоеЗначение  = Новый ПолеКомпоновкиДанных("ТабличнаяЧастьОстатков.ПонадНорму");
ОтборЭлемента.ВидСравнения   = ВидСравненияКомпоновкиДанных.Больше;
ОтборЭлемента.ПравоеЗначение = 0;
```

## 6. Что произойдёт после запуска (ожидаемый результат)

Для новой обработки-рабочего места связка выдаёт каркас уровня класса A (планка `ПомощникПродаж`/`ОбеспечениеПотребностей`), наложенный на разметку из ПРИМЕРОВ `СозданиеКомплектацийБух`/`СинхронизироватьТоварыТолькоТовары`:

1. **Тонкая форма** (`epf-init` + `form-compile`): шапка-отбор + таблицы-результаты на реквизитах объекта + командная панель (`Autofill=false`). Логики в форме нет — только мост и UI-навигация.
2. **Движок** (`Ext/ObjectModule.bsl` тонкий + общий модуль `А_<Объект>Сервер`): экспортные методы-фазы (`РассчитатьАнализ`/`СравнитьОстатки`/`АнализДокументы`/…) — тяжёлая логика делегирована в общий модуль, `ObjectModule` форвардит (подъём над ПРИМЕРОМ, где логика жила прямо в `ObjectModule`).
3. **Мост форма↔движок** (канон):
   ```bsl
   &НаСервере
   Процедура РассчитатьНаСервере()
       ОбъектОбработки = РеквизитФормыВЗначение("Объект");
       Попытка
           ОбъектОбработки.РассчитатьАнализ();
       Исключение
           Сообщить(КраткоеПредставлениеОшибки(ИнформацияОбОшибке()));
           Возврат;
       КонецПопытки;
       ЗначениеВРеквизитФормы(ОбъектОбработки, "Объект"); // обязательный обратный — иначе ТЧ не вернутся
   КонецПроцедуры
   ```
   *(приём моста взят из ПРИМЕРА `_Rarzrabotki/Обработки/Создания комплектаций для бух учета/Forms/Форма/Ext/Form/Module.bsl`; на запись/расчёт поднимается до образца класса A — логика на сервере, не round-trip всего объекта на клик).*
4. **Запросы** (если читают данные): протестированы в Python COM перед вставкой (Rule #-1); остатки/обороты с правильными префиксами полей.
5. **Заполнение документов** (если создают/правят): транзакция + обязательные поля + `Курс=1`/`Кратность=1` + А_-флаги обмена + идемпотентность (отмена ранее созданных / get-or-create по ключу).
6. **Тяжёлый расчёт** — в фон по триаде `ДлительныеОперации.ВыполнитьВФоне` → `ОжидатьЗавершение` → `*Завершение` (образец `ОбеспечениеПотребностей`).
7. **Сборка `.epf`** через `epf-build` + COM-smoke (для `.erf`-обработок — `erf-build`, например `А_ОбработкаДисбалансаПоПодразделениям` это `ExternalReport`).
8. **Проверка** через `bas-verify`.

Если цвет подсветки задан через `<TextColor>style:...</TextColor>` в `Form.xml` — сборка `.epf` упадёт «Исключение XDTO»; цвет ставится **только кодом** (`УсловноеОформление`/`ЦветаСтиля` или `Элементы.Х.ЦветФона`), см. `obr_forma_otbory_itogi.md` и память `epf_load_xdto_textcolor.md`.

## 7. Q&A

**Q: Нужно ли писать `/obr-obrabotka`?**
Нет. Достаточно «создай обработку … в стиле рабочего места класса A» или «доработай движок обработки …». Скил-хаб включится по смыслу и сам подтянет `epf-*`/`form-*` и тематический скил. Слеш — опционально.

**Q: Чем «фильтр в обработке» отличается от запроса с фильтром?**
«Фильтр в обработке» = клиентский отбор по уже загруженному полному набору (`obr-forma-otbory-itogi`): перебор `Объект.ТЧ`, равенство через `ОтборСтрок = Новый ФиксированнаяСтруктура` + поиск подстрокой `СтрНайти`, подытоги в том же проходе — без перезапроса БД. Грунт-ПРИМЕР: `ПрименитьОтборИИтоги` в `СозданиеКомплектацийБух`. Если нужен фильтр в самом запросе (`ГДЕ`/параметры виртуальной таблицы) — это `obr-zapros-zapolnenie`.

**Q: Почему встроенный «Найти» не годится для фильтра-с-итогами?**
Штатный поиск платформы (`SearchStringAddition`, Ctrl+F) только подсвечивает/скроллит к совпадению — **не генерирует событие** в модуле формы, нечего перехватить и пересчитать. Нужен реквизит-строка `Пошук` с `Event OnChange → ПрименитьОтборИИтоги`: каждое изменение даёт своё событие → код перестраивает видимую копию из полного набора и в том же проходе считает подытоги. Видимая ТЗ ≠ полный набор (полный — в ТЧ объекта). См. `case_sozdanie_komplektacij.md` §2.

**Q: «Создай обработку запрос остатков X → документы Y» — что включится?**
`obr-zapros-zapolnenie` (запрос остатков/оборотов + транзакционное заполнение/создание документа) поверх `obr-obrabotka`, плюс `bas-doc-fill` для обязательных полей расчётных документов. ЭТАЛОН транзакционного оркестратора — `ПомощникПродаж` (`СоздатьДокументыСервер`). ПРИМЕРЫ-обработки на подъём: `СозданиеКомплектацийБух` (остатки сч.2051 → `КомплектацияНоменклатуры`), `СоздатьПриобретениеПоРеализации`.

**Q: Как сделать «итоги по поиску» (подытоги по отфильтрованным строкам)?**
«Добавь итоги-по-поиску»: в одном цикле фильтра накапливать `Итого* = Итого* + Стр.X` по отобранным строкам (а не по всему набору). → `obr-forma-otbory-itogi`.

**Q: «Сверка ЕРП↔Казна» — что под капотом?**
`obr-sverka-sinhronizaciya`: COM-подключение, мост по UUID 1:1 (`V83.string(...)`→`ПолучитьСсылку(УИД)` / `РС.СоответствияОбъектовИнформационныхБаз`, НЕ по ссылкам и НЕ по Номер+Дата), нетование сторон (Приход−Расход ↔ ОборотДт−Кт), отбор/итоги, перепроведение помеченных **только из UI**. ПРИМЕРЫ-обработки: `СинхронизироватьДеньгиКасса`, `СинхронизироватьТоварыТолькоТовары`, `СинхронизироватьВзаиморасчеты`.

**Q: Почему «перепровести помеченные» нельзя автономным COM-перепроводом?**
COM-перепровод в новой архитектуре взаиморасчётов теряет `РегистраторРасчётов` → парная проводка пропадает. Перепроведение вызывается ТОЛЬКО из интерактивной UI-сессии, и после `РежимЗаписиДокумента.ОтменаПроведения` объект ОБЯЗАТЕЛЬНО перечитывается `ПолучитьОбъект()` (иначе падение на закрытом менеджере ВТ). См. память `feedback_com_repost_skips_registrator_raschetov` и `feedback_delete_doc_obmen_zagruzka`.

**Q: Чем промт «как класс A» сильнее обычного «создай обработку»?**
Слова «в стиле рабочего места класса A» / «как ПомощникПродаж» / «транзакцией» / «в фоне» / «идемпотентно» поднимают планку с tier 1–2 (одна форма-обёртка, ручные итоги, round-trip объекта) до tier 5 (транзакционный оркестратор, фон, вынос логики в общий модуль, условное оформление кодом). Без них скил даёт корректный, но «плоский» каркас. Шкала tier 1–5 — в `obr_arhitektura_obrabotki.md`.

**Q: Можно ли запустить только проверку готовой обработки?**
Да: «проверь обработку А_X перед коммитом» → `bas-verify` (Python COM запросы по Rule #-1, `form-validate`/`meta-validate`, `1c-bsl-review`, сборка `.epf`/`.erf`, копирование в основную конфигурацию). Новый гейт-скил под обработки НЕ создаётся — `bas-verify` покрывает.

**Q: Скил упорно не подхватывается — что делать?**
Назови явно: «используй `obr-zapros-zapolnenie`» / «используй `obr-sverka-sinhronizaciya`». И добавь класс-слово из §4 (например «через COM ЕРП↔BuhBud» или «заполнить документ кодом транзакцией») — оно однозначно разводит хаб и тематический скил.
