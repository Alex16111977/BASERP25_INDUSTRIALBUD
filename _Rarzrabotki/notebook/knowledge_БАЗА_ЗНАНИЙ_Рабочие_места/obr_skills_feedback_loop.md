# Развитие скилов рабочих обработок `obr-*` и обратная связь по их выполнению

> Тип файла: ПОСТОЯННЫЙ (правится при каждом найденном пробеле скилов `obr-*` и при изменении гейта `bas-verify`). Раздел «Известные пробелы» (§6) — ЗМІННЫЙ: дополняется при каждом новом грабле.
> ⭐ Главный файл петли: как ИИ должен **развивать скилы `obr-*`** и **давать обратную связь по их выполнению**, не угадывая, а проверяя на ЭТАЛОНАХ и свежим агентом.
> Источник: `.claude/skills/{obr-obrabotka, obr-zapros-zapolnenie, obr-forma-otbory-itogi, obr-sverka-sinhronizaciya}/SKILL.md` + гейт `.claude/skills/bas-verify/SKILL.md` (тело прочитано 1:1).
> Связан с: [obr_skills_overview.md](obr_skills_overview.md) · [obr_arhitektura_obrabotki.md](obr_arhitektura_obrabotki.md) · [obr_zaprosy_zapolnenie.md](obr_zaprosy_zapolnenie.md) · [obr_forma_otbory_itogi.md](obr_forma_otbory_itogi.md) · [obr_sverka_sinhronizaciya.md](obr_sverka_sinhronizaciya.md) · [obr_skills_prompts.md](obr_skills_prompts.md) · кейсы [case_sozdanie_komplektacij.md](case_sozdanie_komplektacij.md) / [case_sinhronizirovat_tovary.md](case_sinhronizirovat_tovary.md). Аналог-структура: `_Rarzrabotki/notebook/knowledge_БСП/bsp_skills_feedback_loop.md`.

Этот файл отвечает на один вопрос: **как развивать скилы `obr-*`, чтобы свежий агент строил обработку «запрос→анализ→заполнение документов» на ПРОФЕССИОНАЛЬНОМ уровне — по образцу класса A эталонных рабочих мест, а не по образцу того, что пользователь когда-то написал сам.** Принцип сквозной: скил не «дописан», пока свежий агент по нему не собрал рабочую обработку профессионального уровня, а движок не прошёл гейт `bas-verify`.

## 1. Философия: скилы грунтованы на ЭТАЛОНАХ, не на примерах пользователя

🔒 **Ключевое разделение ролей источников (соблюдать неукоснительно):**

| Роль | Где живёт | Чему учит | Как использовать в скиле |
|---|---|---|---|
| **ЭТАЛОН** «как профессионально» | `_Rarzrabotki/Рабочие места/` (6 tier-5 РМ) + файл `БАЗА_ЗНАНИЙ_Рабочие_места_1С.md` | транзакционный оркестратор, фоновые операции, master-detail, программное оформление, отборы/итоги, пакетные действия, дерево, динсписки | **отсюда** берём вербатим-паттерны и заземляем «как надо»; ссылка-путь к РМ даётся агенту |
| **ПРИМЕР** «что было до подъёма» | `_Rarzrabotki/Обработки/` (Создания комплектаций для бух учета, СинхронизироватьТоварыТолькоТовары и др.) | то, что пользователь писал САМ; источник граблей и реальных полей/UID | **только** как «до → применить эталонный паттерн → профессионально» в кейсах; **НЕ называть эталоном** |

- **Rule #-1 / грунт на реальном коде:** прежде чем добавить контракт/сигнатуру/паттерн в скил — найди его в коде **эталонного РМ** (чтение `Forms/Форма/Ext/Form/Module.bsl`), скопируй дословно со ссылкой на путь и строки, не по памяти.
- **Прямой эталон задачи «запрос→документы» = класс A** («Операционный формирователь-корзина»): `ПомощникПродаж` (12 типов документов одним действием в одной транзакции) и `ОбеспечениеПотребностей` (wizard из 5 шагов + фоновые операции). Их доминирующий сценарий ровно совпадает с целью скилов — набрать корзину/условия → одним действием сформировать и провести ПАКЕТ документов.
- **Примеры пользователя — НЕ образец стиля.** `Создания комплектаций для бух учета` и `СинхронизироватьТоварыТолькоТовары` дают факты (поля `Хозрасчетный`, рахунок 2051, UID-мост, магические строки-статусы), но архитектурно их надо **поднимать** до эталона (вынос логики в общий модуль, перечисления вместо строк-статусов, штатные итоги/оформление, обёртка записи в `Попытка`). Перенос «как есть» в новый скил-эталон запрещён.

> **Зачем инверсия ролей.** Если заземлять скил на пользовательских обработках, ИИ воспроизведёт их слабые места (порожний `Исключение`, хардкод пароля/счёта, ручные итоги циклом, round-trip всего объекта на каждый клик). Цель петли — научить ИИ строить **как класс A РМ**, а примеры держать ровно как «было плохо → стало профессионально».

## 2. Петля приёмки свежим агентом (как давать обратную связь по выполнению)

`bas-verify §4` дословно: «Дай отдельному агенту без контекста скил и тест-задачу. Справился без подсказок → готово. Буксует → допиши, чего не хватило, повтори.»

```
1. ГРУНТ. Выбрать ЭТАЛОН-аналог в _Rarzrabotki/Рабочие места/ под задачу (класс A для
   «запрос→документы»); дать скилу ссылку-путь к его Module.bsl. НЕ грунтовать на обработке
   пользователя — её брать только как «до» в кейсе.
2. ЗНАНИЕ. Дать СВЕЖЕМУ агенту (чистый контекст) скил-хаб obr-obrabotka + нужную ветвь как
   REQUIRED BACKGROUND + соответствующий knowledge-файл.
3. ЗАДАЧА. Поставить тест-задачу СЛОВАМИ ПОЛЬЗОВАТЕЛЯ («сделай рабочее место: из остатков
   набрать корзину и одним действием создать и провести пакет документов»), не терминами скила.
4. ПРОВЕРКА. Прогнать вывод через гейт bas-verify (Python COM по Rule #-1 → form-validate →
   1c-bsl-review → COM-smoke). Проверки гоняет контроллер сам.
5. ФИКСАЦИЯ ПРОБЕЛА. Где агент забуксовал / выдумал поле / опустил флаг / съехал на уровень
   «примера» вместо «эталона» → записать в §6 «Известные пробелы».
6. ПРАВКА REFERENCE. Дозаписать недостающее в SKILL.md или reference/*.md нужного скила —
   ВЕРБАТИМ из эталонного РМ, со ссылкой на путь+строки.
7. ПОВТОР. Новый свежий агент, та же задача → справился без подсказок и на уровне класса A = пробел закрыт.
```

Петля закрывается на шаге 7: **«справился без подсказок И на профессиональном уровне»** = критерий готовности скила (`bas-verify §4`).

**Правила приёмки рабочих обработок:**

- ⭐ **Свежесть обязательна.** Агент, писавший скил, держит недосказанное в голове и пройдёт там, где реальный пользователь споткнётся. Брать агента без истории сессии — это объективный детектор пробелов триггеров и reference.
- **Задача словами пользователя, не терминами скила.** «сделай рабочее место сверки товаров ЕРП↔BuhBud», а НЕ «реализуй мост `РеквизитФормыВЗначение` + транзакционный оркестратор + 3 фазы». Если для срабатывания скила нужны внутренние термины — это пробел триггеров (правь `description`).
- **Один скил-хаб читается первым.** `obr-obrabotka` — хаб; три ветви (`obr-zapros-zapolnenie`, `obr-forma-otbory-itogi`, `obr-sverka-sinhronizaciya`) держат его в REQUIRED BACKGROUND. Проверять, что цепочка подтягивается сама (см. [obr_skills_overview.md](obr_skills_overview.md) §3), а не вручную.
- **Грунт на ЭТАЛОННОЕ РМ, не на пример.** Эталон даётся агенту через ссылку-путь к `Рабочие места/<РМ>/...`. Если агент пишет «идеализированный» или «упрощённый» документ вместо профессионального — это сигнал, что в reference нет ссылки на живой код эталона (ровно как `bas-bsp-form` ссылается на `Documents/АмортизацияОС/...`).
- **«На уровне эталона» — отдельный критерий, не только «компилируется».** Свежий агент может выдать работающую, но «плоскую» обработку (логика в форме, итоги вручную, без транзакции). Это **забуксовал по качеству**, даже если smoke зелёный.
- **Вывод проверяет контроллер сам.** Не плодить reviewer-субагентов: один агент-исполнитель на задачу, проверки гоняет контроллер (память `feedback_controller_verifies_no_reviewer_subagents`).

**Что считается «забуксовал»:**

| Симптом у свежего агента | Где пробел | Куда дописать |
|---|---|---|
| Пакетное создание документов БЕЗ транзакции (нет `НачатьТранзакцию/Попытка/ОтменитьТранзакцию`) | reference не подал транзакционный оркестратор класса A как обязательный | `obr-zapros-zapolnenie` |
| Положил логику в модуль формы вместо `ObjectModule`/общего модуля (как «пример», а не «эталон») | хаб не объяснил «тонкая форма + движок» по образцу класса A | `obr-obrabotka` §моста |
| Выдумал поле виртуальной таблицы (`Дебет` вместо `СуммаПриход`) | нет Rule #-1 в reference запросов | `obr-zapros-zapolnenie` |
| Забыл `Курс=1/Кратность=1` → `СуммаВзаиморасчетов=0` | reference не подчеркнул обяз. поля расчётного документа | `obr-zapros-zapolnenie` (делегирует в `bas-doc-fill`) |
| Тяжёлый расчёт/создание пачки сделал синхронно, блокируя сеанс | нет фоновой триады `ВыполнитьВФоне`/`ОжидатьЗавершение`/`*Завершение` | `obr-forma-otbory-itogi` |
| Итоги ТЧ посчитал вручную циклом на клиенте (как в примере комплектаций) | reference не подал штатные итоги в подвале | `obr-forma-otbory-itogi` |
| Задал цвет через `<TextColor>` в `Form.xml` → epf-build «Исключение XDTO» | не вынесен запрет XDTO-цвета | `obr-forma-otbory-itogi` |
| Не перечитал объект после `ОтменаПроведения` → падение на закрытом менеджере ВТ | reference перепроведения неполон | `obr-sverka-sinhronizaciya` |
| COM-перепровод вместо UI → потеря `РегистраторРасчётов` | не зафиксировано «перепроводить только из UI» | `obr-sverka-sinhronizaciya` |

## 3. Гейт качества — существующий `bas-verify` (новый НЕ создавать)

Гейт рабочих обработок = тот же `bas-verify`, что и для документов/справочников. Новый гейт не плодим. Применительно к `obr-*` релевантные пункты чек-листа:

| Пункт `bas-verify` | Что значит для обработки | Грунт |
|---|---|---|
| §1 Python COM (Rule #-1) | КАЖДЫЙ запрос обработки (`Остатки`/`Обороты`/COM к BuhBud) прогнать через `V83.COMConnector` ДО вставки в `.bsl` | `bas-verify` §1, шаблон скрипта в нём |
| §2 form-validate | `Form.xml` обработки — уникальность id, компаньон-элементы, ссылки команд `Form.Command.X`; для динсписков `~Список.*` — ложные срабатывания (память `form_validate_tilde_spisok_false_positive`) | `bas-verify` §2 |
| §3 1c-bsl-review | `ОбменДанными.Загрузка=Истина` при служебной записи; нет запросов в цикле; транзакции корректны; **нет порожнего `Исключение`** (антипаттерн примера `СинхронизироватьТоварыТолькоТовары`) | `bas-verify` §3 |
| §4 свежий агент | приёмка скила на уровне класса A (раздел 2 этого файла) | `bas-verify` §4 |
| §5 копирование в основную конфигурацию | `cp` `.epf`/`.xml`/`.bsl` из worktree в `C:\Configuration_downloads\BASERP25\` (Rule #4) | `bas-verify` §5 |

**Смоук для обработки (специфика, поверх гейта):**

- [ ] Если артефакт — `.epf`: `epf-build` собрал без ошибок, затем COM-smoke (`ВнешниеОбработки.Создать(путь)` → вызов экспортного метода движка → проверка количества строк ТЧ результата). Кейс комплектаций (ПРИМЕР, поднятый до эталона): `РассчитатьАнализ` → 126 строк, баланс 0 ([case_sozdanie_komplektacij.md](case_sozdanie_komplektacij.md)).
- [ ] **Транзакционность пакета:** при создании/проведении пачки документов — сбой одного откатывает все (`НачатьТранзакцию`/`Исключение→ОтменитьТранзакцию`+`ЗаписьЖурналаРегистрации`), как в эталоне `ПомощникПродаж.СоздатьДокументыСервер`. Проверять подачей заведомо негодной строки.
- [ ] **Идемпотентность:** повторный прогон НЕ задваивает (`Очистить()` перед заполнением; отмена ранее созданных через `ОтменитьПроведениеРанееСозданных`/get-or-create по бизнес-ключу; флаг `Обработано`; дедуп). Проверять двойным прогоном.
- [ ] **Фон для тяжёлого:** если расчёт/массовое создание долгие — `ДлительныеОперации.ВыполнитьВФоне` ↔ `ДлительныеОперацииКлиент.ОжидатьЗавершение` ↔ `*Завершение`, результат через временное хранилище (эталон `ОбеспечениеПотребностей`).
- [ ] Если `.epf` собирается при заблокированной Designer-ом базе — собирать против изолированной/другой базы (BuhBud-обработки против BuhBud), либо через патч stub-cfg версии (память `sinhronizirovat_vzaimoraschety`).
- [ ] Финал — пользователь открывает в карточке «Дополнительные обработки» и перезагружает `.epf` (память `feedback_run_acceptance_after_signature_change`).

⚠️ Цвет в формах внешних обработок — ТОЛЬКО кодом. `<TextColor>style:...</TextColor>` в `Form.xml` валит `epf-build` «Исключение XDTO» (в формах конфигурации работает, в EPF нет). Задавать `Элементы.X.ЦветФона = ЦветаСтиля.X` в `ПриСозданииНаСервере`. Программное условное оформление — через `УсловноеОформление.Элементы.Добавить()` + `ЦветаСтиля` (эталон, ниже §4). Память: `epf_load_xdto_textcolor`.

## 4. Профессиональные «кирпичики» класса A — что проверять в первую очередь

Самый частый источник «забуксовал по качеству» — агент не вшил каркас класса A. Ниже — вербатим из **ЭТАЛОННЫХ РМ** (не из памяти, не из примеров пользователя). Это девять кирпичиков, из которых собирается любая профессиональная обработка «запрос→заполнение/создание документов».

### 4.1 ⭐ Транзакционный оркестратор пакетного создания документов

Сердце класса A: весь пакет создаётся атомарно, идемпотентно, с откатом и журналированием.

```bsl
Функция СоздатьДокументыСервер()
	// ОтменаПроведенияРанееСозданныхДокументов  ← идемпотентность повторного запуска
	Если ДокументыСформированы Тогда
		МассивДокументов = Новый Массив;
		Для Каждого ТекСтрока Из Объект.Документы Цикл
			МассивДокументов.Добавить(ТекСтрока.ПолучитьИдентификатор());
		КонецЦикла;
		ПровестиОтменитьПроведениеДокументовСервер(МассивДокументов, Ложь);
	КонецЕсли;
	НачатьТранзакцию();
	Попытка
		Отказ = Ложь;
		МассивНайденныхДокументов = Новый Массив;
		// ... ветвление по ВариантОформленияДокументов, вызовы ЗаписатьЗаказ/ЗаписатьСчетНаОплату/ЗаписатьПКО ...
		// ПометкаНаУдалениеЛишнихДокументов (не вошедших в МассивНайденныхДокументов)
		Если Отказ Тогда
			ВызватьИсключение НСтр("ru='Ошибка завершения создания документов';uk='Помилка завершення створення документів'", ...);
		КонецЕсли;
		ЗафиксироватьТранзакцию();
	Исключение
		ОтменитьТранзакцию();
		ЗаписьЖурналаРегистрации(НСтр("ru='Ошибка завершения создания документов';..."),
			УровеньЖурналаРегистрации.Ошибка,,, ПодробноеПредставлениеОшибки(ИнформацияОбОшибке()));
	КонецПопытки;
	Возврат МассивНайденныхДокументов.Количество();  // счётчик → клиент строит НСтр-оповещение
КонецФункции
```
Источник: **ЭТАЛОН РМ** `_Rarzrabotki/Рабочие места/ПомощникПродаж/Forms/Форма/Ext/Form/Module.bsl` (стр. 5863-6344), класс A, цепочка из 12 типов документов в одной транзакции. Клиентская обёртка — `СоздатьДокументыКлиентФрагмент` (стр. 6441-6477): гейт `ПроверитьЗаполнение()` ДО серверного вызова + `ПоказатьОповещениеПользователя` со счётчиком.

> ⚠️ При создании **расчётных** документов внутри оркестратора соблюдать обязательные поля взаиморасчётов (`Курс=1`, `Кратность=1`, суммы `СуммаВзаиморасчетов`/`СуммаСНДС`, флаги обмена `А_Обработан`/`А_ВведенВЕРП`) — CLAUDE.md «Programmatic Document Creation» + навык `bas-doc-fill`. Иначе суммы и движения уходят в 0.

### 4.2 ⭐ Тонкая форма + движок (мост, по образцу класса A)

Логика — в `ObjectModule`/общем модуле экспортными методами; форма лишь дёргает их через мост и заливает объект обратно.

```bsl
&НаСервере
Процедура АнализДокументовНаСервере()
	мОбъект = РеквизитФормыВЗначение("Объект");
	мОбъект.АнализДокументов();
	ЗначениеВРеквизитФормы(мОбъект, "Объект");   // ← ОБЯЗАТЕЛЬНЫЙ обратный залив!
КонецПроцедуры
```
Образец архитектуры — **ЭТАЛОН РМ** класса A (`ПомощникПродаж`/`ОбеспечениеПотребностей`): тяжёлая логика (запрос, расчёт анализа, формирование документов) живёт вне формы. Локальный пример тонкой формы (ПРИМЕР, поднятый до эталона) — `Создания комплектаций для бух учета`. **Обратный `ЗначениеВРеквизитФормы` агенты регулярно опускают** — без него мутации ТЧ-результата не вернутся в форму.

🚫 Антипаттерн, который приёмка обязана ловить: пустой/однострочный `ObjectModule.bsl` при «толстой форме», где вся логика в модуле формы и не переиспользуется. Так писали **ПРИМЕРЫ** пользователя — это уровень «до подъёма», а НЕ эталон. Для нового скил-эталона тянуть house-style вариант (движок + мост).

## 5. Принцип грунта на ЭТАЛОНЫ + примеры как источник граблей (Rule #-1 / Rule #5)

**Ни одного запроса в `.bsl` без Python COM-прогона.** Это RED-фаза TDD: запрос сначала живёт в `_Rarzrabotki/Python/test/`, проходит на реальной базе, и только потом переносится в модуль. Скилы `obr-*` обязаны вести агента именно так — reference запросов содержит ссылку «прогнать через `bas-verify §1`», а не готовый-якобы-верный текст.

**Грабли запросов/заполнения, которые ловятся ТОЛЬКО прогоном.** Здесь роли источников видны особенно ясно: **ЭТАЛОН** задаёт профессиональный паттерн, **ПРИМЕР** пользователя — конкретный грабли «до подъёма».

| Грабли | Источник (роль) | Урок / как поднять |
|---|---|---|
| Программное создание документов — атомарно, через транзакцию | **ЭТАЛОН** `ПомощникПродаж` (`СоздатьДокументыСервер`) | пакет создавать `НачатьТранзакцию`/`Попытка`/`ОтменитьТранзакцию`, а не голым `Записать()` |
| Запись документа БЕЗ `Попытка` вокруг самого `Записать()`; ошибки глушатся порожним `Исключение` | **ПРИМЕР** `Создания комплектаций для бух учета/Ext/ObjectModule.bsl` | поднять: обернуть запись в `Попытка`, ошибки накапливать в `{Оброблено, Помилки[]}`, не глушить |
| Рахунок `2051` и код спецификации зашиты строковым литералом в тексте запроса (`Счет.Код = ""2051""`), дублируются | **ПРИМЕР** `Создания комплектаций для бух учета` | поднять: счёт искать `ПланыСчетов.Хозрасчетный.НайтиПоКоду` один раз → передавать `&параметром`; литерал в BSL-строке = граблі удвоенных/одинарных кавычек (память `sozdanie_komplektacii_buh`) |
| Строка подключения COM (Srvr/Ref/Usr/**Pwd в открытом виде**) зашита в код; поиск узла обмена дублируется трижды | **ПРИМЕР** `СинхронизироватьТоварыТолькоТовары/Ext/ObjectModule.bsl` | поднять: параметры в реквизиты/`БезопасноеХранилищеДанных` (пароль не в git); узел — один приватный метод `ПолучитьУзелОбмена(V83)` (DRY); подключение в `Попытка`/`Исключение` с гарантированным `V83=Неопределено` в финале |
| Статус/действие строки = «магические» украинские строки (`"Перепровести в ЕРП"`, `СтрНачинаетсяС(Статус,"ПОМИЛКА")`); диспетчер — цепочка `Если Действие = "..."`; одна правка текста ломает форму+диспетчер+лічильники | **ПРИМЕР** `СинхронизироватьТоварыТолькоТовары/Ext/ObjectModule.bsl` | поднять: перечисление `А_ВидДействияСинхронизации`/`А_СтатусСинхронизации` или именованные константы; диспетчер на `ВЫБОР`/карту `{ВидДії→Обработчик}`; результат структурой `{Успіх, Текст}`; условное оформление — по числовому `КодСтану`, не по тексту |
| Round-trip ВСЕГО объекта обработки на каждый клик (`РеквизитФормыВЗначение("Объект")`→метод→`ЗначениеВРеквизитФормы`); итоги/фильтр считаются вручную циклом на клиенте | **ПРИМЕР** `Создания комплектаций для бух учета/Forms/.../Module.bsl` | поднять: итоги — штатно через подвал колонок (`Подвал`/`ПутьКДаннымПодвала`); тяжёлую логику — на сервере `&НаСервереБезКонтекста`/в общем модуле; повідомлення — `ОбщегоНазначения.СообщитьПользователю` с привязкой к полю, не голый `Сообщить` |

**Грабли заполнения/проведения (для `obr-zapros-zapolnenie` и `obr-sverka-sinhronizaciya`):**

- Расчётный документ: `Курс=1; Кратность=1; СуммаВзаиморасчетов=Сумма;` иначе движения = 0 (CLAUDE.md, делегируется в `bas-doc-fill`).
- Программное создание расчётного документа: `А_ВведенВЕРП=Истина` (иначе обмен затрёт `Товары`/`РасшифровкаПлатежа`).
- Служебная правка реквизита БЕЗ проведения: `ДокОбъект.ОбменДанными.Загрузка = Истина; ДокОбъект.Записать();`.
- Перепроведение: `ОтменаПроведения` → **перечитать `СсылкаДок.ПолучитьОбъект()`** → `Проведение`. Без перечита — падение на закрытом менеджере ВТ (память `feedback_delete_doc_obmen_zagruzka`). **Только из UI**, не COM-перепровод (COM теряет `РегистраторРасчётов` → `РСППС=0`; память `feedback_com_repost_skips_registrator_raschetov`).
- COM к другой базе: параметры создавать объектами **удалённой** базы — `V83.NewObject("Массив")`, `V83.NewObject("УникальныйИдентификатор", СтрUID)`; UID извлекать `V83.string(...)` (lowercase, англ.). CLAUDE.md «Cross-base UUID lookup».
- Идемпотентность — обязательный пункт приёмки: `Очистить()` перед заполнением; отмена ранее созданных / get-or-create по бизнес-ключу; флаг `Обработано` + «снимок до»; дедуп по ключу.

## 6. Известные пробелы (ЗМІННЫЙ журнал — дополнять при каждом новом грабле)

> Формат пункта: **#N ⭐ <название>** + **Симптом:** / **Причина:** / **Решение (куда дописать):**. Эмодзи-статус: 🆕 новый, ✏️ дописан в reference, ⚠️ открыт.

### 6.1 ⚠️ Агент пишет на уровне «примера», а не «эталона»
**Симптом:** свежий агент выдаёт работающую, но плоскую обработку — логика в форме, итоги вручную циклом, пакетное создание без транзакции, статусы магическими строками (повторяет стиль **ПРИМЕРОВ** пользователя).
**Причина:** reference заземлён на пример-обработку, а не на класс A эталонных РМ; нет ссылки на `Рабочие места/ПомощникПродаж|ОбеспечениеПотребностей`.
**Решение:** в `obr-obrabotka`/`obr-zapros-zapolnenie` подать каркас класса A (§4.1 транзакция, §4.2 движок+мост) как ОБЯЗАТЕЛЬНЫЙ; ссылки-пути — на эталонные РМ; примеры пользователя упоминать только в формате «до→поднять».

### 6.2 ⚠️ Пакетное создание без транзакции
**Симптом:** агент создаёт пачку документов голым `Записать()` в цикле; сбой на пятом оставляет четыре записанными (half-applied).
**Причина:** reference не подал транзакционный оркестратор класса A.
**Решение:** в `obr-zapros-zapolnenie` зашить §4.1 вербатим из `ПомощникПродаж.СоздатьДокументыСервер` (`НачатьТранзакцию`/`Попытка`/`ОтменитьТранзакцию`+`ЖурналРегистрации`+возврат счётчика); FAIL-пункт в smoke (раздел 3).

### 6.3 ✏️ XDTO-цвет в Form.xml внешней обработки
**Симптом:** `epf-build` падает «Исключение XDTO» после задания цвета элемента.
**Причина:** `<TextColor>style:...</TextColor>` в `Form.xml` EPF не сериализуется.
**Решение:** в `obr-forma-otbory-itogi` зафиксировать: цвет ТОЛЬКО кодом (`ЦветаСтиля.X` / `Новый Цвет(...)` для `ЦветФона`) в `ПриСозданииНаСервере`; программное УО — §4.3. Грунт-эталон: `ПомощникПродаж.УстановитьУсловноеОформление`. Память `epf_load_xdto_textcolor`.

### 6.4 ✏️ Обратный `ЗначениеВРеквизитФормы` опущен
**Симптом:** движок отработал, а форма пустая.
**Причина:** агент не залил объект обратно в реквизит формы.
**Решение:** в `obr-obrabotka` мост подать как нерасторжимую тройку «`РеквизитФормыВЗначение` → метод → `ЗначениеВРеквизитФормы`»; третий вызов выделить как обязательный (§4.2).

### 6.5 ⚠️ Тяжёлый расчёт/создание сделаны синхронно
**Симптом:** массовое создание пачки/тяжёлый расчёт блокируют сеанс, нет прогресса.
**Причина:** не вшита фоновая триада.
**Решение:** в `obr-forma-otbory-itogi` зашить §4.4 (`ДлительныеОперации.ВыполнитьВФоне` ↔ `ОжидатьЗавершение` ↔ `*Завершение`, результат через временное хранилище) вербатим из `ОбеспечениеПотребностей`; диспетчер нескольких фонов — `ТекущаяФоноваяОперация` (`ПооперационноеПланирование2_2`).

### 6.6 ⚠️ Порожний `Исключение` глушит ошибки COM/типизации
**Симптом:** поля остаются пустыми, в журнале — ни следа; диагностика невозможна.
**Причина:** копирование стиля **ПРИМЕРА** `СинхронизироватьТоварыТолькоТовары` (порожній блок обробки).
**Решение:** в `obr-sverka-sinhronizaciya` запретить порожний `Исключение`; минимум — `ЗаписьЖурналаРегистрации(...,УровеньЖурналаРегистрации.Ошибка, ПодробноеПредставлениеОшибки(ИнформацияОбОшибке()))` + диагностика в `Статус`/`КодСтану` строки; перед COM-запросами — Python COM pre-check (Rule #-1). Антипаттерн ловит `1c-bsl-review`.

### 6.7 ⚠️ Итоги ТЧ считаются вручную циклом на клиенте
**Симптом:** три итоговых реквизита наполняются циклом по ТЧ в клиентской процедуре; цвет метрик задан `Новый Цвет(RGB)` хардкодом.
**Причина:** стиль **ПРИМЕРА** комплектаций (`ПрименитьОтборИИтоги`), агент копирует.
**Решение:** в `obr-forma-otbory-itogi` подать штатные итоги в подвале колонок (`Подвал`/`ПутьКДаннымПодвала`/`ГоризонтальноеПоложениеВПодвале`) или `ОтображатьИтоги`; цвет — `ЦветаСтиля`. Эталон-приём — `bas-bsp-form` «итоги в подвале табличной части».

### 6.8 ⚠️ Перепроведение без перечита объекта / COM-перепровод
**Симптом:** падение при повторной `Записать()` после `ОтменаПроведения`; либо после массового COM-перепровода `РСППС=0` (нет `РегистраторРасчётов`).
**Причина:** менеджеры ВТ закрыты, объект устарел; COM в новой архитектуре взаиморасчётов не создаёт `РегистраторРасчётов`.
**Решение:** в `obr-sverka-sinhronizaciya` reference перепроведения — обязательный `ДокОбъект = СсылкаДок.ПолучитьОбъект()` между отменой и проведением; пометка «**только из UI**». Память `feedback_delete_doc_obmen_zagruzka`, `feedback_com_repost_skips_registrator_raschetov`.

### 6.9 ✏️ COM-параметры создаются объектами УДАЛЁННОЙ базы
**Симптом:** запрос к BuhBud через COM падает/пустой при передаче локального `Массив`/UUID.
**Причина:** локальные объекты не годятся для чужого запроса.
**Решение:** в `obr-sverka-sinhronizaciya`: `V83.NewObject("Массив")`, `V83.NewObject("УникальныйИдентификатор", СтрUID)`, даты — `V83.NewObject(...)`/строкой; UID извлекать `V83.string(...)` (lowercase, англ.). Грунт-факт из **ПРИМЕРА** `СинхронизироватьТоварыТолькоТовары`; паттерн — CLAUDE.md «Cross-base UUID lookup».

### 6.10 ⚠️ Хардкод секретов/счетов/узла обмена + нарушение DRY
**Симптом:** пароль COM в открытом виде в `.bsl` (уходит в git); счёт/код спецификации литералом; один и тот же текст запроса узла обмена скопирован трижды.
**Причина:** стиль **ПРИМЕРОВ** пользователя.
**Решение:** в `obr-obrabotka`/`obr-sverka-sinhronizaciya` правило: секреты → `БезопасноеХранилищеДанных`/реквизиты (не в git); счета → `НайтиПоКоду` один раз → `&параметр`; повторяемый фрагмент → один приватный метод. Антипаттерн ловит `1c-bsl-review`.

## 7. Как расширять скилы (добавить новый кирпичик класса A)

Пример: добавить в скил профессиональный приём «диаграмма Ганта» или «дерево из плоского запроса».
1. **Грунт:** найти приём в коде **эталонного РМ** (класс B `РабочееМестоМенеджераПоДоставке` для дерева/drag&drop/итогов выделения; класс D `РегистрацияИзмененийДляОбменаДанными` для динсписков с подменой запроса), прочитать `Module.bsl`, выписать **вербатим** вызовы со ссылкой на путь+строки.
2. **Reference:** добавить блок приёма в SKILL.md/`reference/*.md` нужного скила + в knowledge-файл ([obr_forma_otbory_itogi.md](obr_forma_otbory_itogi.md) / [obr_zaprosy_zapolnenie.md](obr_zaprosy_zapolnenie.md)).
3. **SKILL.md:** упомянуть приём в триггерах (если меняет область применения).
4. **Гейт:** добавить пункт в smoke-чеклист (раздел 3), если приём критичен.
5. **Приёмка:** прогнать петлю §2 — свежий агент воспроизводит приём на уровне эталона без выдумок.
6. **База знаний:** обновить overview + этот журнал.

⚠️ **Никогда** не заземляй новый приём на обработке пользователя из `_Rarzrabotki/Обработки/` — она источник граблей и фактов (поля/UID/счета), но НЕ образец стиля. Образец стиля — только `Рабочие места/`.

## 9. Q&A

**Q: Зачем свежий агент, если я могу проверить вывод сам?**
A: Тот, кто писал скил, держит недосказанное в голове и пройдёт там, где реальный пользователь споткнётся. Свежий агент = честный детектор пробелов триггеров и reference. `bas-verify §4`.

**Q: Почему нельзя заземлять скил на обработках пользователя — они же рабочие?**
A: Они рабочие, но архитектурно «до подъёма» (логика в форме, порожній `Исключение`, хардкод пароля/счёта, ручные итоги, магические строки-статусы). Если грунтовать скил на них, ИИ воспроизведёт слабые места. Эталон «как профессионально» — только класс A РМ (`ПомощникПродаж`/`ОбеспечениеПотребностей`); обработки пользователя — источник фактов и граблей в формате «до→поднять».

**Q: Создавать ли отдельный гейт для обработок?**
A: Нет. Гейт — существующий `bas-verify`. Специфика обработок (epf-build/erf-build + COM-smoke + транзакционность + идемпотентность + фон) — это смоук-чеклист ПОВЕРХ гейта (раздел 3), не новый скил.

**Q: Свежий агент собрал компилируемую обработку, но плоскую (без транзакции/фона/движка). Это PASS?**
A: Нет. «Компилируется» ≠ «на уровне эталона». Это **забуксовал по качеству** (#6.1/#6.2/#6.5/#6.7): фиксировать пробел и дописать каркас класса A в reference, повторить петлю.

**Q: Куда писать новый найденный грабли?**
A: В §6 «Известные пробелы» (Симптом/Причина/Решение + куда дописать), и сразу — правку в SKILL.md/`reference/` нужного скила ВЕРБАТИМ из **эталонного РМ** со ссылкой на путь+строки. Без правки скила запись в журнале — недоведённая петля.

**Q: Скилы в git — как версионировать правки?**
A: Скилы (`.claude/`) в git не идут. Версионируется эта база знаний (`knowledge_БАЗА_ЗНАНИЙ_Рабочие_места/`) + спека/план — там фиксируется эволюция.
