# Развитие скилов `bas-*` и обратная связь по их выполнению

> Тип файла: ЗМІННЫЙ (дополнять при каждом новом пробеле/правке скилов).
> ⭐ Главный файл базы: как ИИ должен **развивать скилы** и **давать обратную связь по их выполнению**.

---

## 1. Философия: скилы грунтованы на конфигурации

Скилы `bas-*` не выдуманы — они **вербатим из типовых объектов** этой конфигурации. Любое развитие
держится на этом принципе:

- **Rule #-1 / грунт на реальном коде:** прежде чем добавить контракт/сигнатуру в скил — найди его в
  типовом объекте (`get_metadata_structure`, чтение `Module.bsl`), скопируй дословно, не по памяти.
- **Эталоны:** документ — `РеализацияТоваровУслуг`; справочник — `Контрагенты`/`Номенклатура`;
  меню (наш) — `А_ПередачаНачисленийМеждуПодразделениями` (⚠ только форма/меню, проведение legacy).
- **Не трогать типовое:** скилы только читают типовые объекты как эталон; новая логика — в `А_*`.

## 2. Петля приёмки (как давать обратную связь по выполнению)

**Метод «свежий агент»** — главный инструмент обратной связи. Применяется (а) при изменении скила,
(б) при подозрении, что скил выдаёт неполный/неверный объект.

```
1. Дать СВЕЖЕМУ субагенту (чистый контекст) ТОЛЬКО файлы скила + тест-задачу
   («по этому скилу спроектируй документ А_Тест … опиши код, в базу не пиши»).
2. Проверить вывод против цели: меню не пустое? контракт вшит? регионы #455? тонкие модули?
3. Попросить агента САМОГО оценить: что не хватает / неоднозначно / сбивает с толку.
4. Зафиксировать пробелы → поправить reference скила → ПОВТОРИТЬ, пока агент не справляется чисто.
```

Почему свежий агент: он без контекста сессии — видит ровно то, что есть в скиле. Если он
галлюцинирует имя/сигнатуру — значит скил неполон. Это и есть объективная обратная связь.

**Где это в скилах:** пункт «Проверка свежим агентом» в `bas-verify`; сквозная приёмка — связка
house-style+common-module+bsp-form+doc-new на одной задаче.

## 3. Гейт `bas-verify` (проверка сгенерированного объекта в рантайме)

После создания/правки объекта — прогнать чек-лист `bas-verify`:
- [ ] Запросы 1С прошли Python COM (Rule #-1, без FAIL).
- [ ] `meta-validate` / `form-validate` без ошибок.
- [ ] `1c-bsl-review` — критичные пункты закрыты.
- [ ] **Меню не пустое** (нет `Autofill=false` при пустой `AutoCommandBar`); контракт «единое окно»
      вшит (вызовы в `ПриСозданииНаСервере` + обработчики `Подключаемый_*`).
- [ ] Модули в БСП-стиле: регионы #455, нейминг #469, логика в `А_<Объект>Сервер`, БСП — только
      Программный интерфейс (#std551).
- [ ] Файлы скопированы в основную конфигурацию; загрузка `db-load-xml`+`db-update`.

## 5. Как расширять скилы (добавить новый контракт/подсистему)

Пример: добавить подсистему БСП «X» в «единое окно».
1. **Грунт:** найти типовой объект, где X подключена; прочитать его форму/менеджер, выписать
   **вербатим** вызовы X в `ПриСозданииНаСервере` + парные обработчики + методы менеджера.
2. **Reference:** добавить блок X в `bas-bsp-form/reference/document-contract.md` (и/или catalog) —
   в порядок вызовов §3 + асимметрию жизненного цикла §4 + обработчики §5.
3. **SKILL.md:** упомянуть X в наборе подсистем + триггерах (если меняет область применения).
4. **Гейт:** добавить пункт проверки в `bas-verify` (если X критична).
5. **Приёмка:** прогнать петлю §2 — свежий агент должен воспроизвести X без выдумок.
6. **База знаний:** обновить `bsp_edinoe_okno_contracts.md` + этот журнал.

Аналогично для нового оркестратора (новый тип объекта) — добавить скил + строку в
`bsp_skills_overview.md` + манифест.

## 6. Как фиксировать обратную связь по конкретному выполнению

Когда сгенерированный объект отклонился от типового:
1. **Локализовать:** какой именно артефакт не как у типового (меню? регионы? проведение? подсистема?).
2. **Проследить до скила/раздела:** меню → `bas-bsp-form`; код-организация → `bas-common-module`;
   состав/реквизиты → `bas-house-style`/`bas-doc-new`; гейт пропустил → `bas-verify`.
3. **Сверить с эталоном:** открыть типовой объект, сравнить вербатим.
4. **Поправить reference** скила (не память!) — добавить недостающее/исправить.
5. **Запротоколировать** в §4 этого файла (что было, как исправили).
6. **Повторить приёмку** §2.

## 7. Q&A

**Q: Как понять, что скил неполон?** Свежий агент по нему галлюцинирует имя/сигнатуру или выдаёт
анти-паттерн (пустое меню, логика inline). Это сигнал дописать reference.
**Q: Откуда брать правильный код при доработке?** Только из типового эталона конфигурации (вербатим),
не из памяти/внешних источников.
**Q: Скилы в git — как версионировать правки?** Скилы (`.claude`) в git не идут. Версионируется эта
база знаний (`_Rarzrabotki/notebook/knowledge_БСП/`) + спека/план — там и фиксируется эволюция.
**Q: Можно ли менять типовой объект, чтобы «упростить» скил?** Нет. Типовое только читаем; скил
адаптируется под типовое, не наоборот.
**Q: Что главный критерий «скил готов»?** Свежий агент проектирует объект **без выдумок**, объект
проходит `bas-verify`, меню не пустое, логика в `А_<Объект>Сервер`.
