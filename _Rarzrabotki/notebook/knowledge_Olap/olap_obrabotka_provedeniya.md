# OLAP — BSL ОбработкаПроведения для А_ФинРез_PL/DDS

> Логіка свёртки PnL і Cashflow при проведенні документів. Stage 1.10 (`3999f1efd`) + Stage 1.12 (`297041586`).

---

## Архітектурний паттерн (обидва документи)

```bsl
Процедура ОбработкаПроведения(Отказ, РежимПроведения)

    // 1. ДУБЛІКАТ-ЗАХИСТ — один проведений документ на (Организация, Месяц[, ВключатьДочерние])
    [перевірка чи є інший проведений документ за той же місяць]
    Якщо знайдено: Отказ=Істина; Возврат

    // 2. ЕНЕЙБЛ ЗАПИСУ
    Движения.<Регистр>.Записывать = Истина;

    // 3. ЗАПИТ — 7-8 CTE з фінальним UNION ALL з колонкою Source
    Запрос = Новый Запрос;
    Запрос.Текст = СформироватьЗапросСверткиPL();  // або DDS
    Запрос.УстановитьПараметр(...);

    // 4. ПАКЕТНИЙ ЗАПИС у регістр
    Движения.<Регистр>.Загрузить(Запрос.Выполнить().Выгрузить());

КонецПроцедуры
```

**Паттерн `.Загрузить(.Выгрузить())`** — еталон з `Documents/А_ПереносДвиженийИзКазны/Ext/ObjectModule.bsl` (line 99). Назва колонок у ТЗ результату повинна збігатись з вимірюваннями + реквізитами + ресурсами регістра. 1С автоматично мапить колонки за іменами.

## А_ФинРез_PL.ОбработкаПроведения

**Файл:** `Documents/А_ФинРез_PL/Ext/ObjectModule.bsl` (592 рядки).

### Структура запиту — 12 CTE + фінальний UNION з 8 гілок

**Базові CTE** (порт з `Reports/А_ОтчетPL/Ext/ObjectModule.bsl` рядки 99-329 без змін):

| # | CTE | Джерело | Призначення |
|---|---|---|---|
| 1 | `втPL` | `Документ.А_ОтчетPL.ДанныеОтчета` | План з Excel: 1 рядок на (PL-стаття × Підрозділ × Документ) |
| 2 | `втPL_ДДС` | `Справочник.А_Статьи_PL.Статьи` | Мапа PL-стаття → ДДС (унікальність гарантовано модулем об'єкта) |
| 3 | `втЕРП_Расх_Детали` | `РегНакоп.ПрочиеРасходы.Обороты(Регістратор)` | Розходи ERP + Контрагент з шапки регістратора |
| 4 | `втЕРП_Доходы_Детали` | UNION (`ВыручкаИСебестоимостьПродаж` + `ПрочиеДоходы.Обороты`) | Доходи з 2 джерел |
| 5 | `втЕРП_CoGS_Детали` | `ВыручкаИСебестоимостьПродаж` (поле Стоимость) | Себестоимість, прив'язана до ДДС-приймача (через прапор `А_ПриёмникСебестоимостиПродажPL`) |
| 6 | `втКазна_ПоПодрДДС` | `А_ДвиженияДенегИзКазны.Обороты` | Каса з Казни, групування по (Подразделение, ДДС, Документ) |

**Деривативні CTE** (для подальшого UNION):

| # | CTE | Source | Логіка |
|---|---|---|---|
| 7 | `втPL_Строки` | `втPL` | PL-рядки з ЕРП=0 (PL-сторона з'єднання) |
| 8 | **`втЕРП_OpEx`** ⚠️ NEW | `втЕРП_Расх_Детали` JOIN `втPL_ДДС` | OpEx виокремлено з оригінального `втЕРП_ПоPL_Расх` для Source=ERP_OpEx |
| 9 | **`втЕРП_CoGS_ПоPL`** ⚠️ NEW | `втЕРП_CoGS_Детали` JOIN `втPL_ДДС` | CoGS виокремлено для Source=ERP_CoGS |
| 10 | `втЕРП_ПоPL_Доходы` | `втЕРП_Доходы_Детали` JOIN `Справочник.А_Статьи_PL` ПО `СтатьяДоходов` | Доходи прив'язані до PL |
| 11 | `втЕРП_БезPL_Расх` | `втЕРП_Расх_Детали` ВНЕ `втPL_ДДС` | Аномалії — розходи без PL-маппінга |
| 12 | `втЕРП_БезPL_Доход` | `втЕРП_Доходы_Детали` ВНЕ `Справочник.А_Статьи_PL` | Аномалії — доходи |
| 13 | `втКазна_ПоPL` | `втКазна_ПоПодрДДС` JOIN `втPL_ДДС` | Каса прив'язана до PL через ДДС |
| 14 | `втКазна_БезPL` | `втКазна_ПоПодрДДС` ВНЕ `втPL_ДДС` | Каса без PL-зв'язку |

⚠️ **Ключова модифікація vs оригіналу Reports/А_ОтчетPL**: оригінал має ОДНЕ `втЕРП_ПоPL_Расх` що об'єднує OpEx + CoGS у одному CTE через UNION ALL. Для нашого регістру треба РОЗДІЛИТИ ці два потоки, щоб у Power BI можна було обрахувати [Виручка ЕРП] - [Собівартість] = [Валова маржа]. Тому 2 окремі CTE.

### Фінальний UNION ALL — 8 гілок з літеральним Source

```sql
ВЫБРАТЬ
    &Организация КАК Организация,
    Подразделение, Подразделение.А_НаправлениеДеятельности КАК НаправлениеДеятельности,
    СтатьяPL, Группа, ДДС, Контрагент, Документ КАК Документ_Источник,
    ЗНАЧЕНИЕ(Перечисление.А_ИсточникPL.PL_Excel) КАК Source,
    NULL КАК СтатьяДоходов, NULL КАК СтатьяРасходов,
    NULL КАК ВалютаОригинала, 1 КАК Курс,
    СуммаPL КАК СуммаПланГрн, СуммаФ1 КАК СуммаПланФ1Грн, СуммаФ2 КАК СуммаПланФ2Грн,
    0 КАК СуммаЕРПГрн, 0 КАК СуммаКазнаГрн
ИЗ втPL_Строки

ОБЪЕДИНИТЬ ВСЕ

[same shape, Source=ERP_OpEx, СуммаЕРПГрн з втЕРП_OpEx, plans=0]
ОБЪЕДИНИТЬ ВСЕ
[Source=ERP_CoGS, з втЕРП_CoGS_ПоPL]
ОБЪЕДИНИТЬ ВСЕ
[Source=ERP_Income, fill СтатьяДоходов]
ОБЪЕДИНИТЬ ВСЕ
[Source=ERP_БезPL_Расх]
ОБЪЕДИНИТЬ ВСЕ
[Source=ERP_БезPL_Доход]
ОБЪЕДИНИТЬ ВСЕ
[Source=Казна_PL, СуммаКазнаГрн = Приход - Расход (нетто)]
ОБЪЕДИНИТЬ ВСЕ
[Source=Казна_БезPL]
```

**18 колонок** (8 dim + 4 attr + 5 res = 17, плюс Source тепер dim — итого 9 dim + 4 attr + 5 res). Колонки точно відповідають структурі регістру.

### Параметри запиту

| Параметр | Джерело | Призначення |
|---|---|---|
| `&НачалоПериода` | `НачалоМесяца(Месяц)` | Початок місяця |
| `&КонецПериода` | `КонецМесяца(Месяц)` | Кінець місяця |
| `&ВключатьДочерние` | `Объект.ВключатьДочерние` | Boolean — фільтр ієрархії підрозділів |
| `&ДДСCoGS` | Функція `ПолучитьДДСПриёмникCoGS()` (та сама що в Reports/А_ОтчетPL) | UUID статті ДДС з прапором `А_ПриёмникСебестоимостиПродажPL = Истина` |
| `&Организация` | `Объект.Организация` | Підставляється в кожну гілку UNION як значення виміру `Организация` |

ЗапросДубль = Новый Запрос;

## А_ФинРез_DDS.ОбработкаПроведения

**Файл:** `Documents/А_ФинРез_DDS/Ext/ObjectModule.bsl` (223 рядки).

### Структура — 1 фінальний UNION з 3 гілок

Без проміжних CTE — простіша архітектура. Запит читає напряму 3 регістри обороту:

#### Гілка 1: ERP_Безнал

```sql
ВЫБРАТЬ
    Б.Регистратор.Дата КАК Период,
    Б.Организация, Б.Подразделение,
    Б.Подразделение.А_НаправлениеДеятельности,
    Б.БанковскийСчет КАК БанковскийСчетКасса,    -- composite-сумісне з Касою
    Б.СтатьяДвиженияДенежныхСредств КАК СтатьяДДС,
    Б.СтатьяДвиженияДенежныхСредств.А_РазделCFS КАК CFS_Section,  -- денормалізація!
    Б.Контрагент, Б.Договор,
    Б.Регистратор КАК Документ_Источник,
    Б.ВидДвижения,                                -- Поступление/Списание
    Б.БанковскийСчет.ВалютаДенежныхСредств КАК ВалютаОригинала,
    1 КАК Курс,
    ВЫБОР КОГДА Б.СуммаПриход <> 0 ТОГДА Б.СуммаПриход ИНАЧЕ Б.СуммаРасход КОНЕЦ КАК СуммаГрн,
    [та сама сума] КАК СуммаВалОригинала,
    ЗНАЧЕНИЕ(Перечисление.А_ИсточникDDS.ERP_Безнал) КАК Source
ИЗ РегистрНакопления.ДенежныеСредстваБезналичные.Обороты(&НачалоПериода, &КонецПериода, Регистратор, ) КАК Б
ГДЕ Б.СуммаПриход <> 0 ИЛИ Б.СуммаРасход <> 0
```

#### Гілка 2: ERP_Нал

Те саме, але:
- `Касса` замість `БанковскийСчет` (поле іншого імені!)
- `Касса.ВалютаДенежныхСредств` для ВалютаОригинала
- Source = `ERP_Нал`

#### Гілка 3: Казна

Інша структура — регістр `А_ДвиженияДенегИзКазны` має інші виміри:

```sql
ВЫБРАТЬ
    К.Регистратор.Дата КАК Период,
    &Организация КАК Организация,                  -- регістр НЕ має Организация!
    К.Подразделение,
    К.Подразделение.А_НаправлениеДеятельности,
    К.БанковскийСчетКасса,
    К.СтатьяДвиженияДенежныхСредств КАК СтатьяДДС,
    К.СтатьяДвиженияДенежныхСредств.А_РазделCFS КАК CFS_Section,
    NULL КАК Контрагент,                          -- регістр НЕ має Контрагент!
    NULL КАК Договор,                             -- НЕ має Договор!
    К.ДокументДвиженияКазны КАК Документ_Источник,
    -- Обчислюємо ВидДвижения зі знаку СуммаОборот:
    ВЫБОР КОГДА К.СуммаОборот > 0 ТОГДА ЗНАЧЕНИЕ(Перечисление.ТипыДвиженияДенежныхСредств.Поступление)
                                  ИНАЧЕ ЗНАЧЕНИЕ(Перечисление.ТипыДвиженияДенежныхСредств.Списание) КОНЕЦ КАК ВидДвижения,
    NULL КАК ВалютаОригинала,                     -- регістр Казна не має валюти
    1 КАК Курс,
    АБС(К.СуммаОборот) КАК СуммаГрн,             -- абсолютна сума
    АБС(К.СуммаОборот) КАК СуммаВалОригинала,
    ЗНАЧЕНИЕ(Перечисление.А_ИсточникDDS.Казна) КАК Source
ИЗ РегистрНакопления.А_ДвиженияДенегИзКазны.Обороты(&НачалоПериода, &КонецПериода, Регистратор, ) КАК К
ГДЕ К.СуммаОборот <> 0
```

### GROUP BY dedup ⚠️ DEVIATION

**Problem:** РКО (РасходныйКассовыйОрдер) одночасно потрапляє у:
- `ДенежныеСредстваНаличные` (Гілка 2 → Source=ERP_Нал)
- `А_ДвиженияДенегИзКазны` (Гілка 3 → Source=Казна)

Без обробки ці 160 рядків зберігаються двічі і ламають unique-key constraint регістру.

**Fix:** додано фінальний `СГРУППИРОВАТЬ ПО` усіх вимірювань + `СУММА(СуммаГрн)`:

```sql
ВЫБРАТЬ
    Период, Организация, Подразделение, ..., Источник,
    СУММА(СуммаГрн) КАК СуммаГрн,
    СУММА(СуммаВалОригинала) КАК СуммаВалОригинала
ИЗ ([UNION 3 гілок])
СГРУППИРОВАТЬ ПО
    Период, Организация, Подразделение, [...],
    Source, CFS_Section, ВидДвижения, ...
```

**Result:** 4812 рядків UNION → 4652 у регістрі (160 cross-branch duplicates merged).

### CFS_Section денормалізація

JOIN на реквізит `СтатьяДДС.А_РазделCFS` робиться у самому запиті (line `Б.СтатьяДвиженияДенежныхСредств.А_РазделCFS`). 1С автоматично переходить через крапку до реквізиту довідника. Завантажується значення EnumRef.А_РазделыCFS у поле CFS_Section регістру.

⚠️ **Поточний стан:** усі 425 статей ДДС мають `А_РазделCFS = ПустаяСсылка` (фінансист не заповнив). Тому в регістрі `CFS_Section = NULL` для всіх 4652 рядків. Power BI слайсер CFS_Section покаже `(Blank)` доки фінансист не заповнить статті.

### Параметри запиту

| Параметр | Джерело |
|---|---|
| `&НачалоПериода`, `&КонецПериода` | З `НачалоМесяца(Месяц)` / `КонецМесяца(Месяц)` |
| `&Организация` | З шапки документа (для гілки Казна де регістр не має Организация) |

### Дублікат-захист

Аналогічний А_ФинРез_PL, але без `ВключатьДочерние` (його немає в А_ФинРез_DDS):
```bsl
ГДЕ Док.Организация = &Организация И Док.Месяц МЕЖДУ &НачМесяца И &КонМесяца
```

### Performance

За лютий 2026: 3-15 сек. Σ записів = **4652 рядки** (1828 ERP_Безнал + 351 ERP_Нал + 2473 Казна).

## Поведінкові нюанси

### 1. .Обороты(Регистратор) vs raw register

`.Обороты(Регистратор)` віртуальна таблиця **не повертає всі реквізити** — тільки виміри + ресурси регістра. Для отримання реквізитів регістра треба:
- Або сирий регістр: `ИЗ РегистрНакопления.X КАК Р` + WHERE Период МЕЖДУ
- Або ВЫРАЗИТЬ через регістратор: `Б.Регистратор.Подразделение`

Ми використовуємо `.Обороты(Регистратор)` для агрегації по періоду + регістратору, але виміри типу Підрозділ/Контрагент тягнемо через `Б.Подразделение` напряму (це доступно через alias).

### 2. ВидДвижения тип fix

Spec §3.6 хибно вказав тип `EnumRef.ВидыДвиженийДенежныхСредств` (55-значне CFS-категорійне перерахування на кшталт `ВыручкаОтПродажи`, `ОплатаТруда`, `ВыплатаДивидендов`...). Реальний тип у регістрах ДС — `ТипыДвиженияДенежныхСредств` (2 значення Поступление/Списание).

**Виправлено у Stage 1.12** (commit `297041586`): тип реквізиту регістру `А_ОтчетDDS_Свод.ВидДвижения` змінено на `EnumRef.ТипыДвиженияДенежныхСредств`. Без цього `Загрузить()` падав з type mismatch.

### 3. Source як Dimension не Attribute (PnL)

⚠️ DEVIATION: spec §3.4 вказав Source у списку Атрибутів. Але це призводило до collapse рядків з різним Source (бо unique-key по dim не включав Source). Виправлено перенесенням Source у Dimensions у Stage 1.10.

**Architecturally correct** — у OLAP-моделях Source-маркери завжди в Dimensions для slowly-changing-attribute pattern.

### 4. Auto-fill при створенні

Обидва документи мають `ОбработкаЗаполнения`:
```bsl
Якщо НЕ ЗначениеЗаполнено(Организация) Тогда
    Организация = А_Привилегированный.А_ПолучитьОрганизациюУпр();
КонецЕсли;
Якщо НЕ ЗначениеЗаполнено(Месяц) Тогда
    Месяц = НачалоМесяца(ТекущаяДатаСеанса());
КонецЕсли;
```

Користувач відкриває новий документ → Організація і Місяць заповнені дефолтами; залишається натиснути "Провести".
