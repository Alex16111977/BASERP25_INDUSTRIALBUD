## Архітектурний паттерн (обидва документи)

```bsl
Процедура ОбработкаПроведения(Отказ, РежимПроведения)

    // 1. ДУБЛІКАТ-ЗАХИСТ — один проведений документ на (Организация, Месяц)
    [перевірка чи є інший проведений документ за той же місяць]
    Якщо знайдено: Отказ=Істина; Возврат

    // 2. ЕНЕЙБЛ ЗАПИСУ
    Движения.<Регистр>.Записывать = Истина;

    // 3. ЗАПИТ — CTE з фінальним UNION ALL з колонкою Источник + dedupe SELECT
    Запрос = Новый Запрос;
    Запрос.Текст = СформироватьЗапрос();
    Запрос.УстановитьПараметр(...);

    // 4. ПАКЕТНИЙ ЗАПИС у регістр
    ТЗ = Запрос.Выполнить().Выгрузить();
    Движения.<Регистр>.Загрузить(ТЗ);

    // 5. (Stage v2, тільки PL) Drill-down register update
    Движения.<Регистр>.Записать(); // дочекатись фіксації
    МассивДок = ЗібратиУнікальніДокументиДвиженія(ТЗ);
    РегистрыСведений.А_ДокументРасшифровка.ОбновитьПоДокументам(МассивДок);

КонецПроцедуры
```

### Stage v2.2 (2026-05-06): Income mapping refactor через ДДС-ланцюжок

**Зміна:** реквізит `Справочник.А_Статьи_PL.СтатьяДоходов` **видалено** з конфігурації. Дохідний mapping переведено на той самий ДДС-механізм що OpEx/CoGS:

```
Стаття доходу (ПрочиеДоходы.СтатьяДоходов / ВыручкаИСебестоимостьПродаж.ВыручкаОтПродаж)
   ↓ deref
ПВХ.СтатьиДоходов.А_СтатьяДвиженияДенежныхСредств
   ↓ JOIN втPL_ДДС.ДДС
Справочник.А_Статьи_PL.Статьи (ТЧ — pairs PL × ДДС)
   ↓
СтатьяPL у регістрі А_ОтчетPL_Свод
```

**8 правок у `СформироватьЗапросСверткиPL()`:**
- втPL CTE — прибрано `ТЧ.Статья.СтатьяДоходов` зі SELECT і GROUP BY (бо реквізит видалений)
- Section 1 (PL_Excel) — `СтатьяДоходов = ПустаяСсылка`, `СтатьяДД = ПустаяСсылка` (план з Excel не специфікує дохідну аналітику)
- Section 4 (PL_ЕРП Income з PL): JOIN змінено з `Справочник.А_Статьи_PL ON PL.СтатьяДоходов = Д.СтатьяДоходов` на `втPL_ДДС ON PLДДС.ДДС = Д.СтатьяДоходов.А_СтатьяДвиженияДенежныхСредств`. SELECT/GROUP BY: `PL.Ссылка → PLДДС.СтатьяPL`
- Section 6 (ERP_БезPL_Доход): фільтр змінено на `НЕ Д.СтатьяДоходов.А_СтатьяДД В (ВЫБРАТЬ PLД.ДДС ИЗ втPL_ДДС)`

**Узгодження ПВХ.СтатьиДоходов** (Phase A — ручна правка фінансистом):
- "Выручка от продаж" → А_СтатьяДД: "Поступление от заказчика" → **"Продажи"** (узгоджено з ТЧ "Статьи" А_Статьи_PL "Виручка от продаж")

### Реквізит `Документ.А_ОтчетPL.НеПроводитьВСверку` — фільтр чернеток

Прапор-чернетка на документі-листі плану з Excel. Реалізовано у CTE `втPL`:

```sql
ИЗ Документ.А_ОтчетPL.ДанныеОтчета КАК ТЧ
ГДЕ ТЧ.Ссылка.Дата МЕЖДУ &НачалоПериода И &КонецПериода
    И НЕ ТЧ.Ссылка.ПометкаУдаления
    И НЕ ТЧ.Ссылка.НеПроводитьВСверку    -- ← виключає чернетки з регістра
```

**Семантика:** план з прапором `НеПроводитьВСверку = Истина` **НЕ потрапляє** у `А_ОтчетPL_Свод` → не йде у Fact_PnL → не у Power BI. **Алe** видний у `Отчет.А_ОтчетPL` (звіт-UI), бо там фільтр відсутній — це навмисна асиметрія для роботи фінансиста з чернетками.

**Workflow для фінансиста при зміні прапора:**
1. Поставити/зняти прапор у `Документ.А_ОтчетPL`
2. **Перепровести** відповідний `Документ.А_ФинРез_PL` за той же місяць (інакше регістр не оновиться)
3. Re-run ETL Ai_Olap (або дочекатися Windows Scheduler 02:00)

Деталі бізнес-логіки чернеток — у `knowledge_PL/pl_report_architecture_analyst.md` §"Чернетки PL".

### Структура запиту — 5 CTE + фінальний 6-секційний UNION + GROUP BY dedupe

#### CTE (5 — Казна повністю прибрана)

| # | CTE | Джерело | Призначення |
|---|---|---|---|
| 1 | `втPL` | `Документ.А_ОтчетPL.ДанныеОтчета` | План з Excel: 1 рядок на (PL-стаття × Підрозділ × Документ). Сума, СуммаФома1, СуммаФорма2 |
| 2 | `втPL_ДДС` | `Справочник.А_Статьи_PL.Статьи` | Мапа PL-стаття → ДДС (унікальність гарантовано модулем об'єкта) |
| 3 | `втЕРП_Расх` | `РегНакоп.ПрочиеРасходы.Обороты(Регістратор)` + ФизЛицо CASE для АвансовогоОтчёта | Розходи ERP. **Stage v2:** додано `ВЫБОР КОГДА Регистратор ССЫЛКА Документ.АвансовыйОтчет ТОГДА Регистратор.ПодотчетноеЛицо ИНАЧЕ NULL КОНЕЦ КАК ФизическоеЛицо` |
| 4 | `втЕРП_Дох` | UNION (`ВыручкаИСебестоимостьПродаж` + `ПрочиеДоходы.Обороты`) | Доходи з 2 джерел |
| 5 | `втЕРП_CoGS` | `ВыручкаИСебестоимостьПродаж` (поле `Стоимость`) | Себестоимість |

**ПРИБРАНО** (Stage v2):
- `втКазна_ПоПодрДДС`, `втКазна_ПоPL`, `втКазна_БезPL` — Казна повністю видалена з PnL.
- `втЕРП_Расх_Детали`, `втЕРП_Доходы_Детали`, `втЕРП_OpEx`, `втЕРП_CoGS_ПоPL`, `втЕРП_БезPL_*` — окремі CTE для аномалій злиті у комбіновані секції UNION.

### Фінальний UNION ALL — 6 секцій (з фінальним GROUP BY)

```sql
ВЫБРАТЬ
    ... 11 dim полів ...
    СУММА(СуммаФ1_Excel), СУММА(СуммаФ2_Excel), СУММА(Сумма_Excel),
    СУММА(СуммаФ1), СУММА(СуммаФ2), СУММА(Сумма)
ИЗ (
    -- Секція 1: PL_Excel
    ВЫБРАТЬ &Организация КАК Организация, ..., 
        ЗНАЧЕНИЕ(Перечисление.А_ИсточникPL.PL_Excel) КАК Источник,
        СуммаФ1_Excel = СуммаФомa1, СуммаФ2_Excel = СуммаФорма2, Сумма_Excel = Сумма,
        0 КАК СуммаФ1, 0 КАК СуммаФ2, 0 КАК Сумма
    ИЗ втPL

    ОБЪЕДИНИТЬ ВСЕ
    
    -- Секція 2-6: PL_ЕРП (5 потоків)
    -- ...OpEx (втЕРП_Расх JOIN втPL_ДДС)
    -- ...CoGS (втЕРП_CoGS JOIN на &ДДСCoGS)
    -- ...Income (втЕРП_Дох JOIN на А_Статьи_PL ПО СтатьяДоходов)
    -- ...БезPL_Расх (втЕРП_Расх ВНЕ втPL_ДДС) — Аномалії
    -- ...БезPL_Доход (втЕРП_Дох ВНЕ А_Статьи_PL) — Аномалії
    -- Усі 5 секцій мають Источник = ЗНАЧЕНИЕ(Перечисление.А_ИсточникPL.PL_ЕРП)
) КАК Выр
СГРУППИРОВАТЬ ПО
    Выр.Организация, Выр.Подразделение, Выр.Источник, Выр.Статья,
    Выр.СтатьяДвиженияДенежныхСредств, Выр.Контрагент, Выр.ФизическоеЛицо,
    -- !!! NULL fallback для службових рухів ВыручкаИСебестоимостьПродаж:
    ВЫБОР КОГДА Выр.ДокументДвижения = НЕОПРЕДЕЛЕНО ТОГДА Выр.Регистратор ИНАЧЕ Выр.ДокументДвижения КОНЕЦ,
    Выр.СтатьяДоходов, Выр.СтатьяРасходов, Выр.Аналитика
```

**Критичні Stage v2 фічі у запиті:**

#### 1. Ф1/Ф2 split за Регістратор
```sql
ВЫБОР КОГДА Регистратор ССЫЛКА Документ.ПриходныйКассовыйОрдер 
        ИЛИ Регистратор ССЫЛКА Документ.РасходныйКассовыйОрдер 
   ТОГДА 0
   ИНАЧЕ Сумма
КОНЕЦ КАК СуммаФ1,

ВЫБОР КОГДА Регистратор ССЫЛКА Документ.ПриходныйКассовыйОрдер 
        ИЛИ Регистратор ССЫЛКА Документ.РасходныйКассовыйОрдер 
   ТОГДА Сумма
   ИНАЧЕ 0
КОНЕЦ КАК СуммаФ2
```

- CoGS секція: тривіальний (всі Ф1, бо composite не містить ПКО/РКО) — `Сумма КАК СуммаФ1, 0 КАК СуммаФ2`.
- Дох секція: тільки ПКО можливий для доходів (РКО — тільки витрати) — обробляється тим же CASE.

#### 2. Аналитика String 200

Семантика залежить від секції UNION:

| Секція UNION | Аналитика |
|---|---|
| 1. PL_Excel | **`ВЫРАЗИТЬ("" КАК Строка(200))`** — пусто (Stage v2.3); коментар у окремому полі `Комментарий` 1000 chars |
| 2-6. PL_ЕРП (OpEx, CoGS, Income, БезPL_Расх, БезPL_Доход) | `Контрагент.Наименование` / `ФизЛицо.Наименование` (для АвансовогоОтчета) |

```sql
-- PL_ЕРП секції:
ВЫРАЗИТЬ(
    ВЫБОР
        КОГДА Контрагент <> NULL ТОГДА Контрагент.Наименование
        КОГДА ФизЛицо    <> NULL ТОГДА ФизЛицо.Наименование
        ИНАЧЕ ""
    КОНЕЦ КАК Строка(200)
) КАК Аналитика

-- PL_Excel секція (Stage v2.3):
ВЫРАЗИТЬ("" КАК Строка(200)) КАК Аналитика
```

Тип `Строка(200)` обов'язковий у всіх 6 секціях — UNION ALL вимагає однакових типів колонок.

#### 3. NULL fallback на Регистратор для ВыручкаИСебестоимостьПродаж
**Проблема:** Регістр `ВыручкаИСебестоимостьПродаж` має поле `ДокументДвижения` що буває NULL для службових рухів (375 рядків з NULL у лютому 2026). Без fallback — два рядки з NULL у `ДокументДвижения` дають однаковий ключ RecorderSubordinate → exception при `Загрузить()`.

**Рішення:** у фінальному `СГРУППИРОВАТЬ ПО` поле `ДокументДвижения` замінено на:
```sql
ВЫБОР КОГДА Выр.ДокументДвижения = НЕОПРЕДЕЛЕНО ТОГДА Выр.Регистратор ИНАЧЕ Выр.ДокументДвижения КОНЕЦ
```

#### 4. Фінальний СГРУППИРОВАТЬ ПО — обов'язковий dedupe
Без цього групування — два рядки з однаковими 11 вимірами в межах одного регістратора = exception при `Загрузить()` (бо ключ RecorderSubordinate = (Регістратор + ВсіВиміри)).

### Структура — 1 фінальний UNION з 3 гілок

Без змін Stage 1.12 (`297041586`). Запит читає напряму 3 регістри обороту:

#### Гілка 1: ERP_Безнал
```sql
ВЫБРАТЬ ... ИЗ РегистрНакопления.ДенежныеСредстваБезналичные.Обороты(...) КАК Б
ГДЕ Б.СуммаПриход <> 0 ИЛИ Б.СуммаРасход <> 0
```

#### Гілка 2: ERP_Нал
Те саме, але `Касса` замість `БанковскийСчет`.

#### Гілка 3: Казна (зберігається у DDS-конвеєрі)
```sql
ВЫБРАТЬ ... ИЗ РегистрНакопления.А_ДвиженияДенегИзКазны.Обороты(...) КАК К
ГДЕ К.СуммаОборот <> 0
```

### GROUP BY dedup
Фінальний `СГРУППИРОВАТЬ ПО` усіх вимірювань + `СУММА(СуммаГрн)` для злиття 160 cross-branch duplicates (РКО потрапляє і у `ДенежныеСредстваНаличные`, і у `А_ДвиженияДенегИзКазны`).

### CFS_Section денормалізація
JOIN на `СтатьяДДС.А_РазделCFS` у самому запиті.

### Performance
За лютий 2026: 3-15 сек. Σ записів = **4652 рядки** (1828 ERP_Безнал + 351 ERP_Нал + 2473 Казна).

## А_ФинРез_DDS.ОбработкаПроведения — Stage v3 (2026-05-08)

**Файл:** `Documents/А_ФинРез_DDS/Ext/ObjectModule.bsl` — повністю переписано під нову структуру `РегСв.А_ОтчетDDS_Свод`.

### Нова структура регістру А_ОтчетDDS_Свод

- **14 вимірів:** ВидДвижения, ТипДенежныхСредств, **Источник** (4 значення: ЕРП/Казна/План/ПланОбъекта), ХозяйственнаяОперация, Организация, Подразделение, ДенежныеСредства (composite БанкСчет/Касса/КассыККМ/...), СтатьяДвиженияДенежныхСредств, Контрагент, Договор, ФизическоеЛицо, Валюта, ДокументДвижения (composite, всі джерельні документи), Аналитика (Строка)
- **5 ресурсів:** Сумма (факт грн), СуммаВВалюте, **СуммаКазна**, **СуммаПлан**, **СуммаПланОбъект**
- **WriteMode:** Nonperiodical RecorderSubordinate (ключ — Регістратор + 14 вимірів)

### 4 гілки UNION ALL → втВсе → фінальний GROUP BY

```
[Branch 1A: ЕРП Безнал] — РегНакоп.ДенежныеСредстваБезналичные (raw, не Обороты!)
                          СтатьяДДС у RAW як реквізит, ВидДвижения — стандартний реквізит
[Branch 1B: ЕРП Нал]    — РегНакоп.ДенежныеСредстваНаличные (raw)
[Branch 2:  Казна]       — РегНакоп.А_ДвиженияДенегИзКазны (raw, signed Сумма)
[Branch 3:  План]        — РегНакоп.А_БюджетыНаМесяц.Обороты(...) +
                            ⚠️ КРИТИЧНО: WHERE Пл.Регистратор.Дата МЕЖДУ &НачПер И &КонПер
                          (без цього коригуючі бюджет-документи з Період<>Дата ламають свёртку)
```

Кожна гілка → 5 ресурсів (Сумма / СуммаКазна / СуммаПлан / СуммаПланОбъект — лише один заповнений у строці).

### Знакова логіка плану

Сума плану береться зі знаком за `СтатьяДДС.А_ТипПоказателя`:
- `Приход` → `+СуммаОборот`
- `Расход` (або порожньо) → `-СуммаОборот`

### Розкладка плану по `ВидПериода`:

- `ВидПериода = Месяц` → запис іде в `СуммаПлан`, Источник = `План`
- `ВидПериода = Объект` → запис іде в `СуммаПланОбъект`, Источник = `ПланОбъекта`

### Заглушки

- ХозОперация для Казни/Плану — `&ХозОпЗаглушка = АвансовыйОтчет` (першій у перерахуванні; реквізит регістру `Заполнить=ShowError`)
- Контрагент/Договор/ФизЛицо/Аналитика — `ПустаяСсылка()` / `""` (поки що без LEFT JOIN; додати при потребі)

### CRITICAL fix (Stage v3): фільтр `Регистратор.Дата` для Branch 3

Без цього фільтра коригуючі бюджет-документи (`А_БюджетМесяц` з `ВидВерсии=Корректировка` що пишуть рухи з `Период=ДокументОснование.Дата` — інший місяць) з'являються в `.Обороты()` декількох місячних А_ФинРез_DDS, що призводить до колізії ключа `Запись с такими ключевыми полями существует` в RecorderSubordinate.

## Поведінкові нюанси

### 1. .Обороты(Регистратор) vs raw register
`.Обороты(Регистратор)` віртуальна таблиця **не повертає всі реквізити** — тільки виміри + ресурси регістра. Реквізити тягнемо через `Б.Регистратор.<реквізит>` напряму (це доступно через alias).

### 2. ВидДвижения тип fix (Stage 1.12)
Реквізит регістру `А_ОтчетDDS_Свод.ВидДвижения` = `EnumRef.ТипыДвиженияДенежныхСредств` (Поступление/Списание), не `ВидыДвиженийДенежныхСредств`.

### 3. Источник як Dimension не Attribute (PnL)
⚠️ Спочатку (Stage 1) Source був у Атрибутах, що призводило до collapse. Stage 1.10 — переніс у Dimensions. Stage v2 — rename `Source → Источник`, тип залишився EnumRef.А_ИсточникPL (тепер 2 значення).

### 4. RecorderSubordinate ключ = (Регістратор, ВсіВиміри) — критично
Два рядки з однаковими вимірами в межах одного регістратора = exception при `Загрузить()`. Завжди фінальний `СГРУППИРОВАТЬ ПО` всіх вимірах + `СУММА()` ресурсів. Lesson Stage v2: `feedback_recordersubordinate_dedupe.md`.

### 5. Auto-fill при створенні
Обидва документи мають `ОбработкаЗаполнения` — Організація і Місяць заповнюються дефолтами при створенні нового документа.
