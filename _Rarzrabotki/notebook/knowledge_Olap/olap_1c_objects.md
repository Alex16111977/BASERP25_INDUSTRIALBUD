## 1. Перечисление А_ИсточникPL (8 значень) ⚠️ FROZEN

**Призначення:** маркер у регістрі `А_ОтчетPL_Свод` для розділення джерел даних PnL у Power BI слайсерах.

**Файл:** `Enums/А_ИсточникPL.xml`. Commit Stage 1.1 (`868512219` після Comment fix).

| # | Имя (Code) | Synonym | Business семантика |
|---|---|---|---|
| 1 | `PL_Excel` | План из Excel | Дані з документа `А_ОтчетPL.ДанныеОтчета` (план PnL імпортований з Excel-файлу від CFO) |
| 2 | `ERP_OpEx` | ERP операционные расходы | Розходи з регістра `ПрочиеРасходы.Обороты`, прив'язані до PL-статті через `СтатьяРасходов.А_СтатьяДвиженияДенежныхСредств → ТЧ Статьи у А_Статьи_PL` (включно з ЗП через ОтражениеЗарплатыВФинансовомУчете) |
| 3 | `ERP_CoGS` | ERP себестоимость продаж | Себестоимість з регістра `ВыручкаИСебестоимостьПродаж` (поле `Стоимость`), прив'язана до PL-статті через ДДС-приймач (1 спецстаття ДДС з прапором `А_ПриёмникСебестоимостиПродажPL = Истина`) |
| 4 | `ERP_Income` | ERP выручка/доходы | Виручка з регістра `ВыручкаИСебестоимостьПродаж` (поле `СуммаВыручки`, СтатьяДоходов hardcoded = `ВыручкаОтПродаж`) + інші доходи з `ПрочиеДоходы.Обороты` |
| 5 | `ERP_БезPL_Расх` | ⚠️ Аномалія | Розходи ERP, у яких ДДС НЕ прив'язана до жодної PL-статті у `А_Статьи_PL.Статьи`. Виявляє аномалії маппінгу — фінансист має додати зв'язок |
| 6 | `ERP_БезPL_Доход` | ⚠️ Аномалія | Доходи ERP, у яких СтатьяДоходов НЕ є у `А_Статьи_PL` |
| 7 | `Казна_PL` | Каса з прив'язкою до PL | Обороти з `А_ДвиженияДенегИзКазны.Обороты`, прив'язані до PL через ДДС |
| 8 | `Казна_БезPL` | Каса без прив'язки до PL | Обороти Казни, ДДС яких не у `А_Статьи_PL` (наприклад, внутрішньогрупові переміщення) |

**⚠️ FROZEN identifiers:** ці 8 імен використовуються як рядкові литерали у DAX (`Fact_PnL[Source]="ERP_Income"`) і в Python ETL. **Будь-яке перейменування = breakage Power BI.** Якщо потрібна зміна — додавай новий, не перейменовуй існуючий.

## 3. Перечисление А_РазделыCFS (4 значення)

**Призначення:** Direct Method Cash Flow Statement — категоризація рухів ДС за міжнародним стандартом IAS 7. Денормалізується у `А_ОтчетDDS_Свод.CFS_Section` через JOIN на реквізит `СтатьяДДС.А_РазделCFS`.

**Файл:** `Enums/А_РазделыCFS.xml`. Commit Stage 1.3 (`7c015c72c`).

| # | Имя | Synonym | Що включає |
|---|---|---|---|
| 1 | `Operating` | Операционная деятельность | Виручка від продажів, оплата постачальникам, ЗП, податки на прибуток, відрядження тощо |
| 2 | `Investing` | Инвестиционная деятельность | Купівля/продаж основних засобів, нематеріальних активів, фінансових вкладень, депозитів |
| 3 | `Financing` | Финансовая деятельность | Кредити, погашення кредитів, дивіденди, фін. лізинг, додаткові внески у капітал |
| 4 | `Internal` | Внутрішні переміщення | Переказ між власними рахунками організації — **виключаються з CFS_Total** для уникнення подвійного рахунку |

**DAX behavior:** `[CFS Total] = [CFS Operating] + [CFS Investing] + [CFS Financing]` — Internal не включено навмисно.

## 4. Реквізит СтатьиДвиженияДенежныхСредств.А_РазделCFS

**Файл:** `Catalogs/СтатьиДвиженияДенежныхСредств.xml` line ~907 (нова `<Attribute>` після `А_ПриёмникСебестоимостиПродажPL`).

**Тип:** `EnumRef.А_РазделыCFS`

**Властивості:**
- `Indexing`: `Index` — потрібно для JOIN у запитах
- `Use`: `ForItem` (не для груп)
- `FillChecking`: `DontCheck` — пусте значення дозволено

**Паттерн:** копія структури `А_ПриёмникСебестоимостиПродажPL` (того самого справочника, додано 2026-04-25), з заміною Type.

**Поточний стан** (станом на 2026-05-03):
- ✅ Реквізит створений у метаданих, повторне завантаження XML підтверджено
- ⚠️ **425 статей ДДС, 0 заповнених** — фінансист має заповнити вручну. Без цього у Power BI слайсер `CFS_Section` покаже `(Blank)` для всіх рядків Cashflow.

**Як перевірити заповнення:**
```sql
ВЫБРАТЬ КОЛИЧЕСТВО(*) КАК Кол ИЗ Справочник.СтатьиДвиженияДенежныхСредств 
ГДЕ А_РазделCFS = ЗНАЧЕНИЕ(Перечисление.А_РазделыCFS.ПустаяСсылка) И НЕ ПометкаУдаления
-- Очікується: 0 (всі заповнено) для production-ready Stage 4 Power BI
```

**Commit Stage 1.4** (`82a26952a`).

## 7. Документ А_ФинРез_PL

**Файл:** `Documents/А_ФинРез_PL.xml`. ObjectModule: `Documents/А_ФинРез_PL/Ext/ObjectModule.bsl` (592 рядки). Commit Stage 1.7 (`a60317563`) + повний BSL Stage 1.10 (`3999f1efd`).

**Призначення:** проводячий документ, при проведенні робить свёртку PnL за місяць і записує у `А_ОтчетPL_Свод`.

### Реквізити шапки (5)

| Поле | Тип | Заповнення |
|---|---|---|
| `Дата` | StandardAttribute | Стандарт |
| `Номер` | StandardAttribute (String, 11 chars) | Auto |
| `Организация` | CatalogRef.Организации | За замовчуванням ТОВ ІНДАСТРІАЛБУД (через `А_Привилегированный.А_ПолучитьОрганизациюУпр()`), `FillChecking=ShowError` |

## Порядок створення (для cf-validate)

Об'єкти мають взаємні залежності типів. Правильний порядок:

1. **3 Перерахування** (без залежностей) → cf-validate green
2. **Реквізит А_РазделCFS** (depends on Перечисление.А_РазделыCFS) → green
3. **Регістри сведень** (depend on Перечислення для атрибутів)
   - ⚠️ Платформенне обмеження: RecorderSubordinate реєстр не може завантажитись без хоча б одного registratora. Workaround: тимчасово додати existing документ як registratora, потім remove у Tasks 7-8.
4. **Документи** (depend on реєстри через RegisterRecords) — спочатку зі stub ОбработкаПроведения для cf-validate
5. **Повний BSL ОбработкаПроведения** — після того як вся структура валідна
