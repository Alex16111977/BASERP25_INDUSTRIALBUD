## Чому ці числа

**Принцип:** для кожного шару архітектури (1С регістр сведень → SQL Fact → Power BI DAX) має бути однаковий результат для одного й того самого фільтру. Якщо відхилення — десь баг.

**Глобино-2 / Виручка** — це найбільший продакшн-сегмент і легко перевіряється фінансистом руками через standard report «Доходы и расходы предприятия» (упр. учёт с НДС). Якщо наш конвеєр дає те саме число — означає логіка правильна.

**Stage v2 parity:** після повного рефактору (8 sources → 2; Casна прибрана; нові Ф1/Ф2 split) acceptance число **залишилося тим самим** — 38 432 968.66 ₴ для Глобино-2 / Виручка / лютий 2026. Це доводить що рефактор не зачепив бізнес-логіку.

## Pipeline Acceptance (для Stage 3 ETL — Stage v2 структура)

Після успішного `python main.py`:

```sql
-- 1. Загальна parity (1С регістр vs SQL Fact)
SELECT 'РегистрСведений' AS Layer, COUNT(*) AS Rows FROM /* MCP */ ...
UNION ALL
SELECT 'Fact_PnL', COUNT(*) FROM Fact_PnL;
-- Очікується: однакова кількість в обох. Δ = 0.

-- 2. Глобино-2 еталон у Fact_PnL (Stage v2)
SELECT SUM(F.Sum_Fact)
FROM Fact_PnL F
JOIN Dim_Departments D ON D.Department_ID = F.Department_ID
JOIN Dim_Income_Articles I ON I.Income_Article_ID = F.Income_Article_ID
WHERE F.Source = N'PL_ЕРП'
  AND F.Period_Month = '2026-02-01'
  AND D.Department_Name = N'Глобино-2'
  AND I.Income_Article_Name LIKE N'Выручка от продаж%';
-- Очікується: 38432968.66

-- 3. Інваріант Sum_F1 + Sum_F2 = Sum_Fact (PL_ЕРП)
SELECT
    SUM(Sum_F1) AS F1,
    SUM(Sum_F2) AS F2,
    SUM(Sum_F1 + Sum_F2) AS F1F2,
    SUM(Sum_Fact) AS Fact,
    ABS(SUM(Sum_F1 + Sum_F2) - SUM(Sum_Fact)) AS Delta
FROM Fact_PnL
WHERE Source = N'PL_ЕРП';
-- Очікується: Delta < 0.01 ₴

-- 4. Dim_Documents наповнено
SELECT COUNT(*), COUNT(DISTINCT Document_Type_ERP) FROM Dim_Documents;
-- Очікується: ~3232 рядки, 19 видів ERP-документів (включно unknown member 0x...01)
```
