## Чому ці числа

**Принцип:** для кожного шару архітектури (1С регістр сведень → SQL Fact → Power BI DAX) має бути однаковий результат для одного й того самого фільтру. Якщо відхилення — десь баг.

**Глобино-2 / Виручка** — це найбільший продакшн-сегмент і легко перевіряється фінансистом руками через standard report «Доходы и расходы предприятия» (упр. учёт с НДС). Якщо наш конвеєр дає те саме число — означає логіка правильна.

## Cashflow Etalons (за лютий 2026)

**Базис:** проведений `Документ.А_ФинРез_DDS` за лютий 2026.

### Σ записів у регістр

```sql
ВЫБРАТЬ КОЛИЧЕСТВО(*) ИЗ РегистрСведений.А_ОтчетDDS_Свод
ГДЕ Регистратор.Месяц = ДАТАВРЕМЯ(2026,2,1) И Регистратор.Проведен
-- Очікується: 4652
```

**Чому 4652** (а не 4812):
- UNION 3 регістрів за лютий 2026 повертає 4812 рядків (1828 + 351 + 2633)
- Але після GROUP BY dedup у фінальному SELECT — 160 cross-branch duplicates коллапсуються (РКО потрапляє і в `ДенежныеСредстваНаличные` і в `А_ДвиженияДенегИзКазны`)
- Σ після dedup = 4652

### Distinct Source

```sql
ВЫБРАТЬ Source, КОЛИЧЕСТВО(*), СУММА(СуммаГрн)
ИЗ РегистрСведений.А_ОтчетDDS_Свод
ГДЕ Регистратор.Месяц = ДАТАВРЕМЯ(2026,2,1)
СГРУППИРОВАТЬ ПО Source
```

| Source | Рядків | Σ СуммаГрн |
|---|---:|---:|
| ERP_Безнал | 1828 | 5 009 938 998.60 ₴ |
| ERP_Нал | 351 | 40 090 065.48 ₴ |
| Казна | 2473 | 5 261 822 347.34 ₴ |
| **TOTAL** | **4652** | **10 311 851 411.42 ₴** |

### ERP_Безнал ≈ Σ Обороты безналу

```sql
-- Реальний регістр (raw):
ВЫБРАТЬ СУММА(Б.СуммаПриход) + СУММА(Б.СуммаРасход) КАК Валовая
ИЗ РегистрНакопления.ДенежныеСредстваБезналичные.Обороты(
    ДАТАВРЕМЯ(2026,2,1), ДАТАВРЕМЯ(2026,2,28,23,59,59))
-- Очікується: ~5 015 250 939.96
```

**Tolerance:** Δ < 0.5% (через нюанси GROUP BY у нашому SELECT vs стандартні 1С агрегати).

Реальне Δ зафіксовано: **0.106%** (5 009 938 998.60 vs 5 015 250 939.96). У межах tolerance.

### CFS_Section розподіл

⚠️ **Поточно: всі 4652 рядки мають CFS_Section = NULL** (фінансист не заповнив реквізит А_РазделCFS у статтях ДДС).

## Pipeline Acceptance (для Stage 3 ETL)

Після успішного прогону `python orchestrator.py --month 2026-02`:

```sql
-- 1. Загальна parity (1С регістр vs SQL Fact)
SELECT 
    'Регістр' AS Layer, COUNT(*) AS Rows, SUM(СуммаПланГрн) AS Sum_Plan FROM РегистрСведений.А_ОтчетPL_Свод 
    WHERE Регистратор.Месяц='2026-02-01'
UNION ALL
SELECT 'Fact_PnL', COUNT(*), SUM(Sum_Plan_Grn) FROM Fact_PnL 
    WHERE Period_Month='2026-02-01';
-- Очікується: одинакові числа в обох рядках. Δ = 0.
```

```sql
-- 2. Глобино-2 еталон в Fact_PnL
SELECT SUM(F.Sum_ERP_Grn)
FROM Fact_PnL F
JOIN Dim_Departments D ON D.Department_ID = F.Department_ID
WHERE F.Source='ERP_Income' 
  AND F.Period_Month='2026-02-01'
  AND D.Department_Name='Глобино-2';
-- Очікується: 38 432 968.66
```
