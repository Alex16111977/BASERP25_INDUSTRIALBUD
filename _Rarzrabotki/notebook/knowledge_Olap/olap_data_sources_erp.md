## Документи (1)

### Документ.А_ОтчетPL — План PnL з Excel

**Призначення:** імпорт планових показників з Excel-файлу від CFO. Ручний імпорт через зовнішню обробку.

**Структура:**
- Шапка: Дата, Номер, Організація, Підрозділ, Місяць
- ТЧ `ДанныеОтчета`:
  - `Статья` (CatalogRef.А_Статьи_PL) — PL-стаття
  - `Сумма` (Number) — сумарний план
  - `СуммаФома1` (Number) — деталізація Форма 1
  - `СуммаФорма2` (Number) — деталізація Форма 2
  - `Комментарий` (String) — коментар фінансиста

**Як використовується у А_ФинРез_PL.ОбработкаПроведения:**
```sql
ВЫБРАТЬ

    ТЧ.Ссылка.Подразделение КАК Подразделение,
    ТЧ.Статья КАК СтатьяPL,
    СУММА(ТЧ.Сумма) КАК СуммаPL,
    СУММА(ТЧ.СуммаФома1) КАК СуммаФ1,
    СУММА(ТЧ.СуммаФорма2) КАК СуммаФ2
ИЗ Документ.А_ОтчетPL.ДанныеОтчета КАК ТЧ
ГДЕ ТЧ.Ссылка.Дата МЕЖДУ &НачалоПериода И &КонецПериода
    И НЕ ТЧ.Ссылка.ПометкаУдаления
СГРУППИРОВАТЬ ПО ТЧ.Ссылка, ТЧ.Ссылка.Подразделение, ТЧ.Статья
```

## Регістри накопичення для PnL (Stage v2: 3 — Казна прибрана)

### 1. ВыручкаИСебестоимостьПродаж ⚠️ Stage v2 NULL fallback

**Призначення:** виручка від продажу + собівартість проданих товарів/послуг.

**Регістратори:** Реалізації, Корекції реалізацій, Акти виконаних робіт, Повернення.

**Поля для свёртки:**
- `Период`, `Регистратор`, `Активность`
- `Подразделение`
- `ДокументДвижения` (composite ref) — ⚠️ **буває NULL для службових рухів** (375 рядків з NULL у лютому 2026)
- `СтатьяДоходов` (NB: для виручки часто hardcoded `ВыручкаОтПродаж`)
- `СуммаВыручки` — Виручка з ПДВ → у Stage v2 потрапляє з СтатьяДоходов!=NULL
- `Стоимость`, `СтоимостьУпрБезНДС` — Себестоимість → у Stage v2 потрапляє з СтатьяРасходов!=NULL (через ДДС-приймач)

**Прив'язка до PL (Stage v2):**
- Виручка (Income): JOIN з `Справочник.А_Статьи_PL` на `СтатьяДоходов` → секція PL_ЕРП Income; якщо JOIN NULL — секція PL_ЕРП БезPL_Доход (аномалія)
- Собівартість (CoGS): hardcoded JOIN на 1 спец-ДДС з прапором `А_ПриёмникСебестоимостиПродажPL` → секція PL_ЕРП CoGS

**⚠️ Критично у Stage v2** — у фінальному `СГРУППИРОВАТЬ ПО` запиту `А_ФинРез_PL.ОбработкаПроведения` поле `ДокументДвижения` замінено на:
```sql
ВЫБОР КОГДА Выр.ДокументДвижения = НЕОПРЕДЕЛЕНО ТОГДА Выр.Регистратор ИНАЧЕ Выр.ДокументДвижения КОНЕЦ
```
Без цього fallback два рядки з NULL `ДокументДвижения` дають однаковий ключ RecorderSubordinate → exception при `Загрузить()`. Деталі: [olap_obrabotka_provedeniya.md](olap_obrabotka_provedeniya.md).

### 2. ПрочиеРасходы.Обороты

**Призначення:** ВСІ розходи ERP включно ЗП через `ОтражениеЗарплатыВФинансовомУчете`.

**Поля:**
- `Период`, `Регистратор`, `Активность`
- `Подразделение`
- `СтатьяРасходов` (ChartOfCharacteristicTypesRef.СтатьиРасходов)
- `СтатьяРасходов.А_СтатьяДвиженияДенежныхСредств` — мапа на ДДС
- `СуммаПриход` (Number) — приріст витрат

**Прив'язка до PL (Stage v2):** через `СтатьяРасходов.А_СтатьяДвиженияДенежныхСредств` → `ТЧ Статьи у А_Статьи_PL.СтатьяДвиженияДенежныхСредств`.

**ФизическоеЛицо CASE для Авансового отчёта:** Stage v2 у CTE `втЕРП_Расх` додано:
```sql
ВЫБОР КОГДА Регистратор ССЫЛКА Документ.АвансовыйОтчет ТОГДА Регистратор.ПодотчетноеЛицо ИНАЧЕ NULL КОНЕЦ КАК ФизическоеЛицо
```

**Stage v2 семантика секцій:**
- секція PL_ЕРП OpEx — ДДС знайдена у мапі А_Статьи_PL (PL-стаття!=NULL)
- секція PL_ЕРП БезPL_Расх (Аномалія) — ДДС НЕ знайдена у мапі (PL-стаття=NULL, але СтатьяРасходов!=NULL)

### 3. ПрочиеДоходы.Обороты

**Призначення:** інші доходи (курсові різниці, фінансова діяльність).

**Поля:**
- `Период`, `Регистратор`, `Активность`
- `Подразделение`, `СтатьяДоходов`, `СуммаПриход`

**Stage v2 секції:**
- PL_ЕРП Income — є у А_Статьи_PL (PL-стаття!=NULL, СтатьяДоходов!=NULL)
- PL_ЕРП БезPL_Доход (Аномалія) — нема у А_Статьи_PL (PL-стаття=NULL, СтатьяДоходов!=NULL)

### ⚠️ Stage v2: А_ДвиженияДенегИзКазны.Обороты — ВИДАЛЕНО з PnL-конвеєра

Стара Stage 1 архітектура читала цей регістр у PnL-конвеєрі (для Source=Казна_PL і Казна_БезPL). **Stage v2 повністю прибрав** Казну з PnL: 4 секції UNION (`втКазна_*`) видалено, ресурс `СуммаКазнаГрн` видалено, два Source-значення (`Казна_PL`, `Казна_БезPL`) — видалено з Перерахування.

Регістр продовжує читатись у Cashflow-конвеєрі (А_ФинРез_DDS) — див. §"Регістри для Cashflow" нижче.

**Документація переносу з Казни:** `_Rarzrabotki/notebook/knowledge/perenos_dvizheniy_iz_kazny.md`.

## Регістри накопичення для Cashflow (3)

### 1. ДенежныеСредстваБезналичные.Обороты

**Призначення:** банк (поточні рахунки, СПОТ, депозити).

**Регістратори:** ПлатежноеПоручениеИсходящее, ПоступлениеБезналичныхДенежныхСредств, СписаниеБезналичныхДенежныхСредств, ОбменВалюты, тощо.

**Поля:**
- `Период`, `Регистратор`, `Активность`
- `Организация`, `Подразделение`

- `СтатьяДвиженияДенежныхСредств`
- `Контрагент`, `Договор` (з шапки регістратора)

- `СуммаПриход`, `СуммаРасход`

**Source у А_ОтчетDDS_Свод:** `ERP_Безнал`.

### 2. ДенежныеСредстваНаличные.Обороты

**Призначення:** каса (готівка).

**Регістратори:** ПриходныйКассовыйОрдер, РасходныйКассовыйОрдер, тощо.

**Поля аналогічні Безналичных, АЛЕ:**
- **`Касса`** ⚠️ (замість `БанковскийСчет`!) — CatalogRef.Кассы
- `Касса.ВалютаДенежныхСредств` — валюта каси

**Source у А_ОтчетDDS_Свод:** `ERP_Нал`.

### 3. А_ДвиженияДенегИзКазны.Обороты (для Cashflow)

Той самий регістр що для PnL (див. вище), але інша вибірка полів:
- Знак з СуммаОборот → ВидДвижения
- Абсолютна сума → СуммаГрн

⚠️ Регістр **не має полів:** Контрагент, Договор, Организация, ВалютаДенежныхСредств. Треба підставити NULL або значення з документа `А_ФинРез_DDS.Организация`.

**Source:** `Казна`.

## Cross-branch duplicates ⚠️

**Problem:** деякі документи (наприклад РКО) реєструються одночасно у:
- `ДенежныеСредстваНаличные` (через стандартний механізм 1С)
- `А_ДвиженияДенегИзКазны` (якщо документ перенесений з Казни)

При UNION 3 гілок DDS такий РКО з'являється двічі — раз з Source=ERP_Нал, раз з Source=Казна.

**Fix у А_ФинРез_DDS.ОбработкаПроведения:** GROUP BY всіх вимірювань + СУММА у фінальному SELECT — 160 cross-branch duplicates за лютий 2026 правильно колапсуються.

Альтернатива — фільтрувати: показати тільки один Source. Не вибрана, бо тоді губиться видимість «звідки саме йде платіж» для звірки.

- ... інші стандартні (КорреспондирующийСчет, ВидДвиженияДенежныхСредств, тощо)

**Поточний стан А_РазделCFS:** 425 статей, 0 заповнено (фінансист ще не починав). Без заповнення слайсер CFS_Section у Power BI = `(Blank)`.

## SQL backend mapping (для Python ETL Stage 3 ✅)

> **Контекст:** Stage 3 (Ai_Olap) читає не через 1С Query Language, а **прямо з MSSQL backend BaseERP** (cluster mode зберігає всі регістри/документи/довідники у згенерованих таблицях `_Reference*`, `_InfoRg*`, `_Document*`). Mapping `1С_object → _SqlTableName + {1С_field: SqlColumn}` згенерований автоматично через `mapping/refresh_mapping.py` (платформенний метод `ПолучитьСтруктуруХраненияБазыДанных()`) і збережений у `_Rarzrabotki/Olap/Ai_Olap/mapping/baserp_storage.json` (56 об'єктів).
>
> Імена `_Fld<N>` залежать від послідовності створення реквізитів — після **значного** оновлення метаданих треба refresh mapping. Поточні значення нижче актуальні станом на 2026-05-03.

### Власна організація

ТОВ ІНДАСТРІАЛБУД ідентифікується по реквізиту `КодПоЕДРПОУ='40645273'` — у SQL це `_Reference329._Fld32799`. UUID організації = `0x80D3000C29BBAC2311E653F06BEE36B2`. Цей UUID зашитий у Fact-pipeline'ах як hex-літерал у WHERE; інші юр.особи фільтруються.

### Дати у BaseERP cluster backend

Усі `_Date_Time` поля зберігаються з **+2000 рік-офсетом**: документ за 2026-02-15 у MSSQL — `4026-02-15`. У Stage 3 це нейтралізується через `auto_period_params=true` в extractor + `period_offset_years: 2000` (default) у Pipeline. Якщо пишете кастомний raw_sql проти BaseERP — додавайте 2000 до Date вручну.
