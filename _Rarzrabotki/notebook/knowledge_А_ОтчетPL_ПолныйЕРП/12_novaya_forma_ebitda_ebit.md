## Формулы водопада (`РассчитатьВодопадКолонки`)

```
ФинРасх = Комиссии(056) + Проценты(075) + Курсовые разницы(076)
Налоги  = НДС/Прочие(054) + НалогНаПрибыль(057)

Маржа   = ОД − СС
EBITDA  = Маржа − ОПЗ(без амортизации) − МЗ − АЗ
EBIT    = EBITDA − Амортизация
ФинДеят = ФинДоход(055) − ФинРасх            // плюс = заработали на финансах
Чистый  = EBIT + ФинДеят − ДР − Налоги       // нижняя строка водопада
%-строка = Чистый / ОД                        // Выкл: «Рентабельность продукции, %», Вкл: «Чистый доход, %»
```

> 🔴 **21.08.2026: строки «Дивиденды» (статья 000000058) и «Прибыль в распоряжении
> компании (нераспределенная прибыль), грн» УДАЛЕНЫ из отчёта БЕЗУСЛОВНО** (в обоих
> режимах названий). Статья 000000058 вычищается из данных ДО разметки

> ОСТАВЛЕН — он нужен самому фильтру.

Знаменатель всех %-строк — операционный доход той же пары (подразделение × колонка),
как и раньше: %-строки хранят ЧИСЛИТЕЛЬ, а знаменатель лежит в поле `Знаменатель`.

**Нижняя строка не поехала.** Алгебраически водопад тождественен старому

## 🔴 Правило источника факта — СТРОГОЕ, без исключений (20.08.2026)

**Правило (решение заказчика):**

    последний месяц периода отчёта -> ТОЛЬКО регистры ЕРП;
    все более ранние месяцы        -> ТОЛЬКО документы А_ОтчетPL;
    месяц без документа            -> НОЛЬ (регистры НЕ подхватываются);
    накопительная колонка          -> документы за всю историю + регистры последнего месяца.

Отменяет пункт 3 версии 3 («месяц без документа по ветке — регистры ЕРП») и снимает
исключение для амортизации, введённое ранее в этот же день.

**Почему понадобилось.** Отчёт за 01.01–31.07.2026 в режиме сводов подтягивал регистры
в январь. Причина: свод-документы `А_ОтчетPL` (галка «Включать дочерние») есть только на
шести подразделениях — Логистика, Производство, Спецтехника, Староконстантинов,
Строительство, ЦО. Ветки **«Девелопмент» (КГ «Подгорцы» и его дома), «Внутригрупповое»,
«И.П.С.»** не покрыты свод-документами ВООБЩЕ, поэтому по ним старое правило брало
регистры за все месяцы. Заказчик выбрал предсказуемость вместо полноты.

**Цена, замеренная до правки** (период 01.01–31.07.2026, свод-режим): из отчёта уходит
**33 018 762,27** за январь–июнь (498 строк), а накопительная колонка теряет
**41 265 855,36** (включая историю до 2026). Июль не меняется. Факт из документов —
801 732 108,56 за период — не тронут.

| Месяц | Ушло из регистров |
|---|---:|
| Январь 2026 | 14 536 121,48 |
| Февраль | 2 958 056,33 |
| Март | 3 454 379,57 |
| Апрель | 4 409 700,99 |
| Май | 3 279 312,97 |
| Июнь | 4 381 190,93 |

Крупнейшие потери: КГ «Подгорцы» 19 530 340,90 · Внутригрупповое 7 329 772,20 ·
И.П.С. 2 498 887,01 — все три без свод-документов. Альтернатива, которую заказчик
отклонил: завести свод-документы PL по этим трём веткам — тогда правило сработало бы
само, без потерь.

**Следствие для EBIT.** Амортизации в документах PL нет вообще, поэтому теперь она видна
ТОЛЬКО в последнем месяце периода: EBIT = EBITDA во всех остальных месяцах.
По всей базе за июль-2026 это 740 970,97, у Глобино-2 — 68 965,72 из 406 395,51,
что есть в регистрах.

**Реализация.** Из пакета УДАЛЕНЫ временные таблицы `втМесяцыДок`, `втДДСАморт`,
`втМесяцыДокАморт` и параметр `&СтатьяАмортизации` (вместе с функцией
`ПолучитьСтатьюPLПоКоду`). Во всех четырёх ЕРП-ветках (`ПрочиеРасходы`,
`ВыручкаИСебестоимостьПродаж` ×2, `ПрочиеДоходы`) условие
`МД.ПодразделениеОтчета ЕСТЬ NULL` заменено на

    ГОД(Период) * 100 + МЕСЯЦ(Период) = &ПоследнийМесяц

Документные ветки не менялись: они и раньше отбирали месяцы `<> &ПоследнийМесяц`
(месячные колонки) и `< &ПоследнийМесяц` (накопительная).

> Запрос переносится в модуль СКРИПТОМ из проверенного `v7_full.sql`, а не руками:
> `extract_sql.py` / `inject_sql.py` в scratchpad сессии. Большой пакет опознаётся по
> содержимому (`ВЫБРАТЬ РАЗЛИЧНЫЕ` + `втСводныеПодразделения`), а НЕ по порядковому
> номеру `Запрос.Текст =` — новые вспомогательные запросы сдвигают индекс и молча
> ломают сверку.

## Условное оформление СКД

В `Template.xml` переименованы правила оформления во ВСЕХ ТРЁХ вариантах
(`PL_Объект`, `PL_СводНаправления`, `PL_Фиксы`):
«Операционная прибыль, грн» → «EBITDA, грн»; «Прибыль после вычета финансовых затрат» →
«EBIT / Операционная прибыль, грн»; «Прибыль до вычета налогов» → «Финансовая деятельность»;
«Операционная прибыль, %» → «EBITDA, %»; добавлено «EBIT / Операционная прибыль, %».
Цвета прежние: грн-показатели `#BDD7EE`, %-показатели `#C6E0B4`, группы `#D9D9D9`.

## Доход через приходный кассовый ордер — Форма 2 (20.08.2026)

**Правило:** доход, зарегистрированный `Документ.ПриходныйКассовыйОрдер`, — это касса,
значит **Форма 2**. Всё остальное на доходной стороне — Форма 1.

**Почему понадобилось.** Ф1/Ф2 у расходов задаёт измерение `ФормаPL` регистра
`ПрочиеРасходы` (Форма1 339 млн / Форма2 103 млн). У доходов отчёт формы не читал вовсе:
финальная ветка писала `СУММА(СуммаЕРП) → Ф1, 0 → Ф2`. Наличный доход показывался безналом.

> 🔴 Измерение `ФормаPL` в `РегистрНакопления.ПрочиеДоходы` **СУЩЕСТВУЕТ, но пустое во всех
> строках** — его никто не заполняет. Поэтому форму определяет ТИП РЕГИСТРАТОРА, а не
> измерение. Если однажды разметку доходов начнут вести, правило надо будет переключить
> на измерение — как у расходов.

**Где именно.** Только ветка `ПрочиеДоходы` внутри `втЕРП_Доходы_Детали`: в
`ВыручкаИСебестоимостьПродаж` ПКО регистратором быть НЕ МОЖЕТ (тип не входит в состав,
запрос падает «Несовместимые типы ССЫЛКА»), поэтому «Выручка от продаж» всегда Ф1.

Реализация — колонка-признак `Наличные` (1/0), протянутая через `втЕРП_Доходы_Детали` →
`втЕРП_ДохCoGS_PL` (у ветки CoGS всегда 0) → финальное объединение, где вместо жёсткого
`Ф1 = всё` стоит `ВЫБОР КОГДА Наличные = 1 ТОГДА ... КОНЕЦ`. Выражение признака обязано
попасть и в `СГРУППИРОВАТЬ ПО`.

**Цена вопроса (замер 20.08.2026, период 01–31.07.2026):**

| Колонка | Ф1 → Ф2 |
|---|---:|
| Июль 2026 | 486 636,00 |
| Накопительный PL | 11 180 067,45 |

Всё в статье «Доход от прочей операционной деятельности», 7 объектов
(КГ «Подгорцы» 6 800 462,45 · 6 БУДИНОК 2 953 496,00 · 10 БУДИНОК 655 293,00 ·
Строительство 248 086,00 · Спецтехника 247 750,00 · II Черга 206 980,00 · MAN №5 68 000,00).
Контроль после сборки — КГ «Подгорцы», накопительно: Ф1 766 305,33 / Ф2 10 616 231,45 /
итого 11 382 536,78 (раньше все 11,38 млн были в Ф1).

**«Итого» не меняется нигде** — это перекладка внутри строки. Поедут только Ф1/Ф2 у
операционного дохода, маржи, EBITDA, EBIT и чистого дохода; рентабельность считается
от итого и остаётся прежней.

**Граница.** В регистре ПКО-дохода 13 515 400,95, до отчёта доходит 11 180 067,45.
Разница ≈2,34 млн лежит в месяцах, ЗАКРЫТЫХ документами `А_ОтчетPL`: там Ф1/Ф2 берутся из
ручной разметки Excel (`СуммаФома1`/`СуммаФорма2`), признака «это был ПКО» в документе нет.
Правило работает только там, где факт идёт из регистров ЕРП.

Приёмка: `test_otchetpl_v6_pko_forma2_2026-08-20.py` (15/15) + `v6_full.sql`.
Проверяет главное: «Итого» не изменилось НИ В ОДНОЙ строке, из Ф1 ушло ровно столько,
сколько пришло в Ф2, и вся дельта — только строки с регистратором ПКО.

## Параметр «Названия на русском» (21.08.2026)

Булев параметр СКД `НазванияНаРусском` (по умолчанию Ложь). Вкл — отчёт выводит
названия из реквизитов `НаименованиеДляОтчетаНаРусском` справочников `А_Статьи_PL` и
`А_ГруппаСтатей_PL` (заполнены скриптом `fill_russkie_naimenovaniya_pl_2026-08-21.py`,
идемпотентным; запись — только через `ОбменДанными.Загрузка=Истина`). Ни одна цифра
не меняется — проверено приёмкой построчно.

Что переключается:

| Что | Выкл | Вкл |
|---|---|---|
| статьи | Наименование | НаименованиеДляОтчетаНаРусском («Выручка от прочей операционной деятельности», «ФА, комиссии», «Аренда техники»…) |
| группы (строки листа) | Наименование | русское («Себестоимость проданной…», «Дополнительные расходы») |
| EBIT-строки | EBIT / Операционная прибыль, грн/% | EBIT / Операционный доход, грн/% |
| %-строка итога | Рентабельность продукции, % | Чистый доход, % |
| колонки Ф1/Ф2 | «Сумма по Ф1, грн» / «Сумма по Ф2, грн» | те же — **от параметра НЕ зависят** (решение 21.08.2026 вечером: «Безнал»/«Нал» отменены; подписи ставятся ВСЕГДА, перекрывая подписи сохранённых вариантов вроде «Факт: безнал (Ф1), грн») |

Механика (все грабли словлены при реализации):

- **Статьи/группы:** служебные строковые поля `СтатьяPLРус`/`ГруппаРус` в наборе +
  `presentationExpression` у полей `СтатьяPL`/`Группа`, равный ПРОСТО служебному полю
  (паттерн `КолонкаСорт -> КолонкаPL`). 🔴 Обращение к самому полю в его же выражении
  (`Представление(СтатьяPL)`) даёт «Рекурсивное получение представления». Поэтому BSL
  (`ЗаполнитьРусскиеНаименования`) заполняет колонки в ОБОИХ режимах: Выкл — обычное
  представление, Вкл — реквизит с фолбэком. Заполнение — СТРОГО ПОСЛЕ разметки и полного
  шаблона, иначе добавленные строки останутся со старым именем и лист двоится.
- **СтрокаЛиста групп:** запрос `РазметкаГрупп` читает `НаименованиеДляОтчетаНаРусском`,
  при Вкл оно кладётся в `Разметка.Имя`.
- **Колонки Ф1/Ф2:** 🔴 у выбранного поля подпись — свойство **`Заголовок`** (в
  сериализации `<title>`); «Представление» у него НЕТ — «Поле объекта не обнаружено».
  Сохранённые варианты несут СВОИ подписи выбранных полей — менять надо именно их
  (`УстановитьЗаголовкиФ1Ф2` + обход структуры, включая Таблица.Строки/Колонки; вызывается БЕЗУСЛОВНО, не под `Если НазванияНаРусском`),
  заголовок из схемы они бы перекрыли.
- **УО:** канонические списки текстов в правилах всех вариантов (`patch_uo_canon.py`) —
  старые и русские тексты сосуществуют, мёртвые (Прибыль в распоряжении, тексты
  до-EBITDA-водопада) вычищены.
- Старые сохранённые настройки без нового параметра работают как Выкл
  (`ЗначениеПараметра("НазванияНаРусском", Ложь)`).

## Колонка «PL с начала года» (24.08.2026)

Третий накопительный разрез: **с 1 января года, в котором лежит КОНЕЦ периода**, по конец
периода. Ось: месяцы → **«PL с начала года» (890000)** → «Накопительный PL» (900000) →
«План итого» (900100) — горизонт растёт слева направо. Флажок **«Выводить: PL с начала
года»** (`ВыводитьСНачалаГода`), по умолчанию **Ложь** — сохранённые варианты не меняются.

Правило источника — тот же ЗАКОН без исключений: последний месяц периода — только регистры
ЕРП, более ранние месяцы года — только документы `А_ОтчетPL`, месяц без документа — ноль.
YTD не зависит от начала периода отчёта (период «только июль» даёт тот же YTD, что и
«январь—июль»). Фиксов и плана в колонке нет, как и в накопительной.

Механика в запросе (`v8_full.sql`):
- маркер месячной колонки ужесточён с `< 900000` до `< 890000` во всех ветках
  (иначе 890000 читался бы как месяц, а фикс-срез размножал бы норму и в YTD);
- фактовые ЕРП-ветки: `ИЛИ (КЛ.КолонкаСорт = 890000 И Д.МесяцКлюч >= &КлючНачалаГода)`;
- накопительная документная ветка: `ИЛИ (КЛ.КолонкаСорт = 890000 И ГОД(Док.Дата) * 100 +
  МЕСЯЦ(Док.Дата) >= &КлючНачалаГода)`;
- новый параметр `&КлючНачалаГода` = ГОД(КонецПериода)·100 + 1.

Эталонные числа (свод, 24.08.2026): YTD января—июля 2026 итого 951 743 961,93
(= Σ месячных колонок, Ф1 868 744 493,46 / Ф2 82 999 468,48); Накопительный − YTD =
2 389 232 584,61 = документы PL прошлых лет копейка-в-копейку.

Спека: `docs/superpowers/specs/2026-08-24-pl-ytd-column-design.md`.

## Жёстко русский язык (26.08.2026)

На сервере с украинским языком сеанса отчёт выходил с «Липень 2026», «Параметри:»,
«Відбір:», «: Так/Ні», «В групі зі списку» (файл «Выгрузка отчета PL/PL по компании
07.2026.xlsx»). Решение заказчика: отчёт всегда русский, независимо от сервера. Три слоя:

1. **Месяцы** — `Формат(ТекМесяц, "Л=ru_RU; ДФ='MMMM yyyy'")`: параметр локали `Л=`
   переключает язык названий месяцев независимо от языка сеанса (доказано форматом
   ячейки табличного документа: Л=uk_UA даёт «Липень 2026», Л=ru_RU — «Июль 2026»).
2. **НСтр удалён полностью** (33 вхождения → обычные строковые литералы): НСтр зависит
   от языка сеанса и основного языка конфигурации; литералы — ни от чего. Многострочные
   литералы с `|`-переносами валидны и без НСтр.
3. **`РусифицироватьСлужебныеТексты(ТабДок)` Экспорт** — вызывается после
   `ПроцессорВывода.Вывести()`. Платформенные надписи служебной шапки (блок параметров,
   отбор, представления булевых и видов сравнения) печатаются на языке сеанса — код на
   них не влияет, поэтому готовый документ дочищается заменами. Обрабатывается ТОЛЬКО
   шапка: строки до заголовка таблицы «Статья PL» (fallback 20 строк) — данные ниже
   границы не затрагиваются (проверено приёмкой на строке «ІНДАСТРІАЛБУД ТОВ, Липень»).
   Словарь: «Параметри:»/«Відбір:», суффиксы «: Так»/«: Ні», виды сравнения (длинные
   формы РАНЬШЕ коротких: «Не дорівнює» до «Дорівнює», «Більше або дорівнює» до обоих),
   украинские месяцы (подстраховка). Экспортность — ради честной приёмки без
   украинского сервера.

Орфо-правки `НаименованиеДляОтчетаНаРусском` (утверждены заказчиком; `Наименование`
НЕ тронуто — его ключ синхронизации с Excel): 000000059 «Штраф/ мат помощь» →
«Штраф / мат. помощь», 000000054 «НДС/ Прочие налоги» → «НДС / прочие налоги».
Остальные 77 значений выверены — грамотны. МАППИНГ приёмки русских названий дополнен
обеими парами. Спека: `docs/superpowers/specs/2026-08-26-pl-hard-russian-design.md`.

## Аналитика РКО «Прочий расход ДС» = Комментарий (27.08.2026)

Расшифровка «Аналитика» у строк от `РасходныйКассовыйОрдер` с операцией
`ХозяйственныеОперации.ПрочаяВыдачаДенежныхСредств` (представление «Прочий расход ДС»)
была безлика: аналитика бралась из Контрагента, а он у таких выдач пуст (июль-2026:
49 РКО на 10,4 млн, контрагент пуст у всех, комментарий заполнен у всех).

Правило (`v9_full.sql`, ветка РКО в CASE поля `Аналитика` втЕРП_Расх_Детали и его
копия в СГРУППИРОВАТЬ ПО): операция «Прочая выдача ДС» И комментарий непуст →
`ВЫРАЗИТЬ(Комментарий КАК Строка(200))`; иначе — Контрагент, как раньше. Пустой
комментарий и остальные операции РКО ничего не теряют.

Грабли:
- `Комментарий` — строка неограниченной длины: в ВЫБОР и ГРУППИРОВАТЬ только через
  `ВЫРАЗИТЬ(… КАК Строка(200))`, иначе запрос не выполнится;
- поле «Аналитика» стало составным (ссылки + строка) — `Аналитика1` в BSL строит
  `Строка(Стр.Аналитика)`, для строки это она сама;
- CASE ветки РКО есть и в поле `Контрагент` — его НЕ трогать (там контрагент по праву);
  якорь для правки — предшествующая ветка `ОтражениеЗарплатыВФинансовомУчете`;
- представление РКО — «Расходный кассовый ордер N…» с ЛАТИНСКОЙ N, резать по «№» нельзя
  (грабля RED-теста).

Разные комментарии = отдельные строки расшифровки. Без включённой группировки
«Аналитика» вид отчёта не меняется (суммы построчно тождественны v8 — 48 322 ключа,
разница 0). Спека: `docs/superpowers/specs/2026-08-27-pl-rko-kommentariy-analitika-design.md`.
