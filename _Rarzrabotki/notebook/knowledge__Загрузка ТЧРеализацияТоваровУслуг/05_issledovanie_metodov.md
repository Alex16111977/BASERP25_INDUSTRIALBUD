решают как «судьи». Это вывод обоих исследователей и эксперимента.

## Методы: формулы и оценка

| # | Метод | Формула / суть | Плюсы | Минусы | Вердикт для нас |
|---|---|---|---|---|---|
| 0 | Нормализация-«скелет» (Unicode UTS #39) | НРег, ё→е, латинские двойники → кириллица, 8,0→8, `[*xх×]` между цифрами → разделитель, г/к→гк | без неё деградирует любая метрика: «M16» лат. ≠ «М16» кир. | сама не метрика; коды вроде S235JR надо беречь | **обязательно** → `ЕдиныеБуквы` |
| 1 | Левенштейн / Дамерау / Indel | ДП `d[i][j]=min(…)`; `sim=1−lev/max(len a, len b)`; `ratio=2·LCS/(len a + len b)` | ловит опечатки в слове | цифра весит как буква; O(len a · len b); 43 000 пар — 3,9 с | только внутри слов |
| 2 | Jaro / Jaro–Winkler | `J=(m/len a + m/len b + (m−t)/m)/3`; `JW=J+ℓ·p·(1−J)` | быстрый, для коротких строк | префиксный бонус всем «болт м16…»; цифры не различает | только внутри слов |
| 3 | Jaccard / Dice / overlap на n-граммах (pg_trgm, «Strike a match») | `J=#(A∩B)/#(A∪B)`, `D=2·#(A∩B)/(#A+#B)` | просто, ложится на язык запросов | нет IDF; overlap = 1 для вложенной строки | дешёвая альтернатива косинусу |
| 4 | Косинус TF-IDF символьных 3-грамм (string_grouper / ING) | `w=tf·idf`, `idf=ln((1+N)/(1+df))+1`, `cos=Σwa·wb/(‖a‖‖b‖)` | порядок слов, опечатки, словоформы; IDF гасит частые куски | неверный размер остаётся в топ-2/3 | **основная текстовая часть** → T |
| 5 | Косинус TF-IDF по словам | то же по токенам (обрезка до 5 букв) | лучшая одиночная метрика эксперимента (P@1 0,78) | словоформа = другой токен | вторая половина `text` в k7 |
| 6 | token_sort / token_set / WRatio (rapidfuzz) | `token_set = max(ratio(I, I+D1), …)` | порядок слов, лишние слова | **100 % для любого подмножества**: «болт м16» = все болты М16 | не использовать как балл |

| 8 | Soft TF-IDF (Cohen 2003) | TF-IDF + JW для близких токенов, порог θ | лучший гибрид в Cohen 2003 | θ хрупок, 55/65 «близки» по JW | выигрыш мал, сложность выше |
| 9 | BM25 | `Σ IDF·f·(k1+1)/(f+k1·(1−b+b·len D/avgdl))` | стандарт поиска, инвертированный индекс | балл не в [0;1] | альтернатива косинусу, не вместе |
| 10 | Атрибуты как жёсткие ограничения | мультимножество размеров; резьба, стандарт, марка, сторона; несовпадение → потолок | **единственный метод, решающий нашу проблему**: М16*55 vs М16*65 | нужен парсер и словари | **обязательно** → N и стели |
| 11 | Fellegi–Sunter (splink, dedupe) | вес уровня `log2(m/u)`, `W=Σw`, `P=2^W/(1+2^W)` | строгое сложение разнородных признаков | нужны размеченные пары | ручные веса сейчас, калибровка позже |

## Эксперимент: 84 строки × 429 остатков

**Эталон `gold.json`** — 84 записи, две разметки:
- **мягкая** — тот же тип и основные размеры;
- **строгая** — не противоречит ни один указанный атрибут. Марки ст.3/3пс/3сп/S235/С245/S275 — одна группа, S355 —
  другая. Атрибут, не указанный в карточке («Балка 20»), — не противоречие.

**Нумерация строк в исследовании** — индекс эталона `i` с нуля: строка файла = `i` + 2 (строка 35 эталона — строка 37
накладной, строка 59 — строка 61 «Болт M16*55 (DIN 933) оц.»). В [04](04_metrika_shozhesti.md) и смоуке — номера строк
файла.

Правильной позиции на складе нет:
- **мягко** — только строка 35: «Шпилька анкерна Hilti HAS 8.8 M12*220мм», на складе только HAS M16x220;
- **строго** — ещё 8 строк: швеллер 30У при 30П; болты DIN 931, DIN 601, DIN 6921 при DIN 933; нержавейка при
  оцинковке; стрижні різьбові DIN 975 класса 10.9 при 8.8 на складе (три строки; в отчёте эксперимента названы
  «шпильками»).

**Метрики:**
- P@1 — правильный товар первый; R@5 — в первой пятёрке;
- T90 / T98 — порог, при котором 90 / 98 % подсказок не ниже порога правильные;
- охват — доля строк, где правильный первый и прошёл порог;
- «ложные (пробы)» — правильный товар убран со склада, а неправильный прошёл порог. Это 83 пробы;
- «конфликты» — доля 9 строгих «нет совпадения», прошедших порог.

- **Строковые метрики (a–g) при любом пороге дают почти нулевой охват.** Неверный размер стоит так же высоко, как верный.
- **Фильтр поднимает P@1 с 0,72 до 1,00.** Но при пороге T90 почти все 9 «конфликтов» проходят по одному баллу. Поэтому
  правило k7 двойное: балл **и** фильтр.

**Метод k7:**
- `text = (cos 3-грамм + cos слов) / 2` по строке `NormU`: числа ≥ 1000, кратные 10, переводятся мм → м;
  `tf = 1 + ln(cnt)`; для терма вне корпуса `idf = ln(N+1)+1`.
- `gate` — произведение множителей:

  | Условие | Множитель |
  |---|---|
  | жёсткое число накладной найдено среди жёстких у кандидата | ×1 |
  | найдено только среди мягких | ×0,5 (точно) / ×0,9 (через мм↔м) |
  | не найдено | ×0,3 |
  | мягкие числа накладной | ×(1 − 0,15 × доля ненайденных) |
  | лишнее жёсткое число кандидата | ×0,6 за каждое |
  | в накладной нет жёстких чисел | ×0,75 |
  | конфликт резьбы или стороны | ×0,18 |
  | конфликт стандарта | ×0,6 |
  | конфликт группы стали | ×0,8 |
  | конфликт покрытия, класса прочности, класса арматуры | ×0,6 |
  | главное слово не совпало (в любую сторону) | ×0,6 |

- `score = text × gate`.
- **Зоны k7:**
  - «сильная» — `score ≥ 0,20 и gate ≥ 0,85`: точность 1,000, охват 95 % строгих строк, 0 из 83 ложных проб, 0 из 9
    конфликтов;
  - «слабая» — `score ≥ 0,10`.
- На этой накладной: **71 сильная (все верные), 12 слабых, 1 «не найдено»** (строка 35, верно). Из 12 слабых:
  - 8 — правильный размер, но другой вариант товара;
  - 4 — правильный товар, который надо проверить: анкер ↔ капсула, KNZ ×2, «для сходинок» без чисел.
- Один порог `score ≥ 0,25` без условия на фильтр хуже: точность 0,987, и 4 из 9 конфликтов становятся «сильными».

**Оговорка исследования:** эталон размечен самим агентом, пороги подобраны на тех же 84 строках. Цифры оптимистичные,
на следующей накладной их надо перепроверить.

## Что реализовано на самом деле (на 09.10.2026)

**В обработку перенесён не k7.** Работает схема «`100·(0,5T+0,5N)` + стели» по мотивам рекомендации второго
исследователя, доработанная по 14 находкам ревью. N в обработке другое: не мультимножественный Жаккар, а доля размеров
файла со штрафом за лишние. Синтез-спецификация писалась после первой версии обработки (f6880f7e9d). Она прямо отмечала
расхождение: «Эта формула на эталоне не проверялась. Её нужно заменить на k7». Решение о замене в источниках не записано.

| Аспект | k7 (эксперимент) | Обработка (`ОценкаСходства`) |
|---|---|---|
| Текст | (cos 3-грамм по всей строке + cos слов по 5 букв) / 2, `tf = 1+ln` | cos 3-грамм **только слов**, каждое слово обрамляется отдельно, `tf` = счётчик |
| Числа в тексте | да, с мм→м | нет: числа только в N |
| IDF терма вне корпуса | `ln(N+1)+1` (максимум) | 1 (минимум) |
| Числа | жёсткие и мягкие, мм↔м для ≥ 1000 | одно мультимножество, точное равенство строк |
| Комбинация | `text × gate` | `100·(0,5T+0,5N)` × множители, потом стели 75/70/49/40 |
| Атрибуты | резьба, сторона, стандарт с эквивалентами, группа стали, покрытие, класс прочности, класс арматуры, главное слово с синонимами | стандарт, марка (без групп), сторона, тип (4 буквы, двусторонне); резьба — размер `м16` |
| Пороги | сильная `score ≥ 0,20 и gate ≥ 0,85`, слабая ≥ 0,10 | кнопка ≥ 85, подсказка ≥ 60, вариант ≥ 20 |
| Проверка | `gold.json`: P@1 83/83, 0/83 проб, 0/9 конфликтов | 15 случаев ревью (`review_cases.py`) + смоук АСУБЗ; **на `gold.json` не прогонялась** |

→ Реализованная формула закрывает главный риск: неверный размер ≤ 49, другая марка или стандарт ≤ 75. Но её P@1 на
эталоне неизвестен. **Первый шаг любой доработки — прогнать `ОценкаСходства` на `gold.json`** ([10](10_kak_rabotat_i_dorabotat.md)).

## Что взято из библиотек и работ

| Источник | Что взяли | Что сознательно не взяли |
|---|---|---|
| **Unicode UTS #39 (confusables, skeleton)** | карта латинских двойников → кириллица в `ЕдиныеБуквы`; одна функция для обеих сторон | NFD-декомпозицию (не нужна) |
| **rapidfuzz** | идея `default_process`: регистр и пунктуация → разделитель (у нас лексер); замер «Indel ≈ 95 % для неверного размера» как довод за судей | `token_set_ratio` (100 % на подмножествах), Jaro–Winkler/Indel на целой строке |
| **string_grouper (ING)** | TF-IDF по символьным 3-граммам; IDF как в sklearn `ln((1+N)/(1+df))+1` | порог 0,8 (только ориентир; зоны 85/60 в обработке — из рекомендации исследователя 2); `normalize_to_ascii=True` по умолчанию: NFKD → ASCII **стирает кириллицу** |
| **pg_trgm** | 3-граммы по отдельным словам с обрамлением пробелами (у pg_trgm 2 пробела слева и 1 справа, у нас по 1) | Jaccard без IDF; порог 0,3 (только ориентир) |
| **splink / Fellegi–Sunter** | уровни сравнения по полям и мысль «несовпадение размера — сильный отрицательный сигнал», отсюда стели | EM-оценку m/u (нет размеченных пар); плавные decay-функции для чисел: 55 и 65 отличаются на 15 % и дали бы «почти совпадение» |
| **dedupe** | `commonIntegerPredicate` (множество целых чисел названия) → идея сравнивать числа отдельно от текста (у нас — мультимножество, N); `firstTokenPredicate` → тип изделия (мягкий блок: ≤ 40, а не исключение) | жёсткое блокирование: промахнётся на «Сталевий лист…» |
| **Product matching: SciTePress 2019 (в отчёте исследователя 1 — «Köpcke et al.») и arXiv 2104.09576** | извлечение атрибутов из названия поднимает точность; «другой размер или фасовка — не совпадение» | ML-модели |
| **Cohen, Ravikumar, Fienberg 2003** | вывод, что TF-IDF + символьная метрика — сильная база | Soft TF-IDF (хрупкий порог θ) |
| **БСП `ПоискИУдалениеДублей`** | ничего: проверили и отклонили | `StringSearch` без балла |

## Идеи на будущее

1. **Прогнать текущую формулу на `gold.json`** (P@1, R@5, охват при 85/60, ложные пробы, конфликты) и сравнить с k7 в
   той же таблице. Это дёшево и отвечает на вопрос, переносить ли k7.
2. **Калибровка по журналу сопоставления.** Журнал «Журнал зіставлення <файл>.xlsx» (21 колонка) хранит «Автопідбір:
   номенклатура/код/спосіб/схожість» с **первой** загрузки, «Обрано: …» и «Виправлено бухгалтером»
   ([07](07_vlozheniya_i_zhurnal.md)). Из журналов 1–2 следующих накладных:
   - точность «Схоже ≥ 85» = доля строк без исправления. Если < 98 % — поднять порог кнопки; для k7 исследование
     предлагало 0,25 вместо 0,20;
   - после 200–300 подтверждённых пар посчитать по каждому признаку `m` (доля совпадений у верных пар) и `u` (у
     неверных) и заменить ручные множители и стели весами `log2(m/u)` (Fellegi–Sunter, без EM).
3. **Перенос k7 по Rule #-1:**
   - **parity-тест:** Python COM вызывает экспортную функцию `.epf` на 84 × 429 и сравнивает с `simlib.py`: тот же
     top-1, |Δscore| < 0,0001;
   - **приёмка:** P@1 83/83, 71 «сильная» и все верные, 0/83 проб, 0/9 конфликтов;
   - ключ памяти при этом заморозить (`КлючПамяти_v1`), иначе накопленная память обнулится.
4. **Точечные правила из спецификации k7.** Каждое — сначала случаем в `review_cases.py`:
   - числа в скобках — мягкие («Лист ПВЛ … (32*85)»);
   - мм↔м для целых ≥ 1000, кратных 10 (1500*6000 = 1,5*6);
   - эквиваленты стандартов: 934 ≡ 4032, 933 ≡ 4017, 931 ≡ 4014, 7089/7090 → 125;
   - группы стали: ст.3/3пс/3сп/S235/С245/S275 — одна, S355 — отдельно;
   - покрытие: н/ж против цб/оц/цж/zn (сейчас «н/ж» vs «цб» → 91);
   - класс арматуры: А-III ≡ А400;
   - синонимы главного слова: кутик → кутник, сходинки → сходи, плити → плита, стальний → сталевий;
   - пометка «дві рівноцінні картки» для дублей с разницей < 0,02.
5. **Резервный поиск по справочнику.**
   - Группировать строки по ключу «основа типа + первое целое жёсткое число < 1000».
   - Запрос `ПЕРВЫЕ 2000` со вторым `ПОДОБНО "%16%"`; при 2000 строках писать «пошук поза залишками неповний».
   - Для строк без типа — индекс 3-грамм в языке запросов через `МенеджерВременныхТаблиц`: замерено на BaseERP
     **1,6 с построение + ~86 мс на строку** (20 запросов — 1,71 с, 100 строк ≈ 9 с).
   - Оба текста запроса — сначала через Python COM на BuhBud.
6. **Память по контрагенту.** Сейчас ключ общий для всех. Исследование предлагало хранить «(Контрагент, ключ) →
   номенклатура». В ERP для этого есть `Справочник.НоменклатураПоставщиков`, в BuhBud — свой регистр или хранилище.
7. **Фон.** Больше ~300 строк или резерв по 44 000 позиций → вызов в `ДлительныеОперации.ВыполнитьВФоне`. Оценка
   исследования: 84 строки × 429 ≈ 1–3 с, не замерялось в BSL.
