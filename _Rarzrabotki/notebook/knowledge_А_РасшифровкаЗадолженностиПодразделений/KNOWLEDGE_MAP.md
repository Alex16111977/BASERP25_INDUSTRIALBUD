# KNOWLEDGE MAP — Отчёт `А_РасшифровкаЗадолженностиПодразделений`

> **Назначение:** on-disk база знаний по управленческому отчёту-расшифровке
> `Отчёт.А_РасшифровкаЗадолженностиПодразделений` (BAS ERP 2.5 INDUSTRIALBUD).
> Отчёт показывает бухгалтеру **почему был автоматически создан** документ
> `ВзаимозачетЗадолженности`: какой актив/расчёт между подразделениями, какой
> склад/контрагент/договор/счёт/касса/физлицо породили межподразделенческий
> дисбаланс. Использует те же текстовые поля `Аналитика1/2/3`, что выгружаются
> в Power BI `Fact_Balance` (зеркало `РегистрСведений.А_ОтчетБаланс_Свод`).
>
> Аналог структуры: `knowledge_А_ПередачаНачисленийМеждуПодразделениями/`.
> Для разработчика/инженера 1С (не для NotebookLM).
>
> **Прочитать первым.**

## TL;DR (за 60 секунд)

1. **Бизнес-проблема.** Обработка `А_ОбработкаДисбалансаПоПодразделениям` автоматически
   создаёт документы `ВзаимозачетЗадолженности` (контрагенты-партнёры подразделений с
   заполненным `Партнеры.А_Подразделение`), но **бухгалтеру не видно ПОЧЕМУ** — какой
   склад/счёт/договор/контрагент-внешний участвовал, по какой паре статей актив одной
   стороны столкнулся с расчётом/расходом другой.

2. **Что делает отчёт.** Для каждого взаимозачёта показывает **фактическую пару статей**
   из движений ПАП документа-основания (а НЕ хранимое `А_СтатьяДисбалансаПоПодразделению`),
   декодирует Аналитику стороны по `Источник` (рецепт из `Документ.А_ФинРез_Баланс`) и
   делит сумму на **Приход (увеличение долга)** / **Расход (уменьшение долга)**.

3. **Уровни группировки (вариант «Основной»).**
   `Контрагент → Договор → Статья движения денег/Суть → Взаимозачёт`
   → детальные строки сторон (с `Встречное подразделение`, `Хранимая статья`, `Аналитика1/2/3`).
   `Статья движения денег` — текстовая «суть» операции основания (см. §A ниже).

4. **Зерно (грейн) набора данных.** Контрагент-перспектива × Взаимозачёт × Сторона-ПАП.
   Каждый взаимозачёт даёт **4 строки**: 2 перспективы (контрагент-дебитор / контрагент-кредитор)
   × 2 стороны (приход / расход). Поля «Приход» и «Расход» заполняются НЕ-нулём
   только на одной стороне → СУММА по группировкам считает каждый взаимозачёт **ровно один раз**.

5. **Базис = живой ПАП**, не свёртка `А_ОтчетБаланс_Свод`. Работает в любом периоде
   (включая незакрытый месяц). Документ-основание поднимается через
   `Вз.А_ДокументОснованиеДляБаланса`, стороны — `ПАП.Регистратор = Основание`.

6. **Аналитика по Источник.** Себестоимость → Склад/Подр-склада/Номенклатура;
   Расчёты с поставщиками/клиентами → Контрагент/Договор; Прочие расходы → СтатьяРасходов;
   Денежные средства → Банкс-чёт/Касса/ФизЛицо; Оплата труда → ФизЛицо. См.
   [`rzp_analytics_decoding.md`](rzp_analytics_decoding.md).

7. **§A. Статья движения денег / Суть** (`СтатьяДвижения`, строка). Вычисляется
   **один раз на взаимозачёт** из реквизита документа-основания по его типу
   (`СтатьяДвиженияОснования`): Приобретение→`А_СтатьяДвиженияДенежныхСредств`,
   Безнал/ПКО/РКО→`СтатьяДвиженияДенежныхСредств`, СписаниеНедостач→`СтатьяРасходов`,
   Перемещение/ПередачаНачислений/Реализация/… → фикс-текст; **иначе или при пустом
   реквизите → синоним типа документа** (fallback). Даёт бухгалтеру итоги Приход/Расход
   «по сути»: по каким статьям денег копится/уменьшается межподразделенческий долг.
   На данных декабря 2025 fallback несёт основную нагрузку (у ПКО/Безнал-оснований
   реквизит-статья пуст) — это by-design.

## Что отчёт ДЕЛАЕТ и ЧТО НЕ ДЕЛАЕТ

**ДЕЛАЕТ:**
- Объясняет ПРИЧИНУ создания взаимозачёта (актив + расчёт + договор + аналитика).
- Сверяет хранимое `А_СтатьяДисбалансаПоПодразделению` с фактом из ПАП → колонка
  `Флаг расхождения` («Да» = реквизит врёт).
- Группирует по контрагенту-партнёру (= подразделению), договору, статье движения
  денег (сути операции), конкретному взаимозачёту (встречное подразделение и хранимая
  статья дисбаланса — в детальных строках).
- Считает суммы Приход/Расход на каждом уровне (в т.ч. по статье движения денег).

**НЕ ДЕЛАЕТ:**
- НЕ ИСПРАВЛЯЕТ хранимый реквизит `А_СтатьяДисбалансаПоПодразделению` — это задача
  обработки `А_ОбработкаДисбалансаПоПодразделениям` (вне scope).
- НЕ перепроводит документы.
- НЕ выгружает в Power BI напрямую — но `Аналитика1/2/3` совпадают с `Fact_Balance` (отчёт
  и Power BI говорят на одном языке).

## Грабли (TL;DR)

1. **Хранимый `А_СтатьяДисбалансаПоПодразделению` не равен факту** — отчёт всегда
   считает пару из движений ПАП основания, реквизит показывается ДЛЯ ИНФОРМАЦИИ.
2. **Грейн дублирует `СуммаРегл` x4** (2 перспективы × 2 стороны) — поэтому суммы делятся
   через Приход = СуммаРегл при `СторонаЗнак="Дебитор"` и Расход при `"Кредитор"`,
   `Сумма(Приход)/Сумма(Расход)` корректны на любом уровне.
3. **Одно основание может породить НЕСКОЛЬКО взаимозачётов** (напр., 1 покупка с услугой на
   технику делится на MAN №3, №4, №5 → 3 отдельных пары). Фильтр сторон по ДВУМ
   подразделениям пары — обязателен (`fix 128c86212`).
4. **СКД-параметры из формы** читаются через `КомпоновщикНастроек.ПолучитьНастройки()`
   (не `СхемаКомпоновкиДанных.НастройкиПоУмолчанию`) — тогда отчёт уважает выбор пользователя.
5. **`.erf` кэшируется в сессии 1С Enterprise** — после правки пересборки ОБЯЗАТЕЛЬНО
   закрыть и заново открыть вкладку отчёта; иначе видна старая версия.
6. **Сборка `.erf` против stub-базы НЕ работает на 8.3.20** — генератор stub-конфигурации
   пишет формат `2.17`, платформа его не грузит («Неизвестная версия формата 2.17»).
   Собирать `/erf-build` ПРОТИВ реальной BaseERP, и Конфигуратор должен быть закрыт
   (иначе «Ошибка блокировки информационной базы для конфигурирования»).
7. **Две копии отчёта** (внешняя `.erf` + config-side `Reports/`) — правки в ОБЕ.
   ObjectModule идентичен (config-side с BOM); Template.xml структурно различается
   (порядок типов, `AllowedLength`) — копировать один поверх другого нельзя, править каждый.
