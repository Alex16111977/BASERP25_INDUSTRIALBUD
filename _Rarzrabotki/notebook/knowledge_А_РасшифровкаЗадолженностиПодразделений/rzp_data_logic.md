# Алгоритм данных: получение ТЗ для СКД

## Точка входа

`Отчет.А_РасшифровкаЗадолженностиПодразделений.МодульОбъекта` → процедура
`ПриКомпоновкеРезультата`:

```bsl
Процедура ПриКомпоновкеРезультата(ДокументРезультат, ДанныеРасшифровки, СтандартнаяОбработка)
    СтандартнаяОбработка = Ложь;
    Настройки = КомпоновщикНастроек.ПолучитьНастройки();  // НЕ НастройкиПоУмолчанию!

    Параметры = Новый Структура;
    Параметры.Вставить("НачалоПериода",         ЗначениеПараметраНастроек(Настройки, "НачалоПериода"));
    Параметры.Вставить("ОкончаниеПериода",      ЗначениеПараметраНастроек(Настройки, "ОкончаниеПериода"));
    Параметры.Вставить("Организация",           ЗначениеПараметраНастроек(Настройки, "Организация"));
    Параметры.Вставить("ТолькоРасхождения",     Булево(...));
    Параметры.Вставить("ВключатьНепроведенные", Булево(...));

    ТЗ = ПолучитьТаблицуРасшифровки(Параметры);
    ВнешниеНаборы = Новый Структура("Расшифровка", ТЗ);
    ... композиция ПроцессорКомпоновкиДанных ...
КонецПроцедуры
```

## Основной цикл — `ПолучитьТаблицуРасшифровки(Параметры)`

### Шаг 1. Запрос взаимозачётов периода

```sql
ВЫБРАТЬ Вз.Ссылка, Вз.Дата, Вз.СуммаРегл, Вз.Проведен,
        Вз.КонтрагентДебитор, Вз.КонтрагентКредитор,
        ВЫРАЗИТЬ(Вз.КонтрагентДебитор КАК Справочник.Контрагенты).Партнер.А_Подразделение  КАК ПодрДебитор,
        ВЫРАЗИТЬ(Вз.КонтрагентКредитор КАК Справочник.Контрагенты).Партнер.А_Подразделение КАК ПодрКредитор,
        Вз.А_ДокументОснованиеДляБаланса КАК Основание,
        Вз.А_СтатьяДисбалансаПоПодразделению КАК ХранимаяСтатья
ИЗ Документ.ВзаимозачетЗадолженности КАК Вз
ГДЕ Вз.Дата МЕЖДУ &Нач И &Кон
  И Вз.А_ДокументОснованиеДляБаланса <> НЕОПРЕДЕЛЕНО
  И НЕ Вз.ПометкаУдаления
  [И Вз.Организация = &Орг -- если задан]
  [И Вз.Проведен        -- если НЕ ВключатьНепроведенные]
УПОРЯДОЧИТЬ ПО Вз.Дата
```

Якорь = `Документ.ВзаимозачетЗадолженности`. Только авто-созданные обработкой
(основание заполнено) и не удалённые.

### Шаг 2. Гард-проверки на взаимозачёт

Для каждой строки:

```bsl
Если НЕ ЗначениеЗаполнено(ВыборкаВз.ПодрДебитор)
    ИЛИ НЕ ЗначениеЗаполнено(ВыборкаВз.ПодрКредитор)
    ИЛИ ВыборкаВз.ПодрДебитор = ВыборкаВз.ПодрКредитор Тогда
    Продолжить;
КонецЕсли;
```

Отсекает «битые» взаимозачёты, где один из партнёров не имеет А_Подразделение или
оба партнёра указывают на одно подразделение.

### Шаг 3. Фактические стороны ПАП — `ПолучитьСтороныПАП`

**Ключевой запрос отчёта.** Фильтрует движения ПАП по двум подразделениям пары
(критический фикс `128c86212`):

```sql
ВЫБРАТЬ ПАП.Подразделение, ПАП.Статья, ПАП.Источник,
       СУММА(ВЫБОР КОГДА ПАП.ВидДвижения = ЗНАЧЕНИЕ(ВидДвиженияНакопления.Приход)
                  ТОГДА ПАП.Сумма ИНАЧЕ -ПАП.Сумма КОНЕЦ) КАК Сальдо
ИЗ РегистрНакопления.ПрочиеАктивыПассивы КАК ПАП
ГДЕ ПАП.Регистратор = &Основание
  И ПАП.Подразделение В (&ПодрДеб, &ПодрКред)   ←←← КЛЮЧЕВОЙ ФИЛЬТР
СГРУППИРОВАТЬ ПО ПАП.Подразделение, ПАП.Статья, ПАП.Источник
ИМЕЮЩИЕ СУММА(... signed ...) <> 0
```

**Почему фильтр критичен.** Одно основание (напр. покупка ІБ00-007892 на 3 единицы
техники по 190 грн) порождает движения по ВСЕМ задействованным подразделениям
(MAN №3, MAN №4, MAN №5, Логистика), но `А_ОбработкаДисбалансаПоПодразделениям`
создаёт **отдельный взаимозачёт на КАЖДУЮ пару** (MAN №3↔Логистика, MAN №4↔Логистика,
MAN №5↔Логистика). Если читать ПАП по основанию без фильтра подразделений, под каждым
взаимозачётом всплыли бы стороны ЧУЖИХ подразделений (MAN №4/№5 под взаимозачётом
MAN №3↔Логистика). Это был баг до `128c86212`.

### Шаг 4. Определение факт-пары статей

```bsl
СторонаДеб  = ДоминирующаяСторона(Стороны, ВыборкаВз.ПодрДебитор,  Истина);  // макс signed
СторонаКред = ДоминирующаяСторона(Стороны, ВыборкаВз.ПодрКредитор, Ложь);    // мин signed

ФактСтатьяДебитора  = СторонаДеб.Статья;
ФактСтатьяКредитора = СторонаКред.Статья;
```

`ДоминирующаяСторона` находит строку с максимальным (или минимальным) сальдо в
подразделении пары. Это **факт-пара** — отличается от хранимой в реквизите
`А_СтатьяДисбалансаПоПодразделению`, если обработка-генератор её плохо заполнила.

### Шаг 5. Флаг расхождения

```bsl
ФлагРасхождения = ЕстьРасхождение(ВыборкаВз.ХранимаяСтатья, ФактСтатьяДебитора, ФактСтатьяКредитора);
```

`ЕстьРасхождение` читает ТЧ `Справочник.А_ДисбалансПоПодразделению.СтатьиБаланса`
(2 строки) и сравнивает с множеством {ФактДеб, ФактКред}:
- Если хранимая пуста → расхождение = Истина.
- Если множество хранимых != множеству фактических → расхождение = Истина.
- Если равны (порядок не важен) → расхождение = Ложь.

`ТолькоРасхождения` ранний выход:

```bsl
Если Параметры.ТолькоРасхождения И НЕ ФлагРасхождения Тогда Продолжить; КонецЕсли;
```

### Шаг 6. Договор стороны

```bsl
ДоговорДеб  = ПолучитьДоговорСтороны(ВыборкаВз.Взаимозачет, "Дебитор");
ДоговорКред = ПолучитьДоговорСтороны(ВыборкаВз.Взаимозачет, "Кредитор");
```

Берёт первый непустой `ОбъектРасчетов.Договор` из ТЧ
`ДебиторскаяЗадолженность` / `КредиторскаяЗадолженность`. Для внутренних
взаимозачётов это договор «<Подр> внутр.(Закупка)» или «<Подр> внутр.(Реализация)».

### Шаг 7. Массив сторон пары — РОВНО 2 элемента

```bsl
МассивСторон = Новый Массив;
МассивСторон.Добавить(НоваяСторонаПары(ПодрДебитор,  СторонаДеб,  ВыборкаВз.СуммаРегл,  "Дебитор"));
МассивСторон.Добавить(НоваяСторонаПары(ПодрКредитор, СторонаКред, -ВыборкаВз.СуммаРегл, "Кредитор"));
```

**Важно:** сумма стороны = `±СуммаРегл взаимозачёта` (пер-пара), а НЕ signed-сальдо
сырого ПАП по основанию. Это делает суммы корректными даже когда основание расщеплено
на несколько пар (см. шаг 3 — пример с тремя MAN).

### Шаг 8. Выдача 4 строк ТЗ на каждый взаимозачёт

Для каждой из 2 сторон → 2 перспективы контрагента:

```bsl
Для Каждого Сторона Из МассивСторон Цикл
    Расшифровка = ДекодироватьСторону(ВыборкаВз.Основание, Сторона);

    // Перспектива 1: контрагент = дебитор взаимозачёта
    ДобавитьСтроку(ТЗ, ВыборкаВз, КонтрагентДебитор, ПодрКредитор, ДоговорДеб,
                   "Дебитор", ФактСтДеб, ФактСтКред, ФлагРасх, ТипОперации,
                   Сторона, Сторона.СторонаЗнак, Расшифровка);

    // Перспектива 2: контрагент = кредитор взаимозачёта
    ДобавитьСтроку(ТЗ, ВыборкаВз, КонтрагентКредитор, ПодрДебитор, ДоговорКред,
                   "Кредитор", ФактСтДеб, ФактСтКред, ФлагРасх, ТипОперации,
                   Сторона, Сторона.СторонаЗнак, Расшифровка);
КонецЦикла;
```

**Итого 4 строки ТЗ на взаимозачёт.**

## Грейн ТЗ и трюк с Приход/Расход

Грейн: `(Контрагент-перспектива × Взаимозачёт × Сторона-ПАП)` → 4 строки на взаимозачёт.

`СуммаРегл` одинакова во всех 4 строках. Если бы суммировали `Сумма(СуммаРегл)` по
группам, получили бы x4 — оверсчёт. Решение:

```bsl
Строка.Приход = ?(СторонаЗнак = "Дебитор",  ВыборкаВз.СуммаРегл, 0);
Строка.Расход = ?(СторонаЗнак = "Кредитор", ВыборкаВз.СуммаРегл, 0);
```

Из 4 строк взаимозачёта: 2 имеют `Приход = СуммаРегл / Расход = 0` (дебиторская
сторона в обеих перспективах), 2 — наоборот. Сумма по любой группе берёт каждый
взаимозачёт **по 2 раза** для Прихода (по перспективам) — но это ОК, потому что
группы выше уровня «Контрагент» НЕ существуют (нет общей группы для обеих перспектив).
На уровне «Контрагент» каждый взаимозачёт виден ровно один раз с правильной суммой.

## Структура колонок ТЗ (21 колонка)

```
Контрагент, Договор, ВстречноеПодразделение, ХранимаяСтатьяДисбаланса,
Взаимозачет, РольКонтрагента, Дата, СуммаРегл, Проведен,
Основание, ТипОперации, ФактСтатьяДебитора, ФактСтатьяКредитора, ФлагРасхождения,
СторонаЗнак, СторонаПодразделение, СторонаСтатья, СторонаИсточник,
Приход, Расход, Аналитика1, Аналитика2, Аналитика3
```

Типы:
- `Контрагент`: `СправочникСсылка.Контрагенты, СправочникСсылка.Организации`
- `Договор`: `СправочникСсылка.ДоговорыКонтрагентов`
- `ВстречноеПодразделение`, `СторонаПодразделение`: `СправочникСсылка.СтруктураПредприятия`
- `ХранимаяСтатьяДисбаланса`: `СправочникСсылка.А_ДисбалансПоПодразделению`
- `Взаимозачет`: `ДокументСсылка.ВзаимозачетЗадолженности`
- `Основание`: `ОписаниеТипов()` (составной — DocumentRef)
- `ФактСтатья*`, `СторонаСтатья`: `ПланВидовХарактеристикСсылка.СтатьиАктивовПассивов`
- `СторонаИсточник`: `ПеречислениеСсылка.ИсточникиУправленческогоБаланса`
- `СуммаРегл`, `Приход`, `Расход`: Число(18,2)
- `Аналитика1/2/3`: Строка
- `РольКонтрагента`, `СторонаЗнак`, `ТипОперации`: Строка
- `Дата`: Дата; `Проведен`, `ФлагРасхождения`: Булево

## Производительность

- Один SQL-запрос на взаимозачёты периода + по 1–5 декод-запросов на КАЖДЫЙ взаимозачёт.
- За декабрь 2025 (период 31 день): ~500 взаимозачётов → ~1500–2500 декод-запросов
  → ~5–10 сек на типовом железе. Приемлемо для on-demand отчёта.
- НЕ свёрнут в один UNION-мега-запрос намеренно: ветвление декода по `Источник`
  per-сторона делает SQL непрактичным; ясность важнее.

## Известные ограничения

- Если основание = `Документ.ОперацияБух` или другой документ, не пишущий в ПАП напрямую
  (а через дочерний `РегистраторРасчётов`), `ПолучитьСтороныПАП` вернёт пусто, и
  взаимозачёт молча пропускается (`Если Стороны.Количество() = 0 Тогда Продолжить`).
  Для расчётов по срокам — это известный паттерн, см. `knowledge_Balanse_klient`.
- Если в одном подразделении пары несколько строк ПАП с РАЗНЫМИ статьями — берётся
  доминирующая (макс/мин). Очень редко даёт двусмысленность; в эталонах не встречалось.
