# Структура отчёта: группировки, колонки, оформление

## Параметры

| Параметр | Тип | Обязательный | Назначение |
|---|---|:--:|---|
| `НачалоПериода` | Дата (день) | ✅ | `Документ.ВзаимозачетЗадолженности.Дата >= &НачалоПериода` |
| `ОкончаниеПериода` | Дата (день) | ✅ | `Документ.ВзаимозачетЗадолженности.Дата <= КонецДня(&ОкончаниеПериода)` |
| `Организация` | СправочникСсылка.Организации | — | если задан — фильтр `Вз.Организация = &Орг`; иначе все |
| `ТолькоРасхождения` | Булево | — | если Истина — оставлять только взаимозачёты с `ФлагРасхождения = Истина` |
| `ВключатьНепроведенные` | Булево | — | по умолчанию Ложь — `И Вз.Проведен`; Истина — выводить также не проведённые |

> Параметры читаются из `КомпоновщикНастроек.ПолучитьНастройки()` (а не из
> `СхемаКомпоновкиДанных.НастройкиПоУмолчанию`!) — тогда отчёт уважает кастомные
> настройки, заданные пользователем в форме.

## Группировки — 5 уровней

```
1. Контрагент (= партнёр-подразделение взаимозачёта)
2. └ Договор (внутренний договор подразделения, из ТЧ взаимозачёта)
3.    └ Встречное подразделение (вторая сторона взаимозачёта)
4.       └ Хранимая статья дисбаланса (А_СтатьяДисбалансаПоПодразделению, ДЛЯ ИНФО)
5.          └ Взаимозачёт (документ ВзаимозачетЗадолженности)
               └ Стороны (детальные записи — Дебитор / Кредитор)
```

**Зачем такой порядок:**
- **Контрагент** наверху — бухгалтер фильтрует «свои» подразделения.
- **Договор** показывает внутренний договор «Подразделение внутр.(Закупка|Реализация)»,
  по которому возник дисбаланс — критично для понимания «по чему именно».
- **Встречное подразделение** — кому/от кого этот контрагент должен/получает.
- **Хранимая статья** — пара статей в реквизите взаимозачёта; полезно для контроля
  расхождения и для группировки документов с одинаковой природой.
- **Взаимозачёт** — конкретный документ, дата, сумма.
- **Стороны** — реальные движения ПАП с аналитикой.

## Колонки

### На уровне строки взаимозачёта (агрегированные)

| Колонка | Источник | Примечание |
|---|---|---|
| Контрагент | `КонтрагентДебитор`/`КонтрагентКредитор` | в зависимости от перспективы |
| Договор | ТЧ `ДебиторскаяЗадолженность`/`КредиторскаяЗадолженность.ОбъектРасчетов.Договор` | `ПолучитьДоговорСтороны` |
| Встречное подразделение | партнёр.А_Подразделение второй стороны | |
| Хранимая статья дисбаланса | `Вз.А_СтатьяДисбалансаПоПодразделению` | ДЛЯ ИНФО (может врать) |
| Взаимозачёт | `Вз.Ссылка` | |
| Дата | `Вз.Дата` | |
| Сумма (регл.) | `Вз.СуммаРегл` | сумма пары |
| Проведён | `Вз.Проведен` | |
| Основание | `Вз.А_ДокументОснованиеДляБаланса` | первичный документ |
| Тип операции | синоним метаданных основания | напр. «Приобретение товаров и услуг» |
| Факт. статья дебитора | вычислено из ПАП | доминирующая статья в подр. дебитора |
| Факт. статья кредитора | вычислено из ПАП | доминирующая статья в подр. кредитора |
| Флаг расхождения | сравнение хранимая ↔ факт | 🚩 если врёт |
| Роль контрагента | «Дебитор» / «Кредитор» | в этой перспективе |

### На уровне детальной строки стороны

| Колонка | Источник | Примечание |
|---|---|---|
| Сторона-знак | «Дебитор» / «Кредитор» | какая сторона ПАП в подразделении |
| Сторона.Подразделение | `ПАП.Подразделение` | подр-дебитор или подр-кредитор |
| Сторона.Статья | `ПАП.Статья` | факт-статья этой стороны |
| Сторона.Источник | `ПАП.Источник` | определяет рецепт декода |
| Аналитика 1 | по `Источник` | см. [`rzp_analytics_decoding.md`](rzp_analytics_decoding.md) |
| Аналитика 2 | по `Источник` | |
| Аналитика 3 | по `Источник` | |
| Приход (увеличение) | `СуммаРегл` если СторонаЗнак=Дебитор, иначе 0 | |
| Расход (уменьшение) | `СуммаРегл` если СторонаЗнак=Кредитор, иначе 0 | |

> «Сальдо» **убрано** из вывода (бухгалтер думает в терминах увеличения/уменьшения,
> а не математического знака сальдо).

## Ресурсы (totalField)

```xml
<totalField><dataPath>Приход</dataPath><expression>Сумма(Приход)</expression></totalField>
<totalField><dataPath>Расход</dataPath><expression>Сумма(Расход)</expression></totalField>
<totalField>
  <dataPath>СуммаРегл</dataPath><expression>Максимум(СуммаРегл)</expression>
  <group>Взаимозачет</group>
</totalField>
```

- `Сумма(Приход)` и `Сумма(Расход)` — субтотали на всех уровнях. Каждый взаимозачёт
  даёт одно ненулевое значение Приход (на дебиторской стороне) и одно Расход (на
  кредиторской), поэтому суммирование по группировкам корректно.
- `Максимум(СуммаРегл)` на уровне группы `Взаимозачет` — показывает сумму **самого
  взаимозачёта**, не суммированную через детальные строки (так как `СуммаРегл`
  одинакова во всех строках одного взаимозачёта — дублируется в ТЗ).

## Условное оформление

| Условие | Эффект | Назначение |
|---|---|---|
| `ФлагРасхождения = Истина` | красный шрифт | визуальный маркер расхождения хранимая ↔ факт |
| `Проведен = Ложь` | серый шрифт | непроведённые взаимозачёты по умолчанию не выводятся, но если включены — заметны |

## Вариант СКД

Единственный сохранённый вариант — **«Основной»** (ключ `85e10759-a541-473b-a42e-33c637a12976`).
- `РасположениеПолейГруппировки = Separately` — каждое поле группировки в своей строке.
- `Сумма (регл.)`, `Приход`, `Расход` — фиксированные ресурсы.
- Сортировка авто-определяемая по дате.

Пользователь может сохранить свои варианты через «Изменить настройки» — это не ломает
отчёт, потому что данные готовятся программно из параметров, а не из СКД-запроса.

## Точки расширения настроек

Если бухгалтер захочет дополнительный разрез, добавляется без изменения BSL — через
«Изменить вариант → Группировки → +поле»:
- `СторонаИсточник` → разделить «Расчёты с поставщиками по срокам» / «Себестоимость» /
  «Прочие расходы» — увидеть, на каком регистре дисбаланс.
- `Аналитика2` → плоский список контрагентов (как в PBI-матрице).
- `НаправлениеДеятельности` (потребует добавления поля в ТЗ — см. Roadmap).
