# 01. Архитектура: как работает `СоздатьДокументНачисления()`

**Файл:** `Documents/А_ОтражениеЗПпоКазне/Ext/ObjectModule.bsl`
**Процедура:** `СоздатьДокументНачисления() Экспорт` (≈ строка 2548; номера «плывут» при правках — ищи по имени)
**Образец-эталон в коде:** `НачислениеЗарплаты 000Ц-000002`

`СоздатьДокументНачисления` — это метод объектного модуля документа **`А_ОтражениеЗПпоКазне`**.
Все ссылки вида `НачисленияУпр`, `РаспределениеКазна`, `НачисленияБух` и т.д. — это **табличные части
самого `А_ОтражениеЗПпоКазне`** (self). Создаваемый документ `НачислениеЗарплаты` передаётся/держится в
переменной `НЗ`.

---

## Общий поток

```
Guard: А_ОтражениеЗПпоКазне.Проведен? → нет → выход
  ↓
Кеш справочников: ВидНачисленияОсновний = "Оклад (Зарплата)", ВидНачисленияШтраф = "Штраф (упр)",
                  ВидУдержанияАлименты = "Алименты бух"; перечисления НДФЛ/ЕСВ, ставки
  ↓
Find-Or-Create НЗ по реквизиту НачислениеЗарплаты.А_ДокОтражениеЗПпоКазне = Ссылка(self)
  (если найден и проведён — распровести, очистить 5 ТЧ)
  ↓
Заполнить шапку НЗ (Дата, Организация, МесяцНачисления, ...)
  ↓
КешСотрПоФизЛицу = _НЗ_ПобудуватиКешСотрудникПоФизЛицу()       — ФЛ → Сотрудник
МапПодразОргПоСотруднику = _НЗ_ПобудуватиМапПодразОргПоСотруднику() — Сотрудник → {ПодрОрг: вес take-home}
  ↓
[ТЧ Начисления]  Крок1 + Крок2 + Штрафы   (см. ниже)
  ↓  ← здесь вставлен фикс _НЗ_НормалізуватиБольничные (см. 04)
ФЛВНачисленияхСет = множество ФЛ, у кого есть строка в Начисления
  ↓
[ТЧ Удержания]   УдержанияБухгалтерия → "Алименты бух" (фильтр по ФЛВНачисленияхСет)
[ТЧ НДФЛ]        НалогиБухгалтерия.СуммаНДФЛ (НДФЛ / ВоенныйСбор)
[ТЧ ВзносыФОТ]   НалогиБухгалтерия.СуммаФОТ (ЕСВ)
[ТЧ ФизическиеЛица] = УникальныеФЛ
  ↓
НЗ.Записать(Проведение); _НЗ_ОчиститиПерерасчетЗарплаты(...)
```

## ТЧ `Начисления` — три шага (источник дефекта)

ТЧ `Начисления` содержит ТОЛЬКО 2 вида расчёта: «Оклад (Зарплата)» и «Штраф (упр)».
**Оба имеют одинаковый код `ОКЛН ` (дубль в базе) → ищутся по НАИМЕНОВАНИЮ**, не по коду.

| Шаг | Откуда | Что кладёт | Знак |
|---|---|---|---|
| **Крок 1** (≈2653) | `НачисленияУпр` (ФизЛицо, Сумма) — управленческое начисление из zup_2 | «Оклад (Зарплата)» = `НачисленияУпр.Сумма` (как есть, без валоризации) | + |
| **Крок 2** (≈2699) | `РаспределениеКазна.СуммаНачисления` (агрегат по ФЛ) — fallback для тех, у кого НЕТ `НачисленияУпр` | «Оклад (Зарплата)» = `Σ СуммаНачисления` | ± (может быть **минус** = плуг!) |
| **Штрафы** (≈2722) | `УдержанияУпр` (ФизЛицо, Сумма) | «Штраф (упр)» = `−Сумма` | − (но если `Сумма<0`, то **+**) |

Каждый «оклад» раскладывается по `ПодразделенияОрганизаций` пропорционально весам
`РаспределениеКазна.Сумма` (take-home) через `_НЗ_ДодатиРядкиНачисленияПоПодразделениях`.

> 🔴 **Корень дефекта:** для больничных «оклад» берётся из **Казны**, а реальный больничный лежит
> в бухгалтерских закладках `НачисленияБух` (первые-5-дней) и `НачисленияБухЗасчетФондов` (ФСС),
> которые `СоздатьДокументНачисления` **вообще не читает**. См. [03_bug_i_anomalii.md](03_bug_i_anomalii.md).

## Источники остальных ТЧ

| ТЧ дочки `НачислениеЗарплаты` | Источник (ТЧ родителя `А_ОтражениеЗПпоКазне`) | Заметки |
|---|---|---|
| `Удержания` → «Алименты бух» | `УдержанияБухгалтерия` (ФизическоеЛицо, Сумма, Субконто1=Контрагент-получатель) | фильтр: только ФЛ, у кого есть строка в `Начисления` |
| `НДФЛ` | `НалогиБухгалтерия.СуммаНДФЛ`, `.СуммаДохода`, `.ТипНалога` (НДФЛ/ВоенныйСбор), `.КодДохода` | ✅ корректно из ZUP_1, фикс это не трогает |
| `ВзносыФОТ` | `НалогиБухгалтерия.СуммаФОТ`, `.База` (ЕСВ 22%) | ✅ корректно, фикс не трогает |
| `ФизическиеЛица` | `УникальныеФЛ` (множество из всех шагов) | |

**Важно:** для декрета (Горбачова) `НалогиБухгалтерия.СуммаНДФЛ = 0` → НДФЛ-строки нет → take-home = GROSS.

## Find-Or-Create и идемпотентность

- Поиск дочки: `ВЫБРАТЬ ПЕРВЫЕ 1 ... ИЗ Документ.НачислениеЗарплаты ГДЕ А_ДокОтражениеЗПпоКазне = &Осн И НЕ ПометкаУдаления`.
- Повторный вызов находит ТОТ ЖЕ документ, распроводит, очищает ТЧ, перезаполняет — UUID сохраняется (проверено `test_create_nachislenie_zarplaty.py`).
- COM-перезапись `НачислениеЗарплаты` **надёжна** (это НЕ документ новой архитектуры взаиморасчётов — он не теряет `РегистраторРасчётов`, в отличие от Реализации/Приобретения). Поэтому смок на 1 документе можно гонять через COM. Но историю перепроводит пользователь в UI.
