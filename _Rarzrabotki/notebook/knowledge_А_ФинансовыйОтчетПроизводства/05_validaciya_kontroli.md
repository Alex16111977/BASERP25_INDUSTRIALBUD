# 05. Валидация и контроли

Два слоя. **П\*** — проверки параметров ДО расчёта, часть блокирует. **К\*** — контроли ПОСЛЕ
расчёта, все информируют. Оба слоя пишут в ТЧ `Контроль` и дублируются в панель сообщений
с привязкой к строке ТЧ.

> (сводка исключений). К10 переформулирован: «проведіть документ або виправте первинку».

## Как работает привязка к строке

```bsl
Сообщение = Новый СообщениеПользователю;
Сообщение.Текст = Код + ": " + Текст;
Сообщение.Поле  = "Объект.Подразделения[0].ПроцентУдержания";
Сообщение.УстановитьДанные(ЭтотОбъект);
Сообщение.Сообщить();
```

Клик по сообщению ставит курсор в проблемное поле. `УстановитьДанные` обёрнут в
`Попытка/Исключение`: на незаписанном объекте привязка недоступна, текст всё равно покажется.

Платформенный `СообщениеПользователю` выбран вместо БСП-обёртки — меньше зависимостей.

## Уровни

`А_УровниКонтроляФинотчета`: **Ошибка** (блокирует расчёт), **Предупреждение**, **Информация**.
После `ПроверитьПараметры()` наличие хотя бы одной ошибки → расчёт не запускается,
статус `ЕстьЗамечания`.

**П22 и П26 — принципиальные.** Ручная сумма и исключение документа без объяснения запрещены:
именно так «магическая константа 1 194 270» жила в Excel годами, и никто не знал, откуда она.

Часть проверок **чинит на месте и предупреждает**: П10 обрезает процент, П19 — коэффициент,
П06 подставляет счёт, П14 — вариант формулы, П15/П17 удаляют дублирующие строки.

## К14–К23 — оплаты по казне и параметры K (с 28.09.2026)

К06 **удалён**: K договора теперь не меньше 0, его роль берёт К19. Коды К14–К23 были свободны.

| Код | Уровень | Что показывает |
|---|---|---|
| К14 | Информ. | договор перенесён по казне: «РО141392 → МД ООН 2026 за казною: DL-012958 від 28.07.2026 — 4 770 134,46» |
| К14 | Предупр. | оплата договора с актами (или со смешанными оплатами) в казне относится к другому подразделению отчёта — ничего не переносится, проверить разнесение |
| К15 | Информ. | **одной строкой**: оплаты оставлены как в бухгалтерии — подразделение казны вне отчёта (на 25.09 — 51), не сопоставлено (1), не от ПНРС; сумма и первые 5 документов |
| К16 | Предупр. | обратный поиск: казна относит оплату к подразделению отчёта, бухгалтерия — к договору вне расчёта. Подсказка по классу договора: общий договор → «перепровести оплату на договор объекта»; пустое подразделение/направление → «добавить в "Договоры дополнительно" или заполнить подразделение и направление договора» |
| К17 | Информ. | P: \|A − C×p/100\| > 1 грн; C = 0 → «сумма соглашения не заполнена» |
| К18 | Предупр. | P: аванс поступил не полностью (оплаты до первого акта < A); при действующей дате зачёта не выводится |
| К19 | Информ. | K договора отрицательное → показано 0 (аванс не отработан / переплата); сводно по подразделению |
| К20 | Предупр. | договор с H ≥ 1 грн без записи в регистре — считается Z(0) |
| К21 | Предупр. | P: НачалоПериода позже первой оплаты договора — аванс не виден, остаток недостоверен |
| К22 | Предупр. | P без `СуммаПредоплаты`, неизвестный вариант или `ПравилоНДС` → договор считается как Z(p) с ОтАктов |
| К23 | Информ. | `СуммаГарантийногоУдержания` > 0 и G + H больше суммы — долг сверх удержания |

К03 и К16 пересекаются: К03 не видит договоров с пустым направлением. В тексте К03 для договоров из
обоих списков — ссылка «див. К16».

**Лимит сообщений.** `ВывестиЗамечанияПользователю` выводит не больше 10 сообщений на пару «код +
уровень» и строку «і ще N — вкладка «Контроль»». ТЧ `Контроль` хранит всё.

**К10 назван поимённо намеренно.** Непроведённый документ — самая частая причина расхождения
с ручным отчётом, и пользователь должен видеть конкретный документ, а не общую цифру.

**К01 вычитает только проведённую часть H** — непроведённых в сальдо нет. Первая версия
вычитала всё H и ругалась на каждую строку с непроведёнными ([LESSONS §4](LESSONS.md)).
