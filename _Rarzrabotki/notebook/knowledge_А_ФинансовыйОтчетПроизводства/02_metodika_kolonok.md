# 02. Методика колонок: что означают E, F, G, H, J, K

Одиннадцать колонок ручного Excel «Финансовый_отчет Производства». Четыре из них считаются
из бухучёта, остальные — параметры договора либо производные.

| Кол. | Заголовок в Excel | Откуда |
|---|---|---|
| A | Контрагент / Договор | иерархия отчёта |
| B | Примечание | реквизит договора `А_ОбъектПримечание` |
| C | Сумма утвержденного соглашения | реквизит договора `А_СуммаСоглашения` |
| D | Сумма ДЦ поданной на рассмотрение | реквизит договора `А_СуммаДЦ` |
| **E** | Выполненные работы грн. | **оборот Дт 361 по документам С отметкой «Оригінал»** |
| **F** | Оплачено грн. | **оборот Кт 361** (весь) |
| **G** | Задолженность, грн. (аванс−) | **`E − F`** — это НЕ сальдо счёта |
| **H** | Акты поданные на Заказчика | **проведённые БЕЗ отметки + непроведённые документы** |
| I | Гарантийные платежи | `−min(СуммаГарантийногоУдержания; max(0; G + H))` (с 28.09.2026) |
| J | Сумма незарегистрированного НДС | по `ПравилоНДС` договора: `−H/6` / 0 / `−max(0; G)/6` |
| K | ИТОГО сумма к получению | по варианту формулы договора, не меньше 0 |

## «Оригінал» — это булев ресурс, а не строка

В постановке задачи было «галочка Оригинал». В базе это
`РегистрСведений.ОтправкаПолучениеДокументов`: измерение **`Документ`**, ресурсы
**`ДокументыОтправлены`, `ДокументыПолучены`, `ДатаОтправки`, `ДатаПолучения`**.
`ДокументыПолучены` возвращает **Истина/Ложь**.

Соединять `ПО ОПД.Документ = Об.Регистратор`, пустое соединение трактовать как «не получен»:
`ЕСТЬNULL(ОПД.ДокументыПолучены, ЛОЖЬ)`.

Поиск строки «Оригинал» ничего не даст — ошибка из первой постановки.

## H состоит из двух веток

① **проведённые документы без отметки** — их обороты уже в 361;
② **непроведённые документы реализации** — в регистре их нет вообще, берётся `СуммаДокумента`.

Виды документов: `РеализацияТоваровУслуг`, `РеализацияУслугПоПереработке`,
`АктОбОказанииПроизводственныхУслуг`, `ИмпРеализацияСтроительныхРаботУслуг`.
Реквизит договора у всех называется **`ДоговорКонтрагента`**, а не `Договор` — обращение
`Р.Договор.…` падает с «Поле не найдено».

Обе ветки подтверждены на живых данных:

| Проверка | Из базы | Эталон Excel |
|---|---|---|
| Кривий Ріг, E (с отметкой) | 4 713 575,00 | 4 713 575,00 |
| Кривий Ріг, F (оборот Кт) | 4 823 281,25 | 4 823 281,25 |
| Кривий Ріг, H (без отметки, 3 документа) | 1 481 816,00 | 1 481 816,00 |
| E + H = полный оборот Дт | 6 195 391,00 | 6 195 391,00 |
| МД IRC 2026, H (3 непроведённых) | 3 758 899,20 | 3 758 899,20 |

У IRS оборотов по 361 нет вовсе — вся сумма пришла второй веткой. Это и доказывает,
что ветка непроведённых обязательна.

## G — это не сальдо счёта

Реальный остаток по 361 включает акты, поданные без оригинала. Excel их вычитает:

```
Кривий Ріг: сальдо Дт 361      = 1 372 109,75
            H (акты без оригинала) = 1 481 816,00
            1 372 109,75 − 1 481 816,00 = −109 706,25 = G ✓
эквивалентно: G = E − F = 4 713 575,00 − 4 823 281,25 = −109 706,25 ✓
```

Считать через `G = E − F`. Сальдо использовать **только как контрольную сверку** (код К01):
`Сальдо − H_проведённые` обязано дать `G`. Расхождение показывать пользователю, а не прятать.

⚠ В К01 вычитается **только проведённая часть H** — непроведённых в сальдо нет по определению.
Первая версия вычитала всё H и давала ложную тревогу на каждой строке с непроведёнными.

## K: два варианта формулы вместо четырёх

В ручном Excel итог считался по-разному в каждом договоре. Разбор формул показал, что все
четыре случая — это два варианта с одним параметром «процент гарантийного удержания»:

| Договір | % | Формула | Расчёт | K в Excel |
|---|---|---|---|---|
| Глобино 15/10/25 | 0 | `G + I + J + H×1` | −80 598,42 − 15 709,75 + 94 258,50 | −2 049,67 |
| Глобино 21/01-26 | 20 | `J + H×0,8` | −1 414,70 + 6 790,56 | 5 375,86 |
| Глобино 09/04-25 | 20 | `J + H×0,8` | −2 407,18 + 11 554,48 | 9 147,30 |
| Кривий Ріг 06/04/26 | 15 | `(E+H)×0,85 + J − F` | 5 266 082,35 − 246 969,33 − 4 823 281,25 | 1 390 101,77 |

Отсюда:

```
ЗадолженностьПлюсАкты  = G + I + J + H×(1 − Процент/100)
ВыполнениеМинусОплата  = (E + H)×(1 − Процент/100) + J − F
ТолькоРучной           = 0
```

То, что раньше называлось «коэффициент актов» (0,8), — это и есть удержание 20 %.
Отдельного параметра для него не нужно.

⚠ Разбор выше — исторический (август). Пример Глобино 15/10/25 с −2 049,67 — расчёт документа того
времени; директор отрицательный K не показывает (см. ниже), а 15 % Кривого Рога оказались **зачётом
аванса**, а не удержанием.

## K с 28.09.2026: зачёт предоплаты, правило НДС, K ≥ 0

Перепись 8 недель директорских отчётов (07.08…25.09, 967 строк) свела всё к одной модели
(`_Rarzrabotki/Python/test/finrep_k_model.py`, 15 тестов). Спецификация:
`_Rarzrabotki/notebook/specs/2026-09-28-finzvit-oplaty-kazna-predoplata-design.md`.

```
I = −min(СуммаГарантийногоУдержания; max(0; G + H))
J: ОтАктов (или пусто) = −Hб/6; Hб = H для Z/V, для P — неавансовая часть H − min(A_ост; H×p/100)
   НеУчитывать         = 0
   ОтЗадолженности     = −max(0; G)/6
   ПослеРегистрацииПН  = −Σ min(НДС ПН акта (без ПН — акт/6); неоплаченный остаток акта) по актам,
                         чья ПН не зарегистрирована в ЄРПН (с 29.09; оплаты гасят акты по дате)
Z ЗадолженностьПлюсАкты: K = G + I + J + H×(1 − p/100)
V ВыполнениеМинусОплата: K = (E + H)×(1 − p/100) + J − F + I
P ЗачетПредоплаты:
   A_факт = min(A; оплаты с датой ≤ даты первого акта договора)
   A_ост  = ДатаЗачетаПредоплаты заполнена и ≤ ДатаРасчета
              ? max(0; ОстатокПредоплатыНаДату − E_после_даты × p/100)
              : max(0; A_факт − E × p/100)
   K = G + A_ост + H − min(A_ост; H × p/100) + J + I − u/100 × max(0; H − min(max(0; H); A_ост/(p/100)))
   u = ПроцентУдержанияПослеАванса (с 02.10.2026; 0 — без удержания)
K договора = max(0; K); отрицательное → К19. Неизвестный вариант → как Z (К22).
```

Три вида предоплаты: (а) зачёт долей p с каждого акта — Кривий Ріг 06/04/26 (15 %, 1 194 270,00),
Каменец 07/07/26 (50 %, 1 516 008,00) → `ЗачетПредоплаты`; (б) гасится первыми актами полностью —
Глобино, ООН рамка, Чорноморськ, ОРІЛЬ БА1103 → хватает Z; (в) чистый аванс без актов — Кернел Кухня,
ООН РО/PO → `ЗачетПредоплаты` с p = 100.

Формула Excel директора `(E+H)×(1−p) + J − F + A` совпадает с P, **пока A_ост ≥ H×p/100 и F ≥ A**.
При меньшем остатке модель расходится с Excel сознательно: остаток аванса гасится первым.

Отрицательного K у директора нет ни одного за 8 недель, поэтому K ≥ 0 (К06 удалён, красное оформление
формы снято). НДС: −H/6 до 04.09, с 11.09 директор снял J в 7 строках с H > 0 (167 501,77), у ОРІЛЬ 1203
и Подгорцев 28.08–11.09 было −G/6 — отсюда три правила; сейчас везде `НеУчитывать`.

Эталоны на 25.09 (приёмка `doc_finrep_acceptance_oplaty.py`): Кривий Ріг 06/04/26 — 221 548,60
(с датой зачёта 22.09; без неё — 363 559,36, как Excel), элеватор 01/07/26 — 33 163,20, Каменец —
371 004,00, ОРІЛЬ 1203 — 316 611,41, Кернел Кухня — 0,00.

## K суммируется вверх, а не пересчитывается

Итог считается **на строке договора**. На уровнях контрагента и заказчика он складывается
из дочерних, а не вычисляется заново по свёрнутым E/F/G/H.

Проверка на Глобино: `9 147,30 − 2 049,67 + 5 375,86 = 12 473,49` — ровно K строки
«Глобино-2» в Excel. Пересчёт по свёрнутым показателям дал бы другое число.

## Период: только конец дня

Виртуальная таблица `Остатки(М)` берёт остаток **перед** моментом, `Обороты(Н, М)` момент
**включает**. На `00:00:00` они расходятся: по договору ОРІЛЬ сальдо 391 440,55 при нулевом
обороте; на `23:59:59` — ноль и ноль.

Движок приводит дату сам через `МоментРасчета()` = `КонецДня(ДатаРасчета)`. Это не косметика:
COM при записи срезает время до полуночи, и без приведения расчёт уезжает на начало дня.

Связанные файлы: [03_istochniki_zaprosy.md](03_istochniki_zaprosy.md) — тексты запросов;
[04_parametry_dogovora.md](04_parametry_dogovora.md) — где живут C, D, B и процент.

**С 02.10.2026 — удержание после зачёта аванса (u).** Кривий Ріг 06/04/26: аванс 1 194 270,00 зачтён к 22.09, дальше директор считает `G + I + J + H×0,8` (лист 25.09.2026). Ресурс `ПроцентУдержанияПослеАванса` = 20: удерживается u % с той части H, которую остаток аванса уже не покрывает (A_ост/p). Пока аванса хватает — удержания нет (прежняя формула 0,85). На 02.10: K = 177 238,88 (06/04/26) и 33 163,20 (01/07/26) — совпадает с директором. Модель `finrep_k_model.py` под u не обновлялась.

## Кривий Ріг 06/04/26 — формула директора (с 09.10.2026)

Логика договора (подтверждена пользователем 09.10): аванс 15 % (1 194 270 = 15 % × 7 961 800), с каждого акта платят
85 %, 15 % — в зачёт аванса; аванс исчерпается, только когда акты дойдут до полной цены договора. Отсюда директор
каждую неделю (07.08 … 02.10) считает `K = (E + H)×0,85 + J − F + 1 194 270`, исключение — только лист 25.09 «Отчет на
докладе» (`G + I + J + H×0,8`), в «Последних отчетах» 25.09 он вернул свою формулу.

**Ошибка 02.10 (исправлена 09.10):** по этому одному листу в регистр записаны дата зачёта 22.09 + остаток 0 (оплата
22.09 = ровно E − F принята за досрочный зачёт аванса) и «% удержания после аванса» = 20 (условие «80 % суммы акта после
подписания, 20 % после регистрации ПН» — это СРОКИ оплаты 85 %, а не удержание) → K = 0,8×H = 177 238,88 вместо
363 559,36. Теперь у договора: `ЗачетПредоплаты`, p = 15, A = 1 194 270, без даты зачёта, u = 0.

Формула директора тождественна варианту P без даты зачёта, пока остаток аванса покрывает p % поданных актов:
`A_ост = A_факт − E·p ≥ H·p` ⇒ `G + A_ост + H − H·p + J + I = (E + H)(1 − p) − F + A_факт + J + I`.
На 02.10 (данные директора) остаток аванса 175 243,05, K = 363 559,36; на данных 09.10 (задним числом акт, H 243 920,60)
— 382 575,56.

Внутренние договоры ІНДЕПТ СТІЛ → ІНДАСТРІАЛБУД (Чорноморськ, Глобино) с 09.10 снова по формулам директора (Z), правка
04.10 «аванс 30 %» отменена решением пользователя — см. [04](04_parametry_dogovora.md).
