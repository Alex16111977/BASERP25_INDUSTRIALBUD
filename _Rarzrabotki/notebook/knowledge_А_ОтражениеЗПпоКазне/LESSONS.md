## §1. Cross-base UUID: только `V83.string(...)` (английский lowercase)

**Проблема:** при попытке извлечь UUID документа Казны для поиска документа в ERP получаешь либо пустую строку, либо exception.

| Что НЕ работает | Результат |
|---|---|
| `Строка(V83_UUID)` | возвращает `""` или `'None'` — `Строка()` в ERP не сериализует COM-объект чужой базы |
| `XMLСтрока(V83_UUID)` | **Exception:** «Ошибка преобразования данных XML» — XML-сериализатор ERP отбрасывает чужой COM-объект |
| `V83.XMLСтрока(V83_UUID)` | Ненадёжно через COM dispatch (Cyrillic method names через прокси V83.COMConnector) |
| `V83.String(...)` (capitalized) | Может работать в Python, но в BSL предпочтительно lowercase |

**Единственный работающий паттерн:**
```bsl
УИДСтр = V83.string(СтрТЗ.Регистратор.УникальныйИдентификатор());
```

**Why:** BSL COM-proxy предпочитает английские имена методов в lowercase. Этот паттерн используется в production-обработках `Обработка_ПлатежВЕРП`, `ПометитьНаУдалениеБухАкты`.

**How to apply:** для любого cross-base lookup используй `V83.string(REF.УникальныйИдентификатор())`. Никогда — `Строка()` или `XMLСтрока()` на чужом COM-объекте.

⚠️ См. также CLAUDE.md «Cross-base UUID lookup» — детальный разбор всех вариантов.

## §2. `Ссылка` — зарезервированное имя локальной переменной

**Проблема:** объявление `Ссылка = Документы.X.ПолучитьСсылку(УИД)` ломает работу `ПолучитьОбъект()` внутри `Попытка/Исключение` — исключение возникает молча.

**Why:** `Ссылка` в BSL конфликтует со системным свойством `.Ссылка` любого объекта документа. Платформа пытается разрешить имя как свойство объекта, а не как локальную переменную.

**WRONG:**
```bsl
Ссылка = Документы.А_РаспределениеЗаработнойПлаты.ПолучитьСсылку(УИД);  // тихо ломается
Если Ссылка.ПолучитьОбъект() <> Неопределено Тогда ... // молчаливый exception
```

**CORRECT:**
```bsl
ДокСсылка = Документы.А_РаспределениеЗаработнойПлаты.ПолучитьСсылку(УИД);
Если ДокСсылка.ПолучитьОбъект() <> Неопределено Тогда ...
```

**How to apply:** никогда не называй локальную переменную `Ссылка`. Используй `ДокСсылка`, `РезСсылка`, `НайденнаяСсылка`, `ОснСсылка`.

## §3. `ЗначениеВСтрокуВнутр` между разными базами с разными типами справочников

**Проблема:** сериализация `ТаблицаЗначений`, содержащей ссылки на справочники чужой базы, в строку через `V83.ЗначениеВСтрокуВнутр(ТЗ)` и десериализация в ERP через `ЗначениеИзСтрокиВнутр(стр)` дают **невалидные ссылки**, на которых `.УникальныйИдентификатор()`, `XMLСтрока()` и `ЗначениеЗаполнено()` падают молча (внутри Попытка) или с exception.

**Why:** в ZUP/Казна — `Справочник.Сотрудники`/`Справочник.БанковскиеСчета`/etc. В ERP этих типов **не существует** (или они другие). После десериализации в ERP rebuild ссылки с типом «незнакомый» → она ведёт себя как broken ref.

**Конкретный пример из CLAUDE.md (СинхронизироватьТовары):**
- BuhBud имеет `Справочник.БанковскиеСчета`
- ERP имеет `Справочник.БанковскиеСчетаОрганизаций`
- После `ЗначениеИзСтрокиВнутр` в ERP — ссылка невалидна
- `.УникальныйИдентификатор()` бросает exception (молчит в Попытка)

**OK** для ТЗ с примитивами (строки/числа/даты/булево):
```sql
-- В zup_1 → ТЗ → в ERP — OK
У.Сотрудник.Физлицо.КодПоДРФО КАК СотрудникИНН,    -- строка
У.ДокументОснование.Получатель.КодПоЕДРПОУ КАК ЕДРПОУПолучателя,  -- строка
СУММА(У.Результат) КАК Сумма                       -- число
```

**FAIL** для ТЗ со ссылками:
```sql
У.Сотрудник КАК Сотрудник  -- СправочникСсылка.Сотрудники ИЗ zup_1, не из ERP
```

**How to apply:** в COM-запросах ВСЕГДА извлекать ссылки через ".Поле.Поле" до примитивов. Никаких `КАК Сотрудник`/`КАК Контрагент` через ЗначениеВСтрокуВнутр между базами с РАЗНЫМИ типами справочников.

## §4. Rule #-1 — Python COM test BEFORE BSL для запросов к чужим базам

**Проблема:** в Казне и ЗУП есть свои особенности (например, `ВзаиморасчетыПоНДФЛ.Доход` → реально `ДоходПриход` для оборотов; `Сумма` в Хозрасчетном → `КоличествоДт`/`КоличествоКт`). Без Python COM-теста запрос упадёт в Designer/Enterprise с непонятной ошибкой.

**Why:** запросы к чужим базам нельзя проверить через MCP `execute_query` — он работает только с ERP. Только Python COM позволяет реально выполнить запрос на BuhKazn / zup_1 / zup_2 и поймать ошибки до того, как они попадут в продакшен.

**Pattern, который уже находил ошибки в этом проекте (CLAUDE.md):**
- `ВзаиморасчетыПоНДФЛ.Доход` → реально `ДоходПриход` (сальдовый регистр)
- `ЛЕВОЕ СОЕДИНЕНИЕ ... КАК ПО` → реально `КАК ПодрОрг` (`ПО` зарезервировано)
- `Сотрудник.Физлицо.Наименование` у `.Обороты()` где Сотрудник — **реквизит**, не измерение → недоступно

**How to apply:** прежде чем писать ЛЮБОЙ COM-запрос в BSL — сначала прогнать его через Python COM:
```python
import win32com.client, sys
sys.stdout.reconfigure(encoding='utf-8')

v8 = win32com.client.Dispatch("V83.COMConnector")
zup1 = v8.Connect('Srvr="localhost";Ref="zup";Usr="cfo";Pwd="2442"')

q = zup1.NewObject("Запрос")
q.Текст = """..."""
try:
    r = q.Выполнить().Выгрузить()
    print(f"OK, rows={r.Количество()}")
except Exception as e:
    if hasattr(e, 'excepinfo') and e.excepinfo:
        print(f"FAIL: {e.excepinfo[2]}")
    else:
        print(f"FAIL: {e}")
```

Только после успешного запуска — переносить в BSL.

## §5. COM-сессии нужно закрывать ЯВНО

**Проблема:** после COM-вызовов оставшиеся ссылки `V8` / `V83` держат сессию 1cv8.exe на сервере несколько минут (даже после завершения BSL), что блокирует других пользователей.

**WRONG:**
```bsl
Попытка
    V8 = Новый COMОбъект("V83.COMConnector");
    V83 = V8.Connect(...);
    // ... запрос
Исключение
    // не закрыл COM
КонецПопытки;
// V83/V8 живут до конца сессии BSL
```

**CORRECT:**
```bsl
Попытка
    V8 = Новый COMОбъект("V83.COMConnector");
    V83 = V8.Connect(...);
    // ... запрос
Исключение
    V83 = Неопределено;
    V8 = Неопределено;
    ВызватьИсключение "...";
КонецПопытки;
V83 = Неопределено;
V8 = Неопределено;
```

**How to apply:** ВСЕГДА освобождать `V83 = Неопределено; V8 = Неопределено` в обоих ветках Попытка/Исключение.

## §6. Передача массива в COM-запрос — через NewObject в контексте V83

**Проблема:** обычный ERP-массив (`Новый Массив`), переданный как параметр в COM-запрос к Казне/ЗУП, не работает — V83 не понимает его тип.

**WRONG:**
```bsl
масКодПоЕДРПОУ = Новый Массив;
масКодПоЕДРПОУ.Добавить("40645273");
ЗапросНал.УстановитьПараметр("масКодПоЕДРПОУ", масКодПоЕДРПОУ);  // FAIL
```

**CORRECT:**
```bsl
масКодПоЕДРПОУ = Новый Массив;
// ... fill in ERP-context

// Convert to V83-context
масКодПоЕДРПОУ_V83 = V83.NewObject("Массив");
Для Каждого КодЕДРПОУ Из масКодПоЕДРПОУ Цикл
    масКодПоЕДРПОУ_V83.Добавить(КодЕДРПОУ);
КонецЦикла;

ЗапросНал.УстановитьПараметр("масКодПоЕДРПОУ", масКодПоЕДРПОУ_V83);
```

**How to apply:** любой массив, передаваемый как параметр через COM, должен быть создан через `V83.NewObject("Массив")`.

## §7. Сальдовый регистр накопления → префиксы `Приход`/`Расход`/`Оборот`

**Проблема:** запрос `ВЫБРАТЬ Регистр.Налог ИЗ РегистрНакопления.ВзаиморасчетыПоНДФЛ.Обороты(...)` падает — «Поле не найдено».

**Why:** регистр **сальдовый** (НЕ оборотный), поэтому в виртуальной таблице `.Обороты()` поля имеют префиксы:
- `НалогПриход`, `НалогРасход`, `НалогОборот`
- `ДоходПриход`, `ДоходРасход`, `ДоходОборот`

Без префикса — поле не существует.

**CORRECT:**
```sql
ВЫБРАТЬ
    СУММА(ВзаиморасчетыПоНДФЛ.НалогПриход) КАК СуммаНалога,
    СУММА(ВзаиморасчетыПоНДФЛ.ДоходПриход) КАК СуммаДохода
ИЗ
    РегистрНакопления.ВзаиморасчетыПоНДФЛ.Обороты(&НачП, &КонП,,) КАК ВзаиморасчетыПоНДФЛ
```

**How to apply:** перед использованием `.Обороты()` сальдового регистра — проверить структуру через `mcp__1c-workerp__get_metadata_structure` или Python `kazna.Метаданные.РегистрыНакопления.Найти(...)`. Поля будут с префиксами.

## §8. ФильтрФЛ обязателен для всех ТЧ ЗУП-документа после Начислений

**Проблема:** проведение `НачислениеЗарплаты` падает с ошибкой `«Сотрудник пустой»` для регистра `ВзаиморасчетыССотрудниками`.

**Why:** для ФизЛица, у которого нет записи в ТЧ `Начисления`, нет соответствующего Сотрудника. Если в ТЧ Удержания / НДФЛ / ВзносыФОТ попадает такое ФизЛицо — запись регистра падает.

**CORRECT:**
```bsl
// После заполнения Начислений — построить множество "что в Начислениях"
ФЛВНачисленияхСет = Новый Соответствие;
Для Каждого СтрН Из НЗ.Начисления Цикл
    Если ЗначениеЗаполнено(СтрН.Сотрудник) Тогда
        ФЛ = СтрН.Сотрудник.ФизическоеЛицо;
        Если ЗначениеЗаполнено(ФЛ) Тогда
            ФЛВНачисленияхСет.Вставить(ФЛ, Истина);
        КонецЕсли;
    КонецЕсли;
КонецЦикла;

// Все следующие циклы — фильтр по этому множеству
Для Каждого СтрНБ Из НалогиБухгалтерия Цикл
    Если ФЛВНачисленияхСет[СтрНБ.Сотрудник.ФизическоеЛицо] = Неопределено Тогда
        Продолжить;  // ОБЯЗАТЕЛЬНО
    КонецЕсли;
    // ... заполнение НДФЛ или ВзносыФОТ
КонецЦикла;
```

**How to apply:** в `СоздатьДокументНачисления` после ТЧ Начислений — строить множество ФизЛиц и фильтровать все остальные ТЧ.

## §9. Подмена группы «Прочие пассивы» в `СтатьяАктивовПассивов`

**Проблема:** проведение `ОтражениеЗарплатыВФинансовомУчете` падает, потому что `СтатьяАктивовПассивов = ГРУППА "Прочие пассивы"` (не элемент).

**Why:** в ТЧ `УдержанияБухгалтерия` родителя случайно записана ссылка на ГРУППУ, а не предопределённый ЭЛЕМЕНТ. ERP проверяет тип и отказывается работать с группой.

**CORRECT:**
```bsl
ПрочиеПассивыЭлемент = ПланыВидовХарактеристик.СтатьиАктивовПассивов.ПрочиеПассивы;  // предопределённый ЭЛЕМЕНТ

Если ЗначениеЗаполнено(НоваяСтр.СтатьяАктивовПассивов)
    И НоваяСтр.СтатьяАктивовПассивов.ЭтоГруппа Тогда
    НоваяСтр.СтатьяАктивовПассивов = ПрочиеПассивыЭлемент;
КонецЕсли;
```

**How to apply:** при копировании из родителя в дочку — проверять `.ЭтоГруппа` и подменять на предопределённый элемент.

## §10. Изменение TZ-чувствительных datetime в COM-параметрах

**Проблема:** Python `datetime` (особенно tz-aware) при передаче в COM-параметр запроса проседает в TZ-сдвиг (несколько часов), и фильтр `МЕЖДУ &НачП И &КонП` выдаёт неожиданные результаты.

**Why:** COM-маршаллер не унифицирует TZ — Python `datetime(2026, 4, 1, 0, 0, 0, tzinfo=tz)` может стать в 1С `2026-03-31 22:00:00`.

**WRONG:**
```python
q.УстановитьПараметр("НачП", datetime(2026, 4, 1, 0, 0, 0))  # без TZ-aware
# или
q.УстановитьПараметр("НачП", datetime(2026, 4, 1, 0, 0, 0, tzinfo=tz_utc))  # с TZ
```

**CORRECT — inline в SQL:**
```python
q.Текст = """
ВЫБРАТЬ ...
ИЗ ...
ГДЕ Регистр.Период МЕЖДУ ДАТАВРЕМЯ(2026, 4, 1, 0, 0, 0) И ДАТАВРЕМЯ(2026, 4, 30, 23, 59, 59)
"""
```

**How to apply:** для критичных периодов — inline через `ДАТАВРЕМЯ(...)` в SQL, не как параметр.

## §11. `В ИЕРАРХИИ` внутри агрегата (СУММА/ВЫБОР) запрещено

**Проблема (из CLAUDE.md):** `СУММА(ВЫБОР КОГДА X В ИЕРАРХИИ (...) ТОГДА Y ИНАЧЕ 0 КОНЕЦ)` — выдаёт ошибку «Не допускается использование вложенных запросов и операции В ИЕРАРХИИ внутри агрегатных функций».

**Why:** платформа не умеет компилировать `В ИЕРАРХИИ` в скалярное выражение внутри агрегата.

**Workaround:** `UNION ALL` с `В ИЕРАРХИИ` в `WHERE`:
```sql
ВЫБРАТЬ Сумма КАК Приход, 0 КАК Расход
ИЗ ... ГДЕ СчетДт В ИЕРАРХИИ (...)
ОБЪЕДИНИТЬ ВСЕ
ВЫБРАТЬ 0, Сумма
ИЗ ... ГДЕ СчетКт В ИЕРАРХИИ (...)
```

**How to apply:** если нужна агрегация с фильтром по иерархии — разбивай на 2 запроса через UNION ALL.

## §12. В Хозрасчетный (корреспондентный) нет поля `Количество`

**Проблема:** запрос к `РегистрБухгалтерии.Хозрасчетный` с полем `Количество` падает — «Поле не найдено».

**Why:** регистр **корреспондентный** (Корреспонденция = Истина), поэтому количество разделено по сторонам: `КоличествоДт` + `КоличествоКт`. Аналогично — `СчетДт`/`СчетКт`, `СубконтоДт1-3`/`СубконтоКт1-3`. `Сумма` НЕ разделена (одно поле).

**WRONG:**
```sql
ВЫБРАТЬ СУММА(Д.Количество) ИЗ РегистрБухгалтерии.Хозрасчетный КАК Д
```

**CORRECT:**
```sql
ВЫБРАТЬ
    СУММА(Д.КоличествоДт - Д.КоличествоКт) КАК Количество
ИЗ РегистрБухгалтерии.Хозрасчетный КАК Д
```

⚠️ Это применимо и к BuhBud, и к ERP — оба используют корреспондентный Хозрасчетный.

## §13. Создание сотрудника из чужой базы — через `А_Привилегированный`

**Проблема:** прямое создание `Справочник.Сотрудники` через `СоздатьЭлемент()` в обработке часто требует привилегий (доступ к Физическим Лицам, заполнение паспортов и т.д.).

**Solution:** все создания идут через привилегированную процедуру `А_Привилегированный.СоздатьСотрудникаИзКазны(ФИО, ИНН, КодКазны)`:

```bsl
НайдСотр = А_Привилегированный.СоздатьСотрудникаИзКазны(ФИОК, ІННК, КодК);
```

Это происходит **ТОЛЬКО** если поиск по ФИО (кеш) и ИНН (А_КодПоДРФО) не дал результата.

**How to apply:** для любых operations, требующих повышенных прав в Документах из обработок — использовать `А_Привилегированный.*`. Документ объявлен с `<PostInPrivilegedMode>true</PostInPrivilegedMode>`.

## §14. ОЧЕНЬ ВАЖНО: реальный источник Налогов/Удержаний — `zup_1`, не `BuhBud`

**Проблема:** PROMPT.md описывает архитектуру так, как будто данные приходят из BuhBud (BAS Бухгалтерія). Реальный код подключается к **`zup_1`** (BAS ЗУП регламент).

**Why:** PROMPT.md был основан на устаревшем предположении. Реальный код в `Documents/А_ОтражениеЗПпоКазне/Ext/ObjectModule.bsl` (строка 422):
```bsl
СтрокаПодключенияЗУП = "Srvr=""SQLSERVER"";Ref=""zup_1"";Usr=""cfo"";Pwd=""2442""";
```

**How to apply:** при работе с этим документом — учитывать что:
- Для НалогиБухгалтерия + УдержанияБухгалтерия — connection `zup_1`
- Для НачисленияУпр + УдержанияУпр — connection `zup_2`
- К BuhBud (BAS Бухгалтерія) обращений **нет**

Однако антипаттерны из CLAUDE.md по BuhBud (КоличествоДт/Кт в Хозрасчетный, СубконтоДт1 недоступно в основной таблице) — **актуальны** для других задач/процессоров и могут пригодиться позднее.

## §15. `СуммаНДФЛ ≠ 0`, НЕ `Сумма ≠ 0` для фильтрации НДФЛ-строк

**Проблема:** Op 3 (`_ОтрЗП_ЗаполнитьНДФЛИзНалогов`) ошибочно записывает ЕСВ-строки в НачисленныйНДФЛ — потому что в НалогиБухгалтерия `Сумма` имеет fallback на `СуммаФОТ` для ЕСВ.

**Why:** Сумма для НДФЛ-строк = СуммаНДФЛ, для ЕСВ-строк = СуммаФОТ. Если фильтровать `Сумма > 0` — оба типа попадают.

**WRONG:**
```bsl
Если СтрокаНалога.Сумма = 0 Тогда Продолжить; КонецЕсли;  // ЕСВ-строки тоже пройдут
```

**CORRECT:**
```bsl
// Берём ТОЛЬКО строки с НДФЛ/ВС (СуммаНДФЛ > 0)
Если СтрокаНалога.СуммаНДФЛ = 0 Тогда Продолжить; КонецЕсли;
```

Аналогично для Op 1 — фильтр на СуммаФОТ:
```bsl
Если СтрокаНалога.СуммаФОТ = 0 Тогда Продолжить; КонецЕсли;
```

**How to apply:** в смешанных ТЧ типа НалогиБухгалтерия (НДФЛ+ВС+ЕСВ в одной таблице) — фильтровать ВСЕГДА по специфическому полю суммы (`СуммаНДФЛ` для НДФЛ/ВС, `СуммаФОТ` для ЕСВ), НЕ по общему `Сумма`.

## §16. Источник истины должен быть ОДИН — не дублировать недостающие данные через параметры (2026-05-28)

**Проблема:** изначально (v1 2026-05-27) процедура создания ВКассу жила в `Документ.РаспределениеФ2`, а А_ОтражениеЗПпоКазне через кнопку лишь группировал строки и **передавал недостающие данные параметрами** в Ф2-процедуру:

```bsl
// v1 (плохо): в А_ОтражениеЗПпоКазне
СловарьСтатей = Новый Соответствие;  // (Сотр_UID|ПодрОрг_UID → СтатьяДДС)
// ... заполнить словарь из ТЧ.РаспределениеКазна ...
Ф2Объект.СоздатьВедомостьНаВыплатуВКассуПоРаспределениюФ2(СловарьСтатей, Ссылка);

// v1 (плохо): в Ф2 — попытка получить СтатьюДДС из словаря
СтатьяДДС = СтатьиДДСПоКлючу.Получить(Ключ);
Если СтатьяДДС = Неопределено Тогда
    Сообщить("WARN: СтатьяДДС не найдена...");  // десятки таких WARN'ов
КонецЕсли;
```

**Почему плохо:**
1. **Архитектурный обман.** Кнопка в форме Ф2 + триггер `ПриЗаписи` создавали впечатление, будто Ф2 — самостоятельный источник. На самом деле РаспределениеФ2 в ERP — пустая оболочка после обмена (UUID 1:1 с Казной, **без СтатьиДДС**, которая физически живёт только в БДДС Казны).
2. **Хрупкий ключ.** Словарь индексировался по паре `(Сотрудник, ПодразделениеОрганизаций)`. Обе стороны должны были использовать идентичную конвертацию СтрПредпр→ПодрОрг (`А_Привилегированный`), иначе ключи не совпадали → потеря СтатьиДДС → WARN'ы.
3. **Схлопывание строк.** Если один сотрудник в одном подразделении имел **несколько строк** в БДДС с разными СтатьямиДДС (например, "Зарплата производственного персонала" + "Зарплата ИТР" + "Зарплата управленческого персонала"), словарь с ключом `(Сотр, Подр)` оставлял только одну — последняя перетирала предыдущие.
4. **Двойная поддержка.** Каждое изменение требовало правки в двух местах (Ф2-процедура + сборщик словаря в А_ОтражениеЗПпоКазне), что приводило к рассинхронизации.

**Решение (v2 2026-05-28):** **полностью отказаться** от Ф2-процедуры. Источник истины — `ТЧ.А_ОтражениеЗПпоКазне.РаспределениеКазна`. Она содержит **ВСЁ** необходимое для каждой строки (Сотрудник, исправленное Подразделение, НаправленияДеятельности, СтатьяДвиженияДенежныхСредств, Сумма, связь с Ф2). А_ОтражениеЗПпоКазне напрямую строит ВКассу — без вызовов в Ф2, без словарей.

```bsl
// v2 (хорошо): в А_ОтражениеЗПпоКазне напрямую
Для Каждого СтрРК Из СтрокиРК Цикл
    НовР = ВыкВКассу.А_РасшифровкаВыплатыЗарплатаПоФизлицам.Добавить();
    НовР.НаправлениеДеятельности       = СтрРК.НаправленияДеятельности;
    НовР.СтатьяДвиженияДенежныхСредств = СтрРК.СтатьяДвиженияДенежныхСредств;  // прямо из РК!
    // ...
КонецЦикла;
```

**Результат v2:**
- 0 WARN'ов про "СтатьяДДС не найдена".
- 5 строк Пономаренко (Главный офис) теперь корректно получают **3 разные** СтатьиДДС (а не одну).
- Документ.РаспределениеФ2.ObjectModule: 358 → 20 строк.
- Кнопка из формы Ф2 удалена — пользователь больше не запутается.

**How to apply (общий принцип):** если для создания/заполнения объекта X нужны данные из источника Y, и X-источник Z к этим данным напрямую не имеет доступа, **НЕ передавай данные параметрами через Z** — перенеси создание X **в Y** (или туда, где данные исходно живут). Параметры со словарями недостающих данных — почти всегда симптом неправильного выбора места размещения процедуры.

См. также: [12_button_iz_otrazheniya.md](12_button_iz_otrazheniya.md) §1 «Источник истины должен быть один».

## §17. Гард `А_Необновлять` — защита занятых ВКассу от перезаписи (2026-05-29)

**Проблема:** при повторном нажатии кнопки «Создать ведомости в кассу» в форме А_ОтражениеЗПпоКазне процедура Find-or-Create затирала **уже занятые** ВКассу — те, по которым выпущен и проведён РКО. После такой перезаписи движения РКО (РН.А_ВзаиморасчетыССотрудниками и др.) расходились с реальной ТЧ.А_Расшифровка → возникала рассинхрония, требующая ручного recovery.

**Why:** find-or-create использовал ключ `А_РаспределениеФ2 = &Основание` и при наличии ВКассу безусловно делал `Распровести + Очистить(3 ТЧ) + Перезаписать`. Реквизит `А_Необновлять` (Булево) в метаданных уже был и автоматически выставлялся в Истина процедурой `РасходныйКассовыйОрдер.ПриЗаписи` (стр. 1127-1131, формула `А_Необновлять = Источник.Проведен`), но в `_ОЗП_СоздатьВКассуИзФ2` не учитывался.

**WRONG (до 2026-05-29):**
```bsl
Если НЕ Результат.Пустой() Тогда
    Выб = Результат.Выбрать(); Выб.Следующий();
    ВыкВКассу = Выб.Ссылка.ПолучитьОбъект();    // 🔥 модификация началась
    Если Выб.ПометкаУдаления Тогда ВыкВКассу.УстановитьПометкуУдаления(Ложь); КонецЕсли;
    Если Выб.Проведен Тогда ВыкВКассу.Записать(РежимЗаписиДокумента.ОтменаПроведения); КонецЕсли;
    ВыкВКассу.Зарплата.Очистить();              // 🔥 данные занятой ВКассу затёрты
    ...
КонецЕсли;
```

**CORRECT (с 2026-05-29):**
```bsl
"ВЫБРАТЬ ПЕРВЫЕ 1
|	Д.Ссылка, Д.Проведен, Д.ПометкаУдаления,
|	Д.А_Необновлять КАК А_Необновлять              ← добавлено
|ИЗ Документ.ВедомостьНаВыплатуЗарплатыВКассу КАК Д
|ГДЕ Д.А_РаспределениеФ2 = &Основание"
...
Если НЕ Результат.Пустой() Тогда
    Выб = Результат.Выбрать(); Выб.Следующий();

    Если Выб.А_Необновлять Тогда                   ← гард ПЕРВЫМ ДЕЙСТВИЕМ
        Сообщить("Ф2 " + Строка(Ф2Ссылка) + " → ВКассу " + Строка(Выб.Ссылка)
            + " пропущена (А_Необновлять=Истина, занята РКО)");
        Возврат "Пропущено";
    КонецЕсли;

    ВыкВКассу = Выб.Ссылка.ПолучитьОбъект();
    ...                                              // безопасно — флаг = Ложь
КонецЕсли;
```

**Контракт:** связь «занятая РКО ↔ заблокированная ВКассу» поддерживается **двумя** местами:
1. `РасходныйКассовыйОрдер.ПриЗаписи` → `А_Необновлять = Источник.Проведен` (флаг ставится/сбрасывается автоматически при проведении/распроведении).
2. `_ОЗП_СоздатьВКассуИзФ2` → гард → `Возврат "Пропущено"` (защита от перезаписи).

Без обоих контракт не работает.

**Сигнатура процедуры:** при добавлении гарда удобно сменить `Процедура → Функция` со **строковым кодом результата** (`"Создано" / "Обновлено" / "Пропущено" / "Ошибка"`). Вызывающая (`СоздатьВедомостиВКассуПоОтражениюЗП`) делает switch по коду и инкрементирует 3 счётчика. Параметр byref `Структура` тоже работает, но строковый код проще читать в логе и в коде вызывающей.

**Обратимость:** распроведение РКО → `А_Необновлять = Ложь` (формула) → следующий запуск кнопки обновит ВКассу как раньше. Никакого явного «разблокировщика» в коде писать не надо.

**Пометка удаления + флаг:** теоретически ВКассу может иметь одновременно `ПометкаУдаления = Истина` и `А_Необновлять = Истина` (хотя `РасходныйКассовыйОрдер.ПередЗаписью` обычно этого не допускает). Гард срабатывает первым → пометку удаления НЕ снимаем. Это согласуется с контрактом «не трогать».

**How to apply (общий паттерн):**
- Find-or-Create процедуры, модифицирующие существующий объект, должны **сначала** проверять «можно ли модифицировать» (право, флаг, статус), и только потом начинать модификацию.
- Когда у процедуры появляется 3+ разных исхода — превращать её в Функцию со строковым кодом результата. Скаляр проще читать, чем структуру.
- Связь «занятый источник ↔ заблокированный потребитель» поддерживается **парой** подписей в обоих направлениях. Без обоих контракт рвётся при первом же edge-case.

См. также: [15_vkassu_skip_neobnovlyat.md](15_vkassu_skip_neobnovlyat.md), [14_rko_vzaimoraschety_iz_vkassu.md §Урок №5](14_rko_vzaimoraschety_iz_vkassu.md), CLAUDE.md «Programmatic Document Creation».

## §18. `НачисленнаяЗарплата.Сумма` — это GROSS, движение А_ВзСС САМ вычитает НДФЛ (2026-05-31)

**Проблема:** при разметке `ФормаPL` я положил в Форма1 сумму `bukh = НачисленияБух − НДФЛ − удерж` (NET, take-home). Результат: ОЗФУ «Оплата труда» Форма1 = **19 575,72** вместо **27 913,53** (разница = 8 337,81 = НДФЛ). Двойное вычитание НДФЛ.

**Why:** колонка `НачисленнаяЗарплатаИВзносыПоФизлицам.Сумма` семантически = **GROSS** (начисление). Движение `РегистрНакопления.А_ВзаиморасчетыССотрудниками` («Оплата труда») при проведении ОЗФУ вычисляет take-home = `НачисленнаяЗарплата − НачисленныйНДФЛ − УдержаннаяЗарплата`. Если в колонку класть уже-NET (bukh), НДФЛ вычитается **второй раз**.

**WRONG:**
```bsl
// базис Форма1 = NET (bukh)
Бух[ФЛ] = НачисленияБух − НалогиБухгалтерия.СуммаНДФЛ − УдержанияБухгалтерия;  // 27 913,53
// → А_ВзСС = 27 913,53 − НДФЛ(8 337,81) = 19 575,72 ❌
```

**CORRECT:**
```bsl
// базис Форма1 = GROSS
Бух[ФЛ] = Σ НачисленияБух;  // 36 251,34, БЕЗ вычитания НДФЛ/удержаний
// → А_ВзСС = 36 251,34 − НДФЛ(8 337,81) = 27 913,53 ✓ = РаспределениеКазна.Зарплата = перенос
```

**How to apply:** при разметке/делении GROSS-колонки (`НачисленнаяЗарплата.Сумма`) клади **gross**, не net. Take-home получает движение `А_ВзСС`/`ПАП` вычитанием НДФЛ/удержаний. Эталон контроля: ОЗФУ Форма1 «Оплата труда» = `РаспределениеКазна` «Зарплата управленческого персонала» (NET, выплата в банк). См. [17_formapl_split.md §5](17_formapl_split.md).

## §19. Пере-создание ОЗФУ через COM ПОДВОИТ ТЧ — проверять по saved parent, не по COM-ОЗФУ (2026-05-31)

**Проблема:** при пере-создании `ОтражениеЗарплатыВФинансовомУчете` через `V83.COMConnector` (`obj.СоздатьДокументОтражениеЗарплатыВФинансовомУчете()`) ТЧ `НачисленнаяЗарплатаИВзносыПоФизлицам` **удваивается** (декабрь: 13,9 М вместо 6,9 М; 2618 строк = 2×). ## §20. Счёт 661 = ЗП на BaseERP (имя «ЦПХ»); enum читать через `XMLСтрока`, не `str()` (2026-05-31)

**Проблема 1 (счёт):** при заполнении `НачисленияБух.СчетКт` логично искать «зарплатный» счёт. Классический «Розрахунки за заробітною платою» на BaseERP **пуст**.

**Why:** для строительной «ІНДАСТРІАЛБУД» зарплата идёт через договоры ЦПХ → реальный счёт = **661 «Розрахунки за договорами ЦПХ»** (2908 движений, Σ Кт = 33 229 123,52 ₴).
```bsl
СчетКт661 = ПланыСчетов.Хозрасчетный.НайтиПоКоду("661");
НоваяСтрока.СчетКт = СчетКт661;
НоваяСтрока.СубконтоКт1 = ФизЛицоERP;   // ФизическиеЛица
```

```python
def enum_name(v):

# str(r.ФормаPL) — НЕ использовать для enum
```

**How to apply:** для enum-полей в Python COM — `erp.XMLСтрока(v)` (даёт имя значения) + `erp.ЗначениеЗаполнено(v)`. Ссылки (`<COMObject>` в repr) — это норма, не ошибка. См. [17_formapl_split.md §2](17_formapl_split.md), память `baserp_661_zp_account_cph`.

## §21. Один НДФЛ — один ключ разбивки по подразделениям; разрыв «начислено↔выплачено» = норма (2026-06-01)

**Проблема:** в `А_ВзаиморасчетыССотрудниками` (Ф1) по Шишкіної Спецтехника висел остаток **−0.01** (Приход 6685.70 ≠ перенос `ПередачаНачислений` 6685.71).

**Why:** официальный Ф1-НДФЛ (3994.06) разбивался по подразделениям **дважды по разным ключам**:
- gross-up «Удержание с админ зарплату» в `НачисленнаяЗарплатаИВзносыПоФизлицам` (Op2, `_ОтрЗП_СоздатьСтрокиNETФЛ_Новый`) — равномерно **1997.03/1997.03**;
- ТЧ `НачисленныйНДФЛ` (Op3, `_ОтрЗП_ЗаполнитьНДФЛИзНалогов`) — налог-за-налогом (НДФЛ и ВС отдельными проходами `остаток-на-последнем`) — **1997.02/1997.04**.

Регистр Приход = `Начислено − НачисленныйНДФЛ` = «Зарплата управл» + («Удержание» − НДФЛ); ненулевая разница `(Удержание − НДФЛ) = ±0.01` и есть расхождение с переносом (= «Зарплата управл»).

**Фикс:** новая `_ОтрЗП_ВыровнятьУдержаниеСНДФЛ` — перестраивает gross-up «Удержание» Ф1 **ровно под `НачисленныйНДФЛ` per (ФЛ,Подр)**, Σ per ФЛ сохраняется. Вызов в `ЗаполнитьДляОтражения_...` ПОСЛЕ `РазметитьФормаPL`, ДО `ПроставитьОргБухВсемФорма1`.

```bsl
// WRONG: «Удержание» и НачисленныйНДФЛ разбиты независимо → ±0.01 на подразделение
// CORRECT: «Удержание»(подр) := НачисленныйНДФЛ(подр)  → Начислено−НДФЛ = «Зарплата управл»
```

**How to apply:**
- Если один и тот же налог попадает в две ТЧ — разбивать обе по подразделениям **из одного источника** (производно), а не двумя независимыми проходами округления.
- **Разрыв «начислено(Бухгалтерия) ↔ выплачено(Казна)»** (Шишкіна: −110.26 Ф1, +128.58 Ф2, итого +18.32) — **НОРМА, не дефект** (банк доплатит в след. месяце / касса выплатит меньше). Регистр против фактических выплат за месяц в ноль НЕ сводить. Чинить только копеечный класс (накопления↔перенос).
- Σ-preserving правка (перераспределение внутри ФЛ) безопасна — не может задеть крупные суммы; это отделяет «свой» класс копеек от до-существующих структурных расхождений (196 GROSS-style ФЛ — отложено).

См. [18_vzss_uderzhanie_ndfl_align.md](18_vzss_uderzhanie_ndfl_align.md), память `vzss_f1_uderzhanie_ndfl_align`.

## §22. Op2b-fallback должен идти через ЕДИНЫЙ сплиттер — `РаспределениеКазна.ФормаPL` это источник истины (2026-06-03)

**Проблема:** ФЛ без `НачисленияУпр` (zup_2) — напр. Батрак — проваливались в fallback Op2b
(`_ОтрЗП_ЗаполнитьНачисленияЗП`), который **агрегировал `СуммаНачисления` по сотруднику, схлопывая
Ф1+Ф2 в один бакет** (теряя `ФормаPL`). Дальше `_ОтрЗП_РазметитьФормаPL` пытался восстановить сплит
коэффициентом `Ф1 = Сумма × GROSSбух / ТоталNET`. Результат: Батрак Ф1 «Зарплата управл» = **17 717,12**
вместо **15 400** (Δ 2 317,12). Зеркальный сдвиг в Ф2. Blast-radius: 47 из 128 Op2b-ФЛ, Σ перекоса 92 911,51.

**Фингерпринт:** `35 700 × 20 000 / 40 300 = 17 717,12`; знаменатель 40 300 = 35 700 («Зарплата управл»)
+ 4 600 («Удержание» gross-up, ошибочно в `ТоталNET`).

**Why:** существовали ДВА расходящихся механизма сплита Ф1/Ф2 — явный корректный Op2a
(`_ОтрЗП_СоздатьСтрокиNETФЛ_Новый`: `Ф1 = clamp(GROSSбух−НДФЛ, 0, NET)`) и коэффициентный Op2b. Коэффициент
даёт долю от GROSS, а пост-§21 контракт регистра требует take-home (после выравнивания «Удержание»=НДФЛ
движение даёт `Приход(Ф1) = «Зарплата управл»`).

**Доказано на данных (read-only):** для ВСЕХ 127 Op2b-ФЛ `ФормаPL == тип ДокРаспределениеЗП`
(Ф1⟺`А_РаспределениеЗаработнойПлаты`, Ф2⟺`РаспределениеФ2`) И `Казна_Ф1 == GROSSбух−НДФЛ` — 0 расхождений.
То есть `РаспределениеКазна.ФормаPL` — самосогласованный авторитетный сплит.

**Фикс:** ветку Op2b направить в ТОТ ЖЕ `_ОтрЗП_СоздатьСтрокиNETФЛ_Новый`, что и Op2a, с
`NET = Σ РаспределениеКазна.СуммаНачисления` (все формы). Даёт Ф1=Казна_Ф1, Ф2=Казна_Ф2, по итогам и
по подразделениям. Коэффициент-ветка `_ОтрЗП_РазметитьФормаPL` для «Зарплата управл» становится
неактивной (строки приходят размеченными). GREEN: 0/128 дефектов, инвариант Σ(Ф1+Ф2)=NET у 191 ФЛ,
Батрак 15 400/20 300.

**How to apply:** при наличии fallback-ветки для подмножества объектов — она ДОЛЖНА вызывать тот же
расчётный примитив, что и основная (single source of truth). Не восстанавливать потерянный разрез
эвристикой (коэффициентом), если он уже есть в данных-первоисточнике (здесь — `ФормаPL` на строке Казны).
**Грабли-смежные:** разрыв «начислено(ЕРП Форма1) ↔ Бухгалтерия 661/663» у отдельных ФЛ (Тужиков 3 756,26,
Корнієнко 768,38) — это НЕ коэффициент-баг, а ранее существовавшее расхождение, которое перекос маскировал;
вне scope этого фикса (класс §21).

## §23. НДФЛ/ВС Форма1 закрепляются за юр.лицом из `НалогиБухгалтерия.Организация` (per-org, не пропорция); заполнитель движения А_ВзСС уже org-aware (2026-06-04)

**Проблема:** 11 ФЛ, работающих на нескольких юр.лицах (Воронцов, Манжула, Аулова, Шостак, Соколенко,
Шинкаренко, Шкурат, Пономаренко О/В, Травінський, Скрипник С), давали расхождение `А_ВзСС Форма1` ↔ Бух 661/663
**по каждому юр.лицу** (ФЛ-итог = 0, общий баланс верен). Разлёт каждого = **ровно его НДФЛ+ВС**
(Воронцов ±41 503,50 = ДЖИ 4 703,50 + ІНД 36 800).

**Корневая причина:** «Зарплата управл» Ф1 несла верный per-org `ОрганизацияБухгалтерия` (из Казны), а
**НДФЛ и gross-up «Удержание» теряли организацию**: `_ОтрЗП_ЗаполнитьСтрокуНДФЛ` ставил только `Организация`=шапка,
а `_ОтрЗП_ВыровнятьУдержаниеСНДФЛ` тянул ОргБух из старых «Удержание»-строк → у multi-org ФЛ весь gross-up
садился на ОДНО юр.лицо. В движении А_ВзСС «Оплата труда» `(НачисленнаяЗарплата вкл.«Удержание») − НДФЛ`,
агрегировано по ОргБух: «Удержание» и НДФЛ на РАЗНЫХ юр.лицах → по юр.лицу не гасятся.

**Точный источник:** `НалогиБухгалтерия.Организация` (измерение `Сотрудник`) — ЯВНАЯ организация налога,
заполнена per-org (0 пустых среди 11), даёт точный сплит. **Это НЕ пропорция** (пропорция дала бы ДЖИ ≈ 4 702,8).

**Ключевой инсайт (сократил scope):** заполнитель движения регистра
`РегистрНакопления.А_ВзаиморасчетыССотрудниками.ManagerModule.ЗаполнитьИзОтраженияЗП` **УЖЕ** читает
`НачисленныйНДФЛ.ОрганизацияБухгалтерия` (вычитает со знаком −) и группирует движения по `ОрганизацияБухгалтерия`.
Править его НЕ нужно — достаточно, чтобы ОЗФУ.НачисленныйНДФЛ.ОргБух нёс per-org. Реальный enabler в
`СоздатьДокументОтражениеЗарплатыВФинансовомУчете`: там был **явный override** ОргБух картой «Зарплата управл»
(доминантная орг) — его и заменили на приоритет per-org.

**Фикс (4 правки тега ОргБух в `Documents/А_ОтражениеЗПпоКазне/Ext/ObjectModule.bsl`, суммы инвариантны, Σ-preserving):**
1. `_ОтрЗП_ЗаполнитьСтрокуНДФЛ` — `НоваяСтрока.ОрганизацияБухгалтерия = ?(ЗначениеЗаполнено(СтрокаНалога.Организация), СтрокаНалога.Организация, Организация)`.
2. `_ОтрЗП_ВыровнятьУдержаниеСНДФЛ` — ключ НДФЛ `(ФЛ|Подр|ОргБух)`, «Удержание» зеркалит НДФЛ per-org (убран `ОргБухК` старых строк).
3. `СоздатьДокументОтражениеЗарплатыВФинансовомУчете` — override НДФЛ-ОргБух заменён на `?(ЗначениеЗаполнено(СтрБ.ОрганизацияБухгалтерия), СтрБ.ОрганизацияБухгалтерия, _ОЗП_ОргБухИзКарты(...))` (карта = fallback).
4. `_ПНМП_ЗаполнитьНалоги` — НДФЛ/ЕСВ берут ОргБух из строки-источника, не из «первой орг» (`ОргБухПоФЛ` = fallback).

**Проверено:** GREEN-8a (in-memory, без записи): для всех 11 A-ФЛ `НачисленныйНДФЛ` и «Удержание» per (ФЛ,Орг)

**How to apply:** per-entity атрибут (здесь организация налога) тянуть из строки-первоисточника
(`НалогиБухгалтерия.Организация`), а НЕ из «доминантной/первой» карты-эвристики. Перед правкой заполнителя
движения проверь, не разрезает ли он УЖЕ по нужному измерению (часто да — тогда фикс только в upstream-данных).

data-completeness, НЕ этот фикс. `УдержанияБухгалтерия` (реальные удержания, напр. алименты) остаются на карте

## §25. Больничный «за счёт ФСС» при GROSSбух(661) < НДФЛ: «Зарплата»Ф1 клампится к 0 → осиротевший gross-up «Удержание» съедает НДФЛ → больничный остаётся GROSS (фантом) (2026-06-10, FIXED)

**Проблема:** у ФЛ, где весь официальный доход — больничный «за счёт ФСС» (663), без регулярной ЗП на 661 (GROSSбух=0),
А_ВзСС Форма1 Приход = больничный GROSS (а не NET) → фантомный остаток = НДФЛ больничного (Григоренко фев.2026: +594,74,
выплата 1991,09 NET). Эмпирически: **только 1 из 3** больничных-ФСС ФЛ (Хурсін/Ямковий с регулярной ЗП ≥ НДФЛ — балансны).

**Корень:** Op2a `_ОтрЗП_СоздатьСтрокиNETФЛ_Новый` строит `«Зарплата»Ф1 = Макс(0, GROSSбух − НДФЛ)` (clamp @2068)
+ gross-up `«Удержание» = НДФЛ`. При `GROSSбух < НДФЛ` «Зарплата» клампится к 0 → НДФЛ больничного ничем не поглощается;
осиротевший «Удержание»(+НДФЛ) гасит `НачисленныйНДФЛ`(−НДФЛ) в группировке `А_ВзСС.ManagerModule.ЗаполнитьИзОтраженияЗП`
(per ФЛ,Подр,Ф1,ОргБух) → больничный GROSS не нетится. Op4 step-4 чинит это для `0<ГБ<НД`, но гард `ГБ > 0` пропускал ГБ=0.

**Фикс (Op4 step-4, `_ОтрЗП_ЗаполнитьБольничныеИзФондов`, ObjectModule.bsl:1295-1297):** гард `ГБ > 0 И ГБ < НД` → `ГБ < НД`;
`Р.Сумма = ГБ` → `Р.Сумма = Макс(0, ГБ)`. Клампований больничный (вкл. ГБ=0) → «Удержание»=0 → `НачисленныйНДФЛ`
напрямую нетит больничный GROSS до take-home. Σ bukh(661/663)/`НачисленныйНДФЛ` неизменны.

**Грабли:**
- GROSS-модель больничного сама по себе КОРРЕКТНА (А_ВзСС сам вычитает НДФЛ, §18). Баг — **осиротевший** gross-up «Удержание»,
  который съедает НДФЛ ДО того, как тот уменьшит больничный. Возникает ТОЛЬКО когда «Зарплата»Ф1 клампится к 0 (GROSSбух<НДФЛ).
- Фантом ≠ у всех больничных. H1 прома («фантом у всех больничных-ФСС») **опровергнута** эмпирически (1 из 3).

**Проверено (RED→GREEN, in-memory, БЕЗ записи):** `test_bolnichny_fss_vzss_net.py` — Григоренко Δ +594,74 → 0; Хурсін/Ямковий
регресс Δ=0 (RED и GREEN); март/апрель тот же класс (`diag_grigorenko_months.py` Δ=0). Шишкіна копейка (§21) PASS.
