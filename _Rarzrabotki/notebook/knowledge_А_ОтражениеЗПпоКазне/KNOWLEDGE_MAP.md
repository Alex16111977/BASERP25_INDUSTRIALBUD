# KNOWLEDGE MAP — knowledge_А_ОтражениеЗПпоКазне

Entry-point для ИИ-сессий и аналитиков. **Прочитать первым.**

> База знаний по документу `Документ.А_ОтражениеЗПпоКазне` (BAS ERP 2.5 INDUSTRIALBUD).
> Документ-агрегатор: тянет данные ЗП из **3-х внешних баз** (BuhKazn + zup_1 + zup_2), наполняет 7 ТЧ и порождает 2 подчинённых документа (`НачислениеЗарплаты` + `ОтражениеЗарплатыВФинансовомУчете`).
>
> ⚠️ **Поправка к PROMPT.md:** реальный код подключается к **`zup_1`** (BAS ЗУП регламент) и **`zup_2`** (BAS ЗУП управленческий), а НЕ к BuhBud (BAS Бухгалтерія). Промт был основан на устаревшем предположении. Connection-строки в §1 — проверены через COM на actual config (2026-05-26).

## TL;DR за 60 секунд

Документ `А_ОтражениеЗПпоКазне` (синоним «Отражение зп по казне») — кастомный документ-агрегатор, который:

1. **Подключается к 3 внешним базам через `V83.COMConnector`:**
   - `BuhKazn` (Казна) — РегНакопл.БДДС + Документ.РаспределениеЗаработнойПлаты + Документ.РаспределениеФ2
   - `zup_1` (BAS ЗУП регламент) — РегНакопл.ВзаиморасчетыПоНДФЛ + РегРасчет.ВзносыВФонды + РегРасчет.УдержанияРаботниковОрганизаций
   - `zup_2` (BAS ЗУП управленческий) — Документ.НачислениеЗарплатыРаботникам.{Начисления,Удержания}

2. **Наполняет 8 табличных частей:** `РаспределениеКазна`, `НалогиБухгалтерия`, `УдержанияБухгалтерия`, `НачисленияУпр`, `УдержанияУпр`, `НачисленнаяЗарплатаИВзносыПоФизлицам`, `НачисленныйНДФЛ`, `НачисленияБух` (🆕 2026-05-31 — gross из zup_1, СчётКт=661).

3. **Использует cross-base UUID 1:1** (через правила обмена `_Rarzrabotki/ConvertERP/`) для поиска ERP-документа `А_РаспределениеЗаработнойПлаты` по UUID регистратора из Казны. Паттерн: `V83.string(...)` lowercase (CLAUDE.md §«Cross-base UUID lookup»).

4. **Создаёт 2 подчинённых документа:**
   - `Документ.НачислениеЗарплаты` (ЗУП-документ начисления — 4 ТЧ: Начисления, Удержания, НДФЛ, ВзносыФОТ)
   - `Документ.ОтражениеЗарплатыВФинансовомУчете` (типовой документ отражения — 5 ТЧ)

5. **Движения регистров (1 шт.):** `РегистрНакопления.А_ДенежныеСредстваФинАгенты`. Документ САМ движений почти не делает — это аггрегатор для последующих документов.

6. **🆕 С 2026-05-27 — кнопка «Создать ведомости в кассу»** в форме документа. По нажатию: группировка ТЧ.РаспределениеКазна по `ДокРаспределениеЗП` → создаёт **N×ВедомостьНаВыплатуЗарплатыВКассу** (по одной на каждую уникальную РаспределениеФ2), каждая проведена, СтатьяДДС берётся из ТЧ.РаспределениеКазна. См. [12_button_iz_otrazheniya.md](12_button_iz_otrazheniya.md). Эталон v1 №000000006: 7 ВКассу, Σ=2 954 127 UAH; эталон v2 №000000001: 4 ВКассу, Σ=3 814 768 UAH.

   **⚠️ 2026-05-28 — рефакторинг (v2):** вся логика создания ВКассу **перенесена целиком в А_ОтражениеЗПпоКазне**. Удалена кнопка из формы РаспределениеФ2, процедура `Документ.РаспределениеФ2.СоздатьВедомостьНаВыплатуВКассуПоРаспределениюФ2` и утилиты `_ВЫК_*` (358 → 20 строк в Ф2.ObjectModule). Причина: РаспределениеФ2 в ERP — пустая оболочка после обмена (UUID 1:1, но без СтатьиДДС, которая живёт только в БДДС Казны). Источник истины теперь однозначно ТЧ.РаспределениеКазна. Подразделение в РК уже исправлено через `А_ПолучитьПодразделениеПоНаправлениюИПодразделениюКазны` при COM-загрузке (см. [02_zagruzka_iz_kazni.md §7](02_zagruzka_iz_kazni.md)). СтатьяДДС читается прямо из СтрРК (без словаря). Подробнее: [12_button_iz_otrazheniya.md](12_button_iz_otrazheniya.md) v2.

   **🛡️ 2026-05-29 — гард `А_Необновлять`:** в Find-or-Create функции `_ОЗП_СоздатьВКассуИзФ2` добавлен ранний-возврат: если найденная ВКассу имеет `А_Необновлять = Истина` (флаг ставится `РасходныйКассовыйОрдер.ПриЗаписи` при проведении РКО из этой ВКассу), процедура её **не модифицирует** — `Сообщить + Возврат "Пропущено"`. Сигнатура сменилась с Процедура → Функция со строковым кодом результата (`"Создано" / "Обновлено" / "Пропущено" / "Ошибка"`). Вызывающая агрегирует в 3 счётчика; итоговая строка дополнена `, пропущено заблокированных (А_Необновлять) N`. Обратимость: распроведение РКО автоматически сбрасывает флаг → следующий прогон обновит ВКассу как раньше. Подробнее: [15_vkassu_skip_neobnovlyat.md](15_vkassu_skip_neobnovlyat.md).

7. **🆕 2026-05-31 — закладка `НачисленияБух` + разделение `ФормаPL` (Форма1/Форма2):** новая ТЧ `НачисленияБух` (gross из zup_1.ОсновныеНачисленияРаботниковОрганизаций, СчётКт=661); весь поток отражения размечается `Перечисление.А_ФормыPL` — **Форма1** (бух/официальная, через `А_РаспределениеЗаработнойПлаты`, банк) / **Форма2** (управ/ЦПХ, через `РаспределениеФ2`, касса). Перенос `А_ПередачаНачислений` двигает **только Форма1**. ⚠️ Базис Форма1 = **GROSS** (колонка `НачисленнаяЗарплата.Сумма` — это gross; движение `А_ВзСС` САМ вычитает НДФЛ → take-home). ⚠️ COM-пересоздание ОЗФУ подвоит ТЧ — проверять по saved parent. Эталон Постернак дек.2025: Ф1=36 251,34 (gross), А_ВзСС «Оплата труда»=27 913,53. Подробнее: [17_formapl_split.md](17_formapl_split.md).

8. **🆕 2026-06-01 — фикс −0.01 в `А_ВзаиморасчетыССотрудниками` (Ф1 Приход = перенос до копейки):** официальный Ф1-НДФЛ разбивался по подразделениям дважды по разным ключам (gross-up «Удержание» равномерно vs `НачисленныйНДФЛ` налог-за-налогом) → копеечный разрыв с переносом `А_ПередачаНачислений`. Новая `_ОтрЗП_ВыровнятьУдержаниеСНДФЛ` выравнивает «Удержание» Ф1 под `НачисленныйНДФЛ` per (ФЛ,Подр), Σ per ФЛ сохраняется → `Начислено−НДФЛ`=«Зарплата управл». Копеечных нарушений глобально = 0. ⚠️ Разрыв «начислено↔выплачено» (110/128) — **норма** (timing), не сводить к нулю. 🟡 196 GROSS-style ФЛ — отложено. Подробнее: [18_vzss_uderzhanie_ndfl_align.md](18_vzss_uderzhanie_ndfl_align.md).

**Период документа = весь месяц** (`НачалоМесяца(Дата)..КонецМесяца(Дата)`). По дате документа определяется месяц, за который собирается ЗП из всех 3-х баз.
