## 1. Что сделано

Воспроизведены в ЕРП движения денег по выплате ЗП (которые в Казне идут через `РегНакопл.БДДС`) — через новый `РегистрНакопления.А_ДвиженияДенегДоходыРасходы` («Движения Денежные средства - Доходы/Расходы по Казне»). Регистр = **зеркало БДДС Казны** (cash-flow), Подразделение — исходное.

Источник данных — ТЧ `А_ОтражениеЗПпоКазне.РаспределениеКазна` (там СтатьяДДС из БДДС Казны + исправленное Подразделение). Регистраторы регистра — два документа-распределения: `А_РаспределениеЗаработнойПлаты` (Ф1/безнал) и `РаспределениеФ2` (Ф2/нал).

| # | Объект | Изменение |
|---|--------|-----------|
| 1 | `Documents/А_ОтражениеЗПпоКазне/Ext/ObjectModule.bsl` | **+`#Область ЕРП_СоздатьДвиженияДДС`** — `Процедура СоздатьДвиженияДДСПоОтражениюЗП() Экспорт` (Часть A) |
| 2 | `Documents/А_РаспределениеЗаработнойПлаты/Ext/ObjectModule.bsl` | пустой `ОбработкаПроведения` → запись движений (Часть B, ТипДС=Безналичные) |

## 2. Архитектура (две части)

### Часть A — `СоздатьДвиженияДДСПоОтражениюЗП()` (заполнение + проведение)
Группирует `РаспределениеКазна` по `(ДокРаспределениеЗП, Подразделение, СтатьяДвиженияДенежныхСредств, Сотрудник)` → заливает агрегаты в ТЧ `А_ДвижениеДДС` целевого документа-распределения → перепроводит документ. **Идемпотентно** (на входе чистит `А_ДвижениеДДС`, повторный прогон даёт Δ=0).

Гард на пустой `ДокРаспределениеЗП`; на каждый документ — `ОтменаПроведения` (если проведён) → `Очистить()` ТЧ → заполнение → `Записать(Проведение)`; защитная проверка `ДокОбъект.Проведен` после записи (ловит «тихое понижение» проведения до записи, см. §3 ниже).

### Часть B — `ОбработкаПроведения` каждого документа-распределения
Пишет движения `А_ДвиженияДенегДоходыРасходы` из своей ТЧ `А_ДвижениеДДС`. Выводит измерения из типа документа и реквизитов:

| Измерение | Ф1 (`А_РаспределениеЗаработнойПлаты`) | Ф2 (`РаспределениеФ2`) |
|-----------|---------------------------------------|------------------------|
| `ТипДенежныхСредств` | **Безналичные** | **Наличные** |
| `БанковскийСчетКасса` | **пусто** (см. решение #2) | `А_ВедомостьВКассу.Касса` |
| `Организация` | управ.орг `А_Привилегированный.А_ПолучитьОрганизациюУпр()` (ІНДАСТРІАЛБУД) | то же |
| `А_ОрганизацияБухгалтерия` | `Организация` документа (реальное юр.лицо) | то же |
| `Подразделение` | `Стр.Подразделение` (исходное) | то же |
| `СтатьяДвиженияДенежныхСредств` | `Стр.СтатьяДвиженияДенежныхСредств` | то же |
| `Сумма` | `Стр.Сумма` (положительная) | то же |

> **⚠️ `Сотрудник` (добавлено 2026-06-03):** ТЧ `А_ДвижениеДДС` обоих документов получила колонку `Сотрудник` (`Справочник.Сотрудники`); Часть A группирует по нему и заполняет (`НоваяСтрока.Сотрудник = СтрД.Сотрудник`) — детализация по сотрудникам в закладке «ЕРП» документа.
> **НО в регистре `А_ДвиженияДенегДоходыРасходы` измерения `Сотрудник` НЕТ, и Часть B (`ОбработкаПроведения`) его НЕ пишет** — в движениях регистра сотрудник схлопывается, детализация остаётся только в табличной части документа.
> `Сумма` движений при этом не меняется (доп. поле группировки лишь дробит строки ТЧ на под-строки по сотрудникам — Σ та же, строк больше; цифры счётчиков строк в §4 — ДО добавления `Сотрудник`).
> Чтобы `Сотрудник` попал и в регистр: (1) добавить измерение `Сотрудник` (`Справочник.Сотрудники`) в `РегистрНакопления.А_ДвиженияДенегДоходыРасходы`, (2) дописать `Запись.Сотрудник = Стр.Сотрудник` в обе `ОбработкаПроведения` (Ф1 и Ф2).

## 3. Решения (вбиты в код 2026-06-03 по discovery на эталоне №000000005)

1. **Подразделение = исходное** (`Стр.Подразделение`, зеркало Казны; НЕ корень).
2. **Ф1 `БанковскийСчетКасса` = пусто.** Детерминированного «основного» счёта юр.лица в конфигурации НЕТ: у управ.орг ІНДАСТРІАЛБУД — 85 активных счетов, у двух др. юр.лиц эталона — 0 счетов, флага/реестра «основной счёт» нет, поля `Код` у `БанковскиеСчетаОрганизаций` нет. Поле — вторичное измерение (в инвариантах приёмки его нет). Ф2 получает реальную `Касса` из ведомости.
3. **Организация = управ.орг; А_ОрганизацияБухгалтерия = `Ссылка.Организация`** (реальное юр.лицо документа).
4. **Сумма положительная** (расход Казны как есть).
5. **Перепроводятся ВСЕ Ф2, включая заблокированные** (`А_Необновлять = Истина`, по ним проведён РКО) → **полное зеркало**. В эталоне №5 таких 9 из 11 (Σ 2 973 920 из 3 378 530) — без этого зеркало потеряло бы ~88% наличной выплаты. Перепроведение безопасно: `РаспределениеФ2.ПриЗаписи` — no-op (создание ВКассу убрано 2026-05-28), флаг `А_Необновлять` ставит только `РасходныйКассовыйОрдер.ПриЗаписи` (от перезаписи Ф2 не меняется), ни Ф2, ни Ф1 не обрабатываются подписками `А_СобытияОбъектов`. **Флаг защиты обмена НЕ нужен.** Контраст с [15_vkassu_skip_neobnovlyat.md](15_vkassu_skip_neobnovlyat.md) (там гард `А_Необновлять` нужен, т.к. модифицируется чужой документ ВКассу; здесь — собственное проведение Ф2).
6. **Пустую `СтатьюДДС` НЕ пропускаем.** Часть строк `РаспределениеКазна` приходит без статьи ДДС (в эталоне №5 — 11 строк Ф2, Σ 76 300). Для полного зеркала они тоже дают движения (с пустым измерением `СтатьяДвиженияДенежныхСредств`). Пропускается только `Сумма = 0`.

## 5. Грабли (см. также LESSONS §18)

- **`ЗначениеЗаполнено(...)` НЕ работает в языке запросов** (только в BSL). В запросе пустую ссылку проверять через `= ЗНАЧЕНИЕ(Справочник.X.ПустаяСсылка)`; составное измерение `БанковскийСчетКасса` — через двойное `<> ЗНАЧЕНИЕ(Кассы.ПустаяСсылка) И <> ЗНАЧЕНИЕ(БанковскиеСчетаОрганизаций.ПустаяСсылка)`.
- **Тихое понижение проведения.** `А_СобытияОбъектов.А_ПроверкаНаРазрешенияПроведенияВУчете` (вызывается из подписки ПередЗаписью для всех документов) при `НЕ Организация.А_ВБалансе` или `Дата < Организация.А_ДатаНачалоВеденияУчета` молча меняет `РежимЗаписи` Проведение→Запись (документ остаётся НЕ проведённым, без исключения). Для эталонных орг (все `А_ВБалансе`, ранняя дата начала) не срабатывает; защитная проверка `ДокОбъект.Проведен` после `Записать(Проведение)` ловит этот случай.
- **Несоответствие гарда и инварианта (баг плана).** План пропускал пустую СтатьюДДС, но целевая Σ включала эти строки → smoke не сходился на 76 300. Исправлено снятием гарда (решение #6).
