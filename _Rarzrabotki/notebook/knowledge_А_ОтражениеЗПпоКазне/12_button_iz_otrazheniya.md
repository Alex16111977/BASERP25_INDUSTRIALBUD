## 1. ⚠️ Почему понадобился рефакторинг (v1 → v2)

В **v1** процедура создания ВКассу жила в `Документ.РаспределениеФ2`, а А_ОтражениеЗПпоКазне через кнопку лишь группировал строки и вызывал Ф2-процедуру с двумя параметрами (СтатьиДДСПоКлючу + ссылка на родителя). Параметры передавали недостающие данные, потому что **РаспределениеФ2 в ERP — пустая оболочка после обмена с Казной**: UUID 1:1, но богатая аналитика отсутствует.

Проблемы v1:
1. **СтатьяДДС жила в БДДС Казны**, а не в РаспределениеФ2. Чтобы её донести до создания ВКассу, строился словарь `(Сотр_UID|ПодрОрг_UID → СтатьяДДС)` в А_ОтражениеЗПпоКазне и передавался параметром в Ф2-процедуру. Ключи строились по ПодрОрг, и хрупко зависели от того что обе стороны используют одинаковый алгоритм конвертации.
2. **Подразделение в РаспределениеФ2.Распределение** содержит **сырые данные Казны** (СтрПредпр="Главный офис" для центрального офиса), потому что правила обмена ConvertERP не применяют `А_Привилегированный.А_ПолучитьПодразделениеПоНаправлениюИПодразделениюКазны`. Это видно в Ведомостях.А_Расшифровке: Пономаренко Світлана Юріївна попадала как "Главный офис" вместо реального "Производство".
3. **Кнопка в Ф2 + триггер ПриЗаписи Ф2** создавали впечатление будто Ф2 — самостоятельный источник, что **архитектурно неверно**.

Решение в v2: **полностью отказаться от Ф2 как источника**. Источник истины — ТЧ `А_ОтражениеЗПпоКазне.РаспределениеКазна` (COM-загружается из БДДС Казны и содержит **ВСЁ** необходимое: Сотрудник, исправленное Подразделение, НаправленияДеятельности, СтатьяДвиженияДенежныхСредств, Сумма, ДокРаспределениеЗП).

## 2. v2-архитектура (2026-05-28)

```
[Пользователь] открывает А_ОтражениеЗПпоКазне №000000001
                ↓
   Нажимает «Создать ведомости в кассу»
                ↓
   Documents/А_ОтражениеЗПпоКазне/Ext/ObjectModule.bsl:
   СоздатьВедомостиВКассуПоОтражениюЗП()  ← переписано
     ├─ 1. Guard: Проведён
     ├─ 2. Группировка ТЧ.РаспределениеКазна по ДокРаспределениеЗП
     │     (фильтр: тип = Документ.РаспределениеФ2; А_РаспределениеЗП пропускаем).
     │     ГруппыПоФ2[Ф2.Ссылка] = Массив строк ТЧ.
     │
     ├─ 3. Для каждой Ф2.Ссылка → вызов _ОЗП_СоздатьВКассуИзФ2(Ф2Ссылка, СтрокиРК):
     │     ├─ Find-or-Create ВКассу по А_РаспределениеФ2 = Ф2.Ссылка
     │     ├─ Cleanup: Распровести + Очистить (Зарплата, А_Расшифровка, Состав)
     │     ├─ Шапка: Организация=Касса.Владелец, Касса (Орг.А_ОсновнаяКасса),
     │     │         СпособВыплаты=ПредопредЗарплата, ПроцентВыплаты=100,
     │     │         А_РаспределениеФ2 + А_ОтражениеЗПпоКазне=Ссылка
     │     ├─ КешФЛ = Сотрудник → ФизЛицо (один запрос на массив)
     │     ├─ КешПодрОрг = СтрПредпр → ПодрОрг через
     │     │              А_Привилегированный.ОбеспечитьПодразделенияОрганизацийПоПодразделению
     │     ├─ ТЧ Состав СНАЧАЛА → карта ФЛ→UID для ИдентификаторСтроки
     │     ├─ ТЧ Зарплата + ТЧ А_Расшифровка (зеркало по ИдентификаторСтроки):
     │     │     Подразделение = ПодрОрг (СтрРК.Подразделение УЖЕ исправлено
     │     │                              при COM-загрузке БДДС)
     │     │     НаправлениеДеятельности = СтрРК.НаправленияДеятельности
     │     │     СтатьяДвиженияДенежныхСредств = СтрРК.СтатьяДвиженияДенежныхСредств
     │     │                                     (прямо из строки РК, никаких словарей)
     │     ├─ СуммаПоДокументу = Σ ТЧ.Зарплата
     │     ├─ Записать(Проведение)
     │     └─ Обратная ссылка Ф2.А_ВедомостьВКассу (через ОбменДанными.Загрузка)
     │
     └─ 4. Сообщить("Создано N, ошибок K, пропущено M")
                ↓
   N×ВКассу созданы и проведены.
```

**Никаких вызовов в Ф2-процедуры. Никаких параметров со словарями. Никаких реверс-инженерных хаков.**

## 4. Уроки

### Урок №1 (v2): источник истины должен быть один

**v1** имел два потенциальных источника (Ф2 со словарём + А_ОтражениеЗПпоКазне) и склеивал их через параметры. Это создавало впечатление будто Ф2 умеет создавать ВКассу самостоятельно — но без словаря у Ф2 не хватало СтатьиДДС. Любой разработчик, увидев процедуру `Ф2.СоздатьВедомость...` и кнопку в форме Ф2, делал бы неправильные выводы об архитектуре.

**v2**: единственная точка создания — А_ОтражениеЗПпоКазне. Ф2 — пустой типовой документ для маршрутизации денег по направлениям. Это естественно отражает реальность: данные приходят из обмена с Казной (БДДС), и владельцем этих данных в ERP является А_ОтражениеЗПпоКазне.

### Урок №2 (v2): Подразделение исправляется ОДИН РАЗ при COM-загрузке

В `ЗагрузитьРаспределениеКазна_ОтражениеЗП` (см. [`02_zagruzka_iz_kazni.md` §7](02_zagruzka_iz_kazni.md)) при заполнении ТЧ.РаспределениеКазна применяется функция:

```bsl
Подразделение = А_Привилегированный.А_ПолучитьПодразделениеПоНаправлениюИПодразделениюКазны(
    НаправлениеДеятельности, ПодразделениеКазны);
```

То есть `СтрРК.Подразделение` в ТЧ.РаспределениеКазна **гарантированно содержит реальное подразделение** (не "Главный офис" 00-000043 — оно подменяется на СтрПредпр-направление). Все downstream-потребители (включая v2-кнопку) могут просто читать это поле без повторного вызова функции.

### Урок №3 (v2): СтатьяДДС — атрибут строки, не атрибут пары (Сотр, Подр)

В v1 СтатьяДДС агрегировалась в словарь по ключу `(Сотр_UID|ПодрОрг_UID)`. Это **некорректно** в случае, когда один сотрудник в одном подразделении получает оплату по разным статьям ДДС в разных строках БДДС (например, Пономаренко: Зарплата производственного персонала + Зарплата ИТР + Зарплата управленческого персонала). v1-словарь схлопывал бы такие случаи в один ключ → последняя статья перетёрла бы все предыдущие.

**v2**: СтатьяДДС читается **прямо из СтрРК** — каждая строка ТЧ имеет свою статью. В А_Расшифровке Ведомости каждая строка получает свою СтатьюДДС, идентичную исходной строке РК.

### Урок №4: алиас `КАК В` зарезервирован (наследовано от v1)

В Python COM тесте `КАК В` падает с «Ожидается имя» — буква `В` оператор `В ИЕРАРХИИ` / `В` (in-list). Использовать `КАК Вед` / `КАК Док`.

### Урок №5: COM-объекты с кириллическими атрибутами

`row.ПодрОрг` через `__getattr__` для COM-объекта Python работает, но если атрибут начинается с кириллицы в нестандартном месте (например, после dot-access у row), pywin32 иногда выдаёт `AttributeError`. Безопаснее: использовать ASCII-имена в `КАК` (например, `КАК НомерВед` или `КАК Подр`) или просто выводить нужные поля напрямую.
