# 17 — Закладка `НачисленияБух` + разделение зарплаты по `ФормаPL` (Форма1/Форма2)

> **🟢 РЕАЛИЗОВАНО 2026-05-31.** Новая ТЧ `НачисленияБух` (gross из zup_1) + разметка всего потока
> отражения ЗП реквизитом `ФормаPL` (`Перечисление.А_ФормыPL`: Форма1=бухгалтерская/официальная,
> Форма2=управленческая/ЦПХ). Цель — разделить зарплату на официальную (банк) и управленческую (касса),
> чтобы дальше разносить затраты по Ф1/Ф2 в PL и переносить между подразделениями только официальную часть.
>
> Промты: [PROMPT_НачисленияБух.md](PROMPT_НачисленияБух.md), [PROMPT_ФормаPL_split.md](PROMPT_ФормаPL_split.md).

## 1. Бизнес-смысл (роль бухгалтера/финансиста)

Полная зарплата сотрудника делится на **две составляющие** по способу выплаты:

| `ФормаPL` | Смысл | Источник | Канал | Документ Казны |
|---|---|---|---|---|
| **Форма1** | бухгалтерская / **официальная** | `НачисленияБух − НалогиБух − УдержанияБух` (zup_1) | банк | `А_РаспределениеЗаработнойПлаты` |
| **Форма2** | управленческая / **ЦПХ** | через `РаспределениеФ2` (Казна) | касса | `РаспределениеФ2` |

Для строительной «ІНДАСТРІАЛБУД» официальная часть мала, а основная выплата идёт «управленчески» через
кассу (ЦПХ). `ФормаPL` помечает каждую строку, чтобы:
- перенос обязательств (`А_ПередачаНачисленийМеждуПодразделениями`) двигал **только Форма1**;
- (следующая задача) разносить затраты `РегистрНакопления.ПрочиеРасходы` по измерению `ФормаPL`.

`Перечисление.А_ФормыPL` = {`Форма1`, `Форма2`}.

## 2. Закладка `НачисленияБух` — gross из zup_1

ТЧ `НачисленияБух` (10 полей): `Организация`, `ФизЛицо`, `Сумма`, `ФИО`, `ВидРасчета`, `КодВидРасчета`,
`СчетКт` (Хозрасчетный), `СубконтоКт1..3` (ВидыСубконтоХозрасчетные).

**Заполнение** — расширена `ЗагрузитьНалогиИУдержанияИзЗарплатыБух()` (Блок 2): добавлен 3-й запрос к
`zup_1.РегистрРасчета.ОсновныеНачисленияРаботниковОрганизаций` (та же COM-сессия) + новая `ЗаписатьНачисленияБух_Бух`.

| Компонент | Значение |
|---|---|
| Деталь | строка на (Сотрудник × ВидРасчёта), реальные `ВидРасчета.Наименование`/`Код` |
| Фильтр | `ВидРасчета.Код <> "00021"`, `Результат <> 0`, орг. по `А_ВБалансе`/ЕДРПОУ |
| Матчинг | `ФизЛицо` по `КодПоДРФО` (кеш), `Организация` по `КодПоЕДРПОУ` |
| **Бух-константы ERP** | `СчетКт = ПланыСчетов.Хозрасчетный.НайтиПоКоду("661")`, `СубконтоКт1 = ФизЛицо`, Субконто2/3 пусто |

⚠️ **Счёт 661** «Розрахунки за договорами ЦПХ» — это РЕАЛЬНЫЙ счёт ЗП на BaseERP (33 М Кт, 2908 движ.),
имя обманчиво. Субконто Кт = `Справочник.ФизическиеЛица` (тип «Работники организаций»). Счета `66`/`662`/`663` пусты.

Серия: `НачисленияБух` — это **gross официального начисления** (для Постернака дек.2025: Оклад 31 956,52 +
Премія 2 000 + Відпустка 2 294,82 = **36 251,34**). Используется как **базис Форма1** (см. §4).

## 3. Где живёт `ФормаPL` (метаданные — поля УЖЕ заведены)

| Документ | ТЧ с полем `ФормаPL` (EnumRef.А_ФормыPL) |
|---|---|
| `А_ОтражениеЗПпоКазне` | `РаспределениеКазна`, `НачисленнаяЗарплатаИВзносыПоФизлицам`, `НачисленныйНДФЛ` |
| `ОтражениеЗарплатыВФинансовомУчете` (типовой ОЗФУ) | `НачисленнаяЗарплатаИВзносы`, `НачисленнаяЗарплатаИВзносыПоФизлицам`, `НачисленныйНДФЛ`, `УдержаннаяЗарплата` |
| `РегистрНакопления.А_ВзаиморасчетыССотрудниками` | измерение `ФормаPL` (заполняется при проведении ОЗФУ из ТЧ) |

`НачисленияБух`/`НалогиБухгалтерия`/`УдержанияБухгалтерия` в родителе `ФормаPL` НЕ имеют — это zup_1-входы (по
определению Ф1, источник базиса).

## 4. Цепочка разметки `ФормаPL` (4 этапа)

### Этап 1 — `ЗагрузитьРаспределениеКазна_ОтражениеЗП` (Блок 1)
- `РаспределениеКазна.ФормаPL` = `Форма1` если `ВидДокумента = "А_РаспределениеЗаработнойПлаты"`, иначе `Форма2`
  (тип уже вычисляется CASE в запросе к БДДС Казны).
- **Для Форма2:** `Организация = А_Привилегированный.А_ПолучитьОрганизациюУпр()` (= ТОВ ІНДАСТРІАЛБУД,
  ЕДРПОУ 40645273). Эффект: у управленческой орг `А_ПодразделениеЗарплатаБух` пусто → Ф2-строки «без целевого»
  → перенос их не двигает.

### Этап 2 — `_ОтрЗП_РазметитьФормаPL()` (родитель)
Пост-обработка после `ЗаполнитьДляОтражения_...`: размечает `НачисленнаяЗарплатаИВзносыПоФизлицам` +
`НачисленныйНДФЛ`. **Общая сумма НЕ меняется** — каждый NET-рядок делится на Ф1+Ф2 по коэффициенту доли ФЛ.

| Компонент | Форма1 | Форма2 |
|---|---|---|
| Налоги: `ВзносыВсего` (ЕСВ) + весь `НачисленныйНДФЛ` | **всё Ф1** (официальные налоги) | 0 |
| NET `Сумма` (per ФЛ) | `gross × (gross_ФЛ/total_ФЛ)` | остаток `total − Ф1` |

> **⚠️ КРИТИЧНО (см. §5): базис Ф1 = GROSS (`Σ НачисленияБух`), а НЕ NET.** `gross_ФЛ = Σ НачисленияБух`;
> `total_ФЛ = Σ НачисленнаяЗарплата.Сумма` (поточне відображення); `коеф = min(1, gross/total)`.

### Этап 3 — `СоздатьДокументОтражениеЗарплатыВФинансовомУчете` (протащить в 4 ТЧ ОЗФУ)
- `НачисленнаяЗарплатаИВзносыПоФизлицам.ФормаPL` + `НачисленныйНДФЛ.ФормаPL` — автоматически через
  `ЗаполнитьЗначенияСвойств` (поля совпадают).
- `НачисленнаяЗарплатаИВзносы` (свёртка) — `ФормаPL` добавлен в ключ свёртки.
- `УдержаннаяЗарплата.ФормаPL = Форма1` — явно (источник `УдержанияБухгалтерия` без маркера; удержания официальные).

### Этап 4 — перенос `_ПНМП_*` (только Форма1)
- `_ПНМП_ПостроитьВеса` + `_ПНМП_ЗаполнитьНалоги` + `_ПНМП_ЗаполнитьУдержания`: фильтр `ФормаPL = Форма1`.
- `_ПНМП_ЗаполнитьНачисления`: NET = `НачисленнаяЗарплата(Ф1) − НачисленныйНДФЛ(Ф1) − УдержаннаяЗарплата(Ф1)`
  (Ф1 = GROSS, поэтому вычитание НДФЛ/удержаний даёт take-home). Форма2 в перенос НЕ попадает.

> **🆕 Уточнение 2026-06-01 → [18_vzss_uderzhanie_ndfl_align.md](18_vzss_uderzhanie_ndfl_align.md):** для NET-ФЛ (`НачисленияУпр≠0`) «Зарплата управл» Ф1 — это уже take-home NET (строки создаёт `_ОтрЗП_СоздатьСтрокиNETФЛ_Новый`), и `_ПНМП_ЗаполнитьНачисления` берёт её **напрямую** (`Стр.Сумма`). Чтобы регистр Приход (`Начислено − НачисленныйНДФЛ`) совпал с переносом **до копейки**, добавлен пост-проход `_ОтрЗП_ВыровнятьУдержаниеСНДФЛ` — выравнивает gross-up «Удержание» Ф1 под `НачисленныйНДФЛ` per (ФЛ,Подр). Иначе ±0.01 на подразделение.

## 5. ⚠️ КРИТИЧЕСКИЙ УРОК: `НачисленнаяЗарплата.Сумма` — это GROSS, не NET

**Баг (Постернак, дек.2025):** ОЗФУ Форма1 «Оплата труда» = **19 575,72**, а должно **27 913,53**
(= `РаспределениеКазна` «Зарплата» = перенос). Разница = **8 337,81 = НДФЛ**.

**Причина:** колонка `НачисленнаяЗарплата.Сумма` семантически **GROSS** (начисление). При проведении ОЗФУ
движение `А_ВзСС` («Оплата труда») **САМ вычитает НДФЛ/удержания** → take-home. Первая версия разметки клала в
Ф1 **bukh = NET** (`НачисленияБух − НДФЛ − удерж` = 27 913,53), поэтому НДФЛ вычитался **ВТОРОЙ раз**:
27 913,53 − 8 337,81 = 19 575,72.

**Фикс:** базис Ф1 = **GROSS** (`Σ НачисленияБух` = 36 251,34). Тогда:
`А_ВзСС(Ф1) = GROSS − НДФЛ = 36 251,34 − 8 337,81 = 27 913,53` ✓ = `РаспределениеКазна.Зарплата` = перенос.

**Проверка (эталон Постернак дек.2025, saved parent):** Ф1 (GROSS) = 36 251,34; А_ВзСС Ф1 = 27 913,53;
total НачисленнаяЗарплата = 108 337,81 (неизменно); grand total = 6 922 741,41 (Ф1+Ф2=total).

**How to apply:** маркер делит GROSS-колонку — клади **gross**, а не net. Take-home получает движение
`А_ВзСС`/`ПАП` вычитанием НДФЛ. Не вычитай НДФЛ в разметке (иначе двойное вычитание).

## 6. ⚠️ COM-ловушка: пере-создание ОЗФУ через COM ПОДВОИТ ТЧ

При пере-создании `ОтражениеЗарплатыВФинансовомУчете` через `V83.COMConnector` (СоздатьДокумент → Записать)
ТЧ `НачисленнаяЗарплатаИВзносыПоФизлицам` **удваивается** (декабрь: 13,9 М вместо 6,9 М). Через **UI-кнопку**
«Создать отражение» — одинарно (вероятно подписка `А_СобытияОбъектов` в режиме ExternalConnection дозаполняет).

**How to apply:**
- НЕ перепроводить ОЗФУ через COM — только через UI-кнопки формы.
- Проверку алгоритма Ф1/Ф2 делать по **saved parent** (`А_ОтражениеЗПпоКазне.НачисленнаяЗарплата`) + in-memory,
  а НЕ по COM-пересозданному ОЗФУ.
- Если понадобится надёжный COM — выставлять флаг `А_Обработан = Истина` на ОЗФУ в СоздатьДокумент
  (CLAUDE.md Rule #5) и проверить, что подписка `А_СобытияОбъектов` его уважает.
