# 16 — Документ.А_ПередачаНачисленийМеждуПодразделениями

> **🟢 РЕАЛИЗОВАНО 2026-05-29/30.** Перенос обязательств ЗП (начисления NET + налоги + удержания)
> с реального подразделения работы сотрудника на целевое подразделение юр.лица-плательщика,
> в регистрах `ПрочиеАктивыПассивы` (ПАП) + `А_ВзаиморасчетыССотрудниками` (А_ВзСС). Net-zero по
> организации. Кнопка в форме `А_ОтражениеЗПпоКазне`. Spec/plan: `docs/superpowers/{specs,plans}/2026-05-29-peredacha-nachisleniy-mezhdu-podrazdeleniyami-*.md`.

## TL;DR

- **Зачем:** начисления ЗП/налогов висят на реальных подр. (Глобино-2, ЦО, Автокран…), а выплата идёт
  через кассы целевых юр.лиц (ІНДЕПТ СТІЛ→`Производство`, ІНДАСТРІАЛБУД/ДЖИ ТРИ→`Строительство`). →
  дисбаланс баланса по подразделениям. Документ переносит **обязательства** (не затраты) на целевые.
- **Модель «3 ТЧ ↔ 3 статьи ПАП»:** `Начисления`(NET)→«Оплата труда»(+А_ВзСС per ФЛ),
  `Налоги`(per ТипНалога)→«Налоги»(Аналитика=ТипНалога), `Удержания`→«Прочие пассивы».
- **Движения:** на ИсходномПодразделении — РЕВЕРС начисления (для пассивной статьи = Приход),
  на ЦелевомПодразделении — КОПИЯ (Расход). А_ВзСС — инверсно (исходное Расход / целевое Приход).
  Каждая строка net-zero → Σ КО по организации не меняется, баланс сдвигается между подр.
- **Кнопка** «Создать передачу начислений» в форме А_ОтражениеЗПпоКазне; Find-Or-Create по
  `А_ДокументОснование`; идемпотентно.

## Структура документа

**Шапка:** `Организация`(=ТОВ ІНДАСТРІАЛБУД, управ.орг = ПАП.Организация), `А_ДокументОснование`
(составной: `ОтражениеЗарплатыВФинансовомУчете` + `А_ОтражениеЗПпоКазне` — ключ Find-Or-Create),
`Комментарий`, `Ответственный`.

**3 ТЧ** (поля строки: ФизическоеЛицо, Сотрудник, ОрганизацияБухгалтерия, `ИсходноеПодразделение`
и `ЦелевоеПодразделение` — **оба `Справочник.СтруктураПредприятия`**, Сумма, ПериодВзаиморасчетов,
ДокОснованиеСтроки (составной), ИдентификаторСтроки(Строка36)):
- **Начисления** — NET per (ФЛ × ИсхПодр × ЦелПодр). → ПАП «Оплата труда» + А_ВзСС.
- **Налоги** — + ТипНалога / Налог / КодДохода. → ПАП «Налоги» (Аналитика=ТипНалога).
- **Удержания** — + Получатель (аудит). → ПАП «Прочие пассивы».

Движения: `ПрочиеАктивыПассивы` + `А_ВзаиморасчетыССотрудниками` (объявлены в RegisterRecords
документа — правится метаданное только нового кастомного документа, структуру ПАП не трогаем).

## Заполнение (кнопка → `А_ОтражениеЗПпоКазне.СоздатьПередачуНачисленийМеждуПодразделениями`)

1. **Источник СУММ — дочерний ОЗФУ** (`ОтражениеЗарплатыВФинансовомУчете` где
   `А_ДокОтражениеЗПпоКазне = родитель И Проведен`). Именно он постит ПАП → Σ ТЧ = ПАП по построению.
   - `Начисления` NET = начисления(Налог=Пустая, −4 ВидОперации) − НачисленныйНДФЛ − УдержаннаяЗарплата
     (логика `А_ВзСС.ManagerModule.ЗаполнитьИзОтраженияЗП`), per (ФЛ, ИсхПодр).
   - `Налоги` = НачисленныйНДФЛ (НДФЛ/ВС) + НачисленнаяЗП.ВзносыВсего (ЕСВ, где Налог ПОДОБНО "ЕСВ%").
   - `Удержания` = УдержаннаяЗарплата per (ФЛ, ИсхПодр).
2. **ЦелевоеПодразделение — ПРОПОРЦИОНАЛЬНОЕ дробление** (связь сотрудник↔юр.лицо many-to-many:
   75/178 ФЛ оплачены из >1 юр.лица). Веса per **Сотрудник** из `ТЧ.РаспределениеКазна`
   (Σ Сумма по юр.лицу); целевое = `Организация.А_ПодразделениеЗарплатаБух`. NET каждого (ФЛ, ИсхПодр)
   дробится: `доля = Сумма × вес[Сотрудник] / Σ_всех_весов[ФЛ]`.
3. **Доля юр.лиц без целевого («Управленческая организация») НЕ переносится** — остаётся на исходном
   (управленческий учёт, идёт через кассу наличными — отдельный механизм). На эталоне:
   ВесСЦелью/ВсегоВес = 4 811 341,76 / 7 530 371,76 ≈ 64% → переносится ~62–76%, остальное на исходном.

## Грабли (уроки реализации)

1. **NET ≠ начисления.** ПАП «Оплата труда» = начисления − НДФЛ − ВС − удержания (NET к выплате),
   НЕ сырое `НачисленнаяЗарплата.Сумма` (gross). ТЧ Начисления хранит именно NET (поле ВидОперации
   при netting сворачивается — убрано из ТЧ).
2. **ИсходноеПодразделение = `Справочник.СтруктураПредприятия`** (а НЕ ПодразделенияОрганизаций —
   так предполагал исходный промт). `НачисленнаяЗарплата.ПодразделениеПредприятия` уже СтрПредпр →
   **конвертация `А_Подразделение` НЕ нужна** (она для РКО, knowledge 14, где источник — Ведомость).
3. **Писать ОБА регистра согласованно.** Свод_ОплатаТруда (`А_ФинРез_Баланс`) держит инвариант
   `Σ А_ВзСС per (Орг,Подр,ФЛ) = −ПАП(ОТ) per (Орг,Подр)`. Документ пишет ПАП(ОТ) (per подр) И А_ВзСС
   (per ФЛ) с инверсными знаками → 0 новых плугов. Если писать только один — баланс по подр сломается.
4. **Связь сотрудник↔юр.лицо many-to-many** → одно целевое на ФЛ присвоить нельзя; дробим
   пропорционально весам `РаспределениеКазна` (решение пользователя 2026-05-29). `РаспределениеКазна.Сумма`
   (7 530 371,76) ≠ ПАП — это казначейские суммы, годятся ТОЛЬКО как ВЕСА, не как суммы переноса.
5. **66 пред-существующих плугов ОТ** в апрельском Свод_ОплатаТруда — разрыв покрытия А_ВзСС (не все
   регистраторы ОТ заполняют А_ВзСС: НачислениеЗарплаты, сторно и т.п.). НЕ от этого документа
   (он добавляет 0 — доказано Часть 1 теста). Вне scope.
6. **form-edit пул id** считает по корню формы и не видит id в Popup командной панели → выдал занятые
   578/579. Проверять уникальность id вручную (`grep -oE 'id="[0-9]+"' | sort | uniq -d`), исправлять
   подстрочной заменой (не зависит от отступов XML). Кнопка легла в тело формы (form-edit не вставляет
   в командную-панель Popup через `into`).

### 🐛 Удержания (Ф1) не переносились — Fix 2 (2026-06-02)

**Симптом:** «Удержания 0 строк» в передаче, хотя в источнике есть (алименты/исполнительные, 6853 «Прочие пассивы»).
**Корень:** `УдержанияБухгалтерия` (вход zup_1, `ЗаписатьУдержанияВТЧ_Бух`) **никогда не заполняет `ПодразделениеПредприятия`** → `_ПНМП_ДобавитьСтроку` гард `НЕ ЗначениеЗаполнено(ИсхПодр) → Возврат` отсекает ВСЕ строки. (ОргБух/целевое в порядке — блокер только пустое исходное подразделение.)
**Фикс (как уже делает ОЗФУ через `МапПодразПоФЛ`):** новый `_ПНМП_ПостроитьПодрУдержанийПоФЛ()` берёт ИсхПодр из **дочернего ПРОВЕДЁННОГО ОЗФУ** `УдержаннаяЗарплата` (ФЛ→подразделение по max-Σ) — то же подразделение, где ОЗФУ запостил ПАП «Прочие пассивы» → net-zero. `_ПНМП_ЗаполнитьУдержания` получил параметр `ПодрУдержПоФЛ` + fallback `ИсхПодр = ?(заполнено Стр.ПодразделениеПредприятия, …, ПодрУдержПоФЛ[ФЛ])`.
**Эталон №000000001 (дек):** 4 строки Σ 12 512,50 (Дубінько/Старіков, Глобино-2→целевое); ПАП «Прочие пассивы» net=0, оборот 25 025,00; идемпотентно. Тесты `diag_uderzhaniya_peredacha.py`, `diag_uderzhaniya_fix2.py`, `smoke_uderzhaniya_fix2.py`.

### 🐛 Начисления Ф1 расходились с ОЗФУ (НДФЛ/удержания/ОргБух) — Fix B зеркало ОЗФУ (2026-06-03)

**Симптом:** в отчёте «Взаиморасчёты с сотрудниками» Форма1 у Дубінько Глобино-2 конечный остаток −5 775 (передача сняла 11 550, ОЗФУ положил 5 775).
**Корень:** `_ПНМП_ЗаполнитьНачисления` (Ф1) брал `НачисленнаяЗарплата.Сумма` («Зарплата управл» Ф1) **напрямую**. Эта сумма: для NET-ФЛ = net-of-НДФЛ но **без вычета алиментов**; для не-NET-ФЛ = **gross-of-НДФЛ**. Штатный механизм ОЗФУ при расчёте А_ВзСС «Оплата труда» вычитает И НДФЛ, И удержания → передача расходилась с ОЗФУ у **8 ФЛ**: 2 алименты (Дубінько −5775, Старіков −6737,50), 2 НДФЛ-gross (Алова −6795,45, Пономаренко О. −6307,75), 1 ОргБух-split (Травінський +6092,04), 3 мелких НДФЛ-остатка.
**Фикс (Fix B — зеркало ОЗФУ, решение пользователя):** источник Начислений Ф1 = **знаковые движения `РегистрНакопления.А_ВзаиморасчетыССотрудниками` дочернего ПРОВЕДЁННОГО ОЗФУ** per (ФЛ, Подр, ОргБух), ФормаPL=Форма1; фильтр регистратора `ВЫРАЗИТЬ(ВзС.Регистратор КАК Документ.ОтражениеЗарплатыВФинансовомУчете).А_ДокОтражениеЗПпоКазне = Ссылка`. Передача = **точный реверс ОЗФУ** → А_ВзСС сама учитывает НДФЛ/удержания/gross-up → конечный остаток на исходном подразделении = 0 у каждого ФЛ.
**Эталон №000000001 (дек):** Начисления Ф1 итого 2 040 167,38 → **2 018 898,22**; Дубінько 11 550 → **5 775**; А_ВзСС Дубінько Глобино-2/Строительство = **0/0**; ПАП «Оплата труда» net=0; идемпотентно. Ф2-филлер НЕ трогали (корень, без алиментов/НДФЛ-проблемы). Тесты `diag_dubinko_vzss.py`, `diag_fix_b_red{,2}.py`, `diag_3outliers.py`, `smoke_fix_b.py`.

### 🔧 Ведомость в кассу / РКО — подразделение тоже на КОРЕНЬ (2026-06-03)

**Зачем:** передача Ф2 поднимает обязательство на корень (`_ПНМП_КореньСтрП`), а ведомость на выплату (→ РКО) платила на ИСХОДНОМ подразделении → А_ВзСС не сходился (Сидоренко: Глобино-2 −89 500, Строительство +89 433,72; РКО №53306/53307 на Глобино-2, передача на Строительстве).

Тогда `Зарплата.Подразделение` и `А_РасшифровкаВыплатыЗарплатаПоФизлицам.Подразделение` = ПодрОрг(корень) → РКО пишет А_ВзСС Расход на корне = цель передачи → конечный остаток 0/0.
