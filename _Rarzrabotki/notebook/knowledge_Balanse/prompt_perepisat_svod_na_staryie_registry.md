## 1. Бизнес-проблема (диагноз — НЕ повторять)

В свод-балансе (`РегистрСведений.А_ОтчетБаланс_Свод`) по подразделению **Глобино-2** статья **«Задолженность клиентов»** имеет **плуг Расхождение=Да на +36 804 033,14 ₽** (последнее измерение на 22.05.2026). До этого плуг был **−7 194 594,73**, потом скакнул.

### Корень изменения плуга

Финансист удалил все документы `Документ.РегистраторРасчётов` и запустил **«Регламентные операции по закрытию месяца» → «Актуализация движений документов по данным взаиморасчётов»**. Регламент автоматически:

1. Создал новые `Документ.РегистраторРасчётов` с **Датой = 22.05.2026 19:10:39** (текущий момент).
2. Записал в `РасчетыСКлиентамиПоСрокам` / `РасчетыСПоставщикамиПоСрокам` **все 596 регистраторов** с агрегированными движениями.
3. Также создал `Документ.КорректировкаРегистров 0Ц-00000004 от 30.11.2025` с операцией **«ИсправлениеРазрывовОстатковВзаиморасчётов»** — входящие 43,9 М в `ПоСрокам` (см. `CommonModules\ОперативныеВзаиморасчетыСервер\Ext\Module.bsl` стр. 6918-6973, функция `КорректировкаРегистров()`).

В результате:
- В **«ПоСрокам»** регистрах все исторические остатки **переписаны на дату 22.05.2026** через РегРасчётов.
- Если запросить `.Остатки(31.12.2025)` через виртуальную таблицу — данные правильные (платформа считает по полю `Период`, а не по дате документа).
- НО **исторический срез ненадёжный**: при следующем перезапуске закрытия месяца платформа пересоздаст РегРасчётов с **другой** датой и потенциально с **другими** агрегатами (например, если входящее сальдо отличается).

### Почему это критично для свод-баланса

Текущий `Свод_РасчетыСПартнерами` использует:
- `РегистрНакопления.РасчетыСКлиентамиПоСрокам.ОстаткиИОбороты(&НачМес, &КонМес, ...)`
- `РегистрНакопления.РасчетыСПоставщикамиПоСрокам.ОстаткиИОбороты(...)`

В этих регистрах **записи привязаны к РегистраторРасчётов**, а не к первичке. Когда РегРасчётов **пересоздаётся**, остаток на 31.12.2025 может **подскочить** (как сейчас: было 37 М, стало 81 М).

Эти регистры:

## 2. Архитектурные различия двух регистров — ВАЖНО ДЛЯ ПРАВКИ

### Что есть в новом регистре `РасчетыСКлиентамиПоСрокам` (текущая функция)

| Поле | Тип | Назначение |
|---|---|---|
| Измерение `АналитикаУчетаПоПартнерам` | СпрСсылка | Ключ JOIN-а на `АналитикаУчетаПоПартнерам.КлючАналитики` (где Орг/Партнёр/Контрагент/Договор) |
| Измерение `ОбъектРасчетов` | СпрСсылка | Объект расчётов |
| Измерение `Валюта` | СпрСсылка | Валюта |
| **Ресурс `ДолгРегл`** | Число | Долг (когда нам должен клиент) — отдельное поле |
| **Ресурс `ПредоплатаРегл`** | Число | Предоплата (когда мы должны клиенту) — отдельное поле |
| Ресурс `ДолгУпр`, `ПредоплатаУпр` | Число | Управленческие версии |
| Виртуальная таблица | `.ОстаткиИОбороты(...)` | поля `ДолгУпрНачальныйОстаток`, `ДолгУпрКонечныйОстаток`, `ПредоплатаУпрНачальныйОстаток`, `ПредоплатаУпрКонечныйОстаток` |

### Что в старом регистре `РасчетыСКлиентами` (целевая правка)

| Поле | Тип | Назначение |
|---|---|---|
| Измерение `АналитикаУчетаПоПартнерам` | СпрСсылка | Тот же ключ, идентичный JOIN |
| Измерение `ОбъектРасчетов` | СпрСсылка | ОР |
| Измерение `Валюта` | СпрСсылка | Валюта |
| **Ресурс `Сумма`** | Число | **ОДНО** поле — **знаковое сальдо**: `+` = долг (клиент должен нам), `−` = аванс (мы должны клиенту) |
| Ресурс `КОплате`, `Оплачивается`, `КОтгрузке`, `Отгружается` | Число | Вспомогательные движения |
| Реквизит `СуммаУпр`, `СуммаРегл` | Число | Не виртуально |
| Виртуальная таблица | `.ОстаткиИОбороты(...)` | поля `СуммаНачальныйОстаток`, `СуммаКонечныйОстаток` |

### Аналогично для поставщиков

**`РасчетыСПоставщиками`** — ресурс **`Сумма`** (знак: + = долг нам поставщику, − = выданный аванс).

### Ключевое различие в логике классификации

В **новом** регистре долг/аванс разнесены по **двум полям** (ДолгРегл / ПредоплатаРегл).
В **старом** — по **одному** полю `Сумма` со знаком.

То есть **алгоритм классификации в Свод_РасчетыСПартнерами поменяется**:

| Статья | Новый регистр (текущий код) | Старый регистр (новая правка) |
|---|---|---|
| ЗадолженностьКлиентов | `ДолгУпрКонечныйОстаток` (всегда ≥ 0) | `ВЫБОР КОГДА СуммаКонечныйОстаток > 0 ТОГДА СуммаКонечныйОстаток ИНАЧЕ 0 КОНЕЦ` |
| ПолученныеАвансы | `ПредоплатаУпрКонечныйОстаток` (всегда ≥ 0) | `ВЫБОР КОГДА СуммаКонечныйОстаток < 0 ТОГДА -СуммаКонечныйОстаток ИНАЧЕ 0 КОНЕЦ` |
| ЗадолженностьПередПоставщиками | `ДолгУпрКонечныйОстаток` (постав.) | `ВЫБОР КОГДА СуммаКонечныйОстаток > 0 ТОГДА СуммаКонечныйОстаток ИНАЧЕ 0 КОНЕЦ` (постав.) |
| ВыданныеАвансы | `ПредоплатаУпрКонечныйОстаток` (постав.) | `ВЫБОР КОГДА СуммаКонечныйОстаток < 0 ТОГДА -СуммаКонечныйОстаток ИНАЧЕ 0 КОНЕЦ` (постав.) |

### 4 ветки UNION ALL — точная карта замены

| # | Тип ветки | Старый регистр | Старое поле | Новое поле | Знак фильтра |
|---|---|---|---|---|---|
| 1 | ЗадолженностьКлиентов | `РасчетыСКлиентами` | `СуммаНачальныйОстаток` / `СуммаКонечныйОстаток` | `ДолгУпрНачальныйОстаток` / `ДолгУпрКонечныйОстаток` | `> 0` (фильтр+агрегат) |
| 2 | ПолученныеАвансы | `РасчетыСКлиентами` | `-СуммаНачальныйОстаток` / `-СуммаКонечныйОстаток` | `-ПредоплатаУпрНачальныйОстаток` / `-ПредоплатаУпрКонечныйОстаток` | `< 0` (берём `-Сумма`) |
| 3 | ЗадолженностьПередПоставщиками | `РасчетыСПоставщиками` | `-СуммаНачальныйОстаток` / `-СуммаКонечныйОстаток` | `-ДолгУпрНачальныйОстаток` / `-ДолгУпрКонечныйОстаток` | `> 0` (берём `-Сумма`) |
| 4 | ВыданныеАвансы | `РасчетыСПоставщиками` | `СуммаНачальныйОстаток` / `СуммаКонечныйОстаток` | `ПредоплатаУпрНачальныйОстаток` / `ПредоплатаУпрКонечныйОстаток` | `< 0` (берём `-Сумма`) |

> **Подсказка к веткам 2 и 4 (с минусом):** в исходном коде уже стоит `-Р.ПредоплатаУпрНачальныйОстаток` и `-Р.ДолгУпрНачальныйОстаток`. В новом коде нужно использовать `-СуммаНачальныйОстаток` с фильтром `СуммаНачальныйОстаток < 0`, чтобы получить положительное число для записи в Свод. То есть знак-обратимость сохраняется, но математически делается через `ВЫБОР КОГДА Р.Сумма... < 0 ТОГДА -Р.Сумма... ИНАЧЕ 0 КОНЕЦ`.

## 6. Источник `Source` в новом коде

В исходной функции `Source` = `Перечисление.ИсточникиУправленческогоБаланса.РасчетыСКлиентамиПоСрокам` / `РасчетыСПоставщикамиПоСрокам`.

**ВАЖНО**: финансист может потребовать оставить ИМЕННО `РасчетыСКлиентамиПоСрокам` / `РасчетыСПоставщикамиПоСрокам` в `Source` (по совместимости с OLAP-маппингом + ПАП-фильтром §4 свода) — или заменить на новые значения перечисления (например, `РасчетыСКлиентами` / `РасчетыСПоставщиками`, если они есть в перечислении).

**По умолчанию**: оставить `РасчетыСКлиентамиПоСрокам` / `РасчетыСПоставщикамиПоСрокам` в `Source`. Это обеспечит совместимость с `втПАП`-выборкой (она фильтрует по этому Source) и не сломает OLAP `Fact_Balance.Source`.

## 10. Anti-patterns (не делать)

| Anti-pattern | Почему |
|---|---|
| Менять имя Source в Свод_РасчетыСПартнерами | Сломает OLAP-маппинг `Fact_Balance.Source` и фильтр `втПАП` |
| Менять `втПАП` блок (фильтр Источник) | ПАП — отдельный регистр, его источник не зависит от того откуда мы тянем расшифровку |
| Удалять fallback `ОР.Договор.Подразделение` | Финансист подтвердил что для декабря 2025 fallback не активируется, безопаснее оставить |
| Не делать резервную копию BSL | Стандартный workflow, всегда |
| Не перепровести А_ФинРез_Баланс после правки кода | Без перепровода старые движения в А_ОтчетБаланс_Свод останутся |
| Не запустить snapshot-тест | Без него нельзя доказать что плуг уменьшился |
