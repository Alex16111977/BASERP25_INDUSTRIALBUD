## 3. Чому план НЕ спрацював як описано — резолюція GATE OD-2

З канону §5 OD-2 (перевірено кодом + БД у сесії реалізації):

1. **GATE OD-2 = FAIL по ключу `ИдентификаторФинЗаписи`.** Поля `ИдентификаторФинЗаписи` **немає в `РегистрНакопления.ПрочиеАктивыПассивы`** (Python COM: `Поле не найдено "Б.ИдентификаторФинЗаписи"`). Воно існує лише як **реквізит регістра-ДЖЕРЕЛА** `РасчетыСКлиентами`/`РасчетыСПоставщиками`, а не в ПАП. Тож вихідна ідея join «ПАП ↔ джерело по `ИдентификаторФинЗаписи`» **технічно неможлива**.
2. **Реальний механізм** (вивчено штатну `Обработка.ДвиженияАктивовПассивов` / `ManagerModule.bsl`, проц. `ДобавитьТекстЗапросаРасчетыСПартнерами`): ПАП будується з `РасчетыС…`, де **`ПАП.Регистратор = РасчетыС….Регистратор`** (той самий документ-джерело). `ИдентификаторФинЗаписи` штатна обробка для зв'язку **не використовує**.
3. **✅ Затверджений альтернативний ключ (рішення фінансиста):** зв'язок ПАП↔джерело = **`ПАП.Регистратор = РасчетыС…/СебестоимостьТоваров/ДенежныеСредства….Регистратор`** (+ Организация + Подразделение). Субконто `ОбъектРасчетов` — напряму з регістра-джерела (вимір регістра).
4. **Застереження гранулярності:** ПАП групує по `Регистратор`, не по `ОбъектРасчетов`. Якщо один документ дає кілька `ОбъектРасчетов` — на гранулярності ПАП він неоднозначний → субконто заповнюється **лише коли унікальне на регістратор** (fill-when-unique), інакше порожнє.

**Наслідок:** оскільки зв'язок тепер по `Регистратор`, а **один документ-регістратор може писати в ПАП по різних статтях і одночасно фігурувати в різних типових регістрах**, прив'язка «1 стаття → 1 регістр» з плану **не виконується**. Регістр-розшифровка визначається не статтею, а тим, **який типовий регістр має цей самий `Регистратор`** (за пріоритетом CASE: РасчетыСКлиентами > РасчетыСПоставщиками > СебестоимостьТоваров > ДенСрБезнал > ДенСрНал > ПрочиеАктивыПассивы). Тому **одна стаття має кілька Source**.

Типізовані під-аналітики (`ТипНалога`, `ОбъектСтр-ва`, `ВидОперацииЗП`) **не реалізовані** — їх відповідних вимірів у регістрі немає (OD-9: AI не додає поля); замість них generic `Аналитика3 = ПРЕДСТАВЛЕНИЕ(ПАП.Аналитика)` (аудит-рядок).

## 4. ФАКТ — як працює зараз (з ObjectModule.bsl)

**Суми** — завжди `ПАП.ОстаткиИОбороты`. **Source** — динамічний CASE:

| Source (`А_ИсточникБаланса`) | Регістр-розшифровка | Ключ | Субконто, що дає |
|---|---|---|---|
| `ПрочиеАктивыПассивы` | `ПАП.Аналитика` напряму (`ВЫРАЗИТЬ`) | — | Контрагент/Организация, Партнёр, ОбъектыЭксплуатации, ФизЛицо, НематериальныйАктив |
| `РасчетыСКлиентами` | `РегНак.РасчетыСКлиентами` | `Регистратор` | `ОбъектРасчетов` (якщо унікальний на регістратор) |
| `РасчетыСПоставщиками` | `РегНак.РасчетыСПоставщиками` | `Регистратор` | `ОбъектРасчетов` |
| `СебестоимостьТоваров` | `РегНак.СебестоимостьТоваров` | `Регистратор` | `Номенклатура`, `Склад` |
| `ДенежныеСредстваБезналичные` | `РегНак.ДенежныеСредстваБезналичные` | `Регистратор` | `ДенежныеСредства`=БанковскийСчет |
| `ДенежныеСредстваНаличные` | `РегНак.ДенежныеСредстваНаличные` | `Регистратор` | `ДенежныеСредства`=Касса |
| `ПрочиеРасходы` | `РегНак.ВзаиморасчетыССотрудниками` (тільки «Оплата труда», Етап 4) | Организация+ФизЛицо, розклад ∝ \|сальдо\| | `ФизическоеЛицо` |

Пріоритет CASE (Частина A UNION): `РасчетыСКлиентами` → `РасчетыСПоставщиками` → `СебестоимостьТоваров` → `ДенСрБезнал` → `ДенСрНал` → інакше `ПрочиеАктивыПассивы`.

## 7. Висновок

- **Коректність балансу не постраждала:** Σ по `Статья` == ПАП до копійки; Σ КонОст ≈ 0 (Актив=Пасив); acceptance PASS (січень/ТОВ; контроль 289 064 974,43 по всіх орг).
- **Розходження з планом — архітектурне і свідоме** (рішення фінансиста, резолюція GATE OD-2): ключ `Регистратор` замість неіснуючого `ИдентификаторФинЗаписи`; Source динамічний per-Регистратор; типізовані під-аналітики не вводяться (OD-9).
- **Для аналітика/Power BI:** не очікувати «1 стаття = 1 Source». Фільтрувати/групувати по `Статья` для сум; `Source` використовувати як drill-down-розріз «звідки розшифровка», розуміючи що по одній статті їх кілька.
- **Якщо потрібно привести до плану** (1 стаття = 1 регістр, типізовані під-аналітики) — це **зміна логіки + структури регістра**, рішення фінансиста, окремий цикл. Поточний код **не правиться** (вказівка користувача 2026-05-16).
