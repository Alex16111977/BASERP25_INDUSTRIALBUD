# Розшифровка статей «Расходы/Доходы текущего периода» через `СтатьяДоходыРасходы` (v2 2026-05-26)

> **Тип файлу:** домен-специфічна документація. Описує **бухгалтерську логіку** розшифровки двох спеціальних статей балансу через спеціалізовані сальдові регістри `ПрочиеРасходы` / `ПрочиеДоходы` з правилом відбору **НО ≠ 0 АБО КО ≠ 0**.
>
> **Контекст:** канон-образець #3 (`balanse_pattern_and_roadmap.md` §6.6) — патерн розшифровки через спеціалізовані сальдові регістри. v1 (JOIN з `ДвиженияДоходыРасходыПрочиеАктивыПассивы`) — відмінено.

---

## 1. Архітектура реєстрів

| Регістр | Тип | Роль | Вимір розрізу |
|---|---|---|---|
| `РегНакопл.ПрочиеАктивыПассивы` (ПАП) | Balance | **Первинний** регістр балансу. Підсумок «Расх.тек.пер.»/«Дох.тек.пер.» per (Орг,Подр). | Статья (ПВХ.СтатьиАктивовПассивов) |
| `РегНакопл.ПрочиеРасходы` | Balance | **Розшифровує первинний** для «Расходы тек.пер.». Пишеться тими ж первинними документами що ПАП. | **`СтатьяРасходов`** (ПВХ.СтатьиРасходов) |
| `РегНакопл.ПрочиеДоходы` | Balance | **Розшифровує первинний** для «Доходы тек.пер.». | **`СтатьяДоходов`** (ПВХ.СтатьиДоходов) |

**Зв'язок ПАП ↔ розшифровуючі регістри:** обидва оновлюються одним і тим же документом-регістратором при проведенні. Тобто Σ ПрочиеРасходы.ОстаткиИОбороты per (Орг,Подр) ≈ Σ ПАП.ОстаткиИОбороты per (Орг,Подр,Статья=Расх.тек.пер.). Невеликі розбіжності (наприклад «Амортизация ОС» пише в ПАП без розшифровки в ПрочиеРасходы) компенсуються плугом у свод-проведенні.

## 2. Бухгалтерська логіка (від фінансиста)

«Расходы текущего периода» (Актив, АктивПассив=Актив) і «Доходы текущего периода» (Пассив) — це **статті поточного періоду**. Семантика:

- Документ-первинка (РКО, Розподіл расхода, Списання, Амортизація ОС, тощо) **збільшує** «Расходы тек.пер.» на суму витрати по реальній СтатьеРасходов.
- Регламент **закриття місяця** в кінці періоду **списує** ці накопичені витрати на фінрезультат — «Прибыли и убытки» (рух «мінус» по «Расходы тек.пер.» + «плюс» по «Прибыли и убытки»).
- Після закриття місяця «Расходы тек.пер.» обнулюється — переходящих остатків НЕ повинно бути.

**Що бачимо у Глобино-2 апрель 2026:**

| Статья расходов | НО (01.04) | Приход | Расход | КО (30.04) | У свод? | Причина |
|---|---|---|---|---|---|---|
| Будівельні матеріали | 0 | 3 468 650,79 | 3 468 650,79 | 0 | НЕ пишемо | Закрилася всередині міс. — у балансі немає |
| Зарплата ИТР | 0 | 510 000,00 | 510 000,00 | 0 | НЕ пишемо | те ж саме |
| ... ~50 інших закритих статей | 0 | X | X | 0 | НЕ пишемо | оборотка, не баланс |
| **Затраты на служебные командировки и содержание аппарата управления предприятием** | 0 | **2 400,00** | 0 | **2 400,00** | **ПИШЕМО** | **Незакритий остаток** на 30.04 |

Σ ПАП(Глобино-2, Расх.тек.пер., ВСІ Источники) КО на 30.04 = **2 400** (з оборотки УпрБалансу + регістра ПрочиеРасходы).

## 3. Правило відбору

З `.ОстаткиИОбороты(&НачМес, &КонМес)` розшифровуючого регістра пишемо в свод **тільки** рядки де:

```sql
ИМЕЮЩИЕ
    СУММА(СуммаНачальныйОстаток) <> 0
    ИЛИ СУММА(СуммаКонечныйОстаток) <> 0
```

**Чому НЕ просто «КО ≠ 0»:** у бухгалтерському балансі рядок повинен показуватися якщо стаття **присутня в балансі** хоча б на одну з двох опорних дат (01.04 або 30.04). Якщо стаття переходить з минулого місяця з НО=500 і повністю закрилася в текущему місяці (КО=0) — її потрібно показати з НО=500, КО=0 (рух був). Якщо НО=0 і КО=0 — її в балансі не було, не показуємо.

## 4. Структура BSL запиту (ветви A і B Свод_ПрочиеРасходыДоходы)

### Ветка A — Расходы текущего периода

```bsl
ВЫБРАТЬ
    ПР.Организация КАК Организация,
    ЕСТЬNULL(ПР.Подразделение, ЗНАЧЕНИЕ(Справочник.СтруктураПредприятия.ПустаяСсылка)) КАК Подразделение,
    &РасхТекПер КАК Статья,
    ЗНАЧЕНИЕ(Перечисление.ИсточникиУправленческогоБаланса.ПустаяСсылка) КАК Source,
    ЗНАЧЕНИЕ(Справочник.ОбъектыЭксплуатации.ПустаяСсылка) КАК ОбъектыЭксплуатации,
    ЗНАЧЕНИЕ(Справочник.НематериальныеАктивы.ПустаяСсылка) КАК НематериальныйАктив,
    ЗНАЧЕНИЕ(Перечисление.ТипыНалогов.ПустаяСсылка) КАК ТипНалога,
    ПР.СтатьяРасходов КАК СтатьяДоходыРасходы,
    СУММА(ПР.СуммаНачальныйОстаток) КАК СуммаНачальныйОстаток,
    СУММА(ПР.СуммаКонечныйОстаток) КАК СуммаКонечныйОстаток
ПОМЕСТИТЬ втПРД
ИЗ РегистрНакопления.ПрочиеРасходы.ОстаткиИОбороты(&НачМес, &КонМес, Авто, , Организация = &Орг) КАК ПР
СГРУППИРОВАТЬ ПО
    ПР.Организация,
    ЕСТЬNULL(ПР.Подразделение, ЗНАЧЕНИЕ(Справочник.СтруктураПредприятия.ПустаяСсылка)),
    ПР.СтатьяРасходов
ИМЕЮЩИЕ
    СУММА(ПР.СуммаНачальныйОстаток) <> 0
    ИЛИ СУММА(ПР.СуммаКонечныйОстаток) <> 0
```

### Ветка B — Доходы текущего периода (симетрично)

Через `РегистрНакопления.ПрочиеДоходы.ОстаткиИОбороты` + вимір `СтатьяДоходов`.

### Ветка C — інші статті джерел {ПрочиеДоходы/Партии/ПрочиеРасходы}

Без змін відносно попередньої логіки: основна таблиця ПАП з фільтром `Т.Источник В (&Ист) И Т.Статья <> &РасхТекПер И Т.Статья <> &ДохТекПер` + ВЫРАЗИТЬ(ПАП.Аналитика) для субконто (ТипНалога/ОбъектыЭксплуатации/НМА).

### втПАП — для плугів

```bsl
ВЫБОР КОГДА Т.Статья = &РасхТекПер ИЛИ Т.Статья = &ДохТекПер
    ТОГДА ЗНАЧЕНИЕ(Перечисление.ИсточникиУправленческогоБаланса.ПустаяСсылка)
    ИНАЧЕ Т.Источник
КОНЕЦ КАК Source,
...
ГДЕ
    Т.Организация = &Орг И Т.Период <= &КонМес
    И ((Т.Статья = &РасхТекПер ИЛИ Т.Статья = &ДохТекПер)              -- БЕЗ фільтра Источник
       ИЛИ (Т.Источник В (&Ист) И Т.Статья <> &РасхТекПер И Т.Статья <> &ДохТекПер))
    И НЕ Т.Статья В ИЕРАРХИИ(&Искл)
```

## 5. Заповнення вимірів РС `А_ОтчетБаланс_Свод`

| Вимір | Значення для статей Расх/Дох тек.пер. |
|---|---|

| `СтатьяДоходыРасходы` | `ПрочиеРасходы.СтатьяРасходов` / `ПрочиеДоходы.СтатьяДоходов` (реальна стаття) |

| решта субконто (ОбъектыЭксплуатации, НМА, ТипНалога, Номенклатура, Контрагент, Договор, ОбъектРасчетов, Партнер, Склад, ФизическоеЛицо, ДенежныеСредства) | ПустаяСсылка |

## 6. Виключення з `Свод_ПрочиеАктивыПассивы_Прямой`

Щоб не дублювати рухи (статті Расх/Дох тек.пер. з Источник=ПустаяСсылка типу Амортизація ОС), у `Свод_ПрочиеАктивыПассивы_Прямой` додано:

```bsl
ГДЕ
    ...
    И Т.Источник = ЗНАЧЕНИЕ(Перечисление.ИсточникиУправленческогоБаланса.ПустаяСсылка)
    И НЕ Т.Статья В ИЕРАРХИИ(&Искл)
    И Т.Статья <> &ОТ
    И Т.Статья <> &РасхТекПер     -- ← v2 2026-05-26
    И Т.Статья <> &ДохТекПер      -- ← v2 2026-05-26
```

Це означає: рухи Амортизація ОС по «Расходы тек.пер.» (signedΣ=+296 802,71 в Глобино-2 апр) **тепер обробляє лише `Свод_ПрочиеРасходыДоходы`** через ПрочиеРасходы.ОстаткиИОбороты. Регістр ПрочиеРасходы містить ці рухи в розшифровуючій формі.

## 7. Інваріант (контрольна сума)

```
Σ свод.КО per (Орг,Подр,Статья=Расх.тек.пер.) == ПАП.ОстаткиИОбороты.КО per same до 0.01
Σ свод.НО per (Орг,Подр,Статья=Расх.тек.пер.) == ПАП.ОстаткиИОбороты.НО per same до 0.01
```

Якщо є розбіжність — плуг (Расхождение=Истина, СтатьяДоходыРасходы=NULL, Аналитика1="") компенсує. Це може траплятися для документів які пишуть в ПАП без запису в ПрочиеРасходы (рідкісні корекційні операції).

**Приклад апрель 2026:**
- Глобино-2: 1 деталь (Командировки 2 400), 0 плугів, Σ=2 400 ✓
- Виробництво: 0 деталей (всі статті закрилися), 1 плуг +3 964,80 (Амортизація ОС не покрита ПрочиеРасходы), Σ=3 964,80 == ПАП
- ЦО: 0 деталей, 1 плуг −3 964,80 (зеркало Виробництва), Σ=−3 964,80 == ПАП
- В сумі по організації: 2 400 + 3 964,80 − 3 964,80 = **2 400** == УпрБаланс ✓

## 9. Чому v1 (JOIN з ДвиженияДоходыРасходыПрочиеАктивыПассивы) відмінено

**Спроба v1 (commit `ebb20e149`):** JOIN ПАП ⨝ `ДвиженияДоходыРасходыПрочиеАктивыПассивы` per (Регістратор, Період, Підрозділ) для розшифровки.

**Проблеми v1 (за відгуком фінансиста):**
1. ПАП накопичує signed Σ ВСІХ рухів до КонМес (включаючи багатомісячні накопичення з прошлих періодів). Σ деталі per Источник могла бути ≠ 0 для НО, навіть якщо в реальному регістрі ПрочиеРасходы НО=0. Користувач бачив у звіті багато рядків з НО ≠ 0 — це візуально не відповідає бухгалтерському балансу де НО для статей "текущего периода" має бути 0.
2. Багато плугів (Расхождение=Истина) для розбіжностей по копійках між signedΣ ПАП і Σ ДДР через картезіан LEFT JOIN.
3. Свод записував десятки статей у Σ деталей які потім "компенсувалися" нулями — нагромаджували регістр і робили його нечитабельним.

**v2 рішення:** не використовувати signed Σ з ПАП накопичено, а брати остатки ПРЯМО з спеціалізованих регістрів-розшифровок з правилом відбору НО≠0 АБО КО≠0. Це бухгалтерська логіка балансу — показуємо лише незакриті остатки.
