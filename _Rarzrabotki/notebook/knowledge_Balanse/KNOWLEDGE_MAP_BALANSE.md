- **Декомпозиція по `Источник`** (`Перечисление.ИсточникиУправленческогоБаланса`) з ОСНОВНОЇ таблиці `ПрочиеАктивыПассивы` (реквізит `Источник`/`ВидИсточника` — не у віртуальних таблицях). DR-7: фільтр `ВидИсточника` НЕ потрібен (усі шари Σ == ПАП).
- **Структура регістра змінена** (db-load-xml+db-update Dynamic+): `Source` → `Перечисление.ИсточникиУправленческогоБаланса`; `+Расхождение` (Булево); `ДокументДвижения`=ПАП.Регистратор. `Перечисление.А_ИсточникБаланса` — більше не використовується (дубль).
- **`СверкаСПАП`**: Σ по (Орг,Подр,Статья) приводиться до `ПАП.ОстаткиИОбороты` — пропорц. обрізка / добивка пустої аналітики, прапор `Расхождение`. Σ ваг=1 (Оплата труда розклад по ФізОсобі).
- **Acceptance v2 (головний, вимога користувача):** `_Rarzrabotki/Python/test/test_balans_vs_upr_balance_report.py` — Σ по `Статья` проведеного `А_ОтчетБаланс_Свод` == штатний `Отчет.УправленческийБаланс` (його dataset-запит) **до копійки** (Оплата труда tol 1.0); Σ≈0 Актив=Пасив; `Расхождение`=0.00 (per-Источник сходиться точно). **PASS** (січень/ТОВ): 14 статей, проведення 27 062 рядки, ідемпотентно.

### ⚠️ Follow-up (відкладено, рішення користувача 2026-05-16)

Субконто `ОбъектРасчетов / Номенклатура / Склад / ДенежныеСредства` у v2 заповнюються лише через `ВЫРАЗИТЬ(ПАП.Аналитика)`; для статей РасчётыС*/Себестоимость/ДенСр `ПАП.Аналитика` порожня (СтатьиБезАналитики) → ці субконто **поки НЕ заповнюються** (у старому моноліті були через LEFT JOIN регістрів-джерел по Регистратору, Етапи 2-3). **Σ/баланс/звірка зі звітом не залежать від цього і зелені.** Окремий цикл: додати в `_СводПоИсточнику` LEFT JOIN `РасчетыС*ПоСрокам`→ОбъектРасчетов, `СебестоимостьТоваров`→Номенкл/Склад, `ДенСр*`→ДенежныеСредства (fill-when-unique). Тест `test_balans_s4_verify.py` — його assert субконто Етапів 2-3 **superseded** редизайном (інваріант Σ==ПАП він підтверджує: `[OK] Σ по статтях == ПАП`); авторитетний acceptance тепер `test_balans_vs_upr_balance_report.py`.

## TL;DR (найважливіше за 30 секунд)

1. **Документ `А_ФинРез_Баланс`** проводиться помісячно по організації; при проведенні наповнює `РегистрСведений.А_ОтчетБаланс_Свод` згорткою балансу.
2. **Суми ЗАВЖДИ беруться з `РегистрНакопления.ПрочиеАктивыПассивы.ОстаткиИОбороты`** (ПАП) — єдине джерело сум, без UNION-подвоєння. Це той самий ПАП, що й штатний `Отчёт.УправленческийБаланс`.
3. **Аналітику (субконто) «розшифровують» типові регістри** (`РасчетыСКлиентами`, `РасчетыСПоставщиками`, `СебестоимостьТоваров`, `ДенежныеСредства*`, `ВзаиморасчетыССотрудниками`) — приєднуються **LEFT JOIN по `Регистратор`** (документ, що зробив рух ПАП), субконто підставляється **лише коли унікальне на регістратор** (fill-when-unique).
4. **Колонка `Source`** (`Перечисление.А_ИсточникБаланса`, 7 значень) = з якого регістра взято розшифровку рядка. **Не фіксована per-стаття** — одна стаття може мати кілька `Source` (бо різні документи-регістратори по тій самій статті матчаться з різними типовими регістрами).
5. **⚠️ Розходження з планом:** у плані реалізації закладався ключ `ИдентификаторФинЗаписи` і **жорстка прив'язка 1 стаття → 1 регістр**. Фактично: поля `ИдентификаторФинЗаписи` **немає в ПАП** (GATE OD-2 FAIL) → ключ — `Регистратор`; Source **динамічний per-Регистратор**. Деталі та повна таблиця розходжень — у [balanse_mapping_actual_vs_planned.md](balanse_mapping_actual_vs_planned.md).
6. **Код працює коректно** (Σ==ПАП до копійки) — розходження стосується **способу зв'язку**, а не правильності сум.
