# Open-source и 1С-практики прогноза ДДС и бюджетных моделей: что взять как идеи для калькулятора бюджета ДДС (проект × месяц)

> Контекст: ТОВ «Індастріалбуд», BAS ERP 2.5. Свой документ `А_ПредварительныйБюджет` + регистр `А_ПредварительныйБюджетНаМесяц`, факт — регистр ДДС из «Казны». Калькулятор на Python (COM) считает бюджет ДДС на 3 месяца, объясняет каждую сумму и грузит её в 1С. Драйверы: модульные дома (отгружено домов в месяц × нормы техкарты) и металлоконструкции (тонны × ставка за тонну).

## 1. Какие GitHub/open-source решения реализуют прогноз ДДС, driver-based бюджет, S-кривую, 13-недельный cash flow, прогноз оборотного капитала, и какую технику из них стоит взять

### Takeaway
Зрелых open-source «калькуляторов бюджета ДДС» на GitHub почти нет. По запросам «13 week cash flow» и «driver-based budget» находятся десятки учебных проектов с 0–несколькими звёздами. Ценные идеи дают четыре зрелых проекта: hledger (одно правило работает и как бюджет, и как прогноз; сгенерированные строки помечены тегами), OCA MIS Builder (бюджет по KPI или по счетам, пропорция по времени, несколько помеченных строк в одной ячейке, детализация до проводок), ERPNext Budget (бюджет по проекту, помесячное распределение, Stop/Warn/Ignore по стадиям, ревизии бюджета) и cashflower (переменные как функции времени t, допущения отделены от логики). S-кривые и «лаги» удобнее брать из методических статей, а не из кода.

### Cited Findings
**Общая картина поиска на GitHub**
- По запросу «cash flow forecast» почти вся выдача — DCF-оценка акций, личные финансы и учебные проекты. Специализированного инструмента для проектного ДДС в выдаче нет — [GitHub search](https://github.com/search?q=cash+flow+forecast&type=repositories)
- По «13 week cash flow» нашлось около 30 репозиториев. Почти все — портфолио-проекты 2025–2026 годов на Excel/Python/Streamlit — [GitHub search](https://github.com/search?q=%2213+week+cash+flow%22&type=repositories)
- Запрос «driver-based budget / s-curve cash flow project» дал всего 4 результата, все — учебные финмодели компаний. Запрос «s-curve construction cash flow / earned value python» дал 0 результатов — [GitHub search](https://github.com/search?q=driver-based+budget&type=repositories)

**hledger (plain-text accounting, активный проект: последний push 02.10.2026)**
- Бюджет и прогноз задаются одним «периодическим правилом», например «ежемесячно с даты X: статья — сумма». Флаг `--budget` сравнивает факт с этим правилом и показывает процент исполнения. Флаг `--forecast` по тому же правилу генерирует будущие операции — [hledger: Budgeting and forecasting](https://hledger.org/budgeting-and-forecasting.html)
- В бюджетном отчёте выводятся только статьи, у которых есть бюджет. Всё остальное собирается в отдельную строку `<unbudgeted>`, то есть факт без плана не теряется. Режим `--cumulative` переносит остаток бюджета на следующий период — [hledger: Budgeting and forecasting](https://hledger.org/budgeting-and-forecasting.html)
- Прогнозные операции начинаются после последней фактической операции, чтобы факт и прогноз не пересекались — [hledger manual: Forecasting](https://hledger.org/1.40/hledger.html#forecasting)
- Сгенерированные прогнозом операции и строки получают служебные теги `generated-transaction`, `generated-posting`, `modified`. По ним всегда видно, что строка синтетическая и откуда она взялась — [hledger manual: Forecasting](https://hledger.org/1.40/hledger.html#forecasting)
- Разовые события (крупный платёж и т.п.) прогноз из правил не учитывает. Их добавляют отдельными записями — [hledger: Budgeting and forecasting](https://hledger.org/budgeting-and-forecasting.html)

**OCA MIS Builder + mis_builder_budget (Odoo; 184★, 384 fork; push 28.09.2026)**
- Бюджет задаётся двумя способами: по KPI (KPI помечается как «бюджетируемый» и получает способ накопления: сумма для оборотов, среднее для численности и подобного) или по счетам (одна строка на счёт, опционально с аналитикой) — [OCA/mis-builder, mis_builder_budget](https://github.com/OCA/mis-builder/tree/19.0/mis_builder_budget)
- У строки бюджета есть даты начала и конца. В отчёте за другой период сумма пересчитывается пропорционально времени (pro-rata temporis). Строки с пересекающимися датами допускаются: каждая добавляет свою долю. Есть поле label, которое различает несколько вкладов в одну и ту же ячейку — [OCA/mis-builder, mis_builder_budget](https://github.com/OCA/mis-builder/tree/19.0/mis_builder_budget)
- Источник данных выбирается для каждой колонки: факт, бюджет, а также колонки «сумма» и «сравнение» для план-факта и комбинаций — [OCA/mis-builder](https://github.com/OCA/mis-builder)

**ERPNext Budget (Frappe)**
- Поле «Budget Against» принимает Cost Center, Project или Accounting Dimension. Есть периодичность распределения (Monthly / Quarterly / Half-Yearly / Yearly) и флажок «Distribute Equally», иначе распределение по периодам вводится строками вручную — [ERPNext docs: Budgeting](https://docs.frappe.io/erpnext/user/manual/en/budgeting)
- Контроль идёт на четырёх стадиях: заявка на материалы (Material Request), заказ поставщику (Purchase Order), фактический расход и накопленный расход. На каждой стадии своё действие: Stop / Warn / Ignore. Изменения утверждённого бюджета проводятся через Budget Revision, анализ отклонений — в Budget Variance Report — [ERPNext docs: Budgeting](https://docs.frappe.io/erpnext/user/manual/en/budgeting)

**cashflower (Python-фреймворк актуарных моделей денежных потоков; около 62★ по данным страницы; push 24.07.2026)**
- Переменная модели — это функция от времени t, которая может ссылаться на свои значения в t-1 и на другие переменные. Из этих ссылок неявно складывается граф зависимостей, то есть цепочку расчёта можно отследить — [acturtle/cashflower](https://github.com/acturtle/cashflower)
- Проект разложен по файлам: входные данные (`input`), формулы (`model`), допущения и настройки (`settings`), запуск (`run`) — [acturtle/cashflower](https://github.com/acturtle/cashflower)

**py-finstmt (21★; последний push 07.2024)** — библиотека для работы с финотчётностью и проекции FCF. Подробности о методах прогноза по статьям на странице репозитория найти не удалось (см. Gaps) — [nickderobertis/py-finstmt](https://github.com/nickderobertis/py-finstmt)

**13-недельные модели (портфолио, 0★, но с полезными практиками)**
- Скользящий цикл: каждую неделю самая старая прогнозная неделя заменяется фактом и добавляется новая неделя на горизонте 13 — [OsasAnalyst/13-week-cash-flow-forecast](https://github.com/OsasAnalyst/13-week-cash-flow-forecast)
- Задержка поступлений измеряется по истории, отдельно по способам оплаты. Если медианный лаг мал, его сознательно не моделируют и прямо пишут об этом как об упрощении — [OsasAnalyst/13-week-cash-flow-forecast](https://github.com/OsasAnalyst/13-week-cash-flow-forecast)
- Стресс-сценарии строятся по отдельным рычагам: волатильность спроса, задержка оплат клиентов, наложение платежей поставщикам, рост затрат, задержка крупного клиента. Главный вывод: временные сдвиги к концу горизонта отыгрываются, а «реальные» затратные шоки оставляют постоянный разрыв — [OsasAnalyst/13-week-cash-flow-forecast](https://github.com/OsasAnalyst/13-week-cash-flow-forecast)
- Итоговый результат — короткое резюме рисков на одной странице для директора, без методологии — [OsasAnalyst/13-week-cash-flow-forecast](https://github.com/OsasAnalyst/13-week-cash-flow-forecast)
- Каркас 13-недельной модели: остаток на начало берётся по банку, затем поступления и выплаты, затем остаток на конец. Дебиторка прогнозируется по срокам оплаты, к просрочке применяются веса вероятности (у автора: просрочка 30 дней — около 80%, 90+ дней — около 40%) — [John Galt Finance: 13-week](https://johngalt-finance.com/cash-flow-forecasting-13-week/)
- По этому гайду точность недель 1–4 может превышать 90%, если опираться на реальные сроки счетов и подтверждённые обязательства. Предложены три сценария: базовый, downside (поступления на 10–20% ниже, оплаты задержаны), upside. Downside назван главным для управления рисками — [John Galt Finance: 13-week](https://johngalt-finance.com/cash-flow-forecasting-13-week/)
- В обзорах рекомендуют прямой метод (поступления и выплаты, без начислений), автоматическую загрузку факта и разбор только крупнейших отклонений — [Stampli](https://www.stampli.com/resources/13-week-cash-flow-forecast/); [Coupler](https://blog.coupler.io/13-week-cash-flow-model/). Встречаются ориентиры точности «±5% на 30 днях / ±15% на 90 днях» и «95%+», но первоисточник у них не указан (см. Gaps).

**S-кривая проектного cash flow (методические статьи; кода на GitHub не найдено)**
- Строятся три кривые: кривая ценности (контрактная стоимость, разнесённая по графику работ), кривая затрат (обычно опережает ценность: платим раньше, чем получаем) и кривая поступлений (отстаёт из-за выставления, приёмки, срока оплаты и гарантийного удержания) — [constructionai.io](https://www.constructionai.io/blog/cash-flow-forecasting-construction)
- На ранней стадии проекта S-кривую приближают стандартной формулой по нормированному времени со «скосом». Сумма периода равна стоимости, умноженной на прирост кумулятивной доли за период; удержание вычитается отдельно — [mastt: S Curve](https://www.mastt.com/blogs/what-is-an-s-curve-in-capital-projects); [Adventures in CRE](https://www.adventuresincre.com/development-budget-distributing-cash-flows-using-the-s-curve-method/); [PMI: cash flow forecasting for building projects](https://www.pmi.org/learning/library/cash-flow-forecasting-updating-building-projects-2045)
- Удержание часто составляет 5%: половина возвращается при завершении, половина после гарантийного периода — [constructionai.io](https://www.constructionai.io/blog/cash-flow-forecasting-construction)

**Лаги и кривые инкассации (оборотный капитал)**
- Кривая инкассации строится по истории за 6–12 месяцев: какая доля оплачивается в ту же неделю, через 1–2 недели, через 30/60/90 дней. Кривую обновляют ежемесячно — [Chaser: cash collections formula](https://www.chaserhq.com/blog/cash-collections-formula)
- Альтернатива — коэффициенты оплаты по корзинам старения дебиторки или DSO-драйвер (дебиторка / выручка × 365) — [HighRadius: DSO forecast](https://www.highradius.com/resources/Blog/forecast-accounts-receivable-using-dso/); [Wall Street Prep: DSO](https://www.wallstreetprep.com/knowledge/days-sales-outstanding-dso/)

### Inferences
- Готовый код брать неоткуда, зрелых аналогов «проект × месяц × статья ДДС» нет. Брать надо архитектурные приёмы: (1) одно описание драйвера используется и для плана, и для прогноза (hledger); (2) несколько помеченных вкладов суммируются в одну ячейку (MIS Builder: label); (3) явная строка «факт без плана» (hledger: `<unbudgeted>`); (4) допущения отделены от формул (cashflower, FAST); (5) стресс-рычаги разделяются на временные и затратные (13-week).
- Лаговая матрица — ключевая техника для «домиков». Шаблон оплат по этапам (аванс, отгрузка, монтаж, удержание) работает как S-кривая/лаг: доля суммы платежа приходится на месяц события, на событие+1 и т.д. Для металла тот же приём проще: тонны × ставка с лагом оплаты поставщику металла относительно месяца производства.
- Статистические библиотеки временных рядов (Prophet, statsforecast и т.п.) здесь, по всей видимости, малополезны: рядов мало, они короткие и проектные. Калибровать лучше коэффициентами «факт/драйвер» и кривыми лагов (см. п. 3).

## 2. Как стандартное бюджетирование 1С:ERP 2.5 / BAS ERP организует бюджет ДДС и прогноз, и что из этого применимо к нашему подходу

### Takeaway
В стандартном бюджетировании ERP три слоя. Справочники-«оси»: модель, вид бюджета, статьи, показатели, нефинансовые показатели, сценарии. Хранилища: план — `ОборотыБюджетов` через документ `ЭкземплярБюджета`; факт — правила плюс регистр `ФактическиеДанныеБюджетирования` с измерением **Правило**. Контроль — лимиты и процесс подготовки бюджетов. Для нашего калькулятора важны четыре идеи: драйверы как «нефинансовые показатели» по сценарию и периоду; правило-источник как измерение у каждой суммы; скользящий бюджет с «границей фактических данных»; план-факт как пара сценариев плюс формула отклонения. Тащить весь стандартный механизм в проект не нужно.

### Cited Findings
**Структура (подтверждено метаданными нашей конфигурации BAS ERP 2.5)**
- `МоделиБюджетирования` — контейнер процесса. Реквизиты: Статус, Начало/КонецДействия, Периодичность, БюджетыПоОрганизациям, БюджетыПоПодразделениям, ИспользоватьУтверждениеБюджетов, АвтоматическиФормироватьЗадачи — [Catalogs/МоделиБюджетирования.xml](file:///C:/Configuration_downloads/BASERP25/Catalogs/МоделиБюджетирования.xml)
- Моделей может быть несколько, они работают параллельно. Статьи и их аналитики между моделями переиспользуются, а виды бюджетов приходится перенастраивать — [Викиучебник: ERP 2.4/Бюджетирование](https://ru.wikibooks.org/wiki/1%D0%A1:ERP_%D0%A3%D0%BF%D1%80%D0%B0%D0%B2%D0%BB%D0%B5%D0%BD%D0%B8%D0%B5_%D0%BF%D1%80%D0%B5%D0%B4%D0%BF%D1%80%D0%B8%D1%8F%D1%82%D0%B8%D0%B5%D0%BC_2.4/%D0%91%D1%8E%D0%B4%D0%B6%D0%B5%D1%82%D0%B8%D1%80%D0%BE%D0%B2%D0%B0%D0%BD%D0%B8%D0%B5); то же самое (неограниченное число моделей) — [v8.1c.ru/erp/budget](https://v8.1c.ru/erp/budget/)
- `СтатьиБюджетов`: до 6 видов аналитики (ВидАналитики1..6), флаги УчитыватьПоКоличеству и УчитыватьПоВалюте, ЕдиницаИзмерения. **В нашей базе уже добавлен реквизит `А_СтатьяДвиженияДенежныхСредств`**, то есть связь статьи бюджета со статьёй ДДС — [Catalogs/СтатьиБюджетов.xml](file:///C:/Configuration_downloads/BASERP25/Catalogs/СтатьиБюджетов.xml)
- Сквозные обязательные аналитики — организация и подразделение (плюс модель, сценарий и период) — [Викиучебник](https://ru.wikibooks.org/wiki/1%D0%A1:ERP_%D0%A3%D0%BF%D1%80%D0%B0%D0%B2%D0%BB%D0%B5%D0%BD%D0%B8%D0%B5_%D0%BF%D1%80%D0%B5%D0%B4%D0%BF%D1%80%D0%B8%D1%8F%D1%82%D0%B8%D0%B5%D0%BC_2.4/%D0%91%D1%8E%D0%B4%D0%B6%D0%B5%D1%82%D0%B8%D1%80%D0%BE%D0%B2%D0%B0%D0%BD%D0%B8%D0%B5); [mkskom](https://mkskom.ru/blog/byudzhetirovanie-v-1s-erp-upravlenie-predpriyatiem-podrobnyj-razbor)
- `ПоказателиБюджетов` бывают двух типов: Расчетный и Целевой (перечисление `ТипПоказателяБюджетов`). Значение показателя — фактический остаток на начало плюс запланированные обороты статей. Влияние статьи на показатель (увеличивает/уменьшает, с каким коэффициентом) задаётся в регистре `СвязиПоказателейБюджетов` с ресурсами Расход и Коэффициент и трансляцией аналитик — [справка СвязиПоказателейБюджетов](file:///C:/Configuration_downloads/BASERP25/InformationRegisters/СвязиПоказателейБюджетов/Ext/Help/ru.html)

Настраиваются по периодам, сценариям, организациям, подразделениям, до 6 аналитик. Предназначены для расчёта зависимых статей (пример из справки: ФОТ = численность × оклады). Вводятся документом `УстановкаЗначенийНефинансовыхПоказателей` вручную или по правилу из имеющихся данных (флаг ЗагружатьИзДругихПодсистем). ### Inferences
- **Драйвер = нефинансовый показатель.** Стандартная модель «НП по сценарию × периоду × аналитике → зависимая статья» — это ровно наша логика «дома/месяц × норма техкарты» и «тонны × ставка». Стандартные НП заводить не обязательно, но в Python стоит хранить драйверы так же: (сценарий, проект, месяц, показатель, значение, ед.изм, источник значения), отдельно от формул.
- **Правило — это измерение суммы.** В стандарте у `ФактическиеДанныеБюджетирования` есть измерение `Правило`. Нам стоит перенести эту идею в прогноз: каждая сумма в `А_ПредварительныйБюджет` и в регистре должна нести «метод/источник». Реквизит «Источник» в строках документа уже есть. Его стоит протащить в регистр (как измерение или хотя бы реквизит) или вести параллельный РС «Расшифровка расчёта». Тогда план-факт можно строить в разрезе «по какому методу посчитано».
- **Скользящий бюджет и граница факта.** Наш 3-месячный горизонт — это и есть «Скользящий» с границей на последнем закрытом месяце Казны. Месяцы до границы берутся из факта Казны, после неё считаются драйверами. Двигается одна дата расчёта, конец горизонта вычисляется.
- **План-факт — пара сценариев плюс формула «Отклонение».** Факт в документ бюджета не вводим, его тянет отчёт из регистра Казны. В нашем отчёте сравнение «План ↔ Реалистичный ↔ Факт» строится как набор колонок-сценариев с формулами отклонения и процента выполнения.
- **ВидВерсии (Первичный / Корректировка)** — наш аналог Budget Revision в ERPNext и статуса в `ОборотыБюджетов`. Корректировку лучше хранить отдельным документом-дельтой, а не перезаписью: так история версий сохраняется.
- **Лимиты.** Стандартный механизм через сценарий «Исполнение бюджета» можно позже подключить к заявкам на расход ДС, если бюджет начнут использовать как лимит. Для калькулятора это вне scope.
- Стандартную подсистему целиком (модели, виды, экземпляры, ОборотыБюджетов) внедрять ради нашего калькулятора нецелесообразно: она тяжёлая, требует настройки правил под Казну и дублирует уже работающий кастом. Брать концепции, а не объекты.

## 3. Лучшие практики трассируемости бюджетных чисел (строки-пояснения, реестр допущений, версии сценариев), калибровка по факту и тесты сверки

### Takeaway
Трассируемость держится на трёх вещах. Первая — допущения хранятся отдельно от расчёта (FAST: Inputs → Workings → Outputs → Control) и версионируются. Вторая — у каждой сгенерированной суммы есть метка происхождения (hledger: теги; ERP: измерение «Правило»; MIS Builder: label вклада). Третья — регулярный цикл «прогноз ↔ факт» с разбором крупнейших отклонений, а результат разбора возвращается в допущения (калибровка).

### Cited Findings
- FAST Standard: модель делится на Foundation (входы), Workings (расчёты), Presentation (вывод) и Control (проверки, чувствительности, сценарии, учёт изменений, версии). Жёстко заданные допущения изолируются в отдельном блоке и не смешиваются с расчётами — [Brixx: FAST Standard](https://brixx.com/the-fast-standard-in-finance-explained/); [Financial Arena: FAST](https://www.financialarena.co.uk/the-fast-modeling-standard/)
- Расчёт идёт в одном направлении (сверху вниз, слева направо), что само по себе даёт естественный след аудита. Хорошая модель обязательно содержит integrity checks — [Brixx](https://brixx.com/the-fast-standard-in-finance-explained/); [Tilt Analytics](https://tiltanalytics.com/good-vs-bad-financial-model/)
- Метки происхождения: в hledger у прогнозных операций и строк есть скрытые и видимые теги «сгенерировано» и «изменено» — [hledger manual](https://hledger.org/1.40/hledger.html#forecasting). В ERP у факта есть измерение «Правило» — [ФактическиеДанныеБюджетирования.xml](file:///C:/Configuration_downloads/BASERP25/AccumulationRegisters/ФактическиеДанныеБюджетирования.xml). В MIS Builder у строки бюджета есть label для нескольких вкладов в одну ячейку — [mis_builder_budget](https://github.com/OCA/mis-builder/tree/19.0/mis_builder_budget)
- Расшифровки в ERP: отчёты «Справка расчёт показателя бюджетов» и «Расшифровка формулы бюджетного отчёта», у строки экземпляра бюджета есть поле «Примечание» — [Reports](file:///C:/Configuration_downloads/BASERP25/Reports/); [ЭкземплярБюджета.xml](file:///C:/Configuration_downloads/BASERP25/Documents/ЭкземплярБюджета.xml)
- Версии и ревизии: Budget Revision в ERPNext — [ERPNext](https://docs.frappe.io/erpnext/user/manual/en/budgeting); измерение Статус в `ОборотыБюджетов` и утверждение бюджетов в модели ERP — [ОборотыБюджетов.xml](file:///C:/Configuration_downloads/BASERP25/AccumulationRegisters/ОборотыБюджетов.xml); [МоделиБюджетирования.xml](file:///C:/Configuration_downloads/BASERP25/Catalogs/МоделиБюджетирования.xml)
- Калибровка: анализ отклонений сравнивает факт периода с прогнозом, выявляет устойчиво ошибающиеся статьи и возвращает вывод в допущения. Структура модели держится стабильной, чтобы обновление было «обновлением данных», а не перестройкой. Разбирается ограниченное число крупнейших промахов — [Stampli](https://www.stampli.com/resources/13-week-cash-flow-forecast/); [Coupler](https://blog.coupler.io/13-week-cash-flow-model/); [John Galt Finance](https://johngalt-finance.com/cash-flow-forecasting-13-week/)
- Кривые лагов калибруются по истории за 6–12 месяцев и обновляются ежемесячно — [Chaser](https://www.chaserhq.com/blog/cash-collections-formula)
- Проверка механики переката на ретроспективе («3-недельная rolling-симуляция» с контролем отклонения прогноз/факт) — [OsasAnalyst](https://github.com/OsasAnalyst/13-week-cash-flow-forecast)
- Тождество денежного баланса: остаток на конец = остаток на начало + поступления − выплаты, остаток на начало — по банку — [John Galt Finance](https://johngalt-finance.com/cash-flow-forecasting-13-week/)
- В стандартном отчёте «факт без плана» выводится отдельной строкой — [hledger](https://hledger.org/budgeting-and-forecasting.html)

### Inferences
**Рекомендуемая структура строки бюджета калькулятора** (до загрузки в 1С и в журнале расчёта):

| Поле | Назначение |
|---|---|
| Сценарий | План / Реалистичный (+ при необходимости Стресс) |
| ИдРасчёта (run_id), ДатаРасчёта, ГраницаФакта | Версия запуска; месяц, до которого взят факт Казны |
| ВерсияДопущений (хеш файла допущений) | Воспроизводимость: те же допущения дают те же цифры |

| Драйвер: наименование, количество, ед. | «Отгрузка домов, 3 шт.» |

| Основание (ссылка) | Договор, техкарта, заказ, документ Казны |

**Как калибровать** (план → реалистичный):
- Коэффициент «факт / драйвер» по статье и направлению за последние N закрытых месяцев. Например, фактическая оплата металла на тонну против нормативной ставки.
- Профиль лагов «месяц события → месяц платежа» по истории Казны.
- Реалистичный сценарий получается как преобразование плана (×коэффициенты, сдвиг по лагам), а не как отдельный ручной ввод. Тогда разница План ↔ Реалистичный объясняется ровно этими двумя множителями.

**Тесты сверки** (инварианты, а не «было → стало»):
1. Σ вкладов по (проект, месяц, статья, вид оплаты) = строке документа = движению регистра после проведения.
2. Σ по документу = Σ по регистру по сценарию и подразделению.
3. Драйверы калькулятора совпадают с источником: число домов в расчёте = плану отгрузок, тонны = плану производства.
4. Ретро-тест: запуск с границей факта на N месяцев назад и сравнение с фактом Казны. Ошибка считается по статьям, топ-10 промахов выводятся.
5. Строка «факт без плана» по статьям Казны, которых нет в бюджете.
6. Идемпотентность: повторный запуск с тем же хешем допущений даёт те же суммы, и в 1С нет дублей (get-or-create документа на сценарий × проект × период).
7. Денежное тождество: остаток на начало (Казна) + поступления − выплаты = остаток на конец по каждому месяцу горизонта.

### Gaps
- Отдельного open-source «реестра допущений» (assumptions register) как продукта не найдено. Практика описана в стандартах моделирования (FAST, ICAEW) на уровне принципов. Текст ICAEW Financial Modelling Code не открывался.
- Количественных ориентиров точности прогноза ДДС для проектного производства (модульные дома, металлоконструкции) в источниках нет.

## 4. Какие 3–5 приёмов принять

### Takeaway
Принять пять приёмов:
1. **Реестр драйверов и допущений отдельно от формул.** Аналог нефинансовых показателей ERP, cashflower `settings`, FAST Inputs.
2. **Лаговые профили и S-кривая платежей по этапам** с калибровкой по истории Казны.
3. **Метка происхождения у каждой суммы** (Источник / Правило / Пояснение / run_id) с выводом в регистр и отчёт. Аналоги: измерение «Правило» в ERP, теги hledger, label в MIS Builder.
4. **Скользящий 3-месячный бюджет с границей факта** и перекатом: факт заменяет прогноз.
5. **План-факт как набор сценариев-колонок** с формулами отклонения, строкой «факт без плана» и набором инвариантных тестов сверки.
