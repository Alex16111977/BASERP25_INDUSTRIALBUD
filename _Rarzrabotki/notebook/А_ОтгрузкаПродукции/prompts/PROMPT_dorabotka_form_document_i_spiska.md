## §1. Pre-flight (ОБЯЗАТЕЛЬНО, до любых правок)

В git модулей форм никогда не было, но обработчики в Form.xml объявлены с момента создания. Возможно, модуль существует **только в живой базе** и не выгружен.

1. Выгрузить актуальные исходники документа из живой BaseERP частичной выгрузкой (`/db-dump-xml`, список = `Документ.А_ОтгрузкаПродукции`) во временный каталог или с бэкапом текущих файлов основной конфигурации.
2. Сравнить с файлами в `C:\Configuration_downloads\BASERP25\Documents\А_ОтгрузкаПродукции\`:
   - **Если Module.bsl в живой базе ЕСТЬ** — взять его за основу, дорабатывать его (НЕ затирать живой код!), и сохранить выгруженную версию в git до правок.
   - **Если модуля нет** — формы в бою падают/молчат; создавать модули с нуля по §2–§3.
3. Сверить каждый `<Event>` из Form.xml с процедурами итогового модуля (грабли `ozp_form_events_dangling_handlers`): после доработки несоответствий быть не должно.
4. Проверить наличие реквизита `ЕдиницаИзмерения` у `Справочник.Номенклатура` (для §2.2). Если имя иное — использовать реальное.

1. `/form-validate` обеих форм. Ложные срабатывания «attribute '~Список' not found» на колонках динамического списка — игнорировать (известный паттерн, 48 форм конфигурации).
2. `/1c-bsl-review` всех новых/изменённых .bsl.
3. Сверка: каждый `<Event>` в обоих Form.xml имеет процедуру в модуле (Grep `<Event` → имена → Grep по модулю).
4. Новых запросов 1С в задаче нет. Если по ходу появится хоть один — **Rule #-1**: сначала Python COM тест на BaseERP, потом BSL.
5. **Rule #4**: скопировать ВСЕ изменённые/новые файлы из worktree в `C:\Configuration_downloads\BASERP25\...` (включая новые Module.bsl и ManagerModule.bsl).
6. Загрузка в базу: `/db-load-xml -Mode Partial` (сам обновит ConfigDumpInfo) + `/db-update -Dynamic+` для серверной BaseERP (память `feedback_use_db_skills_for_config_load`; с 1cv8.exe вручную не воевать).
7. Smoke (минимум, без перепроведения истории): открыть ФормаСписка → есть кнопки Создать/Провести/Ещё; открыть существующий документ → форма открывается без ошибок, итоги ТЧ заполнены, при правке Количество/Цена строка пересчитывается, в меню Отчёты есть «Структура подчинённости». UI-проверку выполняет пользователь — попросить его и дать чеклист.

### Definition of Done

| # | Критерий |
|---|---|
| 1 | Module.bsl обеих форм существуют, все объявленные `<Event>` имеют процедуры |
| 2 | В списке видны кнопки Создать / Провести / Отменить проведение / Ещё |
| 3 | На обеих формах работают подключаемые команды БСП (Ещё → Отчёты → Структура подчинённости) |
| 4 | Сумма строки = Количество × Цена при изменении; итоги в подвале ТЧ |
| 5 | Единица измерения отображается у строки Состав |
| 6 | Видимость КонтрагентЗаказчик/ПодразделениеЗаказчик переключается флагом СтороннийЗаказчик |
| 7 | form-validate: 0 реальных ошибок; 1c-bsl-review: 0 критичных |
| 8 | Файлы скопированы в основную конфигурацию, конфигурация загружена и применена (db-load-xml + db-update) |
| 9 | ObjectModule.bsl документа байт-в-байт не изменён |

## §6. Ограничения / STOP & ASK

- **НЕ менять** `ObjectModule.bsl` (живая обменная логика и порождение цепочки документов).
- **НЕ менять** состав реквизитов метаданных документа (только формы + ManagerModule + одна строка в ВариантыОтчетовПереопределяемый).
- ЕРП-флаги (`А_Обработан`, `А_Необновлять`) оставить редактируемыми — их вручную сбрасывают при повторной обработке обмена.
- Переменную с именем `Ссылка` в модулях не объявлять (конфликт с системным свойством).
- Массово ничего не перепроводить — задача чисто интерфейсная.
- 🛑 STOP & ASK: если pre-flight (§1) покажет, что в живой базе модуль формы ЕСТЬ и расходится с планом §2 — остановиться и показать пользователю diff перед слиянием логики.
