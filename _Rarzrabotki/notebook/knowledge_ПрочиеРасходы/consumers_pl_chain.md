# Потребители `ПрочиеРасходы`: цепочка факта в P&L

> Тип файла: ПОСТОЯННЫЙ (архитектура потребителей). Обновлять при изменении А_ФинРез_PL / А_ОтчетPL_Свод / OLAP.
>
> Зачем: чтобы при доработке реквизитов `ПрочиеРасходы` (особенно `ФормаPL`) понимать, кто и как читает регистр,
> и что нужно изменить «вниз по течению», чтобы новое измерение дошло до Power BI.

---

## 1. Карта потребителей

```
РегистрНакопления.ПрочиеРасходы  (факт расходов, 7 измерений)
   │
   ├── Документ.А_ФинРез_PL        ── свёртка факта+плана → РегистрСведений.А_ОтчетPL_Свод
   │        (читает .Обороты, фильтр по ДДС-статье, mirror-знак по ТипСтатьи)
   │
   └── Отчет.А_ОтчетPL (СКД, UI)   ── План vs Факт vs Касса для финансиста (читает регистр напрямую)

РегистрСведений.А_ОтчетPL_Свод
   │
   └── OLAP Ai_Olap → Fact_PnL → PL.pbix  (Power BI, P&L одной формулой Σ Sum_Fact)
```

Главный «офлайн»-потребитель для OLAP — **`Документ.А_ФинРез_PL`** (его и упоминал заказчик: `ФормаPL` нужна,
«чтобы проводить формы учёта в учёт PL» именно через этот документ).

---

## 2. `Документ.А_ФинРез_PL` — как читает регистр

Файл: `Documents/А_ФинРез_PL/Ext/ObjectModule.bsl`.

### 2.1 Чтение факта расходов (CTE `втЕРП_Расх`, ~строка 150–217)

```sql
ВЫБРАТЬ
    Р.Подразделение, Р.СтатьяРасходов,
    Р.СтатьяРасходов.А_СтатьяДвиженияДенежныхСредств КАК ДДС,
    Р.Регистратор КАК Документ,
    ВЫБОР КОГДА Р.Регистратор ССЫЛКА Документ.ПриобретениеТоваровУслуг ТОГДА … .Контрагент … КОНЕЦ КАК Контрагент,
    ВЫБОР КОГДА Р.Регистратор ССЫЛКА Документ.АвансовыйОтчет ТОГДА … .ПодотчетноеЛицо … КОНЕЦ КАК ФизЛицо,
    СУММА(Р.СуммаПриход) КАК СуммаЕРП            -- ← СуммаПриход (см. инвариант §3 architecture_invariants)
ПОМЕСТИТЬ втЕРП_Расх
ИЗ
    РегистрНакопления.ПрочиеРасходы.Обороты(&НачалоПериода, &КонецПериода, Регистратор, ) КАК Р   -- ← .Обороты!
ГДЕ
    Р.СтатьяРасходов <> ЗНАЧЕНИЕ(ПланВидовХарактеристик.СтатьиРасходов.ПустаяСсылка)
    И Р.СтатьяРасходов.А_СтатьяДвиженияДенежныхСредств <> ЗНАЧЕНИЕ(Справочник.СтатьиДвиженияДенежныхСредств.ПустаяСсылка)
СГРУППИРОВАТЬ ПО …
```

**Важно для `ФормаPL`:** чтение идёт через `.Обороты(...)` → `ФормаPL` (измерение) **доступна сразу**,
достаточно добавить её в SELECT/GROUP BY и (опц.) в параметр-измерение виртуальной таблицы. Реквизит
`А_ФизическоеЛицо` здесь НЕ используется (в этом документе ФЛ берётся из `АвансовыйОтчет.ПодотчетноеЛицо`).

### 2.2 Привязка к PL — через ДДС-статью

Факт расхода стыкуется с PL-статьёй через `СтатьяРасходов.А_СтатьяДвиженияДенежныхСредств` ↔ ДДС в
`А_Статьи_PL.Статьи` (ТЧ). Подробно: [../knowledge_PL/pl_report_architecture_analyst.md](../knowledge_PL/pl_report_architecture_analyst.md).

### 2.3 Mirror-знак по `ТипСтатьи` (финальный SELECT свёртки)

В `СформироватьЗапросСверткиPL()` 6 ресурсов оборачиваются `ВЫБОР КОГДА Статья.ТипСтатьи = Расход ТОГДА -Сумма
ИНАЧЕ Сумма КОНЕЦ` → P&L одной формулой `Σ Sum_Fact`. См. [../knowledge_PL/pl_finrez_sign_by_type.md](../knowledge_PL/pl_finrez_sign_by_type.md).

### 2.4 Известные грабли А_ФинРез_PL

- `А_ДокументРасшифровка` — вызов закомментирован 2026-05-20 (регистр не создан). Не раскомментировать без создания регистра.
- Дубли ключа Свода при `Комментарий` в группировке (31.03.2026) → `МАКСИМУМ(Комментарий)`.
- Перепроведение 28 документов А_ФинРез_PL за 2024-01..2026-04 — скрипт `scripts/_reprovesti_finrez_pl.py`.

## 3. `РегистрСведений.А_ОтчетPL_Свод` — приёмник свёртки

Файл: `InformationRegisters/А_ОтчетPL_Свод.xml`.

- **Ресурсы (6):** `СуммаФ1_Excel`, `СуммаФ2_Excel`, `Сумма_Excel`, `СуммаФ1`, `СуммаФ2`, `Сумма` (+ реквизит `Комментарий`).
- **Измерения (13):** `Организация`, `Подразделение`, **`ФормаPL`** ✅, `Источник`, `Статья`,
  `СтатьяДвиженияДенежныхСредств`, `Контрагент`, `ФизическоеЛицо`, `ДокументДвижения`, `СтатьяДоходов`,
  `СтатьяРасходов`, `Аналитика`, `Договор`.

> ✅ **КЛЮЧЕВОЙ ФАКТ:** в `А_ОтчетPL_Свод` измерение **`ФормаPL` УЖЕ ЕСТЬ** (как и ресурсы `СуммаФ1`/`СуммаФ2`).
> Значит «низ» цепочки (Свод → Fact_PnL → PBIX) к `ФормаPL` готов.
> **Этап 1 (DONE 2026-06-08):** движения `ПрочиеРасходы` несут `ФормаPL` (ОЗФУ + остальные — см.
> [formapl_ozfu_done.md](formapl_ozfu_done.md), [formapl_ostalnye_done.md](formapl_ostalnye_done.md)).
> **Этап 2 (DONE 2026-06-09):** `А_ФинРез_PL` читает `ФормаPL` из `.Обороты` и пишет измерение `ФормаPL` +
> факт-разрез `СуммаФ1`/`СуммаФ2` в Свод (по реальной форме, не по эвристике ПКО/РКО). См.
> [formapl_finrez_done.md](formapl_finrez_done.md).

Разрез Ф1/Ф2 в Своде теперь идёт И со стороны **плана** (Excel: `СуммаФ1_Excel`/`СуммаФ2_Excel`), И со стороны
**факта** `ПрочиеРасходы` (через `ФормаPL`-измерение свёртки, Этап 2). Доход/CoGS — целиком Форма1.
Осталось довести разрез факта до OLAP/PBIX (Этап 4, см. [formapl_roadmap.md](formapl_roadmap.md)).

## 4. `Отчет.А_ОтчетPL` (UI, СКД)

Читает регистры ЕРП напрямую (План vs Факт vs Касса). Для drill-down по ФЛ использует **прямую таблицу**
`ПрочиеРасходы` (реквизит `А_ФизическоеЛицо`) — отсюда грабля 2026-05-21 (см. [architecture_invariants.md §2.1](architecture_invariants.md)).
Файлы: `Reports/А_ОтчетPL/Ext/ObjectModule.bsl` (живой) + зеркало `_Rarzrabotki/Отчеты/А_ОтчетPL` (BSL идентичен,
СКД чуть различается). Фильтр чернеток `НеПроводитьВСверку` — только в `А_ФинРез_PL`, в отчёте сознательно НЕТ.

✅ **DONE 2026-06-09:** отчёт теперь разносит ФАКТ по форме — ресурсы `СуммаЕРПФ1`/`СуммаЕРПФ2` (расход по
`Р.ФормаPL` в `втЕРП_Расх_Детали`, прямая таблица; доход/CoGS → Ф1) + сравнение `РазницаФ1`/`РазницаФ2`
(`Сумма(СуммаФN) − Сумма(СуммаЕРПФN)`). Существующие `СуммаЕРП`/`Разница` сохранены; инварианты
`ЕРПФ1+ЕРПФ2=ЕРП`, `РазницаФ1+Ф2=Разница`, Σ неизменны (Rule #-1 на декабре 2025: Σ ЕРП=186 822 744,14,
Ф2=11 061 210,00=оборот Форма2; СКД-валидация 0 ошибок; смоук-компоновка OK). Промт:
[PROMPT_ФормаPL_А_ОтчетPL_РесурсыФ1Ф2.md](PROMPT_ФормаPL_А_ОтчетPL_РесурсыФ1Ф2.md). Грабля СКД: `<totalField>`
под корнем = **1 таб** (а `<field>` под `<dataSet>` = 2 таба). Историю отчёт не перепроводит (читает регистры онлайн).

## 5. OLAP / Power BI (вниз по течению)

`А_ОтчетPL_Свод` → ETL `Ai_Olap` → `Fact_PnL` → `PL.pbix`. Если `ФормаPL` нужно довести до Power BI как разрез
факта — каскад правок (ALTER/маппинг/enum/partition) описан в
[../knowledge_PL/pl_finrez_sign_by_type.md](../knowledge_PL/pl_finrez_sign_by_type.md) и `../knowledge_Olap/`.
Здесь НЕ дублируем — только ссылаемся (memory `olap_mapping_refresh_after_metadata_change`,
`pbix_sql_database_schema_cache`).
