# Структура регистра `РегистрНакопления.ПрочиеРасходы`

> Источник: `AccumulationRegisters/ПрочиеРасходы.xml` + `Ext/ManagerModule.bsl` + `Ext/RecordSetModule.bsl`.
> Это **типовой** регистр BAS ERP (не кастомный `А_*`). Структуру ведёт платформа/типовое
> обновление; **наши** добавления — реквизит `А_ФизическоеЛицо` и измерение `ФормаPL`.
>
> Тип файла: ПОСТОЯННЫЙ. Обновлять только при изменении структуры (измерения/ресурсы/реквизиты/RegisterType).
>
> ⚠️ **Правило `feedback_no_typical_register_changes`:** типовые регистры структурно НЕ трогаем.
> Исключения зафиксированы человеком (финансистом/разработчиком): `А_ФизическоеЛицо` и `ФормаPL`.
> Любое НОВОЕ изменение структуры — только через явное согласование, см. [architecture_invariants.md](architecture_invariants.md).

## 2. Измерения (7)

> ⚠️ **Обновлено 2026-06-08:** финансист добавил 7-е измерение `ФормаPL` (разделение
> официальная/управленческая части для PL). Было 6.

| # | Измерение | Тип | Заполнение / роль |
|---|---|---|---|
| 1 | `Организация` | СправочникСсылка.Организации | всегда (RLS, `DenyIncompleteValues=true`) |
| 2 | `Подразделение` | СправочникСсылка.СтруктураПредприятия | подразделение-источник расхода (RLS) |
| 3 | `НаправлениеДеятельности` | СправочникСсылка.НаправленияДеятельности | направление, на которое отнесены расходы |
| 4 | `НалоговоеНазначение` | СправочникСсылка.НалоговыеНазначенияАктивовИЗатрат | налоговое назначение (регл. учёт) |
| 5 | `СтатьяРасходов` | ПланВидовХарактеристикСсылка.СтатьиРасходов | **ключ для PL** (через `.А_СтатьяДвиженияДенежныхСредств`) |
| 6 | `АналитикаРасходов` | Характеристика.СтатьиРасходов (составной) | аналитика отнесения расходов (заказ/объект/орг и т.п.) |
| 7 | **`ФормаPL`** 🆕 | **ПеречислениеСсылка.А_ФормыPL** (Форма1/Форма2) | разделение офиц./управл. части для PL. ✅ **Заполняется из ОЗФУ** (Этап 1 DONE 2026-06-08, см. [formapl_ozfu_done.md](formapl_ozfu_done.md)); прочие регистраторы — пусто (вне scope Фазы 1) |

**Почему `ФормаPL` — измерение, а не реквизит** (КЛЮЧЕВОЙ момент): измерение **доступно в виртуальной
таблице `.Обороты()`**, реквизит — нет. Потребитель `Документ.А_ФинРез_PL` читает регистр именно через
`ПрочиеРасходы.Обороты(...)` (см. [consumers_pl_chain.md](consumers_pl_chain.md)). Поэтому `ФормаPL` сделана
измерением — чтобы её можно было получить в `.Обороты` без перехода на прямую таблицу регистра. Это сознательное
архитектурное решение, см. ⚠️ грабли в [architecture_invariants.md §2](architecture_invariants.md).

**RLS** (`Ext/ManagerModule.bsl`, `ПриЗаполненииОграниченияДоступа`):
```bsl
"РазрешитьЧтениеИзменение
|ГДЕ
|    ЗначениеРазрешено(Организация)
|    И ЗначениеРазрешено(Подразделение)";
```

## 5. ManagerModule — механизм `ДополнительныеПоля` (КАК расширять движения)

Файл: `AccumulationRegisters/ПрочиеРасходы/Ext/ManagerModule.bsl`

Регистр предоставляет **общий конструктор текста запроса движений**, которым пользуются
документы-регистраторы (тот, кто наполняет регистр через свой `ОбработкаПроведения`).
Эти функции принимают параметр `ДополнительныеПоля` — список доп. полей через запятую.

| Функция (экспорт) | Что делает | Маркеров `//ДополнительныеПоля` |
|---|---|---|
| `ТекстОписаниеВтИсходныеПрочиеРасходы(ДополнительныеПоля="")` | «ВЫБРАТЬ ПЕРВЫЕ 0 …» — описание структуры ВТ `ВтИсходныеПрочиеРасходы` | 1 |
| `ТекстЗапросаТаблицаВтПрочиеРасходы(ДополнительныеПоля="")` | промежуточная ВТ `ВтПрочиеРасходы` (логика `ВариантРаспределенияРасходов`, расчёт всех сумм) | 1 |
| `ТекстЗапросаТаблицаПрочиеРасходы(ДополнительныеПоля="")` | **финальные движения** регистра — 3 ветки UNION | **3** |
| `ДобавитьДополнительныеПоляВТекстЗапроса(ДополнительныеПоля, ТекстЗапроса)` | служебная: на каждый маркер подставляет `,Строки.<Поле>` | — |

### 5.1 Как работает подстановка

```bsl
Процедура ДобавитьДополнительныеПоляВТекстЗапроса(ДополнительныеПоля, ТекстЗапроса)
    Если НЕ ЗначениеЗаполнено(ДополнительныеПоля) Тогда Возврат; КонецЕсли;
    ТекстДополнительныеПоля = "";
    СписокПолей = СтрРазделить(ДополнительныеПоля, ",");
    Для каждого ИмяПоля Из СписокПолей Цикл
        ТекстДополнительныеПоля = ТекстДополнительныеПоля + "
        |	,Строки." + ИмяПоля;
    КонецЦикла;
    ТекстЗапроса = СтрЗаменить(ТекстЗапроса, "//ДополнительныеПоля", ТекстДополнительныеПоля);
КонецПроцедуры
```

**Критично:** подстановка делает буквально `,Строки.<ИмяПоля>`. Значит поле с таким именем
**должно физически присутствовать** в исходной ВТ (`Строки` = `ВтИсходныеПрочиеРасходы` / `ВтПрочиеРасходы`).
Сам конструктор регистра (`ТекстОписаниеВтИсходныеПрочиеРасходы`) поля `А_ФизическоеЛицо`/`ФормаPL` **НЕ
содержит** — их добавляет **документ-регистратор** в своей собственной ВТ-источнике (см. прецедент ОЗФУ в
[registratory_and_fill.md §3](registratory_and_fill.md)).

### 5.2 Три ветки финального запроса `ТекстЗапросаТаблицаПрочиеРасходы`

1. **Основная** — движения расходов (`ПОМЕСТИТЬ`/SELECT из `ВтПрочиеРасходы`).
2. **`СторнированиеРасходовУУ`** — сторно у организации-источника при кросс-орг распределении
   (`Строки.ОрганизацияПолучатель <> Строки.Организация`), суммы со знаком `−`.
3. **`РегистрацияРасходовУУ`** — регистрация у организации-получателя, `Организация = ОрганизацияПолучатель`.

Все 3 ветки имеют свой маркер `//ДополнительныеПоля` → доп. поле протаскивается во все три (важно для
сохранения аналитики при кросс-орг перераспределении).

### 5.3 Прочие функции ManagerModule

- **Международный учёт** (хуки `МеждународныйУчетСерверПовтИсп`): `ИсточникиУточненияСчета`,
  `ИсточникиПодразделений`, `ИсточникиНаправлений`, `ИсточникиСубконто`, `ПоказателиВВалюте`,
  `ПоказателиКоличества`, `Показатели`. **Не трогать** — завязаны на регл./МСФО учёт.
- **Обновление ИБ** (`ОписаниеОбработчиковОбновления`, `ЗарегистрироватьДанныеКОбработке…`,
  `ОбработатьДанные…`) — типовые отложенные обработчики версий (3.5.4.400, 3.5.10.5). Не трогать.
