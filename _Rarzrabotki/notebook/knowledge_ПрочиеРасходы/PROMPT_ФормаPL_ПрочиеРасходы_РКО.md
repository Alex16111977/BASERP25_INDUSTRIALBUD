# PROMPT — заполнение измерения `ФормаPL` в движениях `ПрочиеРасходы` при проведении РасходныйКассовыйОрдер (РКО)

> **Документ-источник:** `Документ.РасходныйКассовыйОрдер` (РКО), база **BaseERP**.
> **Файл кода:** `Documents/РасходныйКассовыйОрдер/Ext/ManagerModule.bsl`.
> **Регистр-приёмник:** `РегистрНакопления.ПрочиеРасходы`, измерение **`ФормаPL`** (`EnumRef.А_ФормыPL` = {Форма1, Форма2}).
> **Образец:** `РегистрНакопления.А_ВзаиморасчетыССотрудниками.ЗаполнитьИзРКО` (то же правило ОргБух→Ф1/Ф2).
> **Статус:** дизайн согласован через `/superpowers:brainstorming`. Scope — только РКО → `ПрочиеРасходы.ФормаPL`.
> **База знаний:** `_Rarzrabotki/notebook/knowledge_ПрочиеРасходы/` (читать ПЕРЕД работой); Этап 1 (ОЗФУ) уже сделан —
> см. [formapl_ozfu_done.md](formapl_ozfu_done.md) (тот же механизм `ДополнительныеПоля`).

---

## 1. Цель и правило

Заполнять измерение **`ФормаPL`** в движениях регистра `ПрочиеРасходы` при проведении **РКО**, по правилу
(точно как заказчик и как `А_ВзСС.ЗаполнитьИзРКО`):

| `РасходныйКассовыйОрдер.А_ОрганизацияБухгалтерия` | `ФормаPL` |
|---|---|
| **заполнен** (`ЗначениеЗаполнено` = Истина) | **Форма1** (`Перечисления.А_ФормыPL.Форма1`) — официально, по конкретному юрлицу |
| **пустой** | **Форма2** (`Перечисления.А_ФормыPL.Форма2`) — управленческая |

Сейчас движения `ПрочиеРасходы` по РКО пишутся **с пустой `ФормаPL`** (хелпер регистра вызывается без `ДополнительныеПоля`).

---

## 2. Зачем (контекст — НЕ часть этой задачи)

РКО **переносятся из Казны**. Реквизит `А_ОрганизацияБухгалтерия` — это реальное юрлицо-плательщик (мапится из
документа Казны по `КодПоЕДРПОУ`); если он заполнен — выплата официальная (Ф1). Если пуст — расход управленческий
по «управленческой» организации (ТОВ ІНДАСТРІАЛБУД) → Ф2. См. [../knowledge/perenos_dvizheniy_iz_kazny.md](../knowledge/perenos_dvizheniy_iz_kazny.md),
[../knowledge/exchange_erp_kazna.md](../knowledge/exchange_erp_kazna.md).

Это шаг к разрезу факта PL по формам. ⛔ **В ЭТОЙ задаче `А_ФинРез_PL`, свёртку `А_ОтчетPL_Свод` и отчёт НЕ трогаем**
(это Этап 2, [formapl_roadmap.md](formapl_roadmap.md)). Только заполнение измерения в движениях регистра.

## 4. Образец: `А_ВзаиморасчетыССотрудниками.ЗаполнитьИзРКО`

Файл: `AccumulationRegisters/А_ВзаиморасчетыССотрудниками/Ext/ManagerModule.bsl` (~стр. 367-378):
```bsl
// Если заполнен А_ОрганизацияБухгалтерия — официальная выплата по конкретному юрлицу:
// движения идут как Форма1 + ОрганизацияБухгалтерия. Иначе — управленческая Форма2.
ОргБух    = ДокОбъект.А_ОрганизацияБухгалтерия;
ЭтоФорма1 = ЗначениеЗаполнено(ОргБух);
...
Запись.ФормаPL = ?(ЭтоФорма1, Перечисления.А_ФормыPL.Форма1, Перечисления.А_ФормыPL.Форма2);
```
**Это ровно правило задачи.** Отличие: в `ПрочиеРасходы` наполнение идёт не прямым `Движения.Добавить()`, а через
типовой запрос + механизм `ДополнительныеПоля` (как в Этапе 1 для ОЗФУ).

## 5. Механизм (как РКО наполняет `ПрочиеРасходы`)

РКО использует **тот же конструктор регистра** что и ОЗФУ:
- `ТекстЗапросаТаблицаВтИсходныеПрочиеРасходы` (~стр. 4571) строит **РКО-специфичную** ВТ `ВтИсходныеПрочиеРасходы`
  из `ТаблицаРасшифровкаПлатежа` (плоский SELECT, **без `СГРУППИРОВАТЬ ПО`**), фильтр `ХозОп = ПрочаяВыдачаДенежныхСредств`.
- `ТекстЗапросаТаблицаВтПрочиеРасходы` (~стр. 4619) и `ТекстЗапросаТаблицаПрочиеРасходы` (~стр. 3057) вызывают
  `РегистрыНакопления.ПрочиеРасходы.ТекстЗапросаТаблица…()` **без аргумента** → надо передать `"ФормаPL"`.
- Параметры запроса (`&Организация`, `&ХозяйственнаяОперация`, …) ставятся в `ЗаполнитьПараметрыИнициализации`
  (~стр. 1512) циклом по колонкам запроса реквизитов: `Запрос.УстановитьПараметр(Колонка.Имя, Реквизиты[Колонка.Имя])`.
  → добавив вычисляемую колонку `ФормаPL` в этот запрос, получим **авто-параметр `&ФормаPL`**.

> ⚠️ `ФормаPL` — измерение, но `ВтИсходныеПрочиеРасходы` РКО **не агрегируется**, поэтому никакого GROUP BY-риска
> (в отличие от ОЗФУ) нет. ВТ РКО-специфична → общие ВТ и другие потребители не затрагиваются. Конструктор регистра
> не меняется (он уже умеет `ДополнительныеПоля`; подставит `,Строки.ФормаPL` в 3 ветки финала).

## 6. Блок правок BSL (`Documents/РасходныйКассовыйОрдер/Ext/ManagerModule.bsl`)

> Перед BSL — Python COM тест (Rule #-1), см. §8. Точные номера строк сверить на актуальном файле.

### 6.1 Запрос реквизитов `ЗаполнитьПараметрыИнициализации` (~стр. 1516-1597): добавить вычисляемую `ФормаPL`
В SELECT (рядом с `ДанныеДокумента.Ссылка КАК Ссылка`, ~стр. 1589) добавить колонку:
```sql
|	ВЫБОР
|		КОГДА ДанныеДокумента.А_ОрганизацияБухгалтерия <> ЗНАЧЕНИЕ(Справочник.Организации.ПустаяСсылка)
|			ТОГДА ЗНАЧЕНИЕ(Перечисление.А_ФормыPL.Форма1)
|		ИНАЧЕ ЗНАЧЕНИЕ(Перечисление.А_ФормыPL.Форма2)
|	КОНЕЦ КАК ФормаPL,
```
Цикл `Для Каждого Колонка Из Результат.Колонки` (~стр. 1603-1605) сам создаст параметр **`&ФормаPL`**.
> Правило в одном месте (запрос реквизитов). Альтернатива: добавить колонку `А_ОрганизацияБухгалтерия` → авто-параметр
> `&А_ОрганизацияБухгалтерия`, а CASE сделать в `ВтИсходныеПрочиеРасходы`. Рекомендуется первый вариант (чище).

### 6.2 `ВтИсходныеПрочиеРасходы` (~стр. 4598-4599): добавить колонку `ФормаPL`
В SELECT (например после `НЕОПРЕДЕЛЕНО КАК АналитикаУчетаНоменклатуры`) добавить:
```sql
|	,&ФормаPL КАК ФормаPL
```

### 6.3 Вызовы хелпера регистра: передать `"ФормаPL"`
- ~стр. 4627: `…ТекстЗапросаТаблицаВтПрочиеРасходы()` → `…ТекстЗапросаТаблицаВтПрочиеРасходы("ФормаPL")`
- ~стр. 3069: `…ТекстЗапросаТаблицаПрочиеРасходы()` → `…ТекстЗапросаТаблицаПрочиеРасходы("ФормаPL")`

### 6.4 Чего НЕ делать
- НЕ менять конструктор регистра `AccumulationRegisters/ПрочиеРасходы/Ext/ManagerModule.bsl`.
- НЕ трогать прочие ХозОп РКО, расчёт сумм, `А_ФинРез_PL`.

## 7. Инварианты (что нельзя сломать)

1. **Σ-инвариант:** `Σ Сумма/СуммаУпр/СуммаРегл` движений `ПрочиеРасходы` по РКО == эталон ДО правки, до копейки.
   Меняется только значение измерения `ФормаPL` (Ф1 **или** Ф2 на весь РКО — она header-level). Число движений
   **не меняется** (в отличие от ОЗФУ: тут разрез не дробит строки — у одного РКО одна форма).
2. **`ФормаPL` header-level:** все движения `ПрочиеРасходы` одного РКО получают одну форму (по его `А_ОрганизацияБухгалтерия`).
3. **Кросс-орг ветки** финала (`Сторнирование`/`Регистрация РасходовУУ`) получают `ФормаPL` автоматически (3 маркера).
4. **Перепроведение РКО через COM — надёжно** (≠ ОЗФУ; ≠ РСППС новой архитектуры) → смоук можно гонять через
   `obj.Записать(РежимЗаписиДокумента.Проведение)`. Массовую историю всё равно перепроводит пользователь (UI),
   автономно не запускать (memory `feedback_user_reposts_history_self`).
