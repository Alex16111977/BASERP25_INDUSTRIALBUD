# PROMPT — заполнение измерения `ФормаPL` в движениях `РегистрНакопления.ПрочиеРасходы` при проведении ОЗФУ

> **Документ-источник:** `Документ.ОтражениеЗарплатыВФинансовомУчете` (ОЗФУ), база **BaseERP**.
> **Файл кода:** `Documents/ОтражениеЗарплатыВФинансовомУчете/Ext/ManagerModule.bsl`.
> **Регистр-приёмник:** `РегистрНакопления.ПрочиеРасходы`, измерение **`ФормаPL`** (`ПеречислениеСсылка.А_ФормыPL` = {Форма1, Форма2}).
> **Образец:** заполнение `ФормаPL` в `РегистрНакопления.А_ВзаиморасчетыССотрудниками` из тех же ТЧ ОЗФУ.
> **Статус:** дизайн согласован через `/superpowers:brainstorming` (Фаза 1 — **только ОЗФУ**; `А_ФинРез_PL`/свёртку/отчёт **НЕ трогаем**).
> **База знаний:** `_Rarzrabotki/notebook/knowledge_ПрочиеРасходы/` (читать ПЕРЕД работой).

---

## 1. Цель (что делаем)

Заполнять измерение **`ФормаPL`** (Форма1/Форма2) в движениях регистра `ПрочиеРасходы` при проведении документа **ОЗФУ**, беря значение из табличных частей ОЗФУ (там `ФормаPL` уже размечена во **всех ТЧ** — этап `17_formapl_split`).

Сейчас движения `ПрочиеРасходы` по ОЗФУ пишутся **с пустой `ФормаPL`** (измерение добавлено в метаданные, но ни один регистратор его не заполняет). После доработки движения ЗП-расходов получат `ФормаPL ∈ {Форма1, Форма2}`, при этом **суммы движений не меняются**.

---

## 2. Зачем (контекст — НЕ часть этой задачи)

Это фундамент для будущего разреза факта PL по формам учёта: чтобы потом (отдельная фаза) `Документ.А_ФинРез_PL` смог разнести факт в ресурсы `СуммаФ1`/`СуммаФ2` свода `А_ОтчетPL_Свод` и в `Отчет.А_ОтчетPL` факт сошёлся с планом `Документ.А_ОтчетPL` (план уже разбит на Ф1/Ф2: `СуммаФома1`/`СуммаФорма2`).

> ⛔ **В ЭТОЙ задаче `А_ФинРез_PL`, свёртку `А_ОтчетPL_Свод` и отчёт `А_ОтчетPL` НЕ трогаем.** Только заполнение измерения `ФормаPL` в движениях регистра при проведении ОЗФУ. Разнос факта Ф1/Ф2 в свёртке — следующая фаза (см. [formapl_roadmap.md](formapl_roadmap.md) Этап 2).

## 4. Образец: как `ФормаPL` наполняется в `А_ВзаиморасчетыССотрудниками`

Файл: `AccumulationRegisters/А_ВзаиморасчетыССотрудниками/Ext/ManagerModule.bsl`, процедура `ЗаполнитьИзОтраженияЗП`.

Логика (концептуальный образец):
1. Читает `ФормаPL` **прямо из ТЧ ОЗФУ**: `НачисленнаяЗарплатаИВзносыПоФизлицам.ФормаPL`, `НачисленныйНДФЛ.ФормаPL`, `УдержаннаяЗарплата.ФормаPL` (строки ~103, 120, 134).
2. **Группирует по `ФормаPL`** в свёртке `втСтроки` (`СГРУППИРОВАТЬ ПО … С.ФормаPL`, строка ~166).
3. Пишет в движение: `Запись.ФормаPL = СтрТЗ.ФормаPL` (строка ~180).
4. В ветках-регистраторах без формы — дефолт `Перечисления.А_ФормыPL.Форма1` (строка ~262).

> ⚠️ **Механизм наполнения `ПрочиеРасходы` ДРУГОЙ** (типовой регистр через цепочку ВТ + `ДополнительныеПоля`, а не прямой `Движения.Добавить()` как в `А_ВзСС`). Образец `А_ВзСС` берём только как **семантику** (откуда брать `ФормаPL`, что группировать, дефолт Форма1). Техническая реализация — §5–6.

## 5. Механизм для `ПрочиеРасходы` (ключевой раздел)

`ПрочиеРасходы` — **типовой** регистр. ОЗФУ наполняет его движения через **цепочку временных таблиц** в своём ManagerModule, а финальные движения собирает **общий конструктор регистра** с параметром `ДополнительныеПоля` (см. [register_structure.md §5](register_structure.md)).

### 5.1 Главный принцип: `ФормаPL` идёт по «следу» `ФизическоеЛицо`

Кастомный реквизит `А_ФизическоеЛицо` **уже** протащен по всей цепочке (прецедент 2026-05). `ФормаPL` нужно добавить **ровно туда же, где сейчас фигурирует `ФизическоеЛицо`** — путь уже проложен и проверен.

Цепочка ВТ для движений `ПрочиеРасходы` от ОЗФУ:
```
ТЧ ОЗФУ (НачисленнаяЗарплатаИВзносы свод / НачисленнаяЗарплатаИВзносыПоФизлицам детально)  [ФормаPL есть]
   ↓  Функция ТекстЗапросаТаблицаНачисленнаяЗарплатаИВзносы
ВТТаблицаДокумента            (~стр. 2431–2498, 2 ветки UNION; ФизическоеЛицо: стр.2443/2470)
   ↓
ВТНачисленнаяЗарплатаИВзносы  (ПОМЕСТИТЬ ~стр. 2679, ИЗ ТаблицаДокумента)
   ↓  Функция ТекстЗапросаТаблицаВтИсходныеПрочиеРасходы (~стр. 2991)
ВтИсходныеПрочиеРасходы       (ВТРасходыПоСтатьям.ФизическоеЛицо КАК А_ФизическоеЛицо, стр.3030; GROUP BY стр.3048; fallback стр.3082)
   ↓  ТекстЗапросаТаблицаВтПрочиеРасходы / ТекстЗапросаТаблицаПрочиеРасходы (вызов хелперов регистра с "А_ФизическоеЛицо")
движения РегистрНакопления.ПрочиеРасходы  (измерение ФормаPL)
```

### 5.2 Правило (надёжно и проверяемо)

> **Грепни `ФизическоеЛицо` по функциям ОЗФУ, строящим путь `ПрочиеРасходы`, и в КАЖДОЙ ВТ, где оно есть в `ВЫБРАТЬ` и в `СГРУППИРОВАТЬ ПО`, добавь рядом `ФормаPL`.** В вызовы хелперов регистра добавь `ФормаPL` в список `ДополнительныеПоля`.

⚠️ **`ФормаPL` — ИЗМЕРЕНИЕ** (а `А_ФизическоеЛицо` — реквизит), но механизм `ДополнительныеПоля` одинаков (подстановка `,Строки.ФормаPL`). КРИТИЧНО: `ФормаPL` должна быть в **`СГРУППИРОВАТЬ ПО`** каждой агрегирующей ВТ — иначе строки Ф1 и Ф2 свернутся в одну и разрез потеряется.

## 6. Блок правок BSL (`Documents/ОтражениеЗарплатыВФинансовомУчете/Ext/ManagerModule.bsl`)

> Перед каждым шагом — Python COM проверка соответствующей ВТ (Rule #-1). Точные номера строк сверить на актуальном файле (могут сместиться).

### 6.1 `ВТТаблицаДокумента` (~стр. 2431–2498) — 2 ветки UNION
- **Ветка «свод»** (из `Документ.…НачисленнаяЗарплатаИВзносы`, ~стр. 2431–2453): добавить в `ВЫБРАТЬ` поле `ЗарплатаСводно.ФормаPL КАК ФормаPL`.
- **Ветка «детально»** (из `…НачисленнаяЗарплатаИВзносыПоФизлицам`, ~стр. 2457–2498): добавить `ЗарплатаДетально.ФормаPL КАК ФормаPL` в `ВЫБРАТЬ` **и** `ЗарплатаДетально.ФормаPL` в `СГРУППИРОВАТЬ ПО`.
- ⚠️ Проверить, что у обеих ТЧ реально есть реквизит `ФормаPL` (этап 17_formapl_split — да). Если у свода нет — дефолт `ЗНАЧЕНИЕ(Перечисление.А_ФормыPL.Форма1) КАК ФормаPL`.

### 6.2 `ВТНачисленнаяЗарплатаИВзносы` (ПОМЕСТИТЬ ~стр. 2679, ИЗ `ТаблицаДокумента`)
- Добавить `ВТНачисленнаяЗарплатаИВзносы.ФормаPL` (точнее — поле из источника `ТаблицаДокумента`) в `ВЫБРАТЬ`; если есть `СГРУППИРОВАТЬ ПО` — добавить и туда. Брать за образец, как здесь же протащено `ФизическоеЛицо`.
- Если между `ВТТаблицаДокумента` и `ВТНачисленнаяЗарплатаИВзносы` есть промежуточная ВТ (`ТаблицаДокумента` и др.) — протащить `ФормаPL` и через неё (везде по следу `ФизическоеЛицо`).

### 6.3 `ВтИсходныеПрочиеРасходы` (функция `ТекстЗапросаТаблицаВтИсходныеПрочиеРасходы`, ~стр. 2991)
- **Основная ветка** (из `ВТНачисленнаяЗарплатаИВзносы`, рядом со стр. 3030 `… КАК А_ФизическоеЛицо`): добавить `ВТРасходыПоСтатьям.ФормаPL КАК ФормаPL`.
- **`СГРУППИРОВАТЬ ПО`** (рядом со стр. 3048): добавить `ВТРасходыПоСтатьям.ФормаPL`.
- **Ветка «выработка по прочим работам»** (рядом со стр. 3082 `… ПустаяСсылка … КАК А_ФизическоеЛицо`): добавить `ЗНАЧЕНИЕ(Перечисление.А_ФормыPL.Форма1) КАК ФормаPL` (дефолт).

### 6.4 Вызовы хелперов регистра (~стр. 3112 и 3130)
```bsl
// БЫЛО:
ТекстЗапроса = РегистрыНакопления.ПрочиеРасходы.ТекстЗапросаТаблицаВтПрочиеРасходы("А_ФизическоеЛицо");
...
ТекстЗапроса = РегистрыНакопления.ПрочиеРасходы.ТекстЗапросаТаблицаПрочиеРасходы("А_ФизическоеЛицо");
// СТАЛО:
ТекстЗапроса = РегистрыНакопления.ПрочиеРасходы.ТекстЗапросаТаблицаВтПрочиеРасходы("А_ФизическоеЛицо,ФормаPL");
...
ТекстЗапроса = РегистрыНакопления.ПрочиеРасходы.ТекстЗапросаТаблицаПрочиеРасходы("А_ФизическоеЛицо,ФормаPL");
```
> Хелпер `ДобавитьДополнительныеПоляВТекстЗапроса` сам подставит `,Строки.ФормаPL` во все 3 маркера финального запроса (основная ветка + `СторнированиеРасходовУУ` + `РегистрацияРасходовУУ`) → `ФормаPL` сохранится и при кросс-орг перераспределении.

### 6.5 Чего НЕ делать
- НЕ менять конструктор регистра `AccumulationRegisters/ПрочиеРасходы/Ext/ManagerModule.bsl` (он уже поддерживает `ДополнительныеПоля` — достаточно передать имя поля).
- НЕ трогать расчёт сумм/вариантов распределения, международный учёт, обработчики обновления.
- НЕ трогать `А_ФинРез_PL`, свёртку, отчёт.

## 7. Инварианты (что нельзя сломать) — см. [architecture_invariants.md](architecture_invariants.md)

1. **Σ-инвариант:** `Σ Сумма` (и `СуммаУпр`/`СуммаРегл`) движений `ПрочиеРасходы` по (период, организация) **== эталон ДО правки**, до копейки. Меняется только разбивка по `ФормаPL`; число строк движений может вырасти (Ф1/Ф2 раздельно) — как было с `А_ФизическоеЛицо` (156→843 строк, Σ неизменна).
2. **`ФормаPL` в `СГРУППИРОВАТЬ ПО`** каждой агрегирующей ВТ — иначе Ф1/Ф2 свернутся.
3. **Дефолт `Форма1`** для строк без формы (не оставлять пустую ссылку у измерения).
4. **Кросс-орг ветки** (`Сторнирование`/`Регистрация РасходовУУ`) получают `ФормаPL` автоматически через 3 маркера — не убирать маркеры.
5. **Перепроведение ОЗФУ — только через UI** (COM пере-создание ОЗФУ подваивает ТЧ — см. [../knowledge_А_ОтражениеЗПпоКазне/17_formapl_split.md](../knowledge_А_ОтражениеЗПпоКазне/17_formapl_split.md) §6). Массовое перепроведение истории — пользователь сам в UI (memory `feedback_user_reposts_history_self`).
