# Архитектура и инварианты `РегистрНакопления.ПрочиеРасходы`

> Тип файла: ПОСТОЯННЫЙ (правила архитектуры — не менять без согласования с финансистом).
> Грабли/находки добавлять в §6.
>
> Назначение файла: зафиксировать, **что нельзя сломать** при доработках реквизитов регистра
> (в первую очередь при внедрении `ФормаPL`). Каждый инвариант = потенциальный регресс, если нарушить.

## 1. Базовый принцип: типовой регистр, расширяем — не переписываем

`ПрочиеРасходы` — **типовой** регистр, который наполняют **129 типовых документов** через их штатное
`ОбработкаПроведения`. Мы НЕ пишем для него код наполнения «с нуля» (в отличие от кастомного
`А_ВзаиморасчетыССотрудниками`).

**Разрешённый способ расширения** — добавить новое измерение/реквизит в XML + протащить его через механизм
`ДополнительныеПоля` ManagerModule (см. [register_structure.md §5](register_structure.md)) ТОЛЬКО в тех
документах-регистраторах, где значение реально нужно. Прецедент — `А_ФизическоеЛицо` (только в ОЗФУ).

**Запрещено:**
- ❌ менять/удалять типовые измерения, ресурсы, реквизиты;
- ❌ менять логику расчёта сумм в `ТекстЗапросаТаблицаВтПрочиеРасходы` (варианты распределения, НДС);
- ❌ трогать функции международного учёта и обработчики обновления ИБ;
- ❌ массово править все 129 регистраторов «на всякий случай» — только нужные.

## 2. ⚠️ ГЛАВНАЯ грабля: измерение vs реквизит в `.Обороты()`

**Измерения** регистра доступны в виртуальной таблице `РегистрНакопления.ПрочиеРасходы.Обороты(...)`.
**Реквизиты** — НЕТ (только в прямой таблице регистра).

| Поле | Тип в регистре | Доступно в `.Обороты()` |
|---|---|---|
| `ФормаPL` | **измерение** | ✅ ДА |
| `А_ФизическоеЛицо` | **реквизит** | ❌ НЕТ |
| `Организация`, `Подразделение`, `СтатьяРасходов`, `НаправлениеДеятельности`, `НалоговоеНазначение`, `АналитикаРасходов` | измерения | ✅ ДА |

Именно поэтому `ФормаPL` сделана **измерением**: потребитель `А_ФинРез_PL` читает регистр через `.Обороты`
(см. [consumers_pl_chain.md](consumers_pl_chain.md)), и `ФормаPL` будет доступна без перехода на прямую таблицу.

### 2.1 Реальный регресс из-за этой граблиː 2026-05-21 (отчёт А_ОтчетPL)

Когда в отчёт `Отчет.А_ОтчетPL` понадобился реквизит `А_ФизическоеЛицо` (drill-down по ФЛ), источник в CTE
`втЕРП_Расх_Детали` переключили с `.Обороты` на **прямую таблицу** регистра (иначе реквизит недоступен).
При этом формулу суммы по ошибке заменили:

```sql
-- БЫЛО (виртуальная .Обороты, эквивалент СуммаПриход):
СУММА(Р.СуммаПриход) КАК СуммаЕРП
-- СТАЛО (регрессивно — чистый оборот):
СУММА(ВЫБОР КОГДА Р.ВидДвижения = Приход ТОГДА Р.Сумма ИНАЧЕ -Р.Сумма КОНЕЦ) КАК СуммаЕРП
```

Для подразделений с механизмом `РаспределениеПрочихЗатрат` (каждый Приход X имеет парный Расход X) чистый
оборот = **0** → факты пропали из отчёта («Астарта. Тищенки», март 2026: Σ Приход 505 868,05, Σ Расход 505 868,05,
Σ оборот = 0). **Фикс:** вернули `СУММА(Р.Сумма)` + `ГДЕ Р.ВидДвижения = Приход`. Подробно: 
[../knowledge_PL/pl_report_architecture_analyst.md](../knowledge_PL/pl_report_architecture_analyst.md) §«Грабелька 2026-05-21».

**Урок для `ФормаPL`:** поскольку `ФормаPL` — измерение, **переход на прямую таблицу не нужен** —
читать можно из `.Обороты` (`СуммаПриход` остаётся корректной). Это и есть причина выбора «измерение».

## 3. ⚠️ Инвариант сумм для P&L: `СуммаПриход`, НЕ оборот

Для P&L (`А_ФинРез_PL`, `Отчет.А_ОтчетPL`) факт расхода = **первичный объём** = `Обороты.СуммаПриход`
(метод начисления). Записи `Расход` — это внутреннее перераспределение (`РаспределениеПрочихЗатрат`,
кросс-орг сторно), которое **не должно** уменьшать факт подразделения-донора в P&L.

Семантика виртуальной таблицы (платформа 1С):
- `.Обороты.СуммаПриход` = Σ `Сумма` по движениям `ВидДвижения=Приход`;
- `.Обороты.СуммаРасход` = Σ `Сумма` по `ВидДвижения=Расход` (НЕ `−Сумма`!);
- `.Обороты.СуммаОборот` = `СуммаПриход − СуммаРасход`.

**Правило:** для PL берём `СуммаПриход`. Любая правка, меняющая это на оборот, — регресс (см. §2.1).

## 4. ⚠️ `РаспределениеПрочихЗатрат` — пары донор/получатель

Документ `РаспределениеПрочихЗатрат` (закрытие месяца) перераспределяет расходы между подразделениями/
организациями: первичному `Приход X` соответствует парный `Расход X` (+ запись у получателя). Это же делают
ветки `СторнированиеРасходовУУ` / `РегистрацияРасходовУУ` финального запроса (см. [register_structure.md §5.2](register_structure.md)).

**Следствия:**
- Σ оборот по донору может быть 0 при ненулевом Σ Приход (см. §2.1).
- При добавлении `ФормаPL` в `ДополнительныеПоля` оно автоматически протащится во все 3 ветки → `ФормаPL`
  сохранится и у получателя/сторно (правильно). НЕ убирать маркеры из веток.
- `ДокументДвижения` (реквизит, тип `РаспределениеПрочихЗатрат`) указывает на документ-распределитель.

## 5. ⚠️ Идемпотентность и перепроведение

- Перепроведение документа-регистратора стандартно удаляет его старые движения по ВСЕМ регистрам (включая
  `ПрочиеРасходы`) и пишет новые — идемпотентно.
- **COM-перепроведение** движений `ПрочиеРасходы` надёжно (в отличие от взаиморасчётов новой архитектуры РСППС).
  НО для ОЗФУ есть отдельная ловушка: **пере-создание ОЗФУ через COM ПОДВАИВАЕТ ТЧ** — см.
  [../knowledge_А_ОтражениеЗПпоКазне/17_formapl_split.md](../knowledge_А_ОтражениеЗПпоКазне/17_formapl_split.md) §6.
  Перепроводить ОЗФУ — только через UI-кнопку.
- **Массовое перепроведение боевых документов НЕ запускать автономно** (memory `feedback_user_reposts_history_self`):
  код + проверка на 1–2 документах, остальную историю пользователь перепроводит сам в UI.

## 6. ⚠️ Σ-инвариант при добавлении аналитики (главный критерий «не сломал»)

Добавление измерения/реквизита в движения **НЕ должно менять суммы** регистра. Прецедент `А_ФизическоеЛицо`
(ОЗФУ): движений стало больше (детализация 156→843 строк на 1 ОЗП), но `Σ Сумма` неизменна (= 7 581 561,27 ₽
на тестовом документе; перепроведено 2024–2026 Q1, 4067/4067 движений получили ФЛ).

**Для `ФормаPL` тот же критерий:** после заполнения `ФормаPL` в регистраторе
`Σ Сумма (и СуммаУпр/СуммаРегл) по периоду/организации = эталон ДО правки`, до копейки. Только разбивка по
`ФормаPL` появляется внутри той же суммы. См. [tests_and_etalons.md](tests_and_etalons.md).

> Тонкость дробления: если `ФормаPL` добавляется в `СГРУППИРОВАТЬ ПО` ВТ-источника, строки с разными `ФормаPL`
> перестают сворачиваться → их станет больше, но Σ та же. Если одна (Орг,Подр,Статья,…) имеет и Ф1, и Ф2 —
> получим 2 строки вместо 1 (это и есть цель).

## 7. Грабли (находки)

### 7.1 COM не резолвит `Метаданные…Регистраторы`
`md.Регистраторы` через `V83.COMConnector` падает (`AttributeError`). Список регистраторов получать **grep'ом**
по `AccumulationRegister.ПрочиеРасходы<` в `Documents/*.xml` (дал 129) либо в Конфигураторе.

### 7.2 `ФормаPL`: заполнение (Этапы 1 DONE) + чтение в `А_ФинРез_PL` (Этап 2 DONE)
На 2026-06-08 реализован Этап 1: движения `ПрочиеРасходы` получают `ФормаPL` (Ф1/Ф2) — ОЗФУ
([formapl_ozfu_done.md](formapl_ozfu_done.md)) + РаспределениеПрочихЗатрат/register-дефолт пусто→Форма1
([formapl_ostalnye_done.md](formapl_ostalnye_done.md)). На 2026-06-09 — Этап 2: `А_ФинРез_PL` **читает**
`ФормаPL` из `.Обороты` и пишет разрез Ф1/Ф2 в `А_ОтчетPL_Свод` ([formapl_finrez_done.md](formapl_finrez_done.md);
пусто→Форма1, доход/CoGS→Форма1, факт-расход по реальной форме; Σ Сумма сохранён, Δ=0,00).
⚠️ Существующие движения остаются с прежней `ФормаPL`/свёрткой до **перепроведения** (новый код активен, но
данные перестраиваются только при перепроведении). ОЗФУ перепроводить только в UI (COM задваивает ТЧ);
`А_ФинРез_PL` — COM надёжно, но боевую историю (28 док-тов) массово перепроводит пользователь.

### 7.5 Добавление измерения в `СГРУППИРОВАТЬ ПО` ОБЩЕЙ ВТ — безопасно при re-aggregate потребителей
`ФормаPL` добавлен в GROUP BY общих ВТ `ВТТаблицаДокумента`/`ВТНачисленнаяЗарплатаИВзносы` (у последней **8
потребителей**). Это повышает гранулярность (строка ФЛ может разделиться на Ф1+Ф2). **Это НЕ ломает другие
движения**, потому что все прочие 7 потребителей агрегируют (`СУММА(Сумма)`) и группируют по своим ключам
**без `ФормаPL`** → разбивка схлопывается обратно → их вывод неизменен. Разрез сохраняется только в
`ВтИсходныеПрочиеРасходы` (который ЕДИНСТВЕННЫЙ выбирает `ФормаPL`). Проверено по коду (строки потребителей
2094/3192/3357/3547/3887/3915/3991). **Правило:** перед добавлением поля в GROUP BY общей ВТ — проверить КАЖДОГО
потребителя (агрегирует/схлопывает? или пишет 1:1 → риск задвоения/дубля ключа). См. [formapl_ozfu_done.md §3](formapl_ozfu_done.md).

### 7.3 Дубли ключа в `А_ОтчетPL_Свод` при `Комментарий` в `СГРУППИРОВАТЬ ПО`
В `А_ФинРез_PL` нельзя класть реквизит `Комментарий` в группировку ключа Свода (12+ измерений) — даёт
«Запись с такими ключевыми полями существует». Оборачивать `МАКСИМУМ(...)`. См.
[../knowledge_PL/pl_report_architecture_analyst.md](../knowledge_PL/pl_report_architecture_analyst.md).

### 7.4 Конфигуратор блокирует `/db-load-xml`
При открытом Конфигураторе загрузка XML падает с «Ошибка блокировки информационной базы». Не обходить вручную —
попросить закрыть Конфигуратор. После `cp` .bsl в основную конфигурацию — обновлять `ConfigDumpInfo.xml` или
грузить через `/db-load-xml` + `/db-update -Dynamic+` (memory `feedback_use_db_skills_for_config_load`).

### 7.6 РаспределениеПрочихЗатрат: движения пишет ТОЛЬКО закрытие месяца + нетто-двойной-счёт (2026-06-08)
При внедрении `ФормаPL` в `РаспределениеПрочихЗатрат` обнаружено (подробно [formapl_ostalnye_done.md §2](formapl_ostalnye_done.md)):
- Движения `ПрочиеРасходы` пишет **регламентная операция закрытия** «Распределение расходов по направлениям
  деятельности» (`Выполнить_РаспределениеРасходовПоНаправлениямДеятельности` → `РаспределитьРасходыНаФинансовыйРезультат`
  в режиме записи), а **НЕ проведение документа** (его обработчик `ПрочиеРасходы` не пишет — пустой).
- Добавление `ФормаPL` в чтение `.Остатки` **разворачивает** нулевой нетто-остаток в ненулевые строки по формам →
  обнажает латентный двойной счёт текущего документа (branch2 + branch3, замаскирован `Остатки.Сумма=0→0`). Фикс:
  исключить текущий документ из branch2 в предв.режиме — `И НЕ(&ПредварительныйРасчет И ТекущиеДвижения.Регистратор = &ДокументРаспределения)`.
- Динамическое обновление `-Dynamic+` **не доходит до открытых сеансов** — закрытие выполняется на старом коде до
  полного перезахода 1С (грабля `feedback_designer_cache_invalidation`); свежее COM-соединение видит правку.
