## 1. Цель и scope

Заполнить измерение `ФормаPL` (`EnumRef.А_ФормыPL` = {Форма1, Форма2}) во **ВСЕХ** движениях
`РегистрНакопления.ПрочиеРасходы`, чтобы ни одно движение не осталось без формы. ОЗФУ (Этап 1) и РКО (Этап 3) уже
ставят форму сами и **не трогаются**.

| В scope | Вне scope |
|---|---|
| Часть A: `РаспределениеПрочихЗатрат` наследует `ФормаPL` из остатков | Чтение `ФормаPL` в `А_ФинРез_PL` (Этап 2) |
| Часть B: register-level дефолт пустая `ФормаPL` → `Форма1` | Свёртка `А_ОтчетPL_Свод`, отчёт, OLAP/PBIX |
| Rule #-1 проверка + smoke на 1–2 доках | Массовое перепроведение истории (делает пользователь в UI) |

**Решение заказчика по объёму сессии (2026-06-08):** сначала Часть A (`РаспределениеПрочихЗатрат`) →
протестировать через Rule #-1 → **если всё ОК**, переходить к Части B (`RecordSetModule.ПередЗаписью`).

## 2. Архитектура: 2 части, строгий порядок A → B

```
Часть A (ПЕРВОЙ): РаспределениеПрочихЗатрат протягивает ФормаPL по цепочке остатки→распределение→движения,
                  закрывающий Расход получает форму ИСХОДНОЙ затраты (Ф1→Ф1, Ф2→Ф2).
Часть B (ПОТОМ):  RecordSetModule.ПередЗаписью — пустая ФормаPL → Форма1 (для всех прочих регистраторов).
```

**Почему A раньше B.** Часть B — бланкетный дефолт «пусто→Форма1» на уровне записи набора. Если сделать только B,
то закрывающие `Расход`-движения `РаспределениеПрочихЗатрат` (у которых форма пустая) получат `Форма1`, даже если
исходная затрата была `Форма2` → у донора `Ф2` останется незакрытый приход, у `Ф1` появится сирота-расход →
баланс по форме «поедет». Поэтому `РаспределениеПрочихЗатрат` сперва учим наследовать форму самому (Часть A) —
тогда у его движений `ФормаPL` уже заполнена и дефолт Части B их не трогает (`ЗначениеЗаполнено` = Истина).

**Факт из БД (2026-06-08):** все **2052** движения `РаспределениеПрочихЗатрат` — это `Расход` (ΣПриход = 0). P&L
берёт `СуммаПриход`, значит на факт P&L они сегодня **не влияют**. Часть A нужна для (а) целостности баланса по
форме, (б) корректности повторных распределений (читают `Остатки` по форме), (в) будущего Этапа 2.

### 3.2 Путь погрешности округления (⚠️ ГЛАВНЫЙ РИСК — нет в §4 промта)

Погрешность округления считается как разница (Σ к распределению − Σ распределённого) и добавляется отдельным
движением. Сейчас агрегируется по `Регистратор, НалоговоеНазначение` **без `ФормаPL`**. Если не протянуть форму —
копеечная погрешность ляжет в `Форма1` мимо своей формы → per-form баланс не закроется (TOL 0.01 может упасть).

| # | ВТ / место | Anchor (стр.) | Правка |
|---|---|---|---|
| 11 | `ПогрешностиОкругления`, SELECT + 2 ветки UNION + GROUP BY | 776–842 | + `ФормаPL` в внешний SELECT (786-787), в обе ветки (`РасходыКРаспределению.ФормаPL` 790-801, `РаспределенныеРасходы.ФормаPL` 809-820) и в СГРУППИРОВАТЬ ПО (824) |

### 3.3 Запись движений — авто-перенос формы (правок НЕ требует)

- Основной цикл записи: `НоваяЗапись = ПрочиеРасходы.Добавить(); ЗаполнитьЗначенияСвойств(НоваяЗапись, ВыборкаДетальная);`
  ([1160-1161](../../Documents/РаспределениеПрочихЗатрат/Ext/ManagerModule.bsl)). `ЗаполнитьЗначенияСвойств`
  копирует одноимённые свойства → **`ФормаPL` скопируется автоматически**, если она есть в `ВыборкаДетальная`
  (= `РезультатРаспределения`). Имя колонки обязано быть ровно `ФормаPL`.
- Перенос существующих не-распределительных движений (1206-1210) идёт через `ПрочиеРасходы.*` (932) →
  `ФормаPL` подхватится **без правок**.

### 3.4 Чего в Части A НЕ трогаем

- `РегистраторыКОчисткеДвижений` (852), `РаспределенныеАналитикиРасходов` (897) — идентифицируют (Орг,Подр,Статья,
  Аналитика) для очистки, форм-агностичны (чистим все формы dim-комбо — корректно). `ФормаPL` НЕ нужен.
- Конструктор регистра `AccumulationRegisters/ПрочиеРасходы/Ext/ManagerModule.bsl` — НЕ меняем.
- Логику сумм/коэффициентов/округления — НЕ меняем (только добавляем измерение-спутник).

## 4. Часть A — стратегия проверки (Rule #-1, ПЕРЕД любым BSL)

По образцу `verify_formapl_prochie_chain.py` (Этап 1): собрать **полную модифицированную цепочку** ВТ в Python COM
на BaseERP и исполнить на **1 реальном** `РаспределениеПрочихЗатрат` (с непустым распределением), БЕЗ перепроведения.

Критерии (acceptance):
1. **Σ-инвариант:** Σ по каждому ресурсу (Сумма/СуммаУпр/СуммаРегл/…) движений `ПрочиеРасходы` распределителя ==
   эталон ДО правок, до копейки.
2. **Закрытие баланса по форме:** для каждой формы Σ(закрывающий Расход по форме) == Σ(исходный приход по форме);
   нет «зависших» Ф2→Ф1 (главный смысл Части A). Проверять с TOL 0.01 — особое внимание погрешности округления (§3.2).
3. **Число/структура движений** соответствует ожидаемому (форма как спутник дробит строку только если у dim-комбо
   есть и Ф1, и Ф2).

Только при зелёных 1–3 → переносить правки в BSL, `cp` в основную конфигурацию, `/db-load-xml` + `/db-update`.
Затем smoke: перепровести 1 `РаспределениеПрочихЗатрат` (COM для этого документа допустим — это не ОЗФУ и не РСППС;
подтвердить отдельно) и сверить движения. Массовую историю — пользователь в UI (§6).

## 5. Часть B — register-level дефолт (только после зелёной Части A)

**Файл:** `AccumulationRegisters/ПрочиеРасходы/Ext/RecordSetModule.bsl`, в начало `Процедура ПередЗаписью(Отказ, Замещение)`
(ПЕРЕД `Если ОбменДанными.Загрузка … Возврат`, чтобы дефолт срабатывал на ЛЮБОМ пути записи):

```bsl
Процедура ПередЗаписью(Отказ, Замещение)

	// А_ФормаPL: дефолт формы учёта. Движения, которым документ-регистратор не задал ФормаPL явно
	// (ОЗФУ/РКО/РаспределениеПрочихЗатрат ставят сами), считаем официальной затратой → Форма1.
	Для Каждого Запись Из ЭтотОбъект Цикл
		Если НЕ ЗначениеЗаполнено(Запись.ФормаPL) Тогда
			Запись.ФормаPL = Перечисления.А_ФормыPL.Форма1;
		КонецЕсли;
	КонецЦикла;

	Если ОбменДанными.Загрузка
		Или РасчетСебестоимостиПрикладныеАлгоритмы.ДвиженияЗаписываютсяРасчетомПартийИСебестоимости(ЭтотОбъект) Тогда
		Возврат;
	КонецЕсли;
	// … далее существующий код без изменений …
```

Остальной код `ПередЗаписью`/`ПриЗаписи` (контроль изменений для расчёта себестоимости, GROUP BY без `ФормаPL`) —
**НЕ менять**: дефолт на него не влияет, он агрегирует по своим измерениям.

> Проверка Части B тривиальна (цикл по набору): smoke — перепровести 1 «прочий» документ (ПриобретениеТоваровУслуг
> или СписаниеНедостач) → его движения `ПрочиеРасходы` = `Форма1`, Σ неизменна; перепровести 1 ОЗФУ/РКО → формы
> сохранены (Ф1/Ф2 не затёрты).

## 6. Инварианты (что нельзя сломать)

1. **Σ не меняется** ни по одному ресурсу — добавляется только значение измерения.
2. **ОЗФУ/РКО не трогаются** — приходят с заполненной `ФормаPL` → дефолт пропускает.
3. **Балансовая целостность распределения** — закрывающий Расход и исходный приход имеют ОДНУ форму.
4. **Расчёт себестоимости/партий не затронут** — логика `ПриЗаписи`/контроля изменений не меняется.
5. **Порядок перепроведения истории** (пользователь, в UI): сначала источники (Приобретение, СписаниеНедостач,
   ВнутрПотребление, Амортизация, СБДС, АвансовыйОтчёт, ОЗФУ, РКО…), в конце — `РаспределениеПрочихЗатрат`.
   Массово — НЕ автономно (memory `feedback_user_reposts_history_self`).
