## TL;DR

Pipeline `_Rarzrabotki/Python/PnL/` импортує план з Excel у `Документ.А_ОтчетPL` і **автоматично створює нові PL-статті** в `Catalog.А_Статьи_PL`, якщо їх ще немає. Це створює ризик:

1. **Подвоєння через варіанти написання.** Один Excel-лист пише "Штраф", інший — "Штраф/ мат помощь" → у каталозі з'являються 2 статті, плани розбиваються.
2. **Відновлення видаленого.** Фінансист видалив дубль у 1С → при наступному імпорті pipeline створює його знову.

Захист — **3 шари**:

| Шар | Механізм | Файл | Коли спрацьовує |
|---|---|---|---|
| 1. **Алиаси на етапі сборки** | `ARTICLE_NAME_ALIASES` у `config.py` | `scripts/02_extract_unique_articles.py:22` + `scripts/08_prepare_documents.py:81` | Excel-варіант → каноничне імʼя ДО створення статті |
| 2. **Deny-list** | `BLOCKED_ARTICLE_NAMES` у `config.py` | `scripts/11_upload_articles.py:42` (GUARD #0) | Перед `mgr.СоздатьЭлемент()` — навіть якщо алиас не покрив |
| 3. **Manual lock** | `А_РучнаяКорректировка` у самій картці статті 1С | `scripts/11_upload_articles.py:50` | При update існуючої статті — не чіпати, якщо галка стоїть |

Усі три шари незалежні; кожен може **сам** заблокувати небажану операцію.

## Шар 1: Алиаси (ARTICLE_NAME_ALIASES)

### Що робить

Перейменовує **Excel-варіант** статті на **каноничне імʼя** у `Catalog.А_Статьи_PL` на етапі сборки `02_extract_unique_articles.py`. Після цього всі downstream-скрипти (`04_match_articles`, `08_prepare_documents`, `11_upload_articles`) бачать тільки канон.

### Де налаштовується

`_Rarzrabotki/Python/PnL/config.py`:

```python
ARTICLE_NAME_ALIASES = {
    "Арена сторонней техники": "Аренда сторонней техники",
    # 2024-варианты для существующей "Штраф/ мат помощь":
    "Штраф, Материальная помощь": "Штраф/ мат помощь",
    "Штраф/ мат.помощ": "Штраф/ мат помощь",
    # 2026-05-21: финансист пометил на удаление дубль "Штраф" (000000060),
    # все варианты сводим в единую статью "Штраф/ мат помощь" (000000059).
    "Штраф": "Штраф/ мат помощь",
}
```

### Як перевірити що алиас працює

1. Запустити `python scripts/02_extract_unique_articles.py`.
2. Відкрити `data/json/02_unique_articles.json` і шукати alias-варіант. Він НЕ має зʼявитись як окрема стаття (`articles[]`), а має бути серед `variants[]` у відповідної каноничної.
3. `occurrences` каноничної статті = сума occurrences усіх її варіантів.

Приклад верифікації після додавання `"Штраф": "Штраф/ мат помощь"`:
- До: 2 статті в JSON (`"Штраф"` 540 occ + `"Штраф/ мат помощь"` 307 occ).
- Після: 1 стаття (`"Штраф/ мат помощь"` 847 occ).

### Коли використовувати

- Опечатки в Excel: `"Арена сторонней техники"` (без «д»).
- Старі варіанти написання: `"Штраф, Материальная помощь"` → `"Штраф/ мат помощь"`.
- Уніфікація після злиття дублів у 1С.

### Коли НЕ використовувати

- Якщо варіанти **різні бізнесово**: не зливати "Штраф" з "Пеня" — це різні статті.
- Якщо тільки регістр відрізняється — нормалізатор у скрипті `02_extract_unique_articles.py` (utils/names_cleaner.normalize) сам зробить case-insensitive merge. Алиас потрібен тільки при суттєвій різниці (зайва пунктуація, абревіація, опечатка).

## Шар 2: Deny-list (BLOCKED_ARTICLE_NAMES)

### Що робить

Безусловно блокує створення нових статей з вказаним імʼям у Catalog.А_Статьи_PL — навіть якщо алиас не спрацював і ім'я просочилось у `02_unique_articles.json`. Це останній рубіж захисту від відновлення видаленого фінансистом.

### Де налаштовується

`_Rarzrabotki/Python/PnL/config.py`:

```python
# Deny-list имён PL-статей, которые НЕЛЬЗЯ создавать в Catalog.А_Статьи_PL при заливке.
# Используется как защита от случайного восстановления статьи, которую финансист удалил.
# Проверяется в 11_upload_articles.py перед mgr.СоздатьЭлемент().
#
# Сравнение по точному имени (case-insensitive, с обрезкой пробелов).
BLOCKED_ARTICLE_NAMES = {
    "Штраф",  # 2026-05-21 удалена; вместо неё → "Штраф/ мат помощь"
}
```

### Як працює guard у `11_upload_articles.py`

```python
# scripts/11_upload_articles.py (GUARD #0, найвищий пріоритет)
blocked_names = {n.strip().casefold() for n in getattr(config, "BLOCKED_ARTICLE_NAMES", set())}

for a in articles:
    if a["name"].strip().casefold() in blocked_names:
        skipped_blocked += 1
        print(f"  SKIP-BLOCKED {a['name']!r}  (в config.BLOCKED_ARTICLE_NAMES — статья помечена удалённой)")
        continue
    # ... далі стандартна логіка find/create ...
```

Лог в кінці:
```
Done. found=64 created=0 locked=3 skipped_no_dds=2 skipped_blocked=1
```

### Чому це потрібно ДОДАТКОВО до алиаса

| Сценарій | Чи врятує алиас? | Чи врятує deny-list? |
|---|---|---|
| Excel пише "Штраф" → треба перейменувати в "Штраф/ мат помощь" | ✅ так | ✅ так |
| Хтось запустив старий `02_unique_articles.json` без перегенерації після додавання алиаса | ❌ ні | ✅ так |
| Хтось випадково додав статтю "Штраф" вручну у JSON | ❌ ні | ✅ так |
| Алиас прибрали з config.py (відкат), Excel знову пише "Штраф" | ❌ ні | ✅ так (якщо deny-list залишився) |

Алиас — **очищення на вході**, deny-list — **захист на виході**. Обидва шари треба тримати.

### Коли додавати в BLOCKED_ARTICLE_NAMES

- Фінансист **видалив** статтю в 1С (через інтерфейс або скриптом).
- Фінансист **помітив на удаление** і не хоче автоматичного відновлення при наступному імпорті.
- Виявлено дубль і прийнято рішення мерджити в одну канонічну.

При додаванні в deny-list **обов'язково** також додати алиас, щоб Excel-дані не загубились, а перейшли в каноничну статтю.

## Шар 3: А_РучнаяКорректировка (lock на конкретній статті)

### Що робить

Прапор у самій картці `Catalog.А_Статьи_PL` — фінансист ставить вручну в інтерфейсі 1С. Pipeline при оновленні існуючої статті бачить цей прапор → **пропускає update всіх полів** (Группа, ТЧ Статьи, СтатьяДоходов, ТипСтатьи).

### Як перевіряється

`scripts/11_upload_articles.py:50`:
```python
if is_manually_locked(obj):
    a["uuid"] = ref_uuid(conn, obj.Ссылка)
    locked += 1
    print(f"  LOCK {a['name']}  (А_РучнаяКорректировка=Истина — пропущен)")
    continue
```

Функція `is_manually_locked` у `utils/com_connect.py` читає реквізит `А_РучнаяКорректировка` (тип Булево, def. Ложь).

### Коли використовувати

- Фінансист ВРУЧНУ підібрав специфічну ДДС яку fuzzy-алгоритм не знаходить.
- Фінансист змінив групу статті бо так логічніше для бізнесу.
- Фінансист хоче «заморозити» статтю від подальших автоматичних правок.

### Чим відрізняється від deny-list

| Аспект | А_РучнаяКорректировка | BLOCKED_ARTICLE_NAMES |
|---|---|---|
| Призначення | «не чіпай поля існуючої статті» | «не створюй цю статтю заново» |
| Де налаштовується | Картка статті в 1С | config.py |
| Спрацьовує при | Update існуючої | Create нової |
| Видимий фінансисту | Так (галка в інтерфейсі) | Ні (тільки розробник бачить) |

```

2. scripts/02_extract_unique_articles.py
   ├→ применяє ARTICLE_NAME_ALIASES         ← Шар 1
   └→ data/json/02_unique_articles.json
      (унікальні статті після злиття варіантів)

3. scripts/04_match_articles.py + 04b

   └→ data/json/03_groups_pl.json

5. scripts/08_prepare_documents.py
   ├→ применяє ARTICLE_NAME_ALIASES (повторно для надійності) ← Шар 1
   └→ data/json/08_documents_to_import.json

6. scripts/10_upload_groups.py
   └→ Створює групи в 1С

7. scripts/11_upload_articles.py
   ├→ применяє BLOCKED_ARTICLE_NAMES        ← Шар 2
   ├→ применяє А_РучнаяКорректировка        ← Шар 3
   └→ Створює/оновлює статті в 1С

8. scripts/12_upload_documents.py
   └→ Створює документи А_ОтчетPL в 1С

9. scripts/13_fill_rasshifrovka_listov.py
   └→ Створює А_РасшифровкаЛистов
```

### Що робити після правки фінансиста в 1С

Якщо фінансист **видалив статтю** в 1С → потрібно ОБОВ'ЯЗКОВО:

1. Додати ім'я у `BLOCKED_ARTICLE_NAMES` (config.py).
2. Якщо є канонічна заміна — додати алиас у `ARTICLE_NAME_ALIASES`.
3. Перегенерувати JSON-артефакти:
   ```bash
   python scripts/02_extract_unique_articles.py
   python scripts/04_match_articles.py
   python scripts/08_prepare_documents.py
   ```
4. Перевірити що видалене ім'я не залишилось у:
   - `data/json/02_unique_articles.json` (як окрема стаття)
   - `data/json/05_mapping_pl_to_dds.json` (як `pl_name`)
   - `data/json/08_documents_to_import.json` (як `article_name`)

Якщо фінансист **поставив А_РучнаяКорректировка** — нічого не треба робити в config.py, pipeline сам побачить.

## Кейс-стаді: «Штраф» 2026-05-21

### Початковий стан

У Catalog.А_Статьи_PL існувало 2 PL-статті:
- `000000059 "Штраф/ мат помощь"` — основна, з ДДС "Штраф" + "Материальная помощь"
- `000000060 "Штраф"` — старий дубль з 2024 року, з ДДС "Штраф"

В Excel за 2024-2026 використовувались 4 варіанти написання:
- `"Штраф"` — 540 occurrences
- `"Штраф, Материальная помощь"` — кілька occ
- `"Штраф/ мат помощь"` — 307 occurrences
- `"Штраф/ мат.помощ"` — кілька occ

Фактичні плани розбивались на 2 статті — фінансист не міг бачити загальний план «Штраф+матдопомога» одним рядком.

### Рішення

1. **Фінансист помітив на удаление** `000000060 "Штраф"` у Designer (через інтерфейс 1С).
2. **Додано алиас** `"Штраф": "Штраф/ мат помощь"` у config.py.
3. **Додано deny-list** `BLOCKED_ARTICLE_NAMES = {"Штраф"}` у config.py.
4. **Додано guard** у `scripts/11_upload_articles.py` (SKIP-BLOCKED перед mgr.СоздатьЭлемент).
5. **Перегенеровано** артефакти 02, 04, 08.
6. **Фінансист видалив** `000000060` фізично з 1С.

### Перевірка

```python
# data/json/02_unique_articles.json
'Штраф' як окрема стаття: 0
'Штраф/ мат помощь' occurrences: 847 (540 + 307 = усе одне)
```

```python
# data/json/05_mapping_pl_to_dds.json
mappings зі 'Штраф' як pl_name: 0
mappings зі 'Штраф/ мат помощь' як pl_name: 1 (ДДС=[Штраф, Материальная помощь])
```

```python
# data/json/08_documents_to_import.json
строки з article_name="Штраф": 0
строки з article_name="Штраф/ мат помощь": 843
```

При наступному запуску `11_upload_articles.py` навіть якщо хтось підкине вручну "Штраф" → guard виведе `SKIP-BLOCKED 'Штраф'` і стаття **не буде створена**.

### Lesson learned

Один шар захисту недостатній. Алиас — first line of defense (очищення на вході). Deny-list — last line of defense (захист на виході). Обидва шари треба тримати синхронно для **кожної** видаленої з 1С статті.
