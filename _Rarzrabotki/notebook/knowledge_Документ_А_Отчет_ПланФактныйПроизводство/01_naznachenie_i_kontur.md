## 1. Зачем понадобился контур

До 01.08.2026 план-факт производства существовал **только как расчёт на лету**.
`Отчеты.А_ПланФактныйПроизводствоПолный` — программная компоновка: `ПриКомпоновкеРезультата`
ставит `СтандартнаяОбработка = Ложь` (строка 44), функция `ПолучитьДанные(Период)` (строка 78)
собирает таблицу значений и отдаёт её в СКД внешним набором `"Детали"` (строка 53).
Ничего не сохраняется — таблица живёт только на время формирования отчёта.

Отсюда два ограничения, которые спека (§1) называет причиной работы:

1. **Данные нельзя вытянуть в Power BI.** Внешнего набора СКД в SQL нет; выгружать нечего.
2. **Нельзя сравнить «как было» с «как стало».** Каждый прогон пересчитывает историю заново,
   снимка на дату не остаётся.

Решение: **документ, проведение которого фиксирует ту же самую свёртку в регистр сведений**,
плюс новый отчёт поверх регистра и ETL в OLAP.

## 2. Документ-свёртка vs отчёт-на-лету

| | Отчёт `А_ПланФактныйПроизводствоПолный` | Документ `А_Отчет_ПланФактныйПроизводство` |
|---|---|---|
| Где считается | в памяти при каждом открытии | один раз при проведении |
| Где хранится | нигде | `РегистрСведений.А_ПланФактПроизводство_Свод` |
| Гранулярность обхода | цикл по всем подразделениям с активными СС (строки 105–112) | один документ = одно подразделение (реквизит `Подразделение`) |
| Производные показатели | считаются в финальном `ВЫБРАТЬ` запроса: `ОтклонениеЧасы` (337), `ПроцентЧасы` (340–343), `ЦенаПлан` (368–371), `ЦенаФакт` (372–375), `ПрогнозГрн` (362) | **не хранятся**, считаются на выводе |
| Глубина истории | ограничена параметром `Период` (по умолчанию `'00010101000000'`…`'39991231235959'`, строки 83 и 88) | «от начала времён до `КонецДня(Дата)`» — `Дата` документа = дата актуальности снимка |
| Повторный расчёт | безопасен всегда | перепроведение полностью замещает движения (`RegisterRecordsDeletion = AutoDelete`) |

🔴 **Правило периода — главный инвариант, унаследованный один в один.** В старом отчёте фильтр
`МЕЖДУ &НачП И &КонП` стоит **только** у фактовых веток: табель (строка 251), закупки (строка 284),
EV (строка 315). У плановых веток — работы (строки 184–190) и комплектующие (194–221) — фильтра
периода **нет вообще**. Поэтому в новом контуре факт и «Виконання» читаются **за выбранный период**,
а `План` и `ПланНаФакт` (ETC) — **целиком, без фильтра**. Если при доработке нового отчёта наложить
период на план, план «схлопнется» в ноль на любом коротком интервале, а `Відхилення` и прогноз
станут бессмысленными — при движении слайсера дат в Power BI план обязан стоять неподвижно.

## 3. Четыре решения пользователя (2026-08-01) и что из них следует

Спека §2 фиксирует ровно четыре решения. Каждое имеет техническое следствие, которое нельзя
«улучшить» задним числом:

| Решение | Следствие |
|---|---|
| **Периодичность: не помесячно.** Один документ на одно подразделение, отчёты накопительные с произвольным периодом (напр. 01.06.2026–24.07.2026) | 🔴 Регистр обязан хранить **датированные строки факта**: табель — `НАЧАЛОПЕРИОДА(Т.Период, ДЕНЬ)`, закупки — `НАЧАЛОПЕРИОДА(СТ.Период, ДЕНЬ)`, EV — `НАЧАЛОПЕРИОДА(ВРМ.Период, ДЕНЬ)`; план и ETC — `НАЧАЛОПЕРИОДА(Дата документа, ДЕНЬ)`. Без собственных дат у факта произвольный период отчёта невозможен в принципе |
| **Рабочий отчёт не трогать** | `А_ПланФактныйПроизводствоПолный` остаётся эталоном сверки; новый отчёт живёт рядом. Любая правка старого отчёта ломает регрессию этапа 3/5 (спека §5) |
| **Разрез по кошторису (СС) не добавлять** | В регистре только `Подразделение`. Плановые строки нескольких активных СС **складываются**: у «МД IRS 2026» 4 037,76 (15 м × 6 домов) + 6 838,86 (30 м × 7 домов) = **10 876,62** — ровно как в отчёте |
| **ETC («План на факт») материализовать** | ETC — не вычисляемая на выводе величина, а **отдельные строки регистра** с `ТипСтроки = ПланНаФакт` и ресурсом `ПланНаФактГрн`. Логика перенесена из `ЗаполнитьПланНаФакт` старого отчёта (строки 441–521) в модуль документа |

🔴 `НАЧАЛОПЕРИОДА(..., ДЕНЬ)` обязателен не «для красоты»: периодичность регистра — `Day`
(подтверждено в XML), платформа всё равно обрежет время, и две закупки одного дня с одинаковыми
измерениями дадут ошибку «Запись с такими ключевыми полями существует».

## 5. Что в контур НЕ входит и почему

- **`ПодразделениеОбъекта` (15 м / 30 м).** Не измерение и не реквизит регистра. У «МД IRS 2026»
  две активные СС с одинаковым набором из 44 работ: как реквизит поле было бы неоднозначным
  (две СС в одной записи-ключе), как измерение — не нужно ни одной из трёх настроек.
  В старом отчёте оно есть (строка 132 `СС.ПодразделениеОбъекта`), но заполнено только у плана и EV.
- **Разрез по кошторису (СС).** Явное решение пользователя «не добавлять» (спека §2).
- **Проценты, отклонения, цены, прогноз.** `ОтклонениеЧасы`, `ПроцентЧасы`, `ОтклонениеВиконання`,
  `ПроцентВиконання`, `ПроцентВиконанняФакт`, `ОтклонениеКол`, `ПроцентКол`, `ОтклонениеГрн`,
  `ПроцентГрн`, `ЦенаПлан`, `ЦенаФакт`, `ПрогнозГрн`, `ОтклонениеПрогнозГрн`, `ПроцентПрогнозГрн`
  в регистре отсутствуют. 🔴 Причина не «экономия места»: они **неаддитивны либо производны**.
  Сумма процентов по строкам не равна проценту суммы; сохранённый процент при любой другой
  группировке даст неверное число. Все они считаются на выводе из восьми хранимых ресурсов.
- **Гривны по труду.** Блок `1. Праця` — **только часы** (`ПланГрн = 0`): ветка ФОТ/ОЗФУ удалена
  из отчёта вечером 16.07.2026 (`KNOWLEDGE_MAP.md` старого отчёта, TL;DR п. 2). В контур она
  не переносилась.
- **Помесячные документы.** Их нет по решению пользователя; накопительность обеспечивают
  датированные строки факта, а не нарезка документов.
- **Правка рабочего отчёта `А_ПланФактныйПроизводствоПолный`.** Он эталон сверки. Обе его копии
  (конфигурационная `Reports\А_ПланФактныйПроизводствоПолный\...` и внешняя
  `_Rarzrabotki\Отчеты\А_ПланФактныйПроизводствоПолный.erf`) держатся синхронно —
  см. `knowledge_ПланФактныйПроизводствоПолный\KNOWLEDGE_MAP.md`, раздел «Файлы отчёта».

## 6. Инварианты старого отчёта, перенесённые в документ без изменений

Эти пять правил живут в звене 1 и являются причиной, по которой числа контура сходятся с эталоном.
Ломаются они тихо — расхождение видно только на сверке итогов.

| Инвариант | Где в старом отчёте |
|---|---|
| 🔴 Факт материалов — **брутто, с НДС**: ресурс `СТ.Стоимость`. `СтоимостьБезНДС`/`СтоимостьРегл`/`СтоимостьУпр` — все без НДС, а план (`Комплектующие.Сумма`) заведён с НДС | строка 274; ошибка уже допускалась и исправлялась |
| 🔴 Факт **не соединяется с `ВТ_СС`**: фактовые ветки соединяются с `ВТ_Подр1` (одна строка на подразделение) `ПО ИСТИНА` — иначе при двух активных СС факт удваивается (4 524 428,74 вместо 2 262 214,37) | `ВТ_Подр1` — строки 147–152; соединения — 247–248 и 277–278 |
| Факт материалов = **закупки**: `ВидДвижения = Приход`, `РазделУчета = ТоварыНаСкладах`, `Регистратор ССЫЛКА Документ.ПриобретениеТоваровУслуг`, подразделение — `ПодразделениеЗакупки` (fallback `Подразделение`) `В ИЕРАРХИИ` | строки 280–283; fallback — 133–137 |
| План труда — **только работы с единицей «чол/год»**; `ПланЧасы = Р.Количество × Домов`, где `Домов = ВЫБОР КОГДА СС.КоличествоДомов > 0 ТОГДА СС.КоличествоДомов ИНАЧЕ 1 КОНЕЦ` | фильтр — строка 190, множитель — 177, `Домов` — 138 |
| EV (`ВиконанняЧасы` = `ВРМ.ЧасыВыполнение`) множителем `КоличествоДомов` **не домножается** | строки 303 и 309 |

Правила ETC (приоритет менять нельзя, старый отчёт строки 483–496): `ПланГрн ≤ 0` → строки нет;
`ПланКол ≤ 0` → `Макс(0, ПланГрн − ФактГрн)`; `ФактКол ≤ 0` → `ПланГрн` **ровно**, без пересчёта
через среднюю цену (требование бухгалтера — «без игры с копейками»); иначе
`Макс(0, ПланКол − ФактКол) × (ПланГрн / ПланКол)`. Ключ нетто-группы — `Подразделение` +
нормализованное **имя** общего названия (`КлючГруппыПланНаФакт`, строки 529–547), **без** Этапа и
Категории: добавление Этапа завышало прогноз на 31 932,22 грн.
